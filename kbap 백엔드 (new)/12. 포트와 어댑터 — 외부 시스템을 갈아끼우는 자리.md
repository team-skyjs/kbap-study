# 12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리

> 작성: 2026-08-26 · 맥락: "포트와 어댑터", "헥사고날", "클린 아키텍처" 를 검색하면 **모든 것을 인터페이스로 감싸라**는 그림이 나온다. DB도, 캐시도, 외부 API도. 그런데 kbap-server 를 열면 **DB는 인터페이스로 감싸져 있지 않다** — 리포지토리가 그냥 public 이고 서비스가 직접 부른다. 반면 JWT·S3·SQS·OpenAI 는 전부 인터페이스 뒤에 있다. 이 노트는 그 **비대칭이 실수가 아니라 결정**임을 설명한다.
> 목표: 의존성 역전이 뭔지 설명할 수 있고, kbap 에서 **어떤 것이 포트 뒤에 있고 어떤 것이 없는지, 왜인지** 말할 수 있게 되기.

---

## 0. 한 줄 요약

kbap 은 **외부 시스템(JWT 라이브러리·Firebase·Redis·S3·SQS·OpenAI·구글 Places·환율 API)** 만 인터페이스 뒤에 숨긴다. 계약(`common.port.*`)은 Spring 도 JPA 도 모르는 순수 인터페이스고, 구현은 그걸 쓰는 모듈 안(`common.infra.*` 또는 `api.infra.*`)에, 조립은 config 에 둔다. **DB는 이 대상이 아니다** — 예전엔 감쌌다가 2026-07 에 걷어냈다.

---

## 1. 문제부터 — "외부 시스템" 이 왜 골칫거리인가

`ScanService` 가 메뉴판 사진을 OpenAI 비전 모델에 보내 메뉴명을 뽑는다고 하자. 가장 짧게 쓰면 이렇게 된다.

```kotlin
// 예시 — kbap 실코드 아님
@Service
class ScanService {
    private val chatModel = OpenAiChatModel.builder().apiKey(System.getenv("OPENAI_API_KEY")).build()

    fun scan(imageUrl: String): List<String> {
        val response = chatModel.call(/* ... */)
        return parse(response)
    }
}
```

동작은 한다. 문제는 **이 클래스가 이제 OpenAI 없이는 존재할 수 없다**는 점이다.

| 하고 싶은 일 | 위 코드에서 벌어지는 일 |
|---|---|
| 스캔 판정 로직만 테스트 | 테스트가 실제로 OpenAI 를 호출한다 — 느리고, 돈 들고, 네트워크가 죽으면 테스트가 죽는다 |
| 로컬에서 앱 띄우기 | `OPENAI_API_KEY` 없으면 부팅 실패 |
| 벤더 교체 | `ScanService` 를 뜯어고쳐야 한다 |

FE 로 옮기면 익숙한 그림이다. 화면 컴포넌트 안에서 바로 `fetch('https://api.…')` 를 부르면, 그 컴포넌트는 **서버가 떠 있어야만** 렌더 테스트가 된다. 그래서 보통 `api/client.ts` 로 뽑아낸다.

## 2. 의존성 역전(DIP) — 인터페이스를 **누가 소유하느냐**

`client.ts` 로 뽑아내는 것만으로는 아직 절반이다. 방향이 그대로이기 때문이다.

```
ScanService  ──────▶  OpenAiClient  ──────▶  OpenAI SDK
(중요한 로직)          (세부 기술)
```

화살표는 "이 파일이 저 파일을 import 한다" 다. 중요한 것(판정 로직)이 사소한 것(어떤 벤더를 쓰는지)에 **매달려 있다.** 벤더가 바뀌면 위쪽이 흔들린다.

**의존성 역전(Dependency Inversion Principle, DIP)** 은 이 화살표를 뒤집는다. 방법은 하나뿐이다 — **인터페이스를 쓰는 쪽이 소유한다.**

```
ScanService  ──────▶  MenuBoardVisionExtractor  ◀──────  OpenAiMenuBoardVisionExtractor
(중요한 로직)          (계약 = 포트)                        (세부 기술 = 어댑터)
```

이제 화살표 둘이 **모두 가운데를 향한다.** 구현이 계약을 향해 "나는 이 모양을 만족합니다" 라고 말하는 구조다. 원래 `ScanService → 구현` 이던 화살표가 `구현 → 계약` 으로 **역전**됐다고 해서 의존성 역전이다.

여기서 놓치기 쉬운 핵심: **인터페이스가 `com.openai` 패키지에 있으면 아무것도 역전되지 않는다.** 계약은 그것을 필요로 하는 쪽(우리 코드) 소유여야 한다. kbap 에서 `MenuBoardVisionExtractor` 가 `common.port.llm` 에 있고 `common.infra.llm` 에 없는 이유가 이것이다.

> **비유 ①: `client.ts` 를 타입으로 바꿔 테스트에 가짜를 꽂기**
>
> ```ts
> // 예시 — 계약
> export interface PlaceClient {
>   searchNearby(lat: number, lng: number): Promise<Place[]>
> }
> // 구현 A (실제)
> export const googlePlaceClient: PlaceClient = { async searchNearby(...) { return fetch(...) } }
> // 구현 B (테스트)
> export const fakePlaceClient: PlaceClient = { async searchNearby() { return [{ name: '김밥천국' }] } }
> ```
> 화면은 `PlaceClient` **타입**만 알고, 어느 구현이 들어올지는 위에서 정한다.
>
> **어디까지 같고 어디서부터 다른가**
> - 같은 것: **타입(계약)이 소비자 쪽에 있고, 구현은 나중에 꽂힌다**는 구조. 목적도 같다 — 테스트 대역과 교체 가능성.
> - 다른 것 1 — **꽂는 주체**. TS 는 보통 사람이 import 를 바꾸거나 인자로 넘긴다. Spring 은 컨테이너가 타입을 보고 알아서 꽂는다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]).
> - 다른 것 2 — **강제력**. TS 는 `interface` 를 안 쓰고 구현을 직접 import 해도 아무도 안 막는다. kbap 은 그걸 **테스트가 실패시킨다**([[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]).
> - 다른 것 3 — TS 의 `interface` 는 컴파일 후 사라진다. JVM 인터페이스는 런타임에 실존하는 타입이고, 컨테이너가 그 타입으로 빈을 찾는다.

## 3. "구현이 하나뿐인데 왜 인터페이스를 따로 두나?"

정당한 반문이다. 인터페이스 하나 = 파일 하나 = 읽을 때 한 번 더 점프다. 실제로 이 레포는 **바로 그 이유로 리포지토리 포트를 전부 없앴다**(§8). 그런데 남은 것들에는 값을 치를 이유가 세 개 있다.

### 3-1. 테스트 대역 — 실제로 쓰고 있다

포트가 있으니 테스트에서 가짜를 꽂는다. 실물이 있다.

```kotlin
class FakeExchangeRateClient : ExchangeRateClient {
    private val rates = mutableMapOf(
        CurrencyCode.KRW to BigDecimal("1.0000"),
        CurrencyCode.USD to BigDecimal("1400.5000"),
    )
    var failAll: Boolean = false

    override fun getKrwPerUnitOrNull(currency: CurrencyCode): BigDecimal? {
        if (failAll) return null
        return rates[currency]
    }
}
```
— `api/src/test/kotlin/com/kbap/api/scan/FakeExchangeRateClient.kt:9-24`

- `: ExchangeRateClient` — 실제 환율 API 어댑터와 **같은 계약**을 만족한다. 그래서 서비스는 차이를 모른다.
- `failAll` — 환율 조회가 실패하는 상황을 스위치 하나로 만든다. **실제 API 로는 재현할 수 없는 시나리오**다.
- 이 페이크가 없으면 스캔 테스트가 매번 외부 환율 서버를 때린다.

같은 방식의 페이크가 레포에 최소 5개 있다 — `FakeMenuBoardVisionExtractor`(비전 LLM), `FakePlaceSearchClient`(구글 Places), `FakePresignedUploadPortConfig`(S3), `ScenarioSocialTokenVerifierConfig`(Firebase), 위 환율. **포트 하나당 페이크 하나**라고 봐도 크게 틀리지 않는다.

### 3-2. 벤더 교체 — 실제로 두 번 일어났다

이게 가장 강한 근거다. 추측이 아니라 이 레포의 이력이다.

| 언제 | 무슨 일 | 계약은? |
|---|---|---|
| 2026-08-07 (KB-299) | 임베딩 seam(=포트, 갈아끼우는 이음매) `TextEmbeddingClient` 신설, 구현은 **AWS Bedrock Titan V2**(1024차원) | 신설 |
| 2026-08-13 (KB-328) | 임베딩을 **OpenAI `text-embedding-3-small`(256차원)** 로 교체, AWS 의존 소거 | **그대로** |
| KB-320 | 채팅·비전을 여러 벤더 fan-out 에서 **OpenAI 단일**로 정리, Upstage·Gemini 코드 삭제 | **그대로** |
| 2026-08-19 (KB-350) | 장소 검색을 **카카오 로컬 → 구글 Places (New)** 로 교체 | **바뀌었다** — 아래 참조 |

임베딩 벤더가 AWS → OpenAI 로 통째로 바뀌었는데, 그 벡터를 쓰는 배치 코드(`batch/vector/FoodVectorSyncItemProcessor.kt:18`)는 **한 줄도 바뀌지 않았다.** 바뀐 건 어댑터 클래스와 조립 config 뿐이다. 계약이 없었다면 배치 프로세서가 Bedrock SDK 를 직접 import 하고 있었을 테고, 교체는 그 파일까지 번졌을 것이다.

그런데 **항상 이렇게 깔끔하진 않다.** 세 번째 교체 사건이 그걸 보여준다.

> [!example] 실제 교체 해부 — 카카오 → 구글 (KB-350, 2026-08-19, 커밋 `9cfbe180`)
> `api.infra.place` 는 원래 **카카오 로컬 API** 였다. 지금은 구글 Places API (New) 다. 커밋 하나에서 `KakaoLocalApi.kt`·`KakaoPlaceSearchClient.kt` 가 삭제되고 `GooglePlacesApi.kt`·`GooglePlaceSearchClient.kt` 가 들어왔다. 총 16파일 484줄 추가 / 442줄 삭제.
>
> **포트가 막아준 것 — 벤더 기술의 확산**
> 바뀐 16파일 중 구글 HTTP 타입(`X-Goog-Api-Key`·FieldMask·`places:searchNearby`)을 아는 파일은 **`api/infra/place/` 안의 2개뿐**이다. `PlaceService` 도, 컨트롤러도, 테스트 대역도 구글이라는 단어를 모른다. 카카오 시절에도 몰랐다. 벤더 SDK 는 어댑터 안에 **갇혀 있었고, 갇힌 채로 교체됐다.**
>
> **포트가 못 막은 것 — 추상화 누수**
> 그런데 계약 자체가 바뀌었다(`common/port/place/PlaceSearchClient.kt`, 4줄 추가 / 7줄 삭제):
> ```kotlin
> // 전 — 카카오 시절
> fun searchNearby(query: String, longitude: BigDecimal, latitude: BigDecimal): List<FoundPlace>
> fun searchPage(query: String, …, page: Int): PlaceSearchPage
> data class PlaceSearchPage(val items: List<FoundPlace>, val hasNext: Boolean)
>
> // 후 — 구글
> fun searchNearbyRestaurants(longitude, latitude, lang: LanguageCode): List<FoundPlace>
> fun searchByKeyword(query, longitude, latitude, lang: LanguageCode): List<FoundPlace>
> ```
> `PlaceSearchPage`·`page`·`hasNext` 는 **카카오의 페이징 모델**이었다. 벤더 중립이라 믿었지만 실은 한쪽 벤더의 개념이 계약에 스며 있었고, 구글엔 그게 없어서 포트째 잘려나갔다.
>
> 계약이 바뀌자 **계약을 쓰는 모든 층이 따라 바뀌었다** — `PlaceService.kt`(두 메서드 시그니처 전부), `PlaceController.kt`, `PlaceSearchRequest/Response.kt`(`page` 파라미터·`hasNext` 필드 제거, `lang` 필수 추가), `FakePlaceSearchClient.kt`(새 계약으로 재작성). **앱이 호출하는 HTTP 응답 모양까지 바뀌었다.**
>
> **그래서 정직한 결론**
> "포트를 두면 공짜로 갈아끼워진다" 는 과장이다. 포트의 값어치는 **"변경이 없다"** 가 아니라 **"변경이 어디까지 번지는지 예측 가능하다"** 는 쪽이다. 벤더 기술은 어댑터에 갇혔고(§4 의 3분할이 한 일), 벤더의 *개념*은 계약을 타고 번졌다. 포트를 설계할 때 **"이 시그니처에 저쪽 벤더의 사정이 들어 있지 않나"** 를 의심해야 하는 이유다 — `TextEmbeddingClient` 가 두 줄로 끝나서 무사했던 것과 대비된다.

> [!tip] 이 노트에서 하나만 가져간다면
> "구현이 하나뿐인데 인터페이스가 필요한가?" 의 답은 **"지금 하나인가" 가 아니라 "바뀔 자리인가"** 다. 외부 벤더는 우리가 통제하지 않는다 — 가격이 바뀌고, API 가 deprecate 되고, 팀이 벤더를 정리한다. DB 는 통제한다.

### 3-3. 미설정 폴백 — 없어도 부팅한다

로컬에서 Firebase 자격증명이 없다고 서버가 못 뜨면 개발이 안 된다. 계약이 있으면 **"항상 거절하는 구현"** 을 꽂아 넘길 수 있다.

```kotlin
    @Bean
    fun socialTokenVerifier(
        @Value("\${kbap.auth.firebase.credentials-json:}") credentialsJson: String,
        @Value("\${kbap.auth.firebase.credentials-path:}") credentialsPath: String,
    ): SocialTokenVerifier {
        val verifier = FirebaseSocialAuth.tokenVerifierOrNull(credentialsJson, credentialsPath)
        if (verifier == null) {
            log.warn("Firebase 자격증명 미설정 — 소셜 로그인 비활성(모든 로그인이 401 로 거절된다)")
            return UnavailableSocialAuth
        }
        return verifier
    }
```
— `api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:25-37`

- 반환 타입이 `SocialTokenVerifier`(**포트**) 다 — 진짜 Firebase 검증기든 `UnavailableSocialAuth` 든 소비자에겐 같은 타입이다.
- `AuthService` 는 자기가 어느 쪽을 받았는지 모른다. 알 필요도 없다.

## 4. kbap 의 3분할 규약 — 계약 / 구현 / 조립

레포 규약(`CLAUDE.md:13`, ADR-0018 `docs/adr/0018-dissolve-infra-modules-into-consumers.md`)은 외부 시스템 하나를 **세 자리**로 나눈다.

| 자리 | 어디에 | 무엇이 | 규칙 |
|---|---|---|---|
| **계약(seam)** | `common.port.<영역>` | 인터페이스 + 그 인터페이스가 주고받는 데이터 클래스 | **Spring·JPA 를 모른다.** 애너테이션 0개. ArchUnit 강제 |
| **구현(어댑터)** | batch 도 쓰면 `common.infra.*`<br>api 전용이면 `api.infra.*` | SDK 를 실제로 부르는 클래스 | 벤더 SDK import 는 여기서만 |
| **조립** | `api.core.config` / `batch.config` | 어느 구현을 빈으로 만들지 결정 | **구현 클래스 이름을 직접 쓸 수 있는 유일한 자리**(+ 어댑터 자신). ArchUnit 강제 |

`common.infra` 냐 `api.infra` 냐를 가르는 질문은 딱 하나다 — **"batch 도 쓰나?"** batch 가 안 쓰는 SDK(firebase·jjwt·redis·s3)를 `:common` 에 두면 batch 클래스패스에까지 실린다. 그래서 그것만 `api.infra` 에 둔다(ADR-0018 "Alternatives Considered" 3번째 항목).

### 왜 모듈이 아니라 패키지인가

2026-08-14 이전에는 어댑터마다 Gradle 모듈(`:infra:llm`·`:infra:auth`…)이 있었다. 지금은 없다. ADR-0018 의 이유:

- 어댑터 6종 중 **4종이 1~2파일**이었다. 모듈 하나의 존재 비용(빌드 파일·settings 등록·jacoco 배선)이 격리 이득을 넘었다.
- 대신 **컴파일 타임 격리가 테스트 타임 격리로 격하**됐다 — api 기능 코드가 jjwt 를 import 해도 **컴파일은 통과하고**, `ModuleBoundaryTest` 가 잡는다. ADR 이 이 손실을 명시적으로 기록해 뒀다.

모듈이 3개로 접힌 경위는 [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] 가 정본이다.

## 6. 어댑터 실물 — "계약 ↔ 구현 ↔ 조립" 3점 세트

### 6-1. Redis refresh 토큰 — 조립 config 가 **없는** 경우

**① 계약** — `common/src/main/kotlin/com/kbap/common/port/auth/RefreshTokenStore.kt:5-12`
```kotlin
interface RefreshTokenStore {
    fun save(jti: String, memberId: Long, ttl: Duration)

    // 원자적 소비(조회+삭제) — rotation 경합 방어.
    fun consume(jti: String): Long?

    fun delete(jti: String)
}
```
- import 가 `java.time.Duration` **하나뿐**이다. Redis 라는 단어가 없다.
- `consume` 은 "조회하고 지운다" 를 **한 동작으로** 규정한다 — 이 원자성이 계약의 일부다. 왜 원자성까지 계약에 적었는지는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]] 가 답한다 — 리프레시 회전은 "쓴 토큰은 즉시 죽는다"가 전제라, 조회와 삭제 사이에 틈이 있으면 같은 refresh 로 두 번 재발급받는 경합이 열린다.

**② 구현** — `api/src/main/kotlin/com/kbap/api/infra/redis/RedisRefreshTokenStore.kt:8-23`
```kotlin
@Component
class RedisRefreshTokenStore(
    private val redisTemplate: StringRedisTemplate,
) : RefreshTokenStore {
    override fun consume(jti: String): Long? =
        redisTemplate.opsForValue().getAndDelete(key(jti))?.toLongOrNull()

    private fun key(jti: String): String = "$KEY_PREFIX$jti"
```
- `getAndDelete` — 계약이 요구한 원자성을 Redis 명령 하나로 지킨다.
- 키 접두사(`auth:refresh:`)라는 **Redis 세계의 지식이 여기 갇혀 있다.** 포트 쪽엔 새어 나가지 않는다.

**③ 조립** — 없다. `@Component`(8번 줄) 하나로 끝난다. 구현이 하나뿐이고 조건도 없으면 컴포넌트 스캔이 그대로 빈으로 만든다. **"조립은 config 에서" 규칙은 config 파일을 반드시 만들라는 뜻이 아니라, 구현 클래스 이름을 직접 쓰는 곳을 config 로 제한한다는 뜻이다** — `@Component` 는 아무도 그 이름을 쓰지 않으니 규칙에 걸리지 않는다.

Redis 를 kbap 이 어디에 쓰는지는 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식]]에서 다룬다.

### 6-2. S3 presigned 업로드 — 조건부 조립 + 로컬 페이크

**① 계약** — `common/src/main/kotlin/com/kbap/common/port/storage/PresignedUploadPort.kt:6-8`
```kotlin
interface PresignedUploadPort {
    fun issue(key: String, contentType: String, contentLength: Long, ttl: Duration): PresignedUpload
}
```
- 반환 타입 `PresignedUpload` 도 포트 소속이다(`PresignedUpload.kt:5-11` — `uploadUrl`·`requiredHeaders`·`publicUrl`·`objectKey`·`expiresAt`). AWS SDK 타입을 그대로 반환했다면 SDK 가 계약을 뚫고 나온다.

**② 구현** — `api/src/main/kotlin/com/kbap/api/infra/storage/S3PresignedUploadAdapter.kt:11-19`
```kotlin
class S3PresignedUploadAdapter(
    private val presigner: S3Presigner,
    private val bucket: String,
    private val publicBaseUrl: String,
) : PresignedUploadPort {
    companion object {
        fun create(region: String, bucket: String, publicBaseUrl: String): PresignedUploadPort =
            S3PresignedUploadAdapter(S3Presigner.builder().region(Region.of(region)).build(), bucket, publicBaseUrl)
    }
```
- `create` 의 **반환 타입이 `PresignedUploadPort`** 다. 팩토리조차 구체 타입을 내보내지 않는다.
- `@Component` 가 없다 — 리전·버킷을 프로퍼티에서 받아야 해서 config 가 직접 만든다.

**③ 조립** — `api/src/main/kotlin/com/kbap/api/core/config/StorageConfig.kt:14-28`
```kotlin
@Configuration
@ConditionalOnProperty(prefix = "kbap.storage", name = ["enabled"], havingValue = "true")
class StorageConfig {
    @Bean
    fun presignedUploadPort(
        @Value("\${kbap.storage.region}") region: String,
        …
    ): PresignedUploadPort = S3PresignedUploadAdapter.create(region, bucket, publicBaseUrl)
}
```
- `@ConditionalOnProperty` — `kbap.storage.enabled=true` 인 환경(dev·prod)에서만 이 config 자체가 살아난다. 로컬·테스트에선 **빈이 아예 없다.**
- 그 빈자리를 테스트가 페이크로 채운다(`api/src/test/kotlin/com/kbap/api/image/FakePresignedUploadPortConfig.kt:13-25`).
- 소비자는 계약만 받는다 — `api/src/main/kotlin/com/kbap/api/image/PresignedUploadService.kt:16` 의 `private val port: PresignedUploadPort`. 이 서비스는 자기가 S3 를 쓰는지 페이크를 쓰는지 모른다.

presigned URL 이 왜 이런 모양인지(클라가 S3 로 직접 올리는 이유, 서명에 뭐가 들어가는지)는 [[S3 presigned URL과 클라이언트 시크릿]] 이 다룬다. 이 흐름의 서버 쪽 전체 경로는 [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]].

### 6-3. OpenAI 임베딩 — batch 도 쓰므로 `common.infra`

**① 계약** — `common/src/main/kotlin/com/kbap/common/port/llm/TextEmbeddingClient.kt:3-5`
```kotlin
fun interface TextEmbeddingClient {
    fun embed(texts: List<String>): List<FloatArray>
}
```
- 계약 전체가 **두 줄**이다. "문자열 목록을 넣으면 같은 순서로 벡터 목록이 나온다" — 벤더도, 차원 수도, 모델명도 계약에 없다. 그래서 §3-2 의 Bedrock → OpenAI 교체가 계약을 건드리지 않았다.
- `fun interface` — 메서드가 하나뿐인 인터페이스라 람다로도 구현할 수 있다(Kotlin 의 SAM 변환).

**② 구현** — `common/src/main/kotlin/com/kbap/common/infra/llm/embedding/OpenAiTextEmbeddingClient.kt:9-23`
```kotlin
class OpenAiTextEmbeddingClient(
    private val props: LlmModelProperties.EmbeddingProps,
    baseUrl: String = props.baseUrl ?: OPENAI_BASE_URL,
) : TextEmbeddingClient {
    private val embeddingModel: OpenAiEmbeddingModel by lazy {
        OpenAiEmbeddingModel(
            OpenAiEmbeddingOptions.builder()
                .apiKey(requiredApiKey())
                .model(props.model)
                .dimensions(props.dimension)
                .build(),

    }
```
- `by lazy` — 실제로 임베딩을 부를 때까지 모델 객체를 만들지 않는다. API 키 없이 빈이 만들어져도 부팅은 통과한다.
- 차원 수 검증이 구현 안에 있다(`:32-34`, 응답 차원이 설정과 다르면 예외). 계약은 그런 게 있는 줄 모른다.

**③ 조립** — `common/src/main/kotlin/com/kbap/common/infra/llm/config/LlmConfiguration.kt:54-57`
```kotlin
    @Bean
    @ConditionalOnProperty(prefix = "kbap.llm.embedding", name = ["enabled"], havingValue = "true")
    fun textEmbeddingClient(properties: LlmModelProperties): TextEmbeddingClient =
        OpenAiTextEmbeddingClient(properties.embedding)
```

**왜 `common.infra` 인가**: `llm` 은 api 와 batch 가 **둘 다** 쓰는 유일한 어댑터 영역이다 — 비전은 api 가(`api/scan/ScanService.kt:27`), 임베딩은 batch 가(`batch/vector/FoodVectorSyncItemProcessor.kt:18`) 쓴다. 그래서 `:common` 에 있고, 나머지 어댑터(auth·redis·storage·place·exchange)는 api 전용이라 `api.infra` 에 있다.

### 6-4. SQS — 조립이 config 패키지 밖에 있는 예외

`common.infra.mq.SqsFoodContentEventPublisher` 는 batch 가 쓰는데, 조립이 `batch.config` 가 아니라 **`batch.outbox`** 안에 있다.

## 7. 방향 규칙 — 포트는 도메인을 알아도 되고, 도메인은 포트를 알면 안 된다

레포 규약 한 줄(`CLAUDE.md:28`): **"포트가 도메인 타입을 반환하는 방향은 허용, 도메인이 포트를 아는 역방향은 금지."**

실물로 보면 이렇다.

```kotlin
interface TokenIssuer {
    fun issueAccessToken(memberId: Long, role: MemberRole): String
```
— `common/src/main/kotlin/com/kbap/common/port/auth/TokenIssuer.kt:6-7`

`MemberRole` 은 도메인 타입(`common.domain.member.model`)이다. 포트가 도메인을 **import 했다.** 이건 허용이다. 반대로 `Member` 엔티티가 `TokenIssuer` 를 필드로 갖는 건 금지다.

### 왜 이 방향인가

```
    common.domain  ◀──── common.port  ◀──── common.infra / api.infra
    (엔티티·도메인 로직)    (계약)              (SDK 호출)
```

화살표가 **한 방향으로만** 흐른다. 그래서:

- **도메인만 떼어 읽을 수 있다.** `Food` 를 읽는데 OpenAI 가 튀어나오지 않는다.
- **테스트가 가볍다.** 도메인 테스트에 어떤 외부 시스템도 준비할 필요가 없다.
- **순환이 생기지 않는다.** 도메인이 포트를 알고 포트가 도메인을 알면 두 패키지가 서로를 필요로 하는 매듭이 된다 — 하나를 이해하려면 항상 둘 다 읽어야 한다.

이 방향을 어기면 무슨 일이 나느냐가 아니라, **어기면 테스트가 빨간불이 된다**는 게 kbap 의 답이다.

```kotlin

                noClasses().that().resideInAPackage(sharedDomain)
                    .should().dependOnClassesThat().resideInAnyPackage(
                        "com.kbap.common.port..",
```
— `api/src/test/kotlin/com/kbap/api/architecture/ModuleBoundaryTest.kt:75-78`

이 테스트를 포함해 경계를 지키는 규칙 전체는 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 가 정본이다.

## 8. 그런데 DB 는 왜 포트가 아닌가 — 이 노트에서 가장 중요한 절

인터넷의 포트&어댑터 그림에는 거의 항상 **`MemberRepository` 인터페이스 → `MemberRepositoryAdapter` 구현** 이 있다. kbap 에도 있었다. **지금은 없다.**

### 예전 모습 (2026-07-13 이전)

회원 하나를 다루는 데 조각이 다섯이었다 — 도메인 모델 `Member`, 포트 `MemberRepository`, JPA 엔티티 `MemberJpaEntity`, Spring Data 리포지토리 `MemberJpaRepository`, 어댑터 `MemberRepositoryAdapter`. 게다가 두 모듈에 흩어져 있었다.

### 왜 걷어냈나 (ADR-0012, `docs/adr/0012-dissolve-persistence-module-and-ports.md`)

ADR 의 문장을 그대로 옮기면 — *"이 구조가 사주는 것은 '영속 기술 교체 가능성' 과 '페이크 리포지토리 단위 테스트' 다. 그러나 영속 기술 교체는 일어나지 않았고 (…) 반면 비용은 매일 냈다."*

**보험료는 매일 내는데 사고는 안 났다**는 이야기다. §3-2 의 LLM 벤더 교체와 정반대다.

| | 외부 벤더(LLM·S3·환율…) | DB(MySQL) |
|---|---|---|
| 누가 통제하나 | **저쪽** — 가격·API·모델이 우리 허락 없이 바뀐다 | **우리** |
| 실제 교체 빈도 | 이 레포에서 최소 3회(§3-2) | 0회 |
| 페이크로 테스트하기 | 쉽다(응답 몇 줄) | 어렵다 — 쿼리·제약·트랜잭션까지 흉내 내야 진짜가 된다 |
| 대안 | 없음 | **Testcontainers 로 진짜 MySQL 을 띄운다** |

마지막 줄이 결정타다. 페이크 리포지토리로 테스트해 봐야 진짜 DB 가 거절할 제약을 통과시킨다. ADR-0012 는 그래서 페이크 포트 단위 테스트를 **Testcontainers 통합 테스트로 흡수**시켰다.

### 2단계로 더 걷어냈다 (ADR-0014, `docs/adr/0014-relax-persistence-encapsulation.md`)

ADR-0012 는 포트를 없애는 대신 엔티티·리포지토리를 Kotlin `internal` 로 감추고 **도메인 서비스 하나를 유일한 공개 창구**로 뒀다. 이것도 2026-07-22 에 풀렸다 — 리포지토리만 필요한 소비자(배치)가 **위임만 하는 창구 서비스**를 만들게 됐고, 그 창구엔 도메인 로직이 없어서 "캡슐화가 지키는 실질이 없었다."

지금은 **엔티티가 곧 도메인 모델이고 리포지토리는 public** 이다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]).

> [!warning] ADR-0014 가 함께 기록한 대가
> *"컴파일러가 막아 주던 '도메인 서비스 우회' 가 가능해졌다 — 도메인 로직을 소비 계층에 쓰는 실수는 **이제 리뷰가 잡아야 한다**."*
> 리포지토리가 public 이라고 해서 컨트롤러가 리포지토리를 직접 불러도 된다는 뜻이 아니다. 그건 이제 **테스트도 컴파일러도 못 막는** 규율의 영역이다. 계층 규약은 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]].

### 그래서 남은 문장

> **모든 걸 역전시키지 않는다. 갈아끼울 가능성이 실재하는 곳만 역전시킨다.**

두 ADR 이 "축소" 로 보이지만, 실제로 일어난 건 **포트의 정의가 좁아진 것**이다. 예전엔 "우리 코드 밖의 모든 것", 지금은 **"우리가 통제하지 않는 외부 시스템"**.

## 9. 설정 홀더는 계약이 아니다

`JwtTokenProperties`(비밀키·토큰 만료시간)는 JWT 어댑터가 반드시 필요로 한다. 그렇다면 포트일까? 아니다 — `api.infra.auth.token` 소속이다.

```kotlin
data class JwtTokenProperties(
    val secret: String,
    val accessTtl: Duration,
    val refreshTtl: Duration,
) {
    init {
        require(secret.toByteArray().size >= MIN_SECRET_BYTES) {
            "kbap.auth.jwt.secret 는 ${MIN_SECRET_BYTES}바이트 이상이어야 합니다"
        }
    }
```
— `api/src/main/kotlin/com/kbap/api/infra/auth/token/JwtTokenProperties.kt:5-14`

- **애너테이션이 하나도 없다.** `@ConfigurationProperties` 도 `@Component` 도 없는 순수 Kotlin data class 다.
- `init` 블록이 32바이트 미만 비밀키를 **생성 시점에** 거절한다 — 이건 jjwt 의 HMAC-SHA256 요구사항이지, 우리 도메인의 규칙이 아니다.

조립은 config 가 `@Value` 로 한다.

```kotlin
    @Bean
    fun authTokenProperties(
        @Value("\${kbap.auth.jwt.secret}") secret: String,
        @Value("\${kbap.auth.jwt.access-ttl}") accessTtl: Duration,
        @Value("\${kbap.auth.jwt.refresh-ttl}") refreshTtl: Duration,
    ): JwtTokenProperties = JwtTokenProperties(secret = secret, accessTtl = accessTtl, refreshTtl = refreshTtl)
```
— `api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:18-23`

**판별 기준**은 간단하다.

| 질문 | 계약(포트) | 설정 홀더 |
|---|---|---|
| 소비자가 이걸 받나? | 예 — `AuthService` 가 `TokenIssuer` 를 주입받는다 | 아니오 — `JwtTokenIssuer` 만 받는다(`JwtTokenIssuer.kt:17-18`) |
| 구현을 바꾸면 이것도 바뀌나? | 아니오 | **예** — jjwt 를 버리면 `secret`·TTL 모양도 함께 사라진다 |
| 어느 세계의 지식인가 | 우리 | 벤더 |

즉 설정 홀더는 **계약의 일부가 아니라 구현의 부품**이다. 포트에 두면 "우리 코드가 jjwt 의 비밀키 요구사항을 안다" 는 상태가 되어 역전이 깨진다.

프로퍼티·프로필·`@ConfigurationProperties` 자체는 [[6. 설정과 프로필, 트랜잭션 경계]] 가 정본이다(참고로 이 레포에서 `@ConfigurationProperties` 를 단 클래스는 `FoodVectorProperties`·`LlmModelProperties` 둘뿐이다).

## 10. 주의점 · 헷갈리는 것들

> [!warning] 포트를 새로 만들기 전에 물어볼 것
> 1. **외부 시스템인가?** DB·같은 앱 안의 다른 서비스는 대상이 아니다. 우리가 통제하지 않는 것만.
> 2. **batch 도 쓰나?** 예 → `common.infra`, 아니오 → `api.infra`. 이 한 질문이 위치를 결정한다.
> 3. **계약에 벤더 타입이 새지 않나?** 반환 타입이 SDK 클래스면 포트가 아무것도 막지 못한다. `PresignedUpload` 처럼 우리 data class 를 만든다.

- **`api.infra` 는 "api 계층" 이 아니다.** 이름은 `api` 지만 계층이 아니라 **모듈 이름**이다(`:api` 모듈 안이라는 뜻). 계층 얘기는 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]].
- **`common.port` 에 `@Component` 를 붙이지 마라.** 포트는 Spring 을 몰라야 한다 — ArchUnit `ModuleBoundaryTest.kt:230-237` 이 잡는다. 빈이 되는 건 구현이다.
- **구현 클래스를 서비스에 주입하지 마라.** `private val store: RedisRefreshTokenStore` 는 컴파일은 되지만 `ModuleBoundaryTest.kt:210-220` 이 실패한다. 타입은 `RefreshTokenStore` 로 쓴다.
- **포트가 하나뿐인 구현을 가진다고 지우지 마라.** §3 의 세 이유(테스트 대역·벤더 교체·미설정 폴백) 중 하나라도 걸리면 값을 한다. 걸리는 게 없으면 그건 애초에 외부 시스템이 아닐 가능성이 높다.
- **"클린 아키텍처 노트" 를 찾고 있었다면**: 이 레포에 `:persistence` 모듈도, `:core:kernel` 도, 도메인↔엔티티 변환(`toDomain`/`from`)도 없다. 전부 2026-07 에 걷혔다(ADR-0012·0014·0016). 남은 것은 이 노트의 범위 — **외부 시스템 seam** 뿐이다.

```
common/src/main/kotlin/com/kbap/common/port/     ← 계약 7영역 16인터페이스 (Spring·JPA import 금지)
  auth/     TokenIssuer TokenParser SocialTokenVerifier SocialAccountDeleter RefreshTokenStore
  llm/      MenuBoardVisionExtractor FoodImageBatchClient TextEmbeddingClient
  storage/  StorageObjectStore PresignedUploadPort
  mq/       FoodContentEventPublisher
  place/    PlaceSearchClient ReverseGeocoder
  scan/     ScanTicketManager ScanReservationStore      ← CLAUDE.md 에 없음
  exchange/ ExchangeRateClient                          ← CLAUDE.md 에 없음

common/…/common/infra/    ← batch 도 쓰는 구현: llm(OpenAI) mq(SQS)
api/…/api/infra/          ← api 전용 구현: auth(jjwt·firebase) redis storage(S3) place(Google) exchange

조립 = api.core.config.* / batch.config.* (+ batch.outbox — ArchUnit 명시 예외)
```

| 상황 | 이렇게 |
|---|---|
| 새 외부 시스템을 붙인다 | `common.port.<영역>` 에 인터페이스 → 소비자 기준으로 infra 선택 → config 에서 조립 |
| 테스트에서 외부 호출을 끊고 싶다 | 포트를 구현한 `Fake*` 클래스 + `@Configuration`(`FakeExchangeRateClient.kt` 형태) |
| 미설정이면 빈을 안 만들고 싶다 | `@ConditionalOnProperty`(`StorageConfig.kt:15`) |
| 테스트가 먼저 등록하면 양보하고 싶다 | `@ConditionalOnMissingBean`(`ExchangeConfig.kt:13`) |
| 미설정이어도 부팅은 시키고 싶다 | 항상 실패하는 구현을 반환(`AuthConfig.kt:33` 의 `UnavailableSocialAuth`) |
| DB 접근이 필요하다 | 포트 만들지 마라. 리포지토리를 직접 쓴다(ADR-0014) |
| 포트 목록이 궁금하다 | `ls common/src/main/kotlin/com/kbap/common/port/` — 문서 말고 디렉터리 |

## 12. 용어집

| 용어 | 뜻 | FE 로 치면 |
|---|---|---|
| 의존성 역전(DIP) | 인터페이스를 **쓰는 쪽**이 소유해서, 구현이 계약을 향하게 만드는 것 | 화면이 `PlaceClient` 타입만 알고, 어느 구현을 쓸지는 밖에서 정하는 것 |
| 포트(port) / seam | 외부 시스템과 우리 코드가 맞닿는 **계약 인터페이스** | `client.ts` 가 export 하는 `interface` |
| 어댑터(adapter) | 그 계약을 실제 SDK 로 구현한 클래스 | `fetch` 로 진짜 API 를 부르는 구현체 |
| 조립(assembly) | 어느 어댑터를 빈으로 쓸지 결정하는 코드 | 루트에서 Provider 에 실제 구현을 넣는 자리 |
| 테스트 대역(test double) | 진짜 대신 꽂는 가짜 구현 | msw 핸들러, 목 객체 |
| 헥사고날 아키텍처 | 포트&어댑터의 다른 이름(Cockburn, 2005) | — |

## 13. 체크리스트

- [ ] 의존성 역전이 "인터페이스를 누가 소유하느냐" 의 문제임을 한 문장으로 말할 수 있다
- [ ] 계약·구현·조립 세 자리가 각각 어느 패키지인지 안다
- [ ] `common.infra` 와 `api.infra` 를 가르는 질문 하나("batch 도 쓰나?")를 안다
- [ ] `common/…/port/` 를 직접 `ls` 해 봤고, `scan`·`exchange` 가 레포 문서에 없다는 걸 확인했다
- [ ] "구현이 하나뿐인데 왜?" 에 세 가지 이유(테스트 대역·벤더 교체·미설정 폴백)로 답할 수 있다
- [ ] 임베딩이 Bedrock → OpenAI 로 바뀌었을 때 배치 코드가 안 바뀐 이유를 설명할 수 있다
- [ ] 왜 DB 는 포트로 감싸지 않는지 ADR-0012 의 논리(보험료 vs 사고율)로 말할 수 있다
- [ ] `JwtTokenProperties` 가 포트가 아닌 이유를 판별 기준 3개로 설명할 수 있다
- [ ] 포트가 도메인 타입을 반환하는 건 되고 역방향은 안 되는 이유를 안다
- [ ] `api/infra/redis/RedisRefreshTokenStore.kt` 와 `common/port/auth/RefreshTokenStore.kt` 를 나란히 열어 봤다
