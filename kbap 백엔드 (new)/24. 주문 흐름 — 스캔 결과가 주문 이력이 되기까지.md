# 24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지

> 작성: 2026-08-27 · 맥락: [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 는 "연관관계를 안 쓰면 조합을 손으로 한다"를 **원리로** 설명했다. 주문은 그 원리가 가장 길게 늘어난 실물이다 — **주문 → 주문항목 → 음식 → 이미지** 네 단계가 전부 `Long` id 로만 이어져 있고, 그걸 붙이는 손동작이 `OrderService` 안에 그대로 적혀 있다.
> 목표: ① 주문 상세 응답 하나를 만드는 데 **쿼리가 정확히 몇 번** 나가는지 세고, 그 숫자가 왜 **주문 항목 개수와 무관한지** 설명할 수 있게 되기 ② "스캔 1회당 주문 1회"를 **애플리케이션 검사 + DB 유니크 제약 두 겹**으로 지키는 이유를 말할 수 있게 되기 ③ 외부 API 호출(역지오코딩)이 왜 서비스가 아니라 **컨트롤러**에 있는지 짚을 수 있게 되기.

---

## 0. 한 줄 요약

주문 저장은 **스캔에 썼던 이미지 경로(`imagePath`)를 주문의 신분증으로 삼아** 항목들을 스냅샷으로 굳히는 일이고, 그 경로에 걸린 `UNIQUE` 제약이 "메뉴판 한 장 = 주문 한 건"을 DB 레벨에서 못박는다. 조회는 **연관관계 없이** 주문 → 항목 → 음식을 각각 `IN` 한 번씩으로 긁어와 메모리에서 붙이므로, 목록이든 상세든 **쿼리는 항상 3번**이다.

---

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 로 치면 |
|---|---|---|
| 스냅샷(snapshot) 저장 | 참조만 남기지 않고, 그 순간의 값을 복사해 함께 저장하는 것 | 주문 확정 화면에서 상품명·가격을 그 시점 값으로 굳혀 두는 것. 나중에 상품 가격이 바뀌어도 영수증은 안 바뀐다 |
| 유니크 제약(UNIQUE constraint) | 한 컬럼에 같은 값이 두 번 들어오는 걸 DB 가 거부하는 규칙 | 없음. FE 에는 "동시에 두 번 눌러도 한 번만"을 보장해 주는 장치가 없어서 버튼을 disable 한다 |
| `saveAndFlush` | 저장을 **지금 즉시** DB 로 밀어 넣기 | `await`. `save` 는 "나중에 보낼게", `saveAndFlush` 는 "지금 보내고 결과 볼게" |
| 배치 로딩 | id 를 다 모아 `IN` 한 번으로 가져와 메모리에서 붙이는 것 | 목록 렌더 전에 `Promise.all` 로 한 번에 받아 `Map` 으로 만들어 두는 것 |
| 역지오코딩(reverse geocoding) | 위도·경도 → 사람이 읽는 주소 | `expo-location` 의 `reverseGeocodeAsync` 와 같은 일. 여기선 서버가 한다 |

용어 정의가 필요하면 앞 노트로: `@Transactional` 은 [[6. 설정과 프로필, 트랜잭션 경계]], `BaseResponse`·`ErrorCode` 는 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]], `BaseEntity`·소프트삭제는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]].

## 3. 주문은 어디서 오나 — 스캔과의 이음매

계획서를 확인하러 온 사람을 위해 먼저 답부터: **주문은 스캔이 자동으로 만들어 주지 않는다.** 서버가 스캔 결과를 들고 있다가 "주문됨"으로 바꾸는 상태 전이 같은 건 없다. 사용자가 스캔 결과 화면에서 **고른 것만** 클라이언트가 다시 보내온다.

그런데도 주문은 스캔과 단단히 묶여 있다. 묶는 끈이 **`imagePath` 하나**다.

```
[19·20번] POST /api/scans  { imagePath: "scan/42/menu.jpg" }
              ↓ 응답: items[{ foodId, menuName, price, ... }]
        (사용자가 화면에서 3개 고르고 수량 매김)
              ↓
[이 노트] POST /api/orders { imagePath: "scan/42/menu.jpg",  ← 같은 값 그대로
                             items: [{ foodId, menuName, quantity, price }, ...] }
```

`imagePath` 는 [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]] 에서 클라이언트가 S3 에 직접 올리고 완료 확정까지 받은 **그 오브젝트 경로**다. 스캔 v1·v2 요청이 쓰는 필드와 **글자 그대로 같은 값**이다(`api/src/main/kotlin/com/kbap/api/scan/ScanV2Request.kt:18`, `ScanRequest.kt:24`).

그래서 `imagePath` 는 이 흐름에서 세 가지 일을 동시에 한다.

1. **소유권 증명** — 이 사진을 올린 게 정말 너인가
2. **중복 방지 키** — 이 메뉴판으로 이미 주문했는가
3. **상세·목록 응답의 메뉴판 사진 URL** — 주문 카드에 그날 찍은 사진을 그려 준다

> [!note] 왜 스캔 이력 id 가 아니라 이미지 경로인가
> 스캔 결과를 저장하는 `scan_history` 테이블이 따로 있는데도 주문은 그쪽을 참조하지 않는다. 마이그레이션 주석이 이유를 밝힌다 — 주문 항목은 "저장 시점의 이름·가격 스냅샷"을 자체 보유해서 **음식 마스터 변경과 무관하게 유지**되어야 하기 때문이다(`api/src/main/resources/db/migration/V2026.08.20.16.53.09__order_tables.sql:4`). 스캔 이력을 참조하면 스캔 이력의 수명에 주문이 끌려간다. 이미지 경로는 S3 오브젝트라 서버가 지우지 않는 한 그대로다.
> 곁들여: 가격은 애초에 음식 마스터에 없다. 스펙이 못박아 뒀다 — "가격은 음식 마스터에 없고 스캔 경로에서만 존재한다"(`specs/kb-337-order-history/spec.md`). 그래서 클라이언트가 스캔 응답에서 받은 가격을 주문 요청에 **되돌려 실어 보내는** 구조가 됐다.

### 4-1. 컨트롤러가 외부 API 를 부른다 — 이게 왜 여기 있나

```kotlin
    @PostMapping
    override fun placeOrder(
        @AuthMemberId memberId: Long,
        @Valid @RequestBody request: OrderCreateRequest,
    ): ResponseEntity<BaseResponse<OrderCreateResponse>> {
        val roadAddress = request.latitude?.let { reverseGeocoder.getRoadAddressOrNull(it, request.longitude!!) }
        val orderId = orderService.createOrder(memberId, request, roadAddress)
        return ResponseEntity.ok(BaseResponse.ok(OrderCreateResponse(orderId)))
    }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderController.kt:23-31`

컨트롤러가 서비스를 부르기 **전에** 구글 지오코딩 API 를 때린다. 얼핏 계층 위반처럼 보인다 — 비즈니스 로직은 서비스에 있어야 하는 것 아닌가([[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]]).

이유는 **트랜잭션 경계**다. `createOrder` 에 `@Transactional` 이 붙어 있으므로, 역지오코딩을 서비스 안으로 옮기면 **HTTP 왕복이 트랜잭션 안에서 일어난다.** 구글이 3초 응답하면 DB 커넥션을 3초간 붙잡고 논다. 커넥션 풀은 유한하고([[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프|요청 하나에 스레드 하나]] 의 스레드풀과 같은 이야기), 그러면 주문과 무관한 API 까지 같이 느려진다. 레포 헌법이 "외부 호출은 트랜잭션 밖"으로 못박은 규칙이고, 같은 판단을 `ImageUploadService` 도 한다(주석으로 명시 — `api/src/main/kotlin/com/kbap/api/image/ImageUploadService.kt:16-17`).

`getRoadAddressOrNull` 이라는 이름이 계약을 드러낸다 — **실패해도 예외를 던지지 않고 null 이다.**

```kotlin
    override fun getRoadAddressOrNull(latitude: BigDecimal, longitude: BigDecimal): String? {
        return try {
            val response = googleGeocodingApi.reverseGeocode(...)
            if (response.status != "OK") {
                log.warn("역지오코딩 결과 없음: status={}", response.status)
                return null
            }
```
— `api/src/main/kotlin/com/kbap/api/infra/place/GoogleGeocoder.kt:46-56`

주소는 **부가 정보**라서 구글이 죽어도 주문은 성공해야 한다. 이 판단이 포트 인터페이스의 이름과 시그니처(`String?`)에 새겨져 있다 — 어댑터를 갈아끼워도 이 계약은 유지된다([[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]. 계약은 `common/src/main/kotlin/com/kbap/common/port/place/ReverseGeocoder.kt`, 구현은 `api/infra/place/`).

좌표는 **저장만 하고 어떤 응답에도 안 나간다**. 응답 DTO 어디에도 `latitude` 필드가 없고, 테스트가 문자열 검사로 그걸 지킨다 — `json.contains("latitude") shouldBe false`(`api/src/test/kotlin/com/kbap/api/order/OrderControllerTest.kt:504`).

### 4-2. 서비스 본문 — 검증 셋, 저장 둘

```kotlin
    @Transactional
    fun createOrder(memberId: Long, request: OrderCreateRequest, roadAddress: String?): Long {
        verifyOrderable(memberId, request)
        return saveOrder(memberId, request, roadAddress)
    }

    private fun verifyOrderable(memberId: Long, request: OrderCreateRequest) {
        imageUploadService.verifyImageAccess(memberId, request.imagePath!!)
            ?: throw BusinessException(ErrorCode.SCAN_IMAGE_NOT_VERIFIED)
        if (orderRepository.existsByImagePath(request.imagePath)) {
            throw BusinessException(ErrorCode.ORDER_ALREADY_PLACED)
        }
        val foodIds = request.items.map { it.foodId!! }.distinct()
        if (foodRepository.findByIdIn(foodIds).size != foodIds.size) {
            throw BusinessException(ErrorCode.FOOD_NOT_FOUND)
        }
    }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:30-46`

- **1번 검증 — 이 사진이 네 것인가.** `verifyImageAccess` 는 `uploaded_image` 에서 경로로 찾아 `isOwnedBy(memberId)` 를 확인하고, 아니면 null 을 준다(`api/src/main/kotlin/com/kbap/api/image/ImageUploadService.kt:47-48`). 남의 사진 경로를 훔쳐 넣으면 `SCAN-001`. 존재하지 않는 경로도 같은 에러다 — **"없음"과 "남의 것"을 구분해 주지 않는 게 의도**다(존재 여부를 노출하지 않는다).
- **2번 검증 — 이 메뉴판으로 이미 주문했나.** `existsByImagePath` 한 방. 다음 절의 주인공이다.
- **3번 검증 — 이 음식들이 실재하는가.** `distinct()` 로 중복 id 를 접고, `findByIdIn` **한 번**으로 다 가져와 **개수만 비교**한다. 여기서 이미 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] §3-1 의 손동작이 나온다 — 항목마다 `findById` 를 돌렸다면 항목 50개짜리 주문에 SELECT 50번이었다.
  - 다만 여기서 확인하는 건 **존재**뿐이지 **공개(READY) 여부가 아니다.** 준비중인 음식도 주문할 수 있다. 이건 버그를 고치면서 생긴 결정이다 — 커밋 `a2c339f9`("준비중(미등록) 음식 포함 주문이 ORDER-001 로 거절되던 문제 수정")가 그 판정을 걷어냈고, `ORDER-001` 에러 코드는 지금 `ErrorCode.kt` 에 존재하지 않는다.

## 5. "스캔 1회당 주문 1회" — 두 겹으로 막는다

이 노트에서 **가장 뜯어볼 만한 대목**이다. 같은 사진으로 주문을 두 번 만들면 어떻게 되나?

### 5-1. DDL 부터

```sql

  `id` bigint NOT NULL AUTO_INCREMENT,
  `member_id` bigint NOT NULL,
  `image_path` varchar(512) NOT NULL,
  ...
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_orders_image_path` (`image_path`),
  KEY `idx_orders_recent` (`member_id`, `id`),
  CONSTRAINT `fk_orders_member` FOREIGN KEY (`member_id`) REFERENCES `member` (`id`)

```
— `api/src/main/resources/db/migration/V2026.08.20.16.53.09__order_tables.sql:5-19`

마이그레이션 주석이 의도를 직접 적어 뒀다 — "`image_path` UNIQUE = '스캔 1회당 주문 1회' 를 DB 가 원자적으로 강제(**더블탭 경합 포함**)"(같은 파일 `:2`).

### 5-2. 그런데 코드에도 검사가 있다 — 왜 둘 다?

```kotlin
    private fun saveOrder(memberId: Long, request: OrderCreateRequest, roadAddress: String?): Long {
        val order = try {
            orderRepository.saveAndFlush(request.toOrder(memberId, roadAddress))
        } catch (e: DataIntegrityViolationException) {
            if (isImagePathConflict(e)) throw BusinessException(ErrorCode.ORDER_ALREADY_PLACED)
            throw e
        }
        orderItemRepository.saveAll(request.items.map { it.toItem(order.id) })
        return order.id
    }

    private fun isImagePathConflict(e: DataIntegrityViolationException): Boolean =
        generateSequence(e as Throwable) { it.cause }
            .any { it.message?.contains(IMAGE_PATH_UNIQUE_KEY) == true }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:48-61`

두 겹이 하는 일이 다르다.

| 겹 | 무엇을 막나 | 못 막는 것 |
|---|---|---|
| `existsByImagePath` (§4-2) | 사용자가 **시간 차를 두고** 두 번 주문 — 어제 주문한 메뉴판을 오늘 또 | **동시**에 두 요청이 오면 둘 다 "없음"을 보고 통과한다 |
| `uq_orders_image_path` | 위의 경합까지 전부. INSERT 두 개 중 **하나만 살아남는다** | 없음. DB 가 원자적으로 판정한다 |

그러니까 애플리케이션 검사는 **정중한 에러 메시지를 위한 것**이고, 진짜 보증은 유니크 제약이 한다. 이게 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 나 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] 의 `uq_member_ranking_event` 와 같은 사고방식이다 — **"동시에 두 번"은 코드가 아니라 DB 가 막는다.**

FE 로 옮기면: 버튼 disable 은 `existsByImagePath` 고, 유니크 제약은 그 disable 이 새는 모든 경우(네트워크 재시도, 뒤로가기 후 재제출, 두 기기 동시 조작)를 받아내는 마지막 그물이다.

레포 헌법이 이 선택지를 미리 정해 뒀다는 것도 알아 둘 값이 있다 — "동시성 방어는 **비즈니스 중요도로 판단**한다: 치명적 정합만 **최소 수단(원자 UPDATE·unique 제약)**으로 막고, 비치명 경합은 감수한다. **트랜잭션 격리수준을 손대지 않는다**"(`CLAUDE.md:122`). 그래서 여기에 `SERIALIZABLE` 도 비관적 락도 없다. 유니크 제약 한 줄이 정해진 답이다. [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] 의 원자적 UPDATE 가 같은 문장의 다른 절반이다.

### 5-3. `save` 가 아니라 `saveAndFlush` 인 이유

여기가 핵심이다. `save` 만 쓰면 INSERT 는 **트랜잭션 커밋 시점**에야 DB 로 날아간다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 의 쓰기 지연). 그러면 유니크 위반 예외가 터지는 자리는 **서비스 메서드가 이미 끝난 뒤**다 — `try/catch` 밖이라 잡을 수 없고, 사용자는 `ORDER-003`(409, "이 메뉴판으로는 이미 주문했습니다") 대신 정체불명의 500 을 받는다.

`saveAndFlush` 는 그 INSERT 를 **지금 즉시** 밀어 넣어, 제약 위반을 `try` 블록 **안에서** 터뜨린다. 그래서 예쁜 에러로 번역할 수 있다.

`isImagePathConflict` 가 예외 **원인 체인을 훑어 제약 이름 문자열을 찾는** 것도 그래서다 — `DataIntegrityViolationException` 은 "무슨 제약을 어겼는지"를 구조화해 주지 않으므로, `uq_orders_image_path` 라는 문자열이 메시지 어딘가에 있는지 뒤진다. 이름 하나가 안 맞으면 조용히 500 으로 새어 나가는 코드다.

> [!warning] 문자열 매칭에 걸린 이름은 세 곳에 흩어져 있다
> `uq_orders_image_path` 라는 문자열이 **마이그레이션 SQL**(`:16`)과 **Kotlin 상수**(`OrderService.kt:140`) 두 곳에 각각 하드코딩돼 있다. 마이그레이션에서 제약 이름을 바꾸면 컴파일은 통과하고 테스트도 (경합이 없으면) 통과하는데, 실전에서 더블탭이 500 을 반환한다. 제약 이름을 만질 일이 생기면 `OrderService` 를 같이 찾아라.

### 5-4. 소프트 삭제와 유니크 제약이 어긋나는 자리

`Order` 는 `BaseEntity` 를 상속하고, `BaseEntity` 에는 `@SQLRestriction("status = 'ACTIVE'")` 가 붙어 있다(`common/src/main/kotlin/com/kbap/common/domain/BaseEntity.kt:16`). 즉 **JPA 로 하는 모든 조회는 `ACTIVE` 행만 본다.** 반면 `UNIQUE` 제약은 `DELETED` 행까지 **전부** 본다.

그래서 어떤 주문이 소프트 삭제되면 — `existsByImagePath` 는 `false`(안 보이니까), DB 유니크는 `true`(행은 살아 있으니까). 결과는 §5-2 의 catch 로 흘러가 `ORDER-003` 이다. **동작은 맞다**(이미 주문한 메뉴판이니까). 다만 검사 두 겹이 서로 다른 세계를 보고 있다는 건 알아 둘 값이 있다.

지금은 잠재적이다 — 주문 삭제 API 가 없다(`OrderService` 에 `delete` 계열 메서드 0개). 삭제가 생기는 날 이 자리를 먼저 봐야 한다.

## 6. 트랜잭션 경계 — 주문과 항목은 한 덩어리인가

**그렇다.** `createOrder` 하나에만 `@Transactional` 이 있고, 그 안에서 `orders` INSERT 와 `order_item` INSERT N 건이 함께 일어난다. 항목 저장이 실패하면 주문 행도 함께 롤백된다 — 항목 없는 빈 주문이 남지 않는다.

```
POST /api/orders
 ├── [트랜잭션 밖] 구글 역지오코딩 HTTP     ← 실패해도 주문은 진행 (roadAddress = null)
 └── @Transactional {
       SELECT uploaded_image WHERE object_path = ?      ← 소유권
       SELECT EXISTS orders WHERE image_path = ?        ← 중복
       SELECT food WHERE id IN (...)                    ← 실재 확인 (1번)
       INSERT orders                                    ← saveAndFlush (즉시)
       INSERT order_item × N                            ← saveAll
     }  커밋
```

`@Transactional` 이 정확히 어디서 열리고 닫히는지, 왜 `private` 메서드에 붙이면 안 되는지는 [[6. 설정과 프로필, 트랜잭션 경계]] 에 있다. `verifyOrderable`·`saveOrder` 가 `private` 인데도 트랜잭션 안인 이유도 거기 있다 — **경계는 public 진입점 `createOrder` 가 그었고, 내부 호출은 그 안에 그냥 포함**된다.

> [!note] `saveAll` 은 INSERT 를 몇 번 날리나
> `saveAll(list)` 는 이름과 달리 **한 번의 배치 INSERT 가 아니다.** `hibernate.jdbc.batch_size` 설정이 이 레포 어디에도 없고(`api/src/main/resources/application*.yml` 에 0건), 게다가 `BaseEntity` 의 키 전략이 `GenerationType.IDENTITY` 라 Hibernate 는 **id 를 받아오기 위해 매 행마다 INSERT 를 따로** 보낸다. 항목 3개면 INSERT 3번이다.
> 항목 상한이 50개로 잡혀 있어서(`OrderCreateRequest.kt:26`) 실전 문제는 아니다. 다만 "`saveAll` = 쿼리 1번"이라고 외우면 틀린다.

## 7. 흐름 표 ② — 목록 조회 `GET /api/orders`

| 계층 | 파일 | 하는 일 |
|---|---|---|
| Controller | `api/.../order/OrderController.kt:33-39` | `cursor`(옵셔널)·`size`(기본 10) 쿼리 파라미터를 받아 그대로 넘긴다 |
| Service | `api/.../order/OrderService.kt:63-75` | 커서 파싱 → `size+1` 조회 → `hasNext` 판정 → 카드 조립 |

### 7-1. 커서 페이징 — [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] 과 같은 손동작

```kotlin
    @Transactional(readOnly = true)
    fun getOrderPage(memberId: Long, rawCursor: String?, size: Int): OrderListPage {
        val cursor = CursorParser.parse(rawCursor)
        val pageSize = size.coerceIn(1, MAX_PAGE_SIZE)
        val orders = orderRepository.findPageByMemberId(memberId, cursor, PageRequest.of(0, pageSize + 1))
        val hasNext = orders.size > pageSize
        val pageOrders = orders.take(pageSize)
        return OrderListPage(
            items = summarize(pageOrders),
            hasNext = hasNext,
            nextCursor = pageOrders.lastOrNull()?.id?.toString()?.takeIf { hasNext },
        )
    }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:63-75`

원리는 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]] 와 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] §7 에 이미 있으니 여기선 **같다는 것만** 확인하고 넘어간다. 커서는 마지막으로 본 주문의 `id` 를 문자열로 담은 것이고, 쿼리 조건은 `(:cursor is null or o.id < :cursor)` + `order by o.id desc` 다(`OrderJpaRepository.kt:12-24`). `size+1` 을 떠서 하나가 더 오면 다음 페이지가 있다.

주문만의 자잘한 차이는 셋뿐이다.

- 커서가 **단순 id 하나**다. 리뷰의 복합 keyset(`"17_204"` 를 base64url) 이 필요 없다 — 정렬이 `id desc` **하나뿐**이라 동점이 생기지 않는다.
- `nextCursor` 를 `takeIf { hasNext }` 로 **마지막 페이지에서 null 로 만든다.** FE 는 `nextCursor == null` 만 보고 끝을 판단할 수 있다.
- `size` 는 서버가 `coerceIn(1, 30)` 으로 조인다(`MAX_PAGE_SIZE = 30`). `?size=99999` 로 DB 를 통째로 긁는 걸 막는 자리다. **거절이 아니라 조용한 클램프**라는 게 계약이다 — 400 이 아니라 30개가 온다.

깨진 커서는 `CursorParser` 가 `FOOD-002`("커서 형식이 올바르지 않습니다", 400)로 거절한다(`common/src/main/kotlin/com/kbap/common/util/CursorParser.kt:7-10`). 음식·북마크·리뷰·커뮤니티·주문 다섯 군데가 이 유틸 하나를 공유한다.

> [!note] 응답 봉투는 공용을 안 쓴다
> 커서 페이지 응답에는 공용 타입 `Page<T>`(`api/src/main/kotlin/com/kbap/api/core/Page.kt`)가 있는데 **주문은 그걸 안 쓰고** `OrderListPage` 를 따로 뒀다(`OrderResponses.kt:6-19`). 필드 구성(`items`/`hasNext`/`nextCursor`)은 같지만 `nextCursor` 타입이 다르다 — 공용은 `Long?`, 주문은 `String?` 다. 커서를 **불투명 토큰**으로 취급하겠다는 뜻이다(FE 는 값을 해석하지 말고 그대로 되돌려주면 된다). 공용 `Page<T>` 를 쓰는 쪽은 [[25. 커뮤니티 흐름 — 포스팅·댓글·커서 페이징]] 에서 볼 수 있다.

> [!warning] 에러 코드가 도메인과 어긋난다
> 주문 목록에 깨진 커서를 넣으면 **`FOOD-002`** 가 온다. 주문 API 인데 음식 채번이다. `CursorParser` 가 원래 음식 목록용으로 만들어졌다가 주문·리뷰에 공유되면서 코드만 그대로 남았다. FE 에서 커서 에러를 분기할 때 `ORDER-*` 를 기다리면 영원히 안 온다.

## 8. 상세 조회와 배치 로딩 — 이 노트의 백미

### 8-1. 문제 상황부터

주문 상세 화면 하나를 그리려면 이만큼이 필요하다.

```
주문 1건
 └─ 주문항목 N개  (menu_name, quantity, price 는 스냅샷이라 여기 있음)
     └─ 음식 1개  (food_id 로 참조)         ← 왜 필요? 사진과 READY 여부 때문
         └─ 이미지 URL
```

연관관계를 쓰는 흔한 JPA 코드였다면 `order.getItems()` 하고 `item.getFood().getImageRef()` 를 찍었을 것이고, 항목이 N개면 SELECT 가 **1 + N + N** 번 나갔을 것이다. 이게 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 가 말한 N+1 이다.

그런데 kbap 에는 `@OneToMany` 도 `@ManyToOne` 도 **없다**. ArchUnit 이 아예 금지한다([[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]). `OrderItem` 은 `Order` 를 모르고, `Order` 는 `OrderItem` 을 모른다 — 둘 다 그냥 `Long` 컬럼이다.

```kotlin
@Entity
@Table(
    name = "order_item",
    indexes = [Index(name = "idx_order_item_order", columnList = "order_id")],
)
class OrderItem(
    @Column(name = "order_id", nullable = false)
    var orderId: Long = 0,

    @Column(name = "food_id", nullable = false)
    var foodId: Long = 0,
```
— `common/src/main/kotlin/com/kbap/common/domain/order/model/OrderItem.kt:9-19`

`orderId` 도 `foodId` 도 **그냥 숫자**다. `Order` 타입도 `Food` 타입도 등장하지 않는다.

DDL 을 보면 더 재밌다.

```sql
CREATE TABLE `order_item` (
  ...
  `order_id` bigint NOT NULL,
  `food_id` bigint NOT NULL,
  ...
  KEY `idx_order_item_order` (`order_id`),
  CONSTRAINT `fk_order_item_order` FOREIGN KEY (`order_id`) REFERENCES `orders` (`id`)
) ENGINE=InnoDB ...
```
— `V2026.08.20.16.53.09__order_tables.sql:21-34`

**FK 는 있다.** `fk_order_item_order` 가 실제로 걸려 있고, `orders` 에도 `fk_orders_member` 가 있다. 그런데 `food_id` 에는 FK 가 **없고**, 주석이 왜인지 적어 뒀다 — "`food_id` 는 FK 를 걸지 않는 논리 참조 — 주문 내역은 음식 마스터 변경과 무관하게 스냅샷으로 유지된다"(`:4`).

정리하면 이렇다.

| | `order_item.order_id` | `order_item.food_id` |
|---|---|---|
| DB FK | **있다** (`fk_order_item_order`) | 없다 (의도적) |
| JPA 연관 매핑 | **없다** | 없다 |
| 뜻 | 항목은 주문 없이 존재할 수 없다 → DB 가 강제 | 음식이 지워져도 주문 이력은 남는다 |

**"DB FK 가 있다"와 "JPA 연관이 있다"는 완전히 별개다.** FK 는 데이터 정합성 규칙이고, 연관 매핑은 객체 그래프 탐색 편의다. kbap 은 앞의 것만 쓴다.

```kotlin
    private fun loadFoodsById(items: List<OrderItem>): Map<Long, Food> {
        val foodIds = items.map { it.foodId }.distinct()

        return foodRepository.findAllById(foodIds).associateBy { it.id }
```

네 줄짜리 함수가 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] §3-1 그대로다.

- `items.map { it.foodId }` — **먼저 id 를 다 모은다.** 루프 안에서 조회하지 않는 것이 전부다.
- `.distinct()` — 같은 음식을 두 항목으로 시켰으면 id 가 중복이다. 접는다.
- `if (foodIds.isEmpty()) return emptyMap()` — 빈 `IN ()` 을 만들지 않는 가드. 연관관계가 해 주던 걸 손으로 쓰니 이런 가드도 손으로 붙는다.
- `findAllById(foodIds)` — **SELECT 한 번**. `where id in (7, 12, 30)`.
- `.associateBy { it.id }` — `Map<Long, Food>` 로 정규화. FE 에서 `Object.fromEntries(list.map(f => [f.id, f]))` 하는 것과 같다.

그 다음 `items.map { ... foodsById[it.foodId] }` 는 **메모리에서 Map 을 찍는 것**뿐이다. DB 는 안 간다.

> [!note] `IN` 조회에 정렬 복구가 왜 없나
> [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] §3-1 의 `FoodService.loadInGivenOrder` 는 `IN` 결과를 원래 id 순서로 다시 줄 세운다. 여기엔 그 줄이 없다 — **응답의 순서를 정하는 건 `items` 지 `foods` 가 아니기 때문**이다. `foods` 는 Map 으로 접히므로 조회 순서가 애초에 의미가 없다. 순서를 결정하는 건 `findByOrderIdOrderByIdAsc` 의 `OrderByIdAsc` 다.

- `orders.map { it.id }` → `findByOrderIdInOrderByIdAsc(...)` — **주문 10건의 항목을 SELECT 한 번**으로 전부 긁는다.
- `.groupBy { it.orderId }` — `Map<Long, List<OrderItem>>`. 이게 연관관계였다면 `order.getItems()` 였을 자리다. **직접 만든 `getItems()` 라고 봐도 된다.**
- `itemsByOrderId.values.flatten()` — 10건 주문의 **모든** 항목을 한 리스트로 편다. 그리고 그 전체에 대해 `resolveThumbnails` 를 **한 번** 부른다. 주문별로 부르면 SELECT 가 주문 수만큼 나간다.
- `items.take(4)` — 썸네일 상한. 여기서 잘라도 **조회는 이미 전체를 한 번에 했다** — 자르는 건 응답 조립 단계다.

```kotlin
    private fun resolveThumbnails(items: List<OrderItem>): Map<Long, String> {
        val foodsById = loadFoodsById(items)
        return items.map { it.foodId }.distinct().associateWith { publicImageUrlOf(foodsById[it]) }
    }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:124-127`

`loadFoodsById` 를 **재사용**한다. 상세와 목록이 같은 함수를 쓴다.

### 8-4. 쿼리 개수 — 세어 보자

| 응답 | 쿼리 | 개수 |
|---|---|---|
| **상세** `GET /api/orders/{id}` | ① `SELECT orders WHERE id=?` ② `SELECT order_item WHERE order_id=? ORDER BY id` ③ `SELECT food WHERE id IN (…)` | **3** |
| **목록** `GET /api/orders?size=10` | ① `SELECT orders WHERE member_id=? AND id<? ORDER BY id DESC LIMIT 11` ② `SELECT order_item WHERE order_id IN (…) ORDER BY id` ③ `SELECT food WHERE id IN (…)` | **3** |

**둘 다 3번이고, 항목 개수와 주문 개수에 무관하다.** 항목 50개짜리 주문도 3번, 주문 30건짜리 페이지도 3번이다.

연관관계를 썼다면 상세는 `1 + N`(항목마다 음식), 목록은 `1 + M + Σ Nᵢ`(주문마다 항목, 항목마다 음식)이었다. 주문 30건 × 항목 5개면 **1 + 30 + 150 = 181번**. 그게 3번이 됐다.

이미지 URL 을 만드는 `publicImageUrlOf` 가 **DB 를 안 간다**는 것도 확인해 둘 값이 있다.

```kotlin
    fun resolveImageUrl(food: Food): String? = ImageUrls.resolve(imagePublicBaseUrl, food.imageRef)

    fun resolveImageUrlOrDefault(food: Food?): String =
        food?.let { resolveImageUrl(it) }
            ?: requireNotNull(ImageUrls.resolve(imagePublicBaseUrl, DEFAULT_FOOD_IMAGE_PATH))
```
— `api/src/main/kotlin/com/kbap/api/food/FoodService.kt:195-199`

`ImageUrls.resolve` 는 베이스 URL 과 경로를 붙이는 **순수 문자열 함수**다(`common/src/main/kotlin/com/kbap/common/util/ImageUrls.kt:4-10`). 여기서 조회를 한 번이라도 했으면 §8-2 의 노력이 전부 도로아미타불이었을 것이다. 배치 로딩은 **끝까지 DB 를 안 가야** 성립한다.

`publicImageUrlOf` 한 줄에는 규칙 하나가 더 접혀 있다.

```kotlin
    private fun publicImageUrlOf(food: Food?): String =
        foodService.resolveImageUrlOrDefault(food?.takeIf { it.isReady() })
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:129-130`

`takeIf { it.isReady() }` — 음식이 **READY 가 아니면 null 취급**해서 기본 대체 이미지로 보낸다. 준비중인 음식은 사진이 있어도 안 쓴다(커밋 `f5fd3c6e`). 그래서 `ready = false` 인 항목은 응답에서 항상 기본 이미지이고, FE 는 그 플래그로 음식 상세 링크를 비활성화한다(`OrderResponses.kt:92-96`).

## 9. 요청/응답 실물

### 9-1. 주문 저장

```http
POST /api/orders
X-API-Version: 1.0
Authorization: Bearer <accessToken>
Content-Type: application/json
```
```json
{
  "imagePath": "scan/42/menu.jpg",
  "items": [
    { "foodId": 7,  "menuName": "순두부찌개", "quantity": 2, "price": 9000 },
    { "foodId": 12, "menuName": "계란말이",   "quantity": 1, "price": 8000 },
    { "foodId": 30, "menuName": "공기밥",     "quantity": 3 }
  ],
  "latitude": "37.5636000",
  "longitude": "126.9834000"
}
```
```json
{ "success": true, "payload": { "orderId": 123 } }
```

- `price` 는 **생략 가능**하다(스캔에서 가격을 못 읽은 메뉴). `quantity` 는 필수 1 이상.
- `latitude`·`longitude` 는 **함께 보내거나 함께 생략**해야 한다. 한쪽만 보내면 400 — `coordinatesComplete` 라는 `@AssertTrue` 게터가 그걸 검사한다(`OrderCreateRequest.kt:41-44`). 필드 하나에는 못 거는 조건이라 클래스 레벨 검증으로 뺀 자리다.
- 실패 응답: `{ "success": false, "code": "ORDER-003", "message": "이 메뉴판으로는 이미 주문했습니다" }` (409).

### 9-2. 주문 목록

```http
GET /api/orders?size=2
```
```json
{
  "success": true,
  "payload": {
    "items": [
      {
        "orderId": 123,
        "orderedAt": 1765700640000,
        "roadAddress": "서울 중구 소공로 51",
        "totalQuantity": 6,

```

- `orderedAt` 은 **epoch milliseconds(Long)**. `Order.orderedAt()` 이 `createdAt` 을 서버 기본 타임존으로 변환해 만든다(`Order.kt:32`). ISO 문자열이 아니라 숫자다.
- `roadAddress` 가 `null` 인 건 위치 미동의이거나 역지오코딩 실패다. **둘을 구분할 방법이 응답에 없다.**

- 전체 개수(`totalCount`)를 안 준다 — 커서 페이징의 성질이다([[페이징 — Offset vs No-Offset(Keyset·Cursor)]]).

### 9-3. 주문 상세

```http
GET /api/orders/123
```
```json
{
  "success": true,
  "payload": {
    "orderId": 123,
    "orderedAt": 1765700640000,
    "roadAddress": "서울 중구 소공로 51",
    "totalQuantity": 6,
    "totalPrice": 26000,
    "scanImageUrl": "https://cdn.example.com/scan/42/menu.jpg",
    "items": [
      { "menuName": "순두부찌개", "quantity": 2, "price": 9000, "foodId": 7,
        "imageRef": "https://cdn.example.com/images/webp/sundubu.webp", "ready": true },
      { "menuName": "공기밥", "quantity": 3, "price": null, "foodId": 30,
        "imageRef": "https://cdn.example.com/images/webp/default_miss_food/food_not_found.png", "ready": false }
    ]
  }
}
```

- `totalPrice` = **가격이 있는 항목만** (단가 × 수량) 합. `9000×2 + 8000×1 = 26000`, 가격 없는 공기밥은 빠진다. 도메인 모델이 계산한다 — `items.sumOf { (it.price ?: 0) * it.quantity }`(`OrderItem.kt:35`).
- `totalQuantity` 는 **전부** 더한다 — `2 + 1 + 3 = 6`. 가격과 달리 수량은 항상 있다.
- `scanImageUrl` 은 **목록과 값이 완전히 같다.** 이 필드가 상세에 생긴 게 레포 최신 커밋(`9885642d`)이고, 스펙이 그 이유를 "누락은 실수다(의도적 제외 아님)"라고 못박았다(`specs/kb-376-order-detail-scan-image/spec.md`).
- 남의 주문이거나 없는 주문이면 **둘 다 404 `ORDER-002`** 다. 코드가 `findById(...).filter { it.memberId == memberId }` 로 **소유자 불일치를 '없음'과 같은 갈래로 접는다**(`OrderService.kt:79-81`). 403 이 아닌 이유는 **주문의 존재 여부 자체를 노출하지 않기 위해서**다 — id 를 훑어서 "403 이 뜨는 id = 실재하는 남의 주문"을 알아내는 걸 막는다.

## 14. 치트시트

## 15. 용어집

| 용어 | 뜻 |
|---|---|
| 스냅샷 저장 | 참조 대신 그 시점의 값을 복사해 함께 저장. 원본이 바뀌어도 이력은 안 바뀐다 |
| 논리 참조 | id 컬럼으로 가리키되 DB FK 는 걸지 않는 것. 대상이 사라져도 행이 남는다 |
| 유니크 제약 | 같은 값의 두 번째 INSERT 를 DB 가 거부하는 규칙. 동시성까지 원자적으로 처리 |
| `saveAndFlush` | 쓰기 지연을 건너뛰고 즉시 DB 로 보내기. 제약 위반을 여기서 잡으려면 필수 |
| 클램프(clamp) | 값을 허용 범위 안으로 조용히 밀어넣는 것. `coerceIn(1, 30)` |
| 배치 로딩 | id 를 모아 `IN` 한 번으로 가져와 Map 으로 붙이는 것. 연관관계가 하던 일의 수동판 |

## 16. 체크리스트 — 이 노트를 덮고 말할 수 있어야 하는 것

- [ ] 주문이 스캔과 어떻게 묶이는지, 그 끈이 무엇인지 말할 수 있다
- [ ] 같은 사진으로 두 번 주문하면 어떤 응답이 오고, 그걸 **누가**(코드? DB?) 판정하는지 말할 수 있다
- [ ] `save` 대신 `saveAndFlush` 를 쓴 이유를 한 문장으로 말할 수 있다
