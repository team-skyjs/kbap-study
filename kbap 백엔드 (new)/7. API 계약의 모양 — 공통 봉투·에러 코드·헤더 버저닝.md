# 7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝

> 작성: 2026-08-26 · 맥락: kbap-server 컨트롤러 파일을 **아무거나 하나 열면** 첫 20줄 안에 이 세 가지가 전부 나온다. 모르고 보면 코드가 안 읽힌다.
> 목표: 컨트롤러 시그니처 `ResponseEntity<BaseResponse<T>>` 와 `@PostMapping("/me/onboarding", version = "1.1+")` 를 보고 **아무것도 안 찾아보고 이해**하기.

---

## 0. 한 줄 요약

kbap의 모든 API 응답은 **`{success, payload, message, code}` 라는 같은 모양의 봉투**에 담겨 오고, 실패는 HTTP 상태가 아니라 **`code`(`AUTH-004` 같은 안정 식별자)로 구분**하며, 버전은 URL이 아니라 **`X-API-Version` 헤더**로 가른다.

> [!tip] 이 노트가 특별한 이유 — 반대편을 이미 알고 있다
> 이 계약의 **클라이언트 쪽 구현을 이미 매일 만지고 있다.** `kbap-fe/src/lib/api/client.ts` 가 하는 일이 정확히 이거다 — 봉투를 벗겨 `payload`만 화면에 주고, `code`로 401을 분기해 refresh 재시도하고, 모든 요청에 `X-API-Version` 을 붙인다. 이 노트는 **그 파일의 서버 쪽 짝**을 읽는 노트다. 새 개념을 배우는 게 아니라, 이미 아는 계약의 **발신자 쪽**을 보는 것이다.

## 1. 핵심 개념 — 세 가지가 한 세트다

| | 공통 응답 봉투 | 에러 코드 | 헤더 버저닝 |
|---|---|---|---|
| 정체 | 모든 응답을 감싸는 고정 껍데기 `BaseResponse<T>` | `도메인-3자리` 형식의 안정 식별자 enum | `X-API-Version` 헤더로 핸들러를 고르는 라우팅 |
| 어디에 | `api/core/BaseResponse.kt` | `common/core/error/ErrorCode.kt` | `api/core/config/WebConfig.kt` + 각 컨트롤러 |
| 클라가 보는 것 | `json.payload` | `json.code` | 요청 헤더 한 줄 |
| 없으면 | 엔드포인트마다 응답 모양이 제각각 | 클라가 에러 문구를 문자열 매칭 → 문구 바꾸면 앱이 깨짐 | 버전마다 URL이 늘어남 (`/v1`·`/v2`·`/v3`…) |

셋은 각각 독립적으로 보이지만 **한 요청에서 함께 작동**한다. 예를 들어 `X-API-Version` 헤더를 빠뜨리면 → 400 상태 + **봉투에 담긴** `code: "COMMON-002"` 가 온다. 3절에서 그 경로를 코드로 따라간다.

## 2. 공통 응답 봉투 — 모든 응답이 같은 모양이다

### 2-1. 실물

```kotlin
data class BaseResponse<T>(
    val success: Boolean,
    val payload: T? = null,
    val message: String? = null,
    val code: String? = null,
) {
    companion object {
        fun <T> ok(payload: T): BaseResponse<T> = BaseResponse(success = true, payload = payload)

        fun fail(code: String, message: String, payload: Any? = null): BaseResponse<Any> =
            BaseResponse(success = false, payload = payload, message = message, code = code)
    }
}
```
`api/src/main/kotlin/com/kbap/api/core/BaseResponse.kt:3-15`

- `3` — `data class` 는 Kotlin의 값 클래스다. TS의 `interface BaseResponse<T>` 라고 봐도 된다. `<T>` 는 제네릭 — 실제 알맹이 타입이 엔드포인트마다 달라진다.
- `4-7` — 필드 4개가 전부다. **FE의 `BaseResponse<T>` 인터페이스(`client.ts:73-79`)와 필드가 1:1로 같다.** 우연이 아니라 이게 계약이다.
- `10` — 성공 헬퍼. `code`·`message`는 안 채워지므로 성공 응답 JSON엔 그 두 키가 없거나 null이다.
- `12-13` — 실패 헬퍼. **성공 경로와 실패 경로가 같은 클래스**를 쓴다는 게 핵심이다.

컨트롤러는 이 봉투를 **직접 만들지 않는 법이 없다** — 규약상 raw DTO를 그냥 반환하는 게 금지다:

```kotlin
    @GetMapping("/me/profile")
    override fun getMyProfile(
        @AuthMemberId memberId: Long,
    ): ResponseEntity<BaseResponse<MyProfileResponse>> {
        val result = memberService.getMyProfile(memberId)
        return ResponseEntity.ok(BaseResponse.ok(MyProfileResponse.from(result)))
    }
```
`api/src/main/kotlin/com/kbap/api/member/MemberController.kt:37-43`

- `40` — 반환 타입이 **두 겹**이다. 바깥 `ResponseEntity` = HTTP 층(상태 코드·헤더), 안쪽 `BaseResponse` = 우리 계약 층(성공 플래그·payload). **역할이 다르다.**
- `42` — `ResponseEntity.ok(...)` 가 HTTP 200을, `BaseResponse.ok(...)` 가 `success: true` 를 만든다. 두 번 감싸는 게 어색해 보이지만, 이 이중 구조가 다음 절의 트레이드오프 그 자체다.

### 2-2. 비유 — 택배 송장

봉투는 **택배 송장**이다. 안에 든 물건(책이든 옷이든)이 뭐든 겉면 양식은 늘 같다: 배송 성공 여부, 내용물, 사유 문구, 사유 코드. 받는 쪽은 상자를 뜯기 전에 **송장만 보고** 처리 방식을 정할 수 있다.

> [!warning] 비유의 경계
> 택배 송장은 물건 밖에 붙지만, `BaseResponse` 는 **JSON 본문 안에** 있다. 진짜 "겉면"에 해당하는 건 HTTP 상태 코드와 헤더다. 그래서 kbap 응답에는 **성공/실패 신호가 두 군데** 있다 — HTTP 상태(겉)와 `success`(안). 이 중복이 곧 다음 절이다.

### 2-3. 정직하게 — 왜 HTTP 상태만 쓰지 않나 (트레이드오프)

REST 원리주의로 보면 봉투는 **안티패턴에 가깝다.** HTTP는 이미 성공/실패를 표현하는 표준 수단(상태 코드)을 갖고 있는데, 그걸 본문 안에서 한 번 더 표현하기 때문이다. 그래서 정직하게 양쪽을 적자.

| | 봉투를 쓸 때 (kbap) | HTTP 상태만 쓸 때 |
|---|---|---|
| 클라 파싱 | 응답 타입이 항상 하나 → 언래핑 코드가 **한 곳**(`client.ts`)에 모임 | 성공 타입/에러 타입이 따로 → 분기가 호출부마다 흩어지기 쉬움 |
| 에러 식별 | `code` 로 정밀 분기(`AUTH-004` vs `AUTH-006`) | 상태 코드는 401 하나뿐 — 세부 구분 불가, 결국 본문에 코드를 넣게 됨 |
| 진실의 원천 | **두 개**(상태 + `success`) → 어긋날 수 있음 | 하나 |
| 중간 장비 | 프록시·CDN·모니터링이 상태 코드만 보면 정상 판단 가능 | 같음 |
| 표준성 | 비표준(우리만의 규약) | 표준(RFC 9457 Problem Details 같은 공식 대안도 있음) |

kbap이 봉투를 택한 실질 이유는 **"두 번째 열"의 마지막 칸** 때문이다 — 401 하나로는 "access 만료(재발급하면 됨)"와 "refresh 만료(재로그인해야 함)"를 구분할 수 없다. 어차피 본문에 코드를 넣어야 한다면, 그 자리를 **모든 응답에 일관되게** 두는 편이 클라 코드가 단순해진다.

> [!note] 두 진실이 어긋나는 실제 위험
> HTTP 200인데 `success: false` 인 응답이 이론상 가능하다. FE 클라이언트는 이걸 실제로 방어한다 — `client.ts:233-236` 의 주석이 그대로 `// 200 but success:false — never trust HTTP status alone.` 이다. 서버 쪽 `GlobalExceptionHandler` 는 항상 상태와 `success`를 같이 맞춰 내리지만, 클라는 그걸 믿지 않고 한 번 더 확인한다. **계약이 있어도 방어는 양쪽에서 한다.**

### 2-4. 반대편 — FE는 이 봉투를 어떻게 벗기나

```ts
  // 4xx/5xx: BE wraps errors in the same envelope, so prefer its message (§0).
  if (!res.ok) {
    throw new ApiError(json?.message ?? `HTTP ${res.status}`, res.status, json?.code ?? undefined);
  }
  // 200 but success:false — never trust HTTP status alone.
  if (!json || !json.success) {
    throw new ApiError(json?.message ?? `Malformed response (HTTP ${res.status})`, res.status, json?.code ?? undefined);
  }
  // Unit 응답(BaseResponseUnit)은 payload 필드 자체가 없다 — success면 통과.
  return json.payload as T;
```
`/Users/yejinkim/dev/kfood/kbap-fe/src/lib/api/client.ts:229-238`

- `230-232` — HTTP가 4xx/5xx면 **같은 봉투에서** `message`·`code` 를 꺼내 `ApiError` 로 바꾼다.
- `234-236` — 상태가 200이어도 `success: false` 면 똑같이 에러 취급.
- `238` — 성공이면 **`payload` 만** 리턴한다. 그래서 화면 컴포넌트는 봉투의 존재조차 모른다.

**여기가 다리다.** 서버의 `BaseResponse.ok(payload)` 가 만든 것을 FE의 `return json.payload` 가 벗긴다. 이 한 쌍이 kbap의 전 API를 관통한다.

## 3. 에러 코드 체계 — `message` 가 아니라 `code` 로 분기한다

### 3-1. 채번 규약

에러는 `ErrorCode` enum **하나**에 전부 모여 있다. 도메인별 예외 클래스를 만들지 않는다.

```kotlin

    val code: String,
    val status: Int,
    val message: String,

    INVALID_REQUEST("COMMON-002", 400, "잘못된 요청입니다"),
    INTERNAL_SERVER_ERROR("COMMON-003", 500, "서버 오류가 발생했습니다. 잠시 후 다시 시도해 주세요"),
    …
    INVALID_ACCESS_TOKEN("AUTH-003", 401, "유효하지 않은 액세스 토큰입니다. 다시 로그인해 주세요"),
    EXPIRED_ACCESS_TOKEN("AUTH-004", 401, "만료된 액세스 토큰입니다. 토큰을 갱신해 주세요"),
    …
    EXPIRED_REFRESH_TOKEN("AUTH-006", 401, "만료된 리프레시 토큰입니다. 다시 로그인해 주세요"),
```
`common/src/main/kotlin/com/kbap/common/core/error/ErrorCode.kt:4-19` (발췌·중략)

- `5-7` — 항목 하나가 **세 값을 묶는다**: 클라 분기용 `code`, HTTP 상태 `status`, 사람이 읽을 `message`.
- `10` — `COMMON-002`. 앞의 `COMMON-001`은 결번이다 — 폐기된 코드는 **재사용하지 않는다**(레포 주석에 이유가 적혀 있다). 결번을 남기는 이유는 옛 버전 앱이 아직 그 코드를 알고 있을 수 있기 때문이다.
- `16-19` — `AUTH-003`·`AUTH-004`·`AUTH-006` 은 **전부 HTTP 401**이다. 상태 코드만으로는 셋을 구분할 수 없다는 게 봉투를 쓰는 이유의 실물이다.

- `28` — `distinct().size == entries.size` — 코드 중복이 있으면 실패한다. 사람이 새 에러를 추가하다 기존 번호를 재사용하는 사고를 자동으로 막는다.

### 3-2. 던지는 쪽 — `BusinessException` 하나


> `throw new Error()` 를 던지고 최상위 ErrorBoundary가 받아 화면을 결정하는 구조와 같다. 던지는 곳은 "무엇이 잘못됐는지"만 말하고, "그래서 사용자에게 뭘 보여줄지"는 한 군데서 정한다.

### 3-3. 받는 쪽 — 전역 예외 핸들러가 봉투로 번역한다

```kotlin
@RestControllerAdvice
class GlobalExceptionHandler {
    …
    @ExceptionHandler(BusinessException::class)
    fun handleKbap(e: BusinessException, request: HttpServletRequest): ResponseEntity<BaseResponse<Any>> {
        val status = HttpStatus.resolve(e.errorCode.status) ?: HttpStatus.INTERNAL_SERVER_ERROR
        logFailure(e, e.errorCode.code, status, request)
        return ResponseEntity.status(status).body(BaseResponse.fail(e.errorCode.code, e.errorCode.message, e.payload))
    }
```
`api/src/main/kotlin/com/kbap/api/core/GlobalExceptionHandler.kt:18-51` (발췌)

- `18` — `@RestControllerAdvice` 는 "모든 컨트롤러를 감싸는 예외 처리기"를 뜻하는 Spring 애너테이션이다. 이 클래스는 어느 컨트롤러에도 연결돼 있지 않은데 전부에 적용된다 — 컨테이너가 알아서 꽂는다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]).
- `48` — `ErrorCode` 가 들고 있던 `status: Int` 를 실제 HTTP 상태로 바꾼다. **에러 코드 표 한 줄이 상태 코드까지 결정**한다는 뜻이다.
- `50` — 여기서 `ResponseEntity.status(...)`(HTTP 층)와 `BaseResponse.fail(...)`(계약 층)이 **같은 값으로 맞춰진다.** 2-3절에서 말한 "두 진실"이 어긋나지 않게 하는 지점이 바로 이 한 줄이다.

핸들러는 `BusinessException` 말고도 여러 예외를 같은 봉투로 번역한다. 그중 하나가 **버전 헤더 누락**이라 4절과 이어진다:

```kotlin

        if (e is ErrorResponse) {
```

- `85` — `ErrorResponse` 는 "자기가 몇 번 상태여야 하는지 아는 Spring 예외"의 인터페이스다.

### 3-4. 계약 — 클라이언트는 `code` 로만 분기한다

## 4. 헤더 버저닝 — 같은 URL, 다른 계약

### 4-1. 문제: 앱은 강제로 업데이트되지 않는다

웹은 새로고침하면 최신 코드가 뜬다. 앱은 아니다. **스토어에 새 버전을 올려도 옛 앱은 계속 살아서 서버를 호출**한다. 그래서 "온보딩 API가 이제 프로필 사진을 서버가 정해준다"처럼 계약을 바꿔야 할 때, 옛 앱을 깨뜨리지 않으면서 새 앱에는 새 계약을 줘야 한다.

전통적 해법은 URL을 나누는 것이다(`/api/v1/...` → `/api/v2/...`). kbap은 **URL을 그대로 두고 헤더로 가른다.**

| | URL 버저닝 (`/api/v2/members`) | 헤더 버저닝 (kbap) |
|---|---|---|
| 클라 변경 | 모든 호출 경로 문자열 교체 | 요청 헤더 한 줄만 교체 |
| 서버 코드 | 버전마다 컨트롤러 클래스가 늘어남 | 같은 클래스 안에 핸들러 메서드만 추가 |
| 리소스 정체성 | `/v1/members/1` 과 `/v2/members/1` 이 다른 URL — 같은 자원인데 주소가 둘 | 주소 하나 = 자원 하나 |
| 캐싱·로그 | 경로만 봐도 버전이 보임 | 경로만으론 안 보임 — **헤더까지 봐야 함** |
| 눈에 띔 | 명시적 | 숨어 있음(디버깅 시 함정) |

마지막 두 줄은 실제 비용이다. 프록시로 트래픽을 볼 때 **헤더를 안 펼치면 어느 계약으로 처리됐는지 모른다**([[프록시와 MITM 디버깅 (Proxyman)]]에서 헤더 확인하는 법 참조).

### 4-2. 프레임워크 기능이다 — 우리가 만든 게 아니다

### 4-4. `"1.1+"` 라는 표기

Spring은 버전을 `major.minor.patch` 로 파싱하고(빠진 자리는 0), 뒤의 `+` 는 **"이 버전 이상"** 을 뜻한다.

| 선언 | 매칭되는 요청 헤더 |
|---|---|
| `version = "1.0"` | 정확히 `1.0` 만 |
| `version = "1.1+"` | `1.1`, `1.2`, `2.0`, … (1.1 이상 전부) |
| `version` 없음 | 어느 버전이든 (버전 조건이 있는 매핑이 없는 매핑보다 우선) |

그래서 위 온보딩은 이렇게 갈린다 — `1.0` 요청은 첫 핸들러로, `1.1`·`1.2`·`2.0` 요청은 두 번째 핸들러로. **새 버전을 낼 때 옛 핸들러를 건드릴 필요가 없다**는 게 `+` 표기의 값이다.

메서드뿐 아니라 **클래스 전체**에도 걸 수 있다: `ReviewController` 는 `@RequestMapping(ApiPaths.API, version = "1.0+")`(`api/src/main/kotlin/com/kbap/api/review/ReviewController.kt:27`) 로 클래스 통째로 1.0 이상을 받는다.

### 4-5. 헤더를 빠뜨리면 — 400 `COMMON-002` 까지의 경로

이제 앞 절들이 이어진다. 순서대로:

1. `/api/members/...` 요청이 `X-API-Version` 없이 도착
2. 헤더 리졸버가 값을 못 찾음 → 폴백 리졸버도 `/api/` 경로엔 `null` 을 냄(`WebConfig.kt:33-37`)
3. `setVersionRequired(true)` 라서 Spring이 `MissingApiVersionException` 을 던짐 (지원 안 하는 버전을 보내면 `InvalidApiVersionException`)
4. 이 예외는 `ErrorResponseException` 계열이라 **자기 상태(400)를 안다**
5. `GlobalExceptionHandler.handleUnexpected` 의 `if (e is ErrorResponse)` 가지(`GlobalExceptionHandler.kt:85-89`)가 잡아 → **상태 400 + `code: "COMMON-002"`** 봉투로 변환
6. FE `client.ts` 가 봉투를 벗겨 `ApiError(message, 400, "COMMON-002")` 로 던짐

## 5. API 버전 ≠ 앱 버전

> [!info] 헷갈리기 쉬운 두 버전
> **API 버전**(`X-API-Version`)은 "이 요청을 어느 계약으로 처리할까"를 정한다 — 라우팅용이다.
> **앱 버전**(`X-App-Version`, 그리고 `GET /api/app-version`)은 "이 앱을 계속 쓰게 둘까, 스토어로 보낼까"를 정한다 — 게이트용이다.
> 둘은 값도 주기도 다르다. API 버전은 계약이 바뀔 때만 오르고, 앱 버전은 릴리스마다 오른다.

앱 버전 게이트의 서버 쪽은 `api/appversion/` 네 파일이 전부다. 응답은 최소 지원 버전·최신 버전·스토어 링크뿐이고(`AppVersionResponse.kt:7-13`), 판단(강제 업데이트를 띄울지)은 **앱이 한다** — 서버는 기준만 준다.

여기서 4-2절의 예외가 설명된다. `GET /api/app-version` 이 **`X-API-Version` 이 필요 없는 유일한 엔드포인트**인 이유는 이렇다:

> 계약이 크게 바뀌어 옛 앱을 전부 막아야 하는 상황을 상상해보자. 옛 앱은 옛 `X-API-Version` 을 보내고, 서버는 그걸 거부한다. 그런데 **"업데이트하세요"를 안내하는 API마저 거부당하면** 앱은 흰 화면만 띄우고 끝이다. 복구 경로가 사라진다.

그래서 이 하나만 버전 헤더 없이도 열려 있다. FE도 이 엔드포인트만 헤더를 빼도록 예외 처리한다 — `client.ts:40-41` 의 주석이 그대로 `유일 헤더 예외 엔드포인트 — 무인증·X-API-Version 자체가 없는 버전 게이트` 다.

**설계 교훈 하나**: 게이트를 만들 때는 **게이트를 안내하는 통로를 게이트 밖에 둬야 한다.**

## 6. 주의점 (읽다가 걸릴 것들)

- **반환 타입이 두 겹인 게 정상이다.** `ResponseEntity<BaseResponse<T>>` 를 보고 "왜 두 번 감싸지?" 하지 말 것 — 바깥은 HTTP, 안쪽은 우리 계약(2-1절).
- **`Unit` 을 담은 봉투가 흔하다.** `BaseResponse<Unit>` 은 "성공했고 돌려줄 알맹이는 없다"는 뜻이다(Kotlin의 `Unit` = TS의 `void`). FE는 `payload` 키 자체가 없어도 `success` 만 보고 통과시킨다(`client.ts:237-238`).
- **`message` 를 사용자에게 보여주지 않는다.** BE 문구는 한국어 고정이고 FE는 다국어다. `message` 는 개발자·로그용, 사용자 문구는 FE i18n이 만든다.
- **새 컨트롤러 경로를 만들면 `WebConfig` 의 JWT 보호 경로에도 등록해야 한다**(`WebConfig.kt:80-100`). 빠뜨리면 그 엔드포인트의 전 시나리오가 401로 실패한다 — 레포 문서가 "실제로 두 번 밟은 함정"이라고 적어둔 곳이다.
- **헤더 누락 400은 테스트로 안 잡힌다**(4-5절 콜아웃). 로컬 검증은 curl로.
- **`ErrorCode` 결번을 재사용하지 말 것.** `COMMON-001` 은 비어 있고 그대로 둔다. 옛 앱이 그 코드를 기억하고 있을 수 있다.

```
# 실패 응답 (HTTP는 ErrorCode.status)
{ "success": false, "message": "만료된 액세스 토큰입니다…", "code": "AUTH-004" }

# 필수 헤더 (GET /api/app-version 제외 전부)
X-API-Version: 1.0

# 헤더 빠뜨리면
HTTP 400 + { "success": false, "code": "COMMON-002", … }
```

| 하고 싶은 것 | 어디를 보나 |
|---|---|
| 응답 봉투 모양 | `api/core/BaseResponse.kt` |
| 에러 코드 전체 목록 | `common/core/error/ErrorCode.kt` |

## 8. 용어집

- **공통 응답 봉투(envelope)**: 모든 API 응답을 감싸는 고정 구조. kbap에선 `BaseResponse<T>`.
- **`payload`**: 봉투 안의 실제 알맹이. FE가 화면에 넘기는 것.
- **`code`**: 클라이언트가 분기에 쓰는 안정 식별자. `도메인-3자리`(`AUTH-004`). 문구와 달리 **바뀌지 않는다**는 약속.
- **`BusinessException`**: kbap의 유일한 비즈니스 예외 클래스. 구분은 클래스가 아니라 담긴 `ErrorCode` 가 한다.
- **`@RestControllerAdvice`**: 모든 컨트롤러에 걸치는 전역 예외 처리기를 선언하는 Spring 애너테이션.
- **`ErrorResponse`**: 자기가 어떤 HTTP 상태여야 하는지 아는 Spring 예외의 인터페이스. 404·405·버전 누락 등이 해당.
- **API 버저닝(header-based)**: 같은 URL을 요청 헤더 값으로 다른 핸들러에 보내는 라우팅. Spring Framework 7.0의 기본 기능.
- **`"1.1+"`**: "1.1 이상"을 뜻하는 버전 매칭 표기. `"1.0"` 은 정확히 그 버전만.
- **`X-API-Version` vs `X-App-Version`**: 앞은 계약 라우팅용(서버가 씀), 뒤는 앱 릴리스 식별용(게이트·로그용).
- **springdoc / Swagger UI**: 코드에서 API 문서를 자동 생성하는 도구. kbap은 버전별 그룹 문서를 만든다.

## 9. 다음에 빠른 재현 체크리스트

1. 아무 컨트롤러나 열어 반환 타입이 `ResponseEntity<BaseResponse<T>>` 인지 본다 — 아니면 규약 위반이다.
2. 그 메서드에 `version = ` 이 붙어 있나? 붙어 있으면 이건 **특정 버전 전용 계약**이다. 없으면 기본(옛) 계약.
3. 새 에러가 필요하면 → `ErrorCode` 에 `도메인-다음번호` 로 **한 줄 추가**(결번 재사용 금지) → 서비스에서 `throw BusinessException(ErrorCode.XXX)`. 컨트롤러·핸들러는 손대지 않는다.
4. 계약을 바꿔야 하면 → 경로는 그대로, 같은 컨트롤러에 `version = "N.N+"` 핸들러를 **추가**. 옛 핸들러는 건드리지 않는다.
5. 새 경로를 만들었으면 → `WebConfig` 의 `addUrlPatterns` 에 등록했는지 확인(안 하면 전부 401).
6. FE에서 새 에러를 분기하려면 → `ApiError.code` 로 비교. `message` 매칭 금지.
7. 버전 라우팅이 의심되면 → curl로 헤더를 바꿔가며 응답 차이를 직접 본다. 테스트는 기본 헤더를 붙이므로 못 믿는다.
