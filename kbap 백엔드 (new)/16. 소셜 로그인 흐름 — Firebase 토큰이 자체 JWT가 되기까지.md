# 16. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지

> 작성: 2026-08-27 · 맥락: 15번에서 "이미 로그인한 회원"이 프로필을 저장하는 길을 봤다. 그런데 **그 회원은 애초에 어떻게 생겼고, `@AuthMemberId memberId: Long` 은 어디서 왔나?** 이 노트가 그 앞단이다.
> 목표: `POST /api/auth/login` 한 번에 어떤 파일들이 어떤 순서로 실행되는지 말할 수 있고, **"Firebase 를 쓰면서 왜 우리 JWT 를 또 발급하나"** 에 답할 수 있게 되기.

---

## 0. 한 줄 요약

앱이 Firebase 로 구글·애플 로그인을 마치고 받은 **ID 토큰 한 장**을 서버에 던지면, 서버는 그걸 **딱 한 번** 검증해 소셜 신원(provider + 원본 uid)을 꺼내고, 그 신원으로 회원을 찾거나 만든 뒤, **그 이후의 모든 요청에 쓸 자체 토큰 두 장(access·refresh)** 을 발급해 돌려준다. Firebase 는 여기서 끝나고, 앱의 남은 생애는 우리 토큰으로 산다.

---

## 1. 이 흐름의 입구는 서버가 아니다 — 앱에서 시작한다

이 노트가 다른 흐름 노트와 다른 점: **입구의 절반을 이미 직접 만들었다.** 서버 코드를 열기 전에 그 이음매부터 잇는다.

앱에서 일어나는 일은 세 단계다.

```
① 네이티브 소셜 로그인 시트   GoogleSignin.signIn() / AppleAuthentication.signInAsync()
        ↓ (구글·애플이 발급한 idToken / identityToken)
② Firebase 세션 만들기        signInWithCredential(getAuth(), ...Provider.credential(...))
        ↓ (Firebase 가 자기 형식으로 재포장한 ID 토큰)
③ 서버에 제출                 POST /api/auth/login { idToken }      ← 여기부터가 이 노트
```

③의 실코드가 이것이다 — `kbap-fe/src/lib/auth/useSocialAuth.ts:50-55`

```typescript
const exchange = async (): Promise<boolean> => {
  const idToken = await getAuth().currentUser?.getIdToken();
  if (!idToken) throw new Error('no firebase id token after sign-in');
  const { newMember } = await exchangeLogin(idToken);
  return newMember;
};
```

- `2` — 서버로 보내는 토큰은 **구글이 준 `res.data.idToken` 이 아니라**(그건 `:68` 에서 Firebase 에 넘겨주고 끝났다) **Firebase 세션이 발급한 ID 토큰**이다. 한 흐름 안에 이름이 같은 토큰이 두 장 돌아다니니 헷갈리기 쉽다.
- `4` — `exchangeLogin` 은 `kbap-fe/src/lib/auth/beAuth.ts:54-60` 이고, 그 안이 `api.post('/auth/login', { idToken })` 이다.

> [!tip] ①이 왜 그렇게 고생스러웠나
> ① 단계에서 안드로이드가 `DEVELOPER_ERROR`(code 10) 를 뱉던 사고와 `accessToken cannot be empty` 2차 벽은 [[Android 구글 로그인 — SHA-1·OAuth 클라이언트·DEVELOPER_ERROR]] 에 정리돼 있다. **그 노트가 끝나는 지점에서 이 노트가 시작한다** — 거기서 얻어낸 `idToken` 이 여기 `:51` 로 들어온다.

> [!warning] FE 주석 하나가 낡았다
> `useSocialAuth.ts:10-12` 의 헤더 주석은 이렇게 적혀 있다 — *"No BE hand-off here: the BE only verifies the ID token per request with the Admin SDK."* **지금 코드는 정반대다.** 같은 파일 `:25` 가 `exchangeLogin` 을 import 하고 `:53` 이 실제로 호출한다. 이 주석은 **KB-109 시절의 옛 설계**(매 요청마다 Firebase 토큰을 서버가 검증) 를 기술한 화석이고, `beAuth.ts:122-123` 이 그 교체를 명시한다 — *"KB-109의 Firebase ID토큰 부착 구조를 이걸로 교체한다."*
> 그리고 그 폐기된 설계가 바로 다음 절의 질문에 대한 답이다.

## 2. 왜 Firebase 를 쓰면서 자체 JWT 를 또 발급하나

이 노트의 뼈대다. Firebase 토큰을 그냥 계속 쓰면 안 되나?

**옛 설계(KB-109)가 실제로 그거였다.** 앱이 모든 요청에 Firebase ID 토큰을 붙이고, 서버가 매번 Firebase Admin SDK 로 검증한다. 돌아가긴 한다. 그런데 교체됐다. 두 토큰이 **보증하는 것이 다르기 때문**이다.

| | Firebase ID 토큰 | kbap access 토큰 |
|---|---|---|
| 누가 서명 | 구글(Firebase 프로젝트 키) | 우리 서버 (`kbap.auth.jwt.secret`) |
| 보증하는 것 | **"이 사람은 구글/애플 계정 X 의 소유자다"** | **"이 요청은 kbap 회원 #42 다"** |
| 담긴 신원 | 소셜 uid, 이메일, provider | `memberId` 하나 + role |
| 검증 비용 | Admin SDK — 구글 공개키가 필요 | 우리 비밀키로 로컬 서명 검증. 네트워크 0 |
| 수명 | 1시간 (구글이 정함) | 30분 / refresh 14일 (우리가 정함, `application.yml:61-62`) |
| 무효화 | 우리가 못 한다 | refresh 를 Redis 에서 지우면 끝 |

핵심은 첫 두 줄이다.

> **Firebase 는 "누구인가"를 증명하고, kbap 토큰은 "우리 서비스에서 누구인가"를 증명한다.**

`memberId` 는 Firebase 가 모르는 값이다. Firebase 토큰을 계속 쓰면 서버는 **매 요청마다** 소셜 uid → `memberId` 조회를 한 번씩 더 해야 한다. 자체 토큰에 `memberId` 를 박아두면 그 조회가 사라진다 — `sub` 를 `Long` 으로 파싱하는 것으로 끝난다.

수명과 무효화도 크다. Firebase 토큰의 수명은 구글이 정하고, 우리가 특정 사용자를 강제 로그아웃시킬 수단이 없다. 자체 토큰이면 access 는 짧게(30분) 두고 refresh 를 Redis 에서 지우는 것으로 세션을 끊을 수 있다 — 그게 로그아웃이다.

그래서 결론:

> **Firebase 는 소셜 검증까지만. 그 이후의 세션은 전부 우리 토큰.**
> 이 흐름은 그 **단 한 번의 교환**이다.

토큰 인증 일반론(왜 앱은 쿠키·세션을 안 쓰는가, access/refresh 를 왜 둘로 쪼개는가)은 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]] 에 있다. OIDC 의 ID 토큰이 뭔지는 [[OAuth 2.0과 OIDC — 소셜 로그인의 원리]] §4·§7.

## 4. 실코드로 따라가기

### 4-1. 컨트롤러 — 세 줄

`api/src/main/kotlin/com/kbap/api/auth/AuthController.kt:15-21`

```kotlin
@PostMapping("/login")
override fun login(
    @Valid @RequestBody request: LoginRequest,
): ResponseEntity<BaseResponse<LoginResponse>> {
    val result = authService.login(request.idToken)
    return ResponseEntity.ok(BaseResponse.ok(LoginResponse.from(result)))
}
```

- `1` — 클래스에 `@RequestMapping(ApiPaths.API + "/auth")`(`:11`) 가 붙어 있으니 최종 경로는 `/api/auth/login`. **`/v1` 이 없다** — 버전은 경로가 아니라 `X-API-Version` 헤더다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]).
- `3` — `@Valid` 가 `LoginRequest` 의 `@field:NotBlank`(`LoginRequest.kt:6`) 를 강제한다. 빈 문자열이면 **서비스에 도달하기 전에** 400 `COMMON-002`.
- `6` — `authService.login()` 이 반환한 `LoginResult` 를 그대로 내보내지 않고 `LoginResponse.from()` 으로 한 번 갈아탄다. 이유는 4-6절.
- `override` — 컨트롤러가 `AuthApi` 인터페이스를 구현한다. Swagger 애너테이션 수십 줄이 전부 그쪽에 있어서 컨트롤러 본문이 깨끗하다.

> [!note] 트랜잭션이 없다
> `AuthController.login` → `AuthService.login` 경로에 `@Transactional` 이 **하나도 없다.** DB 를 만지는 `findOrSignUp` 안쪽(`memberRepository.save`)만 Spring Data 의 기본 트랜잭션으로 각각 돈다. 외부 HTTP 호출(Firebase 검증)이 이 흐름 한복판에 있는데 그걸 트랜잭션으로 감싸면 **네트워크가 느린 만큼 DB 커넥션을 붙잡고 있게 된다.** 경계 규약은 [[6. 설정과 프로필, 트랜잭션 경계]].

### 4-2. 서비스 — 이 흐름의 전부

`api/src/main/kotlin/com/kbap/api/auth/AuthService.kt:30-44`

```kotlin
fun login(idToken: String): LoginResult {
    val identity = socialTokenVerifier.verify(idToken)
    val (member, isNewMember) = memberService.findOrSignUp(identity)
    val memberId = member.id

    val refreshToken = tokenIssuer.issueRefreshToken(memberId)
    refreshTokenStore.save(refreshToken.jti, memberId, refreshTtl)

    return LoginResult(
        memberId = memberId,
        newMember = isNewMember,
        accessToken = tokenIssuer.issueAccessToken(memberId, MemberRole.USER),
        refreshToken = refreshToken.token,
    )
}
```

이 15줄이 이 노트 제목의 전부다. 읽는 법:

- `2` **검증** — 여기서 Firebase 가 등장하고 **여기서 끝난다.** 아래 어디에도 Firebase 라는 단어가 없다.
- `3` **회원 확보** — 조회든 가입이든 이 한 줄. `Pair<Member, Boolean>` 의 뒤 값이 "새로 만들었나".
- `5-6` **refresh 발급 + 저장** — 발급만으로는 부족하고 서버가 `jti` 를 기억해야 한다. 이걸 기억해야 로그아웃·회전이 가능하다. Redis 쪽 이야기는 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]].
- `12` **access 발급** — role 은 **항상 `MemberRole.USER` 하드코딩**이다. `MemberRole` 에는 `ADMIN` 도 있지만(`MemberRole.kt:3-6`) 이 엔드포인트로는 절대 나오지 않는다. 관리자는 다른 문으로 들어온다.

주목할 것: **`AuthService` 의 생성자 파라미터 6개 중 4개가 인터페이스**다(`:20-25`).

```kotlin
class AuthService(
    private val socialTokenVerifier: SocialTokenVerifier,
    private val memberService: MemberService,
    private val tokenIssuer: TokenIssuer,
    private val tokenParser: TokenParser,
    private val refreshTokenStore: RefreshTokenStore,
    private val socialAccountDeleter: SocialAccountDeleter,
```

`FirebaseTokenVerifier` 도 `JwtTokenIssuer` 도 `RedisRefreshTokenStore` 도 여기 이름이 안 보인다. **`common.port.auth` 의 포트 5개가 전부 이 클래스 하나에 모여 있다** — 레포에서 포트·어댑터가 가장 진하게 쓰인 자리다. 왜 이렇게 하는지는 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] §2·§3.

이 흐름(`login`)에서 실제로 불리는 건 그중 3개다:

| 포트 | 이 흐름에서 | 구현체 | 나머지 |
|---|---|---|---|
| `SocialTokenVerifier` | ✅ `:31` | `FirebaseTokenVerifier` | — |
| `TokenIssuer` | ✅ `:35`,`:41` | `JwtTokenIssuer` | — |
| `RefreshTokenStore` | ✅ `:36` (save 만) | `RedisRefreshTokenStore` | consume·delete 는 17번 |
| `TokenParser` | ❌ | `JwtTokenParser` | refresh·logout 전용 → 17번 |
| `SocialAccountDeleter` | ❌ | `FirebaseAccountDeleter` | 탈퇴 전용 → **§8** |

> **로그인은 토큰을 한 번도 파싱하지 않는다.** 만들기만 한다. 파싱은 전부 다음 노트의 일이다.

### 4-3. Firebase 검증 — 어댑터 두 장

`api/src/main/kotlin/com/kbap/api/infra/auth/firebase/FirebaseTokenVerifier.kt:17-32`

```kotlin
override fun verify(idToken: String): SocialIdentity {
    val decoded = try {
        FirebaseAuth.getInstance(firebaseApp).verifyIdToken(idToken)
    } catch (e: FirebaseAuthException) {
        log.warn("Firebase ID 토큰 검증 실패: authErrorCode={}, message={}", e.authErrorCode, e.message)
        throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)
    } catch (e: IllegalArgumentException) {
        log.warn("Firebase ID 토큰 형식 오류: {}", e.message)
        throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)
    }
    return FirebaseClaimMapper.toSocialIdentity(decoded.claims)
}
```

- `3` — `verifyIdToken` 한 줄이 서명·발급자(`iss`)·수신자(`aud`)·만료(`exp`) 를 전부 본다. [[OAuth 2.0과 OIDC — 소셜 로그인의 원리]] §7 의 "서버가 하는 5가지 체크"를 Admin SDK 가 대신해 주는 것.
- `4-9` — **어댑터의 본업이 여기 있다.** Firebase 예외(`FirebaseAuthException`)를 **우리 예외**(`BusinessException(INVALID_SOCIAL_TOKEN)`)로 갈아끼운다. 이걸 안 하면 벤더 예외가 서비스·컨트롤러까지 새어 나가고, Firebase 를 갈아끼울 때 그 전부를 고쳐야 한다.
- `11` — Firebase 자료구조(`decoded.claims`)는 **여기서 끝난다.** 밖으로는 우리 도메인 타입만 나간다.

번역기는 별도 object 다 — `FirebaseClaimMapper.kt:14-37`

```kotlin
private val PROVIDERS = mapOf(
    "google.com" to SocialProvider.GOOGLE,
    "apple.com" to SocialProvider.APPLE,
)

fun toSocialIdentity(claims: Map<String, Any?>): SocialIdentity {
    val firebase = claims[FIREBASE_CLAIM] as? Map<*, *> ?: throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)
    val signInProvider = firebase[SIGN_IN_PROVIDER] as? String ?: throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)
    val provider = PROVIDERS[signInProvider] ?: throw BusinessException(ErrorCode.UNSUPPORTED_PROVIDER)

    val identities = firebase[IDENTITIES] as? Map<*, *> ?: throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)
    val providerUserId = (identities[signInProvider] as? List<*>)
        ?.firstOrNull()?.toString()?.takeIf { it.isNotBlank() }
        ?: throw BusinessException(ErrorCode.INVALID_SOCIAL_TOKEN)

    return SocialIdentity(provider = provider, providerUserId = providerUserId, email = claims[EMAIL] as? String)
}
```

- `1-4` — **문자열 `"google.com"` 이 `SocialProvider.GOOGLE` 이 되는 지점이 이 세 줄이다.** 이 맵에 없는 provider 는 `UNSUPPORTED_PROVIDER`(AUTH-002, 401). 카카오·네이버를 붙인다면 여기가 첫 수정 지점이다.
- `10-12` — 꺼내는 건 `firebase.identities["google.com"][0]`, 즉 **구글·애플이 발급한 원본 sub**다. **최상위 `sub`(= Firebase 내부 uid) 가 아니다.**
- `15` — `email` 만 `as? String` 이라 **실패해도 예외가 아니고 null 이 된다.**

### 4-4. 왜 uid 로 식별하고 이메일은 nullable 인가

앞 절 마지막 두 줄이 이 노트에서 가장 중요한 설계 결정이다.

**① 이메일로 식별하면 애플에서 깨진다.** 사용자가 "이메일 숨기기"를 고르면 `abc123@privaterelay.appleid.com` 같은 릴레이 주소가 오고, 아예 안 올 수도 있다. 그래서 스키마의 `email` 은 nullable 이고 unique 도 아니다 — `V2026.07.16.21.38.41__init_schema.sql`

```sql
`provider`     enum('GOOGLE','APPLE') NOT NULL,
`provider_uid` varchar(255)           NOT NULL,
`email`        varchar(255)           DEFAULT NULL,
...
UNIQUE KEY `uk_member_provider_uid` (`provider`,`provider_uid`)
```

**신원 키는 `(provider, provider_uid)` 복합 unique 다. 이메일은 참고 정보일 뿐이다.** 이게 정확히 [[Google vs Apple 소셜 로그인 비교]] §5-1 의 결론("유저 테이블: `provider(iss) + provider_user_id(sub)` 복합 식별. 이메일은 참고 정보") 이고, 그 노트를 쓸 땐 원리였던 것이 여기서 DDL 로 서 있다.

**② Firebase uid 를 쓰면 Firebase 에 잠긴다.** Firebase 내부 uid 는 Firebase 프로젝트가 사라지면 의미가 없다. 구글·애플의 원본 sub 는 Firebase 없이도 유효하다. 나중에 Firebase 를 걷어내고 직접 OIDC 검증으로 가더라도 **회원 테이블은 그대로 쓸 수 있다.**

②는 말이 아니라 **테스트로 못 박혀 있다** — `FirebaseClaimMapperTest.kt:40-52`

```kotlin
`when`("최상위 sub(Firebase uid)와 비교하면") {
    then("Firebase uid 는 저장하지 않는다") {
        val identity = FirebaseClaimMapper.toSocialIdentity(
            claims(signInProvider = "google.com",
                   identities = mapOf("google.com" to listOf("google-original-sub")),
                   uid = "firebase-uid-should-not-be-stored"),
        )
        (identity.providerUserId != "firebase-uid-should-not-be-stored") shouldBe true
    }
}
```

픽스처 문자열이 `"firebase-uid-should-not-be-stored"` 다. 테스트가 **의도를 문서처럼** 적어놨다.

애플 릴레이 이메일과 이메일 없음도 각각 테스트가 있다(`:55-84`).

### 4-5. 신규 가입 vs 기존 로그인 — 한 엔드포인트가 둘 다 한다

`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:70-87`

```kotlin
private fun findByIdentity(identity: SocialIdentity): Member? =
    memberRepository.findByProviderAndProviderUidAndMemberStatus(
        identity.provider, identity.providerUserId, MemberStatus.ACTIVE,
    )

fun findOrSignUp(identity: SocialIdentity): Pair<Member, Boolean> {
    findByIdentity(identity)?.let { return it to false }

    return try {
        memberRepository.save(Member.signUp(identity)) to true
    } catch (e: DataIntegrityViolationException) {
        val existing = findByIdentity(identity)
            ?: throw BusinessException(ErrorCode.DUPLICATE_SOCIAL_IDENTITY)
        existing to false
    }
}
```

- `7` — 있으면 `false`(기존 로그인). **가입 API 가 따로 없다.** 앱에는 "회원가입" 버튼이 없고 소셜 버튼만 있으니, 서버도 문을 하나만 뒀다.
- `10` — 없으면 만들고 `true`.
- `11-15` **동시 요청 방어.** 사용자가 로그인 버튼을 두 번 빠르게 누르면 두 요청이 `:7` 을 동시에 통과할 수 있다. 둘 다 `save` 를 시도하고, 하나는 `uk_member_provider_uid` 에 걸려 `DataIntegrityViolationException`. 그때 **다시 조회해서 방금 남이 만든 회원을 쓴다.** 애플리케이션 락 없이 **DB unique 인덱스가 경쟁을 심판**한다.

> [!tip] FE 감각으로
> `findOrSignUp` 은 React Query 의 `getQueryData` → 없으면 `fetch` 와 모양이 같다. 다른 건 **경쟁이 실재한다**는 것. 브라우저 탭 하나 안에서는 중복 fetch 가 낭비로 끝나지만, 서버에서는 중복 INSERT 가 **회원 두 명**이 된다. 그래서 `catch` 절이 필요하다.

**정지 회원은 어떻게 거절되나 — 명시적 체크가 없다.** `:1-4` 의 조회 조건에 `MemberStatus.ACTIVE` 가 들어 있어서 정지 회원은 "없는" 것으로 나온다. 그러면 `:10` 이 `save` 를 시도하고 → unique 에 걸리고 → `:12` 의 재조회도 ACTIVE 가 아니라 null → `DUPLICATE_SOCIAL_IDENTITY`(MEMBER-001, 409). **정지 회원 거절은 unique 인덱스에서 파생된 부수 효과**다. 그래서 테스트가 상태 코드를 특정하지 않고 `(result.status >= 400) shouldBe true` 라고만 쓴다(`AuthControllerTest.kt:241`).

가입 직후 상태는 도메인이 정의한다 — `common/domain/member/model/Member.kt:165-170`

```kotlin
fun signUp(identity: SocialIdentity): Member =
    Member(
        provider = identity.provider,
        providerUid = identity.providerUserId,
        email = identity.email,
    )
```

나머지 필드는 전부 **생성자 기본값**이다(`:22-74`) — `nickname = null`, `onboardingCompleted = false`, `scanCount = 0`, `memberStatus = ACTIVE`. 즉 **가입 = 신원 세 개만 있고 프로필은 텅 빈 회원**. 그 빈칸을 채우는 게 15번 노트다.

> [!note] 엔티티가 곧 도메인 모델
> `Member` 는 `@Entity` 이면서 `signUp`·`completeOnboarding`·`withdraw` 같은 도메인 메서드를 직접 갖는다. 별도 도메인 클래스와 `toDomain()` 변환이 없다 — [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]].
> 또 `Member` 에는 `@OneToMany` 가 하나도 없다. 회원↔리뷰·스캔은 전부 `Long` id 참조다 — [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]].

### 4-6. 토큰 두 장 만들기

`api/src/main/kotlin/com/kbap/api/infra/auth/token/JwtTokenIssuer.kt:22-46`

```kotlin
override fun issueAccessToken(memberId: Long, role: MemberRole): String {
    val now = System.currentTimeMillis()
    return Jwts.builder()
        .subject(memberId.toString())
        .claim(TokenType.CLAIM, TokenType.ACCESS.name)
        .claim(ROLE_CLAIM, role.name)
        .issuedAt(Date(now))
        .expiration(Date(now + properties.accessTtl.toMillis()))
        .signWith(key)
        .compact()
}

override fun issueRefreshToken(memberId: Long): IssuedRefreshToken {
    val now = System.currentTimeMillis()
    val jti = UUID.randomUUID().toString()
    val token = Jwts.builder()
        .subject(memberId.toString())
        .claim(TokenType.CLAIM, TokenType.REFRESH.name)
        .id(jti)
        ...
    return IssuedRefreshToken(token = token, jti = jti)
}
```

두 장의 차이가 전부 여기 보인다.

| | access | refresh |
|---|---|---|
| `sub` | `memberId` | `memberId` |
| `token_type` | `ACCESS` | `REFRESH` |
| `role` | 있음 | **없음** |
| `jti` | **없음** | 있음 (UUID) |
| 수명 | `access-ttl: 30m` | `refresh-ttl: 14d` (둘 다 `application.yml:61-62`. 왜 이 길이인지는 17번) |
| 서버가 기억? | 아니오 (stateless) | **예 — Redis** |

- `5`·`19` — 발급 시 **`token_type` 클레임을 박는다**(`TokenType.kt` 에 `ACCESS`·`REFRESH`·`SCAN_TICKET` 세 값). 이걸로 무엇을 막는지, 검증하는 쪽이 어떻게 강제하는지는 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] 정본.
- `16` — `jti`(JWT ID) 는 refresh **에만** 있다. 이게 Redis 키가 되고(`RedisRefreshTokenStore.kt:23` 의 `auth:refresh:{jti}`), 그래서 refresh 만 서버가 무효화할 수 있다.
- `9` — HMAC-SHA256 대칭키 서명. 키는 `JwtTokenProperties.kt:10-14` 가 **32바이트 미만이면 부팅을 실패시킨다.** 약한 키로 조용히 뜨는 사고를 막는 장치다.

`AuthService` 는 이 클래스를 모른다 — `TokenIssuer` 포트만 안다.

> [!warning] 토큰에 개인정보를 넣지 않는다
> JWT payload 는 **암호화가 아니라 서명**이다. Base64 라서 누구나 디코딩해 읽을 수 있다([[OAuth 2.0과 OIDC — 소셜 로그인의 원리]] §4-2). 그래서 클레임은 `memberId`·`token_type`·`role` 뿐이고 이메일·닉네임은 없다. **이 규칙도 테스트가 지킨다** — `AuthControllerTest.kt:248-256` 이 access 토큰 payload 를 직접 Base64 디코딩해 `payload.contains("gmail.com") shouldBe false` 를 단언한다.

### 4-7. 나가는 문 — `LoginResult` 와 `LoginResponse` 가 왜 둘인가

두 클래스가 거의 같아 보인다.

```kotlin
// api/auth/LoginResult.kt:3-8            // api/auth/LoginResponse.kt:4-8
data class LoginResult(                   data class LoginResponse(
    val memberId: Long,                       val newMember: Boolean,
    val newMember: Boolean,                   val accessToken: String,
    val accessToken: String,                  val refreshToken: String,
    val refreshToken: String,             )
)
```

**차이는 `memberId` 한 줄이다.** 서비스는 `memberId` 를 담아 돌려주지만 **응답에는 싣지 않는다.** 앱은 자기 회원 번호를 알 필요가 없고(access 토큰이 대신 말한다), 안 주면 안 새어 나간다. 이 한 줄이 "DTO 를 왜 계층마다 따로 두나"의 가장 짧은 실증이다 — FE 로 치면 **API 응답 타입과 화면 상태 타입을 나누는 것**과 같은 이유고, 여기선 안쪽 타입을 밖으로 안 내보내는 쪽이다.

이것도 테스트가 지킨다 — `AuthControllerTest.kt:168` 의 `payload.has("memberId") shouldBe false`.

## 5. 계층 경계마다 — 여기서 왜 모듈이 바뀌나

이 흐름은 두 모듈(`:api`·`:common`)을 네 번 넘나든다.

```
:api      AuthController ──▶ AuthService ─────────────────┬──▶ MemberService
                                  │                        │
                                  │ (포트 타입으로만 통신)    │
:common                    port.auth.*                domain.member.model.Member
                                  │                        │      MemberJpaRepository
:api                    infra.auth.firebase.*
                        infra.auth.token.*
                        infra.redis.*
```

| 경계 | 넘어가는 이유 |
|---|---|
| `AuthService` → `common.port.auth` | **계약은 아무에게도 의존하지 않는 자리에 있어야 한다.** `common` 은 모두가 의존하고 아무도 의존하지 않는 모듈이다([[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]). 포트가 `api` 에 있으면 batch 가 못 쓴다 |
| `common.port` → `api.infra.auth` | **구현은 쓰는 쪽에 둔다.** Firebase 검증은 웹 API 만 필요하니 `api.infra` 다. batch 도 썼다면 `common.infra` 로 갔다(ADR-0018) |
| `AuthService` → `MemberService` | 회원 도메인 규칙(`ACTIVE` 만 조회, 가입 시 기본값)은 **auth 가 아니라 member 의 것**이다. auth 는 "신원 하나 줄 테니 회원 찾아줘"만 안다 |
| `Member` → `common.domain` | 엔티티는 `common` 에 산다. `api` 도 `batch` 도 같은 `Member` 를 쓴다 |

**방향은 절대 역전되지 않는다.** `common.port.auth.SocialTokenVerifier` 는 `FirebaseTokenVerifier` 를 모르고, `Member` 는 `TokenIssuer` 를 모른다. 이 방향은 말이 아니라 **ArchUnit 테스트가 컴파일 이후에 강제**한다 — [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]].

포트가 도메인 타입을 반환하는 건 허용된다(`SocialTokenVerifier.verify` 가 `SocialIdentity` 를 준다). 반대는 금지. 근거는 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] §7.

## 6. 조립 — 누가 무엇을 꽂아주나

`AuthService` 가 인터페이스 5개를 받는다면, 그 자리에 실제 객체를 넣는 건 누구인가. 컨테이너다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]). 다만 Firebase 는 **자격증명이 있을 때만** 만들 수 있으므로 `@Component` 로는 안 되고 config 가 직접 만든다.

`api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:25-37`

```kotlin
@Bean
fun socialTokenVerifier(
    @Value("\${kbap.auth.firebase.credentials-json:}") credentialsJson: String,
    @Value("\${kbap.auth.firebase.credentials-path:}") credentialsPath: String,
): SocialTokenVerifier {
    val verifier = FirebaseSocialAuth.tokenVerifierOrNull(credentialsJson, credentialsPath)
    if (verifier == null) {
        log.warn("Firebase 자격증명 미설정 — 소셜 로그인 비활성(모든 로그인이 401 로 거절된다)")
        return UnavailableSocialAuth
    }
    log.info("Firebase 토큰 검증기 활성화")
    return verifier
}
```

- `5` — **반환 타입이 포트다.** 소비자 입장에서 진짜 Firebase 검증기든 폴백이든 구분되지 않는다.
- `8-9` — 자격증명이 없으면 `UnavailableSocialAuth`(`api/auth/UnavailableSocialAuth.kt:10-15`) 를 꽂는다. 이 object 의 `verify` 는 **무조건 `INVALID_SOCIAL_TOKEN` 을 던진다.**

이 폴백의 값어치: **서버가 뜬다.** 자격증명 없이 `@Component` 였다면 부팅이 실패하고, 로그인과 무관한 음식 조회·커뮤니티 API 까지 전부 죽는다. 이 설계면 **로그인만 401** 이고 나머지는 산다. `application.yml:53` 이 그 의도를 그대로 적어놨다 — *"둘 다 없으면 항상 거절하는 폴백 검증기가 등록되어 부팅은 정상이고 `/api/auth/login` 만 401 이다."* 같은 패턴의 다른 사례들은 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] §3-3.

## 7. 요청과 응답 실물

**요청**

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json
X-API-Version: 1.0

{ "idToken": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjE2N..." }
```

`Authorization` 헤더가 **없다.** 아직 토큰이 없으니 당연하고, 그래서 `WebConfig.kt:80-99` 의 `JwtAuthenticationFilter` URL 패턴 목록에 `/api/auth/login` 이 들어 있지 않다 — 이 요청은 필터를 아예 지나지 않는다. 같은 목록에 `/api/auth/withdraw`(`:98`) 는 **들어 있다** — 탈퇴는 로그인한 사람만 할 수 있으니까. 그 필터가 17번의 주제다.

**응답 (신규 가입)**

```json
{
  "success": true,
  "payload": {
    "newMember": true,
    "accessToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInRva2VuX3R5cGUiOiJBQ0NFU1MiLCJyb2xlIjoiVVNFUiIsImlhdCI6...",
    "refreshToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInRva2VuX3R5cGUiOiJSRUZSRVNIIiwianRpIjoiM2Y5Yy0uLi4iLCJpYXQiOiI..."
  },
  "message": null,
  "code": null
}
```

`{success, payload, message, code}` 봉투는 모든 응답이 공유한다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]). `Set-Cookie` 헤더는 **없다** — 토큰은 본문으로만 간다.

**access 토큰 payload 를 디코딩하면** (누구나 할 수 있다)

```json
{ "sub": "42", "token_type": "ACCESS", "role": "USER", "iat": 1756..., "exp": 1756... }
```

**실패 응답**

| 상황 | 상태 | `code` | 어디서 |
|---|---|---|---|
| `idToken` 이 빈 문자열 | 400 | `COMMON-002` | `@Valid` (컨트롤러 진입 전) |
| 서명 위조·만료·`aud` 불일치 | 401 | `AUTH-001` | `FirebaseTokenVerifier.kt:26` |
| 구글·애플 아닌 provider | 401 | `AUTH-002` | `FirebaseClaimMapper.kt:23` |
| claims 구조 훼손 | 401 | `AUTH-001` | `FirebaseClaimMapper.kt:20,22,25,30` |
| 정지(SUSPENDED) 회원 | 409 | `MEMBER-001` | `MemberService.kt:84` (unique 파생) |
| Firebase 자격증명 미설정 | 401 | `AUTH-001` | `UnavailableSocialAuth.kt:11` |

> [!warning] 스펙과 다름
> `specs/kb-118-firebase-jwt-auth/spec.md` 의 **제목**은 *"자체 JWT **쿠키** 발급·재발급·로그아웃"* 이고 US2 본문에도 *"쿠키 제거"* 가 남아 있다. **코드는 쿠키를 쓰지 않는다.** 토큰은 응답 본문으로만 가고, `AuthControllerTest.kt:169` 가 `result.getHeaders("Set-Cookie").isEmpty() shouldBe true` 로 **쿠키가 없음을 적극적으로 단언**한다. 같은 spec 의 US1 본문도 이미 "응답 본문으로 내려주고"라고 고쳐 쓰여 있다 — **제목만 초안 시절 표현이 남았다.** 앱은 쿠키 저장소가 없으니 본문이 맞다([[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]] §4).

## 8. 되감기 — 탈퇴는 로그인을 거꾸로 되돌린다

`PATCH /api/auth/withdraw` 는 같은 컨트롤러에 있고, **로그인이 만든 것을 정확히 역순으로 지운다.** 그래서 이 노트에 붙인다 — 쓰는 포트도 Firebase 어댑터 짝(`SocialAccountDeleter` ↔ `FirebaseAccountDeleter`)이라 4-3절과 같은 자리다.

`api/src/main/kotlin/com/kbap/api/auth/AuthService.kt:80-87`

```kotlin
// 소셜 계정 삭제(외부 호출)를 트랜잭션 밖에서 먼저 수행하고, DB 탈퇴 마킹은 MemberService 트랜잭션에 맡긴다.
fun withdraw(memberId: Long) {
    val member = memberService.getMember(memberId)

    deleteSocialAccount(memberId, member.identity)

    memberService.withdraw(memberId)
}
```

- `1` — **레포에서 보기 드문 Kotlin 주석**이다(kbap 은 self-documenting 을 원칙으로 주석을 거의 안 쓴다). 순서가 자명하지 않아서 남긴 것이고, 그 순서가 이 절의 핵심이다.
- `3` — 저장해 둔 `member.identity`(= `provider` + `providerUid`) 를 꺼낸다. 로그인 때 넣어둔 바로 그 값이다.
- `5` **먼저 Firebase 를 지우고** → `7` **그 다음 DB 를 지운다.**

**왜 이 순서인가.** 반대로 하면 DB 를 지운 뒤 Firebase 삭제가 실패했을 때 `providerUid` 를 잃어버려 **어느 Firebase 계정을 지워야 하는지 알 방법이 사라진다.** 지금 순서면 Firebase 가 실패해도 DB 는 그대로라 재시도가 가능하다 — `:89-103` 이 실패를 삼키지 않고 로그를 남긴 뒤 `SOCIAL_ACCOUNT_DELETE_FAILED`(AUTH-007, **500**) 를 던져 **부분 탈퇴를 만들지 않는다.**

DB 쪽에서 실제로 지워지는 방식은 `common/domain/member/model/Member.kt:152-155`

```kotlin
fun withdraw() {
    providerUid = deletedProviderUid(id)
    delete()
}
```

- `2` — `providerUid` 를 `"DELETED:{id}"` 로 덮어쓴다. **`uk_member_provider_uid` 자리를 비워주는 것**이라 같은 소셜 계정으로 재가입이 열린다(4-5절의 `findOrSignUp` 이 그대로 신규 가입 경로를 탄다).
- `3` — `delete()` 는 `BaseEntity` 의 소프트 삭제다(`status = DELETED`). 행은 남고 `@SQLRestriction("status = 'ACTIVE'")` 가 이후 조회에서 걸러낸다 — [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]].

`WithdrawScenarioTest.kt` 가 이 전 과정을 한 시나리오로 묶어 보장한다 — 온보딩·북마크까지 만든 회원이 탈퇴하면 이전 access 토큰은 `MEMBER-003`, 이전 refresh 는 `AUTH-005` 로 거절되고, **같은 계정 재로그인은 신규 회원이며 이전 북마크가 없다**(`:59`).

탈퇴가 **이미 발급된 토큰들에 미치는 여파**(왜 refresh 가 `AUTH-005` 인지, 탈퇴 후에도 access 가 최대 30분 살아 있는 이유)는 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] 정본이다. 여기서는 **지우는 순서**까지만 다룬다.

> [!note] 탈퇴는 로그인과 달리 인증이 필요하다
> `withdraw` 만 `@AuthMemberId memberId: Long`(`AuthController.kt:41`) 을 받는다. 요청 본문이 없고 **access 토큰이 대상 회원을 결정한다.** 그래서 이것만 JWT 필터 목록에 들어 있다(§7). 그 토큰이 `Long` 이 되는 과정은 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]].

## 9. `newMember` 는 어디로 가나 — 15번과의 이음매

응답의 `newMember` 는 앱의 **분기 신호**다. 그런데 앱 코드를 보면 그것만으로 부족하다 — `kbap-fe/src/app/login.tsx:57-70`

```tsx
onSignedIn={(newMember) => {
  void (async () => {
    if (newMember) return resetToOnboarding(router);
    const completed = await api
      .get<{ onboardingCompleted?: boolean }>('/members/me/profile')
      .then((p) => p.onboardingCompleted === true)
      .catch(() => true);
    if (completed) { router.replace((returnTo ?? '/(tabs)') as Href); }
    else { resetToOnboarding(router); }
  })();
}}
```

- `3` — 신규면 무조건 온보딩. 여기까진 `newMember` 로 충분하다.
- `4-6` — **기존 회원이면 한 번 더 물어본다.** 로그인 응답에는 `onboardingCompleted` 가 없기 때문이다.

왜 없나. 4-5절에서 봤듯 **가입은 신원만 만들고 프로필은 비워 둔다.** 그래서 "계정은 있는데 온보딩은 미완료"인 회원이 실제로 존재한다 — 가입 직후 온보딩 화면에서 이탈한 사람들. 그들에게 `newMember: false` 만 보내면 앱은 빈 프로필로 홈에 들여보내게 된다. 코드의 주석이 그 사고를 그대로 적어놨다(`login.tsx:54-56`).

**그래서 이 흐름은 여기서 끊기고 15번으로 이어진다.**

```
POST /api/auth/login        →  { newMember, accessToken, refreshToken }   ← 이 노트
GET  /api/members/me/profile →  { onboardingCompleted, ... }              ← 15번
POST /api/members/me/onboarding                                           ← 15번
```

두 번째 줄부터는 `Authorization: Bearer {accessToken}` 이 붙고, 그 헤더를 뜯어 `@AuthMemberId memberId: Long` 으로 만드는 게 **17번**이다.

> [!note] 왜 로그인 응답에 `onboardingCompleted` 를 넣지 않았을까
> 넣으면 왕복 한 번이 준다. 다만 그러면 `LoginResponse` 가 **회원 프로필 상태를 알아야** 해서 auth 와 member 가 응답 DTO 수준에서 엉킨다. 실측으론 지금 안 들어 있다는 것만 사실이고, 어느 쪽이 옳은지는 코드가 말해주지 않는다 — **판단이 아니라 관찰로 남긴다.**

이 흐름에는 두 겹의 테스트가 걸려 있다.

**① 단위 — `FirebaseClaimMapperTest.kt`** (139줄, Spring 없이 순수 Kotlin)

**② 통합 — `AuthControllerTest.kt`** (`@SpringBootTest` + Testcontainers 로 MySQL·Redis 실제 기동)

```kotlin

    override fun verify(idToken: String): SocialIdentity {

        return SocialIdentity(SocialProvider.GOOGLE, DEFAULT_SUB, "user@gmail.com")
```

`@TestConfiguration` + `@Primary` 로 진짜 빈을 밀어낸다(`:484-490`). 시나리오 테스트용 대역은 더 짧다 — `ScenarioSocialTokenVerifierConfig.kt:15-18` 은 **보낸 `idToken` 문자열을 그대로 `providerUserId` 로 쓴다.** 그래서 시나리오 테스트가 `login("user-a")`, `login("user-b")` 로 **서로 다른 회원을 마음대로 만들어낼 수 있다.**

**이 대역들이 가능하게 하는 것:**

1. **네트워크 없이 로그인 전 구간을 돈다.** Firebase 콘솔·자격증명·인터넷 없이 CI 가 통과한다.

**이게 포트가 "구현이 하나뿐인데도" 있는 첫째 이유다.** `AuthService` 가 `FirebaseTokenVerifier` 를 직접 받았다면 이 대역들을 꽂을 자리가 없다.

## 11. 주의점 · 헷갈리는 것

- **"idToken" 이 이 흐름에 두 장 있다.** 구글이 앱에 준 것(`useSocialAuth.ts:68`)과 Firebase 가 발급한 것(`:51`). 서버로 가는 건 **후자**다. 서버가 전자를 받으면 `verifyIdToken` 이 실패한다.
- **`provider_uid` ≠ Firebase uid.** DB 에 저장되는 건 구글·애플의 원본 sub 다. Firebase 콘솔에서 본 uid 로 DB 를 조회하면 안 나온다.
- **로그인은 토큰을 파싱하지 않는다.** 발급만 한다. `TokenParser` 는 이 흐름에서 한 번도 안 불린다.
- **access 토큰은 발급 후 무효화할 수 없다.** stateless 라서 그렇다. 그래서 30분이다. 즉시 끊어야 하면 refresh 를 지우고 최대 30분을 기다리는 수밖에 없다.
- **탈퇴한 계정으로 다시 로그인하면 신규 회원이 된다.** `Member.withdraw()`(`:152-155`) 가 `providerUid` 를 `"DELETED:{id}"` 로 바꿔 unique 자리를 비워주기 때문이다. 이전 프로필은 승계되지 않는다. 전체 순서는 §8.
- **`kbap.auth.jwt.secret` 이 32바이트 미만이면 앱이 안 뜬다.** 로그인 시점이 아니라 **부팅 시점**에 터진다(`JwtTokenProperties.kt:11-13`). 로컬에서 `JWT_SECRET` 을 짧게 넣고 "왜 안 뜨지" 하기 딱 좋은 자리다.
- **Firebase 자격증명 미설정과 진짜 위조 토큰은 응답이 똑같다** — 둘 다 401 `AUTH-001`. 구분은 부팅 로그에서만 된다(`AuthConfig.kt:32` 의 warn).

## 13. 용어집

| 용어 | 뜻 |
|---|---|
| **ID 토큰** | "이 사람은 누구다"를 증명하는 서명된 JWT. OIDC 가 OAuth 에 더한 것 |
| **provider uid (sub)** | 구글·애플이 발급한 사용자 불변 식별자. kbap 의 신원 키 절반 |
| **claims** | JWT payload 안의 키-값들. `sub`·`exp`·`email`·`firebase.identities` 등 |

| **`token_type`** | kbap 자체 클레임. `ACCESS`/`REFRESH`/`SCAN_TICKET` 을 구분해 오용을 막는다 |
| **HS256** | 대칭키 HMAC-SHA256 서명. 발급자와 검증자가 같은 비밀키를 쓴다(= 우리 서버 혼자) |
| **테스트 대역(fake)** | 진짜 구현 자리에 꽂는 가짜. `@Primary` 로 실제 빈을 밀어낸다 |
