# 29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식

> 작성: 2026-08-27 · 맥락: 커리큘럼 내내 Redis 가 두 번 스쳐 갔다. 17번에서 refresh 토큰이 거기 저장됐고, 20번에서 스캔 예약이 거기서 원자적으로 잡혔다. 둘 다 "Redis 니까 캐시겠지" 라고 넘기기 쉬운 자리였고, 두 노트 모두 "아니다" 라고 한 줄 달고 이 노트로 미뤘다. 미룬 걸 여기서 갚는다.
> 목표: ① 캐시가 무엇이고 왜 어려운지를 세 질문으로 설명할 수 있게 되기 ② **kbap 에 캐시 계층이 하나도 없다**는 사실과 그 이유를 근거와 함께 말할 수 있게 되기 ③ "Redis = 캐시" 라는 등식을 버리고, Redis 의 네 가지 성질이 kbap 의 두 용도에 각각 왜 필요한지 대응시켜 말할 수 있게 되기.

---

## 0. 한 줄 요약

캐시는 **"비싼 계산의 결과를 싼 자리에 복사해 두는 것"** 이고, 어려운 건 만드는 쪽이 아니라 **언제 버리느냐**다. 그런데 kbap 은 캐시를 **한 군데도 쓰지 않는다** — `@Cacheable`·`@EnableCaching` 이 레포 전체에 0건이다. Redis 는 켜져 있지만 캐시로 쓰이지 않고, **refresh 세션**과 **스캔 예약** 두 곳에서 "프로세스 밖에 있고, 스스로 만료되고, 원자적으로 조작되는 키-값 저장소" 로 쓰인다. 둘 다 **날아가면 복구할 원본이 없는 원본 데이터**다.

---

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 |
|---|---|---|
| **캐시(cache)** | 비싼 계산·조회의 결과를 더 싸게 닿는 자리에 복사해 둔 것. **원본이 따로 있다**는 게 정의의 핵심 | TanStack Query 의 쿼리 캐시 — 진실은 서버, 앱이 가진 건 사본 |
| **캐시 히트 / 미스** | 찾던 값이 캐시에 있었다 / 없어서 원본까지 다녀왔다 | `useQuery` 가 즉시 데이터를 주느냐, 로딩을 띄우느냐 |
| **무효화(invalidation)** | 원본이 바뀌었으니 사본을 버리는 일 | `queryClient.invalidateQueries(['food', id])` |
| **TTL (Time To Live)** | 저장한 값이 **스스로** 사라지는 시각. 아무도 지우지 않아도 만료된다 | `staleTime`/`gcTime`. 단 앱이 죽어도 저장소 쪽에서 사라진다는 게 다르다 |
| **eviction(축출)** | 메모리가 꽉 찼을 때 저장소가 **임의로** 값을 버리는 것. TTL 과 달리 내가 정한 시각이 아니다 | 브라우저가 용량 압박에 캐시를 비우는 것 |
| **인메모리(in-memory)** | 값을 디스크가 아니라 RAM 에 둔다. 빠르지만 프로세스·서버가 죽으면 원칙적으로 사라진다 | JS 변수에 담아 둔 상태 |
| **키-값 저장소(key-value store)** | 키 하나로 값 하나를 넣고 꺼내는 저장소. 테이블·조인·질의어가 없다 | `Map<string, T>` |
| **원자적(atomic)** | 중간 상태를 아무도 볼 수 없는, 쪼갤 수 없는 한 덩어리 연산 | `setCount(c => c + 1)` 의 함수형 업데이트 |
| **분산 락(distributed lock)** | 서버가 여러 대일 때 "이 일은 한 대만 한다" 를 보장하는 장치 | (FE 에 대응물이 거의 없다 — 기기가 하나라 필요가 없었다) |
| **캐시 어사이드(cache-aside)** | 앱이 직접 "캐시 먼저 보고, 없으면 원본 조회 후 캐시에 넣기" 를 하는 가장 흔한 패턴 | `useQuery` 의 기본 동작이 바로 이 모양 |

## 2. 캐시의 세 질문

캐시를 도입하자는 말이 나오면 실제로 결정해야 하는 건 세 가지뿐이다.

### ① 무엇을 캐시하나 — 비싼 것만

캐시는 **비용 회피 장치**다. 회피할 비용이 없으면 캐시는 순손해다(메모리 + 코드 복잡도 + 틀린 값을 줄 위험). "비싸다" 는 대개 셋 중 하나다.

- **느린 I/O** — DB 조회, 특히 여러 번 왕복하는 조회.
- **돈이 드는 외부 호출** — LLM API, 유료 지오코딩 API.
- **CPU 를 태우는 계산** — 무거운 집계·정렬.

동시에 **같은 입력이 같은 출력을 낸다**는 성질이 필요하다. 요청마다 답이 달라야 하는 것(내 주문 목록, 지금 남은 스캔 횟수)은 캐시 후보가 아니거나, 캐시하더라도 키에 사용자를 넣어야 한다.

### ② 어디에 두나 — 계층이 여러 겹이다

| 자리 | 예 | 범위 | 특징 |
|---|---|---|---|
| 클라이언트 | TanStack Query, AsyncStorage | 기기 1대 | 가장 빠르다. 서버가 통제 못 한다 |
| HTTP / CDN | `Cache-Control`, CloudFront | 전 세계 | 서버에 요청이 아예 안 온다. 개인화된 응답엔 못 쓴다 |
| 서버 프로세스 안 | `ConcurrentHashMap`, Caffeine | **서버 1대** | 네트워크 왕복 0. **서버 2대면 사본도 2개** → 서로 다른 답을 준다 |
| 서버 밖 공유 | **Redis**, Memcached | 전 서버 | 왕복 1회는 든다. 대신 모든 서버가 같은 값을 본다 |
| DB 안 | MySQL 버퍼 풀 | — | 우리가 켜고 끄는 게 아니다. 공짜로 이미 있다 |

FE 개발자에게 이 표에서 가장 낯선 줄은 **"서버 프로세스 안"** 이다. 앱은 기기 하나에서만 도니까 "메모리에 넣어 둔다" 가 곧 "모두가 같은 값을 본다" 였다. 서버는 **같은 코드가 여러 프로세스에서 동시에 돌기 때문에**(→ [[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]]) 프로세스 안에 넣는 순간 사본이 인스턴스 수만큼 생긴다. 이게 뒤에서 계속 나올 축이다.

### ③ 언제 버리나 — 여기가 어렵다

> 컴퓨터 과학에는 어려운 문제가 둘 뿐이다: 캐시 무효화와 이름 짓기.
> — 널리 인용되는 농담(Phil Karlton 에게 귀속)

농담이지만 정확한 관찰이다. 캐시를 **채우는** 코드는 세 줄이고, **버리는** 코드는 원본을 바꾸는 **모든 경로**를 알아야 한다. 리뷰를 쓰면 음식 평점 캐시를 버려야 하고, 관리자가 음식을 수정해도 버려야 하고, 배치가 밤에 값을 갱신해도 버려야 한다. 하나만 빠뜨리면 사용자는 **틀린 값을** 본다 — 그것도 조용히, 재현이 안 되는 형태로.

그래서 현실의 선택지는 대체로 셋이다.

1. **TTL 만 쓴다** — "5분까진 옛날 값이어도 괜찮다" 고 선언하고 무효화 코드를 아예 안 쓴다. 가장 싸고 가장 흔하다. 대신 최대 5분간 틀린 값이 나간다.
2. **명시적 무효화** — 원본을 바꾸는 자리마다 캐시를 지운다. 정확하지만, 지워야 할 자리를 **사람이 기억해야 한다.**
3. **둘 다** — 무효화하되 TTL 을 보험으로 건다.

> [!tip] 이 셋을 이미 FE 에서 골라 봤다
> TanStack Query 를 쓸 때 `staleTime` 만 주고 넘어가면 1번, 뮤테이션 성공 콜백에서 `invalidateQueries` 를 부르면 2번이다. 서버 캐시에서 바뀌는 건 **틀렸을 때의 피해 범위**뿐이다 — 앱에선 그 기기 사용자 한 명이 잠깐 옛 화면을 보지만, 서버 공용 캐시가 틀리면 **전원이** 같은 틀린 값을 본다.

## 3. 반전 — kbap 에는 캐시가 없다

여기까지가 일반론이고, 이제 실측이다.

```
$ grep -rn "EnableCaching\|Cacheable\|CacheEvict\|CacheManager\|caffeine" \
    --include="*.kt" --include="*.kts" --include="*.yml" --include="*.toml" .
$ echo $?
1
```

**0건이다.** 애너테이션도, 캐시 매니저 빈도, 캐시 라이브러리 의존성도 없다. `build.gradle.kts` 어디에도 `spring-boot-starter-cache` 가 없다.

Spring 을 쓰면 캐시는 원래 이렇게 생겼다 — **일반 예시 코드**(kbap 코드가 아니다):

```kotlin
@Configuration
@EnableCaching
class CacheConfig

@Service
class FoodService(private val repository: FoodJpaRepository) {
    @Cacheable("foods")
    fun getFood(id: Long): Food = repository.findById(id).orElseThrow()

    @CacheEvict("foods", key = "#food.id")
    fun update(food: Food) { repository.save(food) }
}
```

Spring 공식 문서의 설명 그대로다 — "`computePiDecimal` 을 호출하기 **전에**, 추상화가 `piDecimals` 캐시에서 `precision` 인자에 맞는 항목을 찾는다. 있으면 캐시 내용을 즉시 반환하고 **메서드는 호출되지 않는다.**" 그리고 캐시 라이브러리를 아무것도 추가하지 않으면 Spring Boot 는 **`ConcurrentHashMap` 기반의 simple 프로바이더**를 자동 구성해 준다("프로덕션 용도로는 권장하지 않지만 시작하기에는 훌륭하다").

kbap 에는 이 코드가 한 줄도 없다. 그래서 이 노트의 나머지는 "kbap 의 캐시 전략" 이 아니라 **"그럼 Redis 는 왜 켜져 있나"** 에 대한 답이다.

> [!warning] "Redis 가 있다 = 캐시가 있다" 는 자동으로 성립하지 않는다
> 면접이든 온보딩이든 "우리 Redis 써요" 를 들으면 캐시를 떠올리는 게 기본값이다. kbap 에서는 **틀린 추측**이다. 17번 노트가 이미 이 콜아웃을 달아 뒀다 — refresh 키가 날아가면 "다시 채우면 그만" 이 아니라 **전 사용자 강제 로그아웃**이다. 복구할 원본이 없는 데이터는 정의상 캐시가 아니다.

## 4. Redis 의 네 가지 성질

캐시라는 이름표를 떼고 나면 Redis 는 성질 네 개짜리 부품이다. kbap 이 쓰는 건 이 넷 중 **뒤의 셋**이다.

| # | 성질 | 무슨 뜻인가 | kbap 이 이걸 쓰나 |
|---|---|---|---|
| ① | **인메모리** | 값이 RAM 에 있어 조회가 마이크로초 단위 | 부수적으로만 — 속도 때문에 고른 게 아니다 |
| ② | **TTL 내장** | 키마다 만료 시각을 걸 수 있고, 아무도 살아 있지 않아도 사라진다 | **핵심** — 두 용도 모두 이것 때문에 Redis 다 |
| ③ | **원자적 실행** | 명령 실행이 단일 스레드라 두 클라이언트의 명령이 섞이지 않는다. Lua 스크립트는 통째로 한 덩어리로 돈다 | **핵심** — 스캔 예약, refresh 회전 |
| ④ | **프로세스 밖 공유** | 서버가 몇 대든 같은 저장소를 본다 | **핵심** — 무상태 서버의 전제 |

③ 은 Redis 공식 문서가 명시한다 — "Redis 는 스크립트의 원자적 실행을 보장한다. 스크립트가 실행되는 동안 서버의 **모든 활동이 그 실행 시간 내내 차단된다.**" Redis 8 에서 `io-threads` 로 네트워크 I/O 는 여러 스레드가 나눠 처리하지만, **명령 실행 자체는 여전히 단일 스레드**라 원자성과 일관성이 유지된다.

`★ 왜 이게 JVM 서버에서 그렇게 값진가 ─────────────`
JVM 서버는 요청마다 다른 스레드가 돈다(→ [[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]]). 즉 "값을 읽고 → 판단하고 → 쓴다" 사이에 **다른 요청이 얼마든지 끼어들 수 있다.** Node 의 이벤트 루프에서도 `await` 지점마다 같은 일이 벌어지지만, 서버가 여러 대가 되면 언어의 동시성 장치(`synchronized`, 뮤텍스)로는 **아예 손이 닿지 않는다** — 다른 프로세스, 다른 기계다. 그때 "판단과 쓰기를 한 덩어리로 묶어 줄" 제3자가 필요하고, Redis 가 그 자리다.
`─────────────────────────────────────────`

## 5. 용도 ①: refresh 토큰 — 무상태 JWT 인데 왜 서버가 상태를 갖나

정본은 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] 이다. 여기서는 **저장소 선택**이라는 각도만 본다.

JWT 의 자랑은 무상태다. 토큰 안에 회원 ID 와 만료가 들어 있고 서명으로 위조를 막으니, 서버는 **아무것도 기억하지 않고** 검증만 하면 된다. 서버를 몇 대로 늘려도 세션 공유 문제가 없다 — 이게 앱이 쿠키·세션 대신 JWT 를 쓰는 이유였다(→ [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]]).

그런데 무상태에는 대가가 있다. **서버가 기억하지 않으면, 서버가 취소할 수도 없다.** 로그아웃을 눌러도 이미 발급된 토큰은 만료될 때까지 유효하다.

kbap 은 이 딜레마를 **토큰을 둘로 쪼개서** 푼다. 설정 파일의 주석이 근거를 그대로 적어 뒀다.

```yaml
      # access 는 stateless 라 만료 전 무효화가 불가능하므로 짧게, refresh 는 Redis 폐기가 가능하므로 길게.
      access-ttl: 30m
      refresh-ttl: 14d
```
— `api/src/main/resources/application.yml:60-62`

- **access(30분)** — 완전 무상태. 서버는 서명과 `exp` 만 본다. 취소 불가라서 짧다.
- **refresh(14일)** — Redis 에 기록이 있다. 기록을 지우면 그 자리에서 죽는다. 취소 가능하므로 길어도 된다.

저장소 구현은 이게 전부다.

```kotlin
@Component
class RedisRefreshTokenStore(
    private val redisTemplate: StringRedisTemplate,
) : RefreshTokenStore {
    override fun save(jti: String, memberId: Long, ttl: Duration) {
        redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
    }

    override fun consume(jti: String): Long? =
        redisTemplate.opsForValue().getAndDelete(key(jti))?.toLongOrNull()
```
— `api/src/main/kotlin/com/kbap/api/infra/redis/RedisRefreshTokenStore.kt:8-17`

- `:11` — 인터페이스 `RefreshTokenStore` 는 `common/port/auth/` 에 있고 Redis 를 전혀 모른다. 구현만 `api/infra/redis/` 에 있다(→ [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]).
- `:13` — 값은 회원 ID 하나. `set(키, 값, ttl)` 의 세 번째 인자가 **TTL** 이다. 14일 뒤 아무도 안 지워도 사라진다.
- `:17` — `getAndDelete` = Redis 의 `GETDEL`. **읽기와 삭제가 한 명령**이라 두 요청이 동시에 같은 refresh 를 들고 와도 한쪽만 값을 받는다.

세 성질이 전부 쓰였다.

| 성질 | 여기서 하는 일 |
|---|---|
| **TTL** | 14일치 세션 만료를 코드 0줄로 처리한다. 만료된 세션을 청소하는 배치가 필요 없다 |
| **원자성** | `GETDEL` 하나가 refresh 동시 회전 경합을 막는다. `GET` 후 `DELETE` 였다면 둘 다 새 세션을 받아 하나가 유실된다 |
| **프로세스 밖 공유** | A 서버에서 로그인하고 B 서버로 재발급 요청이 가도 같은 기록을 본다 |

포트 선언 자체에 이 의도가 주석으로 남아 있다.

```kotlin
interface RefreshTokenStore {
    fun save(jti: String, memberId: Long, ttl: Duration)

    // 원자적 소비(조회+삭제) — rotation 경합 방어.
    fun consume(jti: String): Long?
```
— `common/src/main/kotlin/com/kbap/common/port/auth/RefreshTokenStore.kt:5-9`

**왜 MySQL 이 아닌가?** 세션 테이블을 만들어도 동작은 한다. 다만 ① 만료 행을 치우는 배치를 직접 짜야 하고 ② `SELECT` 후 `DELETE` 사이의 경합을 막으려면 트랜잭션·잠금을 걸어야 하고 ③ 로그인/재발급마다 트랜잭션이 하나 늘어난다. **셋 다 Redis 에선 공짜로 딸려 온다.** 반대로 세션 데이터가 잃어도 되는 성격(재로그인하면 그만)이라 DB 의 내구성 보장이 필요 없다 — 그래서 교환이 성립한다.

## 6. 용도 ②: 스캔 예약 — 왜 이 데이터가 DB 가 아닌가

정본은 [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] 다. Lua 스크립트 해설과 check-then-act 경합은 거기 있다. 여기서는 **"왜 이 데이터의 집이 Redis 인가"** 만 본다.

상황: 무료 사용자는 스캔 3회까지다. 스캔 한 번은 비전 LLM 호출이라 **돈이 들고 오래 걸린다.** 그래서 호출 **전에** 슬롯을 하나 잡아 두고(예약), 성공하면 DB 카운트를 올리고, 실패하면 예약을 풀어야 한다.

이 "예약" 이라는 데이터의 성질을 뜯어 보자.

| 성질 | 예약 데이터 | 그래서 |
|---|---|---|
| 수명 | 수십 초. 길어야 5분 | 영구 저장할 이유가 전혀 없다 |
| 잃으면? | **슬롯이 복구된다 = 사용자에게 유리** | 내구성 보장이 필요 없다 |
| 누가 보나 | 요청을 받은 서버 아무 대나 | 프로세스 안에 두면 깨진다 |
| 판단이 필요한가 | "지금 몇 개 잡혀 있나 → 한도 미만이면 잡기" | **읽고 판단하고 쓰기가 한 덩어리여야 한다** |
| 확정 데이터인가 | 아니다. 성공할지 모르는 **in-flight** | 확정 카운트(`scan_count`)와 섞이면 안 된다 |

TTL 의 값어치가 여기서 가장 선명하다. 설정 주석이 이유를 그대로 적었다.

```yaml
    # 스캔 예약(무료 슬롯 선점)의 TTL — LLM 최대 타임아웃보다 충분히 길게. 프로세스가 죽어 해제를 못 해도 만료로 슬롯이 복구된다.
    reservation-ttl-seconds: ${SCAN_RESERVATION_TTL_SECONDS:300}
```
— `api/src/main/resources/application.yml:44-45`

**"프로세스가 죽어 해제를 못 해도"** 가 핵심이다. DB 로 선점하면 되돌리기는 **앱의 책임**이다. 앱이 그 사이에 죽으면 되돌릴 사람이 없고, 사용자는 쓰지도 않은 무료 1회를 영구히 잃는다. Redis 예약은 **TTL 이 대신 되돌려준다** — 아무도 살아 있지 않아도 5분 뒤 슬롯이 돌아온다.

TTL 이 어디서 걸리는지는 어댑터 코드에 있다.

```kotlin
    @Value("\${kbap.scan.reservation-ttl-seconds:300}") private val reservationTtlSeconds: Long,
…
            redis.call('ZADD', KEYS[1], ARGV[2], ARGV[5])
            redis.call('PEXPIRE', KEYS[1], ARGV[6])
```
— `api/src/main/kotlin/com/kbap/api/infra/redis/RedisScanReservationStore.kt:13`, `:56-57`

- `:13` — TTL 은 설정에서 주입된다(→ [[6. 설정과 프로필, 트랜잭션 경계]]).
- `:56` — 예약 하나를 ZSET 에 넣되, **점수 자리에 만료 시각(ms)** 을 넣는다. 그래서 "지난 예약 치우기" 가 범위 삭제 한 방이 된다.
- `:57` — `PEXPIRE` 로 **키 전체**에도 TTL 을 건다. 한 회원이 스캔을 그만두면 그 회원의 예약 키가 통째로 사라져 메모리가 새지 않는다.

**두 겹의 만료**라는 게 재밌는 지점이다. ZSET 안의 개별 예약은 점수(만료 시각)로 논리적으로 만료되고, 키 자체는 `PEXPIRE` 로 물리적으로 만료된다. 앞의 것은 "이 슬롯은 이제 안 세도 된다", 뒤의 것은 "이 회원 자리를 메모리에서 치워도 된다" 다.

> [!note] 확정과 미확정을 다른 저장소에 두는 게 요점이다
> 확정된 사용 횟수는 MySQL 의 `member.scan_count` 에 있다. 미확정 예약은 Redis 에 있다. 한도 판정은 **둘을 더해서** 한다 — Lua 스크립트가 `confirmedCount`(DB 에서 읽어 인자로 넘어온 값) + `reserved`(ZSET 크기) 를 한도와 비교한다(`RedisScanReservationStore.kt:52-53`). "영구히 남을 값" 과 "5분 뒤 사라져도 되는 값" 을 성질에 맞는 저장소에 각각 둔 셈이다.

## 7. 성질 ↔ 용도 대응표

4절의 네 성질이 두 용도에서 각각 무슨 일을 하는지 한 장으로.

| 성질 | refresh 세션 | 스캔 예약 |
|---|---|---|
| **① 인메모리(빠름)** | 부수적 — 요청당 1~2회 접근이라 속도가 병목이 아니었다 | 부수적 — LLM 호출이 수 초인데 Redis 왕복은 밀리초다 |
| **② TTL** | **필수** — 14일 세션 만료를 코드 0줄로. 만료 청소 배치가 없다 | **필수** — 크래시로 해제를 못 해도 슬롯이 스스로 복구된다 |
| **③ 원자성** | **필수** — `GETDEL` 이 동시 회전에서 한쪽만 이기게 한다 | **필수** — Lua 한 덩어리가 check-then-act 경합을 없앤다 |
| **④ 프로세스 밖 공유** | **필수** — 어느 서버로 재발급 요청이 가도 같은 기록 | **필수** — 서로 다른 서버로 동시 요청이 와도 같은 슬롯 수를 본다 |

**"빠르다" 가 두 칸 다 부수적**이라는 게 이 표의 결론이다. kbap 이 Redis 를 고른 이유는 속도가 아니라 **②③④** 다. 그리고 이 셋 중 어느 것도 "캐시" 라는 단어에 들어 있지 않다.

## 8. FE 의 저장소 선택과 같은 사고방식이다

볼트에 이미 [[클라이언트 저장소 — AsyncStorage·SecureStore·메모리 (K-Bap 실전)]] 노트가 있다. 그 노트의 결론은 이랬다 — 클라이언트 저장소 선택은 **"유출되면 얼마나 아픈가(민감도) × 언제까지 살아야 하나(수명)"** 두 축이면 끝난다. 그래서 JWT 는 메모리, 온보딩 draft 는 AsyncStorage, OAuth 크리덴셜은 SecureStore 였다.

**이 노트는 그 노트의 서버 쪽 짝이다.** 축이 하나 늘어날 뿐, 하는 일은 똑같다.

| | 클라이언트 (그 노트) | 서버 (이 노트) |
|---|---|---|
| 축 1 | **수명** — 앱 종료까지? 재설치까지? | **수명** — 요청 하나? 5분? 14일? 영구? |
| 축 2 | **민감도** — 유출되면 얼마나 아픈가 | **잃어도 되는가** — 날아가면 복구할 원본이 있나 |
| 축 3 | (없음 — 기기가 하나라 필요 없다) | **공유 범위** — 이 프로세스만? 전 서버? |
| 축 4 | (없음) | **원자성이 필요한가** — 읽고-판단하고-쓰기가 한 덩어리여야 하나 |

같은 판단을 나란히 놓으면 이렇다.

| 데이터 | 자리 | 왜 |
|---|---|---|
| 앱: JWT access | 메모리 | 짧고 민감. 앱 종료 시 소멸이 오히려 안전 |
| 앱: 온보딩 draft | AsyncStorage | 길고 무해. 잃어도 "재개 지점이 살짝 옛것" |
| 서버: 스캔 예약 | Redis | **짧고**, 잃으면 사용자에게 유리하고, 전 서버가 봐야 하고, 원자성이 필요 |
| 서버: refresh 세션 | Redis | 14일. 잃으면 재로그인(감당 가능). 전 서버 공유. 원자적 소비 필요 |
| 서버: 회원·음식·주문 | MySQL | **영구**. 잃으면 끝. 트랜잭션·제약·조인이 필요 |

`★ 비유의 경계 ─────────────────────────`
AsyncStorage 는 **기기 한 대** 안의 저장소다. 그 안에 넣은 값을 누가 동시에 건드릴 걱정이 없다. Redis 는 **서버 여러 대가 공유하는** 저장소다. 그래서 FE 저장소에는 없던 문제 두 개가 생긴다 — ① 내가 읽는 사이 다른 서버가 쓴다(→ 그래서 `GETDEL`·Lua 가 필요하다) ② 네트워크 왕복이 있고, 그 왕복이 실패할 수 있다(→ Redis 가 죽으면 로그인·스캔이 안 된다). "키-값 넣고 꺼내기" 라는 인터페이스가 똑같아 보여서 이 차이를 잊기 쉬운데, **동시성과 장애가 바로 그 차이에서 나온다.**
`─────────────────────────────────────────`

## 9. ShedLock 도 Redis 인가 — 아니다, DB 다

이름이 락이고, 락 하면 Redis 를 떠올리기 쉬우니 짚어 둔다. **kbap 의 ShedLock 은 MySQL 을 쓴다.**

```kotlin
@Configuration
@EnableAsync
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30M")
class BackgroundConfig {
    @Bean
    fun lockProvider(dataSource: DataSource): JdbcTemplateLockProvider =
        JdbcTemplateLockProvider(
            JdbcTemplateLockProvider.Configuration.builder()
                .withJdbcTemplate(JdbcTemplate(dataSource))
                .usingDbTime()
                .build(),
        )
}
```
— `api/src/main/kotlin/com/kbap/api/core/config/BackgroundConfig.kt:12-24`

- `:18` — `JdbcTemplateLockProvider`. `DataSource` 를 받는다 = **MySQL** 이다. `shedlock-provider-redis-*` 가 아니다(의존성도 `shedlock-provider-jdbc-template` 다, `api/build.gradle.kts:22`).
- `:22` — `usingDbTime()` — 락 만료 판단에 **DB 서버의 시계**를 쓴다. 앱 서버 두 대의 시계가 어긋나 있어도 판단 기준이 하나가 된다.

락이 사는 테이블은 마이그레이션으로 만들어졌고(→ [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]), 그 파일 머리에 **선택 이유가 적혀 있다.**

```sql
-- ShedLock 표준 스키마(KB-226) — 이미지 회수 @Scheduled 를 api 2대 중 1대만 실행하기 위한 락 테이블.
-- 락 저장소를 상태의 원천(MySQL)과 같은 계층에 둔다 — Redis 재시작·failover 에 영향받지 않는다.
```
— `api/src/main/resources/db/migration/V2026.07.24.14.00.02__shedlock.sql:1-2`

즉 **의도적으로 Redis 를 피했다.** Redis 는 재시작하면 키가 다 날아가는데(kbap 은 영속 볼륨도 안 둔다, 11절), 그 순간 락이 통째로 풀려 두 서버가 같은 잡을 돌 수 있다. 락이 지키려는 건 DB 상태이므로 락도 DB 에 두는 게 맞다는 판단이다.

쓰는 자리는 이렇다.

```kotlin
    @Scheduled(cron = "\${kbap.food-image.collect-cron:0 0 */3 * * *}")
    @SchedulerLock(name = "food-image-collect", lockAtMostFor = "PT30M", lockAtLeastFor = "PT1M")
    fun collectOnSchedule() = collectSubmitted()
```
— `api/src/main/kotlin/com/kbap/api/food/FoodImageBatchCollectService.kt:42-44`

3시간마다 **모든 인스턴스가 깨어나고**, ShedLock 이 그중 한 대만 통과시킨다(`application.yml:121` 의 주석이 그대로 이렇게 적어 뒀다). 이 잡의 내용은 [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]] 에 있다.

> [!note] 잠금도 "프로세스 밖 공유" 의 한 형태다
> 4절의 성질 ④ 를 다시 보자. 분산 락은 **공유 저장소에 "내가 잡았다" 는 표시를 원자적으로 남기는 것**일 뿐이다 — 성질 ③+④ 를 쓰는 또 하나의 용례다. kbap 은 이걸 Redis 가 아니라 MySQL 로 구현했을 뿐, 발상은 스캔 예약과 같은 계열이다.

## 10. 캐시를 안 쓰는 게 문제인가

정직하게 답하면: **지금은 문제라고 말할 근거가 레포에 없다.**

캐시 도입을 정당화하려면 최소한 셋이 필요하다 — ① 느린 엔드포인트가 실제로 있다는 **측정치** ② 그 느림이 반복 조회 때문이라는 **원인 분석** ③ 그 데이터가 조금 낡아도 된다는 **제품 판단**. 레포에는 셋 다 없다. 성능 측정 결과도, 캐시를 논한 ADR 도, 스펙 문서도 없다. 그러니 "kbap 은 캐시가 필요한데 안 쓰고 있다" 는 말도, "필요 없다고 판단했다" 는 말도 **둘 다 근거 없이 하면 틀린 말**이다. 관찰 가능한 사실은 하나다 — **아직 도입하지 않았다.**

다만 캐시를 안 쓰고도 지금까지 온 이유는 코드에서 읽힌다.

- **비싼 조회를 애초에 안 만들었다.** 연관관계가 0개고 N+1 이 설계 단계에서 제거돼 있다(→ [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]). 캐시로 덮어야 할 만큼 무거운 쿼리가 잘 안 생긴다.
- **가장 비싼 호출은 캐시가 원래 못 돕는다.** LLM 비전 스캔은 매번 **다른 사진**이 입력이다. 같은 입력이 없으니 캐시 히트가 날 수가 없다.
- **가장 무거운 계산은 이미 비동기로 뺐다.** 임베딩·콘텐츠 채움은 배치와 큐로 나갔다(→ [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]], [[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]]). 요청 경로에 안 남아 있으면 캐시할 것도 없다.

**나중에 후보가 될 만한 자리**를 굳이 꼽자면(어디까지나 후보다 — 측정이 먼저다):

| 후보 | 성격 | 왜 후보인가 | 왜 아직 아닌가 |
|---|---|---|---|
| 홈 조회의 fan-in | 한 요청이 4개 서비스를 부른다(→ [[18. 홈 화면 조회 흐름 — 여러 서비스를 한 응답으로 모으기]]) | 호출 횟수가 가장 많은 화면이고 조합 비용이 가장 크다 | **개인화된 응답**이다. 회원별 키가 필요하고, 히트율이 회원 재방문 빈도에 좌우된다 |
| 음식 상세 | 거의 안 바뀌는 마스터 데이터 | 전 사용자 공통이라 히트율이 높을 자리 | 단건 PK 조회다. 캐시로 줄일 비용이 애초에 작다 |
| 랭킹 목록 | 조회 시점 계산(→ [[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]]) | 집계형이라 계산이 무거워질 여지 | 지금 규모에서 무겁다는 증거가 없다 |

세 줄 다 **"측정하면 답이 나온다"** 로 끝난다는 게 요점이다. 캐시는 성능 문제의 해법이지 기본 구성이 아니다. 없는 문제에 캐시를 넣으면 2절 ③ 의 무효화 부채를 공짜로 떠안는다.

> [!tip] 합류하고 나서 이 주제를 꺼낸다면
> "캐시 넣죠" 보다 "이 엔드포인트 p95 가 얼마죠, 어디서 시간을 쓰죠" 가 먼저다. 캐시는 두 번째 질문의 답이 나온 뒤에 고르는 도구다.

## 11. 로컬 실행에 Redis 가 필요한 이유

`docker compose up` 을 하면 컨테이너가 셋 뜬다 — 앱, MySQL, **Redis**. 왜 Redis 까지 필요한가? 캐시라면 없어도 앱이 돌아야 하는데, **없으면 로그인이 안 되기 때문**이다.

```yaml
  redis:
    image: redis:8
    container_name: kbap-redis
    ports:
      - "6379:6379"
    # refresh token 저장소(KB-118). TTL 로 만료가 자동 처리되므로 영속 볼륨을 두지 않는다 —
    # 재시작 시 세션이 날아가면 사용자는 재로그인하면 된다(복구 가능한 데이터).
```
— `docker-compose.yml`

- `image: redis:8` — 4절에서 본 그 버전이다.
- 주석 두 줄이 이 노트 전체의 요약이다. **"refresh token 저장소"** — 캐시라고 부르지 않는다. **"영속 볼륨을 두지 않는다"** — MySQL 은 `kbap-mysql-data` 볼륨이 있는데 Redis 는 없다. 즉 `docker compose down` 하면 세션이 전부 사라진다. 그래도 괜찮은 이유까지 적어 뒀다.

앱 컨테이너 쪽 설정에도 한 줄 있다.

```yaml
      # 컨테이너 안에서 localhost 는 자기 자신 — refresh 세션 저장소는 서비스명(redis)으로 접속한다.
      REDIS_HOST: redis
      REDIS_PORT: 6379
```
— `docker-compose.yml`

이 환경 변수가 프로필 설정으로 흘러 들어간다.

```yaml
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
      ssl:
        # 로컬 docker Redis 는 평문 — TLS 로 검증하려면 REDIS_SSL_ENABLED=true (KB-169)
        enabled: ${REDIS_SSL_ENABLED:false}
```
— `api/src/main/resources/application-local.yml:16-21`

기본값이 `localhost` 라서, **DB 만 컨테이너로 띄우고 앱은 `bootRun` 으로 도는 방식**(compose 파일 머리말이 안내하는 `docker compose up -d mysql`)에서도 그대로 맞는다. 단 그 경우 Redis 도 따로 띄워야 한다.

> [!warning] 신규 세팅에서 제일 자주 밟는 자리
> 앱은 뜨는데 **로그인만 500** 이 나면 Redis 연결을 의심한다. `@Cacheable` 이 아니라 인증 경로가 직접 Redis 를 쓰기 때문에, "캐시 없으면 느려질 뿐" 이 아니라 **기능이 아예 안 된다.** `docker compose ps` 로 `kbap-redis` 가 healthy 인지 먼저 본다.

## 12. 주의점 · 트러블슈팅

| 증상 / 함정 | 원인 | 대응 |
|---|---|---|
| "Redis 있으니 캐시 있겠지" | 이름에서 온 선입견 | grep 0건이 근거다. 두 용도는 캐시가 아니라 원본 저장소다 |
| 로컬에서 로그인만 500 | Redis 미기동 | Redis 는 선택 부품이 아니다(11절) |
| 스테이징 Redis 를 재시작했더니 전원 로그아웃 | 영속 볼륨이 없다 = 재시작 시 키 소멸 | 설계상 감당 가능한 손해(재로그인)다. **다만 배포 창을 잡을 땐 알고 하자** |
| "Redis 에 락 넣죠" | ShedLock 은 이미 MySQL 이다(9절) | 락은 상태의 원천과 같은 계층에 있다. 옮기려면 재시작 시 락 유실을 감수해야 한다 |
| 프로세스 안 `ConcurrentHashMap` 으로 캐시하기 | 서버가 2대면 사본도 2개 | 사용자마다 다른 답을 볼 수 있다. 공유가 필요하면 Redis, 아니면 애초에 캐시하지 말 것 |
| `@Cacheable` 을 붙였는데 안 먹는다 | ① `@EnableCaching` 이 없다 ② **같은 클래스 안에서 자기 메서드를 호출**해 프록시를 안 거친다 | ②는 `@Transactional` 의 self-invocation 과 **완전히 같은 함정**이다(→ [[15. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]). Spring 의 애너테이션은 대개 프록시로 동작한다 |
| TTL 없이 Redis 에 키를 넣기 | 지우는 사람이 없으면 메모리가 샌다 | kbap 의 두 용도 모두 TTL 이 걸려 있다. 새 키를 만들 땐 **만료를 먼저 정한다** |

## 13. 치트시트

```
캐시의 세 질문
  ① 무엇을  — 비싸고(느린 I/O·유료 호출·무거운 계산), 같은 입력이 같은 출력을 내는 것만
  ② 어디에  — 클라 / CDN / 프로세스 안(서버마다 사본!) / Redis(공유) / DB 버퍼풀
  ③ 언제 버리나 — TTL만 / 명시적 무효화 / 둘 다     ← 여기가 어려운 부분

kbap 실측
  @Cacheable · @EnableCaching · CacheManager · caffeine  →  전부 0건
  Redis 는 켜져 있지만 캐시가 아니다

Redis 4성질과 kbap 의 사용
  ① 인메모리(빠름)      → 부수적. 이것 때문에 고른 게 아니다
  ② TTL 내장            → 핵심. 만료 청소 코드가 0줄
  ③ 원자적(단일 스레드) → 핵심. GETDEL · Lua
  ④ 프로세스 밖 공유    → 핵심. 무상태 서버의 전제

용도 두 개
  auth:refresh:{jti}      = 회원ID,  TTL 14일,  GETDEL 로 원자적 소비   → 17번
  scan:reservations:{id}  = ZSET,    TTL 5분,   Lua 로 원자적 예약      → 20번
  둘 다 "날아가면 복구할 원본이 없는" 원본 데이터 = 정의상 캐시가 아니다

ShedLock = MySQL (Redis 아님)
  JdbcTemplateLockProvider · usingDbTime() · shedlock 테이블
  이유: 락 저장소를 상태의 원천과 같은 계층에 (Redis 재시작/failover 무관)

저장소 고르는 축 (FE 2축 → 서버 4축)
  수명 · 잃어도 되는가 · 공유 범위 · 원자성 필요 여부
  영구+잃으면 끝           → MySQL
  짧음+잃어도 됨+공유+원자 → Redis
  요청 하나짜리            → 그냥 지역 변수

로컬
  docker compose up -d          # app + mysql + redis
  docker compose up -d mysql    # DB만 (앱은 bootRun) — Redis 는 따로 필요
  Redis 는 영속 볼륨 없음 → 재시작하면 세션 전부 소멸(재로그인으로 복구)
```

## 14. 용어집

| 말 | 뜻 |
|---|---|
| **캐시** | 비싼 결과의 사본. **원본이 따로 있다**는 게 정의 |
| **무효화** | 원본이 바뀌었으니 사본을 버리는 일. 캐시의 어려운 절반 |
| **TTL** | 값이 스스로 사라지는 시각. 청소 코드를 대체한다 |
| **eviction** | 메모리 압박에 저장소가 임의로 값을 버리는 것. TTL 과 다르다 |
| **캐시 어사이드** | 앱이 "캐시 먼저, 없으면 원본, 그리고 캐시에 넣기" 를 직접 하는 패턴 |
| **`GETDEL`** | 읽으면서 지우는 Redis 명령. Spring Data 에서 `getAndDelete` |
| **ZSET** | 값마다 점수가 붙는 Redis 정렬 집합. kbap 은 점수에 만료 시각을 넣는다 |
| **`PEXPIRE`** | 키에 밀리초 단위 TTL 을 거는 명령 |
| **분산 락** | 서버 여러 대 중 한 대만 어떤 일을 하도록 공유 저장소에 남기는 표시 |
| **ShedLock** | `@Scheduled` 를 여러 인스턴스 중 한 대만 실행시키는 라이브러리. kbap 은 JDBC(MySQL) 프로바이더 |
| **`lockAtMostFor` / `lockAtLeastFor`** | 락 최대 보유 시간(죽어도 이만큼 뒤엔 풀린다) / 최소 보유 시간(너무 빨리 끝나도 이만큼은 쥔다) |
| **io-threads** | Redis 8 의 네트워크 I/O 분산 설정. **명령 실행은 여전히 단일 스레드** |
| **in-flight** | 시작했지만 아직 확정되지 않은 작업. kbap 의 스캔 예약이 그것 |

## 15. 체크리스트

- [ ] 캐시의 정의에서 **"원본이 따로 있다"** 가 왜 핵심인지, 그래서 refresh 세션이 왜 캐시가 아닌지 설명할 수 있다
- [ ] 캐시의 세 질문을 말하고, 셋 중 무엇이 어려운지와 그 이유를 설명할 수 있다
- [ ] 캐시를 **프로세스 안**에 두는 것과 **Redis** 에 두는 것의 차이를 서버 2대 상황으로 설명할 수 있다
- [ ] kbap 에 캐시가 없다는 사실을 **어떤 grep 으로 확인했는지**까지 말할 수 있다
- [ ] Redis 의 네 성질을 대고, 그중 kbap 이 실제로 쓰는 셋을 짚을 수 있다
- [ ] "빠르다" 가 kbap 의 Redis 선택 이유가 **아니라는** 것을 두 용도 각각에 대해 설명할 수 있다
- [ ] 무상태 JWT 인데 refresh 만 서버 기록을 갖는 이유를, access-ttl / refresh-ttl 값과 함께 말할 수 있다
- [ ] 스캔 예약이 MySQL 이 아니라 Redis 에 있는 이유를 **TTL 이 되돌리기를 대신한다**는 논지로 설명할 수 있다
- [ ] FE 의 저장소 선택 축(민감도 × 수명)과 서버의 축(수명 · 잃어도 되는가 · 공유 범위 · 원자성)이 어떻게 이어지고 **어디서 갈라지는지** 말할 수 있다
- [ ] ShedLock 의 락 저장소가 무엇이고 왜 Redis 가 아닌지, 마이그레이션 주석의 근거를 대며 설명할 수 있다
- [ ] "캐시를 넣어야 하나" 라는 질문에 근거 없이 답하지 않고, 무엇을 먼저 측정해야 하는지 말할 수 있다
- [ ] 로컬에서 Redis 없이 앱을 띄우면 **무엇이 안 되는지** 말할 수 있다
