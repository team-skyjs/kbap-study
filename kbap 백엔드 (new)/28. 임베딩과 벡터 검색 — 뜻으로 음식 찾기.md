# 28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기

> 작성: 2026-08-27 · 맥락: 19번에서 서버가 메뉴명을 찾는 방법을 실측했다 — `matchKey` **정확 일치** 한 방이다. 한 글자만 달라도 못 찾는다. 그 한계를 완전히 다른 방식으로 넘으려던 장치가 이 노트의 주제다. 27번에서 본 아웃박스가 여기서 두 번째로, 다른 목적지를 향해 다시 등장한다.
> 목표: ① "텍스트를 벡터로 만든다"가 무슨 말인지 수식 없이 설명할 수 있게 되기 ② 음식 하나가 승인되고 나서 벡터가 되기까지의 전 경로를 파일 단위로 짚을 수 있게 되기 ③ **이 파이프라인이 지금 절반만 살아 있다**는 사실과 그 이유를 근거와 함께 말할 수 있게 되기.

## 0. 한 줄 요약

관리자가 음식을 승인하면 같은 트랜잭션에서 `food_vector_outbox` 행이 하나 생기고, 매시 30분에 도는 `foodVectorSyncJob` 이 그 행을 읽어 **"이름 + 긴 설명"을 OpenAI 임베딩 API 로 보내 256개의 숫자로 바꾼 뒤** DocumentDB 에 문서 하나로 적재한다. 그렇게 채워 넣은 벡터를 **읽는 코드는 지금 레포에 없다** — 스캔이 쓰던 유사 음식 검색은 2026-08-19 에 제품 결정으로 걷혔고, 적재 파이프라인만 남아 계속 돈다.

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 (kbap 기준) |
|---|---|
| **임베딩(embedding)** | 텍스트를 고정 길이 숫자 배열로 바꾼 것. 뜻이 가까운 텍스트끼리 배열도 가까워지도록 학습된 모델이 만든다 |
| **차원(dimension)** | 그 배열의 길이. kbap 은 **256** |
| **코사인 유사도** | 두 벡터가 같은 방향을 가리키는 정도. −1~1, 클수록 비슷 |
| **벡터 검색** | 질의 벡터와 가장 방향이 비슷한 문서 k개를 저장소가 찾아 주는 것 |
| **DocumentDB** | AWS 의 MongoDB 호환 문서 DB. 벡터 인덱스를 지원해서 kbap 의 벡터 저장소로 쓴다 |
| **`embeddingHash`** | `SHA-256(모델명\|차원\|원문)`. 같으면 임베딩 API 를 아예 호출하지 않는다 |
| **문서(document)** | 행(row) 대신 JSON 덩어리 하나. 스키마가 테이블처럼 고정돼 있지 않다 |

> [!note] 이 노트가 설명하지 않는 것
> **아웃박스 패턴 자체**(왜 DB 행에 먼저 쓰나, at-least-once, 상태 기계, 재시도)는 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] 이 정본이다. **Spring Batch 골격**(Job/Step/chunk, Reader·Processor·Writer 가 뭔지, 잡을 어떻게 기동하나)은 [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] 이 정본이다. 여기서는 그 틀 안에 들어 있는 **내용물**만 읽는다.

## 2. 문제부터 — 글자로 찾으면 못 찾는 것들

[[19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]] 에서 실측한 매칭 로직은 세 줄이다.

```kotlin
fun matchKey(raw: String): String =
    Normalizer.normalize(raw, Normalizer.Form.NFC)
        .filter { it in '가'..'힣' }
```

- `common/src/main/kotlin/com/kbap/common/util/KoreanMenuNameNormalizer.kt:8-10`

NFC 로 통일한 뒤 **한글 음절만 남긴다.** 그 결과를 `food.korean_name` 과 **`=` 로 비교**한다(`ScanService.kt:114` 부근, `findByKoreanNameIn`). 이게 전부다 — 퍼지 매칭도, 형태소 분석도, 유사어 사전도 없다.

이 방식이 이기는 경우와 지는 경우가 뚜렷하다.

| 메뉴판에 적힌 말 | `matchKey` 결과 | 정확 일치로 찾히나 |
|---|---|---|
| `순두부 찌개` | `순두부찌개` | ✅ 공백이 탈락해서 찾힌다 |
| `순두부찌개 (2인)` | `순두부찌개` | ✅ 괄호·숫자가 탈락 |
| `할머니손맛찌개` | `할머니손맛찌개` | ❌ 카탈로그에 없다 |
| `엄마표김치찌개` | `엄마표김치찌개` | ❌ 김치찌개인 걸 아는데 못 찾는다 |
| `참치김치찌개` | `참치김치찌개` | ❌ 별개 음식으로 취급 |

아래 세 줄이 이 노트가 존재하는 이유다. 사람 눈에는 "아 김치찌개 계열이구나" 가 즉시 보이는데, 문자열 비교에는 그 정보가 하나도 없다. `"엄마표김치찌개"` 와 `"김치찌개"` 는 `==` 앞에서 `"엄마표김치찌개"` 와 `"자동차"` 만큼이나 다르다.

**정확 일치의 한계를 넘는 길은 크게 두 갈래다.**

| 접근 | 방법 | 한계 |
|---|---|---|
| ① 글자를 더 똑똑하게 비교 | 편집 거리, n-gram, 형태소 분석, 유사어 사전 | `"짜장면"` ↔ `"자장면"` 은 잡지만 `"짜장면"` ↔ `"중국식 검은 국수"` 는 못 잡는다. 규칙을 사람이 계속 관리해야 한다 |
| ② **글자를 버리고 뜻을 비교** | 텍스트를 뜻의 좌표로 바꿔서 좌표끼리 거리를 잰다 | 좌표를 만드는 데 외부 모델 호출(=돈·지연)이 필요하고, **틀려도 그럴듯한 답을 낸다** |

kbap 이 만든 게 ②다.

> [!important] 두 접근은 경쟁 관계가 아니다
> 벡터 검색은 정확 일치를 **대체**하려고 만든 게 아니라 **정확 일치가 실패한 뒤**에만 부르는 것이었다. 흐름은 `matchKey` 로 먼저 찾고 → 못 찾은 것만 벡터로 → 그것도 못 찾으면 `UNKNOWN`. 정확 일치는 싸고 확실하고, 벡터는 비싸고 불확실하다. 싼 것부터 쓴다.

## 3. 임베딩이 뭔가 — 뜻을 좌표로

### 3-1. 색을 숫자 세 개로 적는 것과 같다

FE 개발자에게 가장 가까운 것은 **색상 코드**다.

`#FF0000` 은 빨강, `#FE0201` 도 빨강이다. 두 색이 비슷하다는 걸 사람이 판단하지 않아도 된다 — **숫자 세 개(R, G, B)의 거리가 가까우면 색도 비슷하다**는 성질이 좌표계에 이미 들어 있기 때문이다. `"빨강"` 과 `"레드"` 라는 *글자*를 비교하면 아무 관계도 안 나오지만, `(255,0,0)` 과 `(254,2,1)` 이라는 *좌표*를 비교하면 즉시 나온다.

임베딩은 **같은 일을 "뜻"에 대해 하는 것**이다. 텍스트를 넣으면 숫자 배열이 나오고, 뜻이 가까운 텍스트끼리 배열도 가깝다.

```
"김치찌개"       → [0.021, -0.113, 0.077, ... ]   (256개)
"엄마표김치찌개"  → [0.019, -0.108, 0.081, ... ]   ← 가깝다
"아메리카노"      → [-0.204, 0.311, -0.055, ... ]  ← 멀다
```

> [!warning] 비유의 경계 — 여기서부터 색과 다르다
> **RGB 의 세 축은 사람이 이름을 붙일 수 있다**(빨강·초록·파랑). 임베딩의 256개 축에는 **아무도 이름을 못 붙인다.** 37번째 숫자가 "매운맛 정도"라거나 "국물 여부"라는 식으로 해석되지 않는다. 모델이 학습 과정에서 알아서 정한 축이고, 사람이 읽을 수 있는 의미가 없다. 그래서 임베딩은 **"왜 이게 비슷하다고 나왔는지" 를 설명할 수 없다.** 벡터 검색이 이상한 답을 냈을 때 디버깅이 어려운 이유가 여기 있다.
> 또 하나: RGB 는 색을 **완전히** 표현하지만, 임베딩은 뜻을 **압축**한다. 256개 숫자에 문장의 모든 정보가 들어가지는 않는다 — 정보가 반드시 손실된다.

### 3-2. 256차원이란 무슨 뜻인가

숫자가 **256개**라는 뜻이다. 그게 전부다.

색은 3개면 충분하다. 뜻은 3개로는 어림도 없다 — 3개 숫자로 구별할 수 있는 "서로 다른 뜻"의 개수가 너무 적어서, 김치찌개와 된장찌개와 부대찌개가 전부 같은 자리에 뭉개진다. 숫자를 늘릴수록 구별할 여지가 늘어난다.

kbap 이 쓰는 모델 `text-embedding-3-small` 은 **기본 1536차원**인데, 요청에 `dimensions` 를 명시해 **256으로 잘라 받는다.**

```kotlin
OpenAiEmbeddingModel(
    OpenAiEmbeddingOptions.builder()
        .apiKey(requiredApiKey())
        .baseUrl(baseUrl)
        .model(props.model)
        .dimensions(props.dimension)
        .timeout(props.timeout)
        .build(),
)
```

- `common/src/main/kotlin/com/kbap/common/infra/llm/embedding/OpenAiTextEmbeddingClient.kt:14-22`
- `props.model` = `text-embedding-3-small`, `props.dimension` = `256` (`LlmModelProperties.kt:17-18` 의 기본값)

**왜 굳이 줄이나** — 차원이 작을수록 저장 용량이 작고, 유사도 계산이 빠르고, 인덱스가 가볍다. 대신 표현력이 준다. 256은 그 절충점으로 KB-318 에서 정해진 값이고, 이후 **저장 측과 검색 측이 같은 값을 쓰는 것이 계약**이 됐다.

> [!danger] 차원은 양쪽이 반드시 같아야 한다
> 저장할 때 256차원으로 넣고 검색할 때 1024차원으로 질의하면 — 결과가 나쁜 게 아니라 **아예 성립하지 않는다.** 좌표계가 다르면 거리를 잴 수 없다. 그래서 코드가 응답 차원을 직접 검증한다.
> ```kotlin
> check(embedding.output.size == props.dimension) {
>     "임베딩 차원이 설정과 다릅니다: 설정 ${props.dimension}, 응답 ${embedding.output.size}"
> }
> ```
> `OpenAiTextEmbeddingClient.kt:32-34`. 이 검증이 실제로 결함 하나를 잡아냈다 — §9 에서 다룬다.

### 3-3. 코사인 유사도 — 거리가 아니라 방향

두 벡터가 얼마나 비슷한지 재는 방법으로 kbap 은 **코사인 유사도**를 쓴다(`DocumentDbFoodVectorSearcher.kt:18` 의 `"similarity", "cosine"`).

두 점 사이의 직선 거리를 재는 게 아니라, **원점에서 두 점을 향해 그은 화살표가 얼마나 같은 방향을 가리키는지**를 잰다. 같은 방향이면 1, 직각이면 0, 정반대면 −1.

**왜 방향인가** — 길이를 무시하고 싶어서다. 긴 문장의 임베딩은 대체로 벡터 길이가 길게 나오는 경향이 있는데, 그건 "뜻"이 아니라 "분량"의 차이다. 방향만 보면 `"김치찌개"` 라는 네 글자와 `"김치찌개는 한국의 대표적인 찌개 요리로 …"` 라는 세 문단이 **같은 뜻으로 판정될 수 있다.** kbap 은 저장할 땐 이름+긴 설명(길다)을, 검색할 땐 메뉴명만(짧다) 넣기 때문에 이 성질이 필수다.

## 4. 벡터가 어디 저장되나 — MySQL 이 아니다

### 4-1. 저장소 실체

**MySQL 이 아니라 AWS DocumentDB** 다. MongoDB 호환 문서 DB이고, 접속 정보는 별개의 설정으로 들어온다.

```yaml
  vector:
    enabled: ${VECTOR_ENABLED:false}
    uri: ${VECTOR_DB_URI:}
    database: ${VECTOR_DB_DATABASE:kbap}
    collection: ${VECTOR_DB_COLLECTION:foods}
```

- `batch/src/main/resources/application.yml:66-71` (api 쪽도 `application.yml:103-108` 에 동일 블록)
- 기본이 **`false`** 다 — 로컬처럼 클러스터가 없는 환경에서도 앱이 정상 부팅하도록.

**왜 MySQL 에 안 넣나.** 벡터 검색은 `WHERE embedding = ?` 같은 게 아니다. "이 256개 숫자와 방향이 가장 비슷한 문서 1개" 를 찾아야 하는데, 이건 B-tree 인덱스로 못 한다 — 전용 벡터 인덱스(ANN, 근사 최근접 탐색)가 필요하다. kbap 이 쓰는 MySQL 버전에 그 기능이 없으므로 **그 일을 할 줄 아는 저장소를 따로 둔 것**이다. 저장소를 나눈 대가는 정합성이다 — 두 저장소가 어긋날 수 있고, 그 어긋남을 메우는 장치가 §5 의 아웃박스다.

### 4-2. 저장하는 쪽과 읽는 쪽이 다른 모듈이다

같은 컬렉션을 **api 는 읽고, batch 는 쓴다.** 그래서 접근 코드가 어느 한쪽 모듈에 있으면 안 됐다.

```
common/domain/food/vector/
├── FoodVectorStore.kt              쓰기 계약 (findEmbeddingHash / upsert / delete)
├── FoodVectorSearcher.kt           읽기 계약 (search)
├── DocumentDbFoodVectorStore.kt    쓰기 구현 (mongodb-driver-sync)
├── DocumentDbFoodVectorSearcher.kt 읽기 구현
├── FoodVectorDocuments.kt          필드명 상수 + 임베딩 원문/해시 규칙
└── FoodVectorProperties.kt         @ConfigurationProperties("kbap.vector")
```

조립은 각 부트앱이 따로 한다 — **api 는 searcher 만, batch 는 store 만.**

| 모듈 | 조립 위치 | 만드는 빈 | 조건 |
|---|---|---|---|
| `:api` | `api/core/config/FoodVectorConfig.kt:15-22` | `FoodVectorSearcher` | `kbap.vector.enabled=true` |
| `:batch` | `batch/vector/FoodVectorSyncBatchConfig.kt:33-40` | `FoodVectorStore` | `kbap.vector.enabled` **and** `kbap.llm.embedding.enabled` 둘 다 true |

> [!important] 왜 `common.port.*` 가 아니라 `common.domain.food.vector` 인가
> [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] 의 §8("DB 는 왜 포트가 아닌가")이 이 자리에서 실전으로 반복된다. `FoodVectorStore` 는 인터페이스이고 구현이 하나뿐이니 포트처럼 생겼지만, `common.port.*` 에 있지 **않다.**
> 근거는 KB-328 플랜이 직접 적어 뒀다 — **"벡터 문서는 교체 가능한 외부 시스템이 아니라 food 데이터의 제2 영속"** (`specs/kb-328-food-vector-outbox/plan.md:104-108`). MySQL 리포지토리와 mysql-connector 가 `:common` 에 있는 것과 같은 취급이다. 헌법 원칙 III("외부 시스템 구현은 infra")의 명시적 예외로 Complexity Tracking 에 기록돼 있다.
> 판별 기준을 다시 한 줄로: **"벤더를 갈아끼우면 데이터가 따라오나?"** 결제 게이트웨이를 바꾸면 데이터는 저쪽에 남는다(→ 포트). 벡터 저장소를 바꾸면 우리 데이터를 우리가 옮겨 심는다(→ 영속).
> 반면 **임베딩 API 는 진짜 포트**다 — `common/port/llm/TextEmbeddingClient.kt`. 데이터를 보관하지 않고 계산만 해 주는 외부 시스템이기 때문이다.

## 6. 파이프라인을 한 줄씩

### 6-1. 아웃박스 행이 생기는 자리 — 트랜잭션 안

```kotlin
if (passed) {
    if (food.approve()) {
        vectorOutboxRepository.enqueueIfAbsent(food.id, FoodVectorOutboxOperation.UPSERT)
    }
} else {
    food.reject(reason)
}
```

- `api/src/main/kotlin/com/kbap/api/admin/AdminFoodContentReviewService.kt:37-43` (메서드 `applyContentReviewResult` 에 `@Transactional`, `:30`)
- `if (food.approve())` — `approve()` 가 **Boolean 을 반환**한다. 이미 READY 면 `false` 를 돌려주고 아웃박스를 만들지 않는다. 승인 버튼을 두 번 눌러도 벡터 작업이 두 번 쌓이지 않는다.
- 승인(MySQL 쓰기)과 아웃박스 행(MySQL 쓰기)이 **한 트랜잭션**이다. 그래서 "승인은 됐는데 벡터 반영 요청이 유실됐다" 가 원천적으로 불가능하다. 이게 아웃박스 패턴을 쓰는 이유 전부이고, 자세한 논증은 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] 에 있다.

`enqueueIfAbsent` 는 중복을 한 번 더 막는다.

```kotlin
fun enqueueIfAbsent(foodId: Long, operation: FoodVectorOutboxOperation) {
    val alreadyPending =
        existsByFoodIdAndOperationAndOutboxStatus(foodId, operation, FoodVectorOutboxStatus.PENDING)
    if (!alreadyPending) { … }
}
```

- `common/src/main/kotlin/com/kbap/common/domain/food/FoodVectorOutboxJpaRepository.kt:11-22`
- **인터페이스에 본문이 있다.** Kotlin 인터페이스의 default 메서드다 — Spring Data 가 파생 쿼리(`existsBy…`)와 `save` 를 채워 주고, 그걸 조합한 로직은 인터페이스가 직접 갖는다. 별도 구현 클래스가 필요 없다.

### 6-2. Reader — 커서로 읽는다

```kotlin
override fun read(): FoodVectorOutbox? {
    if (buffer.isEmpty() && !exhausted) {
        val page = outboxRepository.findPendingAfterId(cursor, pageSize)
        if (page.isEmpty()) { exhausted = true }
        else { cursor = page.last().id; buffer.addAll(page) }
    }
    return buffer.removeFirstOrNull()
}
```

- `batch/src/main/kotlin/com/kbap/batch/vector/FoodVectorOutboxItemReader.kt:26-37`
- `WHERE id > :afterId AND outbox_status = 'PENDING' ORDER BY id ASC LIMIT :limit` (`FoodVectorOutboxJpaRepository.kt:34-49`, 네이티브 쿼리)
- **OFFSET 이 아니라 커서**다 — 이유는 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]] 와 같지만, 여기선 성능보다 **정합성**이 이유다. 처리하면서 상태가 PENDING → COMPLETE 로 바뀌므로 결과 집합이 진행 중에 줄어든다. OFFSET 이면 그때마다 항목이 건너뛰어진다.
- `and status = 'ACTIVE'` 조건도 있다 — `outbox_status`(도메인 상태)와 `status`(BaseEntity 의 소프트 삭제)가 **다른 컬럼**이다. 마이그레이션 주석이 이 분리를 명시해 뒀다(`V2026.08.12.19.06.50…sql:3`).

### 6-3. Processor — 이 노트의 심장

```kotlin
val food = foodRepository.findById(foodId).orElse(null)
if (food == null || !food.isReady()) {
    vectorStore.delete(foodId)
    return item
}
val longDescription = food.longDescription
if (longDescription.isNullOrBlank()) {
    return abandon(item, "긴 설명이 비어 있어 임베딩할 수 없습니다: foodId=$foodId")
}
val embeddingText = FoodVectorDocuments.embeddingText(food.koreanName, longDescription)
val embeddingHash = FoodVectorDocuments.embeddingHash(embeddingModel, embeddingDimension, embeddingText)
if (vectorStore.findEmbeddingHash(foodId) == embeddingHash) {
    return item
}
```

- `batch/src/main/kotlin/com/kbap/batch/vector/FoodVectorSyncItemProcessor.kt:32-48`

네 개의 판단이 순서대로 있다.

1. **자격 재검사** — 아웃박스 행이 만들어진 시점과 처리 시점 사이에 최대 1시간이 있다. 그 사이 음식이 삭제됐거나 READY 가 풀렸으면 적재하지 않고, 남아 있을지 모를 문서를 **지운다.** "요청 당시의 사실" 이 아니라 **"처리 시점의 사실"** 을 믿는다.
2. **긴 설명 필수** — 없으면 `abandon` 으로 **즉시 FAILED**. 재시도해도 달라질 수 없는 실패는 재시도하지 않는다(`failPermanently`, `FoodVectorOutbox.kt:42-46`). 일시 실패와 영구 실패를 구분하는 것이 재시도 설계의 핵심이다.
3. **원문 조립** — `"$name\n$longDescription"` (`FoodVectorDocuments.kt:17`). 이름만도 아니고 설명만도 아니다.
4. **해시 비교** — 여기가 돈이 걸린 자리다.

```kotlin
fun embeddingHash(embeddingModel: String, embeddingDimension: Int, embeddingText: String): String {
    val digest = MessageDigest.getInstance("SHA-256")
        .digest("$embeddingModel|$embeddingDimension|$embeddingText".toByteArray())
    return HASH_PREFIX + digest.joinToString("") { "%02x".format(it) }
}
```

- `common/src/main/kotlin/com/kbap/common/domain/food/vector/FoodVectorDocuments.kt:19-23`
- 해시 입력에 **모델명과 차원이 들어가 있다.** 원문이 같아도 모델이 바뀌면 해시가 달라진다 → 자동으로 재임베딩된다. §9 에서 이게 실제로 무슨 일을 했는지 본다.
- 해시가 같으면 **OpenAI 를 부르지 않고 그냥 통과**한다. 아웃박스가 두 번 처리돼도(at-least-once) 결과가 같고 비용도 안 드는 이유다.

### 6-4. Writer — 청크 단위로 완료 기록

```kotlin
override fun write(chunk: Chunk<out FoodVectorOutbox>) {
    chunk.forEach { item ->
        outboxRepository.findById(item.id).orElse(null)?.complete()
    }
}
```

- `batch/src/main/kotlin/com/kbap/batch/vector/FoodVectorSyncResultWriter.kt:11-15`
- `save()` 호출이 없다. `findById` 로 가져온 엔티티는 영속 상태이고 `complete()` 가 필드를 바꾸면 **변경 감지(dirty checking)** 로 UPDATE 가 나간다 — [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 의 그 동작이다.
- 프로세서가 `null` 을 반환한 항목(= `abandon` 된 건)은 라이터까지 오지 않는다. `ItemProcessor` 가 `null` 을 돌려주면 그 항목은 청크에서 빠진다 — 그래서 영구 실패 건이 COMPLETE 로 덮이지 않는다.

### 6-5. 실패 처리 — 3층 구조

| 층 | 장치 | 동작 |
|---|---|---|
| 즉시 재시도 | `RetryPolicy` (`FoodVectorSyncBatchConfig.kt:77-87`) | 최대 2회, 1초 시작 · 2배씩 증가 · ±0.2초 지터 |
| 이번 실행 격리 | `.faultTolerant().skipLimit(50).skip(Exception)` (`:107-111`) | 한 건이 터져도 잡 전체를 죽이지 않는다. 단 50건 넘게 터지면 잡이 실패 |
| 다음 실행 이월 | `FoodVectorOutboxSkipListener` (`:15-25`) | `attempts++`, `last_error` 저장. **5회** 넘으면 FAILED (`FoodVectorOutbox.kt:54`) |

**지터(jitter)** 는 재시도 간격에 무작위를 섞는 것이다. 100건이 동시에 실패해 정확히 1초 뒤 동시에 재시도하면 외부 API 를 다시 한 번 때리게 된다 — 이걸 흩뜨린다.

> [!note] 옆 테이블은 다르게 골랐다
> 같은 레포의 `food_content_outbox` 에는 **시도 상한도 `FAILED` 상태도 없다** — `attempts` 는 표시용이고 어떤 분기에도 안 쓰인다. 왜 두 아웃박스가 다른 선택을 했는지는 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §9 의 대비표가 정본이다.

## 7. 경계를 넘는 지점들

### 7-1. `:api` ↔ `:batch` — 서로를 모른다

**아웃박스 행을 만드는 쪽(api)과 소비하는 쪽(batch)은 서로를 컴파일 의존하지 않는다.** 둘 다 `:common` 의 `FoodVectorOutboxJpaRepository` 와 `food_vector_outbox` 테이블만 안다. 두 앱은 별개의 프로세스이고, 만나는 자리는 **DB 테이블 하나**뿐이다. [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] 의 3모듈 구조가 여기서 그대로 보인다.

### 7-2. 외부 시스템 두 개를 연달아 넘는다

프로세서 한 번의 처리 안에서 프로세스 밖으로 나가는 호출이 **세 번**이다.

| 호출 | 대상 | 계약이 어디 있나 |
|---|---|---|
| `vectorStore.findEmbeddingHash(foodId)` | DocumentDB | `common.domain.food.vector` (영속 취급) |
| `embeddingClient.embed(…)` | OpenAI | `common.port.llm.TextEmbeddingClient` (**진짜 포트**) |
| `vectorStore.upsert(…)` | DocumentDB | `common.domain.food.vector` |

세 호출 다 **되돌릴 수 없다.** DocumentDB 에 문서를 쓴 뒤 MySQL 트랜잭션이 롤백돼도 문서는 그대로 남는다. 그래서 이 설계는 롤백에 기대지 않고 **멱등**(같은 걸 두 번 해도 결과가 같음)으로 정합성을 지킨다 — `upsert` 는 replace 이고, `delete` 는 대상이 없어도 성공이다.

### 7-3. 트랜잭션 경계 — 문서와 코드가 어긋난다

> [!warning] 스펙과 다름
> KB-328 리서치 문서 R4 는 이렇게 결정했다 — **"스텝 트랜잭션은 `ResourcelessTransactionManager` … chunk 의 구조만 취하고 트랜잭션 의미론(청크 롤백·프레임워크 retry/skip)은 쓰지 않는다"** (`specs/kb-328-food-vector-outbox/research.md:30-31`).
> **코드는 그렇지 않다.** 벡터 스텝은 애플리케이션의 진짜 `PlatformTransactionManager`(JPA)를 주입받아 쓴다(`FoodVectorSyncBatchConfig.kt:92`·`:103`), 그리고 프레임워크 retry/skip 도 그대로 쓴다(`:107-111`). 같은 배치 앱의 콘텐츠 아웃박스 잡은 문서대로 `ResourcelessTransactionManager()` 를 쓰고 있어(`batch/outbox/FoodContentOutboxBatchConfig.kt:71`) 두 잡의 스타일이 실제로 갈려 있다.
> **결과적으로 무슨 뜻인가**: 청크 하나(최대 100건)를 처리하는 동안 **MySQL 트랜잭션이 열린 채로 OpenAI 호출과 DocumentDB 왕복이 그 안에서 일어난다.** 라이터의 변경 감지가 동작하려면 이 트랜잭션이 필요하므로 코드 자체는 정합하지만, "외부 호출은 트랜잭션 밖" 이라는 헌법 제약과는 어긋난다. 커넥션을 오래 쥐는 구조이니 건수가 늘면 먼저 아파올 자리다.
> 이 노트는 코드를 기준으로 쓴다. 문서가 낡은 게 아니라 **문서가 계획을 적었고 구현이 다른 선택을 했으며 문서가 갱신되지 않은** 경우다.

## 8. 그런데 이 벡터를 지금 누가 읽나 — 아무도 안 읽는다

이 노트에서 가장 중요한 실측이다.

`FoodVectorSearcher` 를 주입받는 프로덕션 코드가 **레포에 없다.** 빈은 만들어진다(`FoodVectorConfig.kt:21-22`, `kbap.vector.enabled=true` 일 때) — 만들어져서 아무 데도 안 쓰인다.

### 8-1. 원래는 스캔이 썼다

KB-319(2026-08-10)가 스캔 v2 에 붙였던 게 이것이다. `matchKey` 로 못 찾은 메뉴를 벡터로 한 번 더 찾아, 비슷한 음식의 정보를 "정확 매칭 아님" 표시와 함께 내려주는 UX 였다.

```kotlin
val embeddings = embeddingClient.embed(names)
val foodIdByName = names.zip(embeddings).mapNotNull { (name, embedding) ->
    searcher.search(embedding, limit = 1).firstOrNull()
        ?.takeIf { it.score >= similarityThreshold }
        ?.let { name to it.foodId }
}.toMap()
```

- 삭제된 파일 `api/src/main/kotlin/com/kbap/api/scan/SimilarFoodResolver.kt:27-32` (커밋 `d8ef0263^` 시점)
- `embeddingClient: TextEmbeddingClient?` — **타입이 nullable** 이었다. 임베딩이 꺼진 환경에서는 빈이 없으므로 `null` 이 주입되고, 그러면 조용히 빈 맵을 돌려준다. 전체를 실패시키지 않고 기능 하나만 끄는 방식이다.
- `catch (e: Exception) { log.warn(…); emptyMap() }` — 벡터 저장소가 죽어도 **스캔은 성공한다.** 유사 대체만 빠진다(부분 성공).

### 8-2. 2026-08-19, 제품 결정으로 걷혔다

커밋 `d8ef0263` (KB-343). 커밋 메시지가 이유를 직접 말한다.

> 비매칭(DB miss) 메뉴를 유사 음식으로 대체하는 UX 를 폐기하고 1.0 원칙(스캔 추출 결과 그대로·UNKNOWN)으로 통일 — similarFood 응답 필드와 유사 음식 검색 호출을 제거한다. **벡터 적재 파이프라인(KB-328)은 존치** — 스캔의 검색 소비 코드만 걷어낸다.

지워진 것: `SimilarFoodResolver`, `ScanResult`·`ScanV2Response` 의 `similarFood` 필드, 테스트 페이크, 그리고 `kbap.vector.similarity-threshold` 프로퍼티.
남은 것: 포트·어댑터·조립 config·아웃박스·배치 잡 **전부**.

> [!important] 이걸 어떻게 읽어야 하나
> "죽은 코드니까 지워야 한다"는 성급하다. 남긴 게 의도적이고 근거가 문서에 있다 — 검색 UX 는 폐기됐지만 **저장소를 계속 최신으로 유지해 두면 다음에 다시 쓸 때 재색인 없이 바로 켤 수 있다.** 벡터 적재는 한 번 멈추면 따라잡는 데 시간과 돈이 든다.
> 다만 **지금 이 파이프라인은 아무도 읽지 않는 데이터를 위해 임베딩 API 를 계속 호출한다.** 기본이 `enabled: false` 라서 실제 비용이 나는지는 배포 환경 변수(`VECTOR_ENABLED`·`EMBEDDING_ENABLED`)에 달렸다. 합류 후 확인할 만한 자리다.

### 8-3. 검색 품질 — "틀린 답도 그럴듯하게"

지금은 안 쓰지만, 쓸 때 반드시 걸리는 함정이라 남긴다.

```kotlin
Document("vectorSearch", Document()
    .append("vector", embedding.map { it.toDouble() })
    .append("path", FoodVectorDocuments.EMBEDDING)
    .append("similarity", "cosine")
    .append("k", limit))
```

- `common/src/main/kotlin/com/kbap/common/domain/food/vector/DocumentDbFoodVectorSearcher.kt:12-20`

**벡터 검색은 "못 찾음" 을 반환하지 않는다.** `k=1` 로 물으면 컬렉션에 뭐가 들었든 **항상 하나를 돌려준다.** 아메리카노를 질의해도 가장 가까운 찌개가 나온다 — 유사도 0.1 짜리로. SQL 의 `WHERE` 처럼 "조건에 맞는 게 없다" 는 개념이 없다.

그래서 임계값이 유일한 방어선이었다. 그리고 그 값은 —

```yaml
    # 유사도 임계 — 미달이면 유사 대체 없이 미등록 응답. dev 실데이터로 튜닝한다(0.0 = 항상 채택에서 시작).
    similarity-threshold: ${VECTOR_SIMILARITY_THRESHOLD:0.0}
```

- 삭제된 `api/src/main/resources/application.yml` 의 한 줄 (커밋 `d8ef0263` 에서 제거)
- **기본값 0.0 = 방어선을 안 친 상태.** 코사인 유사도가 0 이상이면 무조건 채택, 즉 "항상 뭔가를 보여준다". 주석은 "dev 실데이터로 튜닝한다" 고 예고했지만, 튜닝되기 전에 기능 자체가 폐기됐다.

> [!danger] FE 개발자가 가져갈 교훈
> 정확 일치는 **틀리면 못 찾는다**(빈 결과). 벡터 검색은 **틀려도 답을 낸다**(그럴듯한 오답). 후자가 훨씬 위험하다 — 사용자가 "김치찌개 알레르기 정보" 를 기대했는데 "된장찌개" 정보를 받고 그걸 믿을 수 있다. kbap 이 음식 알레르기·기피 성분을 다루는 앱이라는 걸 생각하면, 임계값 없는 벡터 폴백이 폐기된 게 우연한 결정으로 보이지 않는다.

## 9. 벤더가 두 번 바뀌었다 — 그리고 데이터가 살아남은 이유

[[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] 가 이 교체를 "계약은 그대로" 의 실증으로 든다. 12번은 **코드가 안 바뀐 이야기**를 하고, 이 노트는 **데이터가 어떻게 됐는지**를 잇는다.

| 시점 | 무슨 일 | 차원 | 계약(`TextEmbeddingClient`) |
|---|---|---|---|
| 2026-08-07 (KB-299) | `TextEmbeddingClient` 신설, AWS Bedrock Titan V2 어댑터 | 스펙상 **1024** | 신설 |
| (KB-318) | DocumentDB 벡터 인덱스 구축 — **256, cosine** | 256 | — |
| 2026-08-10 (KB-319) | 스캔 v2 유사 폴백. 설정 `dimension: 256` | 256 요청 | 그대로 |
| 2026-08-13 (KB-328 중) | **결함 발견**: Titan 요청에 `dimensions` 가 안 실렸다 | 실제로는 1024 수신 | 그대로 |
| 2026-08-13 (KB-328) | OpenAI `text-embedding-3-small` 로 전면 교체 | **256** | **그대로** |

### 9-1. 조용히 깨져 있던 결함

KB-299 스펙은 1024차원을 확정했는데(`specs/kb-299-bedrock-embedding-port/spec.md:64`), KB-318 이 구축한 인덱스는 256이었다. KB-319 가 설정을 `dimension: 256` 으로 맞췄고 — 그런데 실제 호출은 계속 1024를 받아왔다. 커밋 메시지가 원인을 정확히 적어 뒀다.

> Spring AI 2.0.0 `TitanEmbeddingRequest` 는 `inputText`·`inputImage` 만 직렬화해 `dimensions` 를 Bedrock 에 보낼 수 없다 — 실 호출은 항상 기본 1024차원을 받아 **256 검증에서 전건 실패**하는 잠복 결함(독립 리뷰 발견, jar 디컴파일로 확정).

- 커밋 `85f2f7dc` 내 `fix(llm)` 항목

**§3-2 의 그 `check` 한 줄이 이걸 잡았다.** 차원을 검증하지 않았다면 1024차원 벡터가 256차원 인덱스로 들어가 조용히 이상한 검색 결과를 내거나, 저장소가 거부하는 걸 아무도 이유를 모른 채 겪었을 것이다. **"조용한 통과 금지"** 는 KB-299 계약 문서의 원문 표현이다(`contracts/text-embedding-client.md:16`).

### 9-2. 차원이 바뀌면 기존 벡터는 전부 무효다 — 그런데 재색인 작업이 없었다

원칙은 단호하다. **좌표계가 바뀌면 이전 좌표는 의미가 없다.** 256차원 인덱스에 1024차원 질의를 던지면 결과가 나쁜 게 아니라 성립하지 않는다.

그런데 kbap 은 별도 재색인 배치를 만들지 않았다. 두 가지가 겹쳤다.

1. **차원은 실제로 안 바뀌었다.** 인덱스는 처음부터 256이었고, Titan 은 256을 *보내려다 실패*했을 뿐이며, OpenAI 도 256이다. 문서 계약이 "기존 인덱스 그대로" 라고 못박아 뒀다(`specs/kb-328-food-vector-outbox/contracts/vector-food-document-v2.md`).
2. **모델명이 바뀐 건 해시가 알아서 처리했다.** `embeddingHash` 입력에 모델명·차원이 들어 있으니(§6-3), 벤더가 바뀌는 순간 **저장된 모든 문서의 해시가 전부 불일치**가 된다 → 다음 배치에서 자동 재임베딩. 커밋 메시지가 그대로 말한다 — *"기존 적재분은 embeddingHash 의 model 변경으로 다음 배치에서 자동 재임베딩된다."*

> [!important] 설계가 벌어 준 것
> 해시 입력에 모델명 한 개를 더 넣어 둔 결정이, 벤더 교체 때 **재색인 스크립트 한 줄도 쓰지 않게** 만들었다. 원문 텍스트만 해싱했다면 "모델은 바뀌었는데 원문은 같으니 스킵" 이 되어 낡은 벡터가 그대로 남았을 것이고, 그걸 발견해서 전량 삭제하는 운영 작업이 필요했을 것이다.
> 반대로 말하면 — **모델을 바꾸면 다음 배치가 전량을 재임베딩한다.** 공짜가 아니다. 음식 수 × 임베딩 단가만큼 한 번에 청구된다.

### 9-3. 재색인·백필은 관리자가 버튼으로 지시한다

전량을 다시 밀어 넣어야 할 때 쓰는 자리가 관리자 화면에 있다.

```kotlin
@Transactional
fun enqueueReadyFoodsForVectorSync() {
    val targetIds = foodRepository.findReadyIdsWithoutVectorUpsertOutbox(PageRequest.of(0, ENQUEUE_MAX))
    vectorOutboxRepository.saveAll(targetIds.map { FoodVectorOutbox.upsert(it) })
}
```

- `api/src/main/kotlin/com/kbap/api/admin/AdminFoodDashboardService.kt:52-55` (`ENQUEUE_MAX = 500`, `:66`)
- 엔드포인트: `POST /admin/foods/vector-outboxes/enqueue` (`AdminFoodPageController.kt:34-38`)

> [!warning] 이 버튼은 "재색인" 이 아니라 "미등록분 백필" 이다
> 쿼리가 `not exists (… operation = UPSERT)` 다 — **UPSERT 아웃박스 행이 한 번이라도 있었던 음식은 대상에서 빠진다**(`FoodJpaRepository.kt:38-52`). COMPLETE 여도 마찬가지다. 즉 이 버튼은 *아직 한 번도 벡터 대기열에 오르지 않은* READY 음식만 줍는다.
> 그래서 **"전량 재색인" 은 이 버튼으로 안 된다.** 다행히 지금 구조에선 모델·차원이 바뀌면 해시 불일치로 자동 재임베딩되므로 전량 재색인이 필요한 상황이 잘 안 생긴다. 하지만 "벡터만 날아가고 아웃박스는 COMPLETE 로 남은" 사고가 나면 이 버튼으로 복구가 안 된다는 뜻이기도 하다.
> 관리자 화면은 그 밖에 대기/완료/실패 건수와 `unenqueued`(=아직 안 올라간 READY 음식 수), 최근 실패 20건을 보여주고, FAILED 한 건을 PENDING 으로 되돌리는 재처리 버튼을 준다(`AdminFoodDashboardService.kt:38-49`·`:58-63`).

## 10. 비용 — 임베딩은 계량되지 않는다

임베딩도 LLM 호출이고 토큰당 돈이 든다. `text-embedding-3-small` 은 **$0.02 / 1M 토큰** (KB-328 커밋 메시지 기준, Titan 과 동일 단가라 전환 근거의 하나였다).

kbap 은 LLM 비용을 DB 에 적립하는 장치를 갖고 있다 — `LlmCallCostIncurred` 이벤트를 발행하면 `LlmCallCostEventListener` 가 받아 `llm_call_cost` 에 쌓고, 관리자 대시보드가 그걸 보여준다.

**그런데 임베딩은 이 장치에 연결돼 있지 않다.** 실측:

| 호출 | 비용 이벤트 발행하나 | 근거 |
|---|---|---|
| 메뉴판 비전 | ✅ | `common/infra/llm/menu/OpenAiMenuBoardVisionExtractor.kt:75` |
| 음식 이미지 배치 | ✅ | `api/food/FoodImageBatchCollectService.kt:156` |
| **임베딩** | ❌ | `OpenAiTextEmbeddingClient` 에 `ApplicationEventPublisher` 자체가 없다 |

이유를 추정할 근거는 두 개다. ① 임베딩 어댑터의 생성자는 `props` 하나뿐이다(`OpenAiTextEmbeddingClient.kt:9-12`) — 이벤트 발행을 아예 설계에 넣지 않았다. ② **비용 리스너가 `:api` 에만 있다**(`api/metering/LlmCallCostEventListener.kt`). 임베딩을 부르는 건 `:batch` 인데, 배치 앱에는 그 리스너가 없다. 이벤트를 발행해도 받을 사람이 없다. 스프링 이벤트는 **같은 애플리케이션 컨텍스트 안**에서만 전달되기 때문이다 — 이 한계가 왜 프로세스를 넘는 일에는 큐가 필요한지를 설명하고, 그건 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] 의 주제다.

> [!note] 그래서 실무적으로는
> 임베딩 비용은 kbap 대시보드에 안 보인다. OpenAI 콘솔에서 봐야 한다. 벌크 재임베딩(§9-2)을 돌릴 때 이 사각지대가 커진다.

- 인덱스 `idx_food_vector_outbox_status_id (outbox_status, id)` 가 리더의 `WHERE outbox_status='PENDING' AND id > ? ORDER BY id` 를 정확히 받아 준다.

### 벡터 문서 (DocumentDB `kbap.foods`)

```json
{
  "foodId": 312,
  "name": "김치찌개",
  "longDescription": "돼지고기와 잘 익은 김치를 넣고 끓인 …",
  "imageRef": "foods/312.webp",
  "embedding": [0.021, -0.113, 0.077, "… 256개 …"],
  "embeddingHash": "sha256:9f2a…",
  "embeddingModel": "text-embedding-3-small",
  "embeddingDimension": 256,
  "indexedAt": "2026-08-26T21:30:11Z"
}
```

- 필드명은 전부 `FoodVectorDocuments.kt:6-15` 의 상수다. 읽는 쪽과 쓰는 쪽이 같은 상수를 참조해 오타로 인한 조용한 파손을 막는다.
- **`foodId` 만 신뢰값이고 나머지는 스냅샷**이다. 검색은 `foodId` 와 `score` 만 꺼내 쓰고, 화면에 보일 이름·설명은 **MySQL 에서 다시 조회**한다(`vector-food-document-v2.md`). 이유가 명확하다 — 문서의 `name` 은 적재 시점 값이라 MySQL 과 어긋날 수 있는데, **표시 데이터의 단일 진실은 MySQL** 이다.
- `foodId` 에 unique 인덱스가 필요하다. KB-318 이 구축한 건 `embedding` 벡터 인덱스뿐이라, 백필 전에 확인하라고 quickstart 가 명시한다(`specs/kb-328-food-vector-outbox/quickstart.md:37`) — 없으면 건당 풀스캔에 중복 문서 위험.

## 15. 용어집

| 말 | 뜻 |
|---|---|
| **임베딩** | 텍스트 → 고정 길이 숫자 배열. 뜻이 가까우면 배열도 가깝다 |
| **차원** | 그 배열의 길이. kbap 은 256. 저장 측과 검색 측이 같아야 성립 |
| **코사인 유사도** | 두 벡터의 방향 일치도(−1~1). 길이(=분량)를 무시하려고 쓴다 |
| **ANN / 벡터 인덱스** | 근사 최근접 탐색. 전수 비교 없이 가까운 벡터를 빨리 찾는 자료구조 |
| **DocumentDB** | AWS 의 MongoDB 호환 문서 DB. kbap 의 벡터 저장소 |
| **컬렉션 / 문서** | 문서 DB 의 테이블 / 행에 해당. 문서는 JSON 덩어리 |
| **`$search` + `vectorSearch`** | DocumentDB 의 벡터 검색 집계 문법. Atlas 의 `$vectorSearch` 와 다르다 |
| **`embeddingHash`** | `sha256(모델\|차원\|원문)`. 같으면 임베딩 호출을 건너뛴다 |
| **upsert** | 있으면 갱신, 없으면 삽입. kbap 은 문서 **전체 교체**(replace) |
| **멱등** | 같은 작업을 두 번 해도 결과가 같음. 되돌릴 수 없는 외부 호출의 정합성 수단 |
| **지터(jitter)** | 재시도 간격에 섞는 무작위. 동시 재시도가 몰리는 걸 흩뜨린다 |
| **백필(backfill)** | 기능이 생기기 전의 기존 데이터를 뒤늦게 채워 넣는 것 |

## 16. 체크리스트

- [ ] 왜 `matchKey` 정확 일치로는 `"엄마표김치찌개"` 를 못 찾는지, 벡터 검색은 어떻게 다르게 접근하는지 설명할 수 있다
- [ ] "텍스트를 256차원 벡터로 만든다" 를 수식 없이 설명하고, **그 비유가 어디서 깨지는지**(축에 이름이 없다, 정보가 손실된다)까지 말할 수 있다
- [ ] 코사인 유사도가 길이를 무시하는 게 왜 kbap 에 필요한지 말할 수 있다(저장은 긴 설명, 검색은 이름만)
- [ ] 벡터가 MySQL 이 아니라 DocumentDB 에 있는 이유를 말할 수 있다
- [ ] `FoodVectorStore` 가 `common.port.*` 가 아니라 `common.domain.food.vector` 에 있는 근거를 말할 수 있다
- [ ] 음식 승인 → 아웃박스 행 → 배치 → DocumentDB 의 전 경로를 파일 이름으로 짚을 수 있다
- [ ] `embeddingHash` 에 **모델명과 차원이 들어간** 이유와 그게 벤더 교체 때 무슨 일을 했는지 설명할 수 있다
- [ ] 벡터 검색이 "못 찾음" 을 반환하지 않는다는 뜻과, 임계값 기본값이 0.0 이었다는 게 무슨 의미인지 말할 수 있다
- [ ] **이 파이프라인의 읽기 쪽이 지금 없다**는 사실과 그 결정(KB-343)을 근거와 함께 설명할 수 있다
- [ ] 임베딩 비용이 `llm_call_cost` 에 안 쌓이는 이유 두 가지를 말할 수 있다
