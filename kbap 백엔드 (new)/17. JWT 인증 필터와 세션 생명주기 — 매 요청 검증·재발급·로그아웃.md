# 17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃

> 작성: 2026-08-27 · 맥락: 앞 노트에서 로그인이 끝나고 access·refresh 토큰 두 개가 앱 손에 쥐어졌다. 그런데 15·18·19번 노트를 열면 컨트롤러 첫 파라미터가 늘 `@AuthMemberId memberId: Long` 이고, **그 값이 어디서 왔는지는 컨트롤러 안 어디에도 없다.** 이 노트가 그 빈칸을 채운다.
> 목표: 요청이 컨트롤러에 닿기 **전에** 이미 무슨 일이 일어나 있는지 그림으로 그릴 수 있고, access 가 만료됐을 때 서버·앱이 각각 무엇을 하는지 시퀀스로 말할 수 있게 되기.

---

## 0. 한 줄 요약

kbap 은 요청마다 **서블릿 필터** 한 겹(`JwtAuthenticationFilter`)이 `Authorization: Bearer …` 헤더를 열어 서명·만료·용도를 검증하고, 꺼낸 회원 PK 를 요청에 꽂아둔다. 컨트롤러는 그 값을 `@AuthMemberId` 로 받아 쓴다. access 는 30분짜리 무상태 토큰이라 서버가 폐기할 수 없고, refresh 만 Redis 에 기록해 두어 **재발급 때 회전**하고 **로그아웃 때 지운다.**

---

## 1. 이건 "하나의 요청" 노트가 아니다

15·16·18번은 요청 하나를 따라간다. 이 노트는 다르다. **모든 요청에 공통으로 걸리는 가로줄**을 다룬다.

FE 로 치면 이렇다. 화면 컴포넌트마다 `fetch` 를 직접 쓰지 않고 `api/client.ts` 한 파일을 거치게 만들어, 헤더 붙이기·에러 정규화·401 재시도를 **한 곳에서** 처리하는 것. kbap 의 필터는 그 `client.ts` 의 서버 쪽 대응물이다. 다만 방향이 반대다 — 나가는 요청이 아니라 **들어오는 요청**을 한 곳에서 검사한다.

Express 를 써 봤다면 `app.use((req, res, next) => …)` 미들웨어가 가장 가깝다. `next()` 를 부르면 다음으로 넘어가고, 안 부르고 `res.status(401).json(…)` 하면 거기서 끝난다. 서블릿 필터도 정확히 같은 모양이다.

| Express 미들웨어 | 서블릿 필터 |
|---|---|
| `(req, res, next) => {}` | `doFilterInternal(request, response, filterChain)` |
| `next()` | `filterChain.doFilter(request, response)` |
| `res.status(401).json(...)` 하고 `next()` 안 부름 | `response.writer.write(...)` 하고 `doFilter` 안 부름 |
| `req.userId = …` 로 뒤에 넘기기 | `request.setAttribute("authMemberId", …)` |
| `app.use('/api/members', mw)` | `FilterRegistrationBean.addUrlPatterns("/api/members/*")` |

> [!note] 비유의 경계
> Express 미들웨어는 라우터와 같은 세계에 산다. 서블릿 필터는 **스프링 MVC 바깥**에 있다 — 서블릿 컨테이너(톰캣)의 규격이고, 스프링은 그 위에 얹힌 서블릿 하나(`DispatcherServlet`)일 뿐이다. 이 차이가 §4 의 "필터에서 던진 예외는 `@RestControllerAdvice` 가 못 잡는다" 를 낳는다.

## 2. 요청 하나가 컨트롤러에 닿기까지 — 전체 그림

```
       HTTP 요청  GET /api/members/me/profile
            │     Authorization: Bearer eyJ...
            ▼
┌─────────────────────────────────────────────────────────┐
│ 톰캣 (서블릿 컨테이너)                                    │
│                                                          │
│  ① RequestLoggingFilter          ← 서블릿 필터            │
│     order = HIGHEST_PRECEDENCE                           │
│     requestId 생성 · MDC 세팅 · "--> GET …" 로그          │
│     ┌──────────────────────────────────────────────┐    │
│     │ ② JwtAuthenticationFilter   ← 서블릿 필터     │    │
│     │    order 미지정 = LOWEST_PRECEDENCE           │    │
│     │    토큰 검증 → attribute 2개 + MDC memberId    │    │
│     │    ✗ 실패하면 여기서 401 JSON 직접 쓰고 끝     │    │
│     │    ┌────────────────────────────────────┐    │    │
│     │    │ ③ DispatcherServlet  ← 스프링 MVC   │    │    │
│     │    │    핸들러 찾기 · X-API-Version 해석  │    │    │
│     │    │    ④ HandlerInterceptor            │    │    │
│     │    │       AdminAuthorizationInterceptor │    │    │
│     │    │    ⑤ ArgumentResolver              │    │    │
│     │    │       @AuthMemberId → Long          │    │    │
│     │    │    ⑥ 컨트롤러 메서드 실행            │    │    │
│     │    │    ⑦ @RestControllerAdvice (예외)   │    │    │
│     │    └────────────────────────────────────┘    │    │
│     └──────────────────────────────────────────────┘    │
│     ⑧ finally: 응답 로그 + MDC.clear()                   │
└─────────────────────────────────────────────────────────┘
            │
            ▼  HTTP 응답
```

| 순서 | 자리 | 파일 | 하는 일 |
|---|---|---|---|
| ① | 서블릿 필터 (바깥) | `api/.../core/logging/RequestLoggingFilter.kt:26` | `requestId` UUID 생성·응답 헤더 부착, 요청/응답 로그 1쌍, `finally` 에서 `MDC.clear()` |
| ② | 서블릿 필터 (안) | `api/.../core/auth/JwtAuthenticationFilter.kt:27` | Bearer 토큰 파싱·검증, `authMemberId`·`authMemberRole` attribute 세팅, MDC 에 `memberId` 추가 |
| ③ | 스프링 MVC 진입 | `DispatcherServlet` (프레임워크) | 핸들러 매핑, `X-API-Version` 헤더로 버전 분기 |
| ④ | 인터셉터 | `api/.../admin/AdminAuthorizationInterceptor.kt:12` | `/api/admin/**` 에서 attribute 의 role 이 `ADMIN` 인지 확인 |
| ⑤ | 인자 리졸버 | `api/.../core/auth/AuthMemberIdArgumentResolver.kt:18` | attribute 를 읽어 `@AuthMemberId` 파라미터에 바인딩 |
| ⑥ | 컨트롤러 | 예: `api/.../member/MemberController.kt:37` | 비즈니스 처리 |
| ⑦ | 전역 예외 처리 | `api/.../core/GlobalExceptionHandler.kt:46` | `BusinessException` → 공통 에러 봉투 |

**여기서 계층이 바뀌는 이유** — ①②는 톰캣의 규격(`jakarta.servlet.Filter`)이고 ③~⑦은 스프링 MVC 의 세계다. 인증을 ②에 둔 건 의도적이다. 인증은 "어느 컨트롤러냐" 와 무관한 **전(前) 조건**이라, 핸들러를 고르기 전에 끝나야 한다. 반대로 "이 사람이 관리자냐" 는 **경로에 따라 다른** 질문이라 ④ 인터셉터에 있다. 두 자리의 차이는 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] 의 "각 계층은 자기 층의 질문만 답한다" 규칙이 횡단 관심사에도 그대로 적용된 것이다.

> [!tip] 순서가 왜 로깅이 바깥인가
> `RequestLoggingFilter` 는 `order = Ordered.HIGHEST_PRECEDENCE` 로 등록되고(`WebConfig.kt:64`), JWT 필터는 `order` 를 지정하지 않아 기본값(가장 낮은 우선순위)을 갖는다. 그래서 로깅이 **바깥**이다. 덕분에 JWT 필터가 401 로 끊어버린 요청도 응답 로그가 정확히 1줄 남는다 — 인증 실패는 로그에서 사라지면 안 되는 사건이다.

## 3. 필터 실코드 — 한 줄씩

`api/src/main/kotlin/com/kbap/api/core/auth/JwtAuthenticationFilter.kt:27-43`

```kotlin
override fun doFilterInternal(
    request: HttpServletRequest,
    response: HttpServletResponse,
    filterChain: FilterChain,
) {
    try {
        val token = bearerToken(request)
        val parsed = tokenParser.parseAccessToken(token)
        request.setAttribute(MEMBER_ID_ATTRIBUTE, parsed.memberId)
        request.setAttribute(ROLE_ATTRIBUTE, parsed.roleName)
        MDC.put(RequestLoggingFilter.MEMBER_ID_KEY, parsed.memberId.toString())
        filterChain.doFilter(request, response)
    } catch (e: BusinessException) {
        writeUnauthorized(response, e)
    }
}
```

- `bearerToken` — `Authorization` 헤더가 없거나 `Bearer ` 로 시작하지 않으면 즉시 `INVALID_ACCESS_TOKEN`(`:45-51`). 헤더 유무 판정과 서명 검증이 **같은 에러 코드**로 합쳐진다는 뜻이다(§11 에서 이게 FE 에 어떻게 보이는지 다룬다).
- `parseAccessToken` — 서명·만료·`token_type` 을 한 번에 검증한다(§6).
- `setAttribute` 두 줄 — 요청 객체에 값을 얹어 둔다. **요청이 살아 있는 동안만** 유효한 임시 보관함이고, 응답이 나가면 사라진다. FE 로 치면 한 번의 `fetch` 호출 안에서만 도는 지역 변수에 가깝다.
- `MDC.put` — 로그 문맥에 `memberId` 를 심는다. 이 이후 찍히는 **모든 로그 줄**에 `[reqId=…][memberId=42]` 가 자동으로 붙는다. 패턴은 `api/src/main/resources/application.yml:1-5` 에 있다(KB-130).
- `filterChain.doFilter` — 이걸 불러야 다음 칸으로 간다. `catch` 로 빠지면 안 부르므로 **컨트롤러는 아예 실행되지 않는다.**

> [!info] `OncePerRequestFilter` 가 뭔가
> 스프링이 주는 필터 베이스 클래스다. 서블릿 컨테이너는 `forward`·`include`·비동기 재개 등으로 같은 요청에 대해 필터 체인을 **여러 번** 태울 수 있다. `OncePerRequestFilter` 는 요청당 정확히 한 번만 `doFilterInternal` 이 돌게 보장한다. 인증·로깅처럼 "두 번 하면 곤란한" 일에 쓴다.

### 실패했을 때 — 필터가 JSON 을 직접 쓴다

```kotlin
private fun writeUnauthorized(response: HttpServletResponse, e: BusinessException) {
    response.status = e.errorCode.status
    response.contentType = MediaType.APPLICATION_JSON_VALUE
    response.characterEncoding = Charsets.UTF_8.name()
    response.writer.write(objectMapper.writeValueAsString(BaseResponse.fail(e.errorCode.code, e.errorCode.message)))
}
```

`JwtAuthenticationFilter.kt:53-58` 이다. `@RestControllerAdvice`(`GlobalExceptionHandler`)가 이미 똑같은 봉투를 만들어 주는데 왜 여기서 또 만드나?

**필터는 `DispatcherServlet` 바깥이기 때문이다.** `@RestControllerAdvice` 는 스프링 MVC 안에서 핸들러 실행 중 터진 예외만 잡는다. 필터에서 던진 예외는 스프링에 도달하지도 않는다. 그래서 필터는 `jacksonObjectMapper()` 를 직접 들고(`:22`) 응답 봉투를 손으로 직렬화한다. 공통 봉투의 모양 자체는 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 참고.

> [!warning] 봉투 생성 코드가 두 군데다
> `BaseResponse.fail(...)` 을 쓰긴 하지만, "상태 코드·content type·인코딩을 세팅하고 쓴다" 는 절차가 필터와 `GlobalExceptionHandler` 두 곳에 따로 있다. 봉투 형식이 바뀌면 두 곳을 함께 고쳐야 한다. 필터라는 자리를 고른 대가다.

## 4. 필터는 모든 요청에 걸리지 않는다

FE 개발자가 가장 놀라는 부분이다. 필터가 **모든 경로**에 도는 게 아니라, 등록할 때 명시한 URL 패턴에만 붙는다.

`api/src/main/kotlin/com/kbap/api/core/config/WebConfig.kt:68-101`

```kotlin
@Bean
fun jwtAuthenticationFilterRegistration(): FilterRegistrationBean<JwtAuthenticationFilter> =
    FilterRegistrationBean(
        JwtAuthenticationFilter(
            tokenParser,
            guestExemptions = listOf(
                JwtAuthenticationFilter.GuestExemption("GET", Regex("^${ApiPaths.API}/community/posts$")),
                JwtAuthenticationFilter.GuestExemption("GET", Regex("^${ApiPaths.API}/community/posts/\\d+$")),
                JwtAuthenticationFilter.GuestExemption("GET", Regex("^${ApiPaths.API}/reviews$")),
            ),
        ),
    ).apply {
        addUrlPatterns(
            "${ApiPaths.API}/members/*",
            "${ApiPaths.API}/scans",
            …
        )
    }
```

`ApiPaths.API` 는 `"/api"` 다(`api/.../core/ApiPaths.kt:4`). **버전이 경로에 없다** — 버전은 `X-API-Version` 헤더로 가른다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]).

보호되는 경로는 실측으로 19개 패턴이다(`WebConfig.kt:80-100`): `members/*`, `foods/scanned`, `scans`, `scans/*`, `bookmarks`, `bookmarks/*`, `reviews`, `reviews/*`, `places/*`, `orders`, `orders/*`, `community/posts`, `community/posts/*`, `community/comments/*`, `reports`, `images`, `images/*`, `auth/withdraw`, `admin/*`.

**목록에 없는 것이 더 중요하다.**

- `/api/auth/login`·`/api/auth/refresh`·`/api/auth/logout` — 없다. 당연하다. 로그인은 토큰을 **얻으러** 오는 요청이고, refresh 는 access 가 만료됐을 때 부르는 것이라 access 를 요구하면 영원히 못 벗어난다. `auth/withdraw` 만 목록에 있다.
- `/api/home` — 없다. 홈은 로그인 전에도 보이는 화면이다([[18. 홈 화면 조회 흐름 — 여러 서비스를 한 응답으로 모으기]]).
- `/api/foods/*` 대부분 — 없다(`foods/scanned` 만 있다).
- `/api/app-version` — 없다. 강제 업데이트 게이트는 인증 이전에 답해야 한다.

### 게스트 예외 — 목록엔 있는데 통과시키는 경우

```kotlin
override fun shouldNotFilter(request: HttpServletRequest): Boolean =
    guestExemptions.any { request.method == it.method && it.path.matches(request.requestURI) }
```

`JwtAuthenticationFilter.kt:24-25`. `shouldNotFilter` 는 `OncePerRequestFilter` 의 훅으로, `true` 를 주면 이 필터를 통째로 건너뛴다.

URL 패턴은 서블릿 규격이라 **메서드를 구분하지 못한다.** `/api/reviews` 를 등록하면 GET 도 POST 도 다 걸린다. 그런데 리뷰 목록은 비로그인도 봐야 하고, 리뷰 작성은 로그인이 필요하다. 그래서 "패턴으로 넓게 걸고, `shouldNotFilter` 로 메서드+경로 조합만 뺀다" 는 2단 구조가 됐다.

| 예외 | 왜 |
|---|---|
| `GET /api/community/posts` | 게스트가 커뮤니티 피드를 읽을 수 있다 |
| `GET /api/community/posts/{id}` | 게시글 상세도 마찬가지 |
| `GET /api/reviews` | 리뷰 목록도 마찬가지 |

> [!note] 실측 — 게시글은 게스트가 읽는데 댓글은 못 읽는다
> `GET /api/community/posts/{postId}/comments` 는 URL 패턴 `"/api/community/posts/*"` 에 걸리지만, 게스트 예외 정규식 `^/api/community/posts/\d+$` 에는 **매칭되지 않는다**(뒤에 `/comments` 가 붙어 끝이 다르다). 그리고 그 핸들러는 `@AuthMemberId`(필수)를 받는다(`api/.../community/CommunityController.kt:112-114`). 즉 **게스트는 글은 보고 댓글은 401 을 받는다.**
>
> 이건 **의도다.** `specs/kb-292-community-comments/spec.md:89`(FR-010)가 못 박았다 — "게스트에게는 댓글 내용을 제공하지 않는다 — 목록 조회는 인증 오류로 거부하고, 댓글 개수만 기존 피드·글 상세 응답으로 노출한다(블러 처리는 FE 책임)." 즉 정규식이 `/comments` 를 안 잡는 게 아니라 **잡으면 안 되는 것**이다. 자세한 근거는 [[25. 커뮤니티 흐름 — 포스팅·댓글·커서 페이징]] §7.
>
> 게스트 예외 목록이 "인증이 필요 없는 경로" 가 아니라 **"제품이 게스트에게 열기로 한 경로"** 라는 걸 보여주는 사례다. 이 목록은 보안 판단이 아니라 기획 판단이 들어오는 자리다.

## 5. 필터가 꽂은 값이 컨트롤러 파라미터가 되기까지

컨트롤러에는 이렇게 쓰여 있다(`api/.../member/MemberController.kt:37-40`).

```kotlin
@GetMapping("/me/profile")
override fun getMyProfile(
    @AuthMemberId memberId: Long,
): ResponseEntity<BaseResponse<MyProfileResponse>> {
```

`@AuthMemberId` 는 kbap 이 직접 만든 애너테이션이고, 몸통이 없다(`AuthMemberId.kt` 5줄이 전부다). 애너테이션 자체는 **표시**일 뿐 아무 일도 하지 않는다. 실제 일은 `HandlerMethodArgumentResolver` 가 한다.

FE 비유: `@AuthMemberId` 는 `useContext(AuthContext)` 에 해당한다. 컴포넌트는 값을 어디서 가져오는지 신경 쓰지 않고 선언만 하고, 값을 넣어주는 건 위쪽의 Provider 다. **차이**: React Context 는 컴포넌트 트리를 타고 흐르지만, 여기서는 "요청 객체" 라는 평평한 보관함에서 꺼낸다.

### 리졸버 A — `AuthMemberIdArgumentResolver` (필수)

`api/.../core/auth/AuthMemberIdArgumentResolver.kt:14-28`

```kotlin
override fun supportsParameter(parameter: MethodParameter): Boolean =
    parameter.hasParameterAnnotation(AuthMemberId::class.java) &&
        parameter.parameterType == Long::class.java

override fun resolveArgument(…): Long {
    val role = webRequest.getAttribute(JwtAuthenticationFilter.ROLE_ATTRIBUTE, RequestAttributes.SCOPE_REQUEST) as? String
    if (role == MemberRole.ADMIN.name) throw BusinessException(ErrorCode.INVALID_ACCESS_TOKEN)
    return webRequest.getAttribute(JwtAuthenticationFilter.MEMBER_ID_ATTRIBUTE, RequestAttributes.SCOPE_REQUEST) as? Long
        ?: throw BusinessException(ErrorCode.INVALID_ACCESS_TOKEN)
}
```

- `supportsParameter` — "내가 이 파라미터를 맡을 수 있나?" 를 스프링이 물어보는 자리. 애너테이션이 붙었고 타입이 `Long` 이면 맡는다.
- **관리자 토큰은 사용자 API 를 못 쓴다**(`:25`). role 이 `ADMIN` 이면 회원 PK 가 있어도 거절한다. 관리자 계정으로 일반 회원 흉내를 내는 경로를 막는 장치다.
- **attribute 가 없으면 `INVALID_ACCESS_TOKEN`.** 여기가 §4 와 이어지는 함정이다.

> [!warning] `@AuthMemberId` 와 URL 패턴 목록은 손으로 맞춰야 한다
> 리졸버는 **필터가 이미 돌았다고 가정**한다. 어떤 컨트롤러에 `@AuthMemberId` 를 붙여 놓고 `WebConfig` 의 `addUrlPatterns` 에 그 경로를 안 넣으면, 정상 토큰을 보내도 attribute 가 비어 있어 **항상 401 AUTH-003** 이 난다. 컴파일러도 ArchUnit 도 이 짝을 검사하지 않는다([[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 의 규칙 목록에 없다). 새 보호 엔드포인트를 만들면 두 곳을 같이 고쳐야 한다.

### 리졸버 B — `AuthMemberIdOrNullArgumentResolver` (선택)

게스트도 부를 수 있지만 "로그인했으면 개인화" 하고 싶은 엔드포인트용이다. 홈·음식 목록·리뷰 목록·커뮤니티 피드가 쓴다(`HomeController.kt:26`, `FoodController.kt:35,46,81`, `ReviewController.kt:97`, `CommunityController.kt:73`).

`api/.../core/auth/AuthMemberIdOrNullArgumentResolver.kt:18-30`

```kotlin
override fun resolveArgument(…): Long? {
    val request = webRequest.getNativeRequest(HttpServletRequest::class.java) ?: return null
    val header = request.getHeader(AUTHORIZATION_HEADER) ?: return null
    if (!header.startsWith(BEARER_PREFIX)) return null
    val parsed = tokenParser.parseAccessToken(header.removePrefix(BEARER_PREFIX))
    if (parsed.role == MemberRole.ADMIN) return null
    return parsed.memberId
}
```

**이 리졸버는 attribute 를 읽지 않는다.** 헤더를 직접 열고 `tokenParser` 로 다시 파싱한다. 필터가 안 도는 경로(`/api/home` 등)에서도 동작해야 하니 당연한 설계다.

> [!warning] "OrNull" 은 "토큰이 틀려도 null" 이 아니다
> `parseAccessToken` 은 예외를 **던진다**. 즉 이름과 달리 이 리졸버가 `null` 을 주는 건 ① 헤더가 없거나 ② `Bearer ` 가 아니거나 ③ 관리자 토큰일 때뿐이다. **만료·위조 토큰을 달고 홈을 부르면 401 이 난다**(리졸버는 MVC 안이므로 이번엔 `GlobalExceptionHandler` 가 봉투를 만든다). 이건 버그가 아니라 오히려 FE 재시도 계약에 필요하다 — §11 참고.

두 리졸버는 `WebConfig.addArgumentResolvers` 에서 등록된다(`WebConfig.kt:48-51`). 리졸버 B 만 `tokenParser` 를 생성자로 받는데, 이게 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] 의 전형적 모양이다 — `WebConfig` 가 컨테이너에서 받은 빈을 손으로 넘겨 조립한다.

## 6. 두 토큰 — 수명과 역할

`api/src/main/resources/application.yml:56-60`

```yaml
    jwt:
      secret: ${JWT_SECRET:}
      access-ttl: 30m
      refresh-ttl: 14d
```

yml 주석이 이유를 그대로 적어 뒀다 — "access 는 stateless 라 만료 전 무효화가 불가능하므로 짧게, refresh 는 Redis 폐기가 가능하므로 길게."

| | access | refresh |
|---|---|---|
| 수명 | 30분 | 14일 |
| 어디에 쓰나 | **모든** 보호 API 의 `Authorization` 헤더 | `POST /api/auth/refresh` 본문 하나뿐 |
| 담긴 것 | `sub`(회원 PK), `token_type=ACCESS`, `role` | `sub`(회원 PK), `token_type=REFRESH`, `jti` |
| 서버 기록 | **없음** (무상태) | Redis `auth:refresh:{jti}` |
| 만료 전 취소 | 불가능 | 가능 (Redis 키 삭제) |
| 검증 주체 | 필터 / 리졸버 B | `AuthService.refresh` |

### `token_type` — 두 토큰을 섞어 쓸 수 없게 하기

`api/.../infra/auth/token/TokenType.kt`

```kotlin
enum class TokenType {
    ACCESS,
    REFRESH,
    SCAN_TICKET,
    ;

    companion object {
        const val CLAIM: String = "token_type"
    }
}
```

발급할 때 이 값을 클레임으로 박고(`JwtTokenIssuer.kt:26,39`), 파싱할 때 기대값과 다르면 서명이 맞아도 거절한다(`JwtTokenParser.kt:41-45`).

왜 필요한가? 세 토큰이 **같은 시크릿**으로 서명되기 때문이다(`JwtTokenParser.kt:21`, `JwtTokenIssuer.kt:20`, `JwtScanTicketManager.kt:21` 모두 `properties.secret`). 이 클레임이 없으면 14일짜리 refresh 토큰을 `Authorization` 헤더에 그대로 넣어도 서명 검증을 통과해 버린다 — 30분 수명 제한이 통째로 무의미해진다. `token_type` 은 **같은 열쇠로 잠근 서랍들을 구분하는 라벨**이다.

`SCAN_TICKET` 은 스캔 한 도 관리용 단기 토큰인데(TTL 기본 300초), 이 노트 범위 밖이다 — 20번 스캔 v2 노트가 다룬다.

### 만료와 조작을 구분한다

`api/.../infra/auth/token/JwtTokenParser.kt:54-63`

```kotlin
private fun claims(token: String, onExpired: ErrorCode, onInvalid: ErrorCode): Claims =
    try {
        Jwts.parser().verifyWith(key).build().parseSignedClaims(token).payload
    } catch (e: ExpiredJwtException) {
        throw BusinessException(onExpired)
    } catch (e: JwtException) {
```

만료(`EXPIRED_*`)와 무효(`INVALID_*`)를 **다른 에러 코드**로 나눈다. 이게 §11 의 FE 계약을 가능하게 하는 핵심이다 — 앱은 "만료면 갱신, 무효면 재로그인" 으로 갈라야 하는데, 코드가 하나면 갈 수 없다.

## 7. refresh 는 왜 Redis 에 있나 — 무상태의 예외

JWT 의 장점은 **서버가 아무것도 기억하지 않아도 된다**는 것이다. 서명만 확인하면 되니 DB 조회가 0회고, 서버를 몇 대로 늘려도 세션 공유 문제가 없다. 쿠키·세션과의 대비는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]] 에 있다.

그 장점의 뒷면이 **취소할 수 없다**는 것이다. 서명이 유효하고 만료 전이면 서버는 거절할 근거가 없다. 로그아웃을 눌러도, 계정이 정지돼도, 토큰이 털려도 마찬가지다.

kbap 은 여기서 타협한다.

- **access(30분)**: 무상태 그대로 둔다. 취소 불가를 받아들이되 **수명을 짧게** 해서 피해 창을 좁힌다.
- **refresh(14일)**: 서버가 기록한다. 14일짜리를 취소할 수 없게 두는 건 위험이 너무 크다.

기록의 자리가 Redis다.

`api/src/main/kotlin/com/kbap/api/infra/redis/RedisRefreshTokenStore.kt`

```kotlin
@Component
class RedisRefreshTokenStore(
    private val redisTemplate: StringRedisTemplate,
) : RefreshTokenStore {
    override fun save(jti: String, memberId: Long, ttl: Duration) {
        redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
    }

    override fun consume(jti: String): Long? =
        redisTemplate.opsForValue().getAndDelete(key(jti))?.toLongOrNull()

    override fun delete(jti: String) {
        redisTemplate.delete(key(jti))
    }

    private fun key(jti: String): String = "$KEY_PREFIX$jti"
    …
}
```

키 하나에 값 하나: `auth:refresh:{jti}` → `"{memberId}"`, TTL 14일. 저장소가 TTL 을 알아서 지워 주므로 **만료된 세션을 청소하는 배치가 필요 없다.** RDB 였다면 만료 행을 지우는 잡을 따로 돌려야 한다.

계약과 구현이 갈라져 있다는 점도 짚어 두자. 인터페이스 `RefreshTokenStore` 는 `common/port/auth/` 에 있고 Redis 를 전혀 모른다. Redis 구현은 그걸 쓰는 모듈(`api/infra/redis/`)에 있다. 이 구조가 왜 이런지는 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]].

> [!note] Redis 를 "캐시" 라고 부르지 말자
> 여기서 Redis 는 캐시가 아니다. 캐시는 날아가도 원본이 어딘가 있어서 다시 채우면 그만인 것을 말한다. 이 키가 날아가면 **모든 사용자가 강제 로그아웃**된다(재발급이 전부 `consume` 에서 null 을 받는다). 복구할 원본이 없다 — 이건 원본 저장소다. kbap 이 Redis 를 쓰는 두 용도(refresh 세션·스캔 예약)가 둘 다 캐시가 아니라는 이야기는 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식]] 에서 다룬다.

## 8. 회전(rotation) — 재발급 시퀀스

`POST /api/auth/refresh` 하나가 전부다. 컨트롤러는 얇다(`api/.../auth/AuthController.kt:23-29`) — 서비스를 부르고 결과를 봉투에 담을 뿐이다.

`api/src/main/kotlin/com/kbap/api/auth/AuthService.kt:46-70`

```kotlin
fun refresh(refreshToken: String): RefreshResult {
    val parsed = try {
        tokenParser.parseRefreshToken(refreshToken)
    } catch (e: BusinessException) {
        if (e.errorCode == ErrorCode.EXPIRED_REFRESH_TOKEN) {
            tokenParser.refreshTokenJtiOrNull(refreshToken)?.let { refreshTokenStore.delete(it) }
        }
        throw e
    }

    val memberId = refreshTokenStore.consume(parsed.jti)
        ?: throw BusinessException(ErrorCode.INVALID_REFRESH_TOKEN)

    if (memberService.getMemberOrNull(memberId) == null) {
        throw BusinessException(ErrorCode.INVALID_REFRESH_TOKEN)
    }

    val rotated = tokenIssuer.issueRefreshToken(memberId)
    refreshTokenStore.save(rotated.jti, memberId, refreshTtl)

    return RefreshResult(
        accessToken = tokenIssuer.issueAccessToken(memberId, MemberRole.USER),
        refreshToken = rotated.token,
    )
}
```

순서대로:

1. **파싱·검증** — 서명·만료·`token_type=REFRESH` 를 본다. 만료였다면 예외를 다시 던지기 전에 **Redis 키를 먼저 지운다**(`:50-52`). 만료된 토큰에서 jti 를 꺼낼 수 있는 건 `refreshTokenJtiOrNull` 이 `ExpiredJwtException.claims.id` 로 폴백하기 때문이다(`JwtTokenParser.kt:47-52`).
2. **소비(consume)** — `GETDEL` 로 값을 읽으면서 **동시에 지운다**. 이게 회전의 심장이다.
3. **회원 존재 확인** — 탈퇴한 회원의 refresh 는 여기서 걸린다. 2번이 이미 키를 지웠으므로 그 토큰은 이 시점에 완전히 죽는다.
4. **새 refresh 발급·저장** — 새 jti, 새 14일 TTL. 즉 **재발급할 때마다 세션 수명이 연장된다**(슬라이딩 만료). 매일 앱을 쓰는 사람은 사실상 로그아웃되지 않고, 14일 이상 안 쓰면 재로그인해야 한다.
5. **새 access 발급** — role 은 `USER` 로 고정 발급된다(`:67`). 관리자 세션이 refresh 로 유지되지 않는다는 뜻이다.

### `consume` 이 왜 원자적이어야 하나

포트 인터페이스에 이유가 주석으로 남아 있다 — `common/port/auth/RefreshTokenStore.kt:8` "원자적 소비(조회+삭제) — rotation 경합 방어."

앱이 여러 화면에서 동시에 API 를 부르다 한꺼번에 401 을 받으면, refresh 요청이 **동시에 두 번** 나갈 수 있다. `GET` 후 `DELETE` 를 따로 하면 둘 다 값을 읽어 둘 다 새 세션을 발급받는다 — 세션이 하나 유실되고, 나중 것이 이긴다. `getAndDelete`(Redis `GETDEL`)는 한 명령이므로 **한쪽만 값을 받고 다른 쪽은 null → 401** 이다. 이 "읽고 쓰기 사이에 끼어드는 문제" 는 요청마다 다른 스레드가 도는 JVM 서버의 기본 조건이다([[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]]).

Node 의 단일 이벤트루프에 익숙하면 이 문제가 낯설다. 하지만 Node 라도 서버를 2대 띄우면 똑같이 겪는다 — 원자성은 언어가 아니라 **공유 저장소**의 문제다.

## 9. 재사용 탐지는 없다 — 정직한 한계

교과서적인 refresh rotation 에는 짝이 하나 더 있다. **재사용 탐지(reuse detection)** — 이미 회전된 옛 토큰이 다시 제출되면 "탈취됐다" 고 판단해 그 **세션 계보 전체**를 폐기하는 것이다.

kbap 에는 없다. 코드를 다시 보면 `consume` 이 null 을 반환할 때 하는 일은 `INVALID_REFRESH_TOKEN` 을 던지는 것뿐이다(`AuthService.kt:56-57`). 옛 토큰이 왜 없는지 — 회전됐는지, 로그아웃됐는지, TTL 이 끝났는지 — 구분하지 않고, 현재 살아 있는 세션에는 아무 영향도 주지 않는다.

함의는 이렇다.

| 상황 | 지금 일어나는 일 | 재사용 탐지가 있었다면 |
|---|---|---|
| 앱이 실수로 옛 토큰 재사용 | 401 → 재로그인 유도 | 같음 (또는 과잉 로그아웃) |
| 공격자가 refresh 를 훔쳐 **먼저** 씀 | 공격자가 새 세션을 갖고, **정상 사용자가** 다음 갱신 때 401 → 재로그인 | 정상 사용자의 갱신이 탈취를 알리고 **양쪽 다** 끊긴다 |
| 공격자가 refresh 를 훔쳐 **나중에** 씀 | 공격자만 401 (정상 사용자는 이미 회전시킴) | 같음 + 알림 |

즉 **탈취를 막지는 못하지만, 탈취가 조용히 영구화되지도 않는다** — 정상 사용자가 재로그인해야 하는 상황이 곧 이상 신호다. 다만 서버는 그 신호를 기록하지 않으므로 사후 추적은 안 된다.

이건 결함이라기보다 위험 대비 복잡도의 선택으로 보인다. 재사용 탐지를 하려면 jti 하나가 아니라 **계보(family) 단위**로 상태를 들고 있어야 하고, 저장 구조가 통째로 바뀐다. 다만 레포 어디에도 이 선택을 기록한 ADR 이나 스펙 문장은 찾지 못했다 — 합류 후 확인해 볼 만한 질문이다.

## 10. 로그아웃 — 서버가 실제로 지우는 것

`api/src/main/kotlin/com/kbap/api/auth/AuthService.kt:72-78`

```kotlin
fun logout(refreshToken: String?) {
    if (refreshToken.isNullOrBlank()) {
        return
    }
    val jti = tokenParser.refreshTokenJtiOrNull(refreshToken) ?: return
    refreshTokenStore.delete(jti)
}
```

세 줄이 전부다. **Redis 키 하나를 지운다.** 그게 서버가 하는 일의 전부다.

- **멱등하다.** 본문이 없어도(`AuthController.kt:33` 이 `required = false`), 토큰이 빈 문자열이어도, 이미 지워진 뒤여도 200 이다. 재시도해도 안전하다는 뜻이고, 실제로 앱은 네트워크가 불안정할 때 로그아웃을 다시 부를 수 있다.
- **만료된 토큰으로도 로그아웃된다.** `refreshTokenJtiOrNull` 은 서명 검증 성공 또는 만료 예외의 클레임 둘 다에서 jti 를 꺼낸다(`JwtTokenParser.kt:47-52`).
- **access 토큰은 손대지 않는다.**

> [!warning] 무상태의 대가 — 로그아웃 후에도 최대 30분
> 로그아웃 직후에도 이미 발급된 access 토큰은 **만료될 때까지 유효하다.** 필터는 DB 도 Redis 도 조회하지 않고 서명과 `exp` 만 보기 때문이다. 사용자가 "로그아웃했는데 왜 아직 되냐" 를 겪지 않는 건 오직 **앱이 저장소에서 토큰을 지우기 때문**이다 — 서버가 아니라 클라이언트가 보장한다.
>
> 탈퇴도 마찬가지다. 회원 행을 소프트 삭제해도 access 토큰은 최대 30분 산다. refresh 는 `AuthService.kt:59-61` 의 회원 존재 확인에서 막힌다.
>
> 이걸 막으려면 필터가 매 요청 "이 토큰 폐기됐나?" 를 조회해야 하고, 그러면 무상태의 이점이 사라진다. 30분이 그 거래의 가격이다.

> [!warning] AUTH-003 이 "토큰 없음" 과 "토큰 위조" 를 합친다
> 필터의 `bearerToken` 은 헤더가 아예 없을 때도 `INVALID_ACCESS_TOKEN` 을 던진다(`JwtAuthenticationFilter.kt:47-49`). 그래서 **게스트가 보호 API 를 부른 경우**와 **토큰이 위조된 경우**가 같은 코드로 나간다. FE 는 여기에 실제로 걸려서 방어 코드를 넣었다 — §아래.

### FE 는 이걸 어떻게 소비하나

사용자의 앱 코드(`kbap-fe/src/lib/api/client.ts`)가 이 계약의 반쪽이다.

```ts
if (res.status === 401 && !isRetry && onUnauthorized && !path.startsWith('/auth/')) {
  let authCode: string | null = null;
  try {
    authCode = (JSON.parse(text) as BaseResponse<T> | null)?.code ?? null;
  } catch { /* 비JSON 401(프록시/게이트웨이) */ }
  const refreshed = await onUnauthorized(authCode).catch(() => false);
  if (refreshed) return request<T>(method, path, body, true, timeoutMs, extraHeaders);
}
```

`kbap-fe/src/lib/api/client.ts:198-207`. 그리고 분기 정책은 `kbap-fe/src/lib/auth/beAuth.ts:132-143`.

```ts
async function handleUnauthorized(code: string | null): Promise<boolean> {
  if (code === 'AUTH-004' || code == null) return tryRefresh();
  if (code === 'AUTH-003' || code === 'AUTH-005' || code === 'AUTH-006') {
    if ((await loadTokens()) != null) await sessionExpired();
    return false;
  }
  return false;
}
```

읽는 법:

- **AUTH-004 만 갱신할 가치가 있다.** 만료는 정상적인 일이므로 refresh 로 새 토큰을 받아 원요청을 **1회** 재시도한다.
- **003·005·006 은 왕복 없이 즉시 세션 만료.** 위조·폐기는 refresh 를 해 봐야 소용없다.
- **`/auth/*` 자체의 401 은 재시도하지 않는다.** 로그인·갱신 실패는 그대로 표면화돼야 한다. 무한 루프 방지이기도 하다.
- `code` 가 null(비JSON 401 — 프록시가 끼어든 경우)이면 refresh 를 1회 시도한다. 진짜 만료였는데 본문이 깨져 세션을 잃는 사고를 막는 fail-safe.
- 그리고 **AUTH-003 분기의 `if ((await loadTokens()) != null)`** — 저장된 토큰이 없는 게스트가 무토큰 401 을 받은 경우다. 지울 세션이 없으니 `sessionExpired()`(캐시 전체 소거)를 건너뛴다. 위의 "AUTH-003 이 두 상황을 합친다" 를 FE 가 이렇게 흡수했다.

앱은 또 로그인·갱신·로그아웃 세 경로에 **Authorization 헤더를 아예 붙이지 않는다**(`client.ts:96, 146-149`). 이유가 주석에 적혀 있다 — 만료된 access 가 붙으면 서버가 요청 자체를 401 시켜 refresh 가 영원히 실패한다. §4 에서 본 "auth 경로는 필터 목록에 없다" 와 짝을 이루는 클라이언트 쪽 규약이다.

> [!tip] 이 노트의 한 줄 실전 가치
> "401 이 뜬다" 는 버그 리포트를 받으면 **응답 본문의 `code` 를 먼저 본다.** AUTH-004 면 갱신 배선 문제, AUTH-003 이면 토큰·헤더 문제이거나 §5 의 URL 패턴 누락, AUTH-005 면 회전 경합이나 로그아웃 이후 요청이다.

## 14. 주의점 정리

- **`@AuthMemberId` 를 붙였으면 `WebConfig.addUrlPatterns` 도 고쳐야 한다.** 안 그러면 정상 토큰에도 항상 AUTH-003. 강제 장치가 없다.
- **URL 패턴은 HTTP 메서드를 모른다.** GET 만 열고 싶으면 패턴으로 걸고 `shouldNotFilter` 로 빼는 2단 구조를 써야 한다.
- **`@AuthMemberIdOrNull` 은 잘못된 토큰을 null 로 삼키지 않는다.** 이름에 속으면 안 된다.
- **필터의 예외는 `@RestControllerAdvice` 가 못 잡는다.** 필터는 MVC 바깥이다.
- **필터가 인터셉터보다 먼저다.** `X-API-Version` 이 없고 토큰도 없으면 400(COMMON) 이 아니라 **401 이 먼저 나간다** — 버전 해석은 `DispatcherServlet` 안(`WebConfig.kt:26-30`)이라 필터 뒤이기 때문이다.
- **MDC 는 반드시 정리돼야 한다.** 서블릿 스레드는 재사용되므로 안 지우면 다음 요청 로그에 남의 `memberId` 가 붙는다. JWT 필터는 자기가 넣은 값을 안 지우고 바깥 로깅 필터의 `MDC.clear()` 에 맡긴다(`JwtAuthenticationFilter.kt:37` 주석). **필터 순서가 바뀌면 이 계약이 깨진다.**
- **access 는 발급 후 취소 불가.** 로그아웃·탈퇴·정지 모두 최대 30분의 꼬리를 남긴다.
- **재사용 탐지 없음**(§9).
- **세 종류 토큰이 같은 시크릿을 쓴다.** `token_type` 클레임이 유일한 구분선이다. 새 토큰 종류를 만들면 반드시 `TokenType` 에 넣고 파싱 쪽에서 강제해야 한다.

| 인터셉터 | 스프링 MVC **안**에서 핸들러 앞뒤에 끼는 훅. 어느 핸들러인지 안다 | 라우트 단위 가드 |

| MDC | 로그 문맥(Mapped Diagnostic Context). 스레드에 붙은 키-값이 로그 줄마다 자동 출력 | 요청 단위 로그 태깅 (AsyncLocalStorage) |
| jti | JWT ID. 토큰 하나를 가리키는 고유 식별자 | 세션 레코드의 PK |
| 클레임(claim) | JWT payload 안의 키-값 (`sub`·`exp`·`role`·`token_type`) | JWT 를 디코드하면 나오는 객체의 필드 |
| 회전(rotation) | 재발급할 때 옛 refresh 를 폐기하고 새것을 주는 것 | — |
| 슬라이딩 만료 | 쓸 때마다 만료 시각이 밀리는 방식 | — |
| 무상태(stateless) | 서버가 세션 정보를 기억하지 않는 것 | — |
| 멱등(idempotent) | 같은 요청을 여러 번 보내도 결과가 같은 것 | 재시도해도 안전한 API |

## 17. 체크리스트

- [ ] 요청이 컨트롤러에 닿기까지 지나는 5칸(로깅 필터 → JWT 필터 → DispatcherServlet → 인터셉터 → 리졸버)을 순서대로 말할 수 있다
- [ ] `filterChain.doFilter` 를 안 부르면 무슨 일이 일어나는지 안다
- [ ] 필터가 401 봉투를 직접 만드는 이유를 한 문장으로 설명할 수 있다
- [ ] `WebConfig.kt:80-100` 을 직접 열어 어떤 경로가 보호되고 어떤 경로가 아닌지 확인했다
- [ ] `/api/auth/refresh` 가 필터 목록에 없어야 하는 이유를 설명할 수 있다
- [ ] `@AuthMemberId` 와 `@AuthMemberIdOrNull` 이 **서로 다른 곳에서** 값을 얻는다는 걸 안다
- [ ] `token_type` 클레임이 없으면 무슨 사고가 나는지 말할 수 있다
- [ ] refresh 만 Redis 에 두는 이유를 access 와 대비해 설명할 수 있다
- [ ] `consume` 이 `getAndDelete` 여야 하는 이유(동시 갱신)를 안다
- [ ] 재사용 탐지가 없다는 사실과 그 함의를 안다
- [ ] 로그아웃 후에도 access 가 최대 30분 사는 이유를 설명할 수 있다
- [ ] AUTH-003 ~ 006 네 코드에 FE 가 각각 어떻게 반응하는지 안다
- [ ] `AuthLifecycleScenarioTest.kt` 를 처음부터 끝까지 읽었다

> **[[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]] §9** 의 요청 흐름표에서 이 노트는 **2단계**다 — 스레드가 배정된 직후, 컨트롤러가 불리기 **전**. 순서가 이렇게 고정돼 있어서 컨트롤러 메서드는 "이미 신원이 확인된 상태" 를 전제로 쓸 수 있다.
> 그리고 이 노트의 `memberId` 가 어떻게 컨트롤러까지 따라오는지의 바탕은 [[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]] §8 이다 — 필터가 심어둔 값을 컨트롤러가 파라미터로 받아 쓸 수 있는 건 **요청 하나가 스레드 하나 위에서 끝까지 도는** 덕이다. 같은 이유로 §8 의 로그 `requestId`(MDC)도 `ThreadLocal` 이라 요청 200개가 섞여도 각 줄에 자기 요청 ID 가 붙는다. 뒤집으면 `@Async` 로 넘어간 코드의 로그에는 그 ID 가 **비어 있는 게 정상**이다.
