# 3. JVM 위의 Kotlin — 컴파일·널 안전·Gradle 3모듈

> 작성: 2026-08-27 (2026-09-03 전면 개정) · 맥락: 1번에서 "서버는 켜두는 프로그램"이라는 세계관을, 2번에서 "요청 하나에 스레드 하나"라는 실행 모델을 봤다. 남은 건 **그 프로그램이 어떤 언어로 쓰이고 어떻게 만들어지는가**다.
> 목표: kbap-server 를 클론했을 때 (1) `.kt` 파일이 실행되기까지 무슨 일이 벌어지는지, (2) 코드에 붙은 `?` 와 `!!` 가 무슨 뜻인지, (3) `./gradlew` 로 뭘 어떻게 돌리는지 말할 수 있게 된다.
> 기준: kbap-server 실측 2026-09-03 · Kotlin 2.3.21 / Spring Boot 4.1.0 / Java 21 toolchain / Spring AI 2.0.0 (`gradle/libs.versions.toml:1-8`) · Gradle Wrapper 9.5.1

---

## 0. 한 줄 요약

Kotlin 은 **자바와 똑같은 자리에서 도는 다른 문법**이다. `.kt` 를 컴파일하면 자바와 같은 `.class` 가 나와 **JVM 위에서 실행**되고, 널 검사는 **실행 파일까지 살아남으며**, 그 전부를 **Gradle 이 3개 모듈(`:common`·`:api`·`:batch`)로 조립**한다.

---

## 1. 왜 코틀린인데 JVM 얘기부터 하나

자바로 API 를 짜 본 적이 있을 것이다. 클래스를 하나 만들고, 위에 `@RestController` 를 붙이고, 메서드 하나가 JSON 을 받아 JSON 을 돌려주게 하고 — 그리고 실행 버튼을 눌렀을 것이다.

그때 **그 코드가 무엇에 의해 실행됐는지**는 아마 생각해 본 적이 없을 것이다. 그게 **JVM** 이다. 자바 코드는 컴퓨터가 직접 읽는 게 아니라, JVM 이라는 프로그램이 읽어서 대신 실행해준다.

그리고 kbap-server 는 자바가 아니라 **Kotlin** 으로 쓰여 있다. 여기서 자연스러운 의문 하나 — **"코틀린이라며? 근데 왜 자바 얘기, JVM 얘기가 나와?"**

답은 이거다. **Kotlin 은 자바를 대체하는 게 아니라, 자바가 서 있던 자리에 문법만 바꿔 서는 언어다.**

- 파일 확장자만 `.java` 대신 `.kt` 다.
- 컴파일하면 **자바와 똑같은 `.class` 파일**이 나오고, 그걸 실행하는 것도 **똑같은 JVM** 이다.
- 그래서 코틀린 코드가 자바로 만들어진 라이브러리를 **그냥 가져다 쓴다.** kbap 이 쓰는 Spring·Hibernate·jjwt 는 전부 자바로 쓰인 것들이다.

> [!tip] 읽는 법
> 2~5절이 **언어**(판이 뭔지 → 문법), 6~9절이 **빌드**(조립 도구)다. 처음 읽을 땐 2절과 3절만 붙잡아도 kbap 코드가 읽히기 시작한다.

---

## 2. JVM 이 뭔가

**JVM(Java Virtual Machine)** = 컴파일된 결과물을 읽어서 실행해주는 **프로그램**이다. "가상 머신"이라는 이름은 이게 마치 **가짜 CPU 하나**처럼 행동하기 때문이다. 실제 CPU 는 종류마다 알아듣는 명령이 다른데, JVM 은 그 사이에 **표준 규격 하나**를 끼워 넣는다.

```
Kotlin 소스(.kt)  ──[컴파일]──▶  바이트코드(.class)  ──[JVM]──▶  실제 CPU 에서 실행
```

- **바이트코드**란 그 표준 규격에 맞춰 나온 결과물이다. `.class` 파일에 들어 있고, 사람이 읽는 글자가 아니라 기계용 이진 파일이다.
- 자바로 짜든 코틀린으로 짜든 **나오는 `.class` 는 같은 규격**이다. 1절의 "코틀린이 자바 라이브러리를 그냥 쓴다"가 여기서 나온다.
- 배포할 때는 `.class` 들을 압축해 **jar** 파일 하나로 만든다. Spring Boot 는 라이브러리까지 전부 넣은 **bootJar**(뚱뚱한 jar)를 만든다 → [[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]] 의 실행 파일 두 개가 이것이다.

### 비유: 해외여행용 변환 어댑터

콘센트 모양은 나라마다 다르지만, 충전기를 나라 수만큼 사지는 않는다. **어댑터 하나**를 챙기고 충전기는 늘 거기에 꽂는다. JVM 이 그 어댑터다. 나라(CPU·운영체제)별 차이는 JVM 이 흡수하니, 내 맥에서 빌드한 jar 가 리눅스 서버에서 그대로 돈다.
**어디까지 같은가**: 중간에 규격 맞춰주는 물건을 하나 끼운다는 구조. **어디서부터 다른가**: 어댑터는 전기를 통과시키기만 하지만, JVM 은 실행 중에 **자주 도는 코드를 더 빠른 기계어로 바꿔치기까지** 한다. 그래서 자바·코틀린 서버는 켜두고 시간이 좀 지나야 제 속도가 나온다.

### Java 21 은 어디서 오나

"그럼 내 컴퓨터에 자바를 깔아야 하나?" 아니다. 이 레포는 **필요한 자바를 빌드 도구가 스스로 구해온다.** (**JDK** = 자바 컴파일러와 JVM 이 함께 들어 있는 설치 묶음.)

```kotlin
configure<JavaPluginExtension> {
    toolchain {
        languageVersion = JavaLanguageVersion.of(javaVersion)
    }
}
```
`buildSrc/src/main/kotlin/kbap.kotlin-common.gradle.kts:24-28` (`javaVersion` 은 버전 목록 파일의 `java = "21"` 을 읽은 값 — 6절)

- 이 선언의 뜻: "이 모듈은 **Java 21 로** 컴파일하고 테스트한다."
- **핵심**: 이 선언은 내 컴퓨터에 뭐가 깔려 있든 **무시하고 이긴다.** JDK 17 만 있어도 Gradle 이 21 을 따로 받아 `~/.gradle/jdks/` 에 깔고 그걸로 빌드한다(받아오는 일은 `settings.gradle.kts:8-10` 의 `foojay-resolver-convention` 플러그인이 한다). 그래서 팀원 전원이 같은 자바로 빌드한다.

> [!note] `./gradlew` 도 같은 사상
> 빌드 도구인 Gradle 자체도 설치하지 않는다. 레포 안의 `gradlew` 스크립트가 정해진 버전(현재 **9.5.1**)을 받아서 쓴다. 그래서 명령은 항상 `gradle` 이 아니라 **`./gradlew`** 다.

## 3. 코틀린이 자바와 다른 가장 큰 지점 — 널 안전

### 3-1. 자바에서 겪었을 그 예외

자바를 조금이라도 짜 봤다면 `java.lang.NullPointerException` 이라는 이름을 봤을 것이다.

자바에서 `String name` 이라고 선언하면, 거기에는 **글자가 들어올 수도 있고 아무것도 안 들어올 수도 있다.** 아무것도 없는 상태를 **null**(널)이라 한다. 컴파일러는 이걸 문제 삼지 않는다. 그러다 `name.length()` 를 호출하는 순간 — 없는 것에 말을 걸었으니 — 그 자리에서 프로그램이 터진다.

문제는 **터지는 자리와 원인이 멀다**는 것이다. 널은 요청이 들어온 지점에서 섞여 들어왔는데, 예외는 한참 뒤 엉뚱한 메서드에서 난다.

### 3-2. 코틀린의 해법 — 타입을 두 개로 쪼갠다

코틀린은 이 문제를 **타입 차원**에서 없앤다.

| 코틀린 표기 | 뜻 |
|---|---|
| `String` | 글자가 **반드시** 있다. 널이 들어올 수 없다 |
| `String?` | 글자가 있을 수도, **널일 수도** 있다 |

이 둘은 이름만 비슷한 **서로 다른 타입**이다. `String?` 을 `String` 자리에 그냥 넣으면 **컴파일이 실패한다.** 자바에서 실행 중에 터지던 것을, 코틀린은 **코드를 짜는 시점에** 막는다. 그래서 널을 다루는 문법이 따로 있다.

| 문법 | 읽는 법 |
|---|---|
| `a?.b` | `a` 가 널이면 `b` 를 부르지 않고 **전체가 널이 된다** (안전 호출) |
| `a ?: b` | `a` 가 널이면 **대신 `b` 를 쓴다**. **엘비스 연산자** — 눕혀 보면 엘비스 프레슬리 앞머리처럼 생겨서 붙은 이름이다 |
| `a!!` | "널 아니라고 내가 보증한다". 보증이 틀리면 **그 줄에서 즉시 예외** |

> [!note] 비유: 겉면에 표시된 택배 상자
> `String` 은 "내용물 있음" 도장이 찍힌 상자, `String?` 은 "비었을 수 있음" 이 찍힌 상자다. 후자를 받은 사람은 **열어보기 전에 확인부터** 해야 한다.
> **어디까지 같은가**: 열기 전에 확인을 강제한다는 점.
> **어디서부터 다른가**: 택배는 확인 안 하고 열어도 그만이지만, 코틀린은 확인을 건너뛰면 **애초에 컴파일이 안 된다.**

### 3-3. 실코드 — 요청 DTO 하나에 다 들어 있다

```kotlin
data class OnboardingRequest(
    val nickname: String? = null,
    val avoidanceSubstanceCodes: List<String> = emptyList(),
    val dietCategories: List<String> = emptyList(),
    val countryCode: String,
    val profileImageUrl: String? = null,
    val spicinessPreference: String,
) {
    ...
    private fun requireField(value: String?): String =
        value ?: throw BusinessException(ErrorCode.INVALID_REQUEST)
}
```
`api/src/main/kotlin/com/kbap/api/member/OnboardingRequest.kt:6-27`

- `nickname: String? = null` — **널이 와도 되는** 필드. 뒤의 `= null` 은 "안 보내면 이 값" 이라는 기본값이다.
- `countryCode: String` — **널이 오면 안 되는** 필드. 물음표가 없다는 것 자체가 계약이다.
- `requireField(value) = value ?: throw ...` — 널이면 **우리 서비스의 에러로 바꿔 던진다.** `String?` 이 들어와서 `String` 이 나가는, **널을 걸러내는 관문**이다. 이런 관문을 통과시켜야만 `String?` 을 `String` 자리에 넣을 수 있다.

또 하나, 널을 다루는 정석 패턴:

```kotlin
        val header = request.getHeader(AUTHORIZATION_HEADER) ?: return null
        if (!header.startsWith(BEARER_PREFIX)) return null
```
`api/src/main/kotlin/com/kbap/api/core/auth/AuthMemberIdOrNullArgumentResolver.kt:25-26` (이 함수의 반환 타입은 `Long?` — **"널이 나올 수 있음"이 함수 이름표에 적혀 있어** 쓰는 쪽이 널 처리를 강제당한다)

- `?: return null` — 널이면 여기서 끝낸다. 그러면 **그 아랫줄부터 `header` 는 널이 아님이 증명된 상태**가 되고 컴파일러가 그걸 기억해준다(**스마트 캐스트**). 그래서 아래에서는 물음표 없이 그냥 쓴다.

### 3-4. 탈출구 `!!`

```kotlin
        val result = scanFacade.scanMenuBoardImageV2(
            memberId,
            request.imagePath!!,
```
`api/src/main/kotlin/com/kbap/api/scan/ScanV2Controller.kt:36-38`

- `imagePath` 는 요청 객체에서 `String?` 인데, 그 앞에 이미 요청 검증이 끝나서 여기선 널일 수 없다 — 그걸 **개발자가 컴파일러에게 보증**하는 표시가 `!!` 다. 보증이 틀리면 그 줄에서 `NullPointerException` 이다.
- 즉 `!!` 는 **자바 시절로 잠깐 돌아가는 문**이라, 코드 리뷰에서 눈에 띄는 신호다. "여기 널이 아님을 정말 아는가?"를 묻는 자리.

### 3-5. 검사가 실행 파일에 진짜로 박힌다

여기가 자바와 갈리는 진짜 지점이다. 코틀린의 널 검사는 "컴파일 때만 잔소리하고 끝"이 아니다. **`.class` 안에 검사 코드가 실제로 들어간다.**

위 `OnboardingRequest` 의 `.class` 를 뜯어보면 생성자 맨 앞에 이런 호출이 박혀 있다.

```
   1: ldc  "avoidanceSubstanceCodes"
   3: invokestatic  Intrinsics.checkNotNullParameter:...
   7: ldc  "dietCategories"         → checkNotNullParameter
  14: ldc  "countryCode"            → checkNotNullParameter
  21: ldc  "spicinessPreference"    → checkNotNullParameter
```
(직접 확인: `javap -p -c api/build/classes/kotlin/main/com/kbap/api/member/OnboardingRequest.class`)

- 뜻만 읽으면 된다. `checkNotNullParameter` = **"이거 널이면 지금 터뜨려라"**. 그게 **정확히 4번**, 소스에서 **물음표가 없던 필드 4개**에만 있다.
- `nickname` 과 `profileImageUrl` 에는 검사가 **없다.** 이 둘이 `String?` 였다.

즉 **소스에 물음표를 붙였는지가 그대로 실행 중 검사 유무가 된다.**

> [!important] 이게 왜 중요한가
> 서버가 받는 JSON 은 **바깥에서 온다.** 자바라면 널이 조용히 흘러들어와 한참 뒤 엉뚱한 곳에서 터진다. 코틀린은 **들어오는 그 자리에서** 터진다. 예외 로그가 진짜 원인을 가리킨다는 뜻이다.

### 3-6. 자바 라이브러리와 만나는 지점

kbap 이 쓰는 Spring 은 자바로 쓰였다. 자바 코드에는 "널일 수 있음/없음" 표시가 없으니, 코틀린 입장에서는 **판단 불가**인 값들이 넘어온다. 이런 걸 **플랫폼 타입**이라 하고, 기본값은 "일단 봐준다" 다.

이 레포는 그 기본값을 조여둔다 — 빌드 설정에 `-Xjsr305=strict` 한 줄이 들어 있다(`buildSrc/src/main/kotlin/kbap.kotlin-common.gradle.kts:33`). 자바 쪽에 널 여부 표시가 달려 있으면 **참고사항이 아니라 진짜 규칙으로** 받아들이라는 뜻이고, Spring 은 그 표시를 성실히 달아둔 편이라 실질적으로 "Spring API 를 쓸 때도 널 안전이 켜진다"가 된다. 이 설정은 **세 모듈 전부에 일괄 적용**된다(8절).

## 4. kbap 코드에서 매일 마주치는 Kotlin 문법 6가지

자바를 조금 써봤다면 오른쪽 열이 다리가 된다.

| 문법 | 예 | 읽는 법 | 자바로 치면 |
|---|---|---|---|
| `val` / `var` | `val memberId: Long` | 값 재대입 불가 / 가능 | `final` 변수 / 그냥 변수 |
| 타입을 뒤에 쓴다 | `fun f(x: Long): String` | 이름 → 콜론 → 타입 순서 | `String f(long x)` 의 순서 뒤집기 |
| **표현식 함수** | `fun getRanking(id: Long): R = R.from(...)` | 중괄호·`return` 없이 `=` 한 줄로 | 한 줄짜리 메서드 몸통을 줄인 것 |
| **이름 붙인 인자 + 기본값** | `MemberProfileInput(memberId = id, nickname = null)` | 순서 대신 **이름으로** 넘긴다 | 자바엔 없다. 인자 많은 생성자의 순서 실수를 없애준다 |
| **`data class`** | `data class ParsedAccessToken(val memberId: Long, ...)` | 값을 담는 클래스 | getter·`equals`·`hashCode`·`toString` 을 **컴파일러가 대신 써준다** |
| **`companion object`** | `MemberRankingResult.from(...)` | 클래스에 딸린 공용 멤버 자리 | `static` 메서드 자리 |

`data class` 가 실제로 뭘 만들어주는지는 `.class` 로 확인된다 — `OnboardingRequest.class` 에는 소스에 없던 `copy(...)`·`toString()`·`hashCode()`·`equals(Object)` 가 들어 있다. **자바에서 손으로 쓰거나 IDE 로 생성하던 것들을 코틀린은 컴파일러가 넣어준다.**

> [!note] 확장 함수 — 개념만 알아두면 된다
> 코틀린에는 "남이 만든 클래스에 내 메서드를 덧붙이는" 확장 함수(`fun String.toSlug(): String`) 문법이 있다. 다만 **kbap-server 운영 코드에는 이런 정의가 없다** — 공통 로직은 `common.util` 아래 객체(`ImageUrls`·`KoreanMenuNameNormalizer`)에 모으는 쪽을 택했다. 남의 코드에서 보면 알아볼 정도로만 기억해두자.

## 5. 클래스가 실행 중에도 남아 있다

`.class` 라는 이름 그대로, 컴파일 결과에는 **클래스가 실체로 들어 있다.** 그래서 실행 중에 "이 클래스 구조가 어떻게 생겼지?"를 프로그램이 스스로 들여다볼 수 있다. 이걸 **리플렉션**이라 한다.

```kotlin
    override fun supportsParameter(parameter: MethodParameter): Boolean =
        parameter.hasParameterAnnotation(AuthMemberIdOrNull::class.java)
```
`api/src/main/kotlin/com/kbap/api/core/auth/AuthMemberIdOrNullArgumentResolver.kt:15-16`

- `AuthMemberIdOrNull::class.java` — 애너테이션 **클래스 자체를 값처럼** 넘기고 있다. Spring 은 이런 식으로 **실행 중에 클래스를 뒤져서** "이 파라미터에 이 애너테이션이 붙었나?"를 묻는다.

이게 왜 중요하냐면 — 자바로 API 를 짤 때 `@RestController` 만 붙였는데 알아서 돌아가던 그 마법이 **전부 이 리플렉션 위에 서 있기** 때문이다. Spring 이 실행 중에 애너테이션을 훑어서 객체를 만들고 연결한다. 그 과정 전체가 다음 노트다 → [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]

> [!warning] 다만 제네릭 인자는 지워진다
> `List<String>` 은 `.class` 에서 그냥 `List` 다. 꺾쇠 안의 `String` 은 컴파일 과정에서 버려진다. 이걸 **타입 소거**라 한다. "클래스는 남고, 그 클래스에 끼운 꺾쇠 안은 지워진다"로 기억하면 된다.

## 7. Gradle 과 3모듈

> 모듈이 **왜** 이렇게 나뉘었는지(도메인 경계)는 [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] 가 정본이다. 여기서는 **빌드 도구가 그걸 어떻게 표현하는가**만 본다.

**Gradle** = 이 프로젝트의 빌드 도구다. 소스를 컴파일하고, 라이브러리를 받아오고, 테스트를 돌리고, jar 를 만드는 일을 전부 맡는다.

### 7-1. 모듈 목차

```kotlin
include(
    ":common",
    ":api",
    ":batch",
)
```
`settings.gradle.kts:20-24`

- 앞의 콜론(`:`)은 모듈 경로 표기다. `:api` = 루트 바로 아래 `api/` 폴더.
- **딱 3개다.** 각 폴더에는 자기 `build.gradle.kts` 가 있어서 자기가 쓸 라이브러리를 적는다.

### 7-2. 의존은 어떻게 선언하나

```kotlin
plugins {
    id("kbap.spring-boot-application")
}

dependencies {
    "implementation"(project(":common"))
```
`api/build.gradle.kts:1-6` (`batch/build.gradle.kts:1-6` 도 **글자까지 같은 모양**이다)

- `project(":common")` — 외부 라이브러리가 아니라 **같은 프로젝트 안의 다른 모듈**에 의존한다는 뜻. 앞에 붙는 단어(`implementation` 등)가 **의존의 종류**를 정한다:

| 종류 | 뜻 |
|---|---|
| `implementation` | 나만 쓴다. 나를 쓰는 쪽에는 안 보인다(실행할 때는 따라온다) |
| `api` | 나를 쓰는 모듈에도 **공개**한다 |
| `runtimeOnly` | 컴파일엔 필요 없고 **실행할 때만** 필요(주로 DB 드라이버) |
| `testImplementation` | 테스트 코드에서만 |

공개 판단이 실제로 쓰인 자리 — `:common` 은 DB 라이브러리(JPA)를 `"api"(...)` 로 공개하고, 내부 사정인 `kotlin-reflect` 는 `"implementation"` 으로 감춘다(`buildSrc/src/main/kotlin/kbap.common-conventions.gradle.kts:28-29`). 공개한 이유는 `:common` 의 데이터 클래스들이 `:api` 모듈 코드에도 그대로 등장하기 때문이다.

### 7-3. 왜 `:api` 와 `:batch` 가 서로를 못 보나

`api/build.gradle.kts` 와 `batch/build.gradle.kts` 어디에도 상대 모듈을 적은 줄이 **없다.** 그래서 `:api` 코드에서 `import com.kbap.batch.…` 를 치면 **IDE 가 빨간 줄을 긋고 컴파일이 실패한다.** 금지 규칙이 따로 있어서가 아니라 **선언하지 않았다는 사실 자체가 벽**이다. 그래서 의존은 **한 방향으로만** 흐른다:

```
:common  ←──  :api    (웹 서버)
         ←──  :batch  (배치 앱)
```

> [!note] Gradle 이 못 막는 경계는 테스트가 막는다
> `:common` **안에서** 도메인끼리 지켜야 할 방향은 모듈이 3개뿐이라 Gradle 이 못 잡는다. 그건 테스트가 맡는다 → [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]

## 8. 공통 설정을 어디에 모으나 — buildSrc

모듈이 3개면 같은 설정(Java 21, 컴파일러 옵션, 테스트 라이브러리)을 세 번 복붙하게 된다. 이 레포는 그걸 `buildSrc/` 폴더로 걷어냈다.

`buildSrc/` 는 Gradle 이 **본 빌드 전에 먼저 컴파일해주는 특별한 폴더**다. 여기에 "우리 프로젝트 전용 설정 묶음"을 만들어두면, 각 모듈은 **한 줄로 자기 성격을 선언**할 수 있다. 7-2절 발췌의 `id("kbap.spring-boot-application")` 한 줄이 그것이다. 이 묶음을 **컨벤션 플러그인**이라 부른다. 회사 문서 서식과 같다 — 문서마다 머리말을 복붙하는 대신, 표준 서식 하나를 적용하는 것이다.

현재 4개다:

| 플러그인 id | 적용 대상 | 담는 것 |
|---|---|---|
| `kbap.kotlin-common` | (토대, 전부가 물려받음) | **Java 21**, 컴파일러 옵션, 공통 테스트 설정 |
| `kbap.spring-conventions` | (토대) | 위 + Spring 관련 기본기 |
| `kbap.spring-boot-application` | **`:api`·`:batch`** | 위 + 실행 가능한 jar 를 만드는 능력 |
| `kbap.common-conventions` | **`:common`** | kotlin-common + JPA 관련 설정(9절) |

이 묶음들은 서로 **겹쳐 쌓인다.** `kbap.spring-boot-application` 은 전문이 네 줄인데, `id("kbap.spring-conventions")` 와 `id("org.springframework.boot")` 두 줄이 전부다(`buildSrc/src/main/kotlin/kbap.spring-boot-application.gradle.kts:1-4`). 첫 줄이 `spring-conventions` 를 끌어오고, 그게 다시 `kotlin-common` 을 끌어온다 — 3층이 모듈 파일의 한 줄로 접힌다.

> [!tip] 모듈 파일에 왜 `"implementation"(...)` 처럼 따옴표가 붙어 있나
> 설정이 컨벤션 플러그인을 거쳐 들어오면 Gradle 이 따옴표 없는 단축 표기를 항상 만들어주지는 않는다. 그래서 이름을 **문자열로 일관되게** 적는다. 오타가 아니라 의도된 표기다.

> [!warning] buildSrc 의 대가
> `buildSrc/` 를 **한 글자만 고쳐도 전체 빌드를 다시 한다.** 빌드가 갑자기 느려졌는데 이유를 모르겠으면 여기를 건드렸는지 먼저 의심한다.

## 9. 컴파일러 플러그인 — 소스에 없는 게 결과물에 생긴다

코틀린에는 자바와 다른 기본값이 둘 있는데, 이게 Spring·JPA 와 정면충돌한다.

| 코틀린 기본값 | 왜 문제인가 |
|---|---|
| **클래스를 물려받을 수 없다** (자바로 치면 전부 `final`) | Spring 은 어떤 기능을 붙일 때 내 클래스를 **물려받은 대역 객체**를 만들어 대신 끼워 넣는다. 물려받기가 막혀 있으면 대역을 못 만든다 |
| **인자 없는 생성자가 없다** | DB 라이브러리는 DB 한 줄을 객체로 되살릴 때 **빈 객체부터 만들고** 값을 채운다. 인자 없는 생성자가 없으면 만들 수가 없다 |

> [!note] "대역 객체"의 최소 정의
> **프록시** = Spring 이 만드는 **대역 배우**. 원본 클래스를 물려받아 똑같이 생긴 객체를 만들고, 메서드가 불릴 때 앞뒤로 할 일(예: DB 작업 묶어서 처리하기)을 끼워 넣은 뒤 원본을 부른다. 우리 코드는 대역인 줄 모르고 부른다. 자세히는 → [[6. 설정과 프로필, 트랜잭션 경계]]

해결책이 **컴파일러 플러그인**이다. 컴파일 중간에 끼어들어 **결과물을 살짝 고쳐주는 장치**다.

| 플러그인 | 하는 일 | 이 레포에서 |
|---|---|---|
| `kotlin-spring` | Spring 애너테이션이 붙은 클래스의 **물려받기 금지를 풀어준다** | 컨벤션 플러그인 전부에 적용 |
| `kotlin-jpa` | DB 애너테이션이 붙은 클래스에 **인자 없는 생성자를 만들어 넣는다** | `kbap.common-conventions`(= `:common` 전용) |

```kotlin
allOpen {
    annotation("jakarta.persistence.Entity")
    annotation("jakarta.persistence.MappedSuperclass")
    annotation("jakarta.persistence.Embeddable")
}
```
`buildSrc/src/main/kotlin/kbap.common-conventions.gradle.kts:12-16` (두 플러그인은 같은 파일 `:6-7` 에서 켠다)

- 이 선언은 **DB 애너테이션이 붙은 클래스도 물려받기를 허용**하라는 뜻이다.

### 결과물로 확인하기

소스에는 없는데 `.class` 에는 있다(`javap -p <클래스파일>` 로 확인):

```
public class com.kbap.api.member.MemberService          ← final 이 아니다 (kotlin-spring)

public class com.kbap.common.domain.food.model.Food extends ...BaseEntity
  public com.kbap.common.domain.food.model.Food();      ← 소스에 없는 생성자 (kotlin-jpa)
```

- `Food.kt` 소스에는 인자를 잔뜩 받는 생성자밖에 없다(`common/src/main/kotlin/com/kbap/common/domain/food/model/Food.kt:19-24`). 인자 0개짜리 `Food()` 는 **컴파일러 플러그인이 만들어 넣은 것**이다.
- 즉 "왜 되는지 소스만 봐선 알 수 없는 일"이 벌어지고, 답이 빌드 설정에 있다. **코틀린+Spring 코드를 읽을 때 빌드 파일도 같이 봐야 하는 이유.**

> [!note] `@Entity` 가 무슨 뜻인지는 8번이 정본
> 여기서는 "컴파일러 플러그인이라는 장치가 있다"까지다. DB 와 클래스를 어떻게 이어 붙이는지는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]].

## 10. 치트시트 — 자주 쓸 명령어

전부 레포 루트에서 `./gradlew` 로 실행한다(Gradle 을 따로 설치하지 않는다).

```bash
# 빌드
./gradlew build                  # 전 모듈 컴파일 + 테스트 + jar 생성
./gradlew clean                  # 빌드 산출물 삭제
./gradlew projects               # 이 빌드에 어떤 모듈이 있나 (:common :api :batch)

./gradlew :batch:bootRun         # 배치 앱
SPRING_PROFILES_ACTIVE=local ./gradlew :api:bootRun    # 프로필 지정

# 테스트
./gradlew test                   # 전 모듈
./gradlew :api:test              # 모듈 하나만  ← 훨씬 빠르다
./gradlew :api:test --tests "com.kbap.api.member.MemberServiceReviewCountTest"   # 클래스 하나만
./gradlew :api:test -Dkotest.tags="arch"    # 경계 테스트만 (앞에 ! 를 붙이면 그것만 빼고)

# 커버리지 집계 / 의존성 파헤치기
./gradlew testCodeCoverageReport
./gradlew :api:dependencies --configuration compileClasspath
```

- `-Dkotest.tags` 가 먹는 이유: `kbap.kotlin-common` 이 이 값을 테스트 쪽으로 전달하도록 배선해뒀다(`buildSrc/src/main/kotlin/kbap.kotlin-common.gradle.kts:47-49`).
- 첫 `./gradlew build` 는 라이브러리와 JDK 를 받느라 오래 걸린다. 두 번째부터 빨라진다(`~/.gradle/` 에 캐시된다).

## 11. 주의점 · 함정

1. **`gradle` 이 아니라 `./gradlew`.** 로컬에 깐 Gradle 을 쓰면 버전이 달라 결과가 달라진다.
2. **`!!` 를 보면 멈춰서 읽는다.** 널 검사를 건너뛰겠다는 선언이고, 틀리면 실행 중에 터진다.
3. **빌드가 갑자기 느려졌다면 `buildSrc/` 를 건드렸는지 의심한다** (8절).
4. **`import com.kbap.batch.…` 가 `:api` 에서 안 잡히는 건 버그가 아니다** (7-3절). 반대도 마찬가지.
5. **인터넷의 Spring Boot 2.x 예제가 안 맞을 수 있다.** 이 레포는 **Boot 4.1** 이다.
6. **레포 안 문서 일부가 낡았다.** 입문서 `docs/guides/gradle-made-easy.md` 의 Gradle 문법 설명(§0~§5)은 지금도 정확하지만 **모듈 구성 서술은 옛 구조**(11개 모듈, `:core` 등)를 가리키고, `gradle/libs.versions.toml` 의 주석도 사라진 모듈 이름을 언급한다. **모듈 구성은 `settings.gradle.kts` 가 정본**이고, 버전 숫자 자체는 유효하다.

## 12. 용어집

| 용어 | 뜻 |
|---|---|
| **JVM** | 컴파일 결과물을 읽어 실행해주는 프로그램. 자바·코틀린 둘 다 이 위에서 돈다 |
| **바이트코드 / `.class`** | 컴파일 산출물. 자바로 짜든 코틀린으로 짜든 같은 규격이다 |
| **JDK** | 자바 컴파일러 + JVM 설치 묶음. 이 레포는 **Java 21** |
| **jar / bootJar** | `.class` 들을 묶은 파일. bootJar 는 라이브러리까지 넣어 바로 실행되는 것 |
| **toolchain** | "이 빌드는 JDK 21 로 한다"는 Gradle 선언. 내 컴퓨터 설정과 무관하게 이긴다 |
| **null(널)** | 값이 아무것도 없는 상태 |
| **`?:` / `!!`** | 널이면 오른쪽 값을 쓴다 / "널 아님" 보증(틀리면 즉시 예외) |
| **스마트 캐스트** | 널 검사를 통과하면 그 아래부터 컴파일러가 널 아님을 기억해주는 것 |
| **플랫폼 타입** | 자바 코드에서 넘어온, 널 여부를 알 수 없는 값 |
| **리플렉션** | 실행 중에 클래스 구조를 들여다보는 기능. Spring 의 마법이 여기서 나온다 |
| **타입 소거** | `List<String>` 의 꺾쇠 안(`String`)이 컴파일 과정에서 지워지는 것 |
| **버전 카탈로그 / BOM** | 버전의 단일 출처 파일 / 서로 호환되는 버전 묶음표(Spring Boot 제공) |
| **컨벤션 플러그인** | `buildSrc/` 에 둔 우리 프로젝트 전용 설정 묶음 |
| **컴파일러 플러그인** | 컴파일 중간에 끼어들어 결과물을 고치는 장치. `kotlin-spring`·`kotlin-jpa` |
| **프록시** | Spring 이 만드는 대역 객체. 원본을 물려받아 앞뒤로 할 일을 끼워 넣는다 |

## 13. 체크리스트

- [ ] "코틀린은 자바와 같은 자리에서 도는 다른 문법"이라는 말을 설명할 수 있다
- [ ] `.kt` → `.class` → JVM 실행 경로를 그림으로 그릴 수 있다
- [ ] `String` 과 `String?` 이 **다른 타입**이라는 말의 뜻을 말할 수 있다
- [ ] 자바의 `NullPointerException` 이 코틀린에서 왜 줄어드는지 설명할 수 있다
- [ ] `?.` · `?:` · `!!` 를 코드에서 보고 즉시 읽을 수 있다
- [ ] `gradle/libs.versions.toml` 을 열어 Kotlin·Spring Boot 버전을 말할 수 있다
- [ ] `settings.gradle.kts` 를 열어 모듈이 3개임을 확인했다
- [ ] `:api` 가 `:batch` 를 import 할 수 없는 이유를 설명할 수 있다
- [ ] `./gradlew :api:test` 로 한 모듈만 테스트를 돌려봤다
- [ ] `kotlin-spring`·`kotlin-jpa` 가 각각 무슨 문제를 푸는지 말할 수 있다
