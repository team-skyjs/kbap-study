# 13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들

> 작성: 2026-08-26 · 맥락: [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]에서 봤듯 kbap-server 의 Gradle 모듈은 **8개에서 3개로 줄었다**. 모듈이 많던 시절에는 "scan 이 food 를 아는가"를 컴파일러가 막아 줬다 — 의존 선언이 없으면 컴파일이 안 됐으니까. 모듈이 3개가 된 지금 그 벽은 사라졌다. `common.domain.scan` 과 `common.domain.review` 는 **같은 모듈, 같은 컴파일 단위** 안에 있어서 서로 import 해도 컴파일이 멀쩡히 통과한다.
> 그래서 경계를 지키는 수단이 **"모듈로 물리적으로 갈라놓기"에서 "테스트로 검사하기"로 바뀌었다.** 지금 이 레포에서 아키텍처를 지키는 자동 장치는 파일 하나뿐이다 — `ModuleBoundaryTest.kt`.
> 목표: 그 파일이 무엇을 금지하고 왜 금지하는지 전부 읽을 수 있게 되고, PR 에서 그 테스트가 빨갛게 떴을 때 "규칙이 틀렸나, 내 코드가 틀렸나"를 판단할 수 있게 되기.

---

## 0. 한 줄 요약

**ArchUnit** 은 "이 패키지는 저 패키지를 import 하면 안 된다" 같은 **아키텍처 규칙을 평범한 테스트 코드로 표현**해서, 어기면 CI 가 빨개지게 만드는 라이브러리다. kbap-server 는 그 규칙 **13종**을 `ModuleBoundaryTest.kt` 한 파일에 모아 두었고, Kotest 태그 `arch` 로 따로 돌릴 수 있다.

---

## 1. 개념표 — 이 노트에 나오는 용어

| 용어 | 뜻 | FE에서 가장 가까운 것 |
|---|---|---|
| ArchUnit | 아키텍처 규칙을 테스트로 표현하는 Java/Kotlin 라이브러리 | ESLint 커스텀 룰 · `import/no-restricted-paths` |
| 아키텍처 테스트 | 기능이 아니라 **코드의 배치·의존 방향**을 검사하는 테스트 | 린트 규칙 위반 검사 |
| 바이트코드 | `.kt` 를 컴파일한 결과물(`.class`). ArchUnit 이 읽는 대상 | 번들러가 만든 출력물 (다만 ESLint 는 이걸 안 읽는다) |
| `JavaClasses` | ArchUnit 이 읽어들인 클래스 집합. 규칙 검사의 입력 | ESLint 가 훑는 파일 목록 |
| 규칙(ArchRule) | `noClasses().that(…).should(…)` 형태의 문장 하나 | 룰 하나 (`no-restricted-paths` 한 zone) |
| 위반(Violation) | 규칙에 걸린 개별 지점(클래스·메서드·줄 번호) | 린트 에러 한 줄 |
| Kotest 태그 | 테스트에 붙이는 라벨. 라벨로 골라 실행/제외 | Jest `testPathIgnorePatterns` · `--testNamePattern` |
| 컨텍스트(바운디드 컨텍스트) | 업무 영역 하나. kbap 에선 `common.domain.<이름>` 패키지 하나 | 모노레포의 도메인 패키지 하나 |

## 2. ArchUnit 이 뭔가 — ESLint 커스텀 룰의 백엔드 판

FE 에서 "`client/` 코드가 `server/` 를 import 하면 안 된다" 같은 규칙을 강제해 본 적이 있다면, 십중팔구 ESLint 로 했을 것이다:

```json
// 예시 (kbap 코드 아님) — eslint-plugin-import
{
  "import/no-restricted-paths": ["error", {
    "zones": [{ "target": "./client", "from": "./server" }]
  }]
}
```

ArchUnit 이 하는 일이 정확히 이것이다. 다만 **표현 수단이 설정 파일이 아니라 테스트 코드**다:

```kotlin
noClasses().that().resideInAPackage("com.kbap.common.core..")
    .should().dependOnClassesThat().resideInAPackage("org.springframework..")
    .check(imported)
```

읽는 법: "`com.kbap.common.core` 아래에 사는 클래스 중 **어느 것도**(`noClasses`) `org.springframework` 아래 클래스에 의존해서는 안 된다." 영어 문장을 그대로 코드로 옮긴 꼴이라, 한 번 눈에 익으면 규칙 파일이 곧 아키텍처 문서가 된다.

> [!warning] 비유의 경계 — 여기서부터 다르다
> ESLint 는 **소스 파일의 `import` 구문을 텍스트/AST 로** 본다. ArchUnit 은 **컴파일된 바이트코드(`.class`)** 를 읽는다. 실질 차이가 셋 있다.
>
> 1. **ArchUnit 이 더 많이 본다.** import 문에 안 나타나는 의존까지 잡는다 — 같은 패키지 안의 참조, 메서드 반환 타입, 필드 타입, 애너테이션, 심지어 호출한 메서드 하나까지. "import 안 썼으니 안 걸리겠지"가 통하지 않는다.
> 2. **ArchUnit 은 컴파일이 끝나야 돈다.** ESLint 는 저장하는 순간 에디터가 빨간 줄을 그어 주지만, ArchUnit 위반은 **테스트를 돌려야** 안다. 그래서 피드백이 느리고, 이 노트 §6 의 "실패 메시지 읽는 법"이 필요해진다.
> 3. **ArchUnit 은 클래스패스에 있는 것만 본다.** 어떤 모듈의 테스트로 돌리느냐가 검사 범위를 정한다(§5-3 에서 이게 실제로 물린다).

kbap 의 의존 선언은 `api/build.gradle.kts:42` 한 줄이 전부다.

```kotlin
"testImplementation"(libs.archunit)
```

`testImplementation` — **테스트에서만** 쓴다. 프로덕션 아티팩트(`bootJar`)에는 ArchUnit 이 들어가지 않는다. 버전은 `gradle/libs.versions.toml:12` 의 `archunit = "1.3.0"` 이다.

## 3. 검사 대상을 읽어들이는 부분

`ModuleBoundaryTest.kt:19-31` — 파일의 도입부다.

```kotlin
@Tags("arch")
class ModuleBoundaryTest : BehaviorSpec({

    val imported: JavaClasses =
        ClassFileImporter()
            .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
            .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TEST_FIXTURES)
            .importPackages("com.kbap")

    val core = "com.kbap.common.core.."
    val sharedDomain = "com.kbap.common.domain.."
    val spring = "org.springframework.."
    val jpa = "jakarta.persistence.."
```

줄 단위 풀이:

- `@Tags("arch")` — 이 테스트 클래스 전체에 `arch` 라벨을 붙인다. §5-2 에서 이걸로 골라 돌린다.
- `BehaviorSpec` — Kotest 의 `given/when/then` 스타일. 레포 전체가 이 스타일로 통일돼 있다(문법 자체는 [[14. SDD와 TDD — 스펙과 테스트로 개발하기]] 소관).
- `ClassFileImporter()` — 바이트코드를 읽어들이는 놈. 이게 ESLint 와 갈라지는 지점이다.
- `DO_NOT_INCLUDE_TESTS` / `DO_NOT_INCLUDE_TEST_FIXTURES` — **테스트 코드와 테스트 픽스처는 검사 대상에서 뺀다.** 테스트는 원래 온갖 계층을 넘나들며 조립하니까, 프로덕션 코드에 거는 규칙을 그대로 들이대면 전부 걸린다.
- `importPackages("com.kbap")` — `com.kbap` 아래 전부를 읽는다. 단 **클래스패스에 실제로 올라와 있는 것만**이다(§5-3).
- 아래 네 줄은 그냥 문자열 상수다. `..` 는 ArchUnit 문법으로 "이 패키지와 그 하위 전부"를 뜻한다(`com.kbap.common.core..` = `common.core` 와 `common.core.error` 등 전부).

## 4. 규칙 전수 해설

파일에는 `given` 블록이 9개, 실제 검사(`then` 블록)가 **26개** 있다. 26개인 이유는 도메인 방향 규칙 하나가 컨텍스트 개수만큼 자동 생성되기 때문이고, **규칙의 종류로 세면 13종**이다. 하나씩 "무엇을 금지하나 / 왜 / 어기면 어떤 코드가 걸리나" 3단으로 본다.

### 4-1. 구 패키지에 클래스가 남아 있으면 안 된다 (`:33-53`)

**무엇을 금지하나** — `com.kbap.domain..` 과 `com.kbap.application..` 패키지에 클래스가 **존재하는 것 자체**를 금지한다. 의존이 아니라 존재다.

**왜** — ADR-0017 이 API 모듈을 `com.kbap.api.<기능>` 기능 패키지로 평탄화하면서 옛 좌표를 버렸다. 옛 구조가 몸에 밴 사람(또는 옛 코드를 복사한 사람)이 `com.kbap.domain.scan` 을 되살리면, 같은 컨텍스트가 두 좌표에 흩어져 읽는 사람이 매번 "어느 쪽이 진짜냐"를 물어야 한다.

**어기면 어떤 코드가 걸리나** — `api/src/main/kotlin/com/kbap/domain/scan/ScanPolicy.kt` 같은 파일을 새로 만드는 순간.

```kotlin
val notExist =
    object : ArchCondition<JavaClass>("구 패키지에 존재하지 않는다") {
        override fun check(item: JavaClass, events: ConditionEvents) {
            val sourceFile = "${item.packageName}/${item.sourceCodeLocation.sourceFileName}"
            if (legacySourceFiles.add(sourceFile)) {
                events.add(SimpleConditionEvent.violated(item, "$sourceFile 이 구 패키지에 존재한다"))
            }
        }
    }

classes().that().resideInAnyPackage("com.kbap.domain..", "com.kbap.application..")
    .should(notExist)
    .allowEmptyShould(true)
    .check(imported)
```

- ArchUnit 기본 DSL 에는 "존재하면 안 된다"가 없어서 `ArchCondition` 을 직접 만들었다 — **무조건 위반으로 기록하는 조건**이다. 그 패키지에 클래스가 잡히기만 하면 실패한다.
- `legacySourceFiles.add(...)` — 같은 소스 파일에서 여러 클래스가 나와도(Kotlin 은 파일 하나에 클래스 여러 개 가능) 위반 메시지를 **파일당 한 줄**로 줄이는 장치다.
- `allowEmptyShould(true)` — 이게 중요하다. ArchUnit 은 기본적으로 **`that()` 이 하나도 안 걸리면 규칙을 실패 처리**한다("패키지 이름 오타로 규칙이 조용히 무력화되는 것"을 막으려는 안전장치다). 그런데 이 규칙은 **아무것도 안 걸리는 게 성공**이므로 그 안전장치를 꺼야 한다. 파일 전체에서 `allowEmptyShould(true)` 가 자주 보이는 이유가 이것이다.

### 4-2. 커널(`common.core`)은 스프링을 모른다 (`:55-71`)

**무엇을 금지하나** — `common.core` 아래 클래스가 스프링·`common.domain`·`common.port`·`common.infra`·`api`·`batch` 에 의존하는 것.

**왜** — `common.core` 는 [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]에서 말한 **커널**이다. `ErrorCode`·`BusinessException` 같이 "누구에게도 속하지 않는 공통재"만 산다. 여기가 스프링을 알기 시작하면 가장 밑바닥 조각이 프레임워크에 묶여서, 순수 단위 테스트도 스프링 컨텍스트를 띄워야 하고 나중에 프레임워크를 갈아탈 여지가 사라진다. 의존 방향은 **위에서 아래로만** — 커널은 자기 위에 뭐가 쌓였는지 몰라야 한다.

**어기면 어떤 코드가 걸리나** — `ErrorCode` 에 `@Component` 를 붙이거나, `BusinessException` 이 `ResponseStatusException` 을 상속하거나, 커널 유틸이 `common.domain.member.model.Member` 를 파라미터로 받는 순간.

```kotlin
noClasses().that().resideInAPackage(core)
    .should().dependOnClassesThat().resideInAnyPackage(
        spring,
        sharedDomain,
        "com.kbap.common.port..",
        "com.kbap.common.infra..",
        "com.kbap.api..",
        "com.kbap.batch..",
    )
    .allowEmptyShould(true)
    .check(imported)
```

- `dependOnClassesThat()` 은 import 만 보는 게 아니다 — 필드 타입·파라미터·반환 타입·상속·애너테이션·호출한 메서드 전부가 "의존"이다.

### 4-3. 도메인은 포트·인프라·부트앱을 모른다 (`:73-86`)

**무엇을 금지하나** — `common.domain` 아래 클래스가 `common.port`·`common.infra`·`api`·`batch` 에 의존하는 것.

**왜** — [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]의 방향을 코드로 못 박은 규칙이다. 포트는 **바깥 시스템을 부르기 위한 계약**이고, 도메인은 그 계약이 있는지도 몰라야 한다. `then` 설명에 그 방향이 그대로 적혀 있다 — "도메인은 계약(port)과 그 구현을 알지 못한다 — **포트가 도메인 타입을 반환하는 방향만 허용**". 즉 `MenuBoardVisionExtractor`(포트)가 도메인 타입을 돌려주는 건 되고, 도메인 모델이 `MenuBoardVisionExtractor` 를 필드로 들고 있는 건 안 된다.

**어기면 어떤 코드가 걸리나** — `Food` 엔티티에 `fun refreshContent(client: TextEmbeddingClient)` 같은 메서드를 다는 순간. "편하잖아"로 시작해서 도메인 모델이 네트워크를 부르게 되는 전형적인 경로다.

### 4-4. 도메인 모델은 ORM 을 모른다 (`:88-102`)

**무엇을 금지하나** — `common.domain` 안의 클래스가 `jakarta.persistence` 에 의존하는 것. 단 **예외가 많다.**

```kotlin
noClasses().that().resideInAPackage(sharedDomain)
    .and().areNotAnnotatedWith("jakarta.persistence.Entity")
    .and().areNotAnnotatedWith("jakarta.persistence.MappedSuperclass")
    .and().areNotAnnotatedWith("jakarta.persistence.Embeddable")
    .and().areNotAnnotatedWith("jakarta.persistence.Converter")
    .and().areNotAnnotatedWith("org.springframework.stereotype.Service")
    .and().areNotAssignableTo("org.springframework.data.repository.Repository")
    .and().haveSimpleNameNotEndingWith("RepositoryCustomImpl")
    .should().dependOnClassesThat().resideInAPackage(jpa)
    .allowEmptyShould(true)
    .check(imported)
```

**왜** — kbap 은 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]에서 봤듯 **엔티티가 곧 도메인 모델**이다(ADR-0014). 그러니 "도메인은 JPA 를 모른다"를 통째로 걸 수는 없다 — 엔티티는 당연히 알아야 한다. 그래서 규칙이 이렇게 뒤집혀 있다: **엔티티·`@Embeddable`·컨버터·리포지토리·리포지토리 커스텀 구현·도메인 서비스를 제외한 나머지**, 즉 **정책 클래스·값 객체·enum 은 JPA 를 몰라야 한다**.

**어기면 어떤 코드가 걸리나** — `Ranking`(점수 계산 값 객체)이나 `RankingTier`(enum) 에 `@Column` 을 달거나, 순수 정책 클래스가 `EntityManager` 를 받는 순간. `.and()` 사슬 7줄은 **"예외 목록"이지 규칙의 본체가 아니다** — 예외에 해당하지 않는 클래스가 JPA 를 만지면 걸린다.

### 4-5. 발견된 컨텍스트 집합 == 허용 맵의 키 (`:125-138`, 허용 맵 정의는 `:108-123`)

이게 이 파일에서 가장 영리한 규칙이고, 처음 보면 "이게 왜 테스트지?" 싶은 것이기도 하다.

```kotlin
val allowedDomainDeps = mapOf(
    "admin" to emptySet(),
    "appversion" to emptySet(),
    "block" to emptySet(),
    "scan" to setOf("food", "member", "image", "ingredient"),
    "food" to emptySet(),
    "bookmark" to setOf("food", "member", "ingredient"),
    "member" to setOf("ingredient"),
    "image" to emptySet(),
    "metering" to emptySet(),
    "order" to emptySet(),
    "ingredient" to emptySet(),
    "review" to emptySet(),
    "report" to emptySet(),
    "community" to emptySet(),
)
```

이 맵이 **kbap 도메인 의존 방향의 단일 출처**다. 읽는 법: `scan` 은 `food`·`member`·`image`·`ingredient` 를 알아도 된다. `food` 는 **아무것도 몰라야 한다**(빈 집합). 실제로 14개 컨텍스트 중 **10개가 빈 집합** — 대부분의 도메인이 서로를 전혀 모른다는 뜻이고, 이게 kbap 의 도메인 그래프가 얕은 이유다.

그리고 그 바로 아래:

```kotlin
val foundContexts = imported
    .filter { it.packageName.startsWith("com.kbap.common.domain.") }
    .map {
        it.packageName
            .removePrefix("com.kbap.common.domain.")
            .substringBefore(".")
    }
    .toSet()

foundContexts shouldBe allowedDomainDeps.keys
```

**무엇을 금지하나** — 맵에 없는 컨텍스트가 코드에 생기는 것(그리고 코드에서 사라진 컨텍스트가 맵에 남는 것).

**왜** — 이게 없으면 규칙에 **구멍**이 생긴다. 새 컨텍스트 `payment` 를 만들면, 아래 §4-6 의 방향 검사는 맵을 순회하므로 `payment` 를 아예 검사하지 않는다. 즉 **디렉터리를 하나 만드는 것만으로 방향 규칙을 통째로 우회**할 수 있다. 이 한 줄이 그 구멍을 막는다 — "맵에 없는 컨텍스트는 방향 검사를 우회할 수 없다"가 `then` 설명 그대로다.

**어기면 어떤 코드가 걸리나** — `common/domain/payment/` 디렉터리를 만들고 클래스를 하나 넣는 순간. 실패 메시지는 `expected: [admin, appversion, ...] but was: [admin, appversion, ..., payment]` 형태로 뜬다. 고치는 법은 **맵에 `payment` 줄을 추가**하는 것 — 그리고 그 순간 리뷰어가 "payment 는 뭘 알아도 되는가"를 의식적으로 결정하게 된다. 규칙이 잔소리가 아니라 **설계 결정을 강제로 표면화하는 장치**로 쓰이고 있다.

### 4-6. 컨텍스트 간 허용 방향 (`:140-152`) — 여기서 14개가 생성된다

```kotlin
allowedDomainDeps.forEach { (context, allowed) ->
    val forbidden = (allowedDomainDeps.keys - allowed - context).sorted()
    `when`("$context 컨텍스트가 허용 목록 $allowed 밖 도메인에 의존하는지 검사하면") {
        then("$forbidden 을 알지 못한다") {
            noClasses().that().resideInAPackage(packageOf(context))
                .should().dependOnClassesThat().resideInAnyPackage(
                    *forbidden.map { packageOf(it) }.toTypedArray(),
                )
                .allowEmptyShould(true)
                .check(imported)
        }
    }
}
```

- `forbidden = 전체 키 - 허용 - 자기 자신` — **화이트리스트를 블랙리스트로 뒤집는다.** 허용 목록에 안 적힌 건 전부 금지라는 뜻이고, 새 컨텍스트가 추가되면 기존 컨텍스트들의 금지 목록에 **자동으로 들어간다.** 규칙을 손보지 않아도 조여진다.
- `forEach` 안에서 `when`/`then` 을 만들기 때문에 컨텍스트 14개 → **검사 14개**가 런타임에 생성된다. 테스트 리포트에 `food 컨텍스트가 허용 목록 [] 밖 도메인에 의존하는지 검사하면` 같은 항목이 14줄 뜨는 게 이 때문이다.

**어기면 어떤 코드가 걸리나** — `Review` 엔티티가 `Member` 를 타입으로 참조하는 순간(`review` 의 허용 목록은 빈 집합이다). 실제로 리뷰가 회원을 가리킬 때 `memberId: Long` 을 쓰는 이유가 여기에도 있다 — [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]의 연관관계 금지와 이 방향 규칙이 같은 방향으로 민다.

**맵은 "현황"이 아니라 "상한"이다** — `common/domain/*` 전체를 훑어 보면 실제로 존재하는 컨텍스트 간 참조는 **`member → ingredient` 단 하나**다(`DietCategory`·`IngredientCode`). `scan → food·member·image·ingredient`, `bookmark → food·member·ingredient` 로 넓게 열어 둔 방향은 **지금 하나도 쓰이지 않는다.** 맵을 읽을 때 "이 도메인들이 서로 얽혀 있구나"로 오해하기 쉬운데, 실제 도메인 그래프는 그보다 훨씬 납작하다 — 자세한 컨텍스트 지도는 [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]에 있다.

> [!tip] 이 규칙이 실제로 잡은 것
> ADR-0016(`docs/adr/0016-module-diet-three-app-modules.md`)이 기록해 두었다 — 모듈이 많던 시절에도 **`scan`·`bookmark` 가 의존 선언 없이 `avoidance` 를 참조**하고 있었고, **Gradle 은 그걸 잡지 못했다**(전이 클래스패스로 딸려 들어와서 컴파일이 통과했다). ArchUnit 을 도입한 시점에 발견됐다. "모듈이 컴파일러로 막아 준다"가 생각만큼 촘촘하지 않았다는 실증이다.

### 4-7. JPA 연관관계 전면 금지 (`:155-167`)

```kotlin
noFields().that().areDeclaredInClassesThat().resideInAPackage("com.kbap..")
    .should().beAnnotatedWith("jakarta.persistence.OneToMany")
    .orShould().beAnnotatedWith("jakarta.persistence.ManyToOne")
    .orShould().beAnnotatedWith("jakarta.persistence.OneToOne")
    .orShould().beAnnotatedWith("jakarta.persistence.ManyToMany")
    .allowEmptyShould(true)
    .check(imported)
```

**무엇을 금지하나** — `com.kbap` 전체에서 `@OneToMany`·`@ManyToOne`·`@OneToOne`·`@ManyToMany` 를 **필드에 다는 것**.

**왜** — [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]가 통째로 이 규칙의 결과를 다룬다. 요약하면: 연관관계를 매핑하면 N+1 이 **자동으로 생길 통로**가 열리고, 그 통로는 코드를 읽어서는 안 보인다(getter 하나가 쿼리 하나다). kbap 은 통로 자체를 막고 참조를 `Long` id 컬럼으로만 둔다.

**어기면 어떤 코드가 걸리나** — `Order` 엔티티에 `@OneToMany val items: List<OrderItem>` 을 다는 순간. 이게 JPA 튜토리얼의 기본형이라 **가장 자연스럽게 어기게 되는 규칙**이고, 그래서 파일 전체에서 유일하게 `noFields()`(클래스가 아니라 **필드**를 검사 대상으로 삼는 진입점)를 쓴다.

**주의** — `noFields()` 는 필드의 애너테이션만 본다. `@OneToMany` 없이 `List<OrderItem>` 을 그냥 필드로 들고 있으면 이 규칙은 못 잡는다(그건 §4-6 의 컨텍스트 방향 규칙이 잡거나, 잡히지 않는다). 규칙은 **JPA 매핑**을 막는 것이지 객체 참조 일반을 막는 게 아니다.

### 4-8. 모든 `@Entity` 는 도메인 패키지에 산다 (`:169-176`)

```kotlin
classes().that().areAnnotatedWith("jakarta.persistence.Entity")
    .should().resideInAPackage(sharedDomain)
    .check(imported)
```

**무엇을 금지하나** — `common.domain` 밖에 `@Entity` 클래스가 존재하는 것.

**왜** — ADR-0016 의 배치 기준 1번이다. **"영속 계층은 종류로 고정해 예외 없이 `:common`."** 스키마는 api 와 batch 가 공유하는 자산이라, 위치를 "지금 누가 읽는가"로 정하면 배치가 테이블 하나를 새로 읽기 시작할 때마다 엔티티가 모듈을 옮겨 다닌다.

**어기면 어떤 코드가 걸리나** — `api/src/main/kotlin/com/kbap/api/order/OrderDraft.kt` 에 `@Entity` 를 붙이는 순간.

**여기만 `allowEmptyShould(true)` 가 없다** — 그리고 그게 의도적이다. `then` 설명이 밝혀 준다: "**하나도 안 잡히면 스캔 자체가 깨진 것**". 엔티티가 0개일 리 없는 레포이므로, 여기서는 ArchUnit 의 기본 안전장치(빈 집합이면 실패)를 **켜 둔 채로 두어 임포터 고장을 감지**한다. §4-1 과 정반대의 이유로 정반대 선택을 한 것이고, 이 대비가 `allowEmptyShould` 를 이해하는 가장 좋은 예시다.

### 4-9. 모든 Spring Data 리포지토리도 도메인 패키지에 산다 (`:178-185`)

```kotlin
classes().that().areAssignableTo("org.springframework.data.repository.Repository")
    .and().resideInAPackage("com.kbap..")
    .should().resideInAPackage(sharedDomain)
    .check(imported)
```

**무엇을 금지하나** — `common.domain` 밖에 Spring Data 리포지토리 인터페이스가 존재하는 것.

**왜** — §4-8 과 같은 이유다. `then` 설명이 "영속은 컨텍스트 불문 `:common` 소속"이라고 못 박는다.

**어기면 어떤 코드가 걸리나** — `api/order/OrderQueryRepository.kt` 를 `JpaRepository` 상속으로 만드는 순간.

- `areAssignableTo("...Repository")` — 이름이 아니라 **상속 관계**로 판정한다. 인터페이스 이름을 `~Store` 로 지어도 `JpaRepository` 를 상속하면 걸린다. 바이트코드를 읽기 때문에 가능한 판정이다.
- `.and().resideInAPackage("com.kbap..")` 이 붙은 이유 — 이게 없으면 스프링 라이브러리 자신의 리포지토리 인터페이스들이 검사 대상에 들어와 전부 위반이 된다.
- 여기도 `allowEmptyShould` 가 없다(§4-8 과 같은 이유).

### 4-10. `common.util` 은 순수 헬퍼다 (`:188-205`)

**무엇을 금지하나** — `common.util` 아래 클래스가 스프링·JPA·도메인·포트·인프라·api·batch 에 의존하는 것. **커널보다도 더 조인다**(커널 금지 목록에 `jakarta.persistence` 가 추가된 형태).

**왜** — `common/util` 에는 지금 `CursorParser`·`ImageUrls`·`KoreanMenuNameNormalizer`·`SearchKeywordParser` 네 개가 있다. 전부 "문자열 넣으면 문자열 나오는" 상태 없는 함수여야 하는 것들이다. 여기가 도메인 타입을 알기 시작하면 유틸이 아니라 도메인 서비스가 되고, 도메인 서비스는 `api.<기능>` 에 있어야 한다(ADR-0016).

**어기면 어떤 코드가 걸리나** — `KoreanMenuNameNormalizer` 가 `Food` 를 받도록 시그니처를 바꾸거나, `@Component` 를 붙여 빈으로 만드는 순간.

### 4-11. 어댑터 구현 직접 참조는 조립 창구에서만 (`:207-225`)

```kotlin
noClasses().that().resideInAnyPackage("com.kbap.api..", "com.kbap.batch..")
    .and().resideOutsideOfPackages(
        "com.kbap.api.core.config..",
        "com.kbap.api.infra..",
        "com.kbap.batch.config..",
        "com.kbap.batch.outbox..",
    )
    .should().dependOnClassesThat().resideInAnyPackage(
        "com.kbap.common.infra..",
        "com.kbap.api.infra..",
    )
    .allowEmptyShould(true)
    .check(imported)
```

**무엇을 금지하나** — api·batch 의 **기능 코드**가 어댑터 구현(`common.infra`·`api.infra`)을 직접 참조하는 것.

**왜** — ADR-0018 이 `:infra:*` 모듈 6개를 해체하면서 생긴 규칙이다. 모듈이 있던 시절엔 "api 기능 코드는 `:infra:auth` 에 의존 선언이 없으니 firebase 를 못 본다"를 **컴파일러가** 막아 줬다. 어댑터가 같은 모듈로 흡수되면서 그 벽이 사라졌고 — ADR-0018 의 표현대로 "**컴파일 타임 SDK 격리가 테스트 타임(ArchUnit)으로 격하**"됐다. 이 규칙이 그 격하된 벽이다. [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]가 말하는 "기능 코드는 `common.port` 계약만 본다"를 강제한다.

**예외 4개가 왜 예외인가** —
- `api.core.config` — **조립 창구**. `AuthConfig.kt:6-7` 이 `JwtTokenProperties`·`FirebaseSocialAuth` 를 import 해서 `SocialTokenVerifier`(포트) 타입 빈으로 만들어 준다. 조립하려면 구현을 알 수밖에 없다.
- `api.infra` — **어댑터 자신**. 어댑터가 같은 어댑터 패키지 안 클래스를 쓰는 걸 막을 이유가 없다.
- `batch.config` — batch 쪽 조립 창구.
- `batch.outbox` — `FoodContentOutboxBatchConfig.kt:7` 이 `SqsFoodContentEventPublisher` 를 직접 import 한다. 잡 정의와 조립이 한 패키지에 있어서 생긴 **예외이자, 규칙이 완벽하지 않다는 표시**다.

**어기면 어떤 코드가 걸리나** — `api/auth/AuthService.kt` 에서 `FirebaseTokenVerifier` 를 직접 생성자 파라미터로 받는 순간. 올바른 형태는 `SocialTokenVerifier`(포트)를 받고, 어느 구현이 꽂힐지는 `AuthConfig` 가 정하는 것이다.

### 4-12. 포트는 순수 계약이다 (`:227-242`)

**무엇을 금지하나** — `common.port` 아래 클래스가 스프링·JPA·`common.infra`·api·batch 에 의존하는 것.

**왜** — 포트는 "무엇을 해 준다"는 **계약**일 뿐, "어떻게 해 준다"를 몰라야 갈아끼울 수 있다. `then` 설명대로 "포트는 순수 계약이다 — 구현 기술을 알지 못한다". 포트가 `RedisTemplate` 을 알면 그건 이미 Redis 어댑터지 계약이 아니다.

**어기면 어떤 코드가 걸리나** — `RefreshTokenStore` 인터페이스에 `@Component` 를 달거나, `PresignedUpload` 데이터 클래스가 S3 SDK 타입을 필드로 갖는 순간.

**주의** — `common.domain` 은 이 금지 목록에 **없다.** 의도적이다(§4-3 참조) — 포트가 도메인 타입을 반환하는 방향은 허용이다.

### 4-13. `IngredientCode` 회귀 방지 (`:244-254`)

```kotlin
val instanceFieldNames = IngredientCode::class.java.declaredFields
    .filterNot { Modifier.isStatic(it.modifiers) }
    .map { it.name }

instanceFieldNames shouldBe listOf("label")
```

**무엇을 금지하나** — `IngredientCode` enum 이 `label`(개발자 가독성용 한글 이름) **외의 인스턴스 필드**를 갖는 것.

**왜** — 성분 코드는 60개 넘는 enum 상수다. 여기에 "영어 번역"·"분류"·"아이콘" 같은 **콘텐츠 데이터**를 얹기 시작하면, 그 데이터를 고칠 때마다 **서버를 재배포**해야 한다. 콘텐츠는 DB(마이그레이션 시드)에 있어야 한다. 한 번 그렇게 정리한 적이 있고, 다시 그 방향으로 돌아가는 걸 막는 **회귀 테스트**다.

**어기면 어떤 코드가 걸리나** — `EGG("계란", "Egg", ALLERGEN)` 처럼 enum 생성자에 인자를 하나 더 다는 순간.

**형태가 다른 유일한 규칙** — ArchUnit 을 안 쓰고 **리플렉션**(`declaredFields` — 실행 중에 클래스 구조를 들여다보는 JVM 기능, [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 에서 정의)으로 직접 확인한다. ArchUnit DSL 로 "필드가 정확히 이것뿐"을 표현하기가 번거로워서 그냥 손으로 쓴 것이고, 아키텍처 규칙이라기보다 **정책 회귀 테스트**가 이 파일에 얹혀 있는 형태다.

| 5 | 컨텍스트 집합 == 허용 맵 키 | `:125-138` | 맵에 없는 새 컨텍스트는 검사 우회 불가 |
| 6 | 컨텍스트 간 방향 (×14) | `:140-152` | 화이트리스트 밖은 전부 금지 |
| 7 | JPA 연관관계 금지 | `:155-167` | `@OneToMany`·`@ManyToOne`·`@OneToOne`·`@ManyToMany` |
| 8 | `@Entity` 위치 | `:169-176` | 엔티티는 `common.domain` 에만 |
| 9 | 리포지토리 위치 | `:178-185` | Spring Data 리포지토리도 `common.domain` 에만 |
| 10 | `common.util` 순수 | `:188-205` | 스프링·JPA·도메인 전부 모름 |
| 11 | 어댑터 직접 참조 | `:207-225` | 조립 config 와 어댑터 자신만 |
| 12 | 포트 순수 계약 | `:227-242` | 포트는 구현 기술 모름 |
| 13 | `IngredientCode` 필드 | `:244-254` | `label` 하나뿐 (콘텐츠는 DB) |

**26 vs 13** — 테스트 리포트에는 26줄이 뜬다. 6번이 컨텍스트 14개만큼 생성되기 때문이다(13 - 1 + 14 = 26).

### 5-2. Kotest 태그 `arch` — 따로 돌리기

클래스 위의 `@Tags("arch")`(`:19`)가 라벨이고, 라벨을 Gradle 로 전달하는 배선은 `buildSrc/src/main/kotlin/kbap.kotlin-common.gradle.kts:47-50` 에 있다.

```kotlin
tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    System.getProperty("kotest.tags")?.let { systemProperty("kotest.tags", it) }
}
```

- `configureEach` — **모든 leaf 모듈**의 모든 테스트 태스크에 건다. 태그 배선의 단일 출처다.
- 두 번째 줄이 하는 일 — Gradle 을 띄운 JVM 의 시스템 프로퍼티 `kotest.tags` 를, **테스트를 실행하는 별도 JVM 으로 전달**한다. Gradle 은 테스트를 자기와 다른 프로세스에서 돌리기 때문에 이 중계가 없으면 `-D` 가 테스트까지 닿지 않는다. `?.let` 이라 프로퍼티가 없으면 아무것도 안 한다(= 전체 실행).

```bash
./gradlew :api:test -Dkotest.tags="arch"     # 아키텍처 테스트만
./gradlew :api:test -Dkotest.tags="!arch"    # 아키텍처 테스트만 빼고
./gradlew :api:test                          # 전부 (태그 미지정)
```

`!arch` 쪽이 레포 `CLAUDE.md:85` 에 적혀 있는 관용구다 — **아키텍처 규칙과 무관한 기능 작업을 할 때** 쓴다. 아키텍처 테스트는 `@SpringBootTest` 가 아니라 **앱도 Testcontainers 도 안 띄우므로** 빠르다. 태그를 나눈 이유가 실행 비용이 아니라 **의도 분리**라는 뜻이다.

> [!warning] `arch` 태그가 붙은 파일은 `ModuleBoundaryTest` 하나뿐이다
> 같은 `api/src/test/.../architecture/` 패키지에 `ErrorCodeStatusTest.kt`(에러 코드 형식·유일성 검사)가 함께 있지만 **`@Tags` 가 없다.** 그래서 `-Dkotest.tags="arch"` 로는 안 돌고, `"!arch"` 로도 안 빠진다. "아키텍처 폴더째 껐다"고 생각하면 틀린다 — 태그는 **폴더가 아니라 클래스에 붙는다.**

### 5-3. 실측 — ArchUnit 이 실제로 읽는 범위는 `:api` 의 클래스패스다

`importPackages("com.kbap")` 은 "com.kbap 전부"처럼 읽히지만, ArchUnit 은 **클래스패스에 실제로 올라온 것만** 읽는다. 그리고 이 테스트는 `api/src/test/` 에 산다.

```
$ ./gradlew :api:dependencies --configuration testRuntimeClasspath | grep "project :"
+--- project :common
```

`:api` 의 테스트 클래스패스에는 **`:common` 뿐이고 `:batch` 는 없다.** 결과가 둘로 갈린다.

- **금지 대상(`dependOnClassesThat`)으로 쓰인 `com.kbap.batch..` 는 정상 작동한다.** ArchUnit 은 임포트 범위 밖 클래스를 **이름만 있는 stub `JavaClass`** 로 만들기 때문에, "이 클래스가 `com.kbap.batch.*` 에 의존하는가"는 이름으로 판정된다. §4-2·4-3·4-10·4-12 는 온전하다.
- **검사 주체(`that().resideInAnyPackage("com.kbap.batch..")`)로 쓰인 곳은 batch 코드를 실제로 못 본다.** 해당하는 건 §4-11(어댑터 조립 창구) 하나다. batch 기능 코드가 어댑터를 직접 참조해도 **이 테스트로는 잡히지 않는다.**

과대평가하지 말자는 이야기지 규칙이 틀렸다는 이야기가 아니다. 다만 "ArchUnit 이 지키니까 괜찮다"고 말할 때, **batch 쪽 조립 창구 규칙은 사람이 지키고 있다**는 걸 알고 말하는 편이 낫다.

### 5-4. CI 에서 언제 도나

`.github/workflows/build.yml` 이 전부다.

```yaml
on:
  pull_request:
    branches: [ "main", "develop", "release/**" ]
    types: [ opened, reopened, synchronize ]
  workflow_dispatch:
...
      - name: Build with Gradle
        run: |
          chmod +x gradlew
          ./gradlew clean build
```

- 트리거 — `main`·`develop`·`release/**` 로 가는 **PR** 이 열리거나 **커밋이 푸시될 때마다**(`synchronize`). 그리고 수동 실행(`workflow_dispatch`).
- `./gradlew clean build` — 태그를 지정하지 않으므로 **`arch` 태그 테스트도 함께 돈다.** 즉 아키텍처 위반은 **PR 을 머지하기 전에 무조건 걸린다.**
- 반대로 로컬 커밋·푸시 자체는 아무것도 막지 않는다(pre-commit 훅 없음). 위반한 코드로 커밋은 되고, PR 이 빨개진다.

## 6. 3층 구조 — 무엇이 무엇을 막나

kbap 에서 경계를 지키는 힘은 세 층이다. **위로 갈수록 빠르고 확실하며, 아래로 갈수록 느슨하다.**

| 층 | 언제 걸리나 | 무엇을 막나 | 어길 수 있나 |
|---|---|---|---|
| **① 빌드(Gradle)** | 컴파일 시점 (초 단위, 에디터가 즉시 빨간 줄) | **api ↔ batch 상호 참조.** 두 모듈 다 `implementation(project(":common"))` 만 선언한다 — 서로를 의존 목록에 넣지 않았다 | 못 어긴다. import 를 쓰면 **컴파일 자체가 안 된다** |
| **② 테스트(ArchUnit)** | `./gradlew test` / PR CI (분 단위) | 이 노트의 규칙 13종 — 패키지 간 방향, 엔티티·리포지토리 위치, 어댑터 참조, 연관관계 | 로컬에서는 어긴 채 커밋된다. **PR 이 빨개진다** |
| **③ 사람(규율·리뷰)** | 코드 리뷰 (사람이 눈치채야) | **도메인 로직의 도메인 서비스 소유**(ADR-0014). batch 쪽 어댑터 조립 창구(§5-3) | 얼마든지 어겨진다. 리뷰어가 놓치면 그대로 들어간다 |

**①이 왜 확실한가** — `api/build.gradle.kts:6` 과 `batch/build.gradle.kts:6` 이 각각 `"implementation"(project(":common"))` 한 줄만 갖는다. `settings.gradle.kts:20-24` 가 세 모듈을 등록하지만 api↔batch 사이에는 화살표가 없다. `api` 코드에서 `import com.kbap.batch.outbox.FoodContentOutboxPublisher` 를 쓰면 **테스트를 돌리기도 전에 컴파일러가 "unresolved reference"** 라고 한다. 이게 가장 좋은 강제다 — 즉각적이고, 우회 불가능하고, 배우기 쉽다.

**③이 왜 남았는가** — ADR-0014(`docs/adr/0014-relax-persistence-encapsulation.md`)가 엔티티·리포지토리의 `internal` 을 걷어내고 public 으로 바꿨다. 소비 계층이 리포지토리를 직접 쓸 수 있어 편해진 대신, ADR 이 명시적으로 인정한다 — "**컴파일러가 막아 주던 '도메인 서비스 우회'가 가능해졌다 — 도메인 로직을 소비 계층에 쓰는 실수는 이제 리뷰가 잡아야 한다.**" 그리고 그 ADR 은 "ArchUnit 으로 재제한하기"를 **의도적으로 기각**했다("완화하는 결정에서 새 제한을 발명하는 자기모순").

즉 **`OrderService` 안에 주문 상태 전이 규칙을 잔뜩 써 넣는 것**은 ArchUnit 이 못 잡는다. 그건 규칙의 구멍이 아니라 **의도된 여백**이고, 리뷰가 채우기로 한 자리다.

> [!note] 방향이 계속 아래로 내려왔다
> ADR-0016(모듈 8→3): 도메인 간 순환 차단이 **컴파일 타임 → 테스트 타임**으로.
> ADR-0018(infra 해체): SDK 격리가 **컴파일 타임 → 테스트 타임**으로.
> ADR-0014(영속 public): 도메인 서비스 경유가 **컴파일 타임 → 리뷰**로.
> 세 번 다 "모듈·`internal` 이라는 벽을 걷어내고, 대신 편해진다"는 거래였다. 그 거래의 대가를 갚고 있는 게 `ModuleBoundaryTest.kt` 한 파일이다. **이 파일이 부실해지면 kbap 아키텍처는 문서에만 남는다.**

## 7. 테스트가 실패했을 때 읽는 법

### 7-1. 메시지 형태

ArchUnit 위반은 `AssertionError` 로 뜨고, 형태가 고정돼 있다.

```
java.lang.AssertionError: Architecture Violation [Priority: MEDIUM] -
Rule 'no classes that reside in a package 'com.kbap.common.core..'
should depend on classes that reside in any package ['org.springframework..', ...]'
was violated (1 times):
Method <com.kbap.common.core.error.ErrorCode.toResponse()> calls method
<org.springframework.http.ResponseEntity.ok()> in (ErrorCode.kt:42)
```

읽는 순서는 **뒤에서 앞으로**다.

1. **맨 끝 `(ErrorCode.kt:42)`** — 고칠 위치. 여기부터 본다.
2. **그 앞의 `calls method <...>`** — 무엇 때문에 걸렸는지. `calls method`·`has field type`·`is annotated with`·`extends` 등 의존의 **종류**가 적힌다. import 를 지웠는데도 안 사라진다면 여기가 이유를 말해 준다.
3. **`was violated (N times)`** — 위반 개수. N 이 크면 규칙 자체를 의심할 신호일 수 있다(§7-2).
4. **`Rule '...'`** — 규칙 문장. `noClasses().that()...should()...` 를 ArchUnit 이 영어 문장으로 되돌린 것이다. `ModuleBoundaryTest.kt` 를 Ctrl+F 로 찾을 때 이 문장의 패키지 이름으로 검색하면 바로 나온다.

§4-5(컨텍스트 집합 대조)와 §4-13(`IngredientCode`)만 형태가 다르다 — ArchUnit 이 아니라 Kotest `shouldBe` 라서 `expected: [...] but was: [...]` 로 뜬다. 두 리스트를 눈으로 비교해 **어느 원소가 늘었는지/줄었는지**를 찾으면 된다.

### 7-2. "규칙이 틀렸나, 내 코드가 틀렸나"

기본값은 **내 코드가 틀렸다**이다. 이 규칙들은 전부 ADR 이 뒷받침하고 있어서, 대부분의 위반은 "몰라서 옛날 방식으로 썼다"이다. 아래 순서로 판단한다.

**1. 규칙 문장이 가리키는 ADR 을 먼저 읽는다.**

| 걸린 규칙 | 읽을 문서 |
|---|---|
| 구 패키지 · 기능 패키지 배치 | ADR-0017(`docs/adr/0017-api-feature-package-flattening.md`) |
| `@Entity`·리포지토리 위치 · 컨텍스트 방향 | ADR-0016(`docs/adr/0016-module-diet-three-app-modules.md`) |
| 어댑터 직접 참조 · 포트 순수성 | ADR-0018(`docs/adr/0018-dissolve-infra-modules-into-consumers.md`) |
| 연관관계 · 엔티티=도메인 모델 · 리포지토리 public | ADR-0014(`docs/adr/0014-relax-persistence-encapsulation.md`) |

ADR 위에 한 층 더 있다 — **헌법**(`.specify/memory/constitution.md`)이다. 예컨대 연관관계 금지는 원칙 IV(Persistence Ownership)에 "**엔티티 간 JPA 연관관계를 두지 않는다. 참조는 id 값으로만 들고…**"라고 못 박혀 있고(`:228`), 그 바로 아래 `:232` 가 "경계는 Gradle 의존 방향 + ArchUnit(`ModuleBoundaryTest`)로 강제한다"고 이 파일을 지목한다. **헌법 → ADR → ArchUnit 규칙** 순으로 좁아지는 구조다(헌법 전반은 [[14. SDD와 TDD — 스펙과 테스트로 개발하기]]).

**2. "규칙을 우회하는 방법"을 찾고 있다면 십중팔구 설계가 틀렸다.** `review` 가 `member` 를 알아야 해서 방향 규칙에 걸렸다면, 답은 **허용 맵에 `member` 를 추가하는 것이 아니라** `memberId: Long` 을 쓰는 것이다. 어댑터 참조 규칙에 걸렸다면 답은 예외 패키지를 늘리는 것이 아니라 **포트 인터페이스를 하나 만드는 것**이다.

**3. 규칙 자체를 고쳐야 하는 경우도 있다** — 새 컨텍스트가 생겼고 그게 정말 다른 컨텍스트를 알아야 하는 경우(§4-5 가 그러라고 만든 장치다), 또는 ADR 이 정말 바뀌어야 하는 경우.

> [!warning] 이 레포의 문화 — 규칙보다 ADR 이 먼저다
> `allowedDomainDeps` 맵에 한 줄 추가하는 건 3초면 된다. 그런데 그 맵은 **아키텍처 결정의 코드판**이지 테스트 설정이 아니다. ADR-0016 이 그걸 명시한다 — "`ModuleBoundaryTest` 의 허용 맵이 방향의 단일 출처가 되므로 **리뷰에서 맵 변경을 의식적으로 다룬다**."
> 그래서 순서는 **ADR 을 먼저 바꾸고(또는 새로 쓰고) 규칙을 따라 바꾼다.** 규칙만 슬쩍 고친 PR 은 "왜 이 방향이 허용됐는지"를 6개월 뒤에 아무도 설명하지 못하게 만든다. 규칙 파일의 진짜 값어치는 **테스트를 통과시키는 것이 아니라 결정을 기록하는 것**이다.

**4. 절대 하지 말 것** — `@Tags("arch")` 를 지우거나, `@Ignore` 를 달거나, 규칙에서 자기 패키지를 예외로 빼는 것. ArchUnit 에는 레거시용 `FreezingArchRule`(기존 위반을 파일로 기록해 두고 **새 위반만** 보고하는 장치)도 있지만, **kbap 은 쓰지 않는다** — `archunit.properties` 파일이 레포에 없고, 위반은 0건 유지가 전제다.

## 8. 치트시트

```bash
# 아키텍처 테스트만 돌리기 (빠름 — Testcontainers 안 뜸)
./gradlew :api:test -Dkotest.tags="arch"

# 아키텍처 테스트만 빼고 돌리기 (기능 작업 중)
./gradlew :api:test -Dkotest.tags="!arch"

# CI 와 같은 것 (태그 미지정 = 전부)
./gradlew clean build
```

```kotlin
// ArchUnit DSL — 이 파일에 쓰인 형태 전부
classes()   .that()...  .should()...    // "~한 클래스는 ~해야 한다"
noClasses() .that()...  .should()...    // "~한 클래스는 ~하면 안 된다"
noFields()  .that()...  .should()...    // 필드 단위 검사 (연관관계 금지)

.resideInAPackage("a.b..")              // 이 패키지 + 하위 전부
.resideInAnyPackage("a..", "c..")       // 여러 개 중 하나
.resideOutsideOfPackages(...)           // 예외 지정
.areAnnotatedWith("...")                // 애너테이션으로 고르기
.areAssignableTo("...")                 // 상속 관계로 고르기 (이름 아님)
.dependOnClassesThat()                  // import·필드·파라미터·호출 전부
.beAnnotatedWith(...) .orShould(...)    // 조건 여러 개 OR
.allowEmptyShould(true)                 // "하나도 안 걸리는 게 정상"일 때
.check(imported)                        // 실행
```

| 상황 | 어디를 본다 |
|---|---|
| 새 도메인 컨텍스트를 만들었다 | `ModuleBoundaryTest.kt:108` 의 `allowedDomainDeps` 에 줄 추가 (+ 왜 그 방향인지 PR 에 설명) |
| 외부 시스템(SDK)을 새로 붙인다 | 포트를 `common.port` 에, 구현을 `infra` 에, 조립을 `config` 에 → [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] |
| 엔티티를 새로 만든다 | 무조건 `common/domain/<컨텍스트>/model/` |
| 리포지토리를 새로 만든다 | 무조건 `common/domain/<컨텍스트>/` |
| 두 테이블을 이어야 한다 | 연관관계 대신 `Long` id → [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] |
| 아키텍처 테스트가 빨갛다 | 메시지 맨 끝 줄 번호 → 해당 ADR → 설계 고치기 (규칙 고치기는 마지막) |

## 9. 용어집

- **ArchUnit** — 아키텍처 규칙을 테스트 코드로 표현하는 라이브러리. 컴파일된 바이트코드를 읽는다.
- **`ClassFileImporter`** — `.class` 파일을 읽어 `JavaClasses` 로 만드는 ArchUnit 의 입구.
- **`ImportOption`** — 무엇을 읽을지 거르는 필터. kbap 은 테스트·테스트픽스처를 제외한다.
- **`allowEmptyShould`** — "검사 대상이 0개일 때 실패할 것인가". 기본은 실패(오타 방어). "0개가 정상"인 규칙에서만 끈다.
- **stub `JavaClass`** — 임포트 범위 밖 클래스를 이름만 가진 껍데기로 만들어 두는 것. 덕분에 클래스패스에 없는 패키지도 **의존 대상으로는** 판정된다.
- **Kotest 태그** — 테스트에 붙이는 라벨(`@Tags("arch")`). `-Dkotest.tags="arch"` / `"!arch"` 로 고른다.
- **`FreezingArchRule`** — 기존 위반을 파일에 얼려 두고 새 위반만 잡는 ArchUnit 기능. **kbap 은 쓰지 않는다.**
- **바운디드 컨텍스트** — 업무 영역 하나. kbap 에선 `common.domain.<이름>` 패키지 하나 → [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]
- **커널** — 누구에게도 속하지 않는 최하위 공통재(`common.core`). 프레임워크를 몰라야 한다.
- **조립 창구(config)** — 포트 타입 자리에 어떤 어댑터 구현을 꽂을지 정하는 곳 → [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]

## 10. 체크리스트

- [ ] ArchUnit 이 ESLint 커스텀 룰과 같은 자리를 차지하지만, **바이트코드를 읽어서 import 문에 없는 의존까지 본다**는 차이를 설명할 수 있다
- [ ] `ModuleBoundaryTest.kt` 를 열어 규칙 13종을 찾을 수 있고, 각각이 어느 ADR 에서 왔는지 짚을 수 있다
- [ ] `allowedDomainDeps` 맵이 왜 "코드에서 발견된 컨텍스트 집합"과 대조되는지(구멍 막기) 설명할 수 있다
- [ ] `allowEmptyShould(true)` 가 있는 규칙과 없는 규칙(`@Entity` 위치)의 차이를 설명할 수 있다
- [ ] `-Dkotest.tags="arch"` / `"!arch"` 를 상황에 맞게 쓸 수 있다
- [ ] **빌드가 막는 것 / 테스트가 막는 것 / 사람이 지켜야 하는 것** 3층을 각각 예를 들어 말할 수 있다
- [ ] ArchUnit 실패 메시지에서 **줄 번호 → 의존 종류 → 규칙 문장** 순으로 읽고 원인을 찾을 수 있다
- [ ] 규칙에 걸렸을 때 "규칙을 고치기 전에 ADR 을 본다"는 순서를 지킬 수 있다

> 이 노트가 다룬 규칙들은 **한 모듈 안에서** 패키지끼리의 방향을 지킨다. 그보다 굵은 경계 하나는 아예 컴파일이 막는다 → [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] §2. `:api` 와 `:batch` 는 서로를 **의존 목록에 갖고 있지 않아** 상호 참조가 ArchUnit 이전에 Gradle 에서 실패한다. 두 앱이 만나는 자리는 `:common` 과 **DB 테이블 하나**뿐이다([[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]] §7-1).
> 여기서 배울 점은 순서다 — **컴파일로 막을 수 있으면 컴파일로, 안 되면 ArchUnit 으로, 그것도 안 되면 테스트로.** 같은 아웃박스 흐름에서 세 층이 다 보인다: 모듈 경계는 Gradle, 포트 순수성은 ArchUnit(`ModuleBoundaryTest`), "SQS 호출이 트랜잭션 밖" 은 런타임 단언이 필요해 테스트가 잡는다([[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §7).

> [!note] 2026-08-27 역링크 — ArchUnit 이 맡는 범위가 **어디서부터**인지
> **[[3. JVM 위의 Kotlin — 컴파일·널 안전·Gradle 3모듈]] §7-4** 가 이 노트 앞의 한 겹을 그어준다. 모듈 사이의 굵은 경계(`:api` ↔ `:batch`)는 ArchUnit 이 아니라 **Gradle 이 막는다** — 의존을 선언하지 않았으니 클래스패스에 아예 없고, 컴파일이 실패한다. 반대로 **`:common` 안에서 도메인끼리 지켜야 할 방향**(`common.domain.food` 가 `common.domain.member` 를 봐도 되나)은 모듈이 3개뿐이라 Gradle 이 못 잡고, 거기서부터가 이 노트다.
> 즉 순서는 **컴파일로 막을 수 있으면 컴파일로, 안 되면 ArchUnit 으로.** [[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]] §9 흐름표의 ※행도 이 노트를 같은 자리에 놓는다.
