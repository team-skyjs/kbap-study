# 14. SDD와 TDD — 스펙과 테스트로 개발하기

> 작성: 2026-08-26 · 맥락: 앞의 11~13번이 "코드를 어디에 두는가"였다면, 이 노트는 **그 코드를 어떤 순서로 만드는가**다. 이 레포에는 기능 하나를 만들 때 반드시 거치는 절차가 문서로 못 박혀 있고, 그걸 모르면 `specs/` 아래 125개 디렉터리가 무슨 물건인지 알 수 없다.
> 목표: SpecKit 의 spec → plan → tasks 흐름과 Test-First 원칙을 설명할 수 있게 되고, **한때 이 레포가 멀티에이전트로 TDD 를 굴리다 왜 걷어냈는지**까지 말할 수 있게 되기.

---

## 0. 한 줄 요약

kbap 은 기능 하나를 만들 때 **코드를 먼저 쓰지 않는다.** 먼저 `specs/<티켓>/` 에 **스펙 문서**를 쓰고(SDD), 그 스펙을 **실패하는 테스트**로 옮긴 다음(TDD), 그 테스트를 통과시키는 코드를 쓴다. 이 순서를 어기지 못하게 못 박아 둔 문서가 레포 안의 **헌법**(`.specify/memory/constitution.md`)이고, 지금 `specs/` 에는 그렇게 만들어진 기능 디렉터리가 **125개** 쌓여 있다.

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 |
|---|---|---|
| **SDD** (Spec-Driven Development) | 구현 전에 "무엇을·왜"를 문서로 확정하고, 그 문서를 단일 출처로 삼아 개발하는 방식 | 피그마 시안 + PRD 를 확정하고 나서 컴포넌트를 짜기 시작하는 것 |
| **SpecKit** | GitHub 이 만든 SDD 도구. `spec → plan → tasks → implement` 4단계와 문서 템플릿을 강제한다 | `create-react-app` 같은 스캐폴더인데, 만드는 게 코드가 아니라 **문서** |
| **헌법** (constitution) | 레포가 절대 어기지 않기로 한 원칙 문서. 모든 계획이 이 문서를 통과해야 다음 단계로 간다 | ESLint 룰셋 + 아키텍처 결정문을 합쳐 한 파일에 못 박아 둔 것 |
| **TDD** | 실패하는 테스트를 먼저 쓰고, 그걸 통과시키는 최소 코드를 쓰고, 그다음 정리하는 개발 순서 | 없음 — FE 에서는 보통 컴포넌트를 먼저 만들고 테스트를 나중에 붙인다 |
| **Red → Green → Refactor** | TDD 한 바퀴. 빨강(실패) → 초록(통과) → 리팩터 | Jest watch 모드에서 빨간 줄이 초록으로 바뀌는 그 사이클을 **의도적으로** 돌리는 것 |
| **Kotest** | Kotlin 테스트 프레임워크. kbap 이 쓰는 것 | Jest / Vitest |
| **BehaviorSpec** | Kotest 의 테스트 작성 스타일 중 하나. `given / when / then` 3단 중첩 | Jest 의 `describe > describe > it` 3단 중첩 |
| **Testcontainers** | 테스트가 돌 때 도커로 **진짜 MySQL** 을 띄웠다가 끝나면 지우는 라이브러리 | msw 로 API 를 흉내 내는 대신, **진짜 서버를 켰다 끄는** 쪽 |
| **커버리지** (coverage) | 테스트가 코드의 몇 %를 실제로 실행했는지 재는 지표. 도구는 **jacoco** | `jest --coverage` 와 같은 것 |

## 2. SDD — 왜 코드보다 문서를 먼저 쓰나

FE 에서 새 화면을 만들 때를 떠올려 보자. 디자인 시안이 없는 상태로 컴포넌트부터 짜기 시작하면, 절반쯤 만든 뒤에 "이 케이스는 어떻게 보여야 하죠?"가 터진다. 빈 목록일 때, 이미지가 없을 때, 위치 권한을 거부했을 때. 그때마다 이미 짠 구조를 뜯는다.

백엔드는 이 비용이 더 크다. **DB 스키마를 이미 배포했으면 되돌리기가 어렵고**([[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] 의 "되돌리기가 어렵다"), **API 계약을 이미 앱에 내보냈으면 앱 스토어 심사를 거쳐야 바뀐다**([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]). 그래서 "짜다 보면 알게 되겠지"가 FE 보다 훨씬 비싸다.

SDD 는 그 순간을 **코드를 쓰기 전으로 옮긴다.** 애매한 케이스를 전부 문서에서 먼저 부딪히고, 결정하고, 그 결정을 문장으로 박아 둔다.

> **비유: 시안 없이 화면을 짜 본 경험**
> SDD 의 `spec.md` 는 **시안 + 요구사항 정의서**이고, `plan.md` 는 **컴포넌트 분해도**이고, `tasks.md` 는 **지라 티켓 목록**이다. 시안이 확정돼야 컴포넌트를 나누고, 컴포넌트가 나뉘어야 티켓을 쪼갤 수 있는 그 순서 그대로다.
>
> **어디까지 같고 어디서부터 다른가**
> - 같은 것: **앞 단계가 확정돼야 뒤 단계로 간다**는 순서, 그리고 **문서가 나중에 "왜 이렇게 했지"의 답이 된다**는 점.
> - 다른 것 1 — **문서가 레포 안에 커밋된다.** 피그마·노션은 코드 밖에 있어서 코드와 따로 낡지만, `specs/` 는 코드와 같은 커밋에 들어가 같이 리뷰되고 같이 히스토리에 남는다.
> - 다른 것 2 — **게이트가 있다.** 시안은 마음에 안 들어도 일단 짜기 시작할 수 있지만, SpecKit 의 `plan` 단계에는 **헌법 검사(Constitution Check)** 라는 통과 조건이 있다(§4).
> - 다른 것 3 — **문서가 곧 테스트 목록이 된다.** `spec.md` 의 "Acceptance Scenarios" 한 줄이 그대로 `tasks.md` 의 테스트 한 줄이 되고, 다시 실제 테스트 코드 한 블록이 된다(§5).

### SpecKit 사이클 4단계

```text
/speckit-specify  →  spec.md      무엇을·왜 (기술 얘기 없음)
      ↓ (게이트: 스펙 검토)
/speckit-plan     →  plan.md      어떻게 (+ research.md · data-model.md · contracts/)
      ↓ (게이트: 헌법 검사 + 계획 검토)
/speckit-tasks    →  tasks.md     T001…T0NN 순서 있는 작업 목록
      ↓
/speckit-implement →  코드         tasks.md 를 위에서부터 소화
```

이 4단계와 두 개의 검토 게이트는 레포에 파일로 박혀 있다:

```yaml
steps:
  - id: specify
    command: speckit.specify
  - id: review-spec
    type: gate
    message: "Review the generated spec before planning."
    options: [approve, reject]
    on_reject: abort
  - id: plan
    command: speckit.plan
  - id: review-plan
    type: gate
    message: "Review the plan before generating tasks."
```
`.specify/workflows/speckit/workflow.yml:28-52`

- `type: gate` — 사람이 승인해야 다음 단계로 넘어간다. `on_reject: abort` 는 거절하면 **사이클 전체를 중단**한다는 뜻이다. 계획이 틀린 채로 코드가 나오는 것보다 처음부터 다시 하는 게 싸다는 판단이다.
- 이 4개 말고도 필요할 때 부르는 보조 명령이 있다 — `/speckit-clarify`(스펙의 빈칸 채우기)·`/speckit-analyze`(스펙↔계획↔작업 정합 검사)·`/speckit-checklist`(요구사항 체크리스트 생성).

### 실물 하나 — `specs/kb-337-order-history/`

주문 이력 기능(지라 KB-337) 하나가 만들어 낸 디렉터리다.

```text
specs/kb-337-order-history/
├── spec.md          13KB  무엇을·왜 — 사용자 스토리 3개 + Acceptance Scenarios
├── research.md       6KB  결정이 필요했던 지점들(R1…R6)과 그 답
├── plan.md           6KB  어떻게 — 기술 선택 + 헌법 검사표
├── data-model.md     3KB  테이블·컬럼 설계
├── contracts/       API 계약 — order-api.md
├── checklists/      요구사항 체크리스트 — requirements.md
├── quickstart.md     2KB  이 기능을 손으로 확인하는 법
└── tasks.md         10KB  T001~T024, 각각 [P](병렬 가능)·[Red] 표시
```

`spec.md` 는 **기술 얘기를 하지 않는다.** 클래스 이름도, 테이블 이름도 없다. 대신 이런 문장이 있다:

```markdown
2. **Given** GPS 좌표를 함께 보낸 주문, **When** 저장하면, **Then** 좌표와 역지오코딩된
   도로명 주소가 함께 저장된다. 좌표 없이 보내면 위치 정보 없이 저장된다(좌표는 옵셔널).
   - 역지오코딩이 실패해도 주문 저장은 성공한다 — 실패 로그를 남기고 주소는 null 로 저장,
     좌표만 남는다(위치는 부가 정보).
```
`specs/kb-337-order-history/spec.md` — User Story 1 의 Acceptance Scenarios

- **Given / When / Then** — 이 세 단어를 기억해 두자. §5 에서 **테스트 코드의 구조가 이 문장과 글자 그대로 같다는 것**을 보게 된다. 스펙에서 테스트로 넘어가는 다리가 이 형식이다.
- "역지오코딩이 실패해도 주문 저장은 성공한다" — 코드를 쓰기 전에 이미 **실패 시 동작이 결정돼 있다.** 짜다 보면 만났을 질문이 문서 단계에서 끝났다.

125개 디렉터리 중 실제로 각 문서가 몇 개씩 있는지 세어 보면(2026-08-26 실측):

| 문서 | 개수 | 뜻 |
|---|---|---|
| `spec.md` | 125 / 125 | **예외 없이** 모든 기능이 스펙에서 시작했다 |
| `checklists/` | 124 | 거의 전부 요구사항 체크리스트를 만들었다 |
| `plan.md` · `research.md` | 116 | 9건은 스펙만 쓰고 계획 단계로 가지 않았다(중단·흡수된 기능) |
| `tasks.md` | 113 | 실제로 작업 목록까지 나온 기능 |
| `data-model.md` | 107 | 스키마 변화가 있던 기능 |
| `contracts/` | 94 | API 계약이 생긴 기능 |

## 3. 헌법 — 규칙을 왜 문서로 못 박나

`.specify/memory/constitution.md`. 파일 이름이 진짜 "헌법"이다. FE 에서는 낯선 장치니 먼저 **왜 있는지**부터.

프로젝트가 커지면 "우리는 이렇게 하기로 했다"가 쌓인다. 문제는 그게 보통 **사람 머릿속과 리뷰 코멘트에만** 있다는 것이다. 그러면 세 가지가 벌어진다.

| 규칙이 사람 머릿속에만 있을 때 | 무슨 일이 벌어지나 |
|---|---|
| 새로 합류한 사람 | 규칙을 모른 채 코드를 쓰고, 리뷰에서 뒤집힌다. 배우는 비용을 매번 리뷰가 낸다 |
| 시간이 지난 뒤 | "왜 이렇게 했더라" 를 아무도 기억 못 해, 규칙을 어긴 코드가 슬쩍 들어온다 |
| 규칙을 바꿀 때 | 언제 왜 바뀌었는지 흔적이 없어, 옛 규칙과 새 규칙이 레포 안에 공존한다 |

헌법은 이 셋을 한 번에 친다. **규칙을 파일로 만들고, 버전을 붙이고, 개정 이력을 남기고, 모든 계획이 통과해야 하는 게이트로 세운다.**

kbap 헌법은 지금 **7.0.0** 이고(`.specify/memory/constitution.md:312`), 파일 맨 위에 v3.0.1 부터 v7.0.0 까지의 개정 사유가 주석으로 통째로 남아 있다. 버전 규칙도 문서 안에 있다 — `MAJOR = 원칙 제거/비호환 재정의, MINOR = 원칙 추가·실질 확장, PATCH = 문구 보정`(`:306-307`). npm 패키지에 SemVer 를 붙이듯, **규칙 자체에 SemVer 를 붙인 것**이다.

> **곁가지 — 이게 왜 유용한지 한 눈에 보이는 예**
> 이 노트 시리즈의 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]·[[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 이 설명하는 "엔티티가 곧 도메인 모델"·"JPA 연관관계 금지"는 어느 날 누가 정한 취향이 아니다. 헌법 원칙 IV 에 문장으로 있고(`:213-237`), 언제 왜 그렇게 바뀌었는지가 파일 상단 개정 이력에 있고(v5.0.0, KB-220), 그걸 어기면 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 의 테스트가 빨갛게 된다. **문서 → 개정 이력 → 자동 검사** 세 겹이다.

### 원칙 다섯 개 — 한 줄씩

| # | 이름 | 한 줄 | 자세히 |
|---|---|---|---|
| **I** | Test-First Development (**NON-NEGOTIABLE**) | 실패하는 테스트를 먼저 쓰고, 통과시키고, 정리한다. 테스트 없는 구현은 머지 대상이 아니다 | 이 노트 §5 |
| **II** | Bounded Contexts | 도메인은 `common.domain.<컨텍스트>` 패키지로 나누고, 도메인끼리는 단방향으로만 의존한다. 다른 컨텍스트는 객체가 아니라 **id 값**으로 참조한다 | [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] |
| **III** | Layered Dependency Direction | 의존은 한 방향 — `:api`·`:batch` → `:common`. 외부 시스템은 **seam 인터페이스로만** 쓴다(계약은 `common.port`, 구현은 소비 모듈, 조립은 config) | [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] |
| **IV** | Persistence Ownership | 엔티티·리포지토리는 데이터를 소유한 도메인 패키지에 public 으로. **엔티티가 곧 도메인 모델**, JPA 연관관계 금지, 트랜잭션 경계는 쓰는 쪽이 명시 | [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] · [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] · [[6. 설정과 프로필, 트랜잭션 경계]] |
| **V** | Domain Content Language Policy | 음식 콘텐츠는 한국어 원문 + 9개 언어 사전 번역. `lang` 은 **필수**(비면 400), 번역이 없으면 `ko`, 지원 안 하는 코드면 `en` 으로 폴백 | 관련: [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] |

### 4-2. 테스트 코드의 모양 — Kotest BehaviorSpec

kbap 의 테스트 스타일은 **고정**돼 있다. 레포 규약에 이렇게 적혀 있다:

> **모든 테스트는 Kotest `BehaviorSpec` 으로 통일**한다(다른 Spec 스타일·JUnit `@Test` 금지). 구조는 **``given("대상/전제") > `when`("상황") > then("기대 결과")``** 를 기본으로 하며, `given`·`` `when` ``·`then` 설명은 **한국어**로 쓴다.
>
> — `CLAUDE.md:107`

실측으로도 그렇다(2026-08-26 기준) — 테스트 소스 174개 파일 중 **테스트 스펙은 151개이고 전부 `BehaviorSpec`** 이다. `FunSpec`·`StringSpec`·`DescribeSpec` 같은 다른 Kotest 스타일도, JUnit 의 `@Test` 도 **한 파일도 없다.** (나머지 23개는 스펙이 아니라 페이크 빈·테스트 설정 같은 도우미 파일이다.)

앞의 T003 이 만든 파일이 실제로 이렇게 생겼다:

```kotlin
class OrderItemTest : BehaviorSpec({

    given("주문 항목 생성") {
        `when`("이름·수량·가격을 주면") {
            then("스냅샷 그대로 보존된다") {
                val item = OrderItem.place(orderId = 10L, foodId = 7L, menuName = "순두부찌개", quantity = 2, price = 9000)
                item.menuName shouldBe "순두부찌개"
                item.quantity shouldBe 2
            }
        }

        `when`("수량이 0 이하면") {
            then("예외를 던진다") {
                shouldThrow<IllegalArgumentException> { OrderItem.place(10L, 7L, "순두부찌개", 0, null) }
            }
        }
    }
})
```
`common/src/test/kotlin/com/kbap/common/domain/order/model/OrderItemTest.kt:7-31` (일부 발췌)

- `class OrderItemTest : BehaviorSpec({ … })` — 클래스가 `BehaviorSpec` 을 상속하고, **생성자에 람다를 넘긴다.** Jest 로 치면 `describe('OrderItem', () => { … })` 의 그 화살표 함수 자리다. Kotlin 에는 톱레벨 `describe` 같은 게 없어서 클래스 형태를 빌린 것뿐, 하는 일은 같다.
- `given("주문 항목 생성")` — **전제/대상**. Jest 의 바깥 `describe` 에 해당한다.
- ``` `when`("수량이 0 이하면") ``` — **상황**. 백틱이 붙은 이유는 `when` 이 Kotlin 의 예약어(우리가 아는 `switch` 문)이기 때문이다. Kotlin 은 예약어를 백틱으로 감싸면 식별자로 쓸 수 있게 해 준다. (Kotest 는 백틱이 싫으면 대문자 `Given`/`When`/`Then` 별칭도 제공하지만, kbap 은 소문자 + 백틱으로 통일했다.)
- `then("예외를 던진다") { … }` — **기대 결과**. Jest 의 `it(...)` 이다. 실제 단정은 이 안에 들어간다.
- `shouldBe` / `shouldThrow<…>` — Kotest 의 단정 함수. `expect(x).toBe(y)` / `expect(fn).toThrow()` 에 해당한다. 중위 함수라 점·괄호 없이 `item.quantity shouldBe 2` 로 영어 문장처럼 쓴다.

**§2 의 스펙 문장과 나란히 놓아 보자.** 스펙이 `**Given** … **When** … **Then** …` 이었고, 테스트가 `given … when … then` 이다. 같은 형식으로 두 번 쓰는 게 아니라, **스펙의 한 줄을 그대로 테스트로 옮길 수 있게** 형식을 맞춰 둔 것이다. 이게 SDD 와 TDD 가 한 노트에 같이 있는 이유다.

> **FE 대비 — 무엇이 진짜로 다른가**
> Jest 의 `describe > it` 은 **그냥 그룹핑**이라 이름을 뭐라 짓든 자유다. BehaviorSpec 의 `given/when/then` 은 **3단이 의미를 갖는다** — given 은 상태, when 은 행위, then 은 결과. 그래서 테스트 하나가 실패했을 때 리포트에 `주문 항목 생성 > 수량이 0 이하면 > 예외를 던진다` 라고 찍히고, **그 줄이 그대로 사람이 읽는 명세**가 된다. 설명을 한국어로 쓰라고 규약에 박은 것도 그래서다.

### 4-3. Red → Green → Refactor 가 실제로 어떤 모양인가

`OrderItem` 을 예로, 한 바퀴를 그려 보자.

| 단계 | 무엇을 하나 | 이 예에서 |
|---|---|---|
| **🔴 Red** | 아직 없는 것에 대해 테스트를 쓰고 **실패를 눈으로 확인** | `OrderItem.place(…)` 자체가 없으니 **컴파일이 안 된다.** 이것도 정당한 Red 다 |
| **🟢 Green** | 통과시키는 **최소** 구현 | `OrderItem` 클래스 + `place()` 팩토리에 `require(quantity > 0)` 같은 검증만. 이 시점에 페이징이나 응답 DTO 를 미리 만들지 않는다 |
| **🔵 Refactor** | 초록을 유지한 채 정리 | 중복된 검증을 묶거나 이름을 고친다. **테스트가 그물이라 안심하고 뜯을 수 있다** |

Refactor 단계가 TDD 의 진짜 값어치다. 테스트가 없으면 "돌아가는 코드를 건드리기 무섭다"가 되어 정리를 안 하게 되고, 정리를 안 하면 코드가 쌓인다. 초록 그물이 깔려 있으면 뜯다가 뭘 깨뜨려도 **10초 안에 알게 된다.**

> [!warning] Red 를 건너뛰면 생기는 일
> 구현을 먼저 하고 테스트를 나중에 붙이면, 테스트는 **이미 있는 코드의 동작을 그대로 받아쓰게** 된다. 코드가 틀렸어도 테스트가 그 틀림을 그대로 굳혀 버린다. Red 단계는 "이 테스트가 지금 통과하지 않는다"를 확인함으로써 **테스트가 실제로 무언가를 검사한다는 증거**를 남기는 절차다.

## 5. 테스트 세 종류 — 무엇을 어디까지 켜고 도나

같은 BehaviorSpec 문법을 쓰지만, **어디까지 실제로 켜서 도느냐**가 다르다.

| 종류 | 무엇을 켜나 | 얼마나 빠른가 | kbap 실물 |
|---|---|---|---|
| **단위 테스트** | 아무것도 안 켠다. 클래스 하나를 그냥 만들어서 부른다 | 밀리초 | 스펙 151개 중 **58개**(아래 아키텍처 스펙 포함). `OrderItemTest`·`RiskLevelTest`·`LanguageCodeTest` 등 — 도메인 모델의 검증·계산 로직 |
| **통합 테스트** | **Spring 앱 전체 + 도커 MySQL** 을 띄우고 진짜 HTTP 요청을 쏜다 | 수 초~수십 초 | 스펙 151개 중 **93개**(`@SpringBootTest`). `OrderControllerTest` 등 |
| **아키텍처 테스트** | 아무것도 안 켠다 — **도커도, 앱도.** 컴파일된 바이트코드의 클래스 구조만 훑는다 | 빠름 | `ModuleBoundaryTest` 한 클래스(규칙 13종·`then` 26개) → **정본은 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]** |

### 통합 테스트가 진짜 MySQL 을 켜는 방법

FE 에서 API 를 테스트할 때는 보통 msw 로 **흉내 낸다**. kbap 의 통합 테스트는 흉내 내지 않고 **진짜 MySQL 을 도커로 띄운다.**

```kotlin
@SpringBootTest
@AutoConfigureMockMvc
@Import(MySqlContainerConfig::class)
class OrderControllerTest : BehaviorSpec() {
    override fun extensions() = listOf(SpringExtension)

    @Autowired
    private lateinit var mockMvc: MockMvc

    @Autowired
    private lateinit var dataSource: DataSource
```
`api/src/test/kotlin/com/kbap/api/order/OrderControllerTest.kt:22-34`

- `@SpringBootTest` — 앱을 **통째로 부팅한다.** [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] 의 그 컨테이너가 실제로 뜨고, 모든 빈이 조립된다.
- `@Import(MySqlContainerConfig::class)` — 테스트가 시작될 때 **도커로 MySQL 8.4 컨테이너를 띄우고**, 끝나면 지운다. 그 설정 클래스는 `common` 모듈의 testFixtures 에 한 벌만 있다(`common/src/testFixtures/kotlin/com/kbap/common/core/testsupport/MySqlContainerConfig.kt`).
- `override fun extensions() = listOf(SpringExtension)` — Kotest 와 Spring 을 잇는 다리. 이게 있어야 `@Autowired` 가 동작한다. 앞의 `OrderItemTest` 는 `BehaviorSpec({ … })` 생성자 스타일이었는데 여기는 `BehaviorSpec()` + `init { }` 본문 스타일인 것도 이 때문이다 — 필드에 빈을 주입받아야 하니 클래스 본문이 필요하다.
- `mockMvc` — 서버를 진짜 포트에 띄우지 않고 HTTP 요청/응답만 흉내 내는 스프링 도구. 컨트롤러부터 DB 까지는 전부 진짜로 돈다.

**왜 H2 같은 가짜 DB 를 안 쓰나?** 방언이 다르기 때문이다. H2 에서 통과한 SQL 이 MySQL 에서 깨지면 테스트가 아무 도움이 안 된다. 게다가 kbap 의 테스트 설정은 **Flyway 를 켜서 운영과 똑같은 마이그레이션 49개를 실제로 적용한 뒤**, Hibernate `ddl-auto=validate` 로 엔티티↔스키마 정합까지 검사한다(`api/src/test/resources/application.yml`) — [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] 가 말한 "테스트도 같은 마이그레이션을 쓴다"가 이 얘기다.

> [!tip] 아키텍처 테스트만 빼고 돌리기
> ArchUnit 스펙은 Kotest 태그 `arch` 가 붙어 있어서 `-Dkotest.tags="!arch"` 로 제외할 수 있다(`CLAUDE.md:85`). 규칙의 내용은 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 에 있다.

## 6. 커버리지 — 무엇을 세지 않기로 했나

**jacoco** 가 커버리지를 잰다. `jest --coverage` 와 같은 역할이고, 모듈 3개(`:common`·`:api`·`:batch`)의 결과를 한 리포트로 합친다.

```kotlin
tasks.named<JacocoReport>("testCodeCoverageReport") {
    val originalClassDirs = classDirectories.files.toList()
    classDirectories.setFrom(
        originalClassDirs.map {
            fileTree(it) {
                exclude(
                    "**/KbapApiApplication*",
                    "**/KbapBatchApplication*",
                    "**/*JpaEntity*",
                )
            }
        },
    )
}
```
`build.gradle.kts:31-44` (루트)

- `id("jacoco-report-aggregation")` + `jacocoAggregation(project(":common"|":api"|":batch"))` (`build.gradle.kts:2-21`) — 세 모듈의 커버리지를 **모아서 한 장으로** 낸다. 모듈이 3개라 각각 보면 그림이 안 잡힌다.
- `exclude("**/KbapApiApplication*")` · `("**/KbapBatchApplication*")` — 두 개의 **부트 진입점**이다. `fun main(args) { runApplication<…>(args) }` 한 줄뿐이라 여기에 테스트를 쓰는 건 의미가 없는데, 세는 대상에 넣어 두면 **커버리지 숫자만 깎는다.** 숫자가 이유 없이 낮으면 사람이 그 숫자를 무시하게 되고, 그러면 지표 자체가 죽는다.
- `exclude("**/*JpaEntity*")` — 이름에 `JpaEntity` 가 들어간 클래스. **다만 지금 레포에 그런 이름의 파일은 하나도 없다** — 엔티티는 `Food`·`Order` 처럼 도메인 이름 그대로고, `JpaRepository` 접미사가 붙는 건 리포지토리 쪽이다. 즉 이 줄은 **엔티티와 도메인 모델을 분리하던 옛 구조의 잔재**다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 가 말하는 그 개편 이전). 지금은 아무것도 제외하지 않는 죽은 줄이다.

> [!note] 실측이 계획과 어긋난 지점
> 재구축 계획서는 `*JpaEntity*` 를 "제외 대상"으로 적었고 설정에도 그렇게 들어 있지만, **매칭되는 클래스가 0개**다. 이 노트는 설정이 아니라 실제 매칭 결과를 기준으로 쓴다.

**커버리지 숫자를 목표로 삼지 않는다**는 점도 같이 기억하자. 헌법 어디에도 "커버리지 N% 이상"은 없다. 원칙 I 이 요구하는 건 비율이 아니라 **순서**(테스트 먼저)다. 커버리지는 "빠뜨린 데가 있나" 를 찾는 지도이지 점수가 아니다.

## 7. ⚠️ AI 에이전트와 함께 개발하는 방식이 바뀐 이력

여기부터는 kbap 이라는 레포가 **Claude Code 로 개발된다**는 사실에 얽힌 얘기다. 이 노트를 읽는 사람이 직접 하네스를 설계·운영하는 사람이라 특히 값진 교훈이 하나 있다.

### 무엇이 있었고, 무엇이 없어졌나

kbap 은 한동안 **멀티에이전트 TDD 하네스**로 구현 단계를 돌렸다. 오케스트레이터 하나가 테스트 작성 에이전트와 구현 에이전트를 각각 띄우는 구조다:

```text
tdd-harness-orchestrator
    ├── test-writer   → 실패하는 테스트를 쓴다 (Red)
    └── implementer   → 그 테스트를 통과시킨다 (Green)
```

원칙 I 을 **에이전트 분업으로 물리적으로 강제**하려는 설계다. 테스트 쓰는 놈과 구현하는 놈이 다르니 순서를 어길 수가 없다. 아이디어로는 깔끔하다.

**이 하네스는 2026-08-14 제거됐다.** 레포 `CLAUDE.md` 의 맨 첫 절이 그 사실과 이유를 명시한다:

```markdown
## 구현 방식

구현(`/speckit-implement`·tasks.md 진행·단발 수정)은 **메인 세션이 직접 수행**한다 —
멀티에이전트 TDD 하네스(tdd-harness-orchestrator·test-writer·implementer)는 2026-08-14
제거했다(구현 단계가 느려지고 과한 코드가 나오는 문제). 헌법 원칙 I(Test-First:
Red→Green→Refactor)은 그대로 유효하며 직접 구현에서 지킨다. 리뷰는 필요할 때만
`kbap-code-review`·`kbap-db-review` 스킬(에이전트: code-reviewer·database-expert)을 명시 호출한다.
```
`CLAUDE.md:7` (레포 루트, 문서의 **가장 첫 절**)

### 지금의 방식

| | 옛 방식 (~2026-08-14) | 지금 방식 |
|---|---|---|
| 구현 | test-writer → implementer 서브에이전트 팀 | **메인 세션이 직접** |
| 원칙 I 강제 수단 | 에이전트 분업 (구조로 강제) | `tasks.md` 의 `[Red]` 딱지와 작업 순서 (문서로 강제) |
| 리뷰 | 파이프라인에 상시 포함 | **필요할 때만 명시 호출** — `kbap-code-review`·`kbap-db-review` 스킬 |
| 원칙 I 자체 | 유효 | **그대로 유효** |

레포에 실제로 남아 있는 것을 확인해 보면 이 표가 사실임을 알 수 있다 — `.claude/agents/` 에는 `code-reviewer.md`·`database-expert.md` **둘뿐**이고(리뷰 전용), `tdd-harness-orchestrator`·`test-writer`·`implementer` 는 없다. `.claude/skills/` 에는 speckit-* 명령 9개와 `kbap-code-review`·`kbap-db-review` 가 있다.

### 왜 이게 값진 교훈인가

제거 사유가 **두 가지**로 적혀 있고, 둘 다 하네스 설계 일반에 적용된다.

1. **"구현 단계가 느려지고"** — 서브에이전트는 컨텍스트를 물려받지 못한다. 메인 세션이 이미 읽은 파일·이미 파악한 규약을 각 에이전트가 처음부터 다시 읽어야 한다. 조사·탐색이 대부분인 작업(리서치·전수 검색)에서는 이 비용을 병렬화 이득이 덮지만, **구현은 이미 맥락이 다 잡힌 상태에서 파일 몇 개를 고치는 일**이라 덮을 이득이 없다.
2. **"과한 코드가 나오는 문제"** — 이게 더 미묘하다. implementer 에이전트는 **자기가 쓴 테스트가 아니라 남이 던진 테스트**를 받는다. 전체 그림을 모르니 "이 테스트를 통과시키는 최소 구현"의 최소가 어디인지 판단할 근거가 없고, 안전하게 가려고 방어 코드·추상화·확장 지점을 얹는다. TDD 의 Green 단계가 요구하는 건 **최소** 구현인데, 분업이 바로 그 최소 판단을 못 하게 만든 셈이다.

한 줄로 줄이면 이렇다:

> **에이전트를 나누는 것 자체가 이득이 아니다.** 나눔이 값을 하려면 (a) 나눈 조각들이 서로의 맥락을 크게 필요로 하지 않아야 하고, (b) 병렬로 돌아 시간을 벌어야 한다. 구현은 둘 다 아니었다. 반대로 **리뷰**는 둘 다 맞다 — 리뷰어는 구현자의 사고 과정을 물려받지 **않는 편이 낫고**, 사람이 원할 때만 부르면 되니 파이프라인을 늦추지 않는다. 그래서 리뷰만 에이전트로 남았다.

에이전트를 걷어냈어도 **규칙은 그대로 남았다**는 점이 마지막 포인트다. 원칙 I 은 여전히 NON-NEGOTIABLE 이고, `tasks.md` 의 `[Red]` 딱지도 그대로다. **강제 수단(하네스)과 규칙(헌법)을 분리해 뒀기 때문에 수단만 갈아치울 수 있었다.** 규칙이 하네스 코드 안에만 있었다면 하네스를 지우는 순간 규칙도 사라졌을 것이다.

> [!warning] 볼트의 옛 노트와 어긋남
> [[2. 행동을 다듬는 장치 — 훅·투두·서브에이전트·스킬]] 과 [[5. 여러 에이전트의 협업]] 은 kbap 을 "test-writer → implementer 팀으로 TDD 를 굴리는 사례"로 인용하고 있다. **그건 2026-08-14 이전의 사실이다.** 지금 기준은 이 절이다.

### 곁가지 — FE 쪽의 같은 장치

같은 팀의 `spec` 레포에도 문서로 흐름을 못 박는 규약이 있다 — `bridge/PROMPTS.md`·`REPORTS.md`·`QA.md`. 지시를 문서로 남기고, 결과를 문서로 받고, 검수를 문서로 쌓는 구조다. **"오가는 것을 레포 안 문서로 만든다"** 는 발상은 SpecKit 의 `specs/` 와 같다.

## 10. 용어집

- **SDD (Spec-Driven Development)** — 구현 전 스펙 문서를 단일 출처로 확정하고 개발하는 방식.
- **SpecKit** — GitHub 의 SDD 도구. `spec → plan → tasks → implement` 를 명령과 템플릿으로 강제한다.
- **헌법 (constitution)** — 레포가 절대 어기지 않기로 한 원칙 문서. SemVer 로 버전 관리되며 개정 이력이 파일에 남는다. kbap 현재 v7.0.0.
- **Constitution Check** — `plan.md` 안의 게이트 표. 원칙마다 PASS/N/A 와 근거를 적어야 다음 단계로 간다.
- **TDD** — 실패 테스트 → 최소 구현 → 리팩터 순서로 개발하는 방식.
- **Red / Green / Refactor** — 각각 실패 확인 / 통과시키는 최소 구현 / 초록 유지한 채 정리.
- **Kotest** — Kotlin 테스트 프레임워크(Jest 위치). `shouldBe`·`shouldThrow` 등의 단정 함수를 제공.
- **BehaviorSpec** — Kotest 의 BDD 스타일. given → when → then 3단 중첩. kbap 의 **유일한** 테스트 스타일.
- **`` `when` ``** — Kotlin 예약어라 백틱으로 감싸 식별자로 쓴다. Kotest 는 대문자 `When` 별칭도 제공하지만 kbap 은 백틱 쪽으로 통일.
- **Testcontainers** — 테스트 중 도커 컨테이너(여기선 MySQL 8.4)를 띄웠다 지우는 라이브러리.
- **`@SpringBootTest`** — 앱 전체를 부팅하고 도는 통합 테스트 애너테이션.
- **MockMvc** — 실제 포트를 열지 않고 HTTP 요청/응답을 흉내 내는 스프링 테스트 도구.
- **jacoco** — JVM 커버리지 측정 도구.
- **`[P]` / `[Red]`** — `tasks.md` 의 딱지. 각각 병렬 가능 / 테스트를 먼저 쓰고 실패 확인.
