# 4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다

> 작성: 2026-08-26 · 맥락: kbap-server 아무 클래스나 열면 `@Service` 와 생성자 파라미터부터 나온다. `new` 가 한 번도 안 보이는 이유를 먼저 알아야 그 아래가 읽힌다.
> 기준: kbap-server 실측 2026-08-26 · Spring Boot 4.1.0 / Kotlin 2.3.21 (`gradle/libs.versions.toml:3-4`)

---

## 0. 한 줄 요약

**부품(객체)을 내가 `new` 로 만들지 않고, 스프링 컨테이너가 앱 시작할 때 전부 만들어 서로 꽂아준다.** 내가 하는 일은 "나는 이런 부품이 필요하다"를 **생성자 파라미터로 선언**하는 것뿐이다.

---

## 1. 핵심 개념

| 용어 | 정체 | FE에서 가장 가까운 것 (완전 동치 아님) |
|---|---|---|
| **IoC** (Inversion of Control) | 객체를 만들고 연결하는 **제어권이 내 코드에서 프레임워크로 넘어간 것** | 라우터가 내 화면 컴포넌트를 언제 렌더할지 정하는 것 — 내가 `render()` 를 부르지 않는다 |
| **IoC 컨테이너** / `ApplicationContext` | 앱 시작 때 객체들을 만들고·조립하고·수명을 관리하는 스프링의 창고 | 루트에서 Provider들을 다 조립해둔 트리 |
| **빈(Bean)** | 그 컨테이너가 만들고 관리하는 객체 하나 | Provider가 `value` 로 들고 있는 인스턴스 |
| **DI** (의존성 주입) | 필요한 부품을 **밖에서 넣어주는 것** | props / `useContext` 로 의존을 내려받기 |
| **생성자 주입** | 생성자 파라미터로 의존을 받는 DI 방식. 스프링 공식 권장 | 함수 인자로 의존을 넘기는 것 (`createApi(fetcher)`) |
| **스코프** | 빈을 몇 개 만들지. 기본값 **singleton** = 컨테이너당 딱 하나 | 앱 전체가 공유하는 모듈 스코프 싱글턴 |

> 스프링 공식 정의: 빈은 *"IoC 컨테이너가 인스턴스화하고, 조립하고, 관리하는 객체. 그렇지 않으면 그저 앱 안의 수많은 객체 중 하나일 뿐"*.

## 2. 원리 — "내가 만들지 않는다"가 정확히 무슨 뜻인가

### 2-1. FE에서 우리가 하던 것

```ts
// 예시 (kbap-server 코드 아님)
class ApiClient {
  constructor(private baseUrl: string) {}
}

class MemberService {
  private api = new ApiClient("https://api.kbap.app")   // ← 내가 직접 만든다
  private storage = AsyncStorage                        // ← 내가 직접 고른다
}
```

`MemberService` 가 **자기 부품을 스스로 고르고 만든다.** 테스트에서 `ApiClient` 를 가짜로 바꾸려면 `MemberService` 코드를 고쳐야 한다. 이게 "제어권이 내 안에 있는" 상태다.

### 2-2. 스프링에서는

```kotlin
// 예시 (형태만 보여주는 코드)
@Service
class MemberService(
    private val memberRepository: MemberJpaRepository,   // ← "이게 필요하다"고 선언만
)
```

`new` 가 없다. `MemberService` 는 `MemberJpaRepository` 를 **어디서 구해오는지 모른다.** 앱이 뜰 때 컨테이너가

1. `com.kbap` 패키지 아래를 훑어서 `@Service`·`@Component`·`@RestController`·`@Configuration` 붙은 클래스를 찾고 (**컴포넌트 스캔**),
2. 각 클래스의 **생성자 파라미터 타입**을 보고 "이 타입의 빈이 창고에 있나?" 를 찾고,
3. 없으면 그 빈부터 먼저 만들고, 있으면 꺼내서 넣고,
4. 그렇게 만든 객체를 창고에 넣어둔다.

이 순서를 컨테이너가 알아서 푼다. 그래서 **"의존성 주입"** 이고, 제어가 뒤집혔다고 해서 **"제어의 역전(IoC)"** 이다.

### 2-3. Kotlin에서는 생성자 파라미터가 곧 주입이다

Kotlin의 `class X(private val a: A)` 는 **주 생성자(primary constructor)** 선언이자 필드 선언이다. 그리고 스프링 공식 문서는 이렇게 못박는다 —

> *"대상 빈이 생성자를 하나만 정의한다면 그 생성자에 `@Autowired` 를 붙일 필요가 없다."*

kbap-server의 모든 빈은 생성자가 하나뿐이다. 그래서 **프로덕션 코드에 `@Autowired` 가 단 한 개도 없다** (실측: `api/src/main`·`common/src/main`·`batch/src/main` 전체에서 `@Autowired` 0건). Kotlin에서 DI 코드는 그냥 "생성자 파라미터를 쓴다"로 끝난다.

---

## 3. 비유 — React 루트의 Provider 조립, 그리고 그 비유의 한계

FE에서 앱 루트는 이렇게 생겼다.

```tsx
// 예시
<QueryClientProvider client={queryClient}>
  <AuthProvider>
    <App />        {/* 안쪽 어디서든 useAuth() 로 꺼내 쓴다 */}
  </AuthProvider>
</QueryClientProvider>
```

- 루트에서 **한 번 조립**해두고, 하위 컴포넌트는 `useContext` 로 **꺼내 쓰기만** 한다 → 컨테이너가 앱 시작 때 빈을 다 만들고, 각 클래스는 생성자로 받아 쓰기만 한다.
- 조립을 바꾸면(`client={mockClient}`) 하위 코드를 안 고치고 동작이 바뀐다 → `@Configuration` 에서 어떤 구현을 꽂을지 바꾸면 서비스 코드를 안 고치고 바뀐다.

> [!warning] 비유가 깨지는 지점 — 반드시 알고 넘어갈 것
> 1. **수명이 다르다.** Provider의 값은 **렌더 트리에 묶여** 있다. 화면이 언마운트되면 사라지고, 다시 마운트되면 새로 생긴다. 스프링 빈은 **앱 프로세스가 사는 동안 딱 하나**다. 요청이 만 번 와도 `MemberService` 인스턴스는 그 하나다.
> 2. **범위가 없다.** Provider는 트리 위치에 따라 다른 값을 줄 수 있다(같은 Context를 두 군데서 다르게 감싸기). 스프링 기본 스코프에는 그런 게 없다 — **타입 하나에 빈 하나**가 원칙이고, 같은 타입 빈이 둘이면 오히려 시작이 실패한다.
> 3. **꺼내 쓰는 방향이 반대다.** `useContext` 는 **내가 능동적으로 꺼낸다**(서비스 로케이터). 생성자 주입은 **밖에서 넣어준다**. 그래서 스프링 쪽은 "이 클래스가 무엇에 의존하는지"가 생성자 시그니처만 보면 전부 드러난다.

## 4. 실코드 — kbap-server에서 빈이 만들어지는 세 가지 자리

### 4-1. 스캔 범위: 어디까지가 창고인가

```kotlin

@SpringBootApplication
class KbapApiApplication

fun main(args: Array<String>) {
	runApplication<KbapApiApplication>(*args)
}
```
`api/src/main/kotlin/com/kbap/KbapApiApplication.kt:1-11`

- **1줄**: 패키지가 `com.kbap` — 이게 전부다. `@SpringBootApplication` 은 **자기 패키지와 그 하위 전부**를 스캔하므로, `com.kbap.api.*` 도 `com.kbap.common.*` 도 다 스캔 대상이다. 이 클래스를 일부러 최상위 패키지에 둔 이유가 그것이다.
- **10줄**: `runApplication` 이 컨테이너를 띄우고, 빈을 전부 만들고, 톰캣을 열고, 그대로 서 있는다.

> [!note] 배치 앱은 창고를 좁힌다
> 두 번째 실행 파일인 배치는 스캔 범위를 명시적으로 잘라둔다 — `@SpringBootApplication(scanBasePackages = ["com.kbap.batch", "com.kbap.common.infra.llm"])` (`batch/src/main/kotlin/com/kbap/batch/KbapBatchApplication.kt:7`). 즉 배치 프로세스에는 `com.kbap.api.*` 의 컨트롤러·서비스 빈이 **아예 존재하지 않는다.** 같은 코드베이스지만 뜨는 빈이 다르다. 배치 앱의 골격은 뒤쪽 노트("배치 앱의 골격 — Spring Batch 잡·트리거·스케줄", 26번)에서 따로 다룬다.

### 4-3. 직접 조립하는 자리 — `@Configuration` + `@Bean`

`@Service` 는 "이 클래스를 스캔해서 만들어라"다. 그런데 **내가 만들지 않은 클래스**(외부 SDK)나 **어떤 구현을 쓸지 조건에 따라 골라야 하는 것**은 그 방식이 안 된다. 그때 쓰는 게 `@Configuration` 클래스 안의 `@Bean` 메서드다 — **"이 메서드의 반환값을 빈으로 등록해라"**.

```kotlin
@Configuration
class AuthConfig {
    @Bean
    fun socialTokenVerifier(
        @Value("\${kbap.auth.firebase.credentials-json:}") credentialsJson: String,
        @Value("\${kbap.auth.firebase.credentials-path:}") credentialsPath: String,
    ): SocialTokenVerifier {
        val verifier = FirebaseSocialAuth.tokenVerifierOrNull(credentialsJson, credentialsPath)
        if (verifier == null) {
            log.warn("Firebase 자격증명 미설정 — 소셜 로그인 비활성(모든 로그인이 401 로 거절된다)")
            return UnavailableSocialAuth
        }
        return verifier
    }
}
```
`api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:14-37` (중략 있음)

- **반환 타입이 `SocialTokenVerifier`(인터페이스)** 라는 게 핵심이다. 창고에 등록되는 **이름표는 인터페이스**이고, 실제 알맹이는 `FirebaseSocialAuth` 일 수도 `UnavailableSocialAuth` 일 수도 있다.
- **30~34줄**: 자격증명이 없으면 "항상 실패하는 구현"을 대신 꽂는다. `AuthService` 코드는 한 글자도 안 바뀐다. **조립을 바꿔서 동작을 바꾼 것.** 이게 DI로 얻는 실익이다.
- `@Bean` 메서드의 **파라미터도 주입 지점**이다. 여기선 `@Value` 로 설정값을 받았지만, 다른 빈 타입을 적으면 그 빈이 들어온다.

`api/src/main/kotlin/com/kbap/api/core/config/` 아래에는 이런 조립 클래스가 9개 있다 — `AuthConfig` · `BackgroundConfig` · `ExchangeConfig` · `FoodVectorConfig` · `OpenApiConfig` · `PlaceConfig` · `PropertiesConfig` · `StorageConfig` · `WebConfig`. **"뭐가 뭐에 꽂히는지 궁금하면 여기부터 연다."**

```kotlin
        redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
    }
```

## 5. 스코프 — 기본은 싱글턴, 그래서 빈은 상태를 가지면 안 된다

스프링 빈의 기본 스코프는 **singleton**이다. 공식 문서 표현으로 *"컨테이너는 그 빈 정의에 대해 정확히 하나의 인스턴스를 만들고, 이후 모든 요청은 캐시된 그 객체를 돌려받는다."*

싱글턴이라는 말이 조용히 함의하는 것이 하나 있다.

> [!danger] 빈은 여러 스레드가 **동시에** 들어온다
> 서버는 요청 하나에 스레드 하나를 붙인다. `MemberService` 인스턴스는 하나뿐이므로, 요청 200개가 동시에 오면 **같은 객체의 메서드를 200개 스레드가 동시에 실행**한다. 여기서 빈이 필드에 값을 들고 있으면 요청끼리 값이 섞인다.
> **규칙: 빈의 필드는 전부 `val`(불변)이어야 한다. 요청마다 달라지는 값은 필드가 아니라 메서드 파라미터·지역 변수로 흘린다.**

kbap-server는 이 규칙을 지키고 있다 — **`@Service`·`@Component` 가 붙은 클래스 전체에서 필드 레벨 `var` 는 0개**다(실측). 4-2의 `imagePublicBaseUrl` 처럼 필드에 값이 있는 경우도 있지만 그건 **앱 수명 내내 안 변하는 설정값**이라 안전하다.

FE 감각으로 옮기면: 모듈 최상단에 `let currentUser` 를 두고 화면마다 덮어쓰는 것과 같은 실수다. 브라우저에선 사용자가 한 명이라 티가 안 나지만, 서버에선 이게 곧 **다른 사람 데이터가 보이는 사고**다.

| 스코프 | 인스턴스 개수 | kbap에서 |
|---|---|---|
| `singleton` (기본) | 컨테이너당 1개 | 전부 이것 |
| `prototype` | 주입될 때마다 새로 | 안 씀 |
| `request` / `session` | HTTP 요청·세션마다 | 안 씀 |

kbap-server 프로덕션 코드에 `@Scope` 는 등장하지 않는다. **"전부 싱글턴"** 이라고 읽으면 된다.

## 6. 왜 생성자 주입인가 — 필드 주입과의 대비

옛 스프링 코드나 튜토리얼에서 이런 걸 본다.

```java
// 예시 (kbap-server에는 없는 형태)
@Service
public class MemberService {
    @Autowired
    private MemberJpaRepository memberRepository;   // 필드 주입
}
```

동작은 한다. 그런데 스프링 팀은 생성자 주입을 권장한다 — *"애플리케이션 컴포넌트를 불변 객체로 구현할 수 있게 해주고, 필수 의존이 `null` 이 아님을 보장하며, 완전히 초기화된 상태로 호출부에 돌아가기 때문"*.

| | 필드 주입 (`@Autowired` 필드) | 생성자 주입 (kbap) |
|---|---|---|
| 불변성 | 필드가 `var` 여야 해서 나중에 바꿔치기 가능 | `val` 로 고정 |
| null 보장 | 컨테이너가 채우기 전엔 null | 생성 시점에 이미 다 채워짐. Kotlin 널 안전과도 맞물림 |
| 의존 목록 | 클래스 전체를 훑어야 보임 | **생성자 한 줄에 다 있음** |
| 숨은 복잡도 | 의존 10개를 넣어도 티가 안 남 | 생성자가 길어져서 바로 눈에 띔 |
| 테스트 | 스프링을 띄우거나 리플렉션으로 꽂아야 함 | **그냥 `MemberService(fakeRepo, "")` 로 만든다** |

마지막 줄이 FE 감각과 정확히 이어진다. TS에서 우리가 이렇게 쓰는 이유와 같다.

```ts
// 예시
export function createScanService(fetcher: Fetcher, storage: Storage) { ... }
// 테스트: createScanService(fakeFetcher, memoryStorage)
```

**의존을 인자로 받으면 테스트가 인자만 바꾸면 된다.** 생성자 주입은 이걸 클래스 문법으로 하는 것뿐이다.

### 6-1. 테스트에서 가짜를 꽂는 실물

통합 테스트에서는 스프링을 띄우되 **조립만 바꿔 끼운다.**

```kotlin
@Configuration
class FakePresignedUploadPortConfig {
    @Bean
    fun fakePresignedUploadPort(): PresignedUploadPort =
        object : PresignedUploadPort {
            override fun issue(key: String, contentType: String, contentLength: Long, ttl: Duration): PresignedUpload =
                PresignedUpload(
                    uploadUrl = "https://s3.example/$key?sig=test",
                    ...
                )
        }
}
```
`api/src/test/kotlin/com/kbap/api/image/FakePresignedUploadPortConfig.kt:12-25` (중략 있음)

- **테스트 소스셋에 있는 `@Configuration`** 이다. 테스트로 앱을 띄우면 이 조립이 들어가서, 실제 S3를 부르는 빈 자리에 가짜가 앉는다.
- 진짜 `StorageConfig` 는 §4-3의 `@ConditionalOnProperty` 로 꺼져 있어 **같은 타입 빈이 둘이 되는 충돌이 안 난다.** 조건이 조립을 비워두고, 테스트 조립이 그 자리를 채우는 짝이다.
- **테스트 대상 코드는 한 줄도 안 고쳤다.** 이게 DI가 사주는 것 전부다.

> [!note] 테스트에는 `@Autowired` 가 269개 있다
> 프로덕션 0개, 테스트 269개다. 모순이 아니다 — 테스트 클래스는 **내가 생성자를 통제하지 못한다**(JUnit/Kotest가 인스턴스를 만든다). 그래서 필드 주입 말고 방법이 없다. "필드 주입은 나쁘다"가 아니라 **"내가 생성자를 쓸 수 있는 곳에서는 생성자를 쓴다"** 가 규칙이다.

## 7. 주의점 / 자주 터지는 것

- **`NoSuchBeanDefinitionException`** — 필요한 타입의 빈이 창고에 없다. 원인 3순위: ① 클래스에 `@Service`/`@Component` 를 안 붙였다 ② 스캔 범위(`com.kbap`) 밖에 뒀다 ③ `@ConditionalOnProperty` 조건이 안 맞아 그 빈이 안 만들어졌다.
- **`NoUniqueBeanDefinitionException`** — 같은 타입 빈이 둘이라 뭘 꽂을지 모른다. `@Primary` 로 기본을 정하거나 `@Qualifier` 로 이름을 지정한다.
- **순환 의존** — A가 B를, B가 A를 생성자로 요구하면 컨테이너가 순서를 못 정하고 **앱이 아예 안 뜬다**. 필드 주입은 이걸 조용히 넘겨서 런타임에 터지지만, 생성자 주입은 **시작할 때 실패한다.** 불편해 보여도 이게 이득이다 — 설계가 꼬였다는 신호를 배포 전에 받는 것.
- **빈 안에서 `new` 로 다른 빈을 만들면 그건 빈이 아니다.** 트랜잭션·프록시가 안 붙어서 `@Transactional` 같은 게 조용히 무시된다.
- **`@Value` 오타는 시작할 때 터진다** — 기본값(`:` 뒤)이 없는 키가 설정에 없으면 앱이 안 뜬다.
- 실패 로그를 볼 땐 스택트레이스 맨 아래가 아니라 **`***************************` 로 시작하는 `APPLICATION FAILED TO START` 블록**을 먼저 읽는다. 스프링이 원인과 조치를 한국어 아닌 영어로 친절히 요약해준다.

```kotlin
// 빈 등록 — 셋 중 하나
@Service        class FooService(private val bar: Bar)     // 업무 로직

class A(private val b: B, @Value("\${key:기본값}") private val k: String)

// 빈이 둘일 때
@Primary        // 기본으로 이걸 써라

@ConditionalOnProperty(prefix = "kbap.storage", name = ["enabled"], havingValue = "true")
```

## 9. 용어집

- **IoC (Inversion of Control)**: 객체 생성·연결의 제어권이 내 코드에서 프레임워크로 넘어간 것.
- **IoC 컨테이너 / `ApplicationContext`**: 빈을 만들고 조립하고 수명을 관리하는 스프링의 객체 창고. `BeanFactory` 의 상위 인터페이스로, 실무에선 사실상 이것만 쓴다.
- **빈(Bean)**: 컨테이너가 만들고 관리하는 객체.
- **DI (Dependency Injection)**: 필요한 부품을 밖에서 넣어주는 것. IoC를 실현하는 구체적 방법.
- **생성자 주입**: 생성자 파라미터로 의존을 받는 DI 방식. 스프링 공식 권장이자 kbap의 유일한 방식.
- **컴포넌트 스캔**: 지정한 패키지 아래를 훑어 `@Component` 계열 클래스를 빈으로 등록하는 것.
- **스테레오타입 애너테이션**: `@Component`(원형) / `@Service` / `@RestController` / `@Repository`. 기능은 대체로 같고 **역할을 알리는 이름표**다.
- **스코프**: 빈을 몇 개 만들지. 기본 `singleton`.
- **`@Primary` / `@Qualifier`**: 같은 타입 빈이 여럿일 때 뭘 꽂을지 정하는 표시.
- **`@ConditionalOnProperty`**: 설정값이 맞을 때만 그 빈을 만드는 조건.
