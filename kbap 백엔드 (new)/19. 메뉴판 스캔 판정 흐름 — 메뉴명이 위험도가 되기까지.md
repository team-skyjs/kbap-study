# 19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지

> 작성: 2026-08-27 · 맥락: 18번까지는 **남이 쓴 서버 코드**를 읽는 일이었다. 이 노트는 다르다 — 이 API 의 **요청 본문을 만드는 코드를 당신이 직접 썼다.** kbap-fe 의 `segmentMenu.ts` 가 묶은 박스, `classifyLine.ts` 가 골라낸 라인이 그대로 `items[]` 가 되어 여기로 온다. 그러니 이 노트는 "서버가 뭘 하나"가 아니라 **"내가 보낸 것이 서버에서 무엇이 되는가"** 를 읽는 노트다.
> 목표: `POST /api/scans` 한 번이 비전 인식 → 이름 정규화 → 음식 카탈로그 매칭 → 위험도 판정 → 이력 기록까지 어떻게 흐르는지 파일·줄 단위로 말할 수 있게 되고, **위험도가 실제로 무엇을 기준으로 계산되는지**(FE 가 화면에 그리는 그 값) 정확히 설명할 수 있게 되기.

---

## 0. 한 줄 요약

`POST /api/scans?lang=ko` 에 **이미지 경로 하나 + FE OCR 후보 목록**을 실어 보내면, 서버는 그 사진을 **비전 모델로 다시 읽어** 메뉴명·가격을 뽑고, 뽑은 한국어 이름을 **한글만 남긴 매칭 키**로 정규화해 음식 카탈로그와 대조한 뒤, 매칭된 음식의 **성분 함유 확률**과 회원의 **기피 성분**을 겹쳐 `SAFE`/`CAUTION`/`DANGER` 를 계산해 돌려준다. 처음 보는 메뉴는 그 자리에서 **조사 대기 상태로 등록**되고 `UNKNOWN` 으로 나간다. 그리고 이 흐름 전체에 **트랜잭션이 하나도 걸려 있지 않다** — 왜 그런지가 이 노트의 절반이다.

---

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 |
|---|---|---|
| **recall / precision** | recall = 놓치지 않고 다 줍기, precision = 주운 것 중 진짜만 남기기 | FE 가 후보를 넉넉히 긁고(recall), BE 가 카탈로그로 걸러 확정한다(precision). 이 API 의 설계 원리 자체 |
| **매칭 키 (match key)** | 표기 흔들림을 지운, 대조 전용으로 만든 문자열 | `slugify()` 와 같은 자리 — 보여주는 문자열과 **비교하는 문자열을 분리**한다 |
| **표시명 / 정규화명** | `display_name`(사람에게 보여줄 원본 표기) vs `korean_name`(대조용 매칭 키) | 같은 데이터의 "렌더용 값"과 "키" 를 따로 들고 있는 것 |
| **함유 확률 (`inclusion_percent`)** | "이 음식에 이 성분이 들어 있을 확률" 1~100 | 없음. 백엔드가 LLM 으로 추정해 넣어둔 값이고, 위험도의 **유일한** 입력이다 |
| **조사 대기 등록 (upsert incomplete)** | 처음 본 메뉴를 빈 껍데기로 먼저 만들어 두고, 내용은 나중에 채우는 것 | 낙관적 UI 로 껍데기 항목을 먼저 넣고 서버 응답을 기다리는 것 — 단, 여기선 **DB 에 실제로 행이 생긴다** |
| **동결 계약 (frozen contract)** | 옛 버전 응답 모양을 **일부러 그대로 두는** 것 | 구버전 앱이 스토어에 남아 있는 한 지워선 안 되는 API. 21번 대신 **20번**에 새 필드가 붙는 이유 |

## 2. 이 API 가 하는 일 — 사용자 관점 한 줄

> 식당에서 메뉴판을 찍으면, 각 메뉴 위에 **내 기피 성분 기준의 색깔 표시**가 뜬다.

그런데 이 문장에서 "찍으면" 과 "뜬다" 사이에 **당신이 쓴 코드가 이미 한 겹 들어가 있다.** 그 이음매부터 본다.

---

## 3. 이음매 — FE 가 recall 로 뽑고, 서버가 precision 으로 확정한다

### 3-1. 당신이 겪은 사고의 답이 이 API 다

[[OCR 라인 분류 — 휴리스틱의 한계와 대안]] 에서 정규식 분류기가 무너진 실사고(KB-72)를 정리하면서, 그 노트는 이렇게 결론지었다 — **"김치찌개인지 판별하는 최고의 방법은 김치찌개처럼 생겼는지 재는 게 아니라, 김치찌개 목록에 있는지 찾아보는 것"**.

그 "목록에 있는지 찾아보는 것"이 서버에서 실제로 구현된 자리가 `ScanService.resolveFoods` 다. 즉 이 노트는 그 노트가 예고한 **2단 precision 의 구현체**를 읽는 것이다.

### 3-2. 세 겹의 책임 분담 (실측)

| 단계 | 어디서 | 무엇을 | 목표 |
|---|---|---|---|
| ① 라인 추출·분류·그룹핑 | **kbap-fe** (`classifyLine.ts`·`segmentMenu.ts`) | 박스를 묶어 `{ itemId, rawMenuName, box }` 후보를 만든다 | **recall** — 놓치지 말고 다 줍는다. 노이즈가 섞여도 된다 |
| ② 사진 재해석 | **서버**, 비전 모델 (`MenuBoardVisionExtractor`) | 같은 사진을 다시 읽어 메뉴명·표준 한국어명·가격을 뽑고, ①의 `idx` 에 매칭한다 | 메뉴가 **아닌** 텍스트(상호·원산지·영업시간)를 여기서 버린다 |
| ③ 카탈로그 대조·판정 | **서버**, `ScanService` | 표준 한국어명을 매칭 키로 정규화해 `food` 테이블과 대조하고 위험도를 계산 | **precision** — 카탈로그에 있는 것만 단언한다 |

> [!important] 여기가 이 노트의 핵심 한 줄
> **FE 는 "이런 후보들이 있다"고 주장하고, 서버는 "이건 김치찌개다"라고 단언한다.** FE 의 OCR 이 `"김치피개"` 처럼 깨져도 상관없다 — 서버 비전이 사진을 다시 읽어 `koreanName = "김치찌개"` 를 만들고, FE 가 보낸 `idx` 는 **"응답을 화면 어느 박스 위에 그릴지"** 를 잇는 실 한 가닥으로만 쓰인다.

`ScanApi.kt:29` 의 문서 문장이 이 계약을 그대로 못박아 둔다.

```kotlin
2. 각 추출 메뉴를 클라이언트 OCR 항목(idx)에 매칭한다 — 사진 속 위치·텍스트로 판단하며,
   클라이언트 OCR 이 깨져도 매칭한다. 응답 결과는 **비전 추출 메뉴**가 기준이다.
```

- `api/src/main/kotlin/com/kbap/api/scan/ScanApi.kt:29`
- **"응답 결과는 비전 추출 메뉴가 기준"** — 응답 배열의 길이는 요청 `items` 개수가 아니라 **비전이 뽑은 메뉴 개수**다. 그래서 요청 17개에 응답 12개가 정상이다.

> [!warning] 당신의 FE 노트 두 곳이 지금 코드와 어긋난다
> [[OCR 메뉴 스캔 — 박스 그룹핑]] 이 `POST /api/v1/scans` 로 적어 두었지만 현재 경로는 **`/api/scans`** 다 — kbap 은 URL 에 버전을 넣지 않고 `X-API-Version` 헤더로 가른다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]). 또 FE 가 부여하는 이름은 `itemId` 지만 서버 DTO 필드명은 **`idx`** 다. 지금 이 두 노트가 가리키는 백엔드 링크(옛 14번)도 이 노트로 갈아끼울 대상이다.

### 4-1. 파사드가 하는 일 — v1 은 정말로 세 줄이다

```kotlin
fun scanMenuBoardImage(
    memberId: Long,
    imagePath: String,
    ocrItems: List<OcrItem>,
    lang: LanguageCode,
): ScanResult {
    val member = memberService.getMember(memberId)
    val result = scanService.scan(member, imagePath, ocrItems, lang, requireDetectedMenu = false)
    memberService.increaseScanCount(memberId)
    return result
}
```

- `api/src/main/kotlin/com/kbap/api/scan/ScanFacade.kt:24-34`
- 같은 클래스의 **v2 메서드(`:36-56`)는 21줄**이다 — 티켓 검증·Redis 예약·한도 검사·실패 시 예약 해제가 붙는다. 그 21줄은 전부 [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] 의 몫이다.
- **v1 에는 무료 횟수 한도 검사가 없다.** `increaseScanCount` 로 카운트만 올릴 뿐 `isScanAllowed()` 를 부르지 않는다. 테스트가 이걸 의도로 못박아 두었다(§8-3). 다만 **v1 도 비전 모델을 부르므로 호출 비용은 똑같이 나간다** — 한도는 비용을 막는 장치가 아니라 신규 앱에만 걸린 정책이다([[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]]).
- 레포 전체에서 Facade 는 이 클래스 하나뿐이다([[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]]). **왜 스캔에만 Facade 가 있는가**는 v2 쪽 사정이므로 [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] 에서 다룬다 — 여기서는 "v1 도 같은 Facade 를 지나지만, 지나가면서 하는 일은 위 세 줄이 전부"만 기억하면 된다.

## 5. 판정 본체 — `ScanService.scan` 을 한 줄씩

### 5-1. 비전 호출과 실패의 두 갈래

```kotlin
val extracted = try {
    visionExtractor.extract(imagePath, ocrItems)
} catch (e: MenuBoardVisionUnavailableException) {
    log.warn("메뉴판 비전 서버 장애 — imagePath={}", imagePath, e)
    throw BusinessException(ErrorCode.SCAN_VISION_UNAVAILABLE)
} catch (e: Exception) {
    log.warn("메뉴판 비전 인식 실패 — imagePath={}", imagePath, e)
    throw BusinessException(ErrorCode.MENU_BOARD_RECOGNITION_FAILED)
}
```

- `api/src/main/kotlin/com/kbap/api/scan/ScanService.kt:40-48`
- `visionExtractor` 의 타입은 `common.port.llm.MenuBoardVisionExtractor` — **포트**다. `ScanService` 는 그 뒤에 어떤 모델이 붙는지 모른다([[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]).
- 실패가 **두 코드로 갈리는 이유**는 FE 분기 때문이다. `SCAN-006`(서버 일시 장애)은 "횟수 차감 없이 재시도" 모달, `SCAN-002`(인식 실패)는 "잠시 후 재시도". 에러 코드 하나로 뭉치면 앱이 안내 문구를 고를 수 없다.
- 발췌 바로 아래에 `requireDetectedMenu` 분기가 한 줄 더 있는데, 그 플래그가 **v1 은 false** 라 v1 은 지나친다 — **메뉴판이 아닌 사진을 보내도 `results: []` 인 200** 이 나간다는 뜻이다. v2 가 여기서 `SCAN-003` 으로 갈라지는 3갈래 전모는 [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] 에 있다(`specs/kb-330-scan-non-menu-board/`).

### 5-2. 매칭 키 — 표기와 대조를 분리한다

```kotlin
object KoreanMenuNameNormalizer {
    const val MAX_MENU_NAME_LENGTH = 255

    fun matchKey(raw: String): String =
        Normalizer.normalize(raw, Normalizer.Form.NFC)
            .filter { it in '가'..'힣' }
}
```

- `common/src/main/kotlin/com/kbap/common/util/KoreanMenuNameNormalizer.kt:5-11`
- `Normalizer.Form.NFC` — 한글은 유니코드에서 **완성형(`김`)과 조합형(`ㄱ`+`ㅣ`+`ㅁ`)** 두 가지로 표현될 수 있다. macOS 파일명과 iOS 키보드 입력이 서로 다른 형태를 뱉는 그 문제와 같은 뿌리다. 눈에는 똑같아 보이는 두 문자열이 `==` 로는 다르므로, 대조 전에 한 형태로 통일한다.
- `.filter { it in '가'..'힣' }` — **한글 음절 이외를 전부 버린다.** 공백·영문·숫자·특수문자가 사라진다.

| 비전이 뽑은 `koreanName` | `matchKey` | 결과 |
|---|---|---|
| `"순두부 찌개"` | `"순두부찌개"` | 띄어쓰기 차이를 흡수 |
| `"들깨 칼국수"` | `"들깨칼국수"` | 〃 |
| `"김치찌개 (2인분)"` | `"김치찌개인분"` | 괄호·숫자는 사라지지만 **한글 조각은 남는다** — 한계 |
| `"Kimchi Stew"` | `""` | 빈 문자열 → `resolveFoods` 에서 걸러진다(`:117`) |

> [!note] 왜 이렇게 단순한가

### 5-3. 카탈로그 대조와 "그 자리에서 등록"


- 등록과 동시에 **콘텐츠 수집 요청이 아웃박스에 쌓인다**(`FoodService.kt:164-173`). 그 행을 나중에 배치가 집어 kbap-langchain 으로 넘긴다 — [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]].

### 5-4. 위험도 판정 — 실측한 진짜 모양

여기가 옛 노트가 "위험도 4단계"라고 적어 둔 자리다. **코드는 조금 다르다.**

```kotlin
enum class RiskLevel(private val severity: Int) {
    SAFE(0), CAUTION(1), DANGER(2), UNKNOWN(-1);

    companion object {
        const val CAUTION_AT_LEAST = 10
        const val DANGER_AT_LEAST = 60

        fun fromInclusionProbability(probability: Int): RiskLevel =
            when {
                probability < CAUTION_AT_LEAST -> SAFE
                probability < DANGER_AT_LEAST -> CAUTION
                else -> DANGER
            }

        fun aggregate(levels: Collection<RiskLevel>): RiskLevel =
            when {
                levels.isEmpty() -> SAFE
                levels.any { it == UNKNOWN } -> UNKNOWN
                else -> levels.maxBy { it.severity }
            }
    }
}
```

- `common/src/main/kotlin/com/kbap/common/domain/food/model/RiskLevel.kt:3-33` (원본에서 `require` 검증 줄 생략)

**등급은 4개 값이지만 3단 척도다.** `SAFE`·`CAUTION`·`DANGER` 만 severity 0·1·2 로 서열이 있고, `UNKNOWN` 은 severity `-1` 로 척도 **밖**에 있다 — "안전하다"도 "위험하다"도 아닌 **"판정 불가"** 다. `aggregate` 에서 `maxBy { severity }` 로 뽑는 로직 안에 `-1` 이 섞이면 절대 이기지 못하므로, `UNKNOWN` 은 `maxBy` 이전에 `any { it == UNKNOWN }` 로 **먼저 가로챈다.** 서열 밖의 값을 서열 계산에 넣지 않으려는 의도적 분기다.

**판정 기준은 성분 함유 확률 하나뿐이다.**

| 조건 | 등급 |
|---|---|
| 기피 성분의 함유 확률 < 10% | `SAFE` |
| 10% ≤ 확률 < 60% | `CAUTION` |
| 확률 ≥ 60% | `DANGER` |
| 겹치는 기피 성분이 **하나도 없음** | `SAFE` (`levels.isEmpty()`) |
| 음식이 `READY` 가 아니거나 성분 데이터가 `null` | `UNKNOWN` |

> [!warning] 옛 노트와 다름 — "위험도 4단계"의 실체
> enum 값이 4개인 건 맞지만, **`UNKNOWN` 은 위험도 등급이 아니라 판정 불가 표시**다. 그리고 옛 노트에 없던 사실이 둘 더 있다 — ① 임계값이 `10`·`60` 두 개로 **하드코딩**돼 있고(설정도 DB 값도 아니다), ② 기피 성분이 하나도 안 겹치면 `SAFE` 지만 **기피 성분을 아예 등록하지 않은 회원도 전부 `SAFE`** 로 나간다(빈 컬렉션 → `SAFE`). "안전 확인됨"과 "확인할 게 없었음"이 같은 값으로 내려간다.

[[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 가 말한 "N+1 을 설계로 제거했다"의 가장 극단적인 사례가 이것이다 — **조인할 테이블 자체를 없앴다.**

### 5-6. `idx` 되돌려주기 — 중복 방지 한 줄


| `image_path` | 사진 ↔ 메뉴 연결은 `orders` 테이블이 소유하게 됐다(KB-337) — [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지]] |

> [!note] 스냅샷을 둘 것인가 참조로 갈 것인가
> 일반론은 "둘 다 맞을 수 있다"이다 — **주문 내역의 가격**처럼 "그때 그 값"이 진실이어야 하는 데이터는 스냅샷이 옳고(그래서 `price` 는 살아남았다), **메뉴 이름**처럼 마스터가 개선되면 같이 개선돼야 하는 데이터는 참조가 옳다. KB-345 는 이 둘을 갈라 놓은 것이다. `price` 하나만 남은 게 우연이 아니다.
> 마이그레이션이 `DROP COLUMN` 을 **되돌리는 파일 없이** 진행된다는 점도 짚어둘 것 — [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] 의 "앞으로만 간다" 원칙 그대로다.

## 8. 요청·응답 실물

### 8-1. 요청

```http
POST /api/scans?lang=en HTTP/1.1
Authorization: Bearer <access token>
X-API-Version: 1.0
Content-Type: application/json
```
```json
{
  "imagePath": "scan/501/menu.jpg",
  "items": [
    { "idx": 0, "rawMenuName": "김치피개" },
    { "idx": 1, "rawMenuName": "불고기" },
    { "idx": 2, "rawMenuName": "한식마당" },
    { "idx": 3, "rawMenuName": "원산지 국내산" }
  ]
}
```

- `lang` 은 **쿼리 파라미터**다(`@ModelAttribute ScanLangRequest`). 바디가 아니다.
- `lang` 은 **필수** — 누락·빈 문자열은 400 `COMMON-002`. 지원 목록에 없는 코드(`"EN"`, `"en-US"` 포함)는 **거절이 아니라 `en` 으로 폴백**한다(`LanguageCode.kt:18`, ADR-0013·ADR-0015).
- `imagePath` 는 **오브젝트 경로**여야 한다 — `^(?!https?://).*` 정규식이 전체 URL 을 막는다(`ScanRequest.kt:18`). 이 경로는 [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]]이 발급한 값이다.
- 회원 프로필의 언어 설정은 **참조하지 않는다.** ADR-0015 가 "언어 출처가 둘이면 화면마다 어느 쪽이 이기는지 달라진다"는 이유로 프로필 언어를 아예 제거했다.

### 8-2. 응답

```json
{
  "success": true,
  "code": "COMMON-000",
  "message": "성공",
  "payload": {
    "degraded": false,
    "results": [
      {
        "idx": 0,
        "matched": true,
        "foodId": 7,
        "riskLevel": "SAFE",
        "name": "Kimchi Stew",
        "koreanName": "김치찌개",
        "price": 9000
      },
      {
        "idx": 1,
        "matched": false,
        "foodId": 812,
        "riskLevel": "UNKNOWN",
        "name": "불고기",
        "koreanName": "불고기",
        "price": 16000
      }
    ]
  }
}
```

읽는 법:

- **요청 4개 → 응답 2개.** `"한식마당"`·`"원산지 국내산"` 은 비전 단계에서 메뉴가 아니라고 판단돼 사라졌다. 배열 길이로 짝을 맞추면 안 되고 **`idx` 로 맞춰야 한다.**
- FE OCR 이 `"김치피개"` 로 깨졌는데도 `idx: 0` 에 `"김치찌개"` 판정이 붙었다 — §3 의 이음매가 작동한 것이다.
- **`matched: false` 인데 `foodId` 가 있다.** 조사 대기로 방금 등록된 행의 id 다. `ScanResponse.kt:31-32` 가 **"`foodId` 유무가 아니라 `matched` 로 판단하라"** 고 명시적으로 경고한다. FE 에서 `if (foodId)` 로 분기하면 틀린다.
- `matched: false` 면 `riskLevel` 은 **항상 `UNKNOWN`** 이고, `name` 은 번역이 없으므로 한국어명이 그대로 온다.
- 봉투(`success`·`code`·`message`·`payload`)는 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 의 `BaseResponse` 다.

### 8-3. 에러

| 코드 | HTTP | 언제 | v1 에서 실제로 나오나 |
|---|---|---|---|
| `COMMON-002` | 400 | `lang` 누락, `imagePath` 형식 위반, `items` 0개/101개, `idx` 중복 | ✅ |
| `SCAN-002` | 503 | 비전 인식 실패 | ✅ |
| `SCAN-006` | 503 | 비전 서버 장애 (횟수 차감 없이 재시도 유도) | ✅ |
| `SCAN-003` | 400 | 메뉴판 미인식 | ❌ **v2 전용** (v1 은 빈 배열 200) |
| `SCAN-004`·`SCAN-005`·`SCAN-007` | 403·409·400 | 한도 초과·중복 요청·티켓 오류 | ❌ **v2 전용** ([[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]]) |
| `SCAN-001` | 400 | 검증 안 된/타인 소유 이미지 | ❌ **문서에만 있다** ↓ |

> [!warning] 스펙과 다름 — 두 곳
> **① `SCAN-001`(이미지 소유 검증)이 스캔 경로에 없다** — `ScanApi.kt:52` 가 문서화만 해뒀을 뿐 v1·v2 어느 쪽도 검증하지 않아, 남의 이미지 경로를 알면 그걸로 스캔이 된다. 발급→업로드→확정 3단계 중 어디가 뚫렸는지는 [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]] 이 다룬다.
> **② `degraded` 는 항상 `false` 인 죽은 필드다.** `ScanService.kt:79` 가 `degraded = false` 를 하드코딩한다. `ScanResponse.kt:8-9` 의 스키마 설명("LLM 이 없거나 실패해 음식 여부를 판정하지 못한 상태")이 가리키는 경로는 이제 없다 — 비전 실패는 `degraded=true` 응답이 아니라 **503 예외**로 나간다. 응답 계약이 동결돼 있으니 필드를 지울 수는 없고, 값만 굳어 있는 상태다.

## 12. 용어집

| 용어 | 뜻 |
|---|---|
| **`idx`** | FE 가 OCR 항목마다 부여하는 식별자. 요청·응답을 잇는 유일한 키. FE 코드에선 `itemId` |
| **`matchedIdx`** | 비전이 "이 추출 메뉴는 그 OCR 항목이다"라고 지목한 `idx`. 서버가 두 번 검증한 뒤 응답 `idx` 가 된다 |
| **`matched`** | 조회 가능한(`READY`) 음식과 붙었는가. **`foodId` 유무와 다르다** |
| **`READY` / `FAILED`** | `FoodContentStatus`. 조사 대기로 막 등록된 음식은 `FAILED` 라 `matched=false` |
| **`degraded`** | 원래 "정제 미적용" 표시. 현재는 **항상 `false`** |
| **매칭 키** | `KoreanMenuNameNormalizer.matchKey` 의 결과. `food.korean_name` 컬럼에 저장 |
| **표시명** | 원본 표기 그대로. `food.display_name` 컬럼 |
| **`inclusion_percent`** | 성분 함유 확률 1~100. 위험도의 유일한 입력 |
| **동결 계약** | 구버전 앱 호환을 위해 응답 모양을 바꾸지 않기로 한 약속 |

## 13. 체크리스트

- [ ] `POST /api/scans` 응답 배열의 길이가 요청 `items` 길이와 다를 수 있는 이유를 설명할 수 있다
- [ ] FE OCR 이 깨져도 판정이 맞는 이유(누가 recall, 누가 precision)를 말할 수 있다
- [ ] `matchKey` 가 `"순두부 찌개"` 와 `"순두부찌개"` 를 같은 음식으로 만드는 과정을 따라갈 수 있다
- [ ] `SAFE`·`CAUTION`·`DANGER`·`UNKNOWN` 의 기준과 `UNKNOWN` 이 척도 밖인 이유를 설명할 수 있다
- [ ] 기피 성분 매칭이 조인이 아니라 메모리 `filter` 인 이유(ADR-0009)를 말할 수 있다
- [ ] `matched=false` 인데 `foodId` 가 있는 경우가 왜 생기는지 안다
- [ ] `scan()` 에 `@Transactional` 이 없는 이유를 트레이드오프로 설명할 수 있다
- [ ] `scan_history` 에서 이름·이미지 경로가 지워지고 `price` 만 남은 판단 기준을 말할 수 있다
- [ ] v1 응답이 `avoidances`·`currency` 를 갖지 않는 것이 누락이 아니라 동결임을 안다

> [!note] 2026-08-27 역링크 — 이 흐름의 LLM 호출에 `await` 가 없는 이유
> **[[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]] §2** 가 이 노트의 코드 한 줄을 **JVM 동시성 모델의 대표 예시로** 인용한다 — `visionExtractor.extract(imagePath, ocrItems)`(`ScanService.kt:40-42`)에는 `await` 도 `.then()` 도 콜백도 없다. 그냥 부르고 결과를 변수에 받는다. 수 초가 걸리는 HTTP 호출인데도 그게 정상인 건, 그 사이 **멈추는 것이 "서버" 가 아니라 "이 요청 하나"** 이기 때문이다(다른 199개 스레드는 각자 자기 요청을 계속 처리한다).
> FE 였다면 앱 전체가 수 초간 프리즈했을 코드다. 이 흐름을 읽을 때 "왜 이렇게 순차적으로 생겼지" 라는 위화감이 들면, 그 답이 2번에 있다.
