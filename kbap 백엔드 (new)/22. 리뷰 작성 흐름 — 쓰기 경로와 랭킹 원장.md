# 22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장

> 작성: 2026-08-27 · 맥락: 15~21번에서 본 흐름은 대부분 **읽기**(홈·스캔 조회·목록)이거나 **인증**이었다. 쓰기라고 해봐야 온보딩 프로필 저장(15번)처럼 "테이블 한 행을 UPDATE 한다" 수준이었다. 리뷰는 다르다 — **한 번의 POST 가 네 개의 테이블을 건드린다.** 그리고 그중 하나는 "이 리뷰가 랭킹에 몇 점을 줬는가"를 기록하는 **원장(ledger)** 이다.
> 목표: ① 쓰기 트랜잭션 하나가 실제로 무엇을 함께 움직이는지 순서대로 말할 수 있게 되기 ② **왜 랭킹을 카운트 컬럼 하나로 끝내지 않고 이벤트 행을 따로 쌓는지**, 그리고 `uq_member_ranking_event` 유니크 제약이 정확히 어떤 사고를 막는지 설명할 수 있게 되기 ③ 내가 차단한 사람의 리뷰가 목록에서 빠지는 그 한 줄이 어디인지 짚을 수 있게 되기.

---

## 0. 한 줄 요약

리뷰 작성은 **`food_review` 에 행 하나를 넣는 일이 아니라**, 같은 트랜잭션 안에서 회원의 랭킹 카운트를 원자적으로 올리고 **`member_ranking_event` 에 "+1/+1" 이라는 거래 내역 한 줄을 남기는 일**이다. 삭제는 그 행을 지우는 게 아니라 **"-1/-1" 이라는 반대 부호 행을 하나 더 쌓는다**. `UNIQUE (review_id, event)` 가 "한 리뷰는 랭킹에 최대 1회 반영·1회 차감"을 DB 레벨에서 못박아, 재시도나 동시 요청이 카운트를 두 번 깎는 사고를 막는다.

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| 원장(ledger) | 잔액을 바꾼 사건 하나하나를 행으로 남기는 테이블 | Redux 의 action 로그. 현재 state(잔액)와 별개로 "무엇이 state 를 이렇게 만들었나"가 남는다 |
| 보상 이벤트(compensating event) | 취소를 "행 삭제"가 아니라 **반대 부호의 새 행**으로 표현하는 것 | 결제 취소가 결제 내역을 지우지 않고 "환불 -10,000원" 줄을 추가하는 것 |
| 멱등(idempotent) | 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같음 | 같은 mutation 을 두 번 눌러도 좋아요가 2 가 되지 않는 것 |
| 낙관적 락(`@Version`) | 행에 버전 숫자를 두고, UPDATE 할 때 "내가 읽었을 때의 버전"이 아직 그대로일 때만 성공시키는 것 | 두 탭에서 같은 문서를 편집할 때 "다른 곳에서 변경됨" 경고를 띄우는 것 |
| 커스텀 리포지토리(`*RepositoryCustomImpl`) | Spring Data 메서드 이름 규약으로 표현 못 하는 쿼리를 `EntityManager` 로 직접 조립하는 자리 | 대부분 훅으로 되지만 딱 하나 손으로 짜야 하는 `useEffect` |
| 뷰어 필터 | 같은 목록이라도 **보는 사람에 따라** 다른 행이 빠지는 것 | 같은 피드 API 인데 내가 뮤트한 계정 글만 안 보이는 것 |

`@Transactional`·영속성 컨텍스트·소프트 삭제는 [[6. 설정과 프로필, 트랜잭션 경계]]·[[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 에서 정의했다. `BaseResponse`·`ErrorCode`·`X-API-Version` 은 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]].

## 2. 이 API 들이 하는 일 — 사용자 관점 한 줄

> **"내가 스캔해서 먹어본 음식에 별점과 사진을 남기고, 남들이 남긴 리뷰를 정렬·필터해서 읽고, 보기 싫은 사람이나 글은 내 화면에서만 치운다."**

리뷰 도메인이 실제로 여는 엔드포인트는 6개다(`api/src/main/kotlin/com/kbap/api/review/ReviewController.kt`).

| 메서드·경로 | 하는 일 | 인증 |
|---|---|---|
| `POST /api/reviews` | 리뷰 작성 | 필수 (`@AuthMemberId`) |
| `PATCH /api/reviews/{id}` | 리뷰 수정(본인 것만) | 필수 |
| `DELETE /api/reviews/{id}` | 리뷰 삭제(본인 것만) | 필수 |
| `POST /api/reviews/{id}/like?liked=true\|false` | 좋아요 등록/취소 | 필수 |
| `GET /api/reviews` | 리뷰 목록(전체 피드 또는 `foodId` 별) | **선택** (`@AuthMemberIdOrNull`) |
| `GET /api/reviews/me` | 내 리뷰 목록 | 필수 |

여기에 이 노트가 **흡수**하는 두 도메인이 붙는다 — 신고(`POST /api/reports`)와 차단(`POST·DELETE·GET /api/members/me/blocks`). 이 둘은 자기 테이블에 행 하나를 남기는 게 전부지만, **그 행이 위 `GET /api/reviews` 의 결과를 바꾼다.** 그래서 별도 노트가 아니라 여기 있다.

### 서비스 본문 — 이게 전부다

```kotlin
foodService.getReadyFood(foodId)

    throw BusinessException(ErrorCode.REVIEW_NOT_ELIGIBLE)
}

    memberService.increaseUniqueReviewedFoodCount(memberId)
}

```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:56-82`

줄 단위 풀이:

- **1줄** — 음식이 존재하고 공개 상태(`isReady`)인지 먼저 본다. 없으면 `FOOD-001`. **자격 검증보다 앞에 있는 게 의도**다(§5).
- **2~4줄** — 자격 검증. 내가 스캔한 적 없는 음식이면 `REVIEW-004`(403).
- **5줄** — 사진 경로가 **내가** 업로드 완료한 **REVIEW 용도** 경로인지 확인. [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]] 에서 만든 `uploaded_image` 행을 여기서 되찾아 쓴다. 아니면 `REVIEW-003`.
- **6줄** — 작성 시점 국적을 **문자열로 복사**한다. 회원이 나중에 국적을 바꿔도 이 리뷰의 국적은 안 바뀐다(스냅샷). 마이그레이션 주석이 이유를 적어뒀다 — "member 조인 없이 같은 국적 평점·필터를 계산하기 위한 불변 스냅샷"(`V2026.07.29.21.00.16__food_review_table.sql:3`). [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 의 연장선이다.
- **7줄** — 회원의 `reviewCount` 를 **원자적 UPDATE** 로 +1. 상세는 [[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]].
- **9줄** — 리뷰 저장.
- **11줄** — "이 음식에 내가 쓴 리뷰가 지금 1건인가?" → 1건이면 **이번이 그 음식의 첫 리뷰**다. `uniqueReviewedFoodCount`(몇 종류의 음식을 리뷰했나)를 올릴지 결정한다.
- **15줄** — 원장에 거래 내역 한 줄.

> [!tip] `countByMemberIdAndFoodId == 1L` 이 왜 성립하나
> `save()` 는 아직 DB 에 INSERT 문을 안 보냈을 수도 있다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 의 "쓰기 지연"). 그런데 바로 다음 줄에서 **같은 테이블을 조회**하면 Hibernate 가 "이 쿼리 결과가 틀리면 안 되지"라며 대기 중인 INSERT 를 먼저 flush 한다(auto-flush). 그래서 방금 저장한 리뷰가 count 에 포함되고, `== 1L` 이 "첫 리뷰"를 뜻하게 된다. flush 는 commit 이 아니다 — 아직 트랜잭션 안이다.

> [!note] `getMember` 가 두 번 불린다
> 6줄에서 한 번(`ReviewService.kt:61`), 응답 조립 때 한 번 더(`ReviewService.kt:283`의 `authorOf`). 사이에 낀 `increaseReviewCount` 가 `@Modifying(clearAutomatically = true)` 라서 **영속성 컨텍스트를 통째로 비운다**(`common/.../member/MemberJpaRepository.kt:33-42`). 그래서 두 번째 호출은 캐시 히트가 아니라 진짜 재조회다 — 그리고 그게 맞다. 방금 +1 한 카운트를 반영한 회원을 응답에 실어야 하니까.

## 4. 쓰기 트랜잭션 하나가 건드리는 테이블

읽기 흐름(18번 홈)에서는 "여러 서비스를 불러 한 응답으로 모은다"가 주제였다. 쓰기에서는 반대다 — **한 요청이 여러 테이블을 함께 바꾸고, 하나라도 실패하면 전부 없던 일이 돼야 한다.**

```
POST /api/reviews  ──┐
                     ├─ (읽기) food            존재·공개 여부
                     ├─ (읽기) scan_history    자격 검증
                     ├─ (읽기) uploaded_image  사진 소유 검증
                     ├─ (쓰기) member          reviewCount +1, uniqueReviewedFoodCount +1?
                     ├─ (쓰기) food_review     INSERT
                     └─ (쓰기) member_ranking_event  INSERT (+1/+1)
                        ─────────── 전부 같은 트랜잭션 ───────────
```

`@Transactional` 은 `ReviewService.createReview` 에 **하나만** 붙어 있다. 그 안에서 부르는 `memberService.increaseReviewCount`(자기도 `@Transactional`)는 **새 트랜잭션을 열지 않고 바깥 것에 합류**한다(전파 기본값 `REQUIRED`). 그래서 원장 INSERT 가 터지면 카운트 +1 도 같이 롤백된다.

> [!warning] FE 감각과 다른 지점
> React 에서 "낙관적 업데이트 후 실패하면 되돌리기"를 손으로 짜본 적이 있다면, 그 되돌리기를 **DB 가 공짜로 해준다**고 보면 된다. 대신 조건이 있다 — 되돌릴 대상이 **같은 트랜잭션 안**이어야 한다. S3 에 이미 올라간 사진 파일은 트랜잭션 밖이라 롤백되지 않는다(그래서 21번의 고아 객체 이야기가 나온다).

## 5. 리뷰를 아무나 쓸 수 있나 — 자격 조건

**아니다.** 2026-08-21 의 KB-369(`specs/kb-369-review-eligibility/`)로 자격 검증이 생겼다.

```kotlin
if (!scanHistoryRepository.existsByMemberIdAndFoodId(memberId, foodId)) {
    throw BusinessException(ErrorCode.REVIEW_NOT_ELIGIBLE)
}
```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:57-59`

규칙을 정확히 옮기면:

| 상황 | 결과 | 근거 |
|---|---|---|
| 내가 스캔해서 **음식 매칭에 성공한** 이력이 있다 | 작성 가능 | `scan_history` 에 `food_id` 가 채워진 활성 행이 있어야 `existsByMemberIdAndFoodId` 가 참 |
| 스캔한 적 없다 | `REVIEW-004` / **403** | `ErrorCode.kt:54` |
| 다른 사람만 그 음식을 스캔했다 | 403 — 자격은 **본인 이력** 기준 | `ReviewControllerTest.kt:1002-1010` |
| 스캔은 했지만 음식 매칭 실패(음식 미확정) | 자격 없음 — `food_id` 가 안 채워졌으므로 | `specs/kb-369-review-eligibility/spec.md` Edge Cases |
| 삭제된 스캔 이력 | 자격 없음 — `BaseEntity` 의 `@SQLRestriction("status = 'ACTIVE'")` 가 자동으로 걸러낸다 | `common/.../domain/BaseEntity.kt:16` |
| **수정**(`PATCH`) | **재검증 안 함** | `updateReview` 에 자격 검사 없음(`ReviewService.kt:86-110`) |
| 존재하지 않는 음식 | 자격 오류가 아니라 `FOOD-001` | 검사 순서가 음식 → 자격이라서 |

마지막 두 줄이 설계 의도다. 수정 재검증을 안 하는 이유는 스펙에 적혀 있다 — 이미 쓴 리뷰가 나중에 스캔 이력이 지워졌다고 수정 불가가 되면 이상하니까(`ReviewControllerTest.kt:1013-1026` 이 이 시나리오를 그대로 테스트한다). 검사 순서를 음식 우선으로 둔 이유도 스펙에 있다 — "음식 자체의 오류가 우선".

그리고 자격은 **작성 시점에만** 튀어나오면 안 된다. 글을 다 쓰고 나서 403 을 받는 UX 를 막으려고, 음식 상세 응답에 `reviewEligible` boolean 이 함께 내려간다(KB-369 User Story 2). FE 는 그 값으로 버튼을 게이트한다.

## 6. 랭킹 원장 — 이 노트의 백미

### 6-1. 잔액과 거래 내역

리뷰를 쓰면 회원의 두 카운트가 오른다.

- `member.review_count` — 총 리뷰 수
- `member.unique_reviewed_food_count` — 몇 **종류**의 음식을 리뷰했나

이것만 있어도 랭킹은 계산된다. 그런데 kbap 은 여기에 테이블을 하나 더 뒀다. 마이그레이션 주석이 이유를 직접 말한다.

```sql
-- 랭킹 이력 원장(KB-128): 리뷰가 랭킹 카운트에 준 영향을 은행 이체 내역처럼 행으로 남긴다.
```

### 6-3. 삭제하면 원장에 무엇이 남나 — **행을 지우지 않는다**

```kotlin

    throw BusinessException(ErrorCode.REVIEW_NOT_FOUND)
}
review.delete()

    memberService.decreaseUniqueReviewedFoodCount(memberId)

```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:114-124`

- `review.delete()` 는 소프트 삭제다 — `status` 를 `DELETED` 로 바꿀 뿐 행은 남는다(`BaseEntity.kt:40-42`).
- 원장의 `REVIEW_CREATED` 행도 **그대로 남는다**. 지우는 게 아니라 `REVIEW_DELETED` 행을 **추가**한다. 이게 보상 이벤트다.
- `countByMemberIdAndFoodId == 0L` — 소프트 삭제된 리뷰는 `@SQLRestriction` 때문에 count 에서 자동으로 빠진다. 0 이면 "이 음식의 마지막 리뷰였다".

**왜 지우지 않고 쌓나?** 지우면 "이 회원의 카운트가 왜 3인가"를 나중에 재구성할 수 없다. 카운트가 틀어졌을 때(버그·수동 개입·부분 실패) 원장을 다시 더해서 잔액을 복원하거나 검증할 수 있는 것 — 그게 원장을 두는 값이다. 은행이 잔액만 저장하고 이체 내역을 안 남기지 않는 것과 같은 이유다.

> [!note] 지금은 아무도 원장을 읽지 않는다
> `MemberRankingEventJpaRepository` 의 메서드는 `existsByReviewIdAndEvent` **하나뿐**이고(`common/src/main/kotlin/com/kbap/common/domain/member/MemberRankingEventJpaRepository.kt:8`), 원장을 합산해 점수를 내는 코드는 레포에 없다. 점수는 전부 `member` 의 잔액 컬럼에서 나온다([[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]]). 즉 원장은 **지금 쓰이는 기능이 아니라 사후 조사·수동 복구를 위한 재료**다. "언젠가 필요할까 봐" 만든 테이블이 아니라 — `uq_member_ranking_event` 가 지금 당장 중복 가감을 막고 있으니 **제약만으로도 밥값을 한다.** 조회 용도는 덤이다.

### 6-4. `uq_member_ranking_event` — 중복 가감이 왜 위험한가

```sql
UNIQUE KEY `uq_member_ranking_event` (`review_id`, `event`)
```
`api/src/main/resources/db/migration/V2026.07.30.13.58.27__member_ranking_event_table.sql:15`

**"한 리뷰 × 한 종류의 사건 = 최대 1행."** 리뷰 101 에 `REVIEW_CREATED` 는 한 번, `REVIEW_DELETED` 도 한 번뿐이다.

이게 없으면 무슨 일이 벌어지나 — 사고 시나리오 셋:

1. **더블 탭.** 사용자가 삭제 버튼을 두 번 누른다. 두 요청이 거의 동시에 들어와 둘 다 "이 리뷰는 아직 ACTIVE 다"를 읽는다. 둘 다 `decreaseReviewCount` 를 부른다. **리뷰 하나를 지웠는데 카운트가 2 줄어든다.**
2. **네트워크 재시도.** 앱이 응답을 못 받아 같은 DELETE 를 재전송한다. 서버 입장에선 정상 요청 두 건이다.
3. **부분 실패 후 재시도.** 트랜잭션이 커밋 직전에 죽었는지 직후에 죽었는지 앱은 모른다. 안전하게 재시도한다.

셋 다 결과가 같다 — **잔액이 실제보다 낮아지고, 원장의 합과 잔액이 어긋난다.** 그리고 카운트 컬럼은 `reviewCount > 0` 조건이 붙어 있어(`MemberJpaRepository.kt:47-54`) 음수까지는 안 가지만, 대신 **조용히 틀린 값**이 된다. 조용히 틀리는 게 제일 나쁘다.

kbap 은 이 사고를 **세 겹**으로 막는다.

| 겹 | 장치 | 어떤 경우를 잡나 | 응답 |
|---|---|---|---|
| ① | `getMyReview` → `findById` + `@SQLRestriction("status = 'ACTIVE'")` | 앞 요청이 **이미 커밋된** 뒤의 재시도 — 소프트 삭제된 리뷰는 조회 자체가 안 됨 | `REVIEW-001` / 400 |
| ② | `existsByReviewIdAndEvent(id, REVIEW_DELETED)` 가드 | ①을 뚫는 경계 케이스에서 원장을 한 번 더 확인 | `REVIEW-001` / 400 |
| ③ | `@Version` 낙관적 락 + `uq_member_ranking_event` | **진짜 동시** — 둘 다 ACTIVE 를 읽고 둘 다 가드를 통과한 경우. 먼저 커밋한 쪽만 살고 나머지는 버전 충돌 | `COMMON` 계열 / **409** |

③의 `@Version` 은 리뷰 엔티티에 있다.

```kotlin

```
`common/src/main/kotlin/com/kbap/common/domain/review/model/Review.kt:42-44`

도입 이유가 마이그레이션에 적혀 있다 — "같은 리뷰의 동시 수정/삭제 경합(중복 차감·삭제 되살림)을 `@Version` 으로 검출한다"(`V2026.07.30.15.44.44__food_review_version_lock.sql:1`). 충돌은 `GlobalExceptionHandler` 가 409 로 바꾼다(`api/src/main/kotlin/com/kbap/api/core/GlobalExceptionHandler.kt:72-76, 96-100`).

> [!tip] 유니크 제약을 "검증 코드"로 보지 말 것
> 애플리케이션에서 `if (이미 있으면) throw` 로 막는 검사는 **읽는 순간과 쓰는 순간 사이의 틈**을 못 막는다 — 이 틈을 **TOCTOU**(time-of-check to time-of-use, 검사 시점과 사용 시점이 어긋나는 경합)라고 부른다. 두 스레드가 동시에 "없네"를 읽으면 둘 다 쓴다. DB 의 유니크 제약은 **쓰는 순간에** 판정하므로 틈이 없다. 그래서 kbap 에서 앱 레벨 검사는 **친절한 에러 메시지용**이고, 진짜 보증은 항상 DB 제약이다. 같은 패턴이 신고(`uk_report_reporter_target`)·차단(`uk_member_block_pair`)·좋아요(`uk_review_like_pair`)에도 그대로 있다.

### 7-2. `ReviewRepositoryCustomImpl` 이 왜 있나

지금까지 본 리포지토리는 전부 둘 중 하나였다 — 메서드 이름 규약(`findByMemberIdAndFoodId`)이거나 고정 `@Query` JPQL. 리뷰 목록만 다르다. **`EntityManager` 로 JPQL 문자열을 직접 조립한다.**

이유는 조합 폭발이다. 이 API 가 받는 축을 세어보면:

- 정렬 5종 — `latest` / `rating_high` / `rating_low` / `food_review_count` / `helpful`
- 커서 유무 2종
- 필터 4종 — `foodId` / `countryCode` / `minRating` / `maxRating` (각각 있거나 없거나)

고정 `@Query` 로 감당하려면 수십 개의 메서드가 필요하다. 스펙이 그 판단을 그대로 적어뒀다 — "정렬 5종 × 커서 유무 × 필터 3종 조합을 고정 `@Query` 로 감당할 수 없어 custom impl 에서 문자열 조립(where·having·order 분기). **파라미터는 전부 바인딩(문자열 직접 삽입 금지)**"(`specs/kb-338-review-sort-filter/plan.md:97`). QueryDSL 은 도입하지 않았다 — 새 의존성 없이 `FoodRepositoryCustomImpl` 선례를 따랐다.

조립의 심장은 이 부분이다.

```kotlin

    ReviewSort.LATEST -> "r.id"
    ReviewSort.RATING -> "r.rating"
    ReviewSort.FOOD_REVIEW_COUNT -> "(select count(r2) from Review r2 where r2.foodId = r.foodId)"
    ReviewSort.HELPFUL -> "count(l)"
}
val cursorCondition = if (sort == ReviewSort.LATEST) {
    "r.id $metricComparator :idCursor"
} else {
    "($metricExpr $metricComparator :metricCursor or ($metricExpr = :metricCursor and r.id < :idCursor))"
}
```
`common/src/main/kotlin/com/kbap/common/domain/review/ReviewRepositoryCustomImpl.kt:32-45`

- **정렬 지표**가 정렬마다 다른 SQL 조각이 된다. `helpful` 은 좋아요 개수라 `left join ReviewLike` 후 `count(l)` 이고, 집계라서 조건이 `where` 가 아니라 `having` 으로 간다(`:48-55`).
- **커서 조건**이 `metric` 과 `id` 두 값을 함께 쓴다. 별점 4점짜리 리뷰가 100개면 "4점" 만으로는 어디까지 읽었는지 알 수 없다 — 동점 안에서는 `id` 로 자른다. 이게 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]] 의 **복합 keyset** 이다.
- 문자열을 조립하지만 **값은 전부 `setParameter` 바인딩**이다(`:65-79`). 조립되는 건 컬럼·연산자·방향 같은 **구조**뿐이고, 사용자 입력이 SQL 문자열에 들어가는 자리는 없다.

커서 인코딩도 정렬에 따라 갈린다.


`api/src/main/kotlin/com/kbap/api/review/ReviewListCursor.kt:27-32`

`latest` 는 숫자 하나(`"204"`), 나머지는 `"17_204"` 를 base64url 로 감싼 불투명 토큰(`"MTdfMjA0"`). `latest` 만 옛 형식을 유지한 건 하위 호환 때문이다 — 이미 배포된 앱이 들고 있는 커서를 깨뜨리지 않으려고.

> [!warning] 커서는 정렬·필터 조합에 종속된다

### 7-3. 9번 노트의 실전 — 여기선 "2단계 조회"가 아니다

[[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 에서 본 2단계 키셋(`id 만 커서 조회 → findByIdIn`)은 **리뷰 목록에는 없다.** `findReviewPage` 는 한 번에 엔티티를 가져온다. 대신 9번의 **다른** 절반 — "연관관계 대신 `Long` id 를 들고, 필요하면 배치로 채운다" — 가 그대로 나온다.

```kotlin
val authorsByMemberId = memberRepository.findAllById(page.map { it.memberId }.toSet()) ...
val foodsByFoodId = foodRepository.findAllById(page.map { it.foodId }.toSet()) ...
val likeCountsByReviewId = reviewLikeRepository.countByReviewIds(reviewIds) ...
val likedReviewIds = viewerMemberId?.let { reviewLikeRepository.findLikedReviewIds(it, reviewIds).toSet() }
```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:256-269`

50건짜리 페이지를 만드는 데 나가는 쿼리는 **목록 1 + 배치 4 = 5개**다. 페이지 크기와 무관하게 5개. 연관관계를 걸었다면 `review.member.nickname` 을 읽는 순간 50번이 더 나갔을 것이다(N+1). `@ManyToOne` 이 없으니 **N+1 이 생길 자리 자체가 없고**, 대신 개발자가 "무엇을 언제 배치로 채울지"를 손으로 정한다.

`ReviewResponse.food` 는 `includeFood` 플래그로 갈린다 — 목록에서만 채우고, 작성·수정 응답이나 음식 상세 동봉 리뷰에서는 **필드 자체를 생략**한다(`@JsonInclude(NON_NULL)`, `ReviewResponse.kt:70-72`). 이미 아는 정보를 다시 안 보낸다.

## 8. 신고·차단이 읽기에 스며드는 법

신고와 차단은 쓰기 자체는 시시하다. 재밌는 건 **그 행이 남의 조회 결과를 바꾼다**는 점이다.

### 8-1. 두 개의 제외 목록

```kotlin
excludedMemberIds = viewerMemberId?.let(::excludedMemberIds) ?: listOf(-1L),
excludedReviewIds = viewerMemberId?.let(::excludedReviewIds) ?: listOf(-1L),
```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:162-163`

```kotlin
private fun excludedMemberIds(viewerMemberId: Long): List<Long> =
    memberBlockService.getBlockedMemberIds(viewerMemberId).ifEmpty { listOf(-1L) }

private fun excludedReviewIds(viewerMemberId: Long): List<Long> =
    reportRepository
        .findTargetIdsByReporterMemberIdAndTargetType(viewerMemberId, ReportTargetType.REVIEW)
        .ifEmpty { listOf(-1L) }
```
`api/src/main/kotlin/com/kbap/api/review/ReviewService.kt:177-183`

그리고 쿼리 조건 첫 두 줄:

```kotlin
val conditions = mutableListOf(
    "r.memberId not in :excludedMemberIds",
    "r.id not in :excludedReviewIds",
    "exists (select 1 from Food f where f.id = r.foodId)",
)
```
`common/src/main/kotlin/com/kbap/common/domain/review/ReviewRepositoryCustomImpl.kt:22-26`

- **차단**은 `member_id` 단위 — 그 사람이 쓴 리뷰가 통째로 빠진다.
- **신고**는 `review_id` 단위 — 내가 신고한 그 글 하나만 빠진다.
- 셋째 줄은 덤이다. 연관관계가 없으니 "음식이 삭제됐으면 리뷰도 안 보인다"를 **`exists` 서브쿼리로 직접** 써야 한다. JOIN 이 있었으면 공짜였을 일이다 — 9번의 트레이드오프가 여기 청구서로 온다.

> [!tip] `listOf(-1L)` 이라는 센티널
> JPQL 의 `not in ()` 은 **빈 리스트를 넣을 수 없다** — 문법 오류이거나 DB 마다 동작이 다르다. 그래서 차단·신고가 하나도 없으면 "절대 존재하지 않는 id" 인 `-1L` 을 넣어 `not in (-1)` 로 만든다. 결과적으로 아무것도 안 걸러진다. 게스트(`viewerMemberId == null`)도 같은 값을 쓴다 — 로그인 안 했으면 차단 목록이 있을 리 없으니까.

### 8-2. 내 화면에서만 사라진다

핵심은 **뷰어 필터**라는 점이다. 내가 B 를 차단해도 B 의 리뷰는 지워지지 않는다.

- B 의 리뷰는 DB 에 그대로 있다.
- **다른 사람 화면에는 계속 보인다.**
- **평균 별점 집계에도 계속 들어간다** — `aggregateRating` 은 제외 목록을 받지 않는다(`ReviewJpaRepository.kt:43-46`).
- 차단을 풀면 **다시 보인다** — 차단 해제는 소프트 삭제이고, 재차단은 같은 행의 부활이다.

테스트가 이 경계를 그대로 문장으로 적어놨다 — "A 의 리뷰 목록에서 B 의 리뷰만 사라지고, **B 의 화면과 집계는 그대로다**"(`api/src/test/kotlin/com/kbap/api/review/ReviewBlockFilterTest.kt:135`).

### 8-3. 차단·신고·좋아요가 공유하는 한 가지 패턴

셋 다 "쌍당 1행, 취소는 소프트 삭제, 재등록은 부활"이다. 그리고 셋 다 같은 문제를 만난다 — **소프트 삭제된 행이 유니크 키를 점유하고 있어서** 재등록 때 `save()` 가 유니크 위반으로 터진다. 해법도 셋 다 같다.

```kotlin
// 신규·중복·재차단(부활)을 한 문장으로 원자 처리 — 트랜잭션 안 save() 예외 폴백은 rollback-only 마킹으로 불가
@Modifying
@Query(
    value = """
        INSERT INTO member_block (blocker_member_id, blocked_member_id, status, created_at, updated_at)
        VALUES (:blockerMemberId, :blockedMemberId, 'ACTIVE', NOW(6), NOW(6))
        ON DUPLICATE KEY UPDATE status = 'ACTIVE', updated_at = NOW(6)
    """,
    nativeQuery = true,
)
```
`common/src/main/kotlin/com/kbap/common/domain/block/MemberBlockJpaRepository.kt:10-16`

`ReviewLikeJpaRepository.upsertActive` 도 글자만 다르고 똑같다(`common/src/main/kotlin/com/kbap/common/domain/review/ReviewLikeJpaRepository.kt:15-29`).

주석의 뒷부분이 진짜 이유다. **"트랜잭션 안 `save()` 예외 폴백은 rollback-only 마킹으로 불가"** — `try { save() } catch (유니크 위반) { 되살리기 }` 를 트랜잭션 안에서 하면, 예외가 난 순간 Spring 이 그 트랜잭션을 이미 "롤백 확정"으로 표시해버려서 catch 블록 안에서 뭘 해도 커밋되지 않는다. FE 에서 `try/catch` 로 복구하는 감각이 여기서는 안 통한다. 그래서 **DB 한 문장으로 원자 처리**한다.

> [!note] 신고는 왜 `try/catch` 를 쓰나
> `ReportService.createReport` 는 `catch (_: DataIntegrityViolationException) { throw BusinessException(REPORT_DUPLICATED) }` 를 쓴다(`api/src/main/kotlin/com/kbap/api/report/ReportService.kt:44-46`). 부활이 아니라 **거절**이라서 가능하다 — 어차피 이 트랜잭션은 실패로 끝날 것이므로 rollback-only 여도 상관없다. "예외를 잡아서 계속 진행" 은 불가능해도, "예외를 잡아서 더 친절한 에러로 바꾸기" 는 된다.
> 신고는 취소가 없어 소프트 삭제 행과 유니크 키가 충돌할 일도 없다(`V2026.08.01.05.16.32__report_table.sql:4-5`).

원장 테스트가 특히 볼 만하다. `member_ranking_event` 를 **JDBC 로 직접 SELECT** 해서 델타를 확인한다.

```kotlin
`when`("중간 리뷰를 삭제하면") {
    then("REVIEW_DELETED -1/0 이벤트가 추가돼 이력 2건이 된다") {
```

`api/src/test/kotlin/com/kbap/api/review/ReviewControllerTest.kt:818-829`

그리고 §6-4 의 사고 시나리오가 그대로 테스트로 있다.

```kotlin
`when`("같은 리뷰를 동시에 2번 삭제하면") {
    then("정확히 1번만 성공하고 카운트는 1번만 차감된다") {
        ...
        statuses.first() shouldBe 200

        rankingCounts(memberId) shouldBe (1 to 1)
    }

```
`api/src/test/kotlin/com/kbap/api/review/ReviewControllerTest.kt:897-920`

`CountDownLatch` 로 두 스레드를 같은 순간에 출발시킨다. 400 이면 §6-4 의 ①·②가, 409 면 ③이 잡은 것이다 — **둘 중 뭐가 이겼든 카운트는 한 번만 깎였다**는 게 검증 대상이다. `(400, 409)` 중 하나를 허용하는 이 느슨함 자체가 "타이밍에 따라 어느 겹이 잡을지는 다르지만 결과는 같아야 한다"는 요구사항의 정확한 표현이다.

바로 아래 "수정과 삭제가 동시에 겹치면" 테스트는 한 발 더 나간다 — 최종 상태가 `DELETED` 면 카운트 `(0,0)`, 아니면 `(1,1)`. **어느 쪽이 이겨도 상관없지만 어긋나면 안 된다.**

## 11. 경계를 넘는 지점 — 정리

| 넘는 곳 | 어디서 | 왜 넘나 |
|---|---|---|
| **`:api` → `:common`** | `ReviewService` 가 `common.domain.review.*`·`common.domain.member.*` 를 직접 import | 리포지토리와 엔티티는 `:common` 소유. 반대 방향(`:common` → `:api`)은 ArchUnit 이 금지([[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]) |
| **트랜잭션 열림** | `ReviewService.createReview`/`deleteReview` (`@Transactional`) | 여러 테이블을 원자적으로 바꿔야 함. Controller 에는 붙지 않는다([[6. 설정과 프로필, 트랜잭션 경계]]) |
| **트랜잭션 합류** | `memberService.increaseReviewCount` 등 | 전파 `REQUIRED` — 새로 열지 않고 바깥에 합류. 그래서 함께 롤백된다 |
| **도메인 간 호출** | `ReviewService` → `FoodService`·`MemberService`·`UploadedImageService`·`MemberBlockService` | kbap 은 도메인 간에 **서비스를 직접 부른다.** 이벤트 버스도 파사드도 없다 — 모듈러 모놀리스의 현실적 선택([[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]) |
| **트랜잭션 밖** | S3 에 올라간 리뷰 사진 | 롤백해도 파일은 남는다. 21번의 고아 객체 |
| **`common.port.*` 통과** | **없음** | 리뷰 흐름은 외부 시스템을 하나도 안 부른다. DB 만 쓴다. [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] 의 포트가 여기엔 등장하지 않는 게 정상이다 |

마지막 줄이 의외로 중요하다. 이 노트가 다루는 흐름은 **kbap 에서 가장 순수한 CRUD** 다 — LLM 도, S3 도, Redis 도, SQS 도 없다. 그래서 트랜잭션과 DB 제약만으로 정합성을 지킬 수 있다. 반대로 20번(스캔 v2)처럼 외부 호출이 끼면 그게 불가능해져서 Redis 예약 같은 별도 장치가 필요해진다.


## 15. 용어집

| 말 | 뜻 |
|---|---|
| 원장(ledger) | 잔액을 바꾼 사건을 행으로 남기는 테이블. 여기선 `member_ranking_event` |
| 보상 이벤트 | 취소를 행 삭제가 아니라 반대 부호 행 추가로 표현하는 것 |
| 멱등 | 같은 요청을 N 번 보내도 결과가 1번과 같음 |
| TOCTOU | 검사(check)와 사용(use) 사이에 상태가 바뀌는 경합. 앱 레벨 중복 검사가 못 막는 틈 |
| 낙관적 락 | 버전 숫자로 "내가 읽은 뒤 아무도 안 건드렸을 때만" UPDATE 를 허용 |
| 센티널 값 | 의미를 담은 특수값. 여기선 "제외할 게 없음"을 뜻하는 `-1L` |
| 뷰어 필터 | 보는 사람에 따라 결과가 달라지는 조회 조건 |
| 복합 keyset | 커서를 (정렬 지표, id) 쌍으로 만들어 동점을 처리하는 페이징 |
| 스냅샷 컬럼 | 조인 대신 작성 시점 값을 복사해 박아둔 컬럼. 여기선 `author_country_code` |

## 16. 체크리스트 — 이 노트를 덮고 말할 수 있어야 하는 것

- [ ] `POST /api/reviews` 한 번이 읽는 테이블 3개와 쓰는 테이블 3개를 댈 수 있다
- [ ] 리뷰를 쓸 자격이 무엇인지, 수정에는 왜 그 자격이 다시 필요 없는지 말할 수 있다
- [ ] 잔액(카운트 컬럼)과 거래 내역(원장)을 왜 둘 다 두는지 설명할 수 있다
- [ ] 삭제가 원장에서 행을 지우지 않고 무엇을 하는지 안다
- [ ] `uq_member_ranking_event` 가 없을 때 벌어지는 사고를 한 문장으로 말할 수 있다
- [ ] 앱 레벨 `if` 검사가 왜 유니크 제약을 대체하지 못하는지 안다
- [ ] `^/api/reviews$` 정규식의 `^`·`$` 가 없으면 무엇이 뚫리는지 안다
- [ ] `ReviewRepositoryCustomImpl` 이 존재하는 이유를 조합 개수로 설명할 수 있다
- [ ] `latest` 커서와 나머지 정렬의 커서가 왜 형식이 다른지 안다
- [ ] 내가 차단한 사람의 리뷰가 **어디까지** 사라지고 어디는 그대로인지 말할 수 있다
- [ ] `listOf(-1L)` 이 왜 필요한지 안다
- [ ] 50건 목록을 만드는 데 쿼리가 몇 개 나가는지, 왜 페이지 크기와 무관한지 안다
