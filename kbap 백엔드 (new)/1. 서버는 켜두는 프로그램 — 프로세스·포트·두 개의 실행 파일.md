# 1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일

> 작성: 2026-08-27 · 맥락: 지금까지 내가 쓴 코드는 전부 **화면을 그리는 코드**였다. 앱을 켜면 시작되고, 앱을 끄면 사라진다. 백엔드는 그 반대편이다 — 아무도 안 보고 있어도 계속 떠 있고, 누가 부르기를 기다린다. 이 세계관 전환이 안 되면 뒤 노트 전부가 공중에 뜬다.
> 목표: `./gradlew :api:bootRun` 을 쳤을 때 **무슨 일이 일어나는지**, 그게 `npx expo start` 와 어떻게 다른지, 그리고 kbap 에 왜 실행 파일이 **두 개**인지 말할 수 있게 된다.

---

## 0. 한 줄 요약

**서버는 한 번 켜면 끄기 전까지 죽지 않고 도는 프로그램이고, "포트"라는 번호표 하나를 붙잡고 앉아 요청이 오기를 무한정 기다린다.** kbap 에는 그런 프로그램이 두 개 있다 — 사람의 요청을 받는 `:api` 와, 시켜야 일하는 `:batch`.

## 1. 핵심 개념

| 용어 | 정체 | FE에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| **프로세스** | 지금 컴퓨터에서 **실행 중인 프로그램 하나**. 자기 메모리를 가지고, 끝나거나 죽기 전까지 산다 | 크롬 탭 하나, 또는 `npx expo start` 를 띄운 그 터미널 |
| **포트(port)** | 한 컴퓨터 안에서 프로그램을 구분하는 **번호**(0~65535). 한 번호는 한 프로그램만 차지한다 | Metro 번들러가 `8081` 을 잡는 것 — 이미 켜져 있으면 "포트 사용 중"이 뜬다 |
| **바인딩(binding)** | 프로세스가 특정 포트를 **점유하고 대기 상태로 들어가는 것** | `expo start` 가 8081 을 잡고 "waiting on..." 을 찍는 순간 |
| **`localhost`** | "이 컴퓨터 자신"을 가리키는 주소(`127.0.0.1`) | Expo 앱에서 `http://localhost:8080` 으로 백엔드를 부를 때의 그 localhost |
| **진입점 / `main`** | JVM이 프로그램을 시작할 때 **가장 먼저 부르는 함수**. 딱 하나여야 한다 | `index.js` / `App.tsx` — 앱이 시작되는 파일 |
| **jar** | 컴파일된 클래스와 라이브러리를 묶은 **배포 단위 파일 하나** | 번들된 `.js` + 에셋 = `.apk`/`.ipa` |
| **bootJar** | 그중 **`main` 이 들어 있어 `java -jar` 로 바로 실행되는** jar. 스프링 부트가 만들어 준다 | 실행 가능한 빌드 산출물 |

> 이 노트에서 새로 나오는 용어는 위 7개뿐이다. 스프링·빈·계층 같은 말은 아직 하나도 안 쓴다 — 그건 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] 부터다.

## 2. 원리 — "켜 둔다"가 정확히 무슨 뜻인가

### 2-1. FE 프로그램과 서버 프로그램의 수명이 다르다

React Native 앱의 코드는 **사용자가 앱을 켤 때** 실행되고 **끌 때** 사라진다. 코드가 사는 곳은 사용자 손안의 폰이고, 사용자 수만큼 복사본이 돈다. 코드가 실행되는 시간은 사용자가 화면을 보고 있는 그 몇 분이다.

서버 코드는 정반대다.

| | RN/Expo 앱 | kbap 서버(`:api`) |
|---|---|---|
| 어디서 도나 | 사용자 폰마다 한 벌씩 | AWS의 서버 한두 대 |
| 언제 시작하나 | 사용자가 앱 아이콘을 누를 때 | **배포할 때 한 번**. 그 뒤로 안 끈다 |
| 언제 끝나나 | 사용자가 앱을 끌 때 | 배포로 교체하거나, 죽거나(장애), 끌 때 |
| 몇 명이 쓰나 | 그 사용자 한 명 | **동시에 전부** |
| 상태 | 그 사람의 화면 상태 | 모두가 공유하는 데이터 |

마지막 두 줄이 백엔드 코드의 거의 모든 어려움을 만든다. "몇 명이 동시에 쓰나"는 [[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]] 가, "모두가 공유하는 데이터"는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 이 받는다.

### 2-2. 무한 루프가 아니라 "대기"다

"계속 도는 프로그램"이라고 하면 `while (true) {}` 를 떠올리기 쉬운데, 그러면 CPU가 100%로 탄다. 실제로는 **아무 일도 안 하면서 커널이 깨워 주기를 기다리는** 상태다. 정확히는 이런 순서다.

1. 프로그램이 시작한다 (`main` 실행)
2. 8080번 포트를 **잡는다**(bind) — 이미 다른 프로그램이 잡고 있으면 여기서 실패하고 죽는다
3. "8080으로 뭔가 오면 깨워 줘"라고 운영체제에 등록하고 **잠든다**(CPU 0%)
4. 요청이 오면 운영체제가 깨운다 → 처리한다 → 응답을 돌려준다 → **다시 3번으로**
5. 종료 신호를 받을 때까지 3~4를 반복한다

`npx expo start` 를 켜 놓으면 터미널이 안 돌아오고 커서가 멈춰 있는 그 상태 — 그게 정확히 3번이다. Metro 번들러도 서버다. **이미 서버를 켜 본 적이 있는 셈이다.**

### 2-3. `localhost:8080` 을 쪼개 읽기

FE 코드에서 백엔드를 부를 때 이렇게 쓴다.

```
http://localhost:8080/api/home
└─┬─┘  └───┬────┘ └┬┘ └──┬──┘
프로토콜  어느 컴퓨터  어느 포트  그 프로그램 안 어느 기능
```

- **`localhost`** — 지금 이 컴퓨터. 그래서 내 맥에서 `:api` 를 띄우고 브라우저로 `localhost:8080` 을 열면 내 맥의 그 프로세스에 닿는다. ⚠️ **폰 시뮬레이터/실기기에서 `localhost` 는 "폰 자신"**이라 내 맥의 서버에 안 닿는다 — 맥의 LAN IP(`192.168.x.x`)를 써야 한다. 이건 이미 겪어 본 문제다 → [[Metro 연결 실패 — Mac·폰 IP 불일치 (link-local·서브넷)]] (거기선 Metro 의 8081, 여기선 `:api` 의 8080 일 뿐 원인이 같다). 배포 환경에서는 `https://dev.kbap.site` 처럼 도메인이 이 자리에 온다.
- **`8080`** — 그 컴퓨터 안에서 **어느 프로그램인지**. 컴퓨터 한 대에 프로그램은 여럿 뜰 수 있으니 번호로 구분한다.
- **`/api/home`** — 여기서부터가 그 프로그램 **안쪽** 이야기다. 이 경로를 누가 어떻게 받는지는 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] 와 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]].

kbap `:api` 의 포트가 8080인 이유는 **아무도 안 정했기 때문**이다. `api/src/main/resources/` 의 어느 yml에도 `server.port` 가 없다 — 스프링 부트 공식 문서의 *"By default, the embedded server listens for HTTP requests on port 8080"* 이 그대로 적용된다.

> [!note] "embedded server"라는 말
> 예전 자바 웹 개발은 톰캣(Tomcat)이라는 **웹 서버 프로그램을 따로 설치**하고, 거기에 내 코드를 담은 파일을 **집어넣는** 방식이었다. 스프링 부트는 그 톰캣을 **내 실행 파일 안에 통째로 넣어 버렸다**(embedded). 그래서 `java -jar app.jar` 한 줄이면 웹 서버가 뜬다. 별도로 설치할 웹 서버가 없다.

## 3. 비유 — 앱은 방문객, 서버는 가게

FE 앱은 **손님이 들고 다니는 물건**이다. 손님이 꺼내면 켜지고 집어넣으면 꺼진다.

서버는 **가게**다.
- 손님이 하나도 없어도 **불을 켜 두고 문을 열어 둔다**(대기).
- 주소가 있어야 손님이 찾아온다 — 그게 도메인+포트다.
- 한 주소에 가게는 하나만 있을 수 있다 — 포트 충돌.
- 여러 손님이 **동시에** 들어온다 — 그래서 "지금 몇 명이 안에 있나"가 문제가 된다([[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]]).
- 가게가 갑자기 문을 닫으면(장애) 손님은 그냥 못 들어온다. 그래서 **누가 계속 문이 열려 있는지 확인**한다(§8 헬스체크).

**어디까지 같고 어디서부터 다른가**: 가게는 "손님이 없는 시간"이 있지만, 서버는 그런 시간에도 **여전히 요금이 나간다**(EC2/ECS 인스턴스 비용). 그래서 뒤에 나올 배치는 "필요할 때만 트럭을 부른다"에 가깝다 — 고 하고 싶지만 kbap 은 그것도 켜 두고 있다(§5-3에서 정직하게 다룬다).

## 4. 진입점 — `main` 함수는 어디 있나

kbap-server 를 클론해서 처음 열면 파일이 수백 개다. **"어디서부터 실행되지?"** 의 답은 딱 두 파일이다.

`api/src/main/kotlin/com/kbap/KbapApiApplication.kt:1-11`

```kotlin
package com.kbap

import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.runApplication

@SpringBootApplication
class KbapApiApplication

fun main(args: Array<String>) {
	runApplication<KbapApiApplication>(*args)
}
```

줄 단위로 읽으면 (레포는 코드에 주석을 달지 않는 규약이라 풀이는 여기 둔다):

- `:6` `@SpringBootApplication` — "이 클래스가 앱의 시작점이다"라는 표시. 이 애너테이션 하나가 **부품 조립·자동 설정·패키지 스캔** 세 가지를 켜는데, 그게 무슨 뜻인지는 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] 의 주제다. 지금은 "여기가 시작"만 알면 된다.
- `:7` 클래스 본문이 **비어 있다**(`{}` 조차 없다). 진짜 아무것도 안 한다 — 표지판일 뿐이다.
- `:9-11` `main` — JVM이 부르는 진짜 첫 함수. `runApplication<...>` 이 스프링을 띄우고, 그 안에서 톰캣이 8080을 잡고, **이 함수가 리턴하지 않은 채** 대기 상태로 들어간다. §2-2의 1~3번이 이 한 줄이다.

**FE 대응**: `index.js` 의 `registerRootComponent(App)` 한 줄과 같은 자리다. 실제 로직은 하나도 없고 "여기서 시작해"만 있다.

두 번째 진입점은 다른 모듈에 있다.

`batch/src/main/kotlin/com/kbap/batch/KbapBatchApplication.kt:7-13`

```kotlin
@SpringBootApplication(scanBasePackages = ["com.kbap.batch", "com.kbap.common.infra.llm"])
@AutoConfigurationPackage(basePackages = ["com.kbap"])
class KbapBatchApplication

fun main(args: Array<String>) {
    runApplication<KbapBatchApplication>(*args)
}
```

- `:7` `scanBasePackages` — api 쪽은 아무 인자가 없었는데 여기엔 있다. 기본값은 "**이 클래스가 있는 패키지 아래 전부**"인데, 배치는 자기 패키지(`com.kbap.batch`) 밖의 것도 일부 써야 해서 명시했다.
- `:8` `@AutoConfigurationPackage(basePackages = ["com.kbap"])` — 엔티티(DB 테이블과 짝지어진 클래스)를 찾을 범위를 `com.kbap` 전체로 넓힌다. 배치도 같은 DB를 읽고 쓰기 때문이다.
- `:11-13` `main` — api와 글자 그대로 똑같다.

이 두 애너테이션 인자가 왜 필요한지는 [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] 와 [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] 에서 다시 만난다. 지금 붙잡을 사실은 하나다 — **`main` 이 두 개다.**

## 5. 왜 실행 파일이 두 개인가

### 5-1. 모듈은 3개, 실행 파일은 2개

`settings.gradle.kts:20-24`

```kotlin
include(
    ":common",
    ":api",
    ":batch",
)
```

`:common` 에는 `main` 이 없다. 둘이 함께 쓰는 **라이브러리**다(도메인 모델, DB 접근, 외부 시스템 계약). 나머지 둘만 혼자 실행될 수 있고, 그래서 **bootJar는 2개**다.

`Dockerfile:10` 과 `Dockerfile.batch:12` 를 나란히 보면 정확히 이 둘을 따로 굽는 것이 보인다.

```
 && ./gradlew :api:bootJar   -x test --no-daemon     ← Dockerfile:10
 && ./gradlew :batch:bootJar -x test --no-daemon     ← Dockerfile.batch:12
```

`-x test` 는 "테스트는 빼고 빌드해라"(테스트는 CI에서 따로 돈다). 이미지가 두 개라는 건 **배포도 따로, 재시작도 따로, 늘리고 줄이는 것도 따로**라는 뜻이다.

### 5-2. 왜 하나로 안 합쳤나

한 프로그램에 다 넣으면 이런 일이 생긴다.

| | 사용자 요청 처리 | 배치 작업 |
|---|---|---|
| 언제 도나 | 항상, 예측 불가 | 정해진 시각 또는 시켰을 때 |
| 한 번에 얼마나 | 짧게(수십~수백 ms) | 길게(수 분~수십 분) |
| 늘려야 할 때 | 사용자가 몰릴 때 | 처리할 데이터가 많을 때 |
| 죽으면 | 사용자가 즉시 못 쓴다 | 다음 트리거에 다시 하면 된다 |

같은 프로세스에 두면 **무거운 배치 작업이 CPU와 메모리를 잡아먹는 동안 사용자 요청이 느려진다.** 반대로 사용자 트래픽 때문에 서버를 늘리면 배치도 같이 복제돼서 **같은 일을 여러 번 하게 된다.** 수명·부하 모양·실패 대응이 다르면 프로세스를 나누는 게 정석이다.

### 5-3. 정직하게 — "일하고 죽는 프로그램"은 아니다

배치를 설명할 때 흔히 "요청을 기다리는 프로그램 vs 할 일을 하고 죽는 프로그램"으로 가르는데, **kbap 의 `:batch` 는 그 후자가 아니다.** 실측하면 이렇다.

`batch/build.gradle.kts:11-12`

```kotlin
    "implementation"("org.springframework.boot:spring-boot-starter-batch")
    "implementation"(libs.spring.boot.starter.web)
```

배치도 **web 스타터를 의존한다** — 즉 톰캣이 뜨고 포트를 잡는다. `batch/src/main/resources/application.yml:36-37` 에 `server.port: 8080` 이 명시돼 있고, `Dockerfile.batch:3-5` 의 설명이 못을 박는다.

> 배치 앱(:batch) — 상시 기동되며 잡은 `POST /internal/batch/jobs?jobName=` 로 비동기 트리거하고 `GET /internal/batch/executions/{id}` 로 결과를 폴링한다. 8080 은 도커 네트워크 안에서만 쓰므로 호스트로 publish 하지 않는다.

그러니까 **둘 다 켜 두는 프로그램**이고, 차이는 수명이 아니라 **누가 부르느냐**다.

| | `:api` | `:batch` |
|---|---|---|
| 부르는 쪽 | 사용자 폰 (앱) | 내부 시스템 — 젠킨스·스케줄러, 그리고 자기 자신의 cron |
| 포트를 밖에 여나 | 연다 (ALB → 8080) | **안 연다** — 도커 네트워크 안에서만 |
| 하는 일 | 요청 하나를 짧게 처리 | 잡 하나를 길게 돌리고 진행 상황을 DB에 적음 |

⚠️ `docs/guides/batch-deploy.md:3-4` 는 아직 *"상시 서비스가 아니라 run-to-completion ECS 태스크"* 라고 적혀 있다 — **낡은 문서다.** 코드와 문서가 어긋나면 코드가 정본이다. 자세한 대조는 [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] §5-4.

## 6. 실행하는 법

### 6-1. 개발할 때 — Gradle

```bash
./gradlew :api:bootRun      # web 앱 실행
./gradlew :batch:bootRun    # 배치 앱 실행
```

- `./gradlew` 는 **Gradle 래퍼**다. Gradle을 따로 설치하지 않아도 되고 팀원 전부 같은 버전으로 빌드된다. `npx`(설치 없이 실행) + lockfile(버전 고정)을 한 파일로 합친 것에 가깝다.
- `:api:bootRun` 은 "`:api` 모듈의 `bootRun` 작업을 실행하라". 콜론이 모듈 경로다.
- 앞에 프로필을 붙여야 DB 주소가 채워진다: `SPRING_PROFILES_ACTIVE=local ./gradlew :api:bootRun`. 프로필이 뭔지는 [[6. 설정과 프로필, 트랜잭션 경계]].
- Gradle 자체(모듈·버전 카탈로그·buildSrc)는 [[3. JVM 위의 Kotlin — 컴파일·널 안전·Gradle 3모듈]] 이 정본이다.

> [!warning] `:api` 와 `:batch` 를 동시에 띄우면 포트가 충돌한다
> 둘 다 로컬에서 8080이다(`:api` 는 기본값, `:batch` 는 `application.yml:37` 에 명시). 동시에 필요하면 한쪽에 다른 포트를 주면 된다 — `./gradlew :batch:bootRun --args='--server.port=8081'`.

### 6-2. 배포할 때 — Docker 이미지 두 개

`Dockerfile`(api) 과 `Dockerfile.batch`(batch) 는 구조가 같다. 둘 다 **멀티스테이지 빌드**다.

`Dockerfile:6-14, 24-26`

```dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace
COPY . .
RUN chmod +x gradlew \
 && ./gradlew :api:bootJar -x test --no-daemon \
 && find api/build/libs -name '*.jar' ! -name '*-plain.jar' -exec cp {} /workspace/app.jar \;

FROM eclipse-temurin:21-jre AS runtime
…
COPY --from=build /workspace/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

- `:6` **빌드 스테이지**는 `jdk`(컴파일러 포함) 이미지에서 소스를 통째로 컴파일한다.
- `:11` 만들어진 jar 중 `-plain.jar` 을 **제외**하고 고른다. 스프링 부트는 jar를 두 개 만드는데, `-plain` 쪽은 라이브러리가 안 들어간 껍데기라 혼자 실행되지 않는다. 실행 가능한 쪽이 bootJar 다.
- `:13` **런타임 스테이지**는 `jre`(실행기만) 이미지로 갈아탄다. 컴파일러와 소스가 최종 이미지에 안 들어가서 이미지가 작아진다. RN에서 소스를 번들해 앱에 넣고 소스 자체는 안 넣는 것과 같은 발상이다.
- `:26` `ENTRYPOINT` — 컨테이너가 시작될 때 실행할 명령. `java -jar` 하나면 서버가 뜬다.

`Dockerfile.batch` 는 `:batch:bootJar` 를 굽고 `EXPOSE` 가 없다는 점만 다르다(§5-3의 "포트를 밖에 안 연다").

## 7. 로컬에서 서버 하나 띄우려면 뭐가 필요한가

FE 에서 `npm start` 한 줄이면 개발이 시작되던 것과 여기서 크게 갈린다. **서버는 혼자 못 뜬다** — 데이터를 맡길 DB가 있어야 하고, 세션을 넣어 둘 Redis가 있어야 한다.

`docker-compose.yml` 이 그 주변 장치들의 목록이다. 실측하면 서비스가 세 개다.

| 서비스 | 이미지 | 포트 | 왜 필요한가 |
|---|---|---|---|
| `app` | `Dockerfile` 로 직접 빌드 | 8080 | `:api` 본체 |
| `mysql` | `mysql:8.4` | 3306 | 회원·음식·리뷰… 실제 데이터가 사는 곳 |
| `redis` | `redis:8` | 6379 | refresh 토큰 세션, 스캔 예약 |

`docker-compose.yml:35-40`

```yaml
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped
```

- `:35-39` **앱은 DB와 Redis가 "건강해진 뒤에" 뜬다.** MySQL 컨테이너는 시작 후 초기화에 몇 초가 걸리는데, 그 전에 앱이 붙으면 연결 실패로 죽는다. `condition: service_healthy` 는 `:60-64` 의 `healthcheck`(`mysqladmin ping` 이 통과할 때까지)를 기다리라는 뜻이다.
- `:40` `restart: unless-stopped` — 앱이 죽으면 도커가 **자동으로 다시 띄운다**(§8).

실무에서 가장 많이 쓰는 조합은 파일 머리말 `:7` 에 적힌 이것이다.

```bash
docker compose up -d mysql   # DB 만 도커로 띄우고
./gradlew :api:bootRun       # 앱은 IDE/터미널에서 직접 (코드 고치고 바로 재시작하려고)
```

`redis` 도 필요하면 함께 띄운다. Redis 를 왜 두는지는 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식|29. 캐싱과 키-값 저장소]]에서 다룬다.

### 7-1. 서버가 아예 안 뜨는 가장 흔한 이유들

FE 라면 런타임에 터졌을 일이 백엔드에서는 **부팅 자체를 거부하는** 것으로 나온다. 이게 좋은 설계다 — 반쯤 망가진 채로 떠서 사용자 요청을 받는 것보다, 아예 안 뜨고 로그를 남기는 게 낫다(fail-fast).

**① JWT 서명 키가 없거나 짧다**

`api/src/main/kotlin/com/kbap/api/infra/auth/token/JwtTokenProperties.kt:5-18`

```kotlin
data class JwtTokenProperties(
    val secret: String,
    val accessTtl: Duration,
    val refreshTtl: Duration,
) {
    init {
        require(secret.toByteArray().size >= MIN_SECRET_BYTES) {
            "kbap.auth.jwt.secret 는 ${MIN_SECRET_BYTES}바이트 이상이어야 합니다"
        }
    }

    companion object {
        private const val MIN_SECRET_BYTES = 32
    }
}
```

- `:10-14` 이 객체가 **만들어지는 순간** 검사한다. `require` 는 조건이 거짓이면 예외를 던지는 코틀린 표준 함수다.
- 이 객체는 앱이 시작할 때 조립되는 부품 중 하나라, 여기서 예외가 나면 **조립이 실패하고 앱이 안 뜬다.** `JWT_SECRET` 을 `.env` 에 32바이트 이상으로 채우면 된다(`openssl rand -base64 32`).
- `docker-compose.yml:30` 도 같은 방어를 한 겹 더 한다 — `JWT_SECRET` 이 없으면 **컨테이너를 만들기도 전에** compose 가 에러를 낸다.

**② 포트 8080이 이미 사용 중** — 이전에 띄운 서버가 안 죽었거나 `:api` 와 `:batch` 를 같이 띄웠다. `lsof -i :8080` 으로 범인을 찾는다.

**③ DB 스키마가 코드와 안 맞는다** — `api/src/main/resources/application-local.yml:12-13` 이 `ddl-auto: validate` 다. "테이블 구조가 엔티티와 맞는지 검사만 하고, 안 맞으면 부팅을 거부해라"라는 뜻이다(자동으로 고치지 **않는다**). 스키마는 [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] 가 관리한다.

**④ `.env` 를 만들지 않았다** — `cp .env.example .env` 후 값을 채운다. 다만 `local` 프로필은 대부분 `localhost` 기본값을 갖고 있어서 `JWT_SECRET` 만 있으면 대체로 뜬다.

## 8. 서버가 죽으면 어떻게 되나

프로세스도 프로그램이라 죽는다 — 메모리를 다 쓰거나(OOM), 배포 중이거나, 서버 장비가 재부팅되거나. 대비는 두 층으로 되어 있다.

### 8-1. 죽으면 다시 띄운다

로컬에서는 도커가 한다 — `docker-compose.yml:40` 의 `restart: unless-stopped`("내가 직접 멈춘 게 아니면 다시 띄워라"). 배포 환경에서는 ECS가 같은 일을 한다. **서버 코드에 "죽지 않게 하는 코드"를 쓰는 게 아니라, 죽으면 다시 띄우는 바깥 장치를 두는 것**이 백엔드의 기본 사고방식이다.

### 8-2. "살아 있음"을 어떻게 아나 — 헬스체크

프로세스가 살아 있는 것과 **요청을 제대로 처리할 수 있는 것**은 다르다. JVM은 떠 있는데 DB 연결이 끊겼다면, 그 서버로 요청을 보내면 전부 실패한다. 그래서 바깥에서 주기적으로 **"지금 요청 받을 수 있어?"를 물어보는 전용 주소**를 둔다.

kbap은 `spring-boot-starter-actuator`(`api/build.gradle.kts:26`)를 넣어서 그 주소를 얻는다. 액추에이터는 앱 상태를 들여다보는 표준 엔드포인트 묶음이고, 공식 문서상 **HTTP로 기본 노출되는 건 `/actuator/health` 하나**다.

실제로 그 주소를 두 군데서 쓴다.

`iac/terraform/modules/ecs-environment/alb.tf:21-28`

```hcl
  health_check {
    path                = "/actuator/health/readiness"
    matcher             = "200"
    interval            = 15
    timeout             = 5
    healthy_threshold   = 2
    unhealthy_threshold = 3
  }
```

- `:22` 로드밸런서(사용자 요청을 서버들에 나눠 주는 앞단)가 **15초마다** 이 주소를 찔러 본다.
- `:27-28` 2번 연속 성공하면 "정상"으로 보고 트래픽을 보내고, **3번 연속 실패하면 그 서버로 요청을 안 보낸다.** 사용자는 장애를 못 느낀다 — 남은 서버가 받는다.

`iac/terraform/modules/ecs-environment/api.tf:46-51` 은 컨테이너 자체의 체크다.

```hcl
      healthCheck = {
        command     = ["CMD-SHELL", "curl -sf http://localhost:8080/actuator/health/readiness || exit 1"]
        interval    = 15
        timeout     = 5
        retries     = 3
        startPeriod = 150
      }
```

- `startPeriod = 150` — **뜨는 데 150초까지는 봐준다.** 자바 앱은 시작이 느리다(JVM 기동 + 부품 조립 + DB 커넥션 풀 + 마이그레이션). Metro 번들러가 몇 초면 뜨는 것과 대비되는 지점이고, "배포 = 즉시 반영"이 아닌 이유이기도 하다.

> [!question] 확인하지 못한 것 — readiness 경로
> 스프링 부트 공식 문서는 liveness/readiness 하위 그룹을 *"If deployed in a Kubernetes environment"* 자동 활성화한다고 적는다. kbap 은 쿠버네티스가 아니라 ECS이고, 레포 어디에도 `management.endpoint.health.probes.enabled` 나 `spring.main.cloud-platform` 설정이 없다(전수 grep 0건). 나는 **설정 배선만 읽었고 실제 응답은 확인하지 못했다.** 로컬에서 `curl localhost:8080/actuator/health` 와 `.../health/readiness` 를 둘 다 찔러 보면 5초면 판별된다 — 합류 후 첫 주에 해 볼 만한 확인이다.

## 10. 주의점 · 트러블슈팅

| 증상 | 원인 | 확인/해결 |
|---|---|---|
| `Web server failed to start. Port 8080 was already in use` | 이전 프로세스가 안 죽었거나 `:api`+`:batch` 동시 기동 | `lsof -i :8080` → `kill <PID>`, 또는 `--args='--server.port=8081'` |
| `kbap.auth.jwt.secret 는 32바이트 이상이어야 합니다` 로 부팅 실패 | `.env` 에 `JWT_SECRET` 이 없거나 짧음 | `openssl rand -base64 32` 결과를 넣는다 |
| DB 연결 실패로 부팅 실패 | MySQL이 안 떠 있음 | `docker compose up -d mysql` → `docker compose ps` 로 healthy 확인 |
| `Schema-validation: missing table [...]` | 마이그레이션 미적용 (`ddl-auto: validate`) | [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] |
| 폰(시뮬레이터)에서 `localhost:8080` 이 안 닿음 | 폰 입장의 `localhost` 는 폰 자신 | 맥의 LAN IP(`192.168.x.x:8080`) 사용 |
| MySQL 유저(`kbap`)로 접속이 안 됨 | `MYSQL_USER` 는 **볼륨 최초 생성 때만** 만들어진다 (`docker-compose.yml:52-53`) | `docker compose down -v && docker compose up -d` (데이터 초기화됨 — 주의) |
| 배포했는데 몇 분간 반영이 안 됨 | 자바 앱 기동이 느리다 (`startPeriod = 150`) | 정상. 헬스체크 통과 후 트래픽이 넘어간다 |

## 11. 치트시트

```bash
# 실행
SPRING_PROFILES_ACTIVE=local ./gradlew :api:bootRun     # web 앱
SPRING_PROFILES_ACTIVE=local ./gradlew :batch:bootRun   # 배치 앱
./gradlew :batch:bootRun --args='--server.port=8081'    # 포트 바꿔서

# 주변 장치
docker compose up -d mysql redis   # DB·Redis 만 띄우기 (앱은 로컬 실행)
docker compose up -d --build       # 앱까지 통째로 도커로
docker compose ps                  # 상태
docker compose logs -f app         # 앱 로그
docker compose down                # 정지 (데이터 유지)
docker compose down -v             # 정지 + 데이터 초기화

# 확인
lsof -i :8080                                  # 8080 을 누가 잡고 있나
curl localhost:8080/actuator/health            # 살아 있나
```

| 알고 싶은 것 | 볼 파일 |
|---|---|
| 실행 파일이 몇 개인가 | `settings.gradle.kts`, `Dockerfile`, `Dockerfile.batch` |
| 앱이 어디서 시작하나 | `api/src/main/kotlin/com/kbap/KbapApiApplication.kt`<br>`batch/src/main/kotlin/com/kbap/batch/KbapBatchApplication.kt` |
| 포트가 몇 번인가 | api: 아무 데도 없음 = 기본 8080 / batch: `batch/src/main/resources/application.yml:37` |
| 로컬에 뭘 띄워야 하나 | `docker-compose.yml` |
| 환경변수로 뭘 줘야 하나 | `.env.example` |
| 배포 환경이 어떻게 감시하나 | `iac/terraform/modules/ecs-environment/{alb,api}.tf` |

## 12. 용어집

| 용어 | 한 줄 정의 |
|---|---|
| **프로세스** | 실행 중인 프로그램 하나. 자기 메모리를 갖는다 |
| **포트** | 한 컴퓨터 안에서 프로그램을 구분하는 번호. 한 번호 = 한 프로그램 |
| **바인딩** | 프로세스가 포트를 점유하고 대기 상태로 들어가는 것 |
| **`localhost` / `127.0.0.1`** | "이 컴퓨터 자신"을 가리키는 주소 |
| **진입점(`main`)** | JVM이 프로그램 시작 시 가장 먼저 부르는 함수 |
| **jar** | 컴파일 결과물을 묶은 파일 하나 |
| **bootJar** | `main` 과 라이브러리가 다 들어 있어 `java -jar` 로 바로 도는 jar |
| **embedded server** | 실행 파일 안에 내장된 웹 서버(톰캣). 따로 설치할 필요가 없다 |
| **멀티스테이지 빌드** | 도커에서 빌드용 이미지와 실행용 이미지를 분리해 최종 이미지를 줄이는 방식 |
| **fail-fast** | 설정이 잘못되면 반쯤 동작하지 말고 아예 부팅을 거부하는 것 |
| **헬스체크** | 바깥에서 주기적으로 "요청 받을 수 있어?"를 물어보는 전용 요청 |
| **액추에이터(actuator)** | 앱 상태를 들여다보는 스프링 부트 표준 엔드포인트 묶음 |

## 13. 체크리스트

- [ ] "서버는 켜 두는 프로그램"이 `while(true)` 가 아니라 **대기**라는 걸 설명할 수 있다
- [ ] `localhost:8080/api/home` 의 네 조각을 각각 무엇이라고 부르는지 안다
- [ ] kbap 의 `main` 함수 두 개의 파일 경로를 안다
- [ ] 모듈은 3개인데 bootJar는 2개인 이유를 말할 수 있다
- [ ] `:api` 와 `:batch` 의 차이가 **수명이 아니라 "누가 부르느냐"** 임을 안다
- [ ] 로컬에서 `:api` 를 띄우려면 MySQL이 먼저 떠 있어야 함을 안다
- [ ] 서버가 부팅을 거부하는 게 왜 좋은 설계인지(fail-fast) 설명할 수 있다
- [ ] 헬스체크가 왜 "프로세스가 살아 있나"와 다른 질문인지 안다
- [ ] §9의 요청 흐름 그림에서 각 단계가 어느 노트인지 짚을 수 있다
