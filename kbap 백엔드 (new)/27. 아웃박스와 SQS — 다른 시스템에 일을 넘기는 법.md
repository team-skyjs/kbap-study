# 27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법

> 작성: 2026-08-27 · 맥락: 26번에서 배치 앱이 잡을 어떻게 정의하고 기동하는지(골격)를 봤다. 이제 그 잡 하나가 **실제로 무슨 일을 하는지**를 연다. 그런데 이 잡은 일을 *하지* 않는다 — 남에게 넘긴다. 왜 그런가가 이 노트의 주제다.
> 목표: ① **이중 쓰기(dual write)** 가 왜 근본적으로 안전하게 안 되는지, 아웃박스가 그걸 어떻게 우회하는지 말할 수 있게 되기 ② 아웃박스 행의 상태 전이(`PENDING → SENT → COMPLETE`)를 따라가며 **"어디서 중복이 생길 수 있나"** 를 짚을 수 있게 되기 ③ **같은 앱 안 비동기**(`@EventListener` + `@Async`)와 **다른 시스템 큐**(SQS)가 각각 무엇을 보장하고 무엇을 못 보장하는지 구분해 쓸 수 있게 되기.

---

## 0. 한 줄 요약

kbap-server 는 음식 설명을 만드는 LLM 을 **직접 부르지 않는다.** 그 일은 별도 레포 kbap-langchain 으로 이관됐고(KB-301), kbap-server 는 대신 **"이 음식 설명 좀 만들어줘" 라는 부탁을 DB 테이블(`food_content_outbox`)에 한 줄 적어둔다.** 매시 정각 배치 잡이 그 행들을 읽어 **SQS 큐**로 밀어넣고, 랭체인이 결과를 만들어 다시 kbap 의 적재 API 를 호출해 마무리한다. 이 "DB 에 먼저 적고 나중에 발행한다" 가 **아웃박스 패턴**이다.

---

## 1. 이 흐름이 하는 일 — 사용자 관점

사용자가 메뉴판을 스캔했는데 **kbap DB 에 없던 음식**이 나왔다고 하자. 앱은 그 음식을 "정보 준비 중" 으로 보여주고 스캔 결과는 즉시 돌려준다. 몇 시간 뒤 다시 열어보면 설명·매운맛·재료·9개 언어 번역이 채워져 있다.

그 사이에 일어난 일이 이 노트의 전부다. 사용자 요청 하나가 **세 개의 시스템**을 가로지른다.

```
[사용자] 스캔
   ↓
[kbap-server :api]  음식 행 저장 + 아웃박스 행 저장   ← 같은 트랜잭션
   ↓  (여기서 사용자 응답은 이미 끝났다)
[kbap-server :batch] 매시 정각, PENDING 행을 읽어 SQS 로 발행
   ↓
[AWS SQS 큐]  메시지가 여기 누워서 기다린다
   ↓
[kbap-langchain]  (다른 레포·다른 프로세스) 메시지 꺼내 LLM 으로 콘텐츠 생성
   ↓
[kbap-server :api]  POST /api/admin/foods/contents 로 결과 적재 → 아웃박스 COMPLETE
```

핵심은 **화살표 사이사이가 전부 끊길 수 있다는 것**이다. 이 노트는 각 끊김에서 무슨 일이 벌어지는지를 실측으로 따라간다.

---

## 2. 먼저 문제 — 이중 쓰기(dual write)

아웃박스를 이해하려면 **아웃박스가 없으면 뭐가 깨지는지**부터 봐야 한다.

가장 순진한 코드는 이렇게 생겼다(예시 — 레포에 이런 코드는 없다).

```kotlin
@Transactional
fun createIncomplete(names: Map<String, String>) {
    foodRepository.upsertIncomplete(...)   // ① DB 에 쓴다
    sqsClient.sendMessage(...)             // ② 큐에 쓴다
}
```

이 두 줄은 **서로 다른 시스템**을 건드린다. ①은 MySQL, ②는 AWS SQS. `@Transactional` 은 **MySQL 한 대의 트랜잭션**이다([[6. 설정과 프로필, 트랜잭션 경계]]) — SQS 는 그 트랜잭션 안에 없다. 그래서 네 가지가 다 가능하다.

| 순서 | 벌어지는 일 | 결과 |
|---|---|---|
| ① 성공 → ② 성공 | 정상 | 😀 |
| ① 성공 → ② 실패(네트워크 끊김) | 음식은 저장됐는데 **아무도 콘텐츠를 안 만든다** | 😱 영원한 "준비 중" |
| ① 성공 → ② 성공 → **커밋 실패**(롤백) | 음식은 없는데 **메시지는 나갔다** | 😱 없는 음식의 콘텐츠 생성 |
| ② 먼저 → ① 실패 | 위와 같음 | 😱 |

> [!note] FE 비유 — 낙관적 업데이트의 반대 문제
> React Query 에서 `mutate` 성공 뒤 `invalidateQueries` 를 부르는데, mutate 는 성공했고 invalidate 직전에 앱이 죽으면 화면만 낡은 상태로 남는다. 그건 새로고침하면 낫는다 — **읽기**니까. 여기는 **쓰기**다. 낫지 않는다. 아무도 다시 안 부른다.

**"둘 다 성공하거나 둘 다 실패하게" 묶는 방법은 원리적으로 없다.** (분산 트랜잭션·2PC 라는 게 있긴 하지만 MySQL↔SQS 사이에는 존재하지 않고, 있어도 느리고 취약해 현대 시스템은 거의 안 쓴다.)

이게 **이중 쓰기(dual write) 문제**다. 서로 다른 두 저장소에 "원자적으로" 쓰려는 시도는 실패한다.

## 3. 해법 — "메시지를 DB 에 적는다"

아웃박스 패턴의 발상은 얄미울 만큼 단순하다.

> **큐에 못 묶는다면, 큐에 보낼 내용을 DB 에 적어라.** DB 에 적는 건 같은 트랜잭션이니까 원자적이다.

즉 위의 두 줄을 이렇게 바꾼다.

```
① 음식 행 INSERT          ┐
② 아웃박스 행 INSERT       ┘ ← 둘 다 MySQL. 하나의 트랜잭션. 원자적.

--- (커밋) ---

③ 별도 프로세스가 아웃박스 행을 읽어 SQS 로 발행 ← 나중에, 몇 번이고 다시 시도 가능
```

②까지가 원자적이므로 **"음식은 있는데 요청이 없다" 는 상태가 원천적으로 안 생긴다.** ③은 실패해도 행이 그대로 남아 있으니 다음 주기에 또 시도하면 된다.

kbap 에서 ①②를 하는 코드가 이것이다.

```kotlin
@Transactional
fun createIncomplete(displayNamesByMatchKey: Map<String, String>): Map<String, Food> {
    if (displayNamesByMatchKey.isEmpty()) return emptyMap()
    return upsertAndResolve(displayNamesByMatchKey)
}

private fun upsertAndResolve(displayNamesByMatchKey: Map<String, String>): Map<String, Food> {
    foodRepository.upsertIncomplete(...)
    …
    enqueueContentRequests(resolved.values)
    return resolved
}
```
`api/src/main/kotlin/com/kbap/api/food/FoodService.kt:145-162`

- `@Transactional` 하나가 `upsertIncomplete`(음식 저장)와 `enqueueContentRequests`(아웃박스 저장)를 **같은 트랜잭션**으로 감싼다.
- 스캔이 중간에 터지면 둘 다 롤백된다. 스펙 문구 그대로다 — "음식도 수집 요청도 남지 않는다(반쪽 상태 금지)"(`specs/kb-302-langchain-food-ingest/spec.md` US2 시나리오 3, FR-001).

아웃박스 행을 만드는 쪽:

```kotlin
private fun enqueueContentRequests(foods: Collection<Food>) {
    if (foods.isEmpty()) return
    val alreadyPending = outboxRepository
        .findByFoodIdInAndOutboxStatus(foods.map { it.id }, FoodContentOutboxStatus.PENDING)
        .map { it.foodId }
        .toSet()
    outboxRepository.saveAll(
        foods.filterNot { it.id in alreadyPending }.map { FoodContentOutbox.pending(it.id, it.displayName) },
    )
}
```
`api/src/main/kotlin/com/kbap/api/food/FoodService.kt:164-173`

- 이미 `PENDING` 인 요청이 있으면 새로 쌓지 않는다(FR-004). 같은 음식이 여러 스캔에 등장해도 큐에 중복으로 안 들어간다.
- **주의**: 이건 애플리케이션 코드의 필터일 뿐 **DB unique 제약이 아니다**. 두 요청이 동시에 들어오면 둘 다 "없다" 고 읽고 둘 다 INSERT 할 수 있다. 23번의 `uq_member_ranking_event` 처럼 DB 가 막아주는 구조가 아니다([[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]]). 여기서는 **적재가 멱등이라 중복 요청이 치명적이지 않다**는 판단으로 넘어간 것으로 읽힌다.

### 아웃박스 행을 만드는 두 경로

레포에서 아웃박스 행이 생기는 자리는 **딱 둘**이다.

| 경로 | 코드 | 언제 |
|---|---|---|
| 스캔에서 처음 본 음식 | `ScanService.kt:121` → `FoodService.kt:146` | 사용자가 메뉴판을 스캔했는데 DB 에 없는 음식이 나옴 |
| 관리자 일괄 재수집 | `api/admin/AdminFoodService.kt:120-145` | 관리자가 검색 조건에 걸린 음식들의 설명을 다시 만들라고 지시(상한 있음) |

둘 다 같은 `FoodContentOutbox.pending(foodId, displayName)` 을 만든다. **발행 쪽 배치는 이 둘을 구분하지 않는다** — 아웃박스가 두 생산자를 하나의 소비자로 합류시키는 지점이다.

## 4. 아웃박스 테이블 — 상태 컬럼이 전부다

아웃박스 패턴의 핵심은 **테이블 스키마**에 다 들어 있다.

```sql
CREATE TABLE food_content_outbox
(
    id            BIGINT                     NOT NULL AUTO_INCREMENT PRIMARY KEY,
    food_id       BIGINT                     NOT NULL,
    display_name  VARCHAR(255)               NOT NULL,
    outbox_status ENUM ('PENDING','SENT')    NOT NULL DEFAULT 'PENDING',
    attempts      INT                        NOT NULL DEFAULT 0,
    sent_at       DATETIME(6)                NULL,
    status        ENUM ('ACTIVE','DELETED')  NOT NULL DEFAULT 'ACTIVE',
    created_at    DATETIME(6)                NOT NULL,
    updated_at    DATETIME(6)                NOT NULL,
    CONSTRAINT fk_food_content_outbox_food FOREIGN KEY (food_id) REFERENCES food (id),
    INDEX idx_food_content_outbox_status_id (outbox_status, id),
    INDEX idx_food_content_outbox_food (food_id)
);
```
`api/src/main/resources/db/migration/V2026.08.11.04.27.20__food_content_outbox_table.sql:5-19`

한 줄씩:

- **`outbox_status`** — 이 행의 발행 진행도. 아웃박스 패턴의 심장이다. 없으면 배치가 "뭘 아직 안 보냈는지" 를 알 수 없다.
- **`status`** — 이건 완전히 **다른 것**이다. `BaseEntity` 가 모든 테이블에 붙이는 소프트 삭제 플래그다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]). 마이그레이션 주석이 이 혼동을 미리 경고한다 — "outbox_status 는 도메인 상태로, BaseEntity 의 소프트삭제 status 와 컬럼을 분리한다"(:3). **컬럼 이름 두 개가 비슷하게 생겼으니 쿼리 읽을 때 조심하라.**
- **`attempts`** — 발행을 몇 번 시도했나. **뒤에서 다시 다룬다 — 이 값은 기록만 되고 아무 분기에도 안 쓰인다.**
- **`sent_at`** — 최초 발행 시각(`COALESCE` 로 첫 값만 유지).
- **`display_name`** — 발행할 때 메시지 본문에 실을 이름. **음식 테이블을 조인하지 않으려고 여기에 복사해 둔다.** 이 레포는 JPA 연관관계를 쓰지 않는다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]) — `food_id` 는 그냥 `Long` 컬럼이다.
- **`INDEX (outbox_status, id)`** — 배치가 매번 던지는 `WHERE outbox_status = 'PENDING' AND id > ? ORDER BY id` 를 그대로 태우려고 만든 인덱스다. 조건 컬럼이 앞, 정렬·커서 컬럼이 뒤.

하루 뒤에 상태 하나가 더 붙는다.

```sql
ALTER TABLE food_content_outbox
    MODIFY COLUMN outbox_status ENUM ('PENDING','SENT','COMPLETE') NOT NULL DEFAULT 'PENDING';
```
`api/src/main/resources/db/migration/V2026.08.12.00.00.00__food_content_outbox_complete.sql:1-2`

- 처음 설계엔 `COMPLETE` 가 없었다. **"보냈다" 와 "저쪽이 처리를 끝냈다" 는 다른 사건**이라는 걸 뒤늦게 반영한 마이그레이션이다.
- 앞 마이그레이션을 고치지 않고 **새 파일로 추가**했다는 게 포인트다 — Flyway 파일은 한 번 나가면 수정 금지다([[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]).

## 6. 상태 전이 — 실측

세 상태 사이를 오가는 전이는 **네 개의 쿼리**가 전부다. 전부 네이티브 SQL 이다.

```
                   (아웃박스 행 INSERT)
                            ↓
                        PENDING ──── 발행 실패 ────┐
                            │                     │ attempts++ 만 하고 PENDING 유지
                            │ 발행 성공            └──→ (다음 주기에 재시도)
                            ↓
                          SENT ─── 랭체인이 결과를 안 돌려주면 여기서 영구 정체
                            │
                            │ 적재 API 호출 성공
                            ↓
                        COMPLETE ─── 두 번째 적재 호출은 409
```

| 전이 | 쿼리 | 위치 |
|---|---|---|
| (없음) → `PENDING` | `FoodContentOutbox.pending()` INSERT | `FoodService.kt:171`, `AdminFoodService.kt:138` |
| `PENDING` → `SENT` | `recordPublishSucceeded(ids)` | `FoodContentOutboxJpaRepository.kt:62-79` |
| `PENDING` → `PENDING` (실패) | `recordPublishFailed(ids)` — **`attempts` 만 +1** | `FoodContentOutboxJpaRepository.kt:81-93` |
| `PENDING`\|`SENT` → `COMPLETE` | `completeIfProcessable(outboxId, foodId)` | `FoodContentOutboxJpaRepository.kt:38-54` |

성공 전이 쿼리를 뜯어보자. 여기 트릭이 하나 있다.

```sql
UPDATE food_content_outbox
SET attempts = attempts + 1,
    sent_at = COALESCE(sent_at, CURRENT_TIMESTAMP(6)),
    outbox_status = CASE
        WHEN outbox_status = 'PENDING' THEN 'SENT'
        ELSE outbox_status
    END,
    updated_at = CURRENT_TIMESTAMP(6)
WHERE id IN (:ids)
  AND outbox_status IN ('PENDING', 'SENT', 'COMPLETE')
  AND status = 'ACTIVE'
```
`common/src/main/kotlin/com/kbap/common/domain/food/FoodContentOutboxJpaRepository.kt:62-79`

- `CASE WHEN outbox_status = 'PENDING' THEN 'SENT' ELSE outbox_status END` — **`COMPLETE` 를 `SENT` 로 되돌리지 않는다.** 발행 응답이 늦게 도착했는데 그 사이 랭체인이 이미 결과를 적재해 `COMPLETE` 가 됐다면, 이 UPDATE 는 상태를 건드리지 않고 `attempts` 만 올린다. **전이는 앞으로만 간다.**
- `COALESCE(sent_at, …)` — `sent_at` 은 최초 발행 시각으로 고정. 재발행해도 안 바뀐다.
- `status = 'ACTIVE'` — 소프트 삭제된 행은 손대지 않는다.
- 이건 **읽어서 → 판단해서 → 쓰는** 코드가 아니라 **한 문장의 UPDATE** 다. 23번에서 본 원자적 카운트와 같은 계열이다 — 조건 판단을 DB 에 맡겨 경쟁 조건을 없앤다.

닫는 전이도 같은 방식으로 방어한다.

```sql
UPDATE food_content_outbox
SET outbox_status = 'COMPLETE', updated_at = CURRENT_TIMESTAMP(6)
WHERE id = :outboxId
  AND food_id = :foodId
  AND outbox_status IN ('PENDING', 'SENT')
  AND status = 'ACTIVE'
```
`common/src/main/kotlin/com/kbap/common/domain/food/FoodContentOutboxJpaRepository.kt:38-54`

- `AND food_id = :foodId` — **outboxId 와 foodId 의 조합**이 맞아야 한다. 랭체인이 엉뚱한 조합을 보내면 0행 갱신 → 400.
- `outbox_status IN ('PENDING', 'SENT')` — 이미 `COMPLETE` 면 0행. 그 0행을 **호출자가 어떻게 해석하는지**가 다음 절이다.

> [!warning] `PENDING` 상태에서도 `COMPLETE` 가 될 수 있다
> `completeIfProcessable` 의 조건에 `PENDING` 이 들어 있다. 즉 **아직 발행 안 한 행에 결과가 먼저 도착해도 받아준다.** 이상해 보이지만 정상 — 발행은 성공했는데 상태 저장이 실패해 행이 `PENDING` 으로 남은 경우(§8)가 있기 때문이다. 도착한 결과를 "발행 기록이 없다"는 이유로 버리면 그게 유실이다.

## 7. 발행 잡 읽기 — 트랜잭션을 언제 열고 언제 닫나

배치가 하는 일의 전부가 이 함수다.

```kotlin

```
`batch/src/main/kotlin/com/kbap/batch/outbox/FoodContentOutboxPublisher.kt:21-60` (발췌·축약)

읽는 순서:

1. **`transactionTemplate` 을 손으로 쓴다.** `@Transactional` 애너테이션이 아니라 `TransactionTemplate` 인스턴스다(:15). 이유는 3번에 나온다.
2. **읽기 트랜잭션 하나** — `findPendingAfterId(cursor, pageSize)` 로 `PENDING` 100건(기본값)을 가져온다. 트랜잭션이 여기서 **닫힌다**.
3. **`eventPublisher.publish(...)` 는 트랜잭션 밖에서 호출된다.** 이게 이 코드의 가장 중요한 한 줄이다. **DB 트랜잭션을 열어둔 채로 외부 시스템(SQS)을 부르면 안 된다** — SQS 가 느려지거나 타임아웃 나는 동안 DB 커넥션과 락이 그만큼 붙잡힌다. 커넥션 풀이 마르면 그때부터는 API 서버까지 같이 죽는다.
   테스트가 이걸 **명시적으로 검증**한다:
   ```kotlin
   val publisher = FoodContentEventPublisher { events ->
       TransactionSynchronizationManager.isActualTransactionActive() shouldBe false
       …
   }
   ```
   `batch/src/test/kotlin/com/kbap/batch/outbox/FoodContentOutboxPublisherTest.kt:54-55`
   `@Transactional` 을 함수에 붙였다면 발행이 트랜잭션 안에 들어왔을 것이다. **`TransactionTemplate` 을 쓴 이유가 이것이다** — 트랜잭션 경계를 애너테이션에 맡기지 않고 코드로 잘라 쓰려고. ("애너테이션 vs 코드" 라는 선택지 자체는 [[6. 설정과 프로필, 트랜잭션 경계]] §5 가 바로 이 파일을 예로 들어 설명한다.)
4. **쓰기 트랜잭션 하나** — 성공/실패 id 를 두 개의 UPDATE 로 되짚는다.
5. 커서를 마지막 id 로 옮기고 다음 페이지. 발행에 **실패한 행은 `PENDING` 인 채 커서 뒤에 남으므로 이번 실행에서는 다시 안 본다.** 다음 주기(한 시간 뒤)에 커서가 0부터 다시 시작하면서 집힌다. 테스트가 이 동작을 문장으로 못 박아 뒀다 — "같은 실행에서는 실패 행을 되돌아가지 않고 다음 페이지까지 처리한다"(`FoodContentOutboxPublisherTest.kt:48`).

> [!note] 왜 커서 페이징인가
> `WHERE id > :afterId ... LIMIT :limit`(`FoodContentOutboxJpaRepository.kt:21-36`)는 OFFSET 을 쓰지 않는다. 발행하는 도중에도 새 행이 계속 INSERT 되므로 OFFSET 은 건너뛰기·중복을 만든다. 같은 이유로 이 레포의 목록 API 들도 전부 커서다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]], 볼트 밖 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]]).

## 8. 정확히 한 번은 불가능하다 — at-least-once 와 멱등

여기가 이 노트에서 제일 중요한 절이다.

§7 의 3번과 4번 사이를 다시 보자.

```
   ③ SQS 로 발행 성공  ←─── 여기까지 성공
   ─────────────────────
   ④ 상태를 SENT 로 저장  ←─── 여기서 프로세스가 죽으면?
```

③과 ④는 **또다시 다른 시스템**이다(SQS ↔ MySQL). 아웃박스는 ①②의 이중 쓰기를 없앴지만, **③④의 이중 쓰기는 없애지 못한다.** 원리적으로 못 없앤다 — 어디에도 "SQS 전송과 MySQL UPDATE 를 함께 커밋" 하는 수단이 없다.

③ 성공 후 ④ 전에 배치가 죽으면:
- 메시지는 **이미 큐에 있다**.
- 행은 여전히 `PENDING` 이다.
- 한 시간 뒤 배치가 그 행을 다시 집어 **같은 메시지를 한 번 더 발행한다.**

**그래서 아웃박스가 주는 보장은 "정확히 한 번(exactly-once)" 이 아니라 "최소 한 번(at-least-once)" 이다.** 유실은 없지만 중복은 있다.

> [!important] 중복이 생기는 자리는 최소 세 곳이다
> 1. **발행 후 상태 저장 실패** (위 시나리오) — 같은 메시지 재발행
> 2. **SQS 자체의 at-least-once** — 표준 큐는 같은 메시지를 두 번 이상 전달할 수 있다. FIFO 큐·중복 제거 ID 를 쓰면 줄일 수 있지만 **kbap 은 안 쓴다**(`specs/kb-302-langchain-food-ingest/contracts/mq-message.md`: "중복 소비 방지를 위한 FIFO 큐·중복 제거 ID 는 쓰지 않는다 — 멱등 적재로 충분").
> 3. **소비자(랭체인)의 재시도** — 결과를 적재하다 응답을 못 받으면 다시 부른다.

중복이 불가피하면 **받는 쪽이 두 번 와도 괜찮게** 만드는 수밖에 없다. 그게 **멱등(idempotent)** 이다.

kbap 의 멱등 장치는 §6 에서 본 `completeIfProcessable` 의 `WHERE` 절 그 자체다.

```kotlin

    if (outboxRepository.completeIfProcessable(outboxId, foodId) == 1) {
        return
    }
    if (outboxRepository.existsByIdAndFoodIdAndOutboxStatus(outboxId, foodId, FoodContentOutboxStatus.COMPLETE)) {
        throw BusinessException(ErrorCode.FOOD_CONTENT_REQUEST_ALREADY_COMPLETED)
    }
    throw BusinessException(ErrorCode.INVALID_REQUEST)
}
```
`api/src/main/kotlin/com/kbap/api/admin/AdminFoodContentIngestService.kt:47-61`

- **갱신된 행이 1이면** 이번 호출이 이 요청을 닫은 것 — 정상 처리.
- **0이면 두 갈래**다. 이미 `COMPLETE` 면 `409 FOOD-004`("이미 처리된 음식 콘텐츠 수집 요청입니다", `common/core/error/ErrorCode.kt:37`), 애초에 그런 조합이 없으면 `400`.
- 409 는 **"실패" 가 아니라 "이미 끝났다" 는 신호**다. API 문서가 이 해석을 명시한다 — "이는 이미 적재된 정상 종료 신호이므로 호출자는 재시도·DLQ 대상에서 제외한다"(`api/admin/AdminFoodContentIngestApi.kt:30`).

> [!tip] 23번과 같은 계열이다
> [[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]] 의 `uq_member_ranking_event` 는 **DB unique 제약**으로 같은 리뷰 이벤트가 두 번 점수를 더하는 걸 막는다. 여기는 **`WHERE` 조건 안의 상태 검사**로 같은 결과가 두 번 적재되는 걸 막는다.
> 수단은 다르지만 원리는 하나다 — **"두 번째 시도가 조용히 아무 일도 안 하게(또는 명확히 거절되게) 만든다."** 분산 시스템에서 재시도를 안전하게 만드는 유일한 방법이다.

## 9. 재시도와 실패 처리 — 실측

계획서와 브리프가 물은 것: 몇 번 재시도하나? 죽은 메시지는 어디로 가나?

**정직하게 — kbap-server 안에는 재시도 상한도 DLQ 도 없다.**

| 질문 | 실측 |
|---|---|
| 발행 재시도 횟수 상한 | **없다.** `attempts` 컬럼이 시도 횟수를 세지만, 이 값을 읽어 분기하는 코드는 레포에 **0줄**이다. `findPendingAfterId` 의 `WHERE` 에 `attempts` 조건이 없다 |
| 재시도 주기 | 매시 정각 (`@Scheduled(cron = "0 0 * * * *", zone = "Asia/Seoul")`, `batch/schedule/BatchJobScheduler.kt:17`) |
| 백오프(재시도 간격 늘리기) | **없다.** 실패해도 다음 정각에 똑같이 시도 |
| 발행 실패 행의 종착지 | **없다.** `PENDING` 인 채로 영원히 매시간 재시도된다 |
| DLQ(dead letter queue) | kbap-server 쪽엔 **없다.** SQS 큐에 DLQ 가 붙어 있는지는 **인프라 설정이라 이 레포에서 확인 불가** |
| `SENT` 인 채 결과가 안 오면 | **아무 일도 안 일어난다.** 서버는 자동 재발행하지 않는다 |

마지막 줄이 특히 의도된 선택이다. 계약 문서가 근거를 적어 뒀다.

> 람다 쪽 런타임 실패는 SQS 재시도 후 DLQ 로 간다. 그 경우 kbap 적재 API 는 호출되지 않고, 아웃박스 행은 `SENT` 인 채 남는다 — **발행은 성공했고 처리가 실패한 상태**이므로 서버가 자동 재발행하지 않는다. 재시도는 관리자가 재수집으로 명시 요청한다.
> — `specs/kb-302-langchain-food-ingest/contracts/mq-message.md`

즉 **책임 분할**이다. kbap-server 는 "큐에 넣는 데까지" 만 책임지고, 그 뒤 실패의 재시도·DLQ 는 **SQS 인프라 설정과 소비자(랭체인)** 의 몫이다. 서버가 `SENT` 행을 자동 재발행하면 랭체인의 재시도와 겹쳐 같은 음식에 LLM 비용이 두 배로 든다.

**대신 사람이 보는 창구가 있다.** `AdminFoodOutboxQueryService.kt:15-20` 이 세 상태 각각의 건수를 세어 관리자 대시보드에 띄운다.

```kotlin
pending = outboxRepository.countByOutboxStatus(FoodContentOutboxStatus.PENDING),
sent = outboxRepository.countByOutboxStatus(FoodContentOutboxStatus.SENT),
complete = outboxRepository.countByOutboxStatus(FoodContentOutboxStatus.COMPLETE),
```

`SENT` 건수가 계속 쌓이면 랭체인 쪽이 막힌 것이다. **자동 복구가 없는 대신 눈으로 보이게 해 뒀다** — 이것도 하나의 설계 선택이고, 노트를 읽는 사람이 알고 있어야 할 트레이드오프다.

### 옆 테이블은 다르게 골랐다

같은 레포에 **또 다른 아웃박스**가 있다 — `food_vector_outbox`(28번 소관). 같은 패턴이지만 **큐를 타지 않는다**: 배치가 DB 행을 직접 읽어 임베딩을 만들고 벡터 저장소에 적재한다. SQS 도 다른 레포도 없다. 그리고 정확히 이 §9 의 지점에서 반대 선택을 했다.

```kotlin
fun recordFailure(error: String?) {
    attempts++
    lastError = error?.take(MAX_LAST_ERROR_LENGTH)
    if (attempts >= MAX_ATTEMPTS) {
        outboxStatus = FoodVectorOutboxStatus.FAILED
    }
}
```
`common/src/main/kotlin/com/kbap/common/domain/food/model/FoodVectorOutbox.kt:34-40` (`MAX_ATTEMPTS = 5`, :54)

| | `food_content_outbox` (이 노트) | `food_vector_outbox` (28번) |
|---|---|---|
| 상태 | `PENDING` / `SENT` / `COMPLETE` | `PENDING` / `COMPLETE` / **`FAILED`** |
| `attempts` 의 쓰임 | **표시용.** 어떤 분기에도 안 쓰인다 | **5회 넘으면 `FAILED` 로 격리** |
| 실패 원인 기록 | 없음(로그만) | `last_error` 컬럼(500자) |
| 재시도 재개 | 관리자가 **재수집**을 새로 요청 | `retry()` 로 `PENDING`·`attempts=0` 복구 |
| 무한 재시도 | **가능하다** | 막혀 있다 |

왜 다른가. **벡터 동기화는 kbap 안에서 끝나는 일**이라 실패가 kbap 책임이고, 그래서 kbap 이 상한과 격리 상태를 갖는다. 실패의 전말을 kbap 이 다 알기 때문에 `last_error` 도 적을 수 있다. **콘텐츠 생성은 남에게 넘긴 일**이라 실패가 랭체인 책임이고, kbap 은 "보냈다" 까지만 안다 — `FAILED` 라는 상태를 만들 근거 자체가 없다.

**경계를 넘느냐 아니냐가 상태 기계를 결정한다.** 같은 아웃박스 패턴이라도 정해진 레시피처럼 외워 쓰면 안 되는 이유다. 벡터 쪽 잡이 실제로 무슨 일을 하는지는 [[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]] 가 다룬다.

- `eventPublisher` 는 Spring 의 `ApplicationEventPublisher` — **같은 JVM 안의 인메모리 이벤트 버스**다. 큐도 네트워크도 없다.
- `@EventListener` 가 그 이벤트를 받는다. `@Async` 가 붙어 **호출자 스레드가 아닌 별도 스레드**에서 돈다 → 스캔 응답이 비용 기록을 기다리지 않는다. (`@Async` 는 `api/core/config/BackgroundConfig.kt:13` 의 `@EnableAsync` 로 켜져 있다. 이게 없으면 `@Async` 는 **조용히 무시되고 동기로 돈다** — 흔한 함정이다.)
- **`try/catch` 가 두 겹**이다. 발행 쪽도, 수신 쪽도 예외를 삼킨다. 비용 기록은 **부가 기능**이므로 실패해도 스캔을 망치면 안 된다. 테스트가 이 계약을 검증한다 — "예외가 전파되지 않고 스캔 흐름에 영향을 주지 않는다"(`api/src/test/kotlin/com/kbap/api/metering/LlmCallCostEventListenerTest.kt:89`).

> [!warning] `@EventListener` 이지 `@TransactionalEventListener` 가 아니다
> 이 리스너는 **커밋 시점이 아니라 `publishEvent()` 호출 시점**에 발동한다. 게다가 `@Async` 라 별도 스레드에서 **새 트랜잭션**을 연다(`LlmCallCostService.record` 의 `@Transactional`). 그래서 **부르는 쪽 트랜잭션이 나중에 롤백돼도 비용 행은 남는다.**
> 여기서는 그게 오히려 맞다 — **LLM 호출은 이미 실제로 일어났고 돈이 나갔다.** 스캔이 실패했다고 비용이 환불되지는 않는다. 하지만 "이벤트로 다른 테이블에 쓰는" 코드를 볼 때마다 **커밋 전인지 후인지**는 반드시 확인해야 한다.

### 대비표 — 무엇을 보장하고 무엇을 못 보장하나

| | **A. 같은 앱 안 비동기**<br>`@EventListener` + `@Async` | **B. 다른 시스템 큐**<br>아웃박스 + SQS |
|---|---|---|
| 실물 | `api/metering/LlmCallCostEventListener.kt` | `batch/outbox/*` + `common/infra/mq/SqsFoodContentEventPublisher.kt` |
| 일이 어디 머무나 | **JVM 힙 안의 스레드풀 큐** | **DB 행 + AWS SQS** (둘 다 디스크) |
| 프로세스가 죽으면 | **일이 사라진다.** 힙에 있던 대기 작업은 복구 불가 | **살아남는다.** 행은 DB 에, 메시지는 큐에 남아 다음 실행이 이어받는다 |
| 재시도 | **없다.** 예외를 잡아 로그만 남기고 끝 | 있다. 다음 정각에 `PENDING` 행을 다시 집는다(상한 없음, §9) |
| 지연 | 밀리초 | **최대 1시간**(스케줄 주기) + 랭체인 처리 시간 |
| 수신자를 아는가 | 안다 — 같은 코드베이스, 컴파일 타임에 타입이 맞는다 | 모른다 — **JSON 계약**만 맞으면 된다. 랭체인은 다른 레포·다른 언어 |
| 수신자가 죽어 있으면 | 애초에 같이 죽어 있다 | **메시지가 큐에 쌓여 기다린다.** 살아나면 밀린 걸 처리 |
| 순서 보장 | 없음(스레드풀) | 없음(표준 큐) |
| 중복 | 없음(한 번만 발동) | **있다** — at-least-once (§8) |
| 트랜잭션과의 관계 | 커밋 전 발동. 롤백돼도 남는다 | 아웃박스 행은 **같은 트랜잭션**. 롤백되면 안 남는다 |
| 언제 쓰나 | **잃어도 되는 부가 기록** (비용 계량, 통계) | **잃으면 안 되는 일**의 위임 (콘텐츠 생성) |

마지막 줄이 결론이다. **A 는 "실패해도 무시할 수 있는 일" 에만 쓴다.** 비용 기록이 몇 건 빠져도 서비스는 굴러간다. 반대로 콘텐츠 생성 요청이 유실되면 그 음식은 **영원히 "준비 중"** 이다 — 아무도 다시 안 부른다. 그래서 B 를 썼다.

> [!note] FE 비유
> A 는 `setTimeout(() => analytics.track(...), 0)` 이다. 앱을 닫으면 그냥 안 간다.
> B 는 **오프라인 큐**다 — 요청을 AsyncStorage 에 적어두고 네트워크가 돌아오면 재전송한다. 앱을 껐다 켜도 살아 있다.
> 차이는 "미룬다" 가 아니라 **"어디에 적어두고 미루느냐"** — 메모리냐 디스크냐다.

## 11. 왜 큐인가 — 직접 HTTP 호출과 비교

kbap-server 가 랭체인을 그냥 `POST https://langchain/generate` 로 부르면 안 되나? 되긴 된다. 무엇을 잃고 무엇을 얻는지가 다르다.

| | **직접 HTTP 호출** | **큐(SQS)** |
|---|---|---|
| 랭체인이 다운되면 | 요청이 그 자리에서 실패. 재시도 로직·백오프를 **kbap 이 직접** 구현해야 함 | **메시지가 큐에 쌓인다.** 랭체인이 살아나면 밀린 걸 순서대로 처리. kbap 은 아무것도 안 함 |
| 트래픽이 몰리면 | 스캔 1000건 → 랭체인에 동시 1000 요청 → 밟혀 죽음 | **부하 평탄화.** 큐가 완충한다. 랭체인은 자기 속도로 소비 |
| LLM 이 30초 걸리면 | kbap 스레드가 30초 붙잡힌다. 요청당 스레드 하나인 JVM 서버에서 치명적([[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]]) | kbap 은 메시지를 넣고 즉시 반환 |
| 랭체인 주소·인증이 바뀌면 | kbap 코드 수정·재배포 | 큐 URL 만 그대로면 무관 |
| 결합도 | kbap 이 랭체인의 **존재·주소·응답 형식**을 안다 | **큐만 안다.** 소비자가 몇 개든, 무슨 언어든 상관없음 |
| **대가 ①** 지연 | 즉시 (수 초) | **최대 1시간 + 처리 시간** |
| **대가 ②** 순서 | 요청 순서 그대로 | **보장 없음** (표준 큐) |
| **대가 ③** 디버깅 | 스택 트레이스 하나로 끝 | **경계가 셋**(DB·큐·다른 레포). "그 음식 왜 안 채워졌지?" 를 답하려면 아웃박스 상태·큐 지표·랭체인 로그를 각각 봐야 한다 |
| **대가 ④** 멱등 부담 | 없음(응답으로 성공 확인) | **받는 쪽이 멱등해야 함** (§8) |

대가 ③이 실무에서 제일 아프다. kbap 이 `SENT` 로 표시했다고 랭체인이 받았다는 뜻이 아니고, 랭체인이 처리했다고 kbap 이 안다는 뜻도 아니다. **`COMPLETE` 로 닫히기 전까지 이 요청의 진짜 상태를 아는 시스템은 어디에도 없다.** 관리자 대시보드의 상태별 건수(§9)가 그 어둠을 밝히는 유일한 창이다.

**① 계약(포트)** — `:common` 모듈. 순수 Kotlin, AWS 라이브러리를 모른다.


계약이 이 세 파일, 총 열 몇 줄이다. **"SQS" 라는 단어가 한 번도 안 나온다.** 계약이 표현하는 건 "이벤트 목록을 주면 어떤 게 나갔고 어떤 게 실패했는지 알려준다" 뿐이다. **부분 실패를 계약에 못 박은 것**(성공 집합과 실패 집합을 따로 돌려줌)이 이 포트의 설계 핵심이다 — 큐 전송은 원래 일부만 성공할 수 있다.

**② 구현(어댑터)** — AWS SDK 를 아는 유일한 파일.

```kotlin
events.chunked(SQS_BATCH_LIMIT).forEach { batch ->
    val requestedIds = batch.mapTo(mutableSetOf()) { it.outboxId }
    try {
        val response = sqsClient.sendMessageBatch(
            SendMessageBatchRequest.builder().queueUrl(queueUrl)
                .entries(batch.map {
                    SendMessageBatchRequestEntry.builder()
                        .id(it.outboxId.toString())
                        .messageBody(objectMapper.writeValueAsString(it))
                        .build()
                }).build(),
        )
        val succeededIds = response.successful().mapNotNullTo(mutableSetOf()) { it.id().toLongOrNull() }
        succeeded += succeededIds.intersect(requestedIds)
        failed += requestedIds - succeededIds
    } catch (exception: Exception) {
        logger.warn("음식 콘텐츠 SQS 묶음 발행에 실패했습니다. outboxIds={}", requestedIds, exception)
        failed += requestedIds
    }
}
```
`common/src/main/kotlin/com/kbap/common/infra/mq/SqsFoodContentEventPublisher.kt:25-48`

- `chunked(SQS_BATCH_LIMIT)` — `SQS_BATCH_LIMIT = 10`(:57). **AWS 가 `SendMessageBatch` 한 번에 10건까지만 받는다.** 배치 페이지는 100건이므로 한 페이지가 10번의 SQS 호출로 쪼개진다. 이 숫자는 **AWS 사정이지 도메인 사정이 아니다** — 그래서 포트가 아니라 어댑터 안에 숨어 있다. 포트를 다른 큐(Kafka 등)로 갈아끼우면 이 상수는 그냥 사라진다.
- 엔트리 `id` 로 **아웃박스 행 id** 를 쓴다. 이게 응답의 `successful()` 에 그대로 돌아오므로 **어떤 행이 나갔는지 되짚을 수 있다.**
- `succeededIds.intersect(requestedIds)` / `requestedIds - succeededIds` — AWS 가 돌려주지 않은 id 는 전부 실패로 친다. **모르면 실패로 취급** — 발행 안 됐는데 됐다고 표시하는 것(유실)보다 됐는데 안 됐다고 표시하는 것(중복)이 낫다. 아웃박스의 at-least-once 철학이 이 한 줄에 들어 있다.
- `catch (exception: Exception)` 으로 **묶음 전체를 실패 처리**한다. 예외가 위로 안 올라가므로 뒤 묶음은 계속 시도된다.

**③ 조립** — 배치 모듈의 `@Configuration` 이 둘을 잇는다.

```kotlin

```
`batch/src/main/kotlin/com/kbap/batch/outbox/FoodContentOutboxBatchConfig.kt:37-43`

- **포트 타입을 반환**하고 어댑터 구현을 그 안에 넣는다. `FoodContentOutboxPublisher` 는 `FoodContentEventPublisher` 만 받으므로 SQS 를 모른다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]).
- `@ConditionalOnMissingBean` — **테스트가 자기 구현을 꽂으면 이 빈은 안 만들어진다.** `FoodContentOutboxPublisherTest` 가 람다 하나로 발행기를 대체할 수 있는 이유다. `fun interface` 로 선언한 것도 이걸 노린 것 — SAM 변환으로 `FoodContentEventPublisher { events -> ... }` 라고 쓸 수 있다.
- 큐 URL 은 `@Value` 로 주입되고 기본값이 없다. 즉 **설정이 없으면 부팅이 실패**한다. `batch/src/main/resources/application.yml:49-52` 가 환경변수로 공급한다(`FOOD_CONTENT_QUEUE_URL`, `AWS_REGION`, `FOOD_CONTENT_OUTBOX_PAGE_SIZE`).

**갈아끼움 실험**: SQS 를 Kafka 로 바꾼다면 건드릴 파일은 `SqsFoodContentEventPublisher.kt`(교체) + `FoodContentOutboxBatchConfig.kt` 의 빈 두 개(조립)뿐이다. `FoodContentOutboxPublisher`·리포지토리·엔티티·마이그레이션은 **한 줄도 안 바뀐다.** 12번 노트가 KB-350(카카오→구글 전환)으로 말한 것과 같은 성질이다 — 포트는 변경을 없애는 게 아니라 **번지는 범위를 가둔다.**

1. **`outboxId` 를 되돌려 받는다.** 메시지에 실어 보낸 값을 그대로 돌려받아야 어떤 요청이 닫히는지 특정할 수 있다. 이게 §8 멱등의 열쇠다.
2. **검증이 요청 DTO 에 몰려 있다.** `AdminFoodContentIngestRequest.kt:35-74` 에 `@AssertTrue` 검증이 9개 있다 — 번역 9개 언어 전수, 재료 코드가 카탈로그에 있는지, 맵기 0~10 등. **경계에서 거절하고 저장하지 않는다.** 외부 시스템이 보낸 데이터는 신뢰하지 않는다.
3. `ingredients` 의 **빈 배열과 누락이 다르다** — "조사했고 해당 없음" 과 "미조사" 는 위험도 계산이 갈린다(`AdminFoodContentIngestRequest.kt:52-54` 주석). 이 판정이 [[19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]] 로 이어진다.

> [!warning] 스펙과 다름 — 중복 도착 처리
> `specs/kb-302-langchain-food-ingest/spec.md` **FR-012**: "같은 결과가 중복 도착해도 **정상 처리(갱신 + 성공 응답)** 한다." Edge Case 절도 "재시도가 오류로 보이지 않아야 한다" 고 적는다.
> **코드는 그렇게 안 한다.** 두 번째 도착은 `409 FOOD-004` 로 **거절**된다(`AdminFoodContentIngestService.kt:51-59`). 중간에 `COMPLETE` 상태가 추가되면서(2026-08-12 마이그레이션) 설계가 바뀐 것으로 읽힌다 — API 문서는 바뀐 쪽에 맞춰 "정상 종료 신호이니 재시도·DLQ 대상에서 제외하라" 고 다시 정의한다(`AdminFoodContentIngestApi.kt:30`).
> **결과는 비슷하다**(어느 쪽이든 재시도가 무한 반복되지 않는다). 다만 **호출자가 409 를 성공으로 해석하도록 구현돼 있어야** 한다 — 스펙만 읽고 만든 클라이언트라면 409 를 실패로 보고 DLQ 로 보낼 것이다. 코드 기준으로 읽어라.

## 16. 용어집

| 용어 | 뜻 |
|---|---|
| **이중 쓰기(dual write)** | 서로 다른 두 저장소에 원자적으로 쓰려는 시도. 원리적으로 안전하게 안 된다 |
| **아웃박스 패턴(Outbox Pattern)** | 발행할 메시지를 **같은 DB 의 테이블에 먼저 기록**하고, 별도 프로세스가 그 행을 읽어 실제로 발행하는 패턴 |
| **at-least-once (최소 한 번)** | 메시지가 유실되지는 않지만 **두 번 이상 도착할 수 있는** 전달 보장. 아웃박스+SQS 가 주는 것 |
| **exactly-once (정확히 한 번)** | 정확히 한 번만 도착하는 보장. **분산 시스템에서 순수하게는 달성 불가** — "at-least-once + 멱등" 으로 흉내낸다 |
| **멱등(idempotent)** | 같은 연산을 여러 번 해도 결과가 한 번 한 것과 같은 성질. 재시도를 안전하게 만드는 유일한 방법 |
| **SQS** | AWS 의 관리형 메시지 큐. 표준 큐는 순서·중복 제거를 보장하지 않는 대신 처리량이 크다 |
| **DLQ (dead letter queue)** | 여러 번 재시도해도 처리 못 한 메시지를 따로 모아두는 큐. 사람이 보라고 있는 것 |
| **부하 평탄화(load leveling)** | 순간적으로 몰린 요청을 큐에 담아두고 소비자가 자기 속도로 처리하게 하는 것 |
| **`@EventListener`** | 같은 JVM 안의 이벤트를 받는 Spring 애너테이션. `publishEvent()` 시점에 발동 |
| **`@TransactionalEventListener`** | 위와 달리 **트랜잭션 커밋 후**에 발동. kbap 은 안 쓴다 |
| **`fun interface`** | 추상 메서드가 하나인 Kotlin 인터페이스. 람다로 바로 구현할 수 있다(SAM 변환) |
| **`TransactionTemplate`** | `@Transactional` 대신 **코드로** 트랜잭션 경계를 여닫는 도구. 경계를 함수보다 잘게 자를 때 쓴다 |

## 17. 체크리스트 — 읽고 나서 답할 수 있어야 하는 것

- [ ] "DB 저장과 큐 발행을 `@Transactional` 로 묶으면 되지 않나?" 에 두 문장으로 답할 수 있다
- [ ] 아웃박스 행이 만들어지는 두 경로를 댈 수 있다
- [ ] `outbox_status` 와 `status` 가 왜 다른 컬럼인지 안다
- [ ] `PENDING → SENT → COMPLETE` 각 전이를 **누가** 일으키는지 안다
- [ ] "발행 성공 직후 배치가 죽으면?" 에 답할 수 있다 (→ 중복 발행 → 멱등이 받아냄)
- [ ] 왜 SQS 호출이 트랜잭션 **밖**이어야 하는지 안다
- [ ] kbap-server 에 발행 재시도 상한과 DLQ 가 **없다**는 사실과, 대신 무엇이 있는지 안다
- [ ] `@EventListener`+`@Async` 를 콘텐츠 생성 요청에 쓰면 왜 안 되는지 설명할 수 있다
- [ ] 큐 대신 직접 HTTP 를 쓸 때 얻는 것과 잃는 것을 각각 두 개씩 댈 수 있다
- [ ] 포트(`common.port.mq`)에 "SQS" 라는 단어가 왜 없는지 안다
