# 11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지

> 작성: 2026-08-26 · 맥락: 여기까지는 "코드 한 줄이 어떻게 도는가"를 봤다. 이 노트부터는 한 단계 물러나 **코드를 어디에 두는가**를 본다. 백엔드 글을 조금만 읽으면 "마이크로서비스로 쪼개라"는 말을 반드시 만나는데, kbap-server 는 쪼개지 않았다. 대신 **한 덩어리 안에 선을 그었다.**
> 목표: 모놀리스·마이크로서비스·모듈러 모놀리스가 각각 뭘 사고 뭘 파는지 설명할 수 있게 되고, kbap 의 모듈 3개와 도메인 패키지 14개가 **어떤 선인지**, 그리고 그 선을 **왜 한때 16개까지 늘렸다가 3개로 줄였는지** 말할 수 있게 되기.

---

## 0. 한 줄 요약

kbap-server 는 **하나의 코드베이스 · 하나의 DB**지만 안에 두 겹의 선이 있다. 바깥 선은 **Gradle 모듈 3개**(`:common`·`:api`·`:batch`)로, 어기면 **컴파일이 안 된다.** 안쪽 선은 **도메인 패키지**(`com.kbap.common.domain.<컨텍스트>` 14개)로, 어겨도 컴파일은 되고 **테스트가 잡는다.** 이 "한 덩어리인데 안이 나뉘어 있음"이 **모듈러 모놀리스**다.

---

## 1. 세 가지 선택지 — 뭘 사고 뭘 파는가

### 1-1. 모놀리스 (monolith)

**한 덩어리로 만들어 한 번에 배포하는 프로그램.** 코드가 한 저장소에 있고, 빌드 결과물이 하나고, 서버 프로세스도 하나다. 회원 기능과 주문 기능이 같은 프로세스 안에서 그냥 **함수 호출**로 서로를 부른다.

FE 로 치면 **앱 하나짜리 프로젝트**다. 화면 A 의 코드가 화면 B 의 유틸을 `import` 해서 쓰는 데 아무 절차가 없다.

- **좋은 것**: 부르는 게 함수 호출이라 빠르고, 실패할 일이 없고, 디버깅이 스택 트레이스 하나로 끝난다. 배포가 한 번이다.
- **나쁜 것**: 아무나 아무거나 `import` 할 수 있어서, 시간이 지나면 **모든 게 모든 걸 아는 상태**가 된다. 한 군데 고치면 어디가 깨질지 아무도 모른다. 이걸 흔히 **진흙 공(big ball of mud)** 이라 부른다.

### 1-2. 마이크로서비스 (microservices)

**기능별로 아예 다른 프로그램으로 쪼개고, 서로 네트워크로 부른다.** 회원 서비스와 주문 서비스가 별도 저장소·별도 배포·별도 DB 를 가진다. 주문이 회원 정보를 알고 싶으면 HTTP 나 메시지 큐로 물어본다.

- **좋은 것**: 경계가 **물리적으로** 강제된다. 남의 DB 테이블을 몰래 읽는 게 불가능하다. 팀별로 따로 배포하고 따로 확장한다.
- **나쁜 것**: 함수 호출이 **네트워크 호출**로 바뀌는 순간 전부 실패할 수 있는 일이 된다. 타임아웃·재시도·부분 실패·분산 트랜잭션·서비스 간 버전 호환·분산 추적이 전부 새 숙제로 들어온다. Martin Fowler 는 이 고정 비용을 **마이크로서비스 프리미엄(MicroservicePremium)** 이라고 부르고, "그 값을 낼 만큼 시스템이 복잡해지기 전에는 손해"라고 정리한다.

그리고 진짜 함정은 이거다 — **처음에는 경계를 어디에 그어야 할지 아무도 모른다.** Fowler 의 표현: *"Any refactoring of functionality between services is much harder than it is in a monolith."* 한 덩어리 안에서 폴더 옮기는 건 30분이지만, 두 서비스 사이에서 기능을 옮기는 건 스키마 이전 + API 신설 + 배포 순서 조율이다. 그래서 그는 **모놀리스로 시작하라(MonolithFirst)** 고 권한다.

### 1-3. 모듈러 모놀리스 (modular monolith)

**배포는 모놀리스처럼 한 덩어리, 코드 구조는 마이크로서비스처럼 경계를 가진 것.** 프로세스는 하나라 호출은 여전히 함수 호출이지만, "이 모듈은 저 모듈을 참조할 수 없다"를 **빌드 도구나 테스트가 강제**한다.

핵심은 **경계를 나중에 서비스로 승격시킬 수 있는 상태로 유지**하는 것이다. 선이 이미 그어져 있으면, 정말로 쪼갤 때가 왔을 때 그 선을 따라 자르면 된다.

### 1-4. 비교표

| | 모놀리스 | 모듈러 모놀리스 | 마이크로서비스 |
|---|---|---|---|
| 배포 단위 | 1개 | 1개 (kbap 은 2개 — 아래 8절) | 서비스 수만큼 |
| 모듈 간 호출 | 함수 호출 | 함수 호출 | 네트워크 호출 |
| 호출이 실패할 수 있나 | 아니오 | 아니오 | **예** (타임아웃·재시도 필요) |
| 경계를 어기면 | 아무 일도 안 일어남 | **컴파일 실패 또는 테스트 실패** | 애초에 불가능 |
| DB | 공유 | 공유 (kbap 도 공유) | 서비스별 분리 |
| 경계를 옮기는 비용 | 낮음 (폴더 이동) | 낮음~중간 | **높음** |
| 트랜잭션 | 하나로 묶임 | 하나로 묶임 | 분산 트랜잭션 문제 |
| 팀별 독립 배포 | 불가 | 불가 | 가능 |

> [!tip] FE 개발자에게: "왜 안 쪼개나"의 답
> 마이크로서비스가 파는 건 **팀 독립성과 장애 격리**이고, 그 값으로 내는 건 **네트워크의 모든 불확실성**이다. kbap 은 팀이 작고 배포가 한 사람 손에서 끝난다 — 살 이유가 아직 없다. 대신 **진흙 공이 되는 건 막아야** 하니, 돈 안 드는 쪽(빌드 도구와 테스트로 선 긋기)만 산 것이다.

## 2. kbap 의 바깥 선 — 모듈 3개

Gradle 에서 **모듈(module)** 은 "따로 컴파일되는 코드 묶음"이다. FE 의 pnpm workspace 패키지, 혹은 모노레포의 `packages/*` 하나하나에 해당한다. 어떤 모듈이 있는지는 딱 한 파일에 적힌다.

```kotlin
include(
    ":common",
    ":api",
    ":batch",
)
```
`settings.gradle.kts:20-24`

- 모듈은 **3개가 전부다.** 이게 레포 전체의 모듈 목록이다.
- 디렉터리도 **루트 직속**이다 — `common/`·`api/`·`batch/` 가 `settings.gradle.kts` 와 나란히 있다. `app/`·`core/`·`infra/` 같은 **껍데기 컨테이너 디렉터리가 없다.**
- 그리고 **패키지가 모듈명을 그대로 미러링**한다: `:api` → `com.kbap.api`, `:batch` → `com.kbap.batch`, `:common` → `com.kbap.common`. 그래서 아무 파일이나 열어 맨 윗줄 `package` 선언만 보면 **그 파일이 어느 모듈 소속인지 즉시 안다.** (`CLAUDE.md:13`)

각 모듈이 뭘 담는지:

| 모듈 | 정체 | 담는 것 |
|---|---|---|
| `:common` | 라이브러리 (실행 불가) | **영속 계층 전부**(`@Entity`·리포지토리) + 두 앱이 함께 쓰는 코드. 자세히는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] |
| `:api` | 실행 파일 (web) | 컨트롤러·API DTO·도메인 서비스. 자세히는 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] |
| `:batch` | 실행 파일 (배치) | 배치 잡·트리거·스케줄 |

### 2-1. 의존 방향은 단방향 고정

```kotlin
dependencies {
    "implementation"(project(":common"))
```
`api/build.gradle.kts:5-6`

```kotlin
dependencies {
    "implementation"(project(":common"))
```
`batch/build.gradle.kts:5-6`

두 파일이 **글자 그대로 똑같다.** 그리고 이 두 파일 어디에도 `project(":api")` 나 `project(":batch")` 는 **없다.**

```
:common  ← :api    (web bootJar)
         ← :batch  (배치 bootJar)
```

- `:common` 은 아무에게도 의존하지 않는 **잎(leaf)** 이다.
- `:api` 와 `:batch` 는 각각 `:common` 만 본다.
- **api 와 batch 는 서로를 모른다.** 이건 규칙이 아니라 **물리적 사실**이다 — 상대 모듈을 의존으로 선언하지 않았으니 상대 클래스가 **컴파일 클래스패스에 아예 없다.** `com.kbap.api.member.MemberService` 를 batch 코드에서 `import` 하면 IDE 가 빨간 줄을 긋고 빌드가 "unresolved reference" 로 죽는다. 리뷰어가 놓쳐도 못 들어온다.

> [!note] 왜 하필 `:common` 이 영속 계층을 통째로 갖나
> 두 앱이 **같은 MySQL 을 공유**하기 때문이다. 엔티티를 각자 정의하면 같은 테이블을 두 번 매핑하게 되고, 한쪽만 컬럼을 추가하는 순간 조용히 어긋난다(**드리프트**). "스키마는 두 앱의 공유 자산"이라 아예 종류로 고정했다 — **영속이면 예외 없이 `:common`**(ADR-0016). 대신 마이그레이션을 실행하는 **주인은 `:api` 하나**고 batch 는 `flyway off` 다 — [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]].

## 3. 백미 — 왜 모듈을 16개까지 늘렸다가 3개로 줄였나

이 레포의 첫 커밋은 2026-06-27 이다. **두 달 사이에 모듈 개수가 8 → 16 → 7 → 3 으로 움직였다.** 이 궤적 자체가 이 노트에서 제일 배울 게 많은 부분이다.

### 3-1. 1막 — 계층별로 쪼갠다 (2026-06-29, ADR-0008)

처음 구조는 **계층마다 모듈**이었다. ADR-0008 이 그린 그림(`docs/adr/0008-modular-monolith-shared-domain.md:21-33`):

```
common/          기술 공통
core/kernel/     공유 커널
core/food/ member/ scan/ …    도메인 (ORM-free)
application/     유스케이스·트랜잭션 경계
infra/persistence/            JPA 엔티티·Adapter
app/api/ app/batch/           두 개의 부트앱
```

의도는 교과서적이다 — 도메인은 ORM 을 모르고, application 이 도메인 포트를 쓰고, infra 가 그 포트를 구현한다. **모듈 경계가 그 방향을 컴파일 타임에 강제**한다.

### 3-2. 2막 — 도메인마다 쪼갠다, 그리고 16개가 된다

도메인이 늘 때마다 모듈이 하나씩 붙었다. ADR-0016 의 진술(`docs/adr/0016-module-diet-three-app-modules.md:9`):

> 도메인이 8종(food·member·avoidance·scan·bookmark·image·metering + review placeholder)까지 늘며 **모듈은 16개**가 됐고, 그 비용이 실이득을 넘어섰다

무엇이 비용이었나(같은 문서 :11-12):

1. **새 코드마다 결정이 하나씩 늘었다** — "이건 어느 모듈이지? 그럼 어떤 의존 선언을 추가해야 하지?" 파일 하나 만들 때마다 이 질문에 답해야 했다.
2. **관리 지점이 모듈 수만큼 늘었다** — 빌드 파일 16개, `settings.gradle.kts` 등록 16줄, 컨벤션 플러그인 배선 16번.
3. **그리고 결정적으로, 모듈이 경계를 지켜주지도 못했다.**

세 번째가 뼈아프다. 원문:

> 실제로 **전이 클래스패스 누수**(scan·bookmark 가 선언 없이 avoidance 를 참조)는 **Gradle 이 잡지 못했고** ArchUnit 도입 시점에 발견됐다

무슨 말이냐면 — A 가 B 를 의존하고 B 가 C 를 의존하면, 설정에 따라 **A 가 C 를 선언 없이 쓸 수 있게 된다.** 모듈 경계를 그어놨는데 옆문이 열려 있던 것이다. FE 로 치면 `package.json` 에 안 적었는데도 `node_modules` 에 올라와 있어서 `import` 가 되는 상황과 같다.

### 3-3. 3막 — 모듈 다이어트 (2026-07-28, ADR-0016)

**애플리케이션 모듈을 `:common`·`:api`·`:batch` 3개로 통합**하고, 도메인 경계 강제는 **패키지 기준 ArchUnit 테스트로 이관**했다. 외부 SDK 어댑터(`:infra:{llm,auth,redis,storage}`)만 "SDK 의존 오염 방지"라는 실이득이 있어 모듈로 남겼다 — 이때 총 7모듈.

### 3-4. 4막 — infra 해체 (2026-08-14, ADR-0018)

남겨둔 어댑터 모듈도 6종까지 늘었는데, 실소비자를 세어 보니(`docs/adr/0018-dissolve-infra-modules-into-consumers.md`):

- api·batch 가 **함께** 쓰는 어댑터는 llm **하나뿐**
- 6종 중 **4종이 1~2 파일 크기**
- batch 의 storage 의존은 **소비자가 없는 죽은 의존**이었다

> 모듈 하나의 존재 비용(빌드 파일·settings 등록·jacoco 배선)이 격리 이득을 넘어섰다

그래서 전부 해체하고 소비 모듈 안 패키지로 흡수했다. **모듈은 3개가 됐다.** 어댑터를 어디에 두는지와 `common.port.*` 계약 이야기는 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] 가 정본이다.

### 3-5. 정직하게 — 뭘 잃었나

모듈을 줄이면 좋기만 한 게 아니다. ADR 들이 스스로 적어둔 대가:

| 잃은 것 | 원문 |
|---|---|
| **순환 차단 시점이 늦어졌다** | "도메인 간 순환 차단이 **컴파일 타임(Gradle)에서 테스트 타임(ArchUnit)으로 늦춰진다**" (ADR-0016) |
| **외부 SDK 격리도 같은 방식으로 격하됐다** | ADR-0018 이 어댑터 모듈을 해체하며 같은 대가를 치렀다 — 자세히는 [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] |
| **한 컨텍스트가 두 곳에 흩어진다** | "api 전용 컨텍스트는 소스가 두 모듈에 흩어진다 — `common/…/domain/<ctx>`(영속)와 `api/…/<ctx>`(서비스)를 함께 봐야 한다" (ADR-0016) |

그래서 **테스트를 안 돌리면 경계가 없는 것과 같다.** 모듈 다이어트는 "경계를 포기한 결정"이 아니라 **"경계를 지키는 책임을 Gradle 에서 테스트로 옮긴 결정"** 이고, 그 테스트가 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 다.

> [!warning] 여기서 얻을 교훈
> **"경계를 잘게 나눌수록 좋다"는 참이 아니다.** 경계 하나에는 값이 붙는다 — 빌드 파일, 등록, 배선, 그리고 무엇보다 **"이건 어디에 두지?"라는 결정을 매번 해야 하는 인지 비용.** 경계의 이득(순환 차단)이 그 값보다 작아지는 지점이 있고, kbap 은 16개에서 그 지점을 지났다고 판단했다. 이건 kbap 만의 이야기가 아니라 **모든 구조 결정의 모양**이다.

## 4. kbap 의 안쪽 선 — 바운디드 컨텍스트

### 4-1. 용어부터 — 바운디드 컨텍스트가 뭔가

**바운디드 컨텍스트(bounded context)** 는 DDD(도메인 주도 설계)의 용어로, **"하나의 일관된 모델이 통하는 범위"** 다.

왜 이런 게 필요한가. Martin Fowler 의 출발점은 이렇다 — *"total unification of the domain model for a large system will not be feasible or cost-effective."* 시스템 전체에 통하는 **단 하나의 완벽한 모델**을 만들려는 시도는 실패한다는 것이다.

이유는 언어에 있다. 조직의 부서마다 **같은 단어를 조금씩 다른 뜻으로** 쓴다. Fowler 가 드는 예는 전력회사의 "미터(meter)" 인데, 어떤 부서에는 전력망 연결점이고, 어떤 부서에는 고객 관계고, 어떤 부서에는 벽에 붙은 물리적 계량기다. 대화에서는 문맥으로 알아듣지만, **코드에서는 그게 클래스 하나로 뭉개지는 순간 모순**이 된다.

그래서 DDD 의 처방은 "하나의 완벽한 모델" 대신 **"각자 안에서만 일관된 여러 모델 + 그 사이의 명확한 경계"** 다. 그 경계 안쪽을 바운디드 컨텍스트라 부른다.

### 4-2. kbap 에서 컨텍스트는 폴더다

**옛날에는 컨텍스트마다 Gradle 모듈이 있었지만, 지금은 패키지 하나다.**

```
common/src/main/kotlin/com/kbap/common/domain/
├── admin/        ├── appversion/   ├── block/       ├── bookmark/
├── community/    ├── food/         ├── image/       ├── ingredient/
├── member/       ├── metering/     ├── order/       ├── report/
├── review/       └── scan/
```

**14개다.** 각 폴더 안에는 `model/`(엔티티 = 도메인 모델)과 리포지토리가 들어 있다.

그리고 이 목록은 문서가 아니라 **코드가 지킨다** — 이 폴더 구성이 6절의 허용 맵과 어긋나면 **테스트가 깨진다.** 폴더를 하나 추가하고 맵에 안 적으면 빌드가 빨갛게 된다.

폴더 이름만 훑어도 앱이 뭘 하는 물건인지 읽힌다 — 음식(`food`)과 성분(`ingredient`)이 있고, 회원(`member`)이 메뉴판을 스캔(`scan`)하고, 주문(`order`)·리뷰(`review`)·커뮤니티(`community`)를 남기고, 신고(`report`)·차단(`block`)으로 서로를 거른다. **바운디드 컨텍스트 목록은 그 자체로 서비스의 목차다.**

> [!note] 컨텍스트 ≠ 폴더 개수 (정직한 단서)
> `common/domain/` 14개는 **영속 계층 기준**이다. 도메인 서비스는 `com.kbap.api.<기능>` 에 있고 거기엔 `auth`·`home`·`place` 처럼 **영속 폴더가 없는 기능 패키지도 있다**(`home` 은 여러 컨텍스트를 조합해 화면 하나를 만드는 자리지, 자기 테이블이 없다). "컨텍스트가 몇 개냐"는 어느 층을 세느냐에 따라 달라진다 — **경계 검사가 대상으로 삼는 14개**가 이 노트의 기준이다.

## 5. 같은 단어, 다른 뜻 — kbap 의 "성분" 삼형제

Fowler 의 "미터" 예시가 kbap 에 그대로 있다. **"성분"이라는 단어가 세 컨텍스트에서 세 가지 다른 물건**이다.

### ① `ingredient` 컨텍스트 — 성분은 **카탈로그 항목**이다

```kotlin
@Entity
@Table(name = "ingredients")
class Ingredient(
    @Enumerated(EnumType.STRING)
    @Column(name = "code", nullable = false, length = 40)
    var code: IngredientCode = IngredientCode.EGG,

    @Column(name = "korean_name", nullable = false, length = 100)
    var koreanName: String = "",
```
`common/src/main/kotlin/com/kbap/common/domain/ingredient/model/Ingredient.kt:14-22`

- `@Entity` + `@Table` — **자기 테이블이 있는 엔티티**다. 계란·땅콩·우유가 각각 한 행이다.
- `code`·`koreanName`·번역·이미지를 가진다 — 화면에 "계란 🥚" 을 그려주기 위한 정보다.
- 이 컨텍스트에서 성분은 **사전 항목**이다. 어느 음식에 들었는지, 누가 싫어하는지는 여기 관심사가 아니다.

### ② `food` 컨텍스트 — 성분은 **함유 확률이 붙은 값**이다

```kotlin
data class FoodIngredient(
    @JsonProperty("code") val code: String,
    @JsonProperty("inclusion_percent") val inclusionPercent: Int,
) {
    fun riskLevel(): RiskLevel = RiskLevel.fromInclusionProbability(inclusionPercent)
}
```
`common/src/main/kotlin/com/kbap/common/domain/food/model/FoodIngredient.kt:6-11`

- `@Entity` 가 **아니다.** `data class` 이고, `Food` 의 JSON 컬럼 안에 리스트로 들어간다(`Food.kt:56-58`).
- 핵심 필드가 `inclusionPercent` — **"이 음식에 이 성분이 들었을 확률 몇 %"** 다. ①에는 없던 개념이다.
- `riskLevel()` — 확률을 **위험도로 번역**한다. 여기서 성분은 "사전 항목"이 아니라 **판정의 근거**다.

### ③ `member` 컨텍스트 — 성분은 **기피 목록에 적힌 코드 문자열**이다

```kotlin
data class AvoidedIngredientCodeRef(
    val value: String,
) {
    init {
        require(value.isNotBlank()) { "member.avoidedIngredientCodeRef 는 blank 일 수 없습니다" }
        require(value == value.trim()) { "member.avoidedIngredientCodeRef 는 앞뒤 공백을 가질 수 없습니다" }
        require(value.matches(FORMAT)) { "member.avoidedIngredientCodeRef 는 대문자·숫자·underscore 형식이어야 합니다" }
    }
```
`common/src/main/kotlin/com/kbap/common/domain/member/model/AvoidedIngredientCodeRef.kt:3-10`

- 필드가 **`String` 하나뿐**이다. 이름도 성분도 확률도 없다.
- 클래스 이름의 `Ref` 가 정직하다 — 성분 **자체**가 아니라 **성분을 가리키는 참조**다.
- 하는 일은 **형식 검증뿐**: 비어있지 않고, 공백이 없고, `EGG`·`PEANUT` 같은 대문자 코드 형식일 것.
- 이 컨텍스트에서 성분은 "회원이 피하겠다고 체크한 항목"일 뿐이다. **그게 실제로 뭔지는 회원의 관심사가 아니다.**

### 정리

| | `ingredient` | `food` | `member` |
|---|---|---|---|
| 클래스 | `Ingredient` | `FoodIngredient` | `AvoidedIngredientCodeRef` |
| 정체 | `@Entity` (자기 테이블) | `data class` (JSON 값) | `data class` (문자열 래퍼) |
| 갖는 것 | 코드·이름·번역·이미지 | 코드 + **함유 %** | 코드 문자열 **뿐** |
| 이 컨텍스트에서 성분이란 | 사전 항목 | 위험도 판정 근거 | 회원이 체크한 항목 |

**이게 바운디드 컨텍스트의 핵심이다.** 이 셋을 "다 성분이니까 `Ingredient` 하나로 합치자"고 하면, 그 클래스는 이름·번역·함유확률·위험도·형식검증을 전부 갖게 되고, 회원 프로필을 저장하는 코드가 **번역 필드를 왜 들고 다니는지 아무도 설명 못 하게** 된다. 나눠뒀기 때문에 각자가 **자기 컨텍스트 안에서만 완결**되어 있고, 각자 작다.

> [!tip] FE 에 이미 있는 감각
> 서버 응답 타입(`FoodResponse`)과 화면 상태 타입(`FoodCardVM`)을 **굳이 따로 두는** 습관이 있다면, 이미 절반은 아는 것이다. 같은 "음식"이지만 **API 경계에서의 음식**과 **화면에서의 음식**은 필요한 필드가 다르고, 합치면 양쪽 다 불편해진다. 바운디드 컨텍스트는 이걸 **비즈니스 개념 수준**으로 끌어올린 것이다.

## 6. 도메인 간 의존은 단방향만

컨텍스트를 나눠놨는데 서로 마구 참조하면 나눈 의미가 없다. 그래서 **"어느 컨텍스트가 어느 컨텍스트를 알아도 되는가"의 목록**이 코드에 딱 한 군데 적혀 있다.

```kotlin
val allowedDomainDeps = mapOf(
    "admin" to emptySet(),
    "appversion" to emptySet(),
    "block" to emptySet(),
    "scan" to setOf("food", "member", "image", "ingredient"),
    "food" to emptySet(),
    "bookmark" to setOf("food", "member", "ingredient"),
    "member" to setOf("ingredient"),
    "image" to emptySet(),
    "metering" to emptySet(),
    "order" to emptySet(),
    "ingredient" to emptySet(),
    "review" to emptySet(),
    "report" to emptySet(),
    "community" to emptySet(),
)
```
`api/src/test/kotlin/com/kbap/api/architecture/ModuleBoundaryTest.kt:108-123`

- **키가 컨텍스트, 값이 "알아도 되는 컨텍스트 집합"** 이다. `emptySet()` 은 "아무도 몰라도 된다".
- `scan to setOf("food", "member", "image", "ingredient")` — 스캔은 음식·회원·이미지·성분을 **알아도 된다.** 메뉴판을 찍은 사람(member)이 어떤 음식(food)을 스캔했고 어떤 성분(ingredient)이 위험한지 판정해야 하니 당연하다.
- **반대는 없다.** `food to emptySet()` — **음식은 스캔을 모른다.** 음식이라는 개념은 스캔이 없어도 성립하기 때문이다. 이게 **단방향**의 의미다.
- 이 파일이 **방향의 단일 출처**다. 방향을 바꾸려면 이 맵을 고쳐야 하고, 맵을 고치면 diff 에 보이므로 **리뷰에서 반드시 눈에 띈다.** ADR-0016 이 노린 게 정확히 이거다.

그리고 맵 바로 아래에 이런 검사가 있다:

```kotlin
foundContexts shouldBe allowedDomainDeps.keys
```
`ModuleBoundaryTest.kt:136`

- 실제 코드에서 **발견된** 컨텍스트 집합과 맵의 키가 **정확히 일치**해야 한다.
- 즉 **새 컨텍스트 폴더를 만들고 맵에 안 적으면 테스트가 깨진다.** 몰래 들어와서 검사를 우회하는 게 불가능하다.
- (그래서 이 맵의 키 14개 = `common/domain/` 폴더 14개다. 4-2 절의 숫자가 여기서 나온다.)

**이 맵을 어떤 방식으로 검사하는지, 그리고 나머지 경계 규칙(커널 Spring-free·`@Entity` 위치·연관관계 금지·어댑터 참조 창구)은 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 이 정본이다.**

> [!note] 실측 — 이 맵은 "현황"이 아니라 "허용 상한"이다
> `common/domain/` 전 폴더에서 다른 컨텍스트를 `import` 하는 곳을 전수 조사한 결과, **실제 컨텍스트 간 의존은 `member → ingredient` 딱 하나**다(`member/model/MemberProfile.kt:7-8` 과 `Member.kt:6` 이 `DietCategory`·`IngredientCode` 를 가져온다). 맵에 적힌 `scan → food·member·image·ingredient` 나 `bookmark → food·member·ingredient` 는 **지금은 한 줄도 쓰이지 않는다.**
> 왜냐면 엔티티끼리 **JPA 연관관계를 안 쓰고 `Long` id 컬럼만** 두기 때문이다 — `ScanHistory` 는 `Food` 를 참조하는 대신 `foodId: Long` 을 가진다. 타입 참조가 없으니 패키지 의존도 없다. 자세히는 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]].
> 그래서 맵은 **"현재 이렇게 얽혀 있다"가 아니라 "이 방향까지는 허용한다"** 로 읽어야 한다. 실제 결합도는 맵이 보여주는 것보다 훨씬 낮다.

> [!warning] 맵의 사각지대
> 이 맵은 `com.kbap.common.domain..` **패키지 안**만 본다. `com.kbap.api.<기능>` 의 기능 패키지들은 **대상이 아니다**(`CLAUDE.md:33`) — 컨트롤러와 조합 로직이 여러 컨텍스트를 가로질러 부르는 게 원래 그 층의 일이기 때문이다. 즉 **"영속 모델끼리는 단방향, 조합은 위층에서 자유롭게"** 가 실제 규율이다.

## 7. FE 와 대비 — `src/lib/<도메인>` 과 뭐가 같고 뭐가 다른가

kbap 의 FE 레포도 도메인별로 폴더를 나눈다.

```
kbap-fe/src/lib/
├── api/  ├── auth/  ├── community/  ├── data/  ├── i18n/
├── notifications/  ├── onboarding/  ├── order/  ├── push/
├── review/  ├── scan/  ├── search/
```

`auth`·`community`·`order`·`review`·`scan` — **백엔드 컨텍스트 이름과 거의 겹친다.** 같은 서비스를 두 쪽에서 나누니 당연히 비슷한 선이 나온다. 여기까지가 비유가 맞는 부분이다.

**여기서부터 다르다:**

| | kbap-fe `src/lib/<도메인>` | kbap-server `common.domain.<컨텍스트>` |
|---|---|---|
| 경계를 강제하는 것 | **없다** | `ModuleBoundaryTest` (테스트 실패) |
| `scan/` 에서 `order/` 를 `import` 하면 | **그냥 된다** | 맵에 없으면 **테스트가 깨진다** |
| 순환 참조 (`a→b→a`) | 번들러가 경고할 수도, 안 할 수도 | 방향 맵이 애초에 막는다 |
| 폴더 목록의 단일 출처 | 없음 (폴더가 곧 목록) | `ModuleBoundaryTest.kt:108-123` 의 맵, 그리고 **일치 검사**(:136) |

kbap-fe 에는 ESLint 설정 파일 자체가 없다 — `no-restricted-imports` 같은 경로 제한 규칙이 **하나도 걸려 있지 않다.** 그래서 FE 의 도메인 폴더는 **약속**이고, 백엔드의 도메인 패키지는 **강제**다.

> [!tip] 비유의 경계
> "폴더로 도메인을 나눈다"까지는 같다. **다른 건 어기는 게 얼마나 쉬운가**다. FE 에서 폴더 경계를 넘는 건 자동완성 한 번이면 끝나고 아무도 모른다. 백엔드에서 그러면 CI 가 빨갛게 된다. 그래서 FE 폴더는 시간이 지나면 서서히 섞이고, 백엔드 컨텍스트는 **섞이려면 맵을 고치는 커밋을 남겨야** 한다.
> 그리고 하나 더 — FE 폴더에는 **방향이 없다.** `scan/` 이 `order/` 를 쓰든 그 반대든 똑같이 자연스럽다. 백엔드는 방향이 명시돼 있고 **역방향은 금지**다. 이 "방향"이 모듈러 모놀리스가 진흙 공을 막는 진짜 장치다.

## 8. 두 개의 실행 파일

한 가지만 예고해두고 넘어간다. `:api` 와 `:batch` 는 **각각 따로 실행되는 프로그램**이다. 빌드하면 실행 가능한 파일(bootJar)이 **두 개** 나오고, 켜는 명령도 따로다:

```bash
./gradlew :api:bootRun      # web 앱
./gradlew :batch:bootRun    # 배치 앱
```
`CLAUDE.md:77-78`

진입점도 각각 있다 — `com.kbap.KbapApiApplication`(`api/src/main/kotlin/com/kbap/KbapApiApplication.kt:6-7`) 과 `com.kbap.batch.KbapBatchApplication`(`batch/src/main/kotlin/com/kbap/batch/KbapBatchApplication.kt:7-9`).

그래서 kbap 은 **"프로세스 1개짜리 순수 모놀리스"가 아니라 "코드베이스 하나 · 프로세스 둘"** 이다. 마이크로서비스와 다른 점은 **둘이 서로를 부르지 않는다**는 것 — 네트워크로도 안 부른다. 두 앱의 접점은 **공유 DB 와 큐**뿐이다.

서버 프로세스라는 게 뭔지, bootJar 가 뭐고 왜 두 개인지는 [[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]] 이 정본이다. 배치 앱이 실제로 뭘 하는지는 [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]].

## 9. 주의점 / 헷갈릴 곳

1. **"모듈러 모놀리스니까 나중에 마이크로서비스로 가는 거죠?" — 반드시 그렇진 않다.** 목적은 승격이 아니라 **선택지를 열어두는 것**이다. 끝까지 안 쪼개도 성공이다.
2. **모듈(Gradle)과 컨텍스트(패키지)를 섞어 부르지 말 것.** 모듈은 3개, 컨텍스트는 14개다. **모듈 경계는 컴파일이 막고, 컨텍스트 경계는 테스트가 막는다.** 강도가 다르다.
3. **옛 자료·옛 노트에 나오는 8모듈·16모듈 구조는 전부 사라졌다.** `:app:api`·`:core:kernel`·`:infra:persistence` 같은 좌표를 어디서 보면 **2026-07 이전 문서**다.
4. **테스트를 안 돌리면 안쪽 선은 없는 것과 같다.** 3-5 절의 대가가 이거다. 로컬에서 경계를 어긴 채 커밋해도 컴파일은 통과한다.
5. **컨텍스트를 새로 만들면 맵에 등록해야 한다.** 안 하면 `foundContexts shouldBe allowedDomainDeps.keys` 가 깨진다. 이건 버그가 아니라 **의도된 방어**다.
6. **`common/domain/<ctx>` 만 보고 그 컨텍스트를 다 안다고 생각하지 말 것.** 거기엔 엔티티와 리포지토리만 있다. 그 컨텍스트의 **비즈니스 로직은 `api/…/<기능>` 에** 있다 — ADR-0016 이 인정한 "소스가 두 모듈에 흩어진다"가 이거다.

## 10. 치트시트

**모듈 3개 — 어디에 두나**

| 새 코드가 | 두는 곳 |
|---|---|
| `@Entity` 또는 리포지토리다 | **무조건** `:common` 의 `common.domain.<컨텍스트>` |
| 배치도 쓴다 | `:common` |
| api 만 쓴다 | `:api` 의 `com.kbap.api.<기능>` |
| 배치 잡이다 | `:batch` |

**읽는 순서 — 낯선 컨텍스트를 처음 열 때**

1. `common/src/main/kotlin/com/kbap/common/domain/<컨텍스트>/model/` — **엔티티부터.** 필드가 곧 개념 목록이다.
2. 같은 폴더의 `*JpaRepository.kt` — 이 컨텍스트가 지원하는 조회 방식.
3. `api/src/main/kotlin/com/kbap/api/<기능>/` — 로직과 HTTP 경계.
4. `ModuleBoundaryTest.kt` 의 맵에서 그 컨텍스트 줄 — 뭘 알아도 되는지.

**빠른 판별**

- 파일이 어느 모듈인가 → **맨 윗줄 `package`**. `com.kbap.common` / `com.kbap.api` / `com.kbap.batch`.
- 이 컨텍스트가 저 컨텍스트를 써도 되나 → `ModuleBoundaryTest.kt:108-123` 맵.
- 컨텍스트 목록이 궁금하다 → `ls common/src/main/kotlin/com/kbap/common/domain/`.
- api 코드를 batch 에서 쓰고 싶다 → **못 쓴다.** 진짜 필요하면 `:common` 으로 올리는 게 유일한 길이고, 그건 구조 변경이라 리뷰 대상이다.

## 11. 용어집

- **모놀리스(monolith)**: 한 덩어리로 빌드·배포되는 애플리케이션.
- **마이크로서비스(microservices)**: 기능별로 독립 배포되는 여러 서비스로 쪼갠 구조. 서로 네트워크로 통신한다.
- **모듈러 모놀리스(modular monolith)**: 배포는 한 덩어리, 내부 구조는 강제된 경계로 나뉜 구조. kbap 이 이것이다.
- **마이크로서비스 프리미엄(MicroservicePremium)**: 마이크로서비스로 가면서 무조건 내야 하는 고정 비용(네트워크 실패·분산 추적·배포 조율 등)을 부르는 Fowler 의 용어.
- **DDD(Domain-Driven Design, 도메인 주도 설계)**: 코드 구조를 기술이 아니라 **업무 개념** 기준으로 잡는 설계 접근.
- **바운디드 컨텍스트(bounded context)**: 하나의 일관된 모델과 용어가 통하는 범위. 경계 밖에서는 같은 단어가 다른 뜻일 수 있다.
- **유비쿼터스 언어(ubiquitous language)**: 개발자와 도메인 전문가가 **같은 단어를 같은 뜻으로** 쓰기로 한 어휘. 바운디드 컨텍스트는 이 어휘가 통하는 범위다.
- **Gradle 모듈**: 따로 컴파일되는 코드 묶음. FE 의 워크스페이스 패키지에 해당.
- **잎 모듈(leaf)**: 아무 모듈에도 의존하지 않는 모듈. kbap 에서는 `:common`.
- **전이 의존(transitive dependency)**: A→B, B→C 일 때 A 가 C 를 (선언 없이) 쓸 수 있게 되는 것. ADR-0016 이 문제로 지목한 누수의 원인.
- **bootJar**: Spring Boot 가 만드는, 그것만으로 실행되는 jar 파일. kbap 은 2개(`:api`·`:batch`).
- **ADR(Architecture Decision Record)**: "이 구조를 왜 이렇게 정했나"를 한 건씩 남기는 문서. kbap 은 `docs/adr/` 에 21건.
- **ArchUnit**: 컴파일된 클래스를 읽어 구조 규칙을 테스트로 검사하는 라이브러리. 자세히는 13번 노트.

## 12. 다음에 빠른 재현 체크리스트

1. **"이 클래스 어디 있지?"** → 컨텍스트 이름을 먼저 짚는다(음식? 회원? 스캔?). 엔티티면 `common/…/domain/<ctx>/model/`, 로직이면 `api/…/<기능>/`.
2. **"이 두 개를 합쳐도 되나?"** → 같은 단어라도 **필요한 필드가 다르면 합치지 않는다.** 성분 삼형제(5절)를 떠올린다.
3. **새 도메인 폴더를 만들었다** → `ModuleBoundaryTest.kt` 의 맵에 키를 추가한다. 안 하면 테스트가 깨진다.
4. **컨텍스트 A 에서 B 를 쓰고 싶다** → 맵을 본다. 없으면 **먼저 맵을 고치는 게 맞는지 자문**한다. 대개는 "위층(`api.<기능>`)에서 둘 다 부르면 되는 일" 이다.
5. **batch 에서 api 코드가 필요하다** → 못 쓴다. `:common` 승격이 유일한 길이고, ADR 급 결정이다.
6. **구조 결정의 근거가 궁금하다** → `docs/adr/` 를 번호순으로 본다. 특히 0008(모듈러 모놀리스 채택) → 0016(모듈 다이어트) → 0018(infra 해체) 이 이 노트의 줄거리다.
7. **PR 리뷰에서 볼 것** → `ModuleBoundaryTest.kt` 의 맵이 바뀐 diff. 그건 **경계가 움직였다**는 뜻이라 그냥 넘기면 안 된다.
