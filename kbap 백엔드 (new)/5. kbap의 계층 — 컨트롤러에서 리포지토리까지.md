# 5. kbap의 계층 — 컨트롤러에서 리포지토리까지

> 작성: 2026-08-26 · 맥락: kbap-server 파일 아무거나 열었을 때 "이건 어느 층 코드지?"가 즉답이 되게 하려고.
> 목표: 이후 노트가 전부 물려 쓸 **어휘**를 여기서 확정한다 — Controller · `*Api` · Facade · Service · Repository.

---

## 0. 한 줄 요약

**요청 하나는 `Controller` → (필요할 때만 `Facade`) → `Service` → `JpaRepository` → DB 순으로 흐르고, 그 코드가 전부 `com.kbap.api.<기능>` 한 폴더에 같이 산다.** 층은 폴더가 아니라 **클래스 이름 접미사**로 표시된다.

---

## 1. 층 한눈에 보기

| 이름 | 정체 | 어디 있나 | 몇 개 | 하는 일 | FE로 치면 |
|---|---|---|---|---|---|
| `<Feature>Controller` | HTTP 경계. `@RestController` | `api/.../com/kbap/api/<기능>/` | 26 | URL·메서드 매핑, 요청 바인딩, 응답 감싸기 | 화면 컴포넌트 (이벤트 받아서 넘기기만) |
| `<Feature>Api` | **문서 전용 인터페이스**. Swagger 애너테이션만 | 같은 폴더 | 23 | springdoc이 읽어서 Swagger UI를 그림. 런타임 로직 없음 | `api/types.ts` 같은 타입·문서 선언 파일 |
| `<Feature>Facade` | 여러 서비스를 한 시나리오로 묶는 조립자 | 같은 폴더 | **1** (`ScanFacade`) | 서비스 A·B·C 호출 순서와 실패 처리 | 여러 훅을 엮는 상위 커스텀 훅 |
| `<Feature>Service` | 비즈니스 로직. `@Service` | 같은 폴더 | 31 | 검증·상태 전이·정책, 트랜잭션 경계 선언 | 커스텀 훅 / 도메인 로직 모듈 |
| `<Feature>JpaRepository` | DB 접근. Spring Data 인터페이스 | `common/.../common/domain/<컨텍스트>/` | 22 | 쿼리. 구현은 Spring이 만들어 줌 | `client.ts` 로 감싼 fetch 함수들 |
| 엔티티 (`Member`·`Food`…) | **DB 행이자 도메인 모델** | `common/.../domain/<컨텍스트>/model/` | — | 데이터 + 도메인 메서드를 함께 가짐 | 서버 응답 타입 + 그 타입을 다루는 로직이 한 파일에 있는 상태 |

> 숫자는 2026-08-26 실측(`find ... -name "*Controller.kt"` 등, `build/`·`bin/` 제외).

**핵심 두 줄**
- **층을 나누는 건 폴더가 아니라 접미사다.** `api/member/` 폴더 하나에 컨트롤러·DTO·서비스가 같이 들어 있다.
- **엔티티만 다른 모듈에 있다.** 엔티티와 리포지토리는 `:common` 모듈에, 나머지는 전부 `:api` 모듈에 있다. 모듈은 3개뿐이다 — `:common`·`:api`·`:batch`.

## 2. FE와 대비해서 보기

RN 앱에서 "찜 목록 화면"을 만들 때 파일이 이렇게 갈라지는 것과 같은 발상이다.

| FE (kbap-fe) | kbap-server | 같은 점 | **다른 점 (중요)** |
|---|---|---|---|
| 화면 컴포넌트 | `Controller` | 바깥(사용자/HTTP)과 닿는 유일한 층. 로직을 두지 않는다 | 컨트롤러는 상태가 없다. 인스턴스 하나를 모든 요청이 공유한다 |
| 커스텀 훅 | `Service` | 로직이 사는 곳 | 훅은 화면당 하나씩 다시 실행되지만, 서비스는 앱 뜰 때 **딱 하나 만들어져 계속 재사용**된다 |
| 여러 훅을 엮는 상위 훅 | `Facade` | 조합 담당 | kbap엔 **단 1개**(`ScanFacade`)뿐이다. 없으면 컨트롤러가 서비스를 바로 부른다 |
| `src/lib/api/client.ts` | — | — | **client.ts가 부르는 그 반대편이 `Controller`다.** FE의 `client.ts`가 요청을 보내는 자리에, 서버에서는 컨트롤러가 받고 있다 |
| `zod` 스키마 / 응답 타입 | 엔티티 | 데이터 모양 정의 | 엔티티는 **살아 있다** — 필드를 바꾸면 트랜잭션 끝에 DB UPDATE가 나간다(※ 상세는 8번 「영속성 컨텍스트와 엔티티 매핑」에서) |

> [!tip] 비유 — 식당 주방
> 컨트롤러는 **홀 직원**이다. 주문을 받아 적기만 하고 요리는 하지 않는다.
> 서비스는 **요리사**다. 실제 조리(로직)를 한다.
> 리포지토리는 **창고 담당**이다. 재료를 꺼내오고 넣는다.
> 파사드는 **주방장**이다. 요리사 여럿이 붙는 복잡한 코스에서만 등장한다 — 단품 주문에는 없어도 된다.
> **어디까지 같고 어디서 다른가**: 홀 직원이 창고에 직접 가는 건 이 비유에선 반칙 같지만, kbap에선 **허용된다**(§5). 로직 없이 데이터만 꺼낼 때는 홀 직원이 직접 가도 된다는 규칙이다.

## 3. 평범한 예 — `member` (파사드 없음)

### 3-1. 컨트롤러

```kotlin
@RestController
@RequestMapping(ApiPaths.API + "/members")
class MemberController(
    private val memberService: MemberService,
) : MemberApi {
    @PostMapping("/me/onboarding", version = "1.0")
    override fun completeOnboarding(
        @AuthMemberId memberId: Long,
        @RequestBody request: OnboardingRequest,
    ): ResponseEntity<BaseResponse<Unit>> {
        memberService.completeOnboarding(request.toInput(memberId, serverAssignsProfile = false))
        return ResponseEntity.ok(BaseResponse.ok(Unit))
    }
```
`api/src/main/kotlin/com/kbap/api/member/MemberController.kt:14-26`

- `@RestController` — 이 클래스가 HTTP 요청을 받는 빈이라고 선언한다.
- `@RequestMapping(ApiPaths.API + "/members")` — 이 클래스의 모든 경로 앞에 `/api/members` 가 붙는다. 문자열 `/api` 를 직접 쓰지 않고 상수를 쓰는 게 규약이다.
- `private val memberService: MemberService` — **생성자 파라미터가 곧 의존성 주입**이다. `new` 하는 코드는 어디에도 없다(→ [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]).
- `: MemberApi` — 문서 인터페이스를 구현한다. 그래서 아래 메서드에 `override` 가 붙는다.
- `version = "1.0"` — 같은 경로에 버전이 다른 핸들러가 여러 개 있을 수 있다. 원리는 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]].
- `@AuthMemberId memberId: Long` — 인증 필터가 이미 확인해 둔 회원 id를 꺼내 주는 커스텀 애너테이션. 컨트롤러는 토큰을 직접 파싱하지 않는다.
- **본문이 두 줄이다.** 서비스 호출 한 줄 + 응답 감싸기 한 줄. 이게 컨트롤러가 해야 하는 일의 전부다.
- `ResponseEntity<BaseResponse<Unit>>` — 모든 응답이 공통 봉투로 감싸여 나간다. 봉투의 내용은 7번 노트에서.

### 3-2. `*Api` 인터페이스 — 왜 따로 있나

```kotlin
@Tag(name = "회원", description = "온보딩·프로필 API")
@SecurityRequirement(name = "bearerAuth")
interface MemberApi {
```
`api/src/main/kotlin/com/kbap/api/member/MemberApi.kt:14-16`

```kotlin
    fun completeOnboarding(
        memberId: Long,
```
`api/src/main/kotlin/com/kbap/api/member/MemberApi.kt:46-47`

- `@Tag`·`@Operation`·`@ApiResponses` 같은 **Swagger 문서 애너테이션만** 여기 있다. 실제 `MemberApi.kt` 는 300줄이 넘는데 그 대부분이 한국어 설명문과 예시 JSON이다.
- 반대로 **`@PostMapping`·`@RequestBody`·`@AuthMemberId` 같은 Spring 애너테이션은 여기 없다** — 인터페이스 쪽 파라미터는 타입만 맞춘다(`memberId: Long` 만 있고 애너테이션이 없는 걸 위에서 확인할 수 있다).
- 왜 이렇게 쪼갰나: 문서 설명이 코드보다 훨씬 길어서 한 파일에 두면 컨트롤러 로직이 파묻힌다. **문서는 인터페이스, 동작은 컨트롤러**로 갈라 두면 컨트롤러 파일만 열어도 경로·바인딩·인증이 한눈에 보인다(레포 `CLAUDE.md` "파라미터 애너테이션 위치" 규약).
- FE로 치면 JSDoc·OpenAPI 주석 덩어리를 별도 선언 파일로 뺀 것에 가깝다. **런타임에 하는 일은 없다.**

### 3-3. 서비스

```kotlin
@Service
class MemberService(
    private val memberRepository: MemberJpaRepository,
    @Value("\${kbap.storage.public-base-url:}") private val imagePublicBaseUrl: String,
) {
```
`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:17-21`

```kotlin
    @Transactional(readOnly = true)
    fun getMyProfile(memberId: Long): MyProfileResult {
        val member = getMember(memberId)
        return MyProfileResult.of(
            member = member,
            ranking = MemberRankingResult.from(member.ranking),
            profileImageUrl = ImageUrls.resolve(imagePublicBaseUrl, member.profile.profileImageUrl),
        )
    }
```
`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:47-55`

- `@Service` — 컨테이너가 관리하는 빈. 컨트롤러가 주입받은 그 객체다.
- 서비스는 **리포지토리를 주입받는다.** 컨트롤러가 리포지토리를 아는 일은 없다.
- `@Transactional(readOnly = true)` — DB를 만지는 서비스 public 메서드는 전부 이 선언을 단다(→ [[6. 설정과 프로필, 트랜잭션 경계]]).
- `MyProfileResult` — 엔티티를 그대로 컨트롤러에 넘기지 않고 **결과 타입**으로 바꿔 준다. 컨트롤러는 그걸 다시 `MyProfileResponse` 로 바꿔 응답한다. 즉 `엔티티 → *Result(서비스 산출물) → *Response(HTTP 응답 DTO)` 3단이다.

### 3-4. 리포지토리

```kotlin
interface MemberJpaRepository : JpaRepository<Member, Long> {
    fun findByIdAndMemberStatus(id: Long, memberStatus: MemberStatus): Member?

    fun countByMemberStatus(memberStatus: MemberStatus): Long
```
`common/src/main/kotlin/com/kbap/common/domain/member/MemberJpaRepository.kt:11-14`

- **인터페이스만 있고 구현 클래스가 없다.** Spring Data JPA가 메서드 **이름을 파싱해서** 구현체를 런타임에 만들어 준다 — `findByIdAndMemberStatus` 는 "id가 같고 memberStatus가 같은 걸 찾아라"로 번역된다.
- 여기만 `common` 모듈이다. 경로에 `common/domain/member` 가 들어가는 걸 확인해라.
- `Member?` — 없으면 `null`. Kotlin 물음표가 "없을 수 있음"을 타입으로 못 박는다.

## 4. 파사드가 있는 예 — `scan` (레포 전체에서 유일)

```kotlin
@RestController
@RequestMapping(ApiPaths.API + "/scans")
class ScanController(
    private val scanFacade: ScanFacade,
) : ScanApi {
```
`api/src/main/kotlin/com/kbap/api/scan/ScanController.kt:15-19`

컨트롤러가 `ScanService` 가 아니라 `ScanFacade` 를 주입받는다. 이유는 파사드 안을 보면 바로 보인다.

```kotlin
@Service
class ScanFacade(
    private val scanService: ScanService,
    private val memberService: MemberService,
    private val reservationStore: ScanReservationStore,
    private val ticketManager: ScanTicketManager,
) {
    fun scanMenuBoardImage(
        memberId: Long,
        imagePath: String,
        ocrItems: List<OcrItem>,
        lang: LanguageCode,
    ): ScanResult {
        val member = memberService.getMember(memberId)
        val result = scanService.scan(member, imagePath, ocrItems, lang, requireDetectedMenu = false)
        memberService.increaseScanCount(memberId)
        return result
    }
```
`api/src/main/kotlin/com/kbap/api/scan/ScanFacade.kt:15-34`

- 의존이 **4개**다 — 스캔 서비스, 회원 서비스, Redis 예약 저장소, 티켓 검증기.
- 한 번의 스캔 요청이 "회원 조회 → 스캔 판정 → 스캔 횟수 증가" **세 도메인을 순서대로** 건드린다. 이 순서를 아는 코드가 어딘가에는 있어야 하는데, 컨트롤러에 두면 HTTP 층에 로직이 새고 `ScanService` 에 두면 스캔 서비스가 회원 도메인을 떠안는다.
- `@Service` 애너테이션이 붙어 있다는 데 주목. **파사드는 Spring이 아는 개념이 아니다** — 그냥 서비스인데 이름으로 "얘는 조합만 한다"고 표시한 것이다.
- `ScanFacade` 를 주입받는 컨트롤러는 `ScanController`·`ScanV2Controller` 둘뿐이다. 즉 **나머지 24개 컨트롤러는 서비스를 직접 부른다.** 층을 습관적으로 하나 더 끼우지 않는다.

> [!note] 언제 파사드를 만드나
> "서비스 여러 개를 **정해진 순서로** 부르고, 그 순서 자체가 로직일 때"만. 서비스 하나만 부르면 파사드를 만들지 않는다.

## 5. 사라진 층 — `UseCase` 는 왜 없나

**2026-08-26 실측: 레포 전체에 `UseCase` 라는 이름의 클래스가 0개다** (`grep -rl "UseCase" --include="*.kt" .` → 0건).

옛 kbap-server에는 층이 이렇게 있었다.

```
[옛 구조]  Controller → UseCase → 도메인 서비스 → persistence 어댑터 → DB
           (패키지도 com.kbap.api / com.kbap.domain / com.kbap.application 로 갈림)

[현재]     Controller → (Facade) → Service → JpaRepository → DB
           (전부 com.kbap.api.<기능> 한 폴더 + common.domain.<컨텍스트>)
```

바뀐 이유가 ADR 두 개에 적혀 있다. **왜 없앴는지를 알면 지금 구조가 훨씬 잘 읽힌다.**

| ADR | 무엇을 바꿨나 | 이유 (원문 요지) |
|---|---|---|
| ADR-0017 (`docs/adr/0017-api-feature-package-flattening.md`) | `com.kbap.domain`·`com.kbap.application` 계층 패키지를 없애고 `com.kbap.api.<기능>` 하나로 평탄화 | "한 기능을 파악하려면 같은 모듈 안의 **세 패키지를 오가야 했고**, 두 분류를 유지해 얻는 컴파일 격리는 없고 탐색 경로만 늘어난다" |
| ADR-0014 (`docs/adr/0014-relax-persistence-encapsulation.md`) | 엔티티·리포지토리의 `internal` 제거 → **public**. 위임 전용 창구 서비스 삭제 | "창구는 리포지토리 호출을 그대로 위임할 뿐 도메인 로직이 없어, **캡슐화가 지키는 실질이 없었다**" |

여기서 나온 규칙 한 줄이 지금 코드 전체를 지배한다.

> **"위임 전용 창구 서비스를 만들지 않는다."** 단순 영속 접근은 소비 계층이 리포지토리를 직접 쓴다. (레포 `CLAUDE.md`, ADR-0014)

그래서 **컨트롤러가 리포지토리를 직접 부르는 코드도 규약 위반이 아니다** — 로직이 없다면. 대신 대가가 있다: 컴파일러가 막아 주던 "도메인 서비스 우회"가 가능해졌고, ADR-0014는 이걸 **"리뷰가 잡아야 한다"**고 명시한다. 층을 지키는 게 도구가 아니라 사람의 규율이 된 자리다.

> [!warning] 옛 자료를 볼 때
> 이 레포의 옛 문서·옛 공부 노트에 나오는 `MemberProfileUseCase`·`ScanUseCase`·`FoodRepositoryAdapter` 같은 이름은 **지금 존재하지 않는다**. 파일을 찾으려 하지 말고 위 표의 현재 이름으로 치환해서 읽어라.

## 6. 엔티티가 곧 도메인 모델

층 이야기에서 FE 개발자가 가장 놀라는 지점이다.

- 보통의 백엔드 교재는 "DB용 엔티티"와 "순수 도메인 모델"을 따로 두고 `toDomain()` / `from()` 으로 변환한다.
- **kbap은 그 변환이 없다.** 엔티티 클래스에 도메인 메서드가 직접 들어 있다.

`MemberService.completeOnboarding` 을 다시 보면 서비스가 하는 일이 거의 없다.

```kotlin
    @Transactional
    fun completeOnboarding(input: MemberProfileInput) {
        getMember(input.memberId).completeOnboarding(
            nickname = input.nickname ?: OnboardingProfileDefaults.randomNickname(),
```
`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:22-25`

- `getMember(...)` 로 꺼낸 것이 `Member` **엔티티**인데, 그 엔티티에 `completeOnboarding(...)` 이라는 **도메인 메서드**가 붙어 있다.
- 서비스는 트랜잭션을 열고, 대상을 찾고, 엔티티에게 시킬 뿐이다. 실제 규칙(닉네임 기본값·상태 전이)은 엔티티 안에 있다.
- `save()` 호출이 없다는 것도 봐 둬라. 왜 저장되는지는 ※ 8번 「영속성 컨텍스트와 엔티티 매핑」에서 다룬다.

FE 비유로는 **"응답 타입(`type Member`)에 메서드가 달려 있는 상태"**다. RN에서라면 어색하지만, 서버에서는 "데이터와 그 데이터의 규칙이 붙어 있어야 규칙이 흩어지지 않는다"는 판단이다.

## 7. 경계는 누가 지키나

층과 도메인 경계를 **모듈이 긋지 않는다** — 모듈은 3개뿐인데 도메인은 14개다(`common/domain/` 하위 컨텍스트 디렉터리 수, 2026-08-26 실측). 대신 **패키지 규칙 + ArchUnit 테스트**가 긋는다.

`api/src/test/kotlin/com/kbap/api/architecture/ModuleBoundaryTest.kt` 하나가 "`com.kbap.domain` 패키지에는 클래스가 존재하지 않는다"(`:35`), "`@Entity` 가 붙은 클래스는 공유 도메인 패키지에만 있다"(`:169-173`) 같은 규칙을 **테스트로 검사**한다. 규칙을 어기면 빌드가 깨진다.

※ 어떤 규칙이 몇 개나 걸려 있고 어떻게 읽는지는 **13번 「경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들」**에서 따로 다룬다. 여기서는 "문서가 아니라 테스트가 지킨다"만 알고 넘어가면 된다.

## 8. 주의점 (실제로 헷갈리는 것)

- **폴더로 층을 찾지 마라.** `api/member/` 안에는 컨트롤러·요청 DTO·응답 DTO·서비스·결과 타입이 전부 섞여 있다. 층은 **파일 이름 끝**을 봐라.
- **`*Api` 를 서비스 인터페이스로 오해하지 마라.** 이름이 `MemberApi` 라 "API 계약 추상화" 같지만 실체는 **Swagger 문서 껍데기**다. 구현체는 컨트롤러 하나뿐이다.
- **`*Api` 파일이 길다고 겁먹지 마라.** `ScanApi.kt` 는 대부분 한국어 설명문과 예시 JSON이다. 실제 시그니처는 파일 끝쪽 몇 줄이다.
- **`*Result` 와 `*Response` 는 다르다.** `*Result` 는 서비스가 돌려주는 내부 타입, `*Response` 는 HTTP로 나가는 타입. 컨트롤러가 `Response.from(result)` 로 바꾼다.
- **파사드를 찾다가 시간 쓰지 마라.** 하나뿐이다. 컨트롤러가 서비스를 바로 부르는 게 정상이다.
- **`scan` 만 클래스가 갈라져 있다.** `ScanController` 와 `ScanV2Controller`(`api/.../scan/ScanV2Controller.kt:21-26`, `@RequestMapping(..., version = "2.0+")`)가 따로 존재한다. 레포 `CLAUDE.md` 는 "`*V2Controller` 를 만들지 않는다"고 적어 두었지만 **코드에는 있다** — 문서보다 코드가 앞서 있는 지점이다. 다른 기능(예: `MemberController`)은 규약대로 한 클래스 안에서 `version` 만 다르게 둔다.

## 10. 용어집

- **계층(layer)**: 요청이 지나가는 책임 단계. kbap에서는 폴더가 아니라 **클래스 이름 접미사**로 표시된다.
- **컨트롤러(Controller)**: HTTP 요청을 받아 서비스에 넘기고 응답을 감싸는 클래스. 로직을 두지 않는다.
- **`*Api` 인터페이스**: springdoc(Swagger) 문서 애너테이션만 모아 둔 인터페이스. 컨트롤러가 구현한다. 런타임 동작 없음.
- **파사드(Facade)**: 여러 서비스를 정해진 순서로 조합하는 클래스. kbap엔 `ScanFacade` 하나.
- **서비스(Service)**: 비즈니스 로직과 트랜잭션 경계를 소유하는 빈. `@Service`.
- **리포지토리(Repository)**: DB 접근 인터페이스. Spring Data JPA가 구현체를 자동 생성한다. kbap에서는 **public** 이라 서비스가 아닌 층도 직접 쓸 수 있다.
- **엔티티(Entity)**: DB 테이블 한 행에 대응하는 객체. kbap에서는 **이게 곧 도메인 모델**이라 도메인 메서드를 함께 갖는다.
- **`*Result` / `*Response`**: 서비스가 돌려주는 내부 결과 타입 / HTTP로 나가는 응답 DTO.
- **UseCase**: 옛 kbap의 조합 계층 이름. **지금은 존재하지 않는다**(ADR-0017).
- **ADR**: Architecture Decision Record. "왜 이렇게 정했나"를 남긴 문서. `docs/adr/NNNN-*.md`.

## 11. 다음에 빠른 재현 체크리스트

1. 낯선 API를 만나면 **경로로 컨트롤러부터** 찾는다 (`grep RequestMapping`).
2. 컨트롤러 파일을 열어 **몇 줄인지** 본다. 짧으면 정상. 길면 로직이 샌 것이다.
3. 컨트롤러가 주입받은 게 `Service` 인지 `Facade` 인지 본다 → 조합 시나리오가 있는지 즉시 알 수 있다.
4. 서비스에서 `@Transactional` 유무와 `readOnly` 를 확인한다 → 읽기인지 쓰기인지.
5. 서비스가 부르는 게 **리포지토리**인지 **엔티티의 도메인 메서드**인지 본다 → 로직이 어디 있는지가 갈린다.
6. `UseCase`·`Adapter` 같은 이름이 나오는 자료를 보면 **옛 구조**라고 의심하고 `docs/adr/` 로 확인한다.
