# 26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄

> 작성: 2026-08-27 · 맥락: 15~25번은 전부 **사용자가 화면에서 무언가를 눌러서** 시작된 흐름이었다. 컨트롤러가 있고, 요청이 있고, 응답을 기다리는 사람이 있었다. 이번 노트부터는 그게 없다 — **아무도 요청하지 않았는데 도는 코드**다. 그리고 그 코드는 지금까지 읽어 온 것과 **다른 실행 파일** 안에 산다.
> 목표: ① "왜 서버가 두 개나 있나"에 한 문단으로 답할 수 있게 되기 ② Job·Step·청크가 각각 무엇이고 코드 어디에 적히는지 짚을 수 있게 되기 ③ **같은 잡을 두 번 트리거하면 무슨 일이 벌어지는지** 근거와 함께 말할 수 있게 되기 ④ 기본이 전부 off 인 배치를 로컬에서 **어떻게 관찰하는지** 알게 되기.

---

## 0. 한 줄 요약

`:batch` 는 kbap 의 **두 번째 실행 파일**이다. 사용자 요청을 받지 않고, 대신 **잡(Job)** 을 정의해 두고 **트리거 3가지**(HTTP·인앱 cron·컨테이너 실행)로 기동하며, 어디까지 했는지를 **DB 의 `BATCH_*` 테이블**에 적는다. 코드에 정의된 잡은 **2개**이고, 기본 설정에서 실제로 뜨는 잡은 **1개**다.

---

## 1. 왜 실행 파일이 두 개인가

FE 에서 "서버"는 보통 하나다. 앱이 `fetch` 하는 그 주소가 서버고, 그게 전부다. kbap 은 그 서버 말고 **하나가 더** 있다.

```kotlin
include(
    ":common",
    ":api",
    ":batch",
)
```
— `settings.gradle.kts`

모듈은 3개인데([[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]), 그중 **혼자 실행될 수 있는 건 `:api` 와 `:batch` 둘**이다. `:common` 은 둘이 함께 쓰는 라이브러리라 `main` 함수가 없다. 즉 **bootJar(실행 가능한 jar)는 2개**다.

> [!tip] FE 로 옮기면
> 모노레포에 `apps/mobile`(사용자가 쓰는 앱)과 `scripts/nightly-cleanup.ts`(밤에 도는 정리 스크립트)가 같이 있는 것과 같다. 둘은 같은 `packages/shared` 를 import 하지만, **실행되는 방식과 시점이 완전히 다르다.** `expo start` 로 뜨는 것과 `node scripts/...` 로 돌리는 것.
> 다른 점: FE 스크립트는 보통 내 노트북에서 한 번 돌고 끝나지만, kbap 배치는 **별도 도커 컨테이너로 서버에 배포되어** 자기 수명을 가진다.

**둘을 왜 나눴나** — 세 가지 이유가 겹친다.

| 이유 | 한 앱이면 생기는 문제 |
|---|---|
| 자원 경쟁 | 배치가 음식 수만 건을 돌며 CPU·DB 커넥션을 다 먹으면 **사용자 요청이 느려진다** |
| 배포 주기 | 배치 로직만 고쳤는데 API 서버까지 재시작해야 한다 |
| 장애 격리 | 배치가 OOM 으로 죽으면 API 도 같이 죽는다 |

배포 단위가 실제로 갈라져 있다는 증거는 `Dockerfile.batch` 라는 **별도 도커파일**이다. api 는 `Dockerfile` 로, 배치는 `Dockerfile.batch` 로 각각 이미지를 굽는다.

```dockerfile
RUN chmod +x gradlew \
 && ./gradlew :batch:bootJar -x test --no-daemon \
```
— `Dockerfile.batch:12`

`:batch:bootJar` — 배치 모듈만 골라 jar 를 만든다. api 코드는 이 이미지에 들어가지 않는다.

### 1-1. 그런데 이 배치는 "돌고 죽는" 프로그램이 아니다

배치 프로그램의 전형은 "할 일 하고 죽는" 것이다. 그런데 kbap 배치는 **떠 있으면서 트리거를 기다린다.**

```
# 배치 앱은 상시 기동이고 잡은 POST /internal/batch/jobs?jobName= 트리거로만 실행한다.
```
— `batch/src/main/resources/application.yml:7`

`Dockerfile.batch` 의 마지막 줄도 `ENTRYPOINT ["java", "-jar", "/app/app.jar"]` — 잡 이름을 인자로 넘기지 않는다. 컨테이너가 뜨면 그냥 **떠 있는다.** 그래서 이 앱에는 컨트롤러가 있다(§5). 이유는 뒤에서 다룬다.

## 2. 전체 그림 — 배치 앱의 부품 6개

배치 모듈의 Kotlin 파일은 전부 **14개**다. api 모듈에 비하면 아주 작다.

| 자리 | 파일 | 하는 일 |
|---|---|---|
| 진입점 | `KbapBatchApplication.kt` | `main` 함수. 컴포넌트 스캔 범위를 좁힌다(§7) |
| 인프라 설정 | `config/BatchJdbcJobRepositoryConfig.kt` | 실행 이력을 **DB 에 적도록** JobRepository 를 조립(§4) |
| 기동 창구 | `trigger/BatchJobLauncher.kt` | 잡 이름 → 실제 기동. 중복 실행 판정(§5) |
| HTTP 트리거 | `trigger/BatchJobTriggerController.kt` | `POST /internal/batch/jobs` → 202, `GET .../executions/{id}` → 상태(§5) |
| 스케줄 트리거 | `schedule/BatchJobScheduler.kt` | cron 으로 잡 기동(§5) |
| 잡 정의 | `outbox/`·`vector/` | 실제 일을 하는 잡 2개(§8) |

**의존 방향**: `:batch` → `:common` 한 방향뿐이다. `:api` 와 `:batch` 는 **서로를 전혀 모른다** — Gradle 이 상호 참조를 차단한다(`CLAUDE.md:17`, [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]).

## 3. Job · Step · 청크 — 배치의 세 단어

Spring Batch(버전 6.0.4)를 처음 만나면 단어 세 개가 먼저 나온다.

| 단어 | 뜻 | 크기 |
|---|---|---|
| **Job** | 한 번의 "할 일" 전체. 이름이 붙어 있다 | 큼 |
| **Step** | Job 을 이루는 단계. Job 하나에 Step 여러 개 가능 | 중간 |
| **청크(chunk)** | Step 안에서 **한 번에 커밋하는 단위** | 작음 |

> [!tip] FE 로 옮기면
> - **Job** = `npm run migrate:images` 스크립트 하나
> - **Step** = 그 스크립트 안의 `// 1) 목록 수집` `// 2) 변환 업로드` 같은 단계
> - **청크** = 5,000개를 100개씩 끊어서 `POST /bulk` 로 올리는 그 "100개"
>
> 청크로 끊는 이유도 FE 와 같다. 5,000개를 한 번에 메모리에 올리면 터지고, 한 번에 한 개씩 보내면 왕복이 5,000번이다. 다른 점: FE 의 100개 묶음은 실패하면 그냥 다시 돌리지만, 배치의 청크는 **DB 트랜잭션 경계**라서 100개 중 하나가 실패하면 그 100개가 통째로 롤백된다.

### 3-1. Step 은 두 가지 모양으로 쓴다

kbap 에는 두 모양이 다 있다. 이게 배치 코드를 읽을 때 가장 먼저 갈라지는 지점이다.

**① Tasklet — "그냥 이 코드 블록을 한 번 실행해"**

```kotlin
    fun foodContentOutboxPublishStep(
        jobRepository: JobRepository,
        publisher: FoodContentOutboxPublisher,
    ): Step =
        StepBuilder("foodContentOutboxPublishStep", jobRepository)
            .tasklet(
                { _, _ ->
                    val summary = publisher.publishAll()
                    …
                    RepeatStatus.FINISHED
                },
                ResourcelessTransactionManager(),
            )
            .build()
```
— `batch/src/main/kotlin/com/kbap/batch/outbox/FoodContentOutboxBatchConfig.kt:55-73`

- `StepBuilder("이름", jobRepository)` — 스텝에는 **이름**이 있어야 한다. 그 이름으로 실행 이력이 DB 에 남기 때문이다(§4).
- `.tasklet { ... }` 안이 그냥 실행할 코드다. **읽기/처리/쓰기 구분이 없다.**
- `RepeatStatus.FINISHED` 를 돌려주면 "이 스텝 끝" 이다. `CONTINUABLE` 을 돌려주면 Spring Batch 가 같은 블록을 다시 부른다.
- 여기서 진짜 일을 하는 `publisher.publishAll()` 이 무엇인지는 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] 이 다룬다. 이 노트에서는 **"스텝은 이렇게 생겼다"** 까지만 본다.

**② 청크 지향 — "읽고 → 바꾸고 → 모아서 쓴다"**

```kotlin
        StepBuilder("foodVectorSyncStep", jobRepository)
            .chunk<FoodVectorOutbox, FoodVectorOutbox>(pageSize)
            .transactionManager(transactionManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .retryPolicy(foodVectorSyncRetryPolicy)
            .skipLimit(skipLimit)
            .skip(Exception::class.java)
            .skipListener(skipListener)
```
— `batch/src/main/kotlin/com/kbap/batch/vector/FoodVectorSyncBatchConfig.kt:101-111`

이게 Spring Batch 를 쓰는 진짜 이유다. 세 부품이 역할을 나눈다.

| 부품 | 계약 | 하는 일 |
|---|---|---|
| **Reader** | `read(): T?` — 한 건씩 돌려주고, 없으면 `null` | 원본을 하나씩 꺼낸다 |
| **Processor** | `process(T): S?` — 변환. `null` 이면 그 건은 버려진다 | 한 건을 가공한다 |
| **Writer** | `write(List<S>)` — **묶음으로** 받는다 | 청크만큼 모아 한 번에 쓴다 |

`.chunk(pageSize)` 의 숫자가 곧 "몇 건 모아서 Writer 에 넘기고 커밋하느냐" 다. `pageSize` 기본값은 100 이다(`FoodVectorSyncBatchConfig.kt:98`).

Reader 의 계약은 이렇게 생겼다.

```kotlin
    override fun read(): FoodVectorOutbox? {
        if (buffer.isEmpty() && !exhausted) {
            val page = outboxRepository.findPendingAfterId(cursor, pageSize)
            if (page.isEmpty()) {
                exhausted = true
            } else {
                cursor = page.last().id
                buffer.addAll(page)
            }
        }
        return buffer.removeFirstOrNull()
    }
```
— `batch/src/main/kotlin/com/kbap/batch/vector/FoodVectorOutboxItemReader.kt:26-37`

- 겉으로는 **한 건씩** 돌려주지만, 속으로는 100건씩 DB 에서 퍼 와 버퍼에 담아 둔다. 매 건마다 쿼리를 날리지 않기 위해서다.
- `cursor = page.last().id` — 커서 페이징이다. 24·25번에서 본 그 방식이 여기서도 쓰인다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]).
- `buffer` 가 비고 `exhausted` 면 `null` 을 돌려주고, 그러면 Spring Batch 가 "다 읽었다"고 판단해 스텝을 끝낸다.

`.faultTolerant()` 아래 세 줄(`retryPolicy`·`skipLimit`·`skip`)은 "외부 API 호출이 섞여 있어 일부 건은 실패한다"는 전제에서 나온 장치다. 무엇을 재시도하고 왜 건너뛰는지는 [[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]] 가 다룬다.

### 3-2. Job 은 Step 을 엮은 것

```kotlin
    fun foodContentOutboxPublishJob(
        jobRepository: JobRepository,
        foodContentOutboxPublishStep: Step,
    ): Job =
        JobBuilder("foodContentOutboxPublishJob", jobRepository)
            .incrementer(RunIdIncrementer())
            .start(foodContentOutboxPublishStep)
            .build()
```
— `batch/src/main/kotlin/com/kbap/batch/outbox/FoodContentOutboxBatchConfig.kt:76-83`

`.start(스텝)` 으로 첫 스텝을 지정하고, 스텝이 더 있으면 `.next(...)` 로 잇는다. kbap 의 두 잡은 **둘 다 스텝이 하나뿐**이라 `.start(...)` 만 있다.

`.incrementer(RunIdIncrementer())` 한 줄이 §6 의 주인공이다. 지금은 넘어간다.

## 4. JobRepository — 어디까지 했는지 DB 에 적는다

`npm run migrate` 를 돌리면 터미널에 로그가 흐르고, 창을 닫으면 그 기록은 사라진다. "지난주 그 마이그레이션 성공했었나?" 를 나중에 물어볼 곳이 없다.

Spring Batch 는 그 기록을 **DB 테이블에 남긴다.** 그 기록을 읽고 쓰는 창구가 `JobRepository` 다.

### 4-1. 기록이 없으면 못 하는 일 3가지

| 못 하는 일 | 왜 기록이 필요한가 |
|---|---|
| 중복 실행 방지 | "지금 이 잡이 돌고 있나?" 를 **다른 프로세스가** 물어볼 수 있어야 한다 |
| 재시작 | 5,000건 중 3,200건에서 죽었을 때 어디부터인지 알아야 한다 |
| 사후 확인 | 새벽 3시에 돈 잡이 성공했는지 아침에 확인해야 한다 |

셋 다 **프로세스가 죽은 뒤에도 남아 있어야** 가능하다. 그래서 메모리가 아니라 DB 다.

### 4-2. 그런데 기본값은 메모리다

```kotlin
@Configuration(proxyBeanMethods = false)
class BatchJdbcJobRepositoryConfig(
    private val batchDataSource: DataSource,
    private val batchTransactionManager: PlatformTransactionManager,
) : DefaultBatchConfiguration() {
    @Bean
    override fun jobRepository(): JobRepository {
        val factory = JobRepositoryFactoryBean()
        factory.setDataSource(batchDataSource)
        factory.setTransactionManager(batchTransactionManager)
        factory.afterPropertiesSet()
        return factory.`object`
    }
```
— `batch/src/main/kotlin/com/kbap/batch/config/BatchJdbcJobRepositoryConfig.kt:13-25`

이 파일이 존재하는 이유가 `application.yml` 에 적혀 있다.

```
# JobRepository 는 BatchJdbcJobRepositoryConfig 가 JDBC 로 명시 조립한다 — Boot 4.1 자동구성
# 기본값은 인메모리(ResourcelessJobRepository)라 실행 이력이 남지 않는다.
```
— `batch/src/main/resources/application.yml:13-14`

> [!warning] 이 설정을 지우면 조용히 망가진다
> `ResourcelessJobRepository`(Spring Batch 6 의 클래스)는 **아무 데도 기록하지 않는다.** 에러가 나지 않고, 잡도 정상적으로 돈다. 다만 실행이 끝나면 흔적이 사라져서 §4-1 의 세 가지가 전부 안 된다. "돌긴 도는데 이력이 없다" 는 증상으로만 드러난다.

- `DefaultBatchConfiguration` 을 상속하고 `jobRepository()` 를 `override` 했다 — 자동구성이 만들 기본 빈을 **내 것으로 갈아끼운 것**이다.
- 생성자 파라미터 이름이 `batchDataSource`·`batchTransactionManager` 지만, **그런 이름의 빈이 따로 있는 게 아니다**(레포 전체에 그 이름의 빈 정의가 없다). 컨테이너에 `DataSource` 가 하나뿐이라 타입으로 해결된다 — 이름은 읽는 사람을 위한 표시다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]).
- `getTransactionManager()` 를 같은 것으로 오버라이드했다(`:27`). 잡 메타데이터 기록과 실제 데이터 처리가 **같은 DB, 같은 트랜잭션 매니저**를 쓴다는 뜻이다.

### 4-3. 테이블은 api 가 만든다

```sql
-- Spring Batch 6.0 메타데이터 스키마(MySQL). 배치 앱(:app:batch)은 flyway off 이고 스키마 owner 는 api 라,
-- 배치가 쓰는 잡/스텝 실행 이력 테이블도 api Flyway 가 소유·생성한다. 원본: spring-batch-core schema-mysql.sql.
```
— `api/src/main/resources/db/migration/V2026.07.21.15.03.58__spring_batch_metadata.sql:1-2`

배치가 쓰는 테이블인데 **api 의 마이그레이션 파일**이 만든다. 스키마 주인은 하나여야 한다는 원칙 때문이다 — 자세한 건 [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]].

배치에 Flyway 가 "꺼져 있는" 것도 설정이 아니라 **의존성이 아예 없어서**다. `batch/build.gradle.kts` 에 flyway 줄이 0개다.

만들어지는 테이블은 9개(실행 이력 6 + id 채번용 3)다.

| 테이블 | 담는 것 |
|---|---|
| `BATCH_JOB_INSTANCE` | "잡 이름 + 파라미터" 조합 하나 = 한 행. `unique (JOB_NAME, JOB_KEY)` |
| `BATCH_JOB_EXECUTION` | 그 인스턴스를 **실제로 돌린 회차**. 시작·종료 시각, 상태, 종료 코드 |
| `BATCH_JOB_EXECUTION_PARAMS` | 그 회차에 넘긴 파라미터 |
| `BATCH_STEP_EXECUTION` | 스텝별 read/write/skip/rollback 건수 |
| `BATCH_*_EXECUTION_CONTEXT` | 재시작용 중간 상태 저장소 |
| `BATCH_*_SEQ` 3개 | MySQL 용 id 채번 테이블 |

**`JobInstance` 와 `JobExecution` 의 차이**가 다음 절의 전부다.
- `JobInstance` = "무엇을 하려는가" (잡 이름 + 파라미터)
- `JobExecution` = "그걸 몇 번째로 시도했는가"

같은 인스턴스를 재시작하면 인스턴스는 그대로고 execution 만 하나 더 생긴다.

**컨트롤러가 곧 "사용자용 API" 는 아니기 때문이다.** 이건 사람이 아니라 **다른 기계**(젠킨스·운영 스크립트)가 부르는 창구다. 그 사실이 세 곳에 박혀 있다.

1. 경로가 `/internal/batch` — [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 이 다룬 `/api` 베이스가 아니다.
2. 응답이 `BaseResponse<T>` 봉투를 **안 쓴다**. `BatchJobRunResponse` 를 날것으로 돌려준다.
3. 포트를 호스트로 열지 않는다 — `Dockerfile.batch:5` 에 "8080 은 도커 네트워크 안에서만 쓰므로 호스트로 publish 하지 않는다".

즉 **인증 필터도, 공통 봉투도, 버전 헤더도 여기엔 없다.** 네트워크 자체가 담장이다.

## 6. 같은 잡을 두 번 돌리면 어떻게 되나

여기가 Spring Batch 에서 가장 자주 데는 자리다.

### 6-1. 원칙 — 같은 잡 + 같은 파라미터 = 한 번만

`BATCH_JOB_INSTANCE` 에 `unique (JOB_NAME, JOB_KEY)` 제약이 있다. `JOB_KEY` 는 **잡 파라미터를 해시한 값**이다. 즉 DB 가 "잡 이름 + 파라미터" 조합을 유일하게 만든다.

그래서 이미 성공한 조합을 다시 돌리면 `JobInstanceAlreadyCompleteException` 이 난다. **의도된 설계**다 — "2026-08-27 자 정산" 을 실수로 두 번 돌리면 안 되니까.

### 6-2. 그런데 kbap 은 매번 파라미터 없이 부른다

```kotlin
val execution = jobOperator.start(job, JobParameters())
```
— `BatchJobLauncher.kt:38`

빈 `JobParameters()` 다. 원칙대로면 **두 번째 트리거부터 전부 실패해야 한다.** 그런데 실패하지 않는다. 답은 잡 정의의 그 한 줄에 있다.

```kotlin
            .incrementer(RunIdIncrementer())
```
— `FoodContentOutboxBatchConfig.kt:81` · `FoodVectorSyncBatchConfig.kt:134`

Spring Batch 안쪽이 이렇게 갈라진다.

```java
		if (job.getJobParametersIncrementer() != null) {
			…
			return startNextInstance(job);
		}
		return run(job, jobParameters);
```
— spring-batch-core 6.0.4 `SimpleJobOperator.java:193-201`

- 잡에 incrementer 가 **있으면** `start(job, params)` 는 넘긴 파라미터를 **무시하고** `startNextInstance(job)` 로 간다.
- `startNextInstance` 는 DB 에서 직전 실행의 파라미터를 읽어 incrementer 에 넘긴다(`:280-287`). `RunIdIncrementer` 는 `run.id` 를 1 올린다.
- 결과: 트리거할 때마다 `run.id=1`, `run.id=2`, `run.id=3`… → **매번 다른 `JOB_KEY` → 매번 새 `JobInstance`.**

> [!important] 한 줄로 정리
> `RunIdIncrementer` 는 "이건 재시작이 아니라 **새 실행**이다" 라고 Spring Batch 에 알리는 장치다. 이 줄을 지우면 잡은 **딱 한 번만 성공하고 그 뒤로는 전부 예외**가 된다.

### 6-3. 그럼 중복 실행은 누가 막나

incrementer 때문에 "같은 잡 두 번" 이 DB 차원에서는 막히지 않는다. 그래서 **`BatchJobLauncher` 가 직접 막는다.**

## 7. 왜 컴포넌트 스캔을 좁히나

```kotlin
@SpringBootApplication(scanBasePackages = ["com.kbap.batch", "com.kbap.common.infra.llm"])
@AutoConfigurationPackage(basePackages = ["com.kbap"])
class KbapBatchApplication
```
— `batch/src/main/kotlin/com/kbap/batch/KbapBatchApplication.kt:7-9`

api 쪽 진입점은 `com.kbap` 패키지 루트에 있어서 **아무 설정 없이** 전 계층을 스캔한다(`CLAUDE.md:102`). 배치는 반대로 **명시적으로 좁힌다.** 두 애너테이션이 서로 다른 일을 한다.

| 애너테이션 | 범위 | 무엇을 줍나 |
|---|---|---|
| `scanBasePackages` | `com.kbap.batch` + `com.kbap.common.infra.llm` | `@Component`·`@Service`·`@Configuration` 붙은 **내 클래스들** |
| `@AutoConfigurationPackage` | `com.kbap` **전체** | JPA **엔티티와 리포지토리** |

### 7-1. 좁히는 이유

`com.kbap.api.*` 에는 도메인 서비스가 잔뜩 있다(`MemberService`·`ScanService`·`HomeService`…). 그것들을 스캔 범위에 넣으면 배치 컨테이너가 **api 의 서비스 그래프를 통째로 올린다.**

문제는 그 서비스들이 저마다 의존을 끌고 온다는 것이다 — Redis, Firebase, S3, jjwt, 비전 LLM… 배치는 그중 아무것도 안 쓰는데, **빈을 만들려면 설정값이 있어야 한다.** `OPENAI_API_KEY` 없이는 api 가 아예 부팅하지 않는다는 규칙까지 있다(`CLAUDE.md:53`). 배치가 그걸 다 짊어질 이유가 없다.

그래서 배치는 **필요한 것만 손으로 조립한다.**

```
common 의 리포지토리 (엔티티·JpaRepository)  ← @AutoConfigurationPackage 로 스캔
common.infra.llm 의 어댑터                  ← scanBasePackages 에 명시적으로 포함
그 둘을 엮는 배치 자신의 @Configuration      ← FoodContentOutboxBatchConfig 등
```

`FoodContentOutboxBatchConfig` 가 `SqsClient` 를 직접 `@Bean` 으로 만드는 것(`:31-43`)도 같은 맥락이다. 자동으로 주워 오는 게 없으니 **조립을 손으로 적는다.**

> [!note] 왜 `common.infra.llm` 만 예외인가
> 벡터 동기화 잡이 임베딩 API 를 부르기 때문이다. 임베딩 어댑터가 그 패키지에 있고, 그건 `:api` 도 함께 쓰는 공유 어댑터라 `common` 에 있다(ADR-0018 — `docs/adr/0018-dissolve-infra-modules-into-consumers.md`). [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] 의 "계약은 `common.port.*`, 구현은 소비 모듈" 규칙에서 **batch 도 쓰는 구현만 `common.infra.*`** 로 가는 그 갈래다.

### 7-2. 엔티티만 넓게 스캔하는 이유

`@AutoConfigurationPackage(basePackages = ["com.kbap"])` 는 엔티티·리포지토리 스캔 기준점이다. 이걸 `com.kbap.batch` 로 좁히면 **엔티티를 하나도 못 찾는다** — 엔티티는 전부 `com.kbap.common.domain.<컨텍스트>.model` 에 있으니까([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]).

정리하면 **"데이터 접근층은 넓게, 비즈니스 로직층은 좁게"** 다.

## 9. 트랜잭션 경계 — 배치는 직접 소유한다

[[6. 설정과 프로필, 트랜잭션 경계]] 는 api 의 `@Transactional` 을 다뤘다. 메서드 하나가 곧 트랜잭션 하나였다. 배치는 그 방식을 안 쓴다.

| | api | batch |
|---|---|---|
| 경계 표시 | `@Transactional` 애너테이션 | `TransactionTemplate` 의 **중괄호** |
| 경계 크기 | 메서드 하나 | 한 페이지 / 한 청크 |
| 정하는 주체 | 프록시(프레임워크) | 코드(개발자) |

이유는 크기다. 배치는 수만 건을 도는 루프인데 "메서드 하나 = 트랜잭션 하나" 로 하면 **루프 전체가 한 트랜잭션**이 된다. 5만 건 중 4만 9천 번째에서 죽으면 앞의 4만 9천 건이 전부 롤백된다. 그래서 **작게 여러 번** 끊는다.

청크 지향 스텝은 이걸 프레임워크가 대신 해준다 — `.chunk(100)` 이 곧 "100건마다 커밋" 이다. Tasklet 스텝은 프레임워크가 모르니 코드가 직접 `TransactionTemplate` 로 끊는다. 실제 코드와 줄별 풀이는 [[6. 설정과 프로필, 트랜잭션 경계]] §5 와 [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] 에 있다.

> [!note] `ResourcelessTransactionManager` 는 "트랜잭션 안 쓴다" 는 뜻이다
> `FoodContentOutboxBatchConfig.kt:71` 이 Tasklet 에 넘기는 트랜잭션 매니저는 진짜 DB 매니저가 아니라 **아무것도 안 하는 매니저**다. Tasklet 안에서 `TransactionTemplate` 로 직접 경계를 잡고 있으니, 스텝 바깥에 트랜잭션을 하나 더 씌우면 그 큰 경계가 §9 첫 문단의 문제를 도로 만든다. "스텝 레벨 트랜잭션은 필요 없다" 는 명시적 선언이다.

## 10. 요청/응답 — HTTP 트리거를 직접 불러 보면

**잡 기동**

```http
POST /internal/batch/jobs?jobName=foodContentOutboxPublishJob
```
```json
{
  "jobName": "foodContentOutboxPublishJob",
  "executionId": 12,
  "status": "STARTING",
  "exitCode": "UNKNOWN",
  "message": null
}
```
→ `202 Accepted`. `status` 가 아직 `STARTING` 인 게 핵심이다. **끝났다는 뜻이 아니다.**

**상태 폴링**

```http
GET /internal/batch/executions/12
```
```json
{
  "jobName": "foodContentOutboxPublishJob",
  "executionId": 12,
  "status": "COMPLETED",
  "exitCode": "COMPLETED",
  "message": null
}
```
→ `200 OK`. `status` 가 `STARTING`·`STARTED` 이면 아직 도는 중이고, 그 외면 끝난 것이다. 테스트의 폴링 조건이 정확히 그렇다(`BatchJobTriggerControllerTest.kt:112`).

**실행 중인 잡을 또 트리거**

```json
{
  "jobName": "foodContentOutboxPublishJob",
  "executionId": 12,
  "status": "ALREADY_RUNNING",
  "exitCode": null,
  "message": "이미 실행 중입니다. 해당 실행이 끝난 뒤 다시 트리거하세요."
}
```
→ `409 Conflict`. **돌고 있는 그 execution 의 id 를 알려준다** — 호출자가 그걸로 폴링하면 된다.

**없는 잡 이름**

```json
{
  "jobName": "unknownJob",
  "executionId": null,
  "status": "NOT_FOUND",
  "exitCode": null,
  "message": "실행 가능한 잡: foodContentOutboxPublishJob"
}
```
→ `404`. 오타를 냈을 때 **실행 가능한 잡 목록을 메시지로 돌려준다**(`BatchJobRunResponse.kt:22-29`). 위 응답은 벡터 잡이 off 인 기본 환경 기준이라 목록에 하나뿐이다.

`status` 값(`STARTING`·`STARTED`·`COMPLETED`·`FAILED`·`STOPPED`…)은 Spring Batch 의 `BatchStatus` 이고, `ALREADY_RUNNING`·`NOT_FOUND` 는 kbap 이 그 자리에 끼워 넣은 자체 문자열이다(`BatchJobRunResponse.kt:22-47`).

## 11. 테스트가 보장하는 것

배치는 손으로 확인하기 어려워서 테스트가 특히 중요하다. 골격을 지키는 테스트는 3개다.

| 테스트 | 무엇을 못 깨게 하나 |
|---|---|
| `KbapBatchApplicationTests` | **컨텍스트가 뜬다** — §7 의 좁힌 스캔으로 빈 조립이 성립하는지 |
| `BatchJdbcJobRepositoryConfigTest` | **실행 이력이 DB 에 남는다** — §4 의 JDBC JobRepository |
| `BatchJobTriggerControllerTest` | **202·409·404 와 폴링** — §5·§6 의 트리거 계약 |

가장 얇아 보이는 첫 번째가 사실 제일 자주 터진다. 본문이 비어 있다.

```kotlin
        given("kbap-batch 애플리케이션") {
            `when`("스프링 컨텍스트를 로드하면") {
                then("정상적으로 기동된다") {
                }
            }
        }
```
— `batch/src/test/kotlin/com/kbap/batch/KbapBatchApplicationTests.kt:15-19`

`@SpringBootTest` 가 컨텍스트를 띄우다 실패하면 **본문에 도달하기 전에** 테스트가 깨진다. 검증문이 없어도 의미가 있는 이유다. 배치는 스캔 범위를 좁혀 놨기 때문에 누가 새 서비스를 추가하면 "빈을 못 찾음" 으로 여기서 걸린다.

두 번째가 §6 을 실증한다.

```kotlin
            `when`("같은 잡을 연달아 두 번 실행하면") {
                then("실행마다 새 JobExecution 이 메타데이터에 영속된다") {
                    val first = jobOperator.start(job, JobParameters())
                    val second = jobOperator.start(job, JobParameters())

                    second.id shouldNotBe first.id
                    jobRepository.getJobExecution(first.id) shouldNotBe null
```
— `batch/src/test/kotlin/com/kbap/batch/config/BatchJdbcJobRepositoryConfigTest.kt:34-41`

**같은 파라미터로 두 번 불렀는데 실행 id 가 다르다** — `RunIdIncrementer` 가 일하고 있다는 증거이자, JobRepository 가 인메모리가 아니라는 증거다(인메모리면 `getJobExecution` 이 `null` 을 준다).

세 번째는 409 를 검증하려고 **일부러 느린 잡을 하나 만든다.**

```kotlin
    fun slowTestStep(jobRepository: JobRepository): Step =
        StepBuilder("slowTestStep", jobRepository)
            .tasklet(
                { _, _ ->
                    Thread.sleep(1500)
                    RepeatStatus.FINISHED
                },
```
— `batch/src/test/kotlin/com/kbap/batch/trigger/BatchJobTriggerControllerTest.kt:122-129`

1.5초 자는 잡을 `@TestConfiguration` 으로 컨테이너에 얹고, 트리거한 직후 다시 트리거해 409 를 확인한다(`:83-95`). **"실행 중" 상태를 인위적으로 만들어야 검증할 수 있는 계약**이라 이런 장치가 필요하다. 첫 트리거가 202 로 즉시 돌아오지 않으면 이 테스트 자체가 성립하지 않으므로, §5-2 의 비동기 실행기까지 함께 검증하는 셈이다.

테스트 전체 방법론은 [[14. SDD와 TDD — 스펙과 테스트로 개발하기]].

## 12. 기본이 다 off 인 배치를 어떻게 관찰하나

로컬에서 배치를 띄워도 **아무 일도 일어나지 않는다.** 세 겹으로 잠겨 있다.

| 잠금 | 위치 | 효과 |
|---|---|---|
| 부팅 시 자동 실행 off | `application.yml:15-17` | 컨테이너가 떠도 잡이 안 돈다 |
| 벡터 잡 조건부 | `FoodVectorSyncBatchConfig.kt:33` | 잡 빈 자체가 안 생긴다 |
| 스케줄러 정각 대기 | `BatchJobScheduler.kt:17` | 정각까지 기다려야 한다 |

첫 줄이 특히 중요하다.

```yaml
  batch:
    job:
      enabled: false
```
— `batch/src/main/resources/application.yml:15-17`

Spring Batch 의 기본 동작은 "앱이 뜨면 등록된 잡을 전부 실행" 이다. 그걸 끈 것이다. 이유는 `:10` 에 있다 — "켜면 컨테이너가 뜰 때마다 전 잡이 돈다".

### 12-1. 관찰하는 방법 4가지

**① 테스트를 돌린다 (가장 빠르다)**

```bash
./gradlew :batch:test
```

Testcontainers 가 MySQL 을 띄우고, 실제 잡이 실제 DB 를 상대로 돈다. 스키마는 마이그레이션이 아니라 드라이버에 딸린 공식 DDL 로 만든다.

```yaml
  sql:
    init:
      mode: always
      continue-on-error: true
      schema-locations: classpath:org/springframework/batch/core/schema-mysql.sql
```
— `batch/src/test/resources/application.yml:12-16`

배치 모듈엔 Flyway 가 없으니(§4-3) 테스트에서는 `BATCH_*` 테이블을 이렇게 직접 만든다. `continue-on-error: true` 는 테스트 클래스마다 컨텍스트가 갈리는데 MySQL 컨테이너는 공유돼 두 번째 `CREATE TABLE` 이 중복 오류를 내기 때문이다(`:10-11`).

**② 직접 띄우고 HTTP 로 찔러 본다**

```bash
SPRING_PROFILES_ACTIVE=local ./gradlew :batch:bootRun
curl -X POST 'http://localhost:8080/internal/batch/jobs?jobName=foodContentOutboxPublishJob'
curl 'http://localhost:8080/internal/batch/executions/1'
```

`SPRING_PROFILES_ACTIVE` 는 **반드시 있어야 한다** — 데이터소스가 프로필 파일에만 있어서(`application.yml:72-73`) 없으면 부팅이 실패한다. [[6. 설정과 프로필, 트랜잭션 경계]] §2 가 그 구조를 다룬다.

**③ 메타 테이블을 직접 조회한다**

```sql
SELECT e.JOB_EXECUTION_ID, i.JOB_NAME, e.STATUS, e.EXIT_CODE, e.START_TIME, e.END_TIME
FROM BATCH_JOB_EXECUTION e
JOIN BATCH_JOB_INSTANCE i ON i.JOB_INSTANCE_ID = e.JOB_INSTANCE_ID
ORDER BY e.JOB_EXECUTION_ID DESC LIMIT 20;
```
(예시 쿼리 — 레포에 있는 코드가 아니다.)

**이게 배치 디버깅의 기본기다.** 잡이 언제 돌았고 성공했는지가 전부 여기 있다. 스텝별 처리 건수는 `BATCH_STEP_EXECUTION` 의 `READ_COUNT`·`WRITE_COUNT`·`SKIP_COUNT` 를 본다.

**④ 로그를 본다**

잡마다 완료 로그를 남긴다.

```
음식 콘텐츠 아웃박스 발행 완료 attempted=120 succeeded=118 failed=2
음식 벡터 동기화 완료 read=100 write=97 skipped=3 rollback=0
```
— `FoodContentOutboxBatchConfig.kt:63-68` · `FoodVectorSyncBatchConfig.kt:115-121`

기동·중복·미구성도 전부 로그로 나온다(`BatchJobLauncher.kt:39,42`, `BatchJobScheduler.kt:26,29,36`). 운영에서는 CloudWatch(`/ecs/kbap-prod-batch`)로 본다.

> [!warning] `application.yml:30-34` 의 `logging.level` 은 낡았다
> `com.kbap.infra.llm.provider` 를 가리키는데, ADR-0018 의 infra 모듈 해체로 그 패키지는 **지금 `com.kbap.common.infra.llm`** 이다. 옛 좌표라 저 설정은 아무 로거에도 안 걸린다. 로그 레벨을 조정할 일이 생기면 현재 패키지명을 확인하고 쓰자.

## 13. 치트시트

**잡을 하나 추가하려면**

```kotlin
@Configuration
class MyJobConfig {
    @Bean
    fun myStep(jobRepository: JobRepository, /* 의존 */): Step =
        StepBuilder("myStep", jobRepository)
            .tasklet({ _, _ -> /* 할 일 */; RepeatStatus.FINISHED }, ResourcelessTransactionManager())
            .build()

    @Bean
    fun myJob(jobRepository: JobRepository, myStep: Step): Job =
        JobBuilder("myJob", jobRepository)
            .incrementer(RunIdIncrementer())   // 없으면 딱 한 번만 성공한다
            .start(myStep)
            .build()
}
```
(예시 — `BatchJobLauncher` 는 `List<Job>` 을 주입받으므로 **트리거 코드는 안 고쳐도 된다.** cron 을 붙이려면 `BatchJobScheduler` 에 `@Scheduled` 메서드 하나만 추가한다.)

**HTTP 응답 코드**

| 코드 | 뜻 |
|---|---|
| `202` | 기동 성공. **끝난 게 아니라 시작한 것** |
| `409` | 이미 실행 중. 응답의 `executionId` 로 폴링 |
| `404` | 그런 잡 없음. `message` 에 실행 가능한 목록 |

**핵심 프로퍼티**

| 키 | 기본값 | 효과 |
|---|---|---|
| `spring.batch.job.enabled` | `false` (고정) | 부팅 시 자동 실행 |
| `kbap.batch.scheduler.enabled` | `true` | 인앱 cron |
| `kbap.vector.enabled` | `false` | 벡터 잡 등록 |
| `kbap.llm.embedding.enabled` | `false` | 벡터 잡 등록(둘 다 true 여야) |
| `kbap.batch.food-content-outbox.page-size` | `100` | 아웃박스 페이지 크기 |

우선순위는 **커맨드라인 인자 > 환경변수 > yml** 이라 재배포 없이 덮어쓸 수 있다(`application.yml:38-40`).

```bash
./gradlew :batch:bootRun --args='--kbap.batch.food-content-outbox.page-size=200'
```

## 14. 용어집

| 용어 | 뜻 |
|---|---|
| **Job** | 한 번의 "할 일" 전체. 이름을 가진 실행 단위 |
| **Step** | Job 을 이루는 단계. Job 하나에 여러 개 가능 |
| **Tasklet** | 읽기/쓰기 구분 없이 코드 블록 하나를 실행하는 스텝 |
| **청크 지향 스텝** | Reader → Processor → Writer 로 나눠 N건씩 커밋하는 스텝 |
| **JobInstance** | "잡 이름 + 파라미터" 조합. `(JOB_NAME, JOB_KEY)` 가 유일 |
| **JobExecution** | 그 인스턴스를 실제로 돌린 회차. 재시도하면 하나 더 생긴다 |
| **JobRepository** | 실행 이력을 DB 에 읽고 쓰는 창구 |
| **JobParameters** | 잡에 넘기는 입력값. 이게 `JOB_KEY` 를 결정한다 |
| **`RunIdIncrementer`** | 매 실행마다 `run.id` 를 1 올려 **새 인스턴스**로 만드는 장치 |
| **`BATCH_*` 테이블** | Spring Batch 의 메타데이터 9개 테이블. api 의 Flyway 가 만든다 |
| **bootJar** | `main` 이 들어 있는 실행 가능한 jar. kbap 에 2개 |

## 15. 체크리스트 — 이 노트를 덮고 말할 수 있어야 하는 것

- [ ] kbap 의 실행 파일이 몇 개고 왜 나눴는지 세 가지 이유로 말할 수 있다
- [ ] Job · Step · 청크를 크기 순으로 배열하고 각각을 FE 의 무엇에 빗댈 수 있다
- [ ] Tasklet 스텝과 청크 지향 스텝이 어떻게 다르고, kbap 의 어느 잡이 어느 쪽인지 말할 수 있다
- [ ] JobRepository 를 DB 로 두지 않으면 못 하게 되는 일 3가지를 댈 수 있다
- [ ] `BATCH_*` 테이블을 왜 api 의 마이그레이션이 만드는지 말할 수 있다
- [ ] **같은 잡을 두 번 트리거하면** 무슨 일이 벌어지는지, `RunIdIncrementer` 가 없으면 어떻게 달라지는지 말할 수 있다
- [ ] 그러면 중복 실행은 누가 어떻게 막는지(202/409의 판정 근거) 말할 수 있다
- [ ] 배치 앱에 컨트롤러가 있는 게 왜 이상하지 않은지, 그 컨트롤러가 `/api` 와 뭐가 다른지 짚을 수 있다
- [ ] 202 + 폴링이 왜 필요한지 20번 스캔과 대비해 설명할 수 있다
- [ ] 202 를 "즉시" 만드는 코드가 어느 파일 어느 줄인지 짚을 수 있다
- [ ] 컴포넌트 스캔을 좁히는 이유와, 그런데 엔티티는 왜 넓게 스캔하는지 말할 수 있다
- [ ] 이 골격에 정의된 잡이 몇 개고, 기본 설정에서 실제로 뜨는 건 몇 개인지 말할 수 있다
- [ ] 로컬에서 배치가 도는 걸 확인하는 방법을 두 가지 이상 댈 수 있다
