# 10. Flyway 마이그레이션 — 스키마를 코드로 관리하기

> **한 줄 요약**: DB 의 표 모양(스키마)을 사람이 손으로 고치지 않고, **번호 붙은 SQL 파일을 레포에 커밋해서** 앱이 뜰 때 순서대로 적용시킨다. kbap 은 그 번호를 **생성 시각 timestamp** 로 짓고, 지금 **49개**의 파일이 쌓여 있다.

---

## 1. FE 에는 없던 개념부터 — "스키마"와 "마이그레이션"

**스키마(schema)** 는 DB 안 표의 **모양**이다. 어떤 표(테이블)가 있고, 각 표에 어떤 칸(컬럼)이 있고, 그 칸이 숫자인지 글자인지, 비어도 되는지, 같은 값이 두 번 들어와도 되는지. 데이터가 **내용**이라면 스키마는 **양식지**다.

FE 에서는 이 양식지를 의식할 일이 거의 없다. AsyncStorage 에 넣는 건 그냥 JSON 문자열이고, 키에 뭘 넣든 저장소가 거절하지 않는다. 그래서 모양이 바뀌어도 저장할 때는 아무 일도 안 일어나고, **읽을 때** 터진다.

그런데 그 경험이 사실 마이그레이션 문제의 축소판이다.

> **비유 ①: AsyncStorage 구조를 바꿔 본 경험**
> 앱 v1 에서 `AsyncStorage.setItem('user', JSON.stringify({ name }))` 로 저장해 두었는데, v2 에서 `{ profile: { name } }` 로 구조를 바꾼다. 새로 설치한 사람은 멀쩡한데, **v1 때부터 쓰던 사람의 폰에는 옛 모양의 데이터가 그대로 남아 있다.** 그래서 앱 시작 시 "옛 모양이면 새 모양으로 옮기는 코드"를 한 번 돌린다. 이게 마이그레이션이다.
>
> **어디까지 같고 어디서부터 다른가**
> - 같은 것: **이미 존재하는 옛 데이터를 새 모양으로 옮기는 일회성 코드**라는 점. 그리고 **한 번만 돌아야 한다**는 점.
> - 다른 것 1 — **개수**. AsyncStorage 는 사용자 폰마다 저장소가 따로라 각자 자기 기기에서 한 번씩 돈다. DB 는 **서버 전체가 공유하는 한 벌**이다. 서버를 3대 띄워도 DB 는 하나고, 마이그레이션은 그 하나에 **딱 한 번** 적용돼야 한다.
> - 다른 것 2 — **거절한다**. AsyncStorage 는 모양이 틀려도 순순히 저장하지만, DB 는 없는 컬럼에 넣으려 하면 **에러를 낸다**. 그래서 "코드 배포"와 "스키마 변경"의 순서가 어긋나면 그 즉시 장애다.
> - 다른 것 3 — **되돌리기가 어렵다**. 폰의 로컬 데이터는 최악의 경우 지우고 다시 받으면 된다. 프로덕션 DB 는 그럴 수 없다.
>
> (K-Bap 앱의 클라이언트 저장소 이야기는 [[클라이언트 저장소 — AsyncStorage·SecureStore·메모리 (K-Bap 실전)]] 에 있다.)

### 스키마를 손으로 고치면 안 되는 이유

DB 접속 툴을 열고 `ALTER TABLE member ADD COLUMN nickname VARCHAR(20);` 을 직접 실행하면, 그 순간에는 잘 된다. 문제는 그다음이다.

| 손으로 고쳤을 때 | 무슨 일이 벌어지나 |
|---|---|
| 내 로컬 DB 에만 실행함 | 동료 로컬 DB·개발 서버·프로덕션에는 그 컬럼이 없다. 내 PC 에서만 되는 코드가 된다 |
| 프로덕션에만 실행함 | 다음에 DB 를 새로 만들 때(신규 환경·테스트 컨테이너) 그 변경이 **재현되지 않는다** |
| 누가·언제·왜 바꿨나 | 아무 데도 안 남는다. `git log` 에도, PR 에도 없다 |
| 되돌리려면 | 무엇을 되돌려야 하는지 아무도 모른다 |

**마이그레이션 도구(Flyway)** 는 이걸 "SQL 파일을 레포에 커밋한다"로 바꾼다. 스키마 변경이 **코드 리뷰를 거치고, git 히스토리에 남고, 어느 환경에서든 같은 순서로 재생**된다.

## 2. 개념표

| 용어 | 한 줄 정의 | FE 로 치면 |
|---|---|---|
| 스키마(schema) | DB 안 표들의 모양(테이블·컬럼·타입·제약) | TypeScript 타입 정의. 단, **런타임에 실제로 강제**된다 |
| 마이그레이션(migration) | 스키마를 A 상태에서 B 상태로 옮기는 **SQL 파일 한 장** | 버전 업 시 한 번 돌리는 데이터 변환 함수 |
| DDL | 표의 모양을 바꾸는 SQL (`CREATE TABLE`·`ALTER TABLE`·`DROP`) | — |
| DML | 표의 **내용**을 바꾸는 SQL (`INSERT`·`UPDATE`·`DELETE`) | — |
| Flyway | 마이그레이션 파일을 **버전 순으로 한 번씩** 적용해 주는 도구 | — |
| `flyway_schema_history` | Flyway 가 DB 안에 직접 만드는 표. **"어느 파일을 언제 적용했는지"의 장부** | git 의 커밋 로그 |
| checksum | 각 파일 내용의 지문. 장부에 함께 저장된다 | 커밋 해시와 비슷한 역할 |
| 버전(version) | 파일명의 `V` 뒤 숫자. **적용 순서를 정한다** | — |
| out-of-order | 이미 적용된 것보다 **과거 버전**이 뒤늦게 나타났을 때 그것도 적용할지 여부 | — |
| 스키마 owner | 그 DB 의 스키마를 **만들고 바꿀 권한을 가진 단 하나의 앱** | — |

## 3. 원리 — Flyway 가 실제로 하는 일

앱이 뜰 때, DB 커넥션이 준비된 직후 Flyway 가 딱 이 순서로 움직인다.

1. DB 에 `flyway_schema_history` 표가 없으면 만든다.
2. 클래스패스의 `db/migration` 폴더에서 `V…__….sql` 파일을 전부 찾는다.
3. 장부(`flyway_schema_history`)를 읽어 **이미 적용된 버전 목록**을 얻는다.
4. **검증(validate)**: 이미 적용된 파일들의 지금 내용 checksum 과, 장부에 저장된 checksum 을 대조한다. **하나라도 다르면 부팅을 거부한다.**
5. 아직 적용되지 않은 파일을 **버전 순으로** 하나씩 실행하고, 실행할 때마다 장부에 한 줄씩 기록한다.

여기서 4번이 핵심이다. Flyway 는 **"이미 적용된 파일은 앞으로 절대 안 바뀐다"** 를 전제로 동작한다.

> **비유 ②: Git 커밋 로그**
> 마이그레이션 파일 하나 = 커밋 하나다. 파일들이 쌓인 폴더 = 커밋 로그이고, `flyway_schema_history` = "이 DB 는 어느 커밋까지 반영됐는가"를 적어 둔 표다. 새 환경에 DB 를 만드는 건 **빈 저장소에 커밋을 처음부터 다시 재생하는 것**과 같다.
>
> 그래서 규칙도 git 과 같다. **이미 push 한 커밋을 `--amend` 로 고치면 안 되듯이, 이미 적용된 마이그레이션 파일은 고치지 않는다.** 고치고 싶으면 **되돌리는 새 커밋(= 새 마이그레이션 파일)** 을 하나 더 쌓는다.
>
> **어디까지 같고 어디서부터 다른가**
> - 같은 것: 앞으로만 쌓인다 · 이미 공유된 과거는 동결이다 · 되돌리기도 "앞으로 쌓는 것"으로 한다.
> - 다른 것 1 — **git 은 각 시점의 전체 스냅샷을 갖고 있지만, Flyway 는 "변경 조각"만 갖고 있다.** Flyway 는 "지금 스키마의 최종 모습"이 뭔지 파일만 봐서는 모른다. 처음부터 전부 실행해 봐야 안다.
> - 다른 것 2 — **`git revert` 같은 자동 되돌리기가 없다.** `ALTER TABLE ... DROP COLUMN` 을 되돌리는 SQL 은 사람이 직접 써야 하고, **지워진 데이터는 돌아오지 않는다.** kbap 레포에도 되돌리기(undo) 파일은 한 장도 없다.
> - 다른 것 3 — **git 히스토리는 다시 쓸 수 있어도(force push) DB 는 못 한다.** 프로덕션에 한 번 적용된 변경은 물리적으로 되돌릴 수 없다. 이게 checksum 동결 규칙이 "권장"이 아니라 "금지"인 이유다.

## 4. kbap 실측 — 파일명이 곧 버전이다

파일은 여기 한 곳에만 있다.

```
api/src/main/resources/db/migration/     ← 총 49개 (2026-08-26 실측)
```

가장 오래된 것과 가장 최근 것:

```
V2026.07.16.21.38.41__init_schema.sql
V2026.08.21.05.32.48__scan_history_drop_snapshot_columns.sql
```

이름을 조각내면 이렇게 읽힌다.

| 조각 | 값 | 뜻 |
|---|---|---|
| 접두(prefix) | `V` | "버전이 붙은 마이그레이션"이라는 표시 (Flyway 기본값) |
| 버전(version) | `2026.08.21.05.32.48` | **파일을 만든 시각** `yyyy.MM.dd.HH.mm.ss`, 점으로 구분, 각 자리 두 글자 zero-pad |
| 구분자(separator) | `__` | **밑줄 두 개**. 하나면 인식 안 된다 |
| 설명(description) | `scan_history_drop_snapshot_columns` | 소문자 스네이크. 무엇을 왜 바꾸는지 |
| 확장자(suffix) | `.sql` | — |

Flyway 는 버전을 **점으로 쪼갠 숫자열로 수치 정렬**한다. 그래서 `2026.08.21.05.32.48` 은 `2026.08.20.16.53.09` 보다 뒤다. 흔히 쓰는 `V1`, `V2`, `V3` 같은 정수 버전도 유효하지만, **kbap 에는 정수 버전 파일이 한 장도 없다.** 전부 timestamp 다.

### 왜 정수를 안 쓰나 — 병렬 브랜치

레포 규약(`CLAUDE.md:123`)이 이유를 못 박아 뒀다.

> 병렬 브랜치에서 각자 다음 정수를 잡을 때 생기는 버전 번호 머지 충돌을 없애기 위함이다

정수 버전이면 이런 일이 벌어진다. A 와 B 가 같은 날 각자 브랜치를 딴다. 둘 다 최신이 `V10` 인 걸 보고 각자 `V11__...sql` 을 만든다. 머지하면 **`V11` 이 두 개**가 되고 Flyway 는 부팅을 거부한다(버전은 유일해야 한다). git 은 파일명이 달라 충돌로 잡아 주지도 않는다.

timestamp 는 초 단위라 두 사람이 같은 초에 파일을 만들지 않는 한 충돌하지 않는다. Flyway 공식 문서도 같은 이유로 **여러 명이 동시에 마이그레이션을 추가하는 팀에는 timestamp 버전을 기본으로 권한다.**

### 파일 안은 그냥 SQL 이다

`api/src/main/resources/db/migration/V2026.08.20.16.53.09__order_tables.sql:5-19`

```sql
CREATE TABLE `orders` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `member_id` bigint NOT NULL,
  `image_path` varchar(512) NOT NULL,
  `status` enum('ACTIVE','DELETED') NOT NULL DEFAULT 'ACTIVE',
  `created_at` datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  `updated_at` datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_orders_image_path` (`image_path`),
  KEY `idx_orders_recent` (`member_id`, `id`),
  CONSTRAINT `fk_orders_member` FOREIGN KEY (`member_id`) REFERENCES `member` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

- `id ... AUTO_INCREMENT` + `PRIMARY KEY` — 행마다 자동으로 붙는 유일한 번호.
- `member_id bigint NOT NULL` — **회원 객체가 아니라 회원의 id 숫자**를 든다. kbap 이 JPA 연관관계를 안 쓰는 설계라 그렇다 → [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]].
- `UNIQUE KEY uq_orders_image_path` — 같은 `image_path` 값이 두 행에 들어올 수 없다. 이 한 줄이 "스캔 1회당 주문 1회"를 **DB 가 원자적으로 강제**한다. 앱 코드로 "먼저 조회해 보고 없으면 저장"을 하면 동시 요청 두 개가 둘 다 통과할 수 있는데, unique 제약은 그 틈이 없다.
- `KEY idx_orders_recent (member_id, id)` — 인덱스. "내 주문을 최근 순으로" 조회를 빠르게 한다.
- `status enum('ACTIVE','DELETED')`, `created_at`, `updated_at` — **거의 모든 테이블에 반복해서 나오는 세 컬럼**이다. 행을 진짜로 지우지 않는 소프트 삭제와 공통 시각 컬럼이 왜 매 테이블에 있는지는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 이 정본이다.

> [!note] SQL 파일에는 주석이 있다
> kbap 은 **Kotlin 소스에 주석을 쓰지 않는** 레포지만(`CLAUDE.md:101`), **Flyway SQL·yml·빌드 스크립트는 그 규약 밖**이다. 실제로 위 파일 맨 위에는 `-- KB-337: ...` 로 시작하는 네 줄짜리 설명이 붙어 있다. **마이그레이션 파일 상단 주석은 "왜 이 변경인가"가 남는 거의 유일한 자리이므로 꼭 쓴다.**

### 되돌리기도 앞으로 쌓는다 — 실물

`api/src/main/resources/db/migration/V2026.08.21.05.32.48__scan_history_drop_snapshot_columns.sql`

```sql
-- KB-345: scan_history 의 스냅샷 컬럼 제거. 메뉴 이름은 food_id 로 food 마스터를 조회하고,
-- 사진(image_path)↔메뉴 연결은 orders(KB-337)가 소유한다. 세 컬럼을 읽는 코드는 없다.
ALTER TABLE `scan_history`
  DROP COLUMN `image_path`,
  DROP COLUMN `menu_name`,
  DROP COLUMN `korean_name`;
```

이 세 컬럼은 예전 마이그레이션이 만든 것이다. 그런데 **그 옛 파일을 열어 지우지 않았다.** 대신 "지운다"는 새 파일을 하나 더 쌓았다. 이것이 규칙의 실물이다. 파일 두 장을 순서대로 재생하면 어느 환경에서든 같은 결과에 도달한다.

마이그레이션이 **DDL 전용도 아니다.** 데이터 자체를 손보는 것도 마이그레이션으로 남긴다.

`api/src/main/resources/db/migration/V2026.07.20.14.04.38__backfill_default_profile_image.sql:1-4`

```sql
UPDATE member
SET profile = JSON_SET(profile, '$.profileImageUrl', '/images/default/profile/profile-default-512.png')
WHERE JSON_EXTRACT(profile, '$.profileImageUrl') IS NULL
   OR JSON_TYPE(JSON_EXTRACT(profile, '$.profileImageUrl')) = 'NULL';
```

- 이미 가입해 있던 회원들의 비어 있는 프로필 이미지를 기본값으로 채운다(**backfill**).
- `WHERE` 절이 "비어 있는 행만" 고르므로, 사용자가 이미 설정한 이미지는 건드리지 않는다.
- 이런 파일은 **두 번 실행되면 안 되거나, 두 번 실행돼도 결과가 같아야 한다.** 여기선 후자다(이미 채워진 행은 `WHERE` 에 안 걸린다).

## 5. 이 레포의 핵심 결정 — `out-of-order: true`

`api/src/main/resources/application.yml:21-26`

```yaml
  flyway:
    # 신규 마이그레이션 버전은 생성 시각 기반 점 구분 timestamp(Vyyyy.MM.dd.HH.mm.ss)라,
    # 먼저 만들고 늦게 머지된 마이그레이션이 이미 적용된 최신보다 과거 버전이 될 수 있다.
    # 이를 validate 실패(부팅 거부)가 아니라 정상 적용(out-of-order)으로 허용한다.
    # 전제: 각 마이그레이션은 실행 순서에 의존하지 않게 독립적으로 작성한다. (KB-44)
    out-of-order: true
```

Flyway 노트에서 **가장 중요한 설정 한 줄**이다. 기본값은 `false` 이므로, 이건 의식적으로 켠 것이다.

### 무엇을 허용하는 설정인가

기본 동작(`false`)에서 Flyway 는 **"이미 적용된 최고 버전보다 낮은 버전이 새로 나타나면 무시하거나 거부한다."** 예전에는 잘 돌던 DB 에 갑자기 과거가 끼어드는 건 사고일 가능성이 크다고 보기 때문이다.

`true` 로 켜면 그런 과거 버전도 **그냥 지금 적용**한다. Flyway 공식 문서의 예시 그대로: 1.0 과 3.0 이 적용된 DB 에서 2.0 을 새로 발견하면, 무시하지 않고 2.0 을 실행한다.

### 왜 timestamp 버전에는 이게 **필요한가**

정수 버전에서는 "과거 버전이 나중에 나타나는" 일이 잘 없다. 개발자가 늘 "지금 최신 + 1"을 잡기 때문이다. 그런데 **timestamp 는 머지 시각이 아니라 파일을 만든 시각**이다. 브랜치를 여러 개 굴리는 팀에서는 이 순서가 쉽게 뒤집힌다.

```
월요일 10:00  A 가 브랜치를 따고 V2026.08.10.10.00.00 을 만든다   ← 리뷰가 길어짐
화요일 09:00  B 가 V2026.08.11.09.00.00 을 만들고 그날 바로 머지 → dev 서버에 적용됨
수요일 15:00  A 의 PR 이 드디어 머지된다
              → dev 서버에는 08.11 까지 적용돼 있는데, 08.10 이 뒤늦게 등장
```

이때 `out-of-order: false` 라면 **A 의 마이그레이션이 영원히 적용되지 않거나(무시), 배포 자체가 실패한다(validate 거부).** 서버가 안 뜬다. 브랜치를 두 개 이상 굴리는 팀에서 이건 드문 사고가 아니라 **일상적으로 일어나는 일**이다.

그래서 kbap은 "timestamp 버전을 쓴다"는 선택의 **필연적인 짝**으로 `out-of-order: true` 를 켰다. 정수 버전의 머지 충돌을 없앤 대가로 순서 뒤바뀜을 감수하고, 그 뒤바뀜을 정상으로 인정한 것이다.

### 대가로 지켜야 하는 규율 — 이게 진짜 내용이다

> [!warning] 전제: 각 마이그레이션은 **실행 순서에 의존하지 않게 독립적으로 작성한다**
> `out-of-order: true` 는 "순서가 뒤바뀌어도 괜찮다"고 **선언**한 것이지, Flyway 가 순서 문제를 **해결해 주는 게 아니다.** 순서가 뒤바뀌어도 괜찮게 만드는 건 **마이그레이션을 쓰는 사람의 책임**이다.

무슨 뜻인지 구체적으로 보자. 아래는 **순서에 의존하는** 나쁜 예시다(kbap 코드가 아니라 설명용 예시).

```sql
-- 예시 ①  V2026.08.10.10.00.00__add_nickname.sql
ALTER TABLE member ADD COLUMN nickname VARCHAR(20) NULL;

-- 예시 ②  V2026.08.11.09.00.00__backfill_nickname.sql
UPDATE member SET nickname = CONCAT('user', id) WHERE nickname IS NULL;
```

②는 ①이 **먼저 적용됐다는 가정** 위에 서 있다. 둘이 같은 PR 로 함께 머지되면 문제없다. 하지만 ①이 다른 브랜치에 있어 나중에 머지되면, 이미 ②만 적용된 DB 에서는 없는 컬럼을 업데이트하려다 실패한다.

그래서 규율은 이렇게 정리된다.

| 규율 | 뜻 |
|---|---|
| **서로 의존하는 변경은 한 파일에 묶는다** | 위 예시 ①②는 파일 하나로 합친다. 파일 하나는 통째로 하나의 트랜잭션 단위처럼 다뤄진다 |
| **다른 미적용 마이그레이션의 결과를 전제하지 않는다** | "그때쯤이면 그 컬럼이 있겠지"를 가정하지 않는다. 내 파일이 필요로 하는 상태는 **내 파일 안에서** 만든다 |
| **같은 대상(테이블·컬럼)을 두 브랜치가 동시에 고치지 않는다** | 이건 Flyway 로 못 막는다. 팀 커뮤니케이션 영역이다 |

즉 이 설정의 진짜 내용은 "옵션 한 줄"이 아니라 **"마이그레이션 파일 한 장은 스스로 완결되어야 한다"는 작성 규율**이다.

## 6. 스키마 owner 는 `:api` 하나다

kbap 은 실행 파일이 **두 개**다(`kbap-api`, `kbap-batch`). 그런데 **DB 는 한 벌을 공유**한다. 이때 스키마를 만들고 바꿀 권한은 **api 한쪽만** 갖는다. 두 앱이 각자 마이그레이션을 들고 있으면 같은 DB 에 두 개의 장부가 생기고 서로 충돌한다.

`api/build.gradle.kts:31-33`

```kotlin
    "implementation"(libs.spring.boot.flyway)
    "implementation"(libs.flyway.core)
    "runtimeOnly"(libs.flyway.mysql)
```

- `flyway-core` — Flyway 라이브러리 본체.
- `spring-boot-flyway` — **부팅 시 자동 실행시켜 주는 스프링 부트 자동구성 모듈.** Spring Boot 4 는 자동구성을 기술별 모듈로 쪼개서, 본체만 넣으면 마이그레이션이 자동으로 돌지 않는다(`gradle/libs.versions.toml:65-66`).
- `flyway-mysql` — MySQL 전용 지원. `runtimeOnly` 라 컴파일 시점엔 필요 없고 실행할 때만 있으면 된다.

`batch/build.gradle.kts` 에서 `flyway` 를 grep 하면 **0줄**이다.

여기서 표현 하나를 바로잡고 가자. 레포 문서는 "batch 는 flyway off"(`CLAUDE.md:31`)라고 쓰지만, **끄는 설정이 있는 게 아니다.** 애초에 **의존성이 없다.** 스프링 자동구성은 **클래스패스에 그 라이브러리가 있을 때만** 동작하므로, 라이브러리가 없으면 끌 것도 없다. "off"는 결과를 요약한 말이지 설정 이름이 아니다. (이 대비는 [[6. 설정과 프로필, 트랜잭션 경계]] 가 api·batch 설정 비교로 이미 다룬다.)

batch 리소스에서 flyway 라는 단어가 나오는 곳은 **주석 딱 한 줄**이다.

`batch/src/main/resources/application.yml:12`

```yaml
  # 메타데이터 테이블(BATCH_*)은 스키마 owner=api 의 Flyway 가 생성하므로 배치는 스키마 초기화를 하지 않는다.
```

### `BATCH_*` 테이블까지 api 가 만든다

배치 앱은 Spring Batch 라는 프레임워크를 쓴다. 이 프레임워크는 **"어떤 잡이 언제 실행됐고 어디까지 갔는지"를 DB 테이블에 기록**한다. 그 테이블 이름이 `BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION` 같은 것들이다.

이 표들은 배치 앱이 자기 것으로 쓰지만, **만드는 건 api 의 마이그레이션**이다.

`api/src/main/resources/db/migration/V2026.07.21.15.03.58__spring_batch_metadata.sql:1-9`

```sql
-- Spring Batch 6.0 메타데이터 스키마(MySQL). 배치 앱(:app:batch)은 flyway off 이고 스키마 owner 는 api 라,
-- 배치가 쓰는 잡/스텝 실행 이력 테이블도 api Flyway 가 소유·생성한다. 원본: spring-batch-core schema-mysql.sql.

CREATE TABLE BATCH_JOB_INSTANCE (
    JOB_INSTANCE_ID BIGINT  NOT NULL PRIMARY KEY,
    VERSION BIGINT,
    JOB_NAME VARCHAR(100) NOT NULL,
    JOB_KEY VARCHAR(32) NOT NULL,
    constraint JOB_INST_UN unique (JOB_NAME, JOB_KEY)
) ENGINE=InnoDB;
```

> [!note] 발췌 속 `:app:batch` 는 지금 없는 이름이다
> 이 주석은 마이그레이션 파일 원문이라 **작성 당시 좌표**가 그대로 굳어 있다. 모듈 다이어트 이후 배치 모듈은 루트 직속 **`:batch`** 다.
> 그리고 같은 주석의 "flyway off" 도 §4에서 본 대로 **설정이 아니라 의존성 부재**다 — `batch/build.gradle.kts` 에 flyway 가 아예 없다.
> 마이그레이션 파일은 **이미 적용된 뒤엔 수정 금지**(§3 checksum)라, 이런 낡은 주석은 고치지 못하고 남는다. 읽을 때 감안할 것.


원본은 Spring Batch 라이브러리에 동봉된 공식 DDL 이고, 그걸 **복사해서 kbap 의 마이그레이션 한 장으로 편입**시킨 것이다. 규칙이 예외 없이 적용된 결과다 — **이 DB 의 모든 테이블은, 그게 누구 것이든, api 의 마이그레이션 폴더에 그 출생 기록이 있다.**

(Spring Batch 가 무엇이고 이 표들을 어떻게 쓰는지는 나중 26번 노트 "배치 앱의 골격 — Spring Batch 잡·트리거·스케줄"에서 다룬다.)

## 7. 테스트도 **같은** 마이그레이션을 쓴다

`api/src/test/resources/application.yml:1-9`

```yaml
spring:
  # 테스트 컨텍스트: 외부 키에 의존하지 않게 한다. DB 는 MySQL Testcontainers(@ServiceConnection)로 붙는다(KB-46).
  # 운영과 동일한 Flyway 마이그레이션으로 스키마를 만들고(ddl-auto=validate 로 엔티티↔스키마 정합만 검증),
  # 마이그레이션 SQL 자체를 실 MySQL 에서 검증한다.
  flyway:
    enabled: true
  jpa:
    hibernate:
      ddl-auto: validate
```

**Testcontainers** 는 테스트가 시작될 때 **진짜 MySQL 을 도커 컨테이너로 띄우고**, 끝나면 버리는 도구다.

`common/src/testFixtures/kotlin/com/kbap/common/core/testsupport/MySqlContainerConfig.kt:12-18`

```kotlin
    @Bean
    @ServiceConnection
    fun mySqlContainer(): MySQLContainer =
        MySQLContainer(DockerImageName.parse(MYSQL_IMAGE))
            .withDatabaseName(DATABASE_NAME)
            .withUsername(USERNAME)
            .withPassword(PASSWORD)
```

- `MySQLContainer(...)` — 이미지 `mysql:8.4`(같은 파일 26번째 줄) 로 실제 MySQL 컨테이너를 띄운다. 가짜 DB(H2 같은 인메모리 DB)가 아니다.
- `@ServiceConnection` — 그 컨테이너의 접속 주소·계정을 **스프링의 datasource 설정에 자동으로 꽂아 준다.** 테스트용 URL 을 손으로 적을 필요가 없다.

그래서 테스트 한 번의 실제 순서는 이렇다.

```
빈 MySQL 컨테이너 기동
   → Flyway 가 49개 마이그레이션을 처음부터 순서대로 실행
   → Hibernate 가 ddl-auto: validate 로 엔티티 ↔ 만들어진 스키마 대조
   → 테스트 실행
```

**이 구조가 주는 것 세 가지**

| 얻는 것 | 설명 |
|---|---|
| 테스트가 **프로덕션과 같은 스키마**를 본다 | 테스트용으로 따로 만든 스키마가 아니다. 프로덕션에 적용될 바로 그 SQL 이 만든 스키마다 |
| **마이그레이션 SQL 자체가 검증된다** | SQL 에 오타가 있거나 MySQL 이 거절하는 문법이면 **테스트 단계에서 터진다.** 배포 후 부팅 실패로 알게 되는 게 아니다 |
| **엔티티와 스키마의 어긋남이 잡힌다** | `ddl-auto: validate` 는 Hibernate 가 스키마를 **만들지 않고 대조만** 한다. 엔티티에 필드를 추가하고 마이그레이션 쓰는 걸 잊으면 컨텍스트 로딩부터 실패한다 (엔티티 매핑 자체는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]) |

### 배치 테스트는 다르다 (그리고 그게 스키마 owner 의 증거다)

`batch/src/test/resources/application.yml:8-16`

```yaml
  # 이 모듈엔 Flyway 가 없으므로(스키마 owner=api) Batch 메타 테이블을 드라이버에 딸린
  # 공식 DDL 로 직접 만든다. Boot 4 는 spring.batch.jdbc.initialize-schema 를 더 이상 읽지 않는다.
  # 테스트 클래스마다 컨텍스트가 갈리는데 MySQL 컨테이너는 공유되므로 두 번째 컨텍스트의
  # CREATE TABLE 은 중복 오류가 난다 — continue-on-error 로 흘린다.
  sql:
    init:
      mode: always
      continue-on-error: true
      schema-locations: classpath:org/springframework/batch/core/schema-mysql.sql
```

배치 모듈에는 Flyway 가 없으니, 배치 테스트는 마이그레이션을 재생할 수 없다. 그래서 필요한 표만 라이브러리 동봉 DDL 로 직접 만든다. **"api 가 없으면 스키마도 없다"** 는 게 설정에까지 그대로 드러난 셈이다.

## 8. 주의점 · 트러블슈팅

> [!danger] 절대 하면 안 되는 세 가지 (`CLAUDE.md:123` 금지 사례)
> 1. **신규 마이그레이션에 정수 버전(`V11`) 쓰기** — timestamp 로 통일돼 있다.
> 2. **공유/프로덕션 DB 에 이미 적용된 파일을 수정하거나 이름 바꾸기** — checksum·history 가 깨져 배포 장애가 난다.
> 3. **다른 미적용 마이그레이션의 실행 순서에 의존하는 파일 쓰기** — `out-of-order: true` 환경에서 언제든 터진다.

### "부팅이 안 되는데 Flyway 얘기가 나온다"

| 증상 | 무엇을 의심하나 |
|---|---|
| **checksum mismatch** (`Migration checksum mismatch for version …`) | ① 이미 적용된 파일을 **고쳤다** — 공백·줄바꿈 한 칸만 바뀌어도 걸린다. ② 파일 **이름은 그대로 두고 내용만** 바꿨다. ③ 브랜치를 옮기며 그 버전의 파일 내용이 달라졌다. → **git 으로 그 파일의 최근 변경을 먼저 본다** |
| **Detected applied migration not resolved locally** | 장부에는 있는데 파일이 **사라졌다.** 파일을 지웠거나, 브랜치가 그 파일이 없는 시점이다 |
| **Detected resolved migration not applied** | 적용 안 된 과거 버전이 있다. `out-of-order` 가 꺼진 환경이라면 이걸로 실패한다 (kbap api 는 켜져 있으니 대개 정상 적용된다) |
| **Migration … failed** 후 다음 부팅부터 계속 실패 | 실패한 마이그레이션이 장부에 실패 기록으로 남았다. 원인 SQL 을 고치기 전에 그 실패 기록을 정리해야 한다 |
| **엔티티↔스키마 불일치** (`Schema-validation: missing column …`) | Flyway 문제가 아니다. 엔티티에 필드를 추가하고 **마이그레이션을 안 썼다** |

### 로컬에서 꼬였을 때 vs 프로덕션에서 꼬였을 때

**로컬은 리셋이 정답이다.** 로컬 DB 를 통째로 drop 하고 다시 만들면 49개가 처음부터 재생돼 깨끗해진다. 프로덕션과 달리 잃을 데이터가 없다.

**프로덕션·공유 DB 는 리셋이 없다.** 여기서는 원인에 따라 다르다.

- **파일을 잘못 고쳐 checksum 이 깨진 경우**: 파일을 **원래 내용으로 되돌리는 것**이 1순위다. git 에 원본이 있다.
- **정말로 장부를 손봐야 하는 경우**: Flyway 의 `repair` 명령이 있다. 실패한 마이그레이션 기록을 지우고, 장부의 checksum·설명을 현재 파일 기준으로 다시 맞추고, 사라진 파일을 삭제 표시한다. **다만 repair 는 DB 안 데이터를 되돌려 주지 않는다** — 실패한 마이그레이션이 이미 만들어 버린 테이블 같은 건 사람이 직접 치워야 한다. **혼자 판단하지 말고 팀에 알리고 하는 작업이다.**
- **스키마를 되돌려야 하는 경우**: 파일을 지우는 게 아니라 **되돌리는 새 마이그레이션을 쌓는다.** (§4 의 `scan_history_drop_snapshot_columns.sql` 이 그 예다.)

> [!warning] 배포 순서
> 컬럼을 **지우는** 마이그레이션은 그 컬럼을 읽는 코드가 **전부 사라진 뒤**에 배포해야 한다. 반대로 컬럼을 **추가하고 그 값을 쓰는** 코드는 마이그레이션이 **먼저** 적용된 뒤여야 한다. kbap 은 api 앱이 뜰 때 마이그레이션이 도니 "새 코드 + 새 마이그레이션"이 한 배포에 함께 가지만, **구버전 인스턴스가 잠깐 함께 떠 있는 순간**(롤링 배포)이 있다면 그 순간에도 안전해야 한다. 위 `scan_history` 삭제 파일 주석이 굳이 "세 컬럼을 읽는 코드는 없다"고 못 박아 둔 이유다.

## 9. 치트시트

### 새 마이그레이션 만들기

```bash
# 1) 버전(= 지금 시각) 생성 — macOS/Linux 공통
date "+V%Y.%m.%d.%H.%M.%S"
#   → V2026.08.26.14.27.44

# 2) 파일 만들기 (설명은 소문자 스네이크, 구분자는 밑줄 두 개)
touch "api/src/main/resources/db/migration/$(date '+V%Y.%m.%d.%H.%M.%S')__add_member_nickname.sql"
```

파일 안에는 이렇게 쓴다.

```sql
-- KB-999: 무엇을 왜 바꾸는지 한두 줄. (SQL 주석은 레포 주석 금지 규약 밖 — 반드시 남긴다)
ALTER TABLE `member`
  ADD COLUMN `nickname` varchar(20) NULL;
```

그다음 **테스트를 돌린다.** Testcontainers 가 이 파일까지 포함해 스키마를 새로 만들고, `ddl-auto: validate` 가 엔티티와 대조해 준다. 여기서 통과하면 스키마 변경은 거의 안전하다.

### 규칙 요약

| 상황 | 이렇게 한다 |
|---|---|
| 새 테이블·컬럼이 필요하다 | 새 파일 한 장. 버전은 `date` 로 뽑은 지금 시각 |
| 방금 만든 파일이 마음에 안 든다 (**아직 아무 데도 안 올림**) | 그냥 고친다. 로컬 DB 는 리셋 |
| 이미 머지돼 dev/프로덕션에 적용됐다 | **파일을 건드리지 않는다.** 되돌리거나 고치는 **새 파일**을 쌓는다 |
| 컬럼 추가 + 그 값 채우기를 같이 해야 한다 | **한 파일에** 넣는다. 두 파일로 쪼개면 out-of-order 에서 순서가 뒤집힐 수 있다 |
| 데이터만 고치면 된다 (backfill) | 그것도 마이그레이션이다. `WHERE` 로 대상을 좁히고, 두 번 돌아도 결과가 같게 쓴다 |
| 다른 브랜치와 같은 테이블을 건드릴 것 같다 | Flyway 가 막아 주지 않는다. 사람끼리 먼저 얘기한다 |

### 확인 명령

```bash
# 마이그레이션 몇 개인가
ls api/src/main/resources/db/migration | wc -l

# 최근 5개는 뭘 바꿨나
ls api/src/main/resources/db/migration | tail -5

# 어떤 마이그레이션이 이 테이블을 만들었나
grep -rl "CREATE TABLE .orders." api/src/main/resources/db/migration/

# 이 파일이 언제 머지됐나 (checksum 사고 조사 1순위)
git log --oneline -- "api/src/main/resources/db/migration/V2026.08.20.16.53.09__order_tables.sql"
```

## 10. 용어집

- **스키마(schema)**: DB 안 표들의 모양. 테이블·컬럼·타입·제약의 집합.
- **DDL / DML**: 표의 **모양**을 바꾸는 SQL(`CREATE`·`ALTER`·`DROP`) / 표의 **내용**을 바꾸는 SQL(`INSERT`·`UPDATE`·`DELETE`).
- **마이그레이션(migration)**: 스키마(또는 데이터)를 한 상태에서 다음 상태로 옮기는 SQL 파일 한 장. **한 번만 실행된다.**
- **`flyway_schema_history`**: Flyway 가 DB 안에 만드는 장부 테이블. 어느 버전을 언제 적용했고 checksum 이 무엇이었는지 기록한다.
- **checksum**: 파일 내용의 지문. 적용 시점 값과 지금 값이 다르면 부팅을 거부한다.
- **out-of-order**: 이미 적용된 최고 버전보다 낮은 버전이 뒤늦게 나타났을 때도 적용할지 여부. Flyway 기본은 `false`, **kbap api 는 `true`**.
- **스키마 owner**: 그 DB 의 스키마를 만들고 바꿀 권한을 가진 **단 하나의 앱**. kbap 에서는 `:api`.
- **backfill**: 새로 만든 컬럼이나 바뀐 형식에 맞춰 **기존 행들의 값을 채워 넣는** 작업.
- **Testcontainers**: 테스트 시작 시 진짜 DB(여기선 MySQL)를 도커 컨테이너로 띄우고 끝나면 버리는 도구.
- **`ddl-auto: validate`**: Hibernate 가 스키마를 **만들지 않고**, 엔티티와 실제 스키마가 맞는지 **대조만** 하는 모드.
- **repair**: 장부의 실패 기록 제거·checksum 재정렬을 하는 Flyway 명령. **DB 데이터는 되돌리지 않는다.**

## 11. 체크리스트

- [ ] "스키마"가 뭔지, 왜 손으로 고치면 안 되는지 한 문장으로 말할 수 있다
- [ ] 마이그레이션 파일명 다섯 조각(`V` / 버전 / `__` / 설명 / `.sql`)을 조각내 읽을 수 있다
- [ ] kbap 이 정수 대신 timestamp 버전을 쓰는 이유(병렬 브랜치 머지 충돌)를 설명할 수 있다
- [ ] `out-of-order: true` 가 **왜 필요했고**, 그 대가로 지켜야 할 규율이 무엇인지 말할 수 있다
- [ ] "이미 적용된 파일은 고치지 않는다"의 이유를 checksum 으로 설명할 수 있다
- [ ] 이미 적용된 변경을 되돌리는 방법(= 새 파일을 쌓는다)을 안다
- [ ] `api/src/main/resources/db/migration/` 을 열어 최근 파일 세 개가 무엇을 바꿨는지 읽어 봤다
- [ ] batch 에 Flyway 가 없는 것이 **설정이 아니라 의존성 부재**임을 안다
- [ ] 테스트가 프로덕션과 같은 마이그레이션으로 스키마를 만든다는 사실과, 그게 왜 이득인지 안다
- [ ] checksum mismatch 를 만났을 때 **가장 먼저 볼 것**(그 파일의 git 변경 이력)을 안다
