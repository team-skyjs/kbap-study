# 🗺️ kbap 백엔드 공부 지도 (2026-08)

프론트엔드(React Native/Expo)만 해온 내가 **kbap-server**(Kotlin·Spring Boot 백엔드)에 합류하기 위한 커리큘럼이다. 이 노트는 목차이자 진도표 — 노트를 하나 끝낼 때마다 체크한다.

## 왜 새로 썼는가

2026-07에 21개 노트로 한 번 완주했지만, 그 뒤 두 달 동안 레포가 통째로 바뀌었다. 모듈이 8개에서 **3개(`:common`·`:api`·`:batch`)로 다이어트**됐고, 노트들의 뼈대였던 **UseCase 계층이 통째로 사라졌으며**(지금은 Controller→Service), 엔티티가 곧 도메인 모델이 되면서 **JPA 연관관계는 아예 금지**됐다. 배치는 Spring Batch로 재작성됐고, LLM 스코어링 파이프라인은 다른 레포로 이관됐다.

고쳐 쓰는 것보다 새로 쓰는 게 빨랐다. 옛 노트 21개는 `kbap 백엔드 (old)` 폴더에 그대로 보관돼 있다 — 2026-07 시점의 기록으로만 유효하니, 지금 코드를 알고 싶으면 이 지도만 따라오면 된다.

> [!info] 읽는 순서의 원칙
> 아래에서 위로 쌓는다. 각 단계는 **바로 앞 단계 지식만 전제**한다. "서버가 뭔지"(1단계)를 알아야 "스프링이 그 서버를 어떻게 조립하는지"(2단계)가 보이고, 조립을 알아야 "데이터를 어떻게 저장하는지"(3단계), 그 위에서 "왜 이런 구조로 나눴는지"(4단계)를 이해한다. 5단계부터는 실제 코드 한 흐름을 세로로 관통하며 앞의 개념들을 한꺼번에 확인한다.

## 1단계 · 백엔드 기초 — 서버라는 프로그램
> 왜 먼저: FE는 "화면을 그리는 코드"였다. 백엔드는 "켜두고 요청을 기다리는 프로그램"이다. 이 세계관 전환이 없으면 뒤 단계 전부가 공중에 뜬다.

- [x] [[1. 서버는 켜두는 프로그램 — 프로세스·포트·두 개의 실행 파일]] — 서버 프로세스와 진입점, kbap이 web·batch 두 개로 도는 이유
- [x] [[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]] — 스레드풀 vs 이벤트루프, 블로킹 호출이 JVM에선 왜 괜찮은지
- [x] [[3. JVM 위의 Kotlin — 컴파일·널 안전·Gradle 3모듈]] — TS와 대비한 컴파일 언어의 안전망, 버전 카탈로그와 buildSrc

> [!tip] 2번 §7 에서 막히면 — 순서를 바꿔라
> 2번의 **§7(동시성의 대가)부터는 스프링의 "빈"** 이 깔린다. 그런데 빈의 정본은 **4번**이라 아직 안 나왔다(2026-09-03 확인된 순서 문제 — 2번 §7-1 에 최소 설명 상자를 넣어 뒀지만 근본 의존은 남는다).
> **막히면 이 순서로**: 2번 §1~§6 → **4번**(빈·싱글턴·DI) → **3번**(JVM 과 코틀린의 관계) → **2번 §7 로 복귀**. §7~§9 는 §1~§6 과 독립적이라 건너뛰어도 앞부분 이해에 지장 없다.

## 2단계 · Spring 핵심 — 부품을 직접 만들지 않는 프레임워크
> 왜 먼저: 1단계에서 "서버가 뜬다"를 알았다. 그 서버 안에서 객체들을 누가·어떻게 연결하는가가 스프링의 전부다. 이걸 모르면 실코드에서 생성자 주입이 마법으로 보인다.

- [x] [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] — 부품을 직접 `new` 하지 않고 컨테이너가 만들어 생성자로 꽂아준다
- [x] [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] — Controller(+`*Api` 인터페이스)→Facade→Service→Repository. UseCase 계층은 왜 없나
- [x] [[6. 설정과 프로필, 트랜잭션 경계]] — `application.yml`·프로필 4종, `@Transactional`이 여는 작업 경계
- [x] [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] — 모든 응답이 `BaseResponse<T>`, 에러는 코드로 분기, 버전은 `X-API-Version` 헤더로

## 3단계 · JPA·영속성 — 객체를 DB에 저장하기
> 왜 먼저: 2단계에서 계층을 나눴다. 그 맨 아래 계층이 DB와 대화한다. 백엔드 버그의 최대 진원지라 개념을 먼저 잡아야 한다.

- [x] [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] — 객체↔테이블 매핑, 변경 감지, BaseEntity와 소프트 삭제
- [x] [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] — N+1이 뭔지, 그리고 kbap이 연관 대신 `Long` id를 쓰는 이유
- [x] [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] — 스키마 버전 관리, timestamp 버전 규칙

## 4단계 · 아키텍처·방법론 — 왜 이렇게 나눴나
> 왜 먼저: 1~3단계로 "부품·조립·저장"을 안다. 이제 kbap이 그것들을 왜 이렇게 쪼갰는지 — 코드를 읽을 때 매번 마주칠 "경계"의 이유를 배운다.

- [x] [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] — 바운디드 컨텍스트, 모듈 3개로 다이어트한 이유
- [x] [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]] — 계약은 port에, 구현은 소비 모듈에, 조립은 config에
- [x] [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] — 경계를 사람의 규율이 아니라 테스트가 지킨다
- [x] [[14. SDD와 TDD — 스펙과 테스트로 개발하기]] — spec→plan→tasks 흐름, Kotest BehaviorSpec Red→Green→Refactor

## 5단계 · 실코드 한 흐름 관통하기
> 왜 나중에: 개념(1~4단계)을 손에 쥔 뒤라야, 하나의 요청이 Controller→Service→리포지토리를 지나는 걸 따라가며 "아 이게 그거였구나"가 된다. 읽기 흐름 → 쓰기 흐름 → 배치 순으로, 쉬운 슬라이스부터 넓게 관통하는 것 순으로 놓았다.

**읽기·인증**

- [x] [[16. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]] — 소셜 검증→회원 조회·가입→토큰 발급
- [x] [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] — 필터라는 횡단 계층, refresh 회전
- [x] [[18. 홈 화면 조회 흐름 — 여러 서비스를 한 응답으로 모으기]] — 읽기 fan-in 조합

## 커리큘럼 완주 요약 (2026-08-27)

- **29노트 · 약 17,000줄 · 76만 자.** 노트 하나가 평균 585줄이라, 한 번에 한 노트씩 앉아서 읽는 분량이다.
- **5단계 + 확장** 구성: 기초 3 → Spring 핵심 4 → 영속성 3 → 아키텍처 4 → 실코드 관통 14 → 확장 1. 앞 18노트가 개념이고 뒤 11노트가 실제 코드 흐름이다.
- **2026-07 커리큘럼(21노트)과 무엇이 달라졌나** — 옛 노트 중 **2주제는 대체 없이 폐기**됐다(옛 19번 "조사 대기열 순회" 구조 제거, 옛 20번 LLM 스코어링 파이프라인은 `kbap-langchain` 레포로 이관). 반대로 **8주제가 새로 생겼다**: API 계약(7)·이미지 업로드(21)·리뷰(22)·주문(24)·커뮤니티(25)·아웃박스와 SQS(27)·임베딩과 벡터 검색(28), 그리고 ArchUnit 경계 테스트(13). 나머지는 같은 주제를 **결론이 바뀐 채로** 다시 썼다 — 특히 9번은 옛 8번("LAZY 로딩과 N+1")과 결론이 정반대다(연관관계를 잘 쓰는 법 → 연관관계를 아예 안 쓴다).
- 옛 21노트는 `kbap 백엔드 (old)` 폴더에 그대로 있다(진입은 [[🏠 홈]]의 📦 보관 줄로 — 이 지도에서 링크를 걸지 않는 건 옛 노트가 검색·그래프에서 현행처럼 보이지 않게 하려는 것). 각 노트 머리에 "지금 기준 노트 → 새 N번" 이 달려 있어, 옛 노트를 보다가도 현행으로 건너올 수 있다.

> [!tip] 어디부터 읽으면 좋은가
> **처음이라면 1번부터 순서대로.** 각 단계가 바로 앞 단계만 전제하도록 짜여 있어서, 건너뛰면 뒤에서 되돌아오게 된다.
>
> **급하게 코드를 읽어야 한다면** — 5번(계층) → 7번(API 계약) → 15번(가장 얇은 요청 흐름) 세 개면 kbap 코드베이스에서 길은 잃지 않는다. 개념은 막힐 때마다 돌아와서 채우면 된다.
>
> **면접·온보딩 대비라면** — 9번(연관관계를 안 쓰는 이유)·13번(ArchUnit)·23번(원자적 카운트)·29번(Redis 를 캐시로 안 쓰는 이유)이 "왜 그렇게 했나" 를 묻기 좋은 자리다. 넷 다 kbap 이 남들과 다르게 선택한 지점이라 설명할 거리가 있다.
