# 6. 설정과 프로필, 트랜잭션 경계

> 작성: 2026-08-26 · 맥락: kbap-server 를 열면 코드보다 먼저 `application.yml` 이 눈에 들어오는데, 여기서 정해진 값이 어디로 흘러가는지 모르면 서비스 코드가 안 읽힌다. 그리고 서비스 코드 맨 위에 거의 항상 붙어 있는 `@Transactional` 이 뭔지 모르면 "이 함수는 대체 언제 DB에 쓰는 거지?"가 끝까지 안 풀린다.
> 목표: **설정값 하나가 앱 안까지 오는 길**과 **DB 작업 한 덩어리의 시작·끝**을 각각 한 문장으로 말할 수 있게 되기.

---

## 0. 한 줄 요약

**설정**은 "환경마다 달라지는 값을 코드 밖 `yml` 로 빼고, 프로필로 골라 넣는 것"이고, **트랜잭션**은 "여기서부터 여기까지의 DB 작업은 **전부 되거나 전부 안 되거나** 둘 중 하나"라고 선언하는 것이다. kbap 에서 후자는 거의 항상 `@Transactional` 한 줄로 선언된다.

---

## 1. 설정 파일 — 값을 코드 밖으로

### 1-1. FE 에서 이미 하고 있던 것

FE 에서 `kbap-fe/.env` 에 이렇게 써 뒀다.

```
EXPO_PUBLIC_BE_BASE=https://dev.kbap.site
```

코드에 `https://dev.kbap.site` 를 박지 않는 이유는 뻔하다. 개발용 서버와 실서비스 서버 주소가 다르고, 주소가 바뀔 때 코드를 고치고 싶지 않기 때문이다. **백엔드 설정 파일도 정확히 같은 동기**로 존재한다. 다른 점은 규모다 — FE 의 `.env` 가 키=값 몇 줄이라면, 백엔드는 DB 주소·Redis 주소·JWT 서명키·S3 버킷·외부 API 키·타임아웃까지 전부 여기로 나온다.

| | FE (`.env`) | 백엔드 (`application.yml`) |
|---|---|---|
| 형식 | 평평한 `KEY=value` | **계층 구조**(YAML 들여쓰기) |
| 읽는 법 | `process.env.EXPO_PUBLIC_BE_BASE` | 스프링이 읽어서 객체에 꽂아 준다 (직접 안 읽음) |
| 환경 분기 | `.env.development` / `.env.production` 파일 교체 | **프로필**(`application-dev.yml` 등)을 런타임에 선택 |
| 빌드 시점 | 번들에 값이 **구워진다** | 실행 시점에 읽는다 — **재빌드 없이 값만 바꿔 재시작 가능** |

마지막 줄이 실무에서 제일 크게 체감되는 차이다. `EXPO_PUBLIC_*` 는 빌드 산출물에 들어가 버려서 값이 바뀌면 다시 빌드해야 하지만, 백엔드는 같은 jar 파일을 그대로 두고 환경변수만 바꿔 재시작하면 된다.

### 1-2. `application.yml` 의 구조 — 남의 구역과 내 구역

`api/src/main/resources/application.yml` 을 열면 최상단 키가 크게 네 종류다.

| 최상단 키 | 누구 것인가 | 예 |
|---|---|---|
| `spring` | **스프링이 정의한 이름** — 이름을 마음대로 못 짓는다 | `spring.datasource.url`, `spring.flyway.out-of-order` |
| `server` | 마찬가지로 스프링(내장 톰캣) 것 | `server.forward-headers-strategy` |
| `logging` | 마찬가지 | `logging.level.…` |
| `kbap` | **우리가 만든 이름** — 완전히 자유 | `kbap.auth.jwt.secret`, `kbap.upload.max-bytes` |

이 구분이 중요하다. `spring.*` 아래 키는 스프링이 이미 아는 이름이라 **적어 두기만 하면 알아서 동작한다**(datasource 를 적으면 DB 연결이 자동으로 만들어진다). 반면 `kbap.*` 는 우리가 지은 이름이라 **아무도 자동으로 안 읽는다** — 읽어서 쓰는 코드를 우리가 직접 써야 한다. 1-4 절이 그 얘기다.

### 1-3. `${...}` — 값을 밖에서 주입받기

설정 파일에 비밀번호를 그대로 적을 수는 없다. 그래서 자리만 비워 두고 실행 환경에서 채우게 한다.

```yaml
    jwt:
      # HS256 서명 키. 32바이트 이상(HMAC-SHA256 최소 길이) — 미설정 시 부팅 실패로 조용한 약한 키를 막는다.
      secret: ${JWT_SECRET:}
      # access 는 stateless 라 만료 전 무효화가 불가능하므로 짧게, refresh 는 Redis 폐기가 가능하므로 길게.
      access-ttl: 30m
      refresh-ttl: 14d
```
— `api/src/main/resources/application.yml:57-62`

- **`${JWT_SECRET:}`** — "환경변수 `JWT_SECRET` 값을 넣어라. 없으면 **콜론 뒤의 값**(여기선 빈 문자열)을 써라"는 뜻이다.
- 즉 `${이름:기본값}` 문법이고, `${JWT_SECRET}` 처럼 **콜론이 아예 없으면 기본값이 없다** — 환경변수가 없으면 부팅이 실패한다. `application-dev.yml:3` 의 `url: ${DB_URL}` 이 그 형태로, dev 환경에서 DB 주소를 안 주면 아예 뜨지 않는다. 조용히 이상한 값으로 뜨는 것보다 낫다는 판단이다.
- `access-ttl: 30m` 처럼 **단위가 붙은 문자열**도 그대로 쓴다. 스프링이 `Duration` 타입으로 받아 줄 때 `30m`·`14d`·`5s` 를 알아서 해석한다.

로컬에서는 환경변수를 쉘에 export 하는 대신 루트의 `.env` 파일을 읽게 해 뒀다.

```yaml
  config:
    import: optional:file:.env[.properties]
```
— `api/src/main/resources/application.yml:17-18`

- `optional:` 이 붙어서 **`.env` 가 없어도 조용히 넘어간다**. 배포 환경엔 `.env` 를 두지 않고 OS 환경변수로 주기 때문이다.
- `[.properties]` 는 "확장자는 `.env` 지만 내용은 `properties` 형식(`KEY=value`)으로 읽어라"는 지시다.

### 1-3-1. 설정이 없을 때 — 못 뜨게 할까, 기능만 끌까

같은 "설정 누락"인데 kbap 은 두 가지로 다르게 대응한다. **이건 취향이 아니라 판단이다.**

| | JWT 서명키 | Firebase 자격증명 |
|---|---|---|
| 설정 키 | `kbap.auth.jwt.secret` | `kbap.auth.firebase.credentials-json` |
| 없으면 | **부팅 실패** | **부팅 성공**, 로그인만 401 |
| 코드 | `JwtTokenProperties.kt:10-14` 의 `require` | 아래 |

```kotlin
        val verifier = FirebaseSocialAuth.tokenVerifierOrNull(credentialsJson, credentialsPath)
        if (verifier == null) {
            log.warn("Firebase 자격증명 미설정 — 소셜 로그인 비활성(모든 로그인이 401 로 거절된다)")
            return UnavailableSocialAuth
        }
```
— `api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:30-34`

- 자격증명이 없으면 **"항상 거절하는" 대역 구현(`UnavailableSocialAuth`)을 대신 꽂는다.** 앱은 정상적으로 뜨고 로그인 API 만 401 을 돌려준다.
- 경고 로그를 남기는 게 핵심이다. 조용히 넘어가면 "왜 로그인이 안 되지" 를 며칠 헤맨다.

**갈리는 기준**: 없으면 **위험한 것**(약한 키로 뜨면 보안 사고)은 부팅을 막고, 없으면 **불편할 뿐인 것**(그 기능만 못 씀)은 뜨게 둔다. Firebase 키 없이도 서버가 떠야 다른 API 를 개발할 수 있다. 같은 이유로 `kbap.llm.embedding.enabled`·`kbap.vector.enabled` 는 기본 `false` 라서, 로컬에 벡터 DB 가 없어도 서버가 뜬다.

> [!note] 레포 문서가 낡은 곳
> 레포의 `.env.example` 머리말은 "⚠️ Spring Boot 는 `.env` 를 자동으로 읽지 않는다 — spring-dotenv 의존성/IDE EnvFile/쉘 export 중 하나가 필요"라고 적혀 있다. **지금은 사실이 아니다.** 위 `spring.config.import` 가 들어가면서 별도 의존성 없이 읽힌다. 문서가 코드보다 낡은 경우이니 `.env.example` 말고 `application.yml` 을 믿으면 된다.

### 1-4. 설정값을 타입 있는 객체로 받기 — 프로퍼티 바인딩

`kbap.auth.jwt.secret` 이라는 문자열이 실제로 코드까지 오는 길을 끝까지 따라가 보자. **kbap 에는 이 길이 두 갈래**다.

#### 갈래 ① `@Value` 로 하나씩 받아 데이터 클래스로 묶기 (kbap 의 주류)

```kotlin
@Configuration
class AuthConfig {
    @Bean
    fun authTokenProperties(
        @Value("\${kbap.auth.jwt.secret}") secret: String,
        @Value("\${kbap.auth.jwt.access-ttl}") accessTtl: Duration,
        @Value("\${kbap.auth.jwt.refresh-ttl}") refreshTtl: Duration,
    ): JwtTokenProperties = JwtTokenProperties(secret = secret, accessTtl = accessTtl, refreshTtl = refreshTtl)
```
— `api/src/main/kotlin/com/kbap/api/core/config/AuthConfig.kt:18-23`

- `@Value("\${키}")` 는 **설정에서 그 키 하나를 꺼내 이 파라미터에 넣어라**는 뜻이다. (Kotlin 에서 `\$` 로 이스케이프한 건 문자열 템플릿과 겹치기 때문이지, 스프링 문법이 다른 게 아니다.)
- 받는 타입이 `Duration` 이면 `30m` 이 알아서 `Duration.ofMinutes(30)` 이 된다. **문자열을 우리가 파싱하지 않는다.**
- 이렇게 모은 값을 `JwtTokenProperties` 라는 데이터 클래스 하나로 묶어 반환한다.

그 홀더 클래스가 이것이다.

```kotlin
data class JwtTokenProperties(
    val secret: String,
    val accessTtl: Duration,
    val refreshTtl: Duration,
) {
    init {
        require(secret.toByteArray().size >= MIN_SECRET_BYTES) {
            "kbap.auth.jwt.secret 는 ${MIN_SECRET_BYTES}바이트 이상이어야 합니다"
        }
    }
```
— `api/src/main/kotlin/com/kbap/api/infra/auth/token/JwtTokenProperties.kt:5-14`

- 스프링 애너테이션이 하나도 없는 **평범한 Kotlin data class** 다. 값을 담는 그릇일 뿐이다.
- `init` 블록의 `require` 가 핵심이다. **설정값 검증을 여기서 한 번만 한다** — 서명키가 32바이트 미만이면 이 객체가 만들어지는 순간(= 앱 부팅 순간) 예외가 터진다. 그래서 "약한 키로 조용히 떠서 몇 달 뒤 사고" 가 아니라 **부팅 실패**로 즉시 드러난다.
- 이 검증 위치가 좋은 이유: `JwtTokenProperties` 를 주입받는 쪽(`JwtTokenIssuer`, `JwtTokenParser`, `JwtScanTicketManager`)은 **이미 검증된 값**이라고 가정하고 쓰면 된다. 세 군데에서 각자 길이를 확인할 필요가 없다.

정리하면 값이 오는 길은 이렇다.

```
OS 환경변수 JWT_SECRET (또는 루트 .env)
  → application.yml 의 ${JWT_SECRET:} 자리에 치환
  → kbap.auth.jwt.secret 이라는 설정 키가 됨
  → AuthConfig 의 @Value 가 꺼냄 (+ 길이 검증)
  → JwtTokenProperties 객체
  → 그걸 생성자로 주입받는 JwtTokenIssuer 등이 사용
```

#### 갈래 ② `@ConfigurationProperties` 로 통째로 받기

```kotlin
@ConfigurationProperties("kbap.vector")
data class FoodVectorProperties(
    val enabled: Boolean = false,
    val uri: String = "",
    val database: String = "kbap",
    val collection: String = "foods",
)
```
— `common/src/main/kotlin/com/kbap/common/domain/food/vector/FoodVectorProperties.kt:5-11`

- `@ConfigurationProperties("kbap.vector")` 는 **`kbap.vector` 아래 하위 키를 이름으로 매칭해 통째로 채워라**는 뜻이다. `kbap.vector.enabled` → `enabled`, `kbap.vector.uri` → `uri` … 로 자동으로 붙는다. `@Value` 를 필드 수만큼 쓰지 않아도 된다.
- 하이픈-케이스와 카멜케이스가 자동으로 이어진다 — `kbap.vector.some-key` 는 `someKey` 에 들어간다.
- Kotlin 기본값(`= false`, `= "kbap"`)이 그대로 **설정이 없을 때의 기본값**이 된다.

이 클래스를 실제로 쓰려면 어딘가에서 "이걸 바인딩해서 빈으로 올려라"고 알려 줘야 하는데, 그 한 줄이 `api/src/main/kotlin/com/kbap/api/core/config/FoodVectorConfig.kt:14` 의 `@EnableConfigurationProperties(FoodVectorProperties::class)` 다. **빈이 조립되는 메커니즘 자체는 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]] 소관**이니 여기선 "설정값이 객체가 되는 지점" 까지만 본다.

> [!tip] 실측 — 어느 쪽이 다수인가
> 레포 전체에서 `@ConfigurationProperties` 를 단 클래스는 **딱 2개**(`FoodVectorProperties`, `LlmModelProperties`)뿐이다. `JwtTokenProperties`·`ImageUploadProperties`·`FoodImageProperties` 는 전부 **애너테이션 없는 data class + `@Value` 조립**(`AuthConfig`, `PropertiesConfig`) 방식이다.
> 왜 이렇게 갈렸는지는 코드만 봐선 단정할 수 없지만, `@Value` 쪽은 **서로 다른 설정 구역의 값을 한 객체에 모을 수 있다**는 실이득이 보인다 — `PropertiesConfig.kt:13-26` 의 `FoodImageProperties` 는 `kbap.llm.image.*` 와 `kbap.food-image.*` 와 `kbap.llm.usd-to-krw` 를 한 그릇에 담는다. `@ConfigurationProperties` 는 접두어 하나에 묶이므로 이게 안 된다.

> [!example] 설정값이 실제로 뭘 정하는지 보고 싶다면
> `kbap.upload.allowed-content-types`·`max-bytes`·`upload-ttl`(`application.yml:132-136`) 은 `ImageUploadProperties` 로 묶여 **presigned URL 발급 정책**이 된다 — 어떤 이미지 형식을 허용하고, 몇 바이트까지 받고, 발급된 업로드 URL 이 몇 분 뒤 만료되는지. 그 URL 이 FE 에서 어떻게 쓰이는지는 [[S3 presigned URL과 클라이언트 시크릿]] 에 정리해 뒀다.

## 2. 프로필 — 같은 코드, 다른 값

### 2-1. 프로필이 뭔가

**프로필(profile)** 은 "지금 이 앱이 어느 환경에서 도는가"를 가리키는 이름표다. 이름표가 정해지면 스프링은 `application-{이름표}.yml` 을 추가로 읽어서 기본 `application.yml` 위에 **덮어쓴다**.

FE 로 치면 Expo 의 **채널/빌드 프로필** 과 같은 자리다. `eas.json` 에 development / preview / production 프로필을 두고 빌드할 때 하나를 고르는 것처럼, 백엔드는 실행할 때 하나를 고른다.

```
SPRING_PROFILES_ACTIVE=local ./gradlew :api:bootRun
```

기본값을 안 박아 뒀다는 점이 중요하다.

```yaml
  # 활성 프로필은 런타임에 지정한다 (예: SPRING_PROFILES_ACTIVE=local|dev|staging|prod).
  # 여기서 기본 프로필이나 datasource 를 강제하지 않는다 — 프로필 없이 뜨는 테스트(@SpringBootTest)는
  # test resources 의 application.yml 오버라이드 + MySQL Testcontainers(@ServiceConnection)로 동작한다.
```
— `api/src/main/resources/application.yml:27-29`

- 기본 프로필이 없으니 **아무 프로필도 안 주면 datasource 가 없어서 못 뜬다.** 실수로 로컬 설정을 안고 운영에 뜨는 사고를 원천 차단한다.
- 예외는 테스트다. 테스트는 프로필 없이 뜨고, `src/test/resources/application.yml` 과 Testcontainers 가 DB 를 대신 공급한다.

### 2-2. 실측 — 프로필 4종, 파일은 10개

프로필 이름은 **`local` · `dev` · `staging` · `prod` 4종**이고, **api 와 batch 가 각자 자기 파일을 갖는다.**

| 프로필 | api 파일 | batch 파일 | api 쪽에서 갈리는 것 |
|---|---|---|---|
| `local` | `application-local.yml` (21줄) | `application-local.yml` (11줄) | DB·Redis 주소에 **localhost 기본값**, `show-sql: true`, Thymeleaf 캐시 off |
| `dev` | `application-dev.yml` (25줄) | `application-dev.yml` (10줄) | 주소 전부 환경변수 **필수**, Redis TLS 기본 on, S3 키 접두 `dev` |
| `staging` | `application-staging.yml` (32줄) | `application-staging.yml` (10줄) | dev 와 거의 같고 + **로그를 JSON(ECS)으로** 출력, `show-sql: false` |
| `prod` | `application-prod.yml` (32줄) | `application-prod.yml` (10줄) | staging 과 동일 구성 + S3 키 접두 `prod` |

여기에 프로필 없는 테스트용 `application.yml` 이 api·batch 각각 1개씩. **총 10개 파일**이다.

두 앱의 프로필 파일을 비교하면 성격 차이가 바로 보인다.

```yaml
spring:
  …
  # 로컬은 환경변수로 덮어쓸 수 있게 하되, 없으면 localhost 기본값으로 바로 뜬다.
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/kbap}
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:root}
```
— `api/src/main/resources/application-local.yml:1,5-9`

- `local` 만 유일하게 **기본값이 있는 `${DB_URL:...}`** 을 쓴다. 레포를 클론해서 `SPRING_PROFILES_ACTIVE=local` 만 주면 별도 설정 없이 뜨게 하려는 배려다.
- `dev`/`staging`/`prod` 는 전부 `${DB_URL}`(기본값 없음)이라 배포 환경이 값을 안 주면 부팅에 실패한다.

batch 쪽 4개 파일은 **datasource 4줄 + JPA 3줄이 전부**다. 로깅·스토리지·Redis 가 없다 — 배치 앱은 HTTP 로 사용자를 받지 않고 S3·Redis 도 안 쓰기 때문이다.

### 2-3. api 와 batch 는 서로 다른 `application.yml` 을 갖는다

kbap-server 는 실행 파일(bootJar)이 **두 개**다. `:api`(웹 서버)와 `:batch`(배치 앱)는 별개의 프로세스로 뜨고, **설정 파일도 각자 자기 모듈 안에 따로** 있다. 공유하지 않는다.

| | `:api` | `:batch` |
|---|---|---|
| `application.yml` 크기 | 136줄 | 74줄 |
| 서버 포트 | 톰캣 기본(설정 없음) | `server.port: 8080` (도커 네트워크 내부 전용) |
| Redis·S3·Firebase 설정 | 있음 | 없음 |
| **Flyway** | **있음 — 스키마 owner** | **없음** |

마지막 줄이 이 절의 핵심이다. **DB 스키마를 만들고 바꾸는 권한은 api 한쪽만 갖는다.** 두 앱이 동시에 스키마를 건드리면 서로 충돌하기 때문이다.

그런데 "batch 는 flyway off" 라는 표현(`CLAUDE.md:31`)이 **설정으로 껐다는 뜻은 아니다.** 실측하면 그런 프로퍼티는 없고, 애초에 **Flyway 라이브러리가 batch 의 의존성 목록에 없다.**

```kotlin
dependencies {
    "implementation"(project(":common"))

    "implementation"(platform(libs.aws.bom))
    "implementation"(libs.aws.sqs)

    "implementation"("org.springframework.boot:spring-boot-starter-batch")
    "implementation"(libs.spring.boot.starter.web)
```
— `batch/build.gradle.kts:5-13`

- Flyway 가 없다. 반면 `api/build.gradle.kts:31-33` 에는 `spring-boot-flyway`·`flyway-core`·`flyway-mysql` 세 줄이 있다.
- 스프링 부트의 자동구성은 **클래스패스에 그 라이브러리가 있을 때만 동작**한다. 라이브러리가 없으면 끄고 말 것도 없다 — 이게 "off" 의 실제 정체다.
- 결과적으로 batch 는 **api 가 이미 만들어 둔 스키마에 얹혀서** 뜬다. Spring Batch 자신의 메타데이터 테이블(`BATCH_*`)조차 api 의 마이그레이션이 만든다.

마이그레이션이 정확히 뭐고 왜 순서가 중요한지는 나중에 나오는 **10번 노트(Flyway 마이그레이션 — 스키마를 코드로 관리하기)** 에서 따로 다룬다.

## 3. 트랜잭션 경계 — 전부 되거나 전부 안 되거나

### 3-1. 핵심 개념

| 구분 | 트랜잭션 없음 | 트랜잭션 있음 |
|---|---|---|
| 정체 | DB 명령 한 줄 한 줄이 즉시 확정 | **여러 줄을 한 덩어리로 묶어** 전부 확정하거나 전부 취소 |
| 중간에 예외가 나면 | 앞줄은 이미 반영됨 → **반쪽만 바뀐 데이터** | 앞줄까지 **되돌림(롤백)** → 아무 일도 없던 상태 |
| 끝나는 방식 | 매 줄마다 | 메서드가 정상 종료 → **커밋** / 예외로 종료 → **롤백** |
| 선언 위치 | — | 메서드에 `@Transactional` 한 줄 |

### 3-2. 비유 — 4인 연석 예매

영화관에서 **연속된 4자리**를 잡는 상황을 떠올려 보자.

- 좌석 선택 화면에 들어가는 순간 = **트랜잭션 시작**. 4자리가 잠시 내 앞으로 잡혀 있다.
- "결제 완료" 를 누르는 순간 = **커밋**. 이제 4자리가 확정으로 내 것이 된다.
- 결제 도중에 카드가 거절되거나 내가 창을 닫으면 = **롤백**. 잡아 뒀던 **4자리가 전부 풀린다.**

여기서 절대 일어나면 안 되는 일이 **"3자리는 잡히고 1자리는 실패한 채로 결제가 끝나는 것"** 이다. 트랜잭션이 막는 게 정확히 이거다. 4자리를 하나씩 확정했다면 3번째에서 실패했을 때 이미 2자리는 팔려 버린 상태가 된다.

> [!warning] 비유의 경계 — 여기서부터는 다르다
> **① 밖으로 나간 것은 안 돌아온다.** 예매가 취소돼도 이미 발송된 "예매 확인" 문자는 회수되지 않는다. 트랜잭션도 똑같아서 **DB 밖에서 벌어진 일은 롤백이 되돌려 주지 않는다** — S3 에 올린 파일, 큐에 발행한 메시지, 남에게 보낸 HTTP 요청은 그대로 남는다. kbap 이 "외부 시스템 호출은 트랜잭션 밖"이라는 규약(`CLAUDE.md:121`)을 둔 이유가 이것이다. 탈퇴 처리에서 소셜 계정 삭제를 트랜잭션 **앞에서** 먼저 하는 것도 같은 맥락이다.
> **② "잡아 둔다"의 범위가 다르다.** 예매는 내가 고른 4자리만 잠기지만, DB 트랜잭션이 무엇을 얼마나 잠그는지는 DB 엔진이 정한다. kbap 은 여기에 손대지 않는다(3-4 절).
> **③ 시간 감각이 다르다.** 예매는 몇 분씩 붙잡고 있어도 되지만, DB 트랜잭션은 **짧을수록 좋다** — 길게 열어 두면 그 시간만큼 다른 요청이 기다린다. "외부 호출은 트랜잭션 밖"이 규약인 두 번째 이유이기도 하다(LLM 호출 몇 초 동안 트랜잭션을 붙잡고 있으면 안 된다).

### 3-3. kbap 의 실제 모습 — 쓰기

```kotlin
    @Transactional
    fun completeOnboarding(input: MemberProfileInput) {
        getMember(input.memberId).completeOnboarding(
            nickname = input.nickname ?: OnboardingProfileDefaults.randomNickname(),
            avoidanceSubstanceCodes = input.avoidanceSubstanceCodes,
            dietCategories = input.dietCategories,
            spicinessPreference = input.spicinessPreference,
            countryCode = input.countryCode,
            profileImageUrl = input.profileImageUrl ?: OnboardingProfileDefaults.randomProfileImagePath(),
        )
    }
```
— `api/src/main/kotlin/com/kbap/api/member/MemberService.kt:22-32`

FE 개발자가 이 코드를 처음 보면 **거의 100% 같은 데서 멈춘다: "저장하는 코드가 어디 있지?"**

- `getMember(...)` 로 회원을 읽어 왔고, 읽어 온 객체의 `completeOnboarding(...)` 을 불러 필드를 바꿨다. **그게 전부다.** `save()` 도 `update()` 도 없다.
- 그런데 DB 에는 반영된다. 트랜잭션 안에서 읽어 온 엔티티는 스프링/JPA 가 **계속 지켜보고 있다가**, 트랜잭션이 닫히는 순간(= 메서드가 정상 종료되는 순간) **바뀐 필드를 찾아내 UPDATE 문을 만들어 밀어낸다.**
- `CLAUDE.md:121` 이 "상태 변경은 관리 엔티티 dirty checking(불필요한 `save()` 호출 금지)"이라고 못 박은 게 이 얘기다. **`save()` 를 부르는 게 오히려 규약 위반**이다.

**"지켜보고 있다"의 정체와 정확히 언제 무엇을 밀어내는지**(flush 와 commit 이 어떻게 다른지)는 나중에 나오는 **8번 노트(영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델)** 의 주제다. 여기서는 **"트랜잭션이 닫힐 때 변경분이 DB 로 밀려 나간다"** 까지만 알면 이 노트를 읽는 데 충분하다.

### 3-4. `readOnly = true` — 읽기라고 미리 말해 주기

```kotlin
    @Transactional(readOnly = true)
    fun getMyProfile(memberId: Long): MyProfileResult {
        val member = getMember(memberId)
        return MyProfileResult.of(
            member = member,
            ranking = MemberRankingResult.from(member.ranking),
            profileImageUrl = ImageUrls.resolve(imagePublicBaseUrl, member.profile.profileImageUrl),
        )
    }
```
— `api/src/main/kotlin/com/kbap/api/member/MemberService.kt:47-55`

`readOnly = true` 는 **"이 안에서는 아무것도 안 바꾼다"는 선언**이고, 두 가지가 따라온다.

1. **성능** — 안 바꿀 거라고 미리 알려 주면 JPA 가 3-3 절의 "지켜보기" 준비를 생략한다. 읽어 온 엔티티의 원본 사본을 떠 두고 나중에 비교하는 작업 자체가 없어진다. 조회가 많을수록 이득이 커진다.
2. **의도의 문서화** — 메서드 시그니처를 보기 전에 애너테이션만 봐도 "이건 조회구나" 를 안다. 실수로 쓰기 코드를 넣으면 드러난다.

> [!note] 여러 조회를 한 스냅샷으로 묶는다는 것
> `getMyProfile` 은 회원 정보와 랭킹을 함께 읽는다. `readOnly` 트랜잭션으로 묶어 두면 이 둘이 **같은 시점의 데이터**임이 보장된다 — 회원 정보를 읽은 직후 남이 랭킹을 바꿔도 이 요청의 응답은 흔들리지 않는다. `CLAUDE.md:121` 의 "여러 조회를 한 스냅샷으로 묶을 때만 선언" 이 이 얘기다.

**실측 규모**: 레포 프로덕션 코드의 `@Transactional` 은 **86개**, 그중 **48개가 `readOnly = true`** 다. 절반 이상이 조회다.

### 3-5. kbap 의 규약 두 줄 (`CLAUDE.md:121-122`)

| 규약 | 내용 | 왜 |
|---|---|---|
| **public 메서드에 명시** | DB 를 만지는 서비스 **public 메서드는 전부** `@Transactional` 을 직접 단다. 리포지토리에 딸린 기본 트랜잭션에 **암묵적으로 기대지 않는다** | 경계가 코드에 눈으로 보인다. "이 메서드는 어디서 시작해 어디서 끝나는가"를 애너테이션 한 줄로 읽을 수 있다 |
| **격리수준은 손대지 않는다** | `@Transactional(isolation = ...)` 을 **쓰지 않는다.** DB 기본값(MySQL 의 REPEATABLE READ)을 그대로 쓴다 | 격리수준을 올려 동시성 문제를 푸는 건 부작용이 크고 재현이 어렵다. kbap 은 대신 **원자적 UPDATE·unique 제약** 같은 최소 수단으로 치명적인 경합만 막는다 |

두 번째 규약의 실물은 나중에 나오는 **23번 노트(회원 랭킹)** 에서 본다. `MemberService.kt:90-94` 의 `increaseScanCount` 가 조회 후 +1 후 저장이 아니라 **UPDATE 한 방**으로 카운트를 올리는 게 그 최소 수단이다.

> [!info] 규약에도 예외는 있다
> `MemberService.kt:77` 의 `findOrSignUp` 은 DB 를 만지는 public 메서드인데 `@Transactional` 이 **없다.** 가입 시 unique 제약 위반이 나면 그걸 잡아 재조회하는 폴백이 있는데, 제약 위반이 터진 순간 트랜잭션이 이미 무효화돼서 그 안에서는 재조회를 할 수 없기 때문이다. `CLAUDE.md:121` 이 "예외는 사유 명시" 라고 둔 자리다. **규약을 어기는 코드를 보면 먼저 이유를 찾아보라**는 신호이기도 하다.

## 4. 가장 자주 데이는 함정 — 같은 클래스 안에서 부르면 안 걸린다

`@Transactional` 이 동작하는 원리를 한 줄로 말하면 이렇다. 스프링은 `MemberService` 를 그대로 주지 않고 **똑같이 생긴 대역(프록시)** 을 만들어 대신 꽂아 준다. 밖에서 `memberService.completeOnboarding(...)` 을 부르면 실제로는 대역이 먼저 받아서 **"트랜잭션 열기 → 진짜 메서드 실행 → 커밋(또는 롤백)"** 을 해 준다.

여기서 함정이 나온다.

```
컨트롤러 → [프록시] → MemberService.completeOnboarding   ← 트랜잭션 걸림 ✅
                          └─ this.getMember(...)          ← 프록시를 안 거침 ❌
```

**같은 객체 안에서 자기 자신의 다른 메서드를 부르면 프록시를 거치지 않는다.** 대역은 바깥 문 앞에 서 있는 문지기라서, 이미 안에 들어온 사람이 옆방으로 이동하는 건 못 본다. 스프링 공식 문서도 이렇게 못 박는다.

> In proxy mode (which is the default), only external method calls coming in through the proxy are intercepted. This means that self-invocation ... does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional`.

**kbap 코드에 실제로 이 상황이 있다.**

```kotlin
    @Transactional(readOnly = true)
    fun getMember(memberId: Long): Member =
        getMemberOrNull(memberId) ?: throw BusinessException(ErrorCode.MEMBER_NOT_FOUND)
```
— `api/src/main/kotlin/com/kbap/api/member/MemberService.kt:130-132`

`getMember` 는 `readOnly = true` 다. 그런데 3-3 절의 `completeOnboarding`(쓰기 트랜잭션)이 **자기 안에서 `getMember` 를 부른다.** 만약 이 내부 호출에 `readOnly = true` 가 적용됐다면 읽어 온 엔티티를 바꿔도 저장이 안 됐을 것이다.

실제로는 **적용되지 않는다.** 내부 호출이라 프록시를 안 거치고, 그래서 `getMember` 의 애너테이션은 아예 읽히지도 않는다. 바깥의 쓰기 트랜잭션이 그대로 이어지고 온보딩 저장은 정상 동작한다. 결과적으로 잘 돌아가지만, **"애너테이션이 붙어 있으니 적용됐겠지"라는 가정 위에 서 있으면 언젠가 반대 방향으로 데인다.**

### 데이는 전형적인 시나리오

FE 개발자가 백엔드에서 가장 흔히 겪는 형태는 이것이다.

```kotlin
// 예시 — kbap 코드 아님
@Service
class SomeService(private val repo: SomeJpaRepository) {
    fun doWork(id: Long) {
        saveIt(id)
    }

    @Transactional
    fun saveIt(id: Long) {
        repo.findById(id).get().change("new")
    }
}
```

- `doWork` 에는 `@Transactional` 이 없고 `saveIt` 에만 있다.
- 밖에서 `doWork` 를 부르면 → 프록시는 `doWork` 만 본다 → `doWork` 에 애너테이션이 없으니 트랜잭션을 안 연다 → `doWork` 안에서 `saveIt` 을 부르는 건 내부 호출이라 프록시를 안 거친다 → **트랜잭션이 아예 없다** → dirty checking 이 안 일어나 **변경이 조용히 사라진다.**
- 예외도 안 나고 로그도 안 남는다. "왜 저장이 안 되지" 로 몇 시간이 날아가는 대표적인 경로다.

**대응**: 트랜잭션이 필요한 경계는 **밖에서 호출되는 진입 메서드**에 단다. 그래서 kbap 규약이 "DB 를 만지는 서비스 **public 메서드**는 전부 명시" 인 것이다 — public 이 곧 "밖에서 들어오는 문" 이고, 문에 걸어야 문지기가 일한다.

> [!tip] 곁가지로 알아 둘 것
> 같은 프록시 원리 때문에 **`private` 메서드에 `@Transactional` 을 달면 아무 일도 안 일어난다.** 스프링 6.0 부터 `protected`·패키지 가시성 메서드까지는 클래스 기반 프록시에서 동작하지만, kbap 규약이 public 으로 못 박아 뒀으니 여기 기댈 일은 없다.

## 5. 배치의 트랜잭션은 방식이 다르다

> [!important] 배치는 경계를 애너테이션이 아니라 **코드로 직접 소유한다**
> `:batch` 는 `TransactionTemplate` 을 써서 "여기부터 여기까지" 를 **코드 블록으로** 감싼다(`CLAUDE.md:31`). 배치는 수만 건을 도는 루프라서 "메서드 하나 = 트랜잭션 하나" 로는 경계가 너무 커지기 때문이다.

```kotlin
            transactionTemplate.executeWithoutResult {
                if (result.succeededOutboxIds.isNotEmpty()) {
                    outboxRepository.recordPublishSucceeded(result.succeededOutboxIds)
                }
                if (result.failedOutboxIds.isNotEmpty()) {
                    outboxRepository.recordPublishFailed(result.failedOutboxIds)
                }
            }
```
— `batch/src/main/kotlin/com/kbap/batch/outbox/FoodContentOutboxPublisher.kt:45-52`

- `transactionTemplate.execute { ... }` / `executeWithoutResult { ... }` 안이 트랜잭션 구간이다. **중괄호가 곧 경계**라서 `@Transactional` 보다 눈에 더 잘 보인다.
- `publishAll()` 은 페이지 단위 루프인데, **한 페이지마다 트랜잭션이 두 번 열렸다 닫힌다** — 조회용 한 번(28-30줄), 결과 기록용 한 번(45-52줄). 그 **사이**에 있는 `eventPublisher.publish(...)`(외부 큐 발행)는 트랜잭션 **밖**이다. 3-2 절 비유의 경계 ①·③ 을 코드로 지킨 모습이다.
- 이 방식이면 100페이지를 돌다 50페이지에서 죽어도 앞의 49페이지 기록은 이미 커밋돼 살아 있다. 전체를 한 트랜잭션으로 묶었다면 전부 날아갔을 것이다.

배치 앱이 잡을 어떻게 정의하고 기동하는지 전체 그림은 나중에 나오는 **26번 노트(배치 앱의 골격 — Spring Batch 잡·트리거·스케줄)** 에서 다룬다.

참고로 api 쪽에도 `TransactionTemplate` 을 쓰는 곳이 두 군데 있다(`FoodImageBatchSubmitService`·`FoodImageBatchCollectService`). 둘 다 외부 LLM 호출을 사이에 끼고 앞뒤로 짧게 커밋해야 하는, 배치와 같은 성격의 코드다.

## 6. 치트시트

**설정 문법**

```yaml
key: ${ENV_NAME:기본값}     # 환경변수 없으면 기본값
key: ${ENV_NAME}           # 환경변수 없으면 부팅 실패
ttl: 30m                   # Duration 으로 받으면 자동 해석 (s/m/h/d)
```

**프로필**

```bash
SPRING_PROFILES_ACTIVE=local ./gradlew :api:bootRun     # local 프로필로 api
SPRING_PROFILES_ACTIVE=local ./gradlew :batch:bootRun   # local 프로필로 batch
# 프로필을 안 주면? datasource 가 없어서 못 뜬다 (테스트 제외)
```

읽히는 순서 — **뒤가 앞을 덮어쓴다**:
`application.yml` → `application-{프로필}.yml` → OS 환경변수 → 커맨드라인 인자

```bash
./gradlew :batch:bootRun --args='--kbap.batch.food-content-outbox.page-size=200'
```

**설정값 받는 두 방법**

```kotlin
// 하나씩 — @Configuration 안에서
@Value("\${kbap.auth.jwt.secret}") secret: String

// 통째로 — 접두어 아래 전부
@ConfigurationProperties("kbap.vector")
data class FooProperties(val enabled: Boolean = false, ...)
```

**트랜잭션**

```kotlin
@Transactional                      // 쓰기. 정상 종료 → 커밋, 예외 → 롤백
@Transactional(readOnly = true)     // 조회 전용. 변경 감지 준비를 생략
// isolation 은 지정하지 않는다 (kbap 규약)
```

**함정 체크 3줄**

```
1. public 메서드에 달았나?          (private 은 무시된다)
2. 밖에서 직접 부르는 메서드인가?    (자기 클래스 내부 호출은 프록시를 안 거친다)
3. 외부 시스템 호출이 안에 있나?     (롤백돼도 안 돌아온다 → 트랜잭션 밖으로 빼라)
```

## 7. 용어집

- **프로퍼티(property)**: 설정 키-값 한 쌍. `kbap.auth.jwt.secret = abc...` 같은 것.
- **프로필(profile)**: 환경 이름표. 이름표에 맞는 `application-{이름표}.yml` 이 기본 설정 위에 덮어씌워진다. kbap 은 `local`·`dev`·`staging`·`prod` 4종.
- **바인딩(binding)**: `yml` 의 문자열을 타입이 있는 Kotlin 객체 필드에 채워 넣는 것. `"30m"` → `Duration` 변환도 포함.
- **홀더 클래스**: 설정값만 담는 data class. kbap 에선 `JwtTokenProperties`·`ImageUploadProperties`·`FoodVectorProperties` 등.
- **트랜잭션(transaction)**: 전부 반영되거나 전부 취소되는 DB 작업 한 덩어리.
- **커밋(commit)**: 트랜잭션 안의 변경을 확정하는 것. `@Transactional` 메서드가 정상 종료될 때 자동으로 일어난다.
- **롤백(rollback)**: 트랜잭션 안의 변경을 전부 되돌리는 것. 메서드에서 예외가 밖으로 나갈 때 자동으로 일어난다.
- **dirty checking(변경 감지)**: 트랜잭션 안에서 읽어 온 엔티티의 필드가 바뀌었는지 JPA 가 알아서 찾아내 UPDATE 를 만들어 주는 것. `save()` 를 부를 필요가 없어진다.
- **프록시(proxy)**: 스프링이 원본 객체 대신 만들어 꽂아 주는 대역 객체. `@Transactional` 같은 애너테이션은 이 대역이 처리한다.
- **self-invocation(자기 호출)**: 같은 객체 안에서 자기 메서드를 부르는 것. 프록시를 안 거쳐서 애너테이션이 적용되지 않는다.
- **격리수준(isolation level)**: 동시에 도는 트랜잭션들이 서로를 얼마나 볼 수 있는지의 단계. kbap 은 **손대지 않고 DB 기본값**을 쓴다.

## 8. 다음에 빠른 재현 체크리스트

1. **설정값 하나를 추적할 때**: `grep` 으로 그 키를 `application*.yml` 에서 찾고 → `@Value("\${그 키}")` 또는 `@ConfigurationProperties("그 접두어")` 를 찾으면 받는 코드가 나온다.
2. **로컬에서 안 뜰 때**: 프로필을 줬는지 먼저 본다(`SPRING_PROFILES_ACTIVE`). 그다음 `${...}` 중 **기본값 없는 것**이 비어 있는지 본다.
3. **"저장이 안 돼요" 를 만나면**: ① 메서드에 `@Transactional` 이 있나 → ② 그 메서드를 **밖에서 직접** 부르나, 같은 클래스 안에서 부르나 → ③ `readOnly = true` 가 잘못 붙어 있진 않나.
4. **새 서비스 메서드를 쓸 때**: DB 를 만지면 public 에 `@Transactional`(조회면 `readOnly = true`)을 **반드시 명시**한다. `isolation` 은 건드리지 않는다.
5. **외부 시스템(S3·SQS·LLM·소셜 API)을 부를 일이 생기면**: 트랜잭션 **밖**으로 뺀다. 롤백이 되돌려 주지 않고, 그 시간만큼 트랜잭션이 길어진다.

> 이 노트 5절이 "외부 시스템 호출은 트랜잭션 밖" 이라고만 적어둔 자리에, 그 규칙 때문에 `@Transactional` 을 **일부러 안 쓴** 코드가 있다 → [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §7. 배치 발행 잡은 `TransactionTemplate` 로 "읽기 트랜잭션 → (밖에서) SQS 발행 → 쓰기 트랜잭션" 세 토막을 손으로 자르고, 테스트가 발행 시점에 `isActualTransactionActive() shouldBe false` 를 단언한다. 애너테이션은 **경계를 메서드 하나로 고정**하기 때문에 이 구조를 못 만든다.
> 배치가 왜 그렇게 잘게 끊어야 하는지(수만 건 루프 = 한 트랜잭션이면 끝에서 죽을 때 전부 롤백)는 [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] §9. 다만 두 배치 잡의 스타일이 실제로 갈려 있다 — 벡터 잡은 반대로 청크 트랜잭션 **안에서** 외부 호출을 한다([[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]] §7-3, 헌법 제약과 어긋나는 자리로 콜아웃돼 있다).
> 이 노트 6절의 `${...}` 기본값 이야기도 배치에서 한 번 더 쓰인다 — `kbap.vector.enabled`·`kbap.llm.embedding.enabled` 가 기본 `false` 라 잡 빈 자체가 안 만들어진다([[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]] §8).
