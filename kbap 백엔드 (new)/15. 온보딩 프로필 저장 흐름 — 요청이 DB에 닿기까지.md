# 15. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지

> 작성: 2026-08-27 · 맥락: 4~14번은 전부 **개념**이었다. 계층이 뭔지, 트랜잭션이 뭔지, 엔티티가 뭔지 따로따로 배웠다. 이 노트부터는 그 개념들이 **한 요청 안에서 실제로 어디에 나타나는지**를 본다. 온보딩은 kbap에서 가장 얇은 세로 슬라이스라 첫 흐름으로 골랐다 — 외부 API도, 큐도, 배치도 끼지 않고 요청 하나가 곧장 DB까지 간다.
> 목표: `POST /api/members/me/onboarding` 을 한 번 부르면 어느 파일이 어떤 순서로 실행되는지 짚을 수 있게 되고, **`save()` 를 부르는 코드가 어디에도 없는데 왜 저장되는지** 설명할 수 있게 되기.

---

## 0. 한 줄 요약

온보딩 요청은 **필터 → 컨트롤러 → 서비스 → 엔티티 → (커밋) → UPDATE** 순으로 흐르는데, 이 흐름에서 실제로 "저장하라"고 명령하는 코드는 **한 줄도 없다.** 서비스가 연 트랜잭션이 끝나는 순간 하이버네이트가 바뀐 필드를 스스로 알아채고 `UPDATE member SET ...` 을 날린다.

---

## 1. 이 API가 하는 일 — 사용자 관점 한 줄

**소셜 로그인만 끝낸 회원이 온보딩 화면에서 고른 값(닉네임·기피 성분·diet·국가·프로필 사진·맵기)을 제출하면, 그게 프로필로 저장되고 다음부터는 온보딩 화면을 건너뛴다.**

한 번뿐인 관문이다. 이미 완료한 회원이 다시 부르면 `400 MEMBER-002` 로 거절된다 — 값 수정은 별도 API(`PATCH /api/members/me/profile`)의 몫이다.

## 3. 한 단계씩 따라가기

### 3-1. 여기 도착했을 때는 이미 `memberId` 가 정해져 있다

컨트롤러 메서드의 첫 인자를 보자.

```kotlin
@PostMapping("/me/onboarding", version = "1.0")
override fun completeOnboarding(
    @AuthMemberId memberId: Long,
    @RequestBody request: OnboardingRequest,
): ResponseEntity<BaseResponse<Unit>> {
```
— `api/src/main/kotlin/com/kbap/api/member/MemberController.kt:19-23`

`@AuthMemberId` 는 스프링이 아는 애너테이션이 아니다. kbap이 직접 만든 것이고(`api/core/auth/AuthMemberId.kt`), 컨트롤러에 값이 도착하기까지 **이미 두 단계를 거쳤다.**

1. `JwtAuthenticationFilter` 가 컨트롤러 도달 **전에** 토큰을 검증하고 결과를 요청 속성에 꽂는다(`:35-36`). 온보딩 경로가 그 필터를 타는 근거는 `WebConfig.kt:81` 의 `${ApiPaths.API}/members/*` 패턴이다.
2. `AuthMemberIdArgumentResolver` 가 그 속성을 꺼내 파라미터에 넣는다(`:24-27`). 값이 없으면 `INVALID_ACCESS_TOKEN`, 역할이 `ADMIN` 이면 회원 API를 못 쓰게 잘라낸다.

**이 노트에서 알아야 할 건 결론 한 줄이다 — 컨트롤러에 도착한 시점에는 `memberId` 가 이미 꽂혀 있다.** 필터가 토큰을 어떻게 뜯는지, 만료되면 어떻게 재발급하는지, 게스트는 어떻게 예외 처리하는지, 필터·인터셉터·리졸버의 실행 순서는 전부 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] 이 정본이다.

FE로 옮기면 이렇다 — RN 앱에서 `useAuth()` 훅이 저장된 토큰을 파싱해 `user.id` 를 화면에 내려주는 것과 역할이 같다. 화면 컴포넌트는 토큰을 몰라도 되고, 컨트롤러도 토큰을 모른다. **다른 점**: 훅은 컴포넌트가 직접 부르지만, `@AuthMemberId` 는 컴포넌트(컨트롤러)가 부르는 게 아니라 **프레임워크가 호출 직전에 넣어 준다.**

### 3-2. 같은 경로에 핸들러가 두 개 — 헤더가 가른다

`MemberController` 에는 `POST /api/members/me/onboarding` 이 **두 번** 등장한다.

```kotlin
@PostMapping("/me/onboarding", version = "1.0")
override fun completeOnboarding(...)  { memberService.completeOnboarding(request.toInput(memberId, serverAssignsProfile = false)) ... }

@PostMapping("/me/onboarding", version = "1.1+")
override fun completeOnboardingWithServerProfile(...) { memberService.completeOnboarding(request.toInput(memberId, serverAssignsProfile = true)) ... }
```
— `api/src/main/kotlin/com/kbap/api/member/MemberController.kt:19-35` (발췌·축약)

경로도 같고 HTTP 메서드도 같다. 다른 건 `version` 하나다.

| `X-API-Version` | 타는 핸들러 | 계약 |
|---|---|---|
| `1.0` | `completeOnboarding` | 닉네임·프로필 사진을 **클라이언트가 보내야 한다**(누락 시 400 COMMON-002) |
| `1.1` 이상 | `completeOnboardingWithServerProfile` | 닉네임·사진을 **서버가 랜덤 지정**한다. 보내도 무시 |
| 없음 | — | 400. 이 경로는 버전 헤더가 필수다 |
| `9.9`·`beta` | — | 400. 지원 목록에 없거나 형식이 틀렸다 |

"없으면 400"의 근거는 `WebConfig.kt:26-38` 이다. `setVersionRequired(true)` 이고, 예외 리졸버가 기본값 `1.0` 을 돌려주는 건 `/api/` 로 시작하지 **않는** 경로와 `/api/app-version` 뿐이라, `/api/members/...` 는 헤더 없이 통과할 방법이 없다.

이 라우팅 방식이 왜 URL 버저닝(`/api/v2/...`)보다 나은지, 봉투와 에러 코드는 어떤 규칙인지는 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 에 있다. 여기서는 **그 규칙이 실제로 쓰이는 첫 자리**를 본 것이다.

### 3-3. 요청 타입이 세 개인 이유

`api/member/` 안에는 비슷하게 생긴 data class가 여럿 있다. 헷갈리기 쉬워 정리해 둔다.

| 클래스 | 어디서 쓰나 | 특징 |
|---|---|---|
| `OnboardingRequest` | 온보딩 1.0·1.1 **둘 다** | `countryCode`·`spicinessPreference` 가 **비-null 필수**. 나머지는 nullable |
| `ProfileUpdateRequest` | `PATCH /me/profile` (버전 무관 기본) | **전 필드 nullable** — 안 보낸 필드는 유지 |
| `ProfileUpdateNoCountryRequest` | `PATCH /me/profile` (1.1 이상) | 위와 같지만 **`countryCode` 필드 자체가 없다** |
| `MemberProfileInput` / `ProfileUpdateInput` | 서비스에 넘기는 값 | 위 셋이 `toInput()` 으로 변환된 결과. `memberId` 가 붙는다 |

버전이 두 개인데 요청 타입은 하나(`OnboardingRequest`)라는 게 포인트다. 갈림길은 컨트롤러가 넘기는 **불리언 하나**다.

```kotlin
fun toInput(memberId: Long, serverAssignsProfile: Boolean): MemberProfileInput =
    MemberProfileInput(
        memberId = memberId,
        nickname = if (serverAssignsProfile) null else requireField(nickname),
        ...
        profileImageUrl = if (serverAssignsProfile) null else requireField(profileImageUrl),
    )

private fun requireField(value: String?): String =
    value ?: throw BusinessException(ErrorCode.INVALID_REQUEST)
```
— `api/src/main/kotlin/com/kbap/api/member/OnboardingRequest.kt:14-26`

- `serverAssignsProfile = true`(1.1 경로) → 닉네임·사진을 **`null` 로 만들어 넘긴다.** 클라가 보낸 값이 있어도 버린다.
- `serverAssignsProfile = false`(1.0 경로) → `requireField` 가 `null` 을 잡아 `COMMON-002` 로 거절한다.
- 즉 `MemberProfileInput` 에서 **`null` 은 "값 없음"이 아니라 "서버가 정하라"는 신호**다. 이 뜻을 받는 쪽은 3-4절에서 본다.

FE 대응: API 응답 타입(`OnboardingRequest`)과 화면/도메인이 쓰는 타입(`MemberProfileInput`)을 분리하는 것 — 이미 하고 있는 패턴이다. **다른 점**: FE는 주로 응답을 변환하지만, 여기서는 **들어오는 요청**을 변환한다. 방향이 반대다.

> [!warning] 코드 주석이 낡았다
> `MemberProfileInput.kt:5` 의 주석은 서버 자동 지정 경로를 `X-API-Version >= 2026.08.07` 이라고 적어 뒀는데, 실제 매핑은 `version = "1.1+"` 이다(`MemberController.kt:28`). 날짜 버전에서 `1.x` 로 바뀐 흔적이 주석에만 남았다. 참고로 kbap은 **Kotlin 소스 주석 금지**가 규약인데(→ [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]) 이 파일에는 예외적으로 주석이 하나 있고, 그 하나가 이렇게 낡았다. 규약의 이유를 보여 주는 표본이다.

### 3-4. 서비스 — 트랜잭션이 열리는 자리

```kotlin
@Transactional
fun completeOnboarding(input: MemberProfileInput) {
    getMember(input.memberId).completeOnboarding(
        nickname = input.nickname ?: OnboardingProfileDefaults.randomNickname(),
        avoidanceSubstanceCodes = input.avoidanceSubstanceCodes,
        dietCategories = input.dietCategories,
        spicinessPreference = input.spicinessPreference,
        countryCode = input.countryCode,
        profileImageUrl = input.profileImageUrl ?: OnboardingProfileDefaults.randomProfileImagePath(),
    )
}
```
— `api/src/main/kotlin/com/kbap/api/member/MemberService.kt:22-32`

`MemberService` 는 `MemberJpaRepository` 를 `new` 로 만들지 않는다 — 생성자 파라미터로 받을 뿐이고(`MemberService.kt:18-21`), 채워 넣는 건 스프링 컨테이너다([[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]). 그래서 테스트에서 이 클래스만 떼어내 다른 리포지토리를 꽂는 것도 가능하다.

여기서 일어나는 일은 딱 세 가지다.

1. **트랜잭션을 연다.** `@Transactional` 이 붙은 이 메서드가 kbap의 트랜잭션 경계다. 이 메서드가 정상 종료하면 커밋, 예외가 나가면 롤백이다.
2. **`null` 을 기본값으로 채운다.** 3-3절에서 만든 "서버가 정하라" 신호가 여기서 소비된다 — `?:` 오른쪽의 `randomNickname()`·`randomProfileImagePath()` 가 그 자리를 메운다(`common/domain/member/model/OnboardingProfileDefaults.kt`: 한식 이름 30개 풀 + 4자리 숫자, 아바타 6종).
3. **엔티티의 메서드를 부른다.** 서비스는 "무엇을 저장할지"를 스스로 정하지 않는다. 값을 모아 엔티티에 건네고 끝이다.

`getMember` 는 같은 클래스 아래쪽에 있다.

```kotlin
@Transactional(readOnly = true)
fun getMember(memberId: Long): Member =
    getMemberOrNull(memberId) ?: throw BusinessException(ErrorCode.MEMBER_NOT_FOUND)
```
— `api/src/main/kotlin/com/kbap/api/member/MemberService.kt:130-132`

> [!warning] 여기가 self-invocation 함정의 실물이다
> `completeOnboarding`(:22, 쓰기 트랜잭션)이 **같은 클래스의** `getMember`(:130, `readOnly = true`)를 부른다. `readOnly = true` 가 적용됐다면 읽어 온 엔티티를 바꿔도 저장이 안 됐을 것이다.
> 적용되지 **않는다.** 내부 호출은 프록시를 거치지 않아 `getMember` 의 애너테이션이 아예 읽히지 않고, 바깥의 쓰기 트랜잭션이 그대로 이어진다. **그래서 이 온보딩이 정상 동작한다.**
> 즉 지금 잘 돌아가는 이유가 "설계"가 아니라 **"프록시가 내부 호출을 못 본다"는 성질** 위에 서 있다. 원리와 반대 방향으로 데이는 사례는 [[6. 설정과 프로필, 트랜잭션 경계]] 3-4절에 있다.
>
> 이 클래스에는 같은 모양이 하나 더 있다 — `getAvoidedCodes`(:124-128)가 같은 클래스의 `getMemberOrNull`(:66-68)을 내부 호출한다. 여기서는 바깥이 이미 `readOnly` 라 안쪽 애너테이션이 무시돼도 결과가 같다. **같은 코드 모양이 한 번은 흐름을 살리고 한 번은 아무 일도 안 하는데, 둘 다 우연이다.** 이 경로를 타는 읽기 흐름은 [[18. 홈 화면 조회 흐름 — 여러 서비스를 한 응답으로 모으기]] 가 다룬다.

### 3-5. 도메인 메서드 — 규칙은 엔티티가 안다

```kotlin
fun completeOnboarding(
    nickname: String,
    avoidanceSubstanceCodes: List<String>,
    dietCategories: List<String> = emptyList(),
    spicinessPreference: String,
    countryCode: String,
    profileImageUrl: String,
) {
    if (onboardingCompleted) {
        throw BusinessException(ErrorCode.ONBOARDING_ALREADY_COMPLETED)
    }
    updateProfile(
        nickname = nickname,
        ...
        currency = CountryCode.from(countryCode)?.currency?.name,
    )
    onboardingCompleted = true
}
```

- **파라미터가 전부 비-null이다.** 서비스가 3-4절에서 기본값을 채워 넣은 덕분에, 여기까지 오면 "값이 없을 수도 있다"는 걱정이 사라진다.

### 3-6. `save()` 가 없다 — 그런데 저장된다

3-1부터 3-5까지 코드를 다시 훑어보면 `memberRepository.save(...)` 가 **한 번도 나오지 않는다.** 그런데 DB의 행은 바뀐다. 이게 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 의 **변경 감지(dirty checking)** 다.

```
① 트랜잭션 시작            @Transactional (MemberService.kt:22)
② SELECT ... FROM member   findByIdAndMemberStatus (MemberJpaRepository.kt:12)
   → 읽어 온 Member 는 영속성 컨텍스트가 "원본 사본"과 함께 들고 있다
③ member.nickname = "길동이"  … 그냥 필드에 대입 (Member.kt:98-105)
④ 메서드 정상 종료 → 커밋
   → 하이버네이트가 ②의 사본과 ③의 현재 값을 비교
   → 달라진 컬럼만 골라 UPDATE member SET ... WHERE id = ?
```

FE 대응: React Query 캐시에 담긴 객체를 그냥 수정해 두면 다음 동기화 때 서버로 반영되는 것과 감각이 비슷하다. **다른 점**: React Query는 `mutate` 를 명시적으로 불러야 하지만, 하이버네이트는 **트랜잭션이 끝나는 시점에 자동으로** 판단한다. 부르는 함수가 없다.

이 성질 때문에 3-4절의 self-invocation 이야기가 무섭다. `readOnly = true` 가 걸린 트랜잭션에서는 하이버네이트가 이 비교를 아예 건너뛴다(`FlushMode.MANUAL`). 그러면 ③에서 값을 바꿔도 ④에서 아무 일도 안 일어난다 — **에러도 없이 조용히** 저장이 사라진다.

## 4. 계층 경계마다 — 여기서 왜 갈리나

| 경계 | 넘어가는 것 | 갈라 둔 이유 |
|---|---|---|
| 필터 → 컨트롤러 | `memberId`(요청 속성) | 인증은 **모든 API에 공통**이다. 컨트롤러마다 토큰을 뜯으면 40군데에 같은 코드가 생긴다 |
| 컨트롤러 → 서비스 | `MemberProfileInput` | 컨트롤러는 **HTTP를 아는 유일한 층**이다. `OnboardingRequest`(JSON 모양)를 그대로 넘기면 HTTP 관심사가 서비스로 샌다 |
| 서비스 → 엔티티 | 검증 안 된 원시 값(`String`, `List<String>`) | 서비스는 **오케스트레이션**만 한다. "이 값이 유효한가"는 도메인 규칙이라 엔티티/값 객체가 답한다 |
| `:api` → `:common` | 도메인·리포지토리 호출 | `:common` 은 아무에게도 의존하지 않는다. `:api` 를 지워도 `:batch` 가 같은 도메인을 그대로 쓴다 |
| 엔티티 → DB | (없음 — 자동) | 3-6절. 저장 명령을 코드로 쓰지 않는 것이 이 경계의 특징이다 |

kbap에 **UseCase 계층이 없다**는 것도 여기서 눈으로 확인된다. 컨트롤러 다음이 바로 `MemberService` 다. 스캔처럼 복잡한 흐름만 Facade를 한 겹 더 두고, 온보딩처럼 단순한 흐름은 두지 않는다 — 근거와 판단 기준은 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] 에 있다.

`Member` 엔티티가 `:common` 에 있고 `MemberProfileInput` 이 `:api` 에 있다는 배치도 우연이 아니다. [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] 의 3모듈 구조 그대로다.

## 5. 프로필은 컬럼인가 JSON인가 — 둘 다다

이 흐름에서 가장 재미있는 실측은 **`member` 테이블이 프로필을 어떻게 담고 있느냐**다. 답은 "예전엔 JSON 한 덩어리였고, 지금은 대부분 개별 컬럼이되 목록 두 개만 JSON"이다.

**출발점** — `V2026.07.16.21.38.41__init_schema.sql`:

```sql
CREATE TABLE `member` (
  ...
  `nickname` varchar(30) ...,
  `profile` json NOT NULL,
  `onboarding_completed` tinyint(1) NOT NULL DEFAULT '0',
  ...
)
```

프로필 전체가 `profile` 이라는 JSON 컬럼 하나였다. 기획이 바뀔 때마다 마이그레이션 없이 필드를 늘릴 수 있어 초기엔 편하다.

**전환** — KB-297이 이걸 세 개의 마이그레이션으로 평탄화했다.

| 파일 | 하는 일 |
|---|---|
| `V2026.08.05.06.19.59__member_profile_flatten_schema.sql` | `spiciness_preference`·`country_code`·`profile_image_url`·`avoidance_substance_codes` 컬럼 **추가** (기존 `profile` 은 그대로 둠) |
| `V2026.08.05.06.22.09__member_profile_flatten_backfill.sql` | `JSON_EXTRACT` 로 옛 JSON에서 새 컬럼으로 **값 이사** |
| `V2026.08.06.16.54.41__member_profile_json_nullable.sql` | 옛 `profile` 컬럼을 **nullable로** 완화. drop은 미룸 |

**세 개로 쪼갠 이유**가 백엔드 배포의 현실이다. 스키마 변경과 코드 배포는 동시에 일어나지 않는다 — 새 컬럼을 먼저 만들고(구코드도 계속 동작), 값을 옮기고, 옛 컬럼은 안정화를 확인한 뒤에야 없앤다. 세 번째 파일의 주석이 그 결정을 그대로 적어 뒀다: "컬럼 drop 은 평탄화 안정화 확인 후 후속 릴리스로 미룬다(2026-08-06 결정)". **지금도 `profile` 컬럼은 살아 있고, 새로 가입하는 회원 행에는 `NULL` 이 들어간다.**

**남은 JSON 둘.** 평탄화 후에도 목록 두 개는 JSON으로 남았다.

```kotlin
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "avoidance_substance_codes", nullable = false)
var avoidanceSubstanceCodes: List<String> = emptyList(),

@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "diet_categories", nullable = false)
var dietCategories: List<String> = emptyList(),
```
— `common/src/main/kotlin/com/kbap/common/domain/member/model/Member.kt:49-55`

`diet_categories` 는 가장 최근(2026-08-19, KB-340)에 추가된 컬럼이고, 역시 JSON이다.

```sql
ALTER TABLE member
    ADD COLUMN diet_categories json NOT NULL DEFAULT (JSON_ARRAY());
```
— `V2026.08.19.02.12.21__member_diet_categories.sql`

**그 선택의 대가.** 값이 하나면 컬럼, 목록이면 JSON — 이 갈림이 우연이 아니다.

- 정석대로면 `member_avoidance_code` 같은 **자식 테이블**을 따로 만든다. 하지만 kbap은 **JPA 연관관계를 레포 전체에서 금지**하고 ArchUnit이 그걸 강제한다(→ [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]). 자식 테이블을 만들면 조회할 때마다 join이나 추가 쿼리가 붙는다.
- JSON 컬럼이면 **회원 행 한 줄만 읽으면 프로필이 전부 딸려 온다.** 온보딩·프로필 조회·스캔 판정 모두 "이 회원의 기피 목록 전체"를 원하지 목록의 일부를 원하지 않으므로, 통째로 읽는 게 오히려 정확하다.
- 대가는 **DB가 그 안을 모른다는 것**이다. "EGG를 기피하는 회원 수"를 세려면 `JSON_CONTAINS` 를 써야 하고 인덱스가 안 듣는다. 외래키 제약도, `NOT NULL` 같은 컬럼 제약도 없다 — 값이 유효한지는 오직 3-5절의 애플리케이션 검증만이 보증한다.
- 그래서 **자주 필터·정렬·집계하는 값은 컬럼으로, 통째로만 읽는 목록은 JSON으로** 가 이 테이블이 내린 답이다. `country_code` 가 컬럼인 것도 그래서다 — 통화 백필처럼 국가로 회원을 훑는 일이 실제로 있었다.

> [!tip] 마이그레이션은 못 고친다 — 대신 테스트로 묶는다
> `V2026.08.11.13.24.22__member_currency.sql` 은 국가→통화 백필을 CASE문 190줄로 적어 뒀는데, 이후 KB-349에서 취급 통화가 줄면서 그 SQL이 언급하는 통화 18종(`AED`·`BHD`·`VND` 등)이 지금은 `CurrencyCode` enum에 없다. 이미 적용된 마이그레이션은 **체크섬이 동결돼 고칠 수 없다**(→ [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]).
> kbap의 대응은 SQL 수정이 아니라 **차이를 테스트로 고정**하는 것이다 — `CurrencyRemapSyncTest.kt:29-41` 이 "백필 SQL − 현재 enum = 폐기 18종", "현재 enum − 백필 SQL = 신규 2종(ISK·RON)"을 못 박는다. 누가 몰래 통화를 늘리거나 줄이면 이 테스트가 먼저 깨진다.

> `MemberProfileUpdateVersionTest.kt:190` 의 given 이름은 "X-API-Version 없이 호출하면"이고 헤더를 안 붙이는데도 200이 난다. 3-2절에서 "헤더 없으면 400"이라고 했으니 모순처럼 보인다.
> 실제로는 **테스트 환경이 모든 MockMvc 요청에 `X-API-Version: 1.0` 을 기본으로 붙인다** — `api/src/test/kotlin/com/kbap/api/core/config/MockMvcDefaultVersionConfig.kt:12-17` 의 `defaultRequest(...)` 다. 그러니 이 테스트가 확인하는 건 "헤더가 없을 때"가 아니라 **"1.0일 때 국적까지 수정된다"** 이다. 진짜 클라이언트가 헤더를 빠뜨리면 400이 맞다.

## 9. 치트시트

```
POST /api/members/me/onboarding
  ├─ RequestLoggingFilter          로그·MDC
  ├─ JwtAuthenticationFilter       request.setAttribute("authMemberId", 1L)
  ├─ X-API-Version 라우팅          1.0 → completeOnboarding
  │                                1.1+ → completeOnboardingWithServerProfile
  │                                없음 → 400
  ├─ AuthMemberIdArgumentResolver  속성 → @AuthMemberId memberId
  ├─ MemberController              OnboardingRequest.toInput(memberId, serverAssignsProfile)
  ├─ MemberService  @Transactional ◀── 트랜잭션 시작
  │    ├─ getMember()              SELECT  (self-invocation — readOnly 미적용)
  │    └─ member.completeOnboarding()
  │         ├─ if (onboardingCompleted) throw MEMBER-002
  │         ├─ MemberProfile.updatedWith(...)   ◀── 값 검증 전부 여기
  │         └─ onboardingCompleted = true
  └─ 커밋                          ◀── 하이버네이트가 UPDATE member 생성
```

- **저장 명령이 없다.** `save()` 를 찾지 마라. 커밋 시 변경 감지가 한다.
- **검증은 엔티티 안쪽**이다. 컨트롤러에 `@Valid` 가 없는 이유다.
- **`null` 은 "값 없음"이 아니다.** `MemberProfileInput` 에서 `null` = "서버가 정하라"(온보딩), `ProfileUpdateInput` 에서 `null` = "안 바꾼다"(수정). 같은 `null` 이 다른 뜻이다.
- **에러 코드는 문자열로 분기**한다. HTTP 상태는 대부분 400이라 구분에 못 쓴다.

## 10. 용어집

- **인자 해석기(HandlerMethodArgumentResolver)**: 컨트롤러 메서드의 파라미터를 프레임워크가 채워 넣는 장치. `@AuthMemberId` 처럼 직접 만든 애너테이션을 지원하려면 이걸 등록한다.
- **요청 속성(request attribute)**: 요청 하나가 살아 있는 동안만 유지되는 키-값 보관함. 필터가 넣고 컨트롤러 쪽이 꺼내는 데 쓴다.
- **변경 감지(dirty checking)**: 트랜잭션 커밋 시점에 하이버네이트가 "읽어 왔을 때의 값"과 "지금 값"을 비교해 달라진 컬럼만 UPDATE하는 동작.
- **평탄화(flatten)**: JSON 한 컬럼에 뭉쳐 두던 값을 개별 컬럼으로 펼치는 스키마 변경.
- **백필(backfill)**: 새 컬럼을 만든 뒤, 기존 행들의 그 컬럼을 옛 값에서 계산해 채워 넣는 일회성 UPDATE.
- **objectKey**: 스토리지에 저장된 파일의 도메인 없는 경로. kbap은 DB에 이것만 저장하고 응답할 때 CDN 도메인을 붙인다.

## 11. 체크리스트

- [ ] `POST /api/members/me/onboarding` 요청이 지나는 계층을 순서대로 말할 수 있다
- [ ] 컨트롤러의 `memberId` 가 어디서 왔는지 설명할 수 있다
- [ ] 같은 경로에 핸들러가 둘인 이유와, 헤더를 빠뜨리면 어떻게 되는지 안다
- [ ] `MemberProfileInput.nickname = null` 이 무슨 뜻인지 말할 수 있다
- [ ] `save()` 없이 저장되는 원리를 설명할 수 있고, `readOnly = true` 였다면 왜 위험한지 안다
- [ ] `completeOnboarding` 이 `getMember` 를 부를 때 `readOnly` 가 적용되지 않는 이유를 말할 수 있다
- [ ] `member` 테이블에서 어떤 값이 컬럼이고 어떤 값이 JSON인지, 왜 그렇게 갈렸는지 안다
- [ ] KB-297이 마이그레이션을 셋으로 쪼갠 이유를 설명할 수 있다
