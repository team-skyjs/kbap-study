# 18. 홈 화면 조회 흐름 — 여러 서비스를 한 응답으로 모으기

> 작성: 2026-08-27 · 맥락: 15~17번은 전부 **쓰기·인증** 경로였다 — 회원을 만들고, 토큰을 발급하고, 매 요청에서 그 토큰을 검증하는 일. 이 노트는 방향을 바꿔 **읽기 경로의 대표**를 본다. 홈은 kbap 에서 가장 많이 불리는 API 이고, 한 화면에 필요한 조각이 여러 도메인에 흩어져 있어 "**서버가 어디까지 말아서 주는가**"라는 질문이 가장 선명하게 드러나는 자리다.
> 목표: 홈 요청 하나가 어떤 서비스 6곳을 거쳐 쿼리 몇 번을 때리고 어떤 응답으로 조립되는지 말할 수 있게 되고, 그 조립을 **서버에서 하는 것과 화면에서 하는 것**의 트레이드오프를 설명할 수 있게 되기.

---

## 0. 한 줄 요약

`GET /api/home?lang=en` 한 번이면 홈 화면에 필요한 **세 섹션**(기피 성분 · 인기 음식 5개 · 최근 스캔 10개)이 카드 모양까지 완성되어 내려온다. 서버 안에서는 이 한 요청이 **서비스 6곳**을 훑어 **쿼리 9방**을 때리고, **읽기 전용 트랜잭션 3개**에 나눠 담긴 뒤, `HomeResult` → `HomeResponse` 두 단계로 조립된다. 로그인하지 않아도 200 이 나오고, 그때는 개인화 섹션이 **빈 배열**로 온다.

---

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 |
|---|---|---|
| **fan-in (조합)** | 여러 곳에서 긁어온 조각을 하나의 응답으로 모으는 일 | 화면에서 `Promise.all([a, b, c])` 로 받아 하나의 화면 상태로 합치는 것 — **그걸 서버가 대신 해준다**는 게 차이 |
| **BFF** (Backend For Frontend) | "이 화면 전용"으로 응답을 말아주는 백엔드 계층 | Next.js 의 route handler 가 여러 API 를 대신 호출해 페이지에 필요한 모양으로 내려주는 것 |
| **조합 엔드포인트** | 도메인 하나에 대응하지 않고 **화면 하나**에 대응하는 API | `/api/home` 처럼 "홈 화면"이라는 이름을 가진 엔드포인트 |
| **인자 리졸버** (`HandlerMethodArgumentResolver`) | 컨트롤러 메서드의 파라미터를 요청에서 뽑아 채워주는 스프링 확장점 | 라우터가 `params`·`searchParams` 를 훅으로 꽂아주는 것 |
| **집계 쿼리** | `avg`·`count` 처럼 여러 행을 묶어 요약값을 뽑는 SQL | 배열을 `reduce` 로 접는 것 — 단, 접는 주체가 앱이 아니라 DB |
| **순서 복원** | `IN` 절로 한 번에 긁으면 순서가 보장되지 않으므로, 미리 정해둔 id 순서대로 다시 세우는 것 | `ids.map(id => byId[id])` 와 정확히 같은 패턴 |

## 2. 이 API 가 하는 일 — 사용자 관점 한 줄

앱을 켜면 뜨는 첫 화면이다. **내가 피하는 성분**이 칩으로 늘어서고, 그 아래 **인기 음식** 카드가 깔리고, 맨 아래 **최근에 스캔한 메뉴**가 뜬다. 카드마다 사진·이름·매운맛·별점·북마크 하트가 이미 다 붙어 있다.

```
GET /api/home?lang=en          ← 앱이 부르는 건 이거 하나
X-API-Version: 1.0
Authorization: Bearer …        ← 선택
```

## 4. 코드로 따라가기

### 4-1. 컨트롤러 — 조합이 **여기서도** 일어난다

```kotlin
@GetMapping
override fun home(
    @Valid @ModelAttribute request: HomeRequest,
    @AuthMemberIdOrNull memberId: Long?,
): ResponseEntity<BaseResponse<HomeResponse>> {
    val result = homeService.getHome(memberId, LanguageCode.from(request.lang))
    val foodIds = (result.popularFoods + result.recentScans).map { it.foodId }
    val bookmarkedFoodIds = bookmarkService.getBookmarkedFoodIds(memberId, foodIds)
    val ratings = reviewService.getFoodRatings(foodIds)
    return ResponseEntity.ok(
        BaseResponse.ok(
            HomeResponse.from(result, authenticated = memberId != null, bookmarkedFoodIds, ratings),
        ),
    )
}
```
`api/src/main/kotlin/com/kbap/api/home/HomeController.kt:23-42` (인자 이름은 원본대로, 마지막 두 인자는 지면상 축약)

- **1줄**: `HomeService` 가 세 섹션의 뼈대를 만든다.
- **2줄**: 두 섹션에 등장한 **음식 id 를 전부 한 줄로 모은다**. 인기 음식 5개 + 최근 스캔 10개 = 최대 15개.
- **3~4줄**: 그 id 목록 하나로 북마크 여부와 별점을 **각각 한 방씩** 긁는다. 카드 15장을 만들면서 북마크 쿼리가 15번 나가지 않는 이유가 이것이다.
- **6줄**: `authenticated` 는 서비스가 모른다 — **토큰이 있었는지**는 HTTP 의 사정이라 컨트롤러가 판정한다.

여기서 놓치기 쉬운 사실: **조합이 두 층에서 일어난다.** `HomeService` 가 회원·성분·음식·스캔 4곳을 모으고, `HomeController` 가 그 결과에 북마크·리뷰 2곳을 더 얹는다. 계획 단계에서는 "`HomeService` 의존 4개"로 적혀 있었지만, 실제 홈 응답을 만드는 데 관여하는 서비스는 **6개**다.

> [!tip] 왜 북마크·리뷰는 `HomeService` 안으로 안 들어갔나
> 이 둘은 **어느 목록 API 든 똑같이 필요한 마지막 덧칠**이다(음식 목록·검색·북마크 목록에도 붙는다). `HomeService` 안에 넣으면 홈 전용이 되고, 컨트롤러에 두면 "음식 카드를 만드는 마지막 한 겹"으로 재사용된다. 실제로 `FoodSummaryResponse.from(view, bookmarked, rating)`(`api/.../food/FoodSummaryResponse.kt:21`)이 그 한 겹의 이름이다.

### 4-2. 서비스 — 세 섹션 만들기

```kotlin
@Transactional(readOnly = true)
fun getHome(memberId: Long?, lang: LanguageCode): HomeResult {
    val member = memberId?.let { memberService.getMemberOrNull(it) }
    val avoidedCodes = memberService.getAvoidedCodes(member?.id)
    val avoidedRefs = avoidedCodes.map { it.name }.toSet()

    return HomeResult(
        avoidedSubstances = (if (avoidedCodes.isEmpty()) emptyList() else ingredientRepository.findByCodeIn(avoidedCodes))
            .map { AvoidedSubstanceView(code = it.code.name, name = it.displayName(lang)) },
        popularFoods = foodService.getRandomReadyFoods(POPULAR_SIZE)
            .map { FoodSummaryView.from(it, lang, avoidedRefs, foodService.resolveImageUrl(it)) },
        recentScans = member?.id?.let { id ->
            val recentIds = scanService.getRecentReadyFoodIds(id, RECENT_SCAN_SIZE)
            val foodsById = foodService.getReadyFoodsByIds(recentIds).associateBy { it.id }
            recentIds.mapNotNull { foodsById[it] }
                .map { FoodSummaryView.from(it, lang, avoidedRefs, foodService.resolveImageUrl(it)) }
        }.orEmpty(),
    )
}
```
`api/src/main/kotlin/com/kbap/api/home/HomeService.kt:19-37`

읽는 순서:

- **`memberId?.let { … }`** — `memberId` 가 `null`(비회원)이면 회원 조회를 아예 건너뛴다. 코틀린의 널 안전 연산자가 "로그인 안 했으면 이 줄은 없는 셈" 을 한 글자로 쓴다.
- **`avoidedCodes`** — 회원이 저장해둔 기피 성분 **코드**(`EGG`, `MILK` …). 이건 회원 행 안의 JSON 컬럼에서 나온다(`Member.profile` 은 컬럼을 조합하는 **계산 프로퍼티**다 — `common/.../member/model/Member.kt:79-88`). 즉 **추가 쿼리가 없다.** 저장 쪽 이야기는 [[15. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]].
- **`ingredientRepository.findByCodeIn`** — 코드만으론 화면에 못 쓰니 `ingredients` 테이블에서 **지역화된 이름**을 가져온다. `EGG` → `Egg` / `卵` / `계란`.
- **`avoidedRefs`** — 아래 카드들의 위험도 계산에 쓰일 문자열 집합. 이 집합이 비면(비회원) 모든 음식이 `SAFE` 로 계산된다.
- **`getRandomReadyFoods(5)`** — "인기"라는 이름이지만 지금은 **완성된 음식 중 무작위 5개**다(뒤 6절).
- **`recentIds.mapNotNull { foodsById[it] }`** — **순서 복원**. `findByIdIn` 은 id 순으로 돌려주므로 스캔 최신순이 무너진다. 그래서 `recentIds` 의 순서대로 Map 에서 다시 꺼낸다. FE 의 `ids.map(id => byId[id])` 와 같은 손동작이다.

## 5. fan-in 은 왜 **서버**에서 하나 — BFF 트레이드오프

FE 관점에서 이 노트의 진짜 질문은 이거다.

> 홈 화면이 API 를 4번 부를 것인가, 서버가 한 번에 말아줄 것인가?

kbap 은 **후자**를 골랐다. 지금 코드라면 앱이 직접 조립할 경우 이렇게 된다.

```ts
// 서버가 안 말아줬다면 화면이 해야 할 일 (예시)
const [profile, popular, recent, ratings] = await Promise.all([...])
const bookmarks = await getBookmarks(pluckIds(popular, recent))  // ← id 를 알아야 부를 수 있다
```

| | 서버가 조합 (`GET /api/home`) | 화면이 조합 (도메인별 API 4~5개) |
|---|---|---|
| 왕복 횟수 | **1회** | 4~5회, 그중 북마크·별점은 **앞 응답의 id 가 있어야** 부를 수 있어 워터폴 |
| 모바일 네트워크 | 지연 1번만 물림 | 지연 × 왕복 수, LTE 에서 체감이 크다 |
| 화면 코드 | 응답을 그대로 렌더 | 조립·정렬·널 병합 로직이 화면에 쌓임 |
| 부분 실패 | 하나 터지면 홈 전체가 실패 | 섹션별로 따로 실패·재시도 가능 |
| 화면 변경 | **서버를 고쳐야 한다** (배포·버저닝 동반) | 화면만 고치면 됨 |
| 재사용 | 홈 전용 — 다른 화면이 못 씀 | 도메인 API 라 어디서든 씀 |
| 캐싱 | 한 덩어리라 통째로만 캐시 | 조각별로 다른 수명 부여 가능 |

kbap 이 서버 조합을 고른 이유는 표의 첫 두 줄이다. **홈은 앱 진입 화면**이라 여기서 지연이 생기면 "앱이 느리다"가 된다. 대신 값을 치른다 — 홈 디자인이 바뀌면 서버 API 가 따라 바뀌고, 그건 [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 의 헤더 버저닝 문제가 된다.

> [!note] "조합 엔드포인트"는 계층 위반이 아니다
> `HomeService` 는 `MemberService`·`FoodService`·`ScanService` 를 **서비스가 서비스를 부르는** 모양이다. [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지]] 에서 본 대로 이 레포는 UseCase 계층이 없고, 이런 가로 호출을 서비스 사이에서 허용한다. 대신 방향이 한쪽으로만 흐르는지는 [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]] 의 몫이다.

## 6. 트랜잭션 — 한 요청, **세 개**의 읽기 트랜잭션

`@Transactional` 은 `HomeService.getHome` **하나에만** 붙어 있다. 컨트롤러에는 없다. 그러면 컨트롤러가 뒤이어 부르는 `getBookmarkedFoodIds`·`getFoodRatings` 는 어디에 담기나? **각자 자기 트랜잭션을 연다.** 둘 다 `@Transactional(readOnly = true)` 를 달고 있고, 바깥에 진행 중인 트랜잭션이 없기 때문이다.

| # | 트랜잭션 | 여는 지점 | 안에서 도는 조회 |
|---|---|---|---|
| T1 | `HomeService.getHome` | `HomeService.kt:19` | 회원 · 성분 · 인기 음식 · 최근 스캔 |
| T2 | `BookmarkService.getBookmarkedFoodIds` | `BookmarkService.kt:31` | 북마크 |
| T3 | `ReviewService.getFoodRatings` | `ReviewService.kt:189` | 별점 집계 |

세 가지가 따라온다.

1. **`readOnly = true`** 는 "쓰지 않겠다"는 선언이다. JPA 는 이 안에서 변경 감지(dirty checking)를 위한 스냅샷 비교를 건너뛰고, DB 쪽에도 읽기 전용 힌트가 갈 수 있다. 규약과 이유는 [[6. 설정과 프로필, 트랜잭션 경계]].
2. **세 트랜잭션은 서로 다른 시점을 본다.** T1 과 T3 사이에 누가 리뷰를 남기면, 카드 목록은 T1 시점이고 별점은 T3 시점이다. 홈에서는 무해하지만(별점이 0.1 다르게 보일 뿐) — **읽기 일관성이 중요한 화면이라면 이 조립을 한 트랜잭션 안으로 넣어야 한다.**
3. **영속성 컨텍스트도 세 번 새로 열린다.** T1 에서 읽은 `Food` 엔티티는 T2·T3 와 공유되지 않는다. [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 의 "캐시는 트랜잭션 수명" 이 그대로 적용된다.

> [!warning] 회원 조회가 두 번 나가는 이유
> **`HomeService` 가 회원을 두 번 요구하기 때문이다.** 21줄에서 `getMemberOrNull(memberId)` 로 한 번 읽고, 22줄에서 `getAvoidedCodes(member?.id)` 를 부르는데 이 메서드가 **자기 안에서 회원을 다시 읽는다**(`MemberService.kt:127`). 이미 손에 든 `member` 로 `member.profile.avoidedCodes()` 를 부르면 될 자리를 id 만 넘겨 다시 조회하는 셈이다.
> `findByIdAndMemberStatus` 는 파생 쿼리라 1차 캐시가 가로채지 못하고 **SELECT 가 실제로 두 번** 나간다(돌아온 행은 이미 캐시에 있는 같은 엔티티 인스턴스에 매핑된다).
> 원인이 **self-invocation 은 아니다.** `getAvoidedCodes` → `getMemberOrNull` 이 같은 클래스 안 호출이라 프록시를 안 거치는 건 맞지만, 그건 안쪽 `@Transactional` 이 무시된다는 뜻일 뿐 메서드를 두 번 실행시키지 않는다(여기서는 바깥이 이미 readOnly 라 결과도 같다). self-invocation 자체의 설명은 [[15. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]] 에 있다.

## 7. 쿼리를 세어 보자 — N+1 이 **안 나는** 대신 눈에 보이는 것

kbap 에는 JPA 연관관계가 하나도 없다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]). 그래서 이 흐름에는 "카드를 렌더하다 갑자기 쿼리 15방이 나가는" 일이 없다. 대신 **쿼리가 전부 코드에 적혀 있어 셀 수 있다.** 회원이 기피 성분 1개, 인기 음식 5개, 최근 스캔 10개를 받는 경우:

| # | 쿼리 | 나오는 곳 |
|---|---|---|
| 1 | `select … from member where id = ? and member_status = 'ACTIVE'` | `MemberService.kt:67` |
| 2 | 같은 쿼리 — `getAvoidedCodes` 가 회원을 다시 읽는다 (6절 경고) | `MemberService.kt:127` |
| 3 | `select … from ingredients where code in (?)` | `IngredientJpaRepository.kt:8` |
| 4 | `select f.id from food … order by rand() limit 5` | `FoodJpaRepository.kt:145-155` |
| 5 | `select … from food where id in (?, …)` | `FoodJpaRepository.kt:117` |
| 6 | `select sh.food_id … group by sh.food_id order by max(sh.created_at) desc limit 10` | `ScanHistoryJpaRepository.kt:22-36` |
| 7 | `select … from food where id in (?, …)` (최근 스캔용) | `FoodJpaRepository.kt:117` |
| 8 | `select … from bookmark where member_id = ? and food_id in (?, …)` | `BookmarkJpaRepository.kt:12` |
| 9 | `select r.foodId, avg(r.rating), count(r) … group by r.foodId` | `ReviewJpaRepository.kt:48-56` |

**총 9방.** 비회원이면 1·2·3·6·7·8 이 통째로 빠져 **3방**(4·5·9)이다.

여기서 배울 두 가지 패턴:

**① 2단계 조회 (id 먼저, 본문 나중).** 4번→5번, 6번→7번이 같은 모양이다. 먼저 **id 목록만** 뽑는 가벼운 쿼리를 던지고, 그 id 로 본문을 `IN` 한 방에 긁는다. 정렬·필터가 복잡할수록 첫 쿼리를 네이티브 SQL 로 두기 쉽고, 두 번째 쿼리는 단순 `findByIdIn` 이라 재사용된다. 키셋 페이징에서 같은 손동작이 나온다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]).

**② id 를 모아 한 번에 (batch loading).** 8번·9번이 그렇다. 카드마다 북마크를 물었다면 15방, 별점을 물었다면 또 15방이 나갔을 자리를 `IN` 절 두 방으로 눌렀다. 연관관계가 있었다면 `food.reviews` 를 건드리는 순간 JPA 가 알아서 15방을 쏘고 우리는 그걸 눈치채지 못했을 것이다. **연관관계를 지운 대가로 우리가 직접 모아야 하고, 대신 몇 방인지 코드만 봐도 안다.**

> [!warning] `order by rand()` 의 천장
> 4번 쿼리는 READY 음식 **전체를 정렬**한 뒤 5개를 자른다. 카탈로그가 작은 지금은 문제없지만 행이 수십만이 되면 이 한 줄이 홈 전체를 느리게 만든다. `HomeApi.kt:37` 이 "인기도 지표가 쌓이기 전까지"라고 적어둔 건 이게 **임시 구현**이라는 뜻이다. 응답 모양은 그대로 두고 안쪽만 바꾸면 되도록 설계돼 있다.

## 8. `HomeResult` vs `HomeResponse` — 왜 DTO 가 두 개인가

```kotlin
data class HomeResult(
    val avoidedSubstances: List<AvoidedSubstanceView>,
    val popularFoods: List<FoodSummaryView>,
    val recentScans: List<FoodSummaryView>,
)
```
`api/src/main/kotlin/com/kbap/api/home/HomeResult.kt:5-9`

`HomeResult` 에는 `authenticated` 도, `bookmarked` 도, `review` 도 없다. **서비스가 아직 모르는 것들**이기 때문이다. 그걸 다 아는 자리는 컨트롤러이고, 최종 모양은 `HomeResponse.from` 이 만든다.

| | `HomeResult` (내부) | `HomeResponse` (API) |
|---|---|---|
| 사는 곳 | 서비스가 반환 | 컨트롤러가 반환 |
| 애너테이션 | 없음 — 순수 `data class` | `@Schema` 투성이 (springdoc 문서화) |
| `RiskLevel` | enum 그대로 | `String` 으로 평탄화 (`overallRiskStatus = view.overallRiskStatus.name`) |
| 바꾸면 | 서버 내부 사정 | **앱이 깨진다** — 계약 변경 |

이 분리의 값은 마지막 줄에 있다. 내부 결과 타입은 리팩터링으로 자유롭게 바꿀 수 있고, **JSON 으로 나가는 모양은 `*Response` 파일에만 있다.** 계약을 한 곳에 가둔 것이다 — [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]. FE 로 치면 "API 응답 타입"과 "화면 상태 타입"을 굳이 분리해 두는 습관과 같다(다만 여기서는 **서버 쪽** 두 타입이다).

`enum` 을 `String` 으로 평탄화하는 것도 의도적이다. 서버가 `RiskLevel` 에 값을 하나 추가해도 JSON 스키마는 `string` 그대로다.

## 9. 로그인하지 않고 홈 열기

홈은 **로그인 전에도 열려야 하는** 화면이다. 그래서 인증이 선택이다.

```kotlin
val header = request.getHeader(AUTHORIZATION_HEADER) ?: return null
if (!header.startsWith(BEARER_PREFIX)) return null
val parsed = tokenParser.parseAccessToken(header.removePrefix(BEARER_PREFIX))
if (parsed.role == MemberRole.ADMIN) return null
return parsed.memberId
```
`api/src/main/kotlin/com/kbap/api/core/auth/AuthMemberIdOrNullArgumentResolver.kt:24-29`

세 갈래가 나온다.

| 요청 | 결과 |
|---|---|
| 헤더 없음 / `Bearer ` 로 시작 안 함 | `memberId = null` → **비회원 200**, 개인화 섹션은 빈 배열 |
| 정상 회원 토큰 | `memberId` 채워짐 → 세 섹션 전부 |
| 위조·만료 토큰 | `parseAccessToken` 이 예외를 던져 **401** — 비회원으로 폴백하지 **않는다** |
| 관리자 토큰 | `null` → 비회원 취급 (관리자에겐 개인 홈이 없다) |

세 번째 줄이 설계 결정이다. "토큰을 안 보낸 사람"과 "잘못된 토큰을 보낸 사람"은 다르게 대한다. 후자는 대개 **앱의 토큰 갱신이 실패한 상태**라, 조용히 비회원 홈을 보여주면 사용자는 자기 데이터가 사라진 줄 안다. 401 을 주면 앱이 재로그인 흐름을 탈 수 있다.

> [!note] 홈에는 JWT 필터가 붙지 않는다
> `/api/home` 은 `JwtAuthenticationFilter` 의 URL 패턴 목록(`WebConfig.kt:80-100`)에 **없다.** 즉 필터는 이 요청을 아예 보지 않고, 토큰 판정은 위 인자 리졸버가 혼자 한다. 필터가 붙은 경로에서 매 요청 검증이 어떻게 도는지는 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] 에 있다.

**언어도 회원 여부와 무관하다.** 표시 언어는 오직 쿼리 파라미터 `lang` 이 정한다(`HomeController.kt:28`, `LanguageCode.from`). 회원 프로필의 앱 언어는 **보지 않는다** — 같은 `lang` 이면 회원과 비회원의 응답 언어가 같다. 지원 목록에 없는 코드(`fr`)는 400 이 아니라 **영어로 폴백**한다(`common/.../LanguageCode.kt:18`). 홈이 앱 진입 화면이라 "언어를 몰라서 화면이 안 열리는" 상황을 만들지 않겠다는 결정이다. `lang` 자체가 없거나 공백이면 그건 클라이언트 버그이므로 400 `COMMON-002`.

## 10. 요청 / 응답 실물

### 요청

```http
GET /api/home?lang=en HTTP/1.1
X-API-Version: 1.0
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

### 응답 200 — 회원 (배열 내용은 `…` 로 축약)

```json
{
  "success": true,
  "payload": {
    "authenticated": true,
    "avoidedSubstances": [
      { "code": "EGG", "name": "Egg" },
      { "code": "MILK", "name": "Milk" }
    ],
    "popularFoods": [
      {
        "foodId": 12,
        "name": "Kimchi Stew",
        "koreanName": "김치찌개",
        "imageRef": "https://cdn.example.com/foods/kimchi.png",
        "spiciness": 3,
        "overallRiskStatus": "SAFE",
        "bookmarked": false,
        "review": { "averageRating": 4.3, "count": 27 }
      },
      …
    ],
    "recentScans": [ … ]
  },
  "message": null,
  "code": null
}
```

- `koreanName` 은 **표시명과 다를 때만** 채워진다. `lang=ko` 면 `null` 이다(`FoodSummaryView.kt:21`).
- `imageRef` 는 저장된 파일 경로에 공개 베이스 URL 을 붙인 **절대 URL**이다. 이미 절대 URL 이면 그대로 둔다(`common/.../util/ImageUrls.kt:4-10`).
- `review` 는 리뷰가 없어도 `null` 이 아니라 `{ "averageRating": 0.0, "count": 0 }` 이다(`FoodSummaryResponse.kt:29-32`).
- `overallRiskStatus` 는 `SAFE` / `CAUTION` / `DANGER` / `UNKNOWN`. 음식 성분과 회원 기피 성분의 **교집합** 중 가장 센 등급이다(`common/.../food/model/Food.kt:148-151`).

### 응답 200 — 비회원

```json
{
  "success": true,
  "payload": {
    "authenticated": false,
    "avoidedSubstances": [],
    "popularFoods": [ … ],
    "recentScans": []
  },
  "message": null,
  "code": null
}
```

**배열은 절대 `null` 이 아니다.** 값이 없으면 빈 배열이라, 앱에 `?? []` 분기가 필요 없다. 비회원은 기피 성분이 없으므로 모든 카드가 `SAFE` 로 계산된다(빈 목록의 집계 = `SAFE`, `RiskLevel.kt:27-32`).

## 12. 스펙과 코드가 다른 곳

> [!warning] 스펙과 다름 — `specs/kb-111-home-screen/contracts/home-api.md`
> 이 계약 문서는 홈의 **최초 스펙**(2026-07)이라 세 곳이 지금 코드와 다르다. **코드가 정본이다.**
> 1. **경로** — 문서는 `GET /api/v1/home`. 지금은 `GET /api/home` + `X-API-Version` 헤더(전 API URI 버전 제거, 커밋 `d69d8839`).
> 2. **언어 결정** — 문서는 "쿼리 파라미터 없음, 서버가 회원 프로필 `appLanguage` 로 결정". 지금은 `lang` **필수 파라미터**이고 프로필 언어는 보지 않는다. 이 변경의 스펙은 `specs/kb-201-home-lang-param/` 이며, 폐기된 `COMMON-001`(미지원 언어 오류) 자리가 그 흔적이다(`common/.../error/ErrorCode.kt:9`).
> 3. **카드 필드** — 문서 예시에 `bookmarked`·`review` 가 없다. 리뷰 평점·리뷰 수는 나중에 목록 응답 전반에 추가됐다(커밋 `cc9a0c76`). 비회원 예시의 `overallRiskStatus: "UNKNOWN"` 도 실제로는 `SAFE` 다(`HomeGuestTest.kt:56-66` 이 못 박는다).

> [!warning] 코드 안 문서끼리도 어긋난 곳
> `HomeResponse.kt:10-11` 의 스키마 설명은 "비회원이면 개인화 섹션이 **null**" 이라고 적혀 있지만, 실제 응답은 **빈 배열**이고 `HomeApi.kt:26` 은 "배열 필드는 null 을 내려주지 않는다"고 정반대로 적어뒀다. 스웨거를 볼 앱 개발자가 헷갈릴 자리다 — 실제 동작은 **빈 배열**.

```
├─ BookmarkService               id 15개 → 북마크 집합            ← T2
├─ ReviewService                 id 15개 → 평점 집계 (group by)   ← T3
└─ HomeResponse.from(...)        + authenticated + bookmarked + review → JSON
```

| 궁금한 것 | 답 |
|---|---|
| 섹션은 몇 개? | 3개 — `avoidedSubstances` · `popularFoods`(5) · `recentScans`(10) |
| 조합에 관여하는 서비스는? | 6개 — member · ingredient · food · scan(서비스 안) + bookmark · review(컨트롤러) |
| 쿼리 몇 방? | 회원 9방 / 비회원 3방 |
| 트랜잭션 몇 개? | 3개, 전부 `readOnly = true` |
| 로그인 안 하면? | 200, 개인화 섹션은 빈 배열, 모든 카드 `SAFE` |
| 언어는 누가 정하나? | 오직 `lang` 파라미터. 모르는 코드는 영어 폴백, 누락은 400 |

## 14. 용어집

- **fan-in** — 여러 출처의 데이터를 하나로 모으는 것. 반대말 fan-out(하나를 여러 곳으로 뿌리기).
- **BFF** — 특정 클라이언트(앱·웹) 전용으로 응답을 재단하는 백엔드 계층.
- **`@ModelAttribute`** — 쿼리 파라미터·폼 값을 객체 하나로 묶어 받는 애너테이션. JSON 바디를 받는 `@RequestBody` 의 쿼리스트링판.
- **`HandlerMethodArgumentResolver`** — 컨트롤러 파라미터를 요청에서 채워주는 스프링 확장점. `@AuthMemberIdOrNull` 이 이걸로 동작한다.
- **파생 쿼리 (derived query)** — `findByMemberIdAndFoodIdIn` 처럼 **메서드 이름**으로 SQL 이 만들어지는 스프링 데이터 기능.
- **네이티브 쿼리** — JPQL 이 아니라 DB SQL 을 그대로 쓰는 것(`nativeQuery = true`). 홈에서는 `order by rand()`·`group by`+`max()` 때문에 쓴다.
- **순서 복원** — `IN` 조회 결과를 미리 정한 id 순서대로 다시 세우는 패턴.
- **평탄화 (flatten)** — enum·중첩 객체를 문자열·단순값으로 낮춰 응답에 싣는 것.

## 15. 체크리스트

- [ ] `HomeController.home` 을 열어 **서비스 호출 3줄**을 짚고, 그중 둘이 왜 컨트롤러에 있는지 설명할 수 있다
- [ ] 홈 응답을 만드는 데 관여하는 서비스 6개를 셀 수 있다
- [ ] 회원 홈이 쿼리 9방, 비회원 홈이 3방인 이유를 표 없이 설명할 수 있다
- [ ] "한 요청에 트랜잭션이 3개"인 이유와, 그게 만드는 읽기 일관성 틈을 말할 수 있다
- [ ] `HomeResult` 와 `HomeResponse` 를 나눈 이유를 한 문장으로 말할 수 있다
- [ ] 연관관계가 없어서 **얻은 것**(N+1 없음)과 **치른 대가**(id 를 직접 모아야 함)를 둘 다 말할 수 있다
- [ ] 화면이 API 를 4번 부르는 안과 서버가 한 번에 마는 안의 트레이드오프를 3가지 이상 댈 수 있다
- [ ] 토큰 없음 / 위조 토큰 / 관리자 토큰이 각각 어떻게 처리되는지 구분할 수 있다
- [ ] `lang=fr` 이 400 이 아닌 이유를 설명할 수 있다
- [ ] `order by rand()` 가 왜 임시 구현인지 말할 수 있다
