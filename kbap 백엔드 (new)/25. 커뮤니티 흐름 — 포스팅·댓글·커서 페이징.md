# 25. 커뮤니티 흐름 — 포스팅·댓글·커서 페이징

> 작성: 2026-08-27 · 맥락: 22번(리뷰)에서 쓰기 트랜잭션 하나가 여러 테이블을 움직이는 걸 봤고, 24번(주문)에서 커서 페이징과 "연관관계 없이 배치 로딩" 을 봤다. 커뮤니티는 그 둘을 다 쓰면서 **새 문제 하나**를 더 얹는다 — 댓글은 자기 자신을 가리킨다. `@OneToMany` 가 금지된 레포에서 트리를 어떻게 만드나.
> 목표: ① 글 하나가 저장될 때 통과하는 검증 세 겹을 순서대로 말할 수 있게 되기 ② **연관관계 없이 1depth 대댓글 트리를 3번의 쿼리로 조립하는 법**을 설명할 수 있게 되기 ③ "게스트는 글은 읽는데 댓글은 401" 이 왜 그런지, 그게 버그인지 설계인지 근거와 함께 답할 수 있게 되기.

---

## 0. 한 줄 요약

커뮤니티는 **글 5개 + 댓글 4개, 총 9개 엔드포인트**가 `CommunityController` → `CommunityService` → `Posting`/`Comment` 엔티티 → 두 개의 `JpaRepository` 로 흐르는 얇은 CRUD다. 특별한 건 세 가지 — **자기 참조 컬럼 하나로 만든 1depth 대댓글**, **커서 페이징 위에 얹힌 게스트 노출 게이트**, 그리고 **"나중에 차단 필터를 넣을 자리" 를 미리 한 곳으로 모아둔 조립 함수**다.

## 1. 이 흐름이 하는 일 — 사용자 관점

사용자는 사진 몇 장과 음식 태그를 붙여 글을 쓰고, 남의 글을 무한스크롤로 읽고, 댓글과 답글을 단다. 비로그인 방문자도 피드 첫 페이지와 글 상세는 볼 수 있지만, 더 스크롤하거나 댓글을 열려고 하면 로그인 벽을 만난다.

엔드포인트 9개(`CommunityController.kt`). 경로 베이스는 `/api` 다 — `/api/v1` 이 아니다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]).

| 메서드 · 경로 | 하는 일 | 인증 | 컨트롤러 |
|---|---|---|---|
| `POST /api/community/posts` | 글 작성 | 필수 | `:28-42` |
| `PUT /api/community/posts/{postId}` | 글 수정(전량 교체) | 필수 | `:44-60` |
| `DELETE /api/community/posts/{postId}` | 글 삭제(소프트) | 필수 | `:62-69` |

## 3. 글 하나가 저장되기까지 — 검증 세 겹

`createPosting` 은 짧다(`CommunityService.kt:31-50`).

```kotlin
@Transactional
fun createPosting(memberId: Long, content: String, imagePaths: List<String>?, foodIds: List<Long>?): PostingResponse {
    verifyImageOwnership(memberId, imagePaths)
    verifyFoodTags(foodIds)

    val posting = postingRepository.save(
        Posting(memberId = memberId, content = content, imageRefs = imagePaths, foodIds = foodIds),
    )
    return PostingResponse.from(posting, imagePublicBaseUrl)
}
```

- `verifyImageOwnership` (`:249-253`) — `UploadedImageService.ownsAllImages(memberId, paths, UploadPurpose.COMMUNITY)`. **"업로드가 끝났고 · 내가 올렸고 · 용도가 커뮤니티인" 경로만 통과.** 실패 시 `COMMUNITY-003`. 21번에서 본 presigned 업로드의 "완료 확정" 이 여기서 회수된다([[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]]).
- `verifyFoodTags` (`:255-263`) — 중복 id 거부, 그리고 `foodService.getReadyFoodsByIds(foodIds).size != foodIds.size` 면 거부. 즉 **`READY` 상태의 실제 음식만** 태그할 수 있다. 실패 시 `COMMUNITY-004`.
- 세 번째 겹은 엔티티 자신이다(`Posting.kt:46-52`) — 본문 공백 금지·2000자·사진 4장·태그 3개·태그 중복 금지를 `require` 로 건다. 요청 DTO 의 jakarta validation(`PostingCreateRequest.kt`)과 **같은 규칙이 두 번** 걸리는 셈인데, DTO 쪽은 HTTP 경계에서 400 을 빠르게 주기 위한 것이고 엔티티 쪽은 "어떤 경로로 만들어져도 깨진 글은 존재할 수 없다" 는 불변식이다.

> [!tip] FE 대비
> DTO 검증 = 폼 제출 전 클라이언트 유효성 검사, 엔티티 `require` = 상태를 만드는 팩토리 함수 안의 방어 코드. 둘 다 있어야 하는 이유가 같다 — 하나는 사용자에게 빨리 알려주려고, 하나는 잘못된 값이 저장소에 들어가는 걸 막으려고.

수정(`updatePosting`, `:52-66`)은 `getMyPosting` 으로 **소유자 확인 후**(`COMMUNITY-002`) 같은 검증을 다시 돌리고 `posting.update(...)` 를 부른다. 여기서 `save()` 를 부르지 않는다는 게 포인트다 — `@Transactional` 안에서 조회한 엔티티는 영속 상태이고, 필드를 바꾸면 커밋 시점에 변경 감지가 UPDATE 를 만든다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]).

삭제(`:68-71`)는 한 줄이다 — `getMyPosting(memberId, postId).delete()`. `delete()` 는 `BaseEntity` 의 소프트 삭제로 `status = DELETED` 만 바꾼다. 행은 남는다.

### `updatedAt` 이 있는데 왜 `editedAt` 을 또 두나

`Posting.kt:28-30` 에 주석이 붙어 있다(kbap 은 주석을 아끼는 레포라, 붙어 있으면 이유가 있다).

```kotlin
// 사용자 수정만 기록한다 — updatedAt 은 관리자 조치 등 모든 변경에 움직여 "(edited)" 표시 판별에 못 쓴다.
@Column(name = "edited_at")
var editedAt: LocalDateTime? = null
```

`updatedAt` 은 `@UpdateTimestamp` 라 소프트 삭제·관리자 조치 같은 **아무 변경에나** 움직인다. 화면에 "(수정됨)" 배지를 띄우는 판단에는 못 쓴다. 그래서 `update()` 안에서만 찍는 별도 컬럼을 뒀다. `Comment` 도 동일(`Comment.kt:25-27`).

## 4. 피드 읽기 — 커서 페이징과 게스트 게이트

커서 페이징의 원리(왜 offset 이 아니라 키셋인지, `PAGE_SIZE + 1` 로 `hasNext` 를 판정하는 이유, `Page` 봉투)는 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]] 와 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] §7 에 있고, **단순 id 커서**의 실물은 [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지]] §7 이 보여준다. 커뮤니티도 주문과 같은 단순 id 커서다 — 여기선 **커뮤니티에서만 다른 두 가지**만 본다.

### 4-1. 같은 패턴, 뒤집힌 부등호

피드는 최신순, 댓글은 등록순이다. 정렬 방향이 반대라 **커서 비교 부등호도 뒤집힌다.**

```kotlin
// PostingJpaRepository.kt:11-19 — 최신순
where (:cursor is null or p.id < :cursor)
order by p.id desc

// CommentJpaRepository.kt:11-20 — 등록순
where c.postId = :postId and c.parentId is null and (:cursor is null or c.id > :cursor)
order by c.id asc
```

커서는 둘 다 "직전 페이지의 마지막 id" 지만, 최신순에서는 그보다 **작은** id 가, 등록순에서는 **큰** id 가 다음 페이지다. 커서 파싱은 주문·리뷰와 같은 공용 유틸을 쓴다(`common/util/CursorParser.kt:7-10`) — 빈 문자열은 `null`(첫 페이지), 숫자가 아니거나 음수면 거절. **거절 코드가 `FOOD-002` 라는 함정**은 [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지]] §7 이 다룬다. 커뮤니티도 똑같이 걸린다 — `CommunityApi.kt:148` swagger 가 "잘못된 커서 형식(FOOD-002)" 이라고 적어뒀다.

응답 봉투는 공용 `Page<T>` 다(`api/core/Page.kt` — `items`/`hasNext`/`nextCursor: Long?`, 세 줄짜리 data class). 커뮤니티는 공용 봉투를 쓰는 쪽이고, 주문은 자체 DTO(`OrderListPage`, `nextCursor: String?`)를 따로 만든 쪽이다 — 공용 봉투가 있는데도 목록 API 마다 모양이 갈리는 실례다.

### 4-2. 게스트는 첫 페이지까지만

```kotlin
// CommunityService.kt:200-205
// 게스트는 첫 페이지만 — 커서가 있다는 것 자체가 두 번째 페이지 이후 요청이다.
private fun verifyGuestPageAccess(viewerMemberId: Long?, cursor: Long?) {
    if (viewerMemberId == null && cursor != null) {
        throw BusinessException(ErrorCode.COMMUNITY_LOGIN_REQUIRED)
    }
}
```

DB 질의 없는 널 체크 두 줄이다. **커서 값이 무엇이든 상관없다** — 게스트가 커서를 손으로 만들어 넣어 우회하는 길을 막는다(`specs/kb-291-community-feed-read/research.md:15`).

`COMMUNITY_LOGIN_REQUIRED("COMMUNITY-005", 401)` 은 토큰 오류(`AUTH-004` 등)와 **일부러 다른 코드**다. FE 가 이 코드로 "로그인하면 더 볼 수 있어요" 게이트 UI 를 띄운다. 토큰이 만료된 회원에게는 이 코드가 나가면 안 된다 — 그쪽은 refresh 후 재시도해야 하니까(`research.md:23-31`).

그래서 만료·위조 토큰은 **조용히 게스트로 강등되지 않는다.** `@AuthMemberIdOrNull` 은 이름과 달리 "토큰이 틀리면 null" 이 아니라 **예외**를 던진다(`AuthMemberIdOrNullArgumentResolver.kt:24-29`) — 헤더가 없거나 `Bearer` 형식이 아닐 때만 `null` 이다. 이 함정은 [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] §5 에서 이미 짚었다.

### 4-3. 탈퇴 작성자의 글은 목록에서 사라진다

```kotlin
// PostingJpaRepository.kt:10-19
// exists(Member) = 탈퇴 작성자 글 숨김 — Member 의 @SQLRestriction(ACTIVE)이 서브쿼리에도 적용된다.
and exists (select m.id from Member m where m.id = p.memberId)
```

연관관계가 없으니 `join` 이 아니라 `exists` 서브쿼리다. 그리고 `BaseEntity` 의 `@SQLRestriction("status = 'ACTIVE'")` 가 이 서브쿼리에도 붙어서, **탈퇴 회원은 애초에 매칭되지 않는다.** 판정 로직을 따로 쓰지 않고 소프트 삭제 규약을 재사용한 것이다. 상세 조회도 같은 정책을 `getVisiblePosting`(`:189-198`)에서 `existsById` 로 한 번 더 확인한다.

> 댓글은 정책이 다르다 — 탈퇴자의 **댓글은 남기고 작성자만 익명화**한다(`(삭제)` + `memberId: null`, `CommunityService.kt:113`, `:267-268`). 글은 사라지고 댓글은 남는다. 댓글이 사라지면 남의 대화 맥락이 끊기기 때문이다.

## 5. 조립 지점 하나 — 그리고 아직 없는 차단 필터

피드와 상세는 **같은 응답 타입**(`PostingItemResponse`)을 쓰고, **같은 함수**로 조립된다.

```kotlin
// CommunityService.kt:207-213
// 피드·상세 공용 단일 조립 지점 — 차단 필터·신고 숨김·번역 후속 태스크는 여기만 고친다.
private fun assemble(postings: List<Posting>, lang: LanguageCode): List<PostingItemResponse> {
    if (postings.isEmpty()) return emptyList()
    val authorsById = memberRepository.findAllById(postings.map { it.memberId }.toSet()).associateBy { it.id }
    val taggedFoodIds = postings.flatMap { it.foodIds.orEmpty() }.distinct()
    val foodsById = foodService.getReadyFoodsByIds(taggedFoodIds).associateBy { it.id }
    val commentCountByPostId = commentRepository.countByPostIds(postings.map { it.id })
        .associate { it.postId to it.commentCount }
```

**글이 20개든 1개든 쿼리 수가 같다.** 목록 1번 + 작성자 일괄 1번 + 음식 일괄 1번 + 댓글수 집계 1번 = 4번. 이게 9번 노트가 말한 "연관관계 없이 id 를 모아서 `IN` 으로 한 번에" 의 실물이다([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]). `getPosting`(상세)도 `assemble(listOf(...))` 로 같은 함수를 부른다 — 글 1개짜리 목록으로 취급한다.

> [!warning] 스펙과 다름 — `viewerMemberId` 는 아직 차단 필터가 아니다
> 계획서와 spec(`kb-291.../spec.md:9`)은 "차단·삭제 필터를 이후 태스크에서 적용할 수 있도록 조회 경로를 한 곳으로 모은다" 고 적었고, 실제로 그 **자리는 마련돼 있다**(위 주석). 하지만 **2026-08-26 실측 기준 커뮤니티 조회에는 차단 필터가 없다.**
> - `getPostingPage(viewerMemberId, ...)` 의 `viewerMemberId` 는 **§4-2 게스트 게이트 판정에만** 쓰이고, `assemble` 에는 전달조차 되지 않는다(`CommunityService.kt:74-84`).
> - `CommunityService` 의 생성자 의존 6개에 `MemberBlockService` 가 없다(`:22-30`).
> - 차단 필터가 실제로 도는 곳은 **리뷰뿐**이다 — `ReviewService.kt:177-178` 의 `excludedMemberIds(viewerMemberId)` = `memberBlockService.getBlockedMemberIds(viewerMemberId).ifEmpty { listOf(-1L) }`, 신고 숨김은 `excludedReviewIds`(`:180-183`).
>
> 즉 커뮤니티에서 `viewerMemberId` 는 **"누가 보느냐" 가 아니라 "회원이냐 게스트냐" 만** 가른다. 22번([[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]])에서 본 뷰어별 필터가 여기로 확장되면, 고칠 곳은 `assemble` 과 `findPage` 두 곳이다.

### 뷰어별 목록이 캐싱과 싸우는 이유

리뷰처럼 "차단한 사람을 뺀 목록" 을 주기 시작하면 **같은 URL 이 사람마다 다른 응답**을 낸다. 그러면 응답 단위 캐시는 키에 `viewerMemberId` 를 넣어야 하고, 캐시 적중률은 회원 수만큼 나뉜다 — 커뮤니티 피드가 아직 차단 필터를 안 갖고 있다는 건, 뒤집어 보면 **지금은 캐시를 붙일 수 있는 상태**라는 뜻이기도 하다. (이 이야기는 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식]]에서 이어진다. 참고로 kbap 에는 현재 `@Cacheable` 이 한 개도 없다.)

> [!note] `likeCount`·`dislikeCount` 는 하드코딩 0
> `assemble` 의 `likeCount = 0, dislikeCount = 0`(`:224-225`)은 리액션 기능 미도입이라 자리만 잡아둔 값이다. 반면 `commentCount` 는 KB-292 에서 실제 집계로 채워졌는데, **`PostingItemResponse.kt:29` 의 swagger 설명은 아직 "댓글 도입 전까지 0" 이라고 적혀 있다** — 문서만 낡았다. Swagger 를 그대로 믿으면 안 되는 실례.

## 6. 댓글과 대댓글 — 연관관계 없이 트리 만들기

여기가 이 노트의 핵심이다. `@OneToMany` 가 ArchUnit 으로 금지된 레포에서([[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]) 트리 구조를 어떻게 만드나.

### 6-1. 컬럼 하나 — `parent_id`

```kotlin
// Comment.kt:11-24
class Comment(
    @Column(name = "post_id", nullable = false) val postId: Long,
    @Column(name = "member_id", nullable = false) val memberId: Long,
    @Column(nullable = false, length = MAX_CONTENT_LENGTH) var content: String,
    // 대댓글이면 항상 최상위 댓글 id — 1depth 불변식은 저장 전 서비스 정규화가 보장
    @Column(name = "parent_id") val parentId: Long? = null,
) : BaseEntity() {
    val isReply: Boolean get() = parentId != null
```

객체 참조(`val parent: Comment?`)가 아니라 **`Long?` 컬럼**이다. `parentId == null` 이면 최상위 댓글, 아니면 대댓글. 타입이 아니라 값으로 종류가 갈린다.

DB 쪽에는 자기 참조 외래키가 실제로 걸려 있다.

```sql
-- V2026.08.05.03.35.30__community_comment_table.sql
CONSTRAINT fk_community_comment_parent FOREIGN KEY (parent_id) REFERENCES community_comment (id),
INDEX idx_community_comment_post_parent (post_id, parent_id, id),
INDEX idx_community_comment_parent (parent_id)
```

**DB 에는 관계가 있고, JPA 매핑에는 없다.** 무결성은 DB 제약이 지키고, 객체 그래프는 만들지 않는다. 이게 kbap 의 일관된 선택이다 — 관계를 부정하는 게 아니라, **관계를 따라 자동으로 쿼리가 나가는 걸** 부정한다.

인덱스 두 개도 뒤에 나올 쿼리 두 개와 정확히 짝이다: `(post_id, parent_id, id)` 는 §6-3 의 최상위 커서 조회, `(parent_id)` 는 대댓글 벌크 조회.

### 6-2. 깊이 제한 — "정규화" 라는 한 줄

유튜브식이다. 대댓글에 답글을 달아도 **트리가 깊어지지 않고** 같은 최상위 댓글 밑에 붙는다. 그 규칙이 사는 곳은 딱 한 함수다.

```kotlin
// CommunityService.kt:169-177
private fun resolveTopLevelParentId(postId: Long, parentCommentId: Long): Long {
    val parent = commentRepository.findById(parentCommentId).orElseThrow {
        BusinessException(ErrorCode.COMMUNITY_COMMENT_NOT_FOUND)
    }
    if (parent.postId != postId) {
        throw BusinessException(ErrorCode.COMMUNITY_COMMENT_NOT_FOUND)
    }
    return parent.parentId ?: parent.id
}
```

마지막 줄이 전부다 — **부모가 이미 대댓글이면 그 부모의 부모(= 최상위)를, 부모가 최상위면 자기 자신을** 반환한다. 저장되는 `parentId` 는 **항상 최상위 댓글 id** 다. 그래서 깊이는 구조적으로 2단을 넘을 수 없다. "3depth 를 막는 검사" 가 아니라 "3depth 가 만들어질 수 없는 저장 형태" 다.

중간의 `parent.postId != postId` 검사는 **다른 글의 댓글을 부모로 지정하는 요청**을 막는다. 경로의 `postId` 와 본문의 `parentCommentId` 가 각각 오니까, 둘이 같은 글에 속하는지 서버가 확인해야 한다.

> [!tip] FE 대비
> 화면에는 트리로 보이지만 저장은 **평평한 배열 + 부모 키**다. React 에서 중첩 컴포넌트를 그리면서 상태는 `{id, parentId}` 의 flat 배열로 들고, 그릴 때 `groupBy(parentId)` 하는 것과 같은 발상이다.

### 6-3. 조립 — 쿼리 3번으로 끝낸다

`getCommentPage`(`:91-137`)의 뼈대.

```kotlin
val rows = commentRepository.findTopLevelPage(postId, cursor, PageRequest.of(0, PAGE_SIZE + 1))   // ① 최상위 21건
val hasNext = rows.size > PAGE_SIZE
val page = rows.take(PAGE_SIZE)
val repliesByParentId = if (page.isEmpty()) emptyMap() else
    commentRepository.findByParentIdInOrderByIdAsc(page.map { it.id }).groupBy { it.parentId!! }  // ② 대댓글 일괄
val authorsById = memberRepository
    .findAllById((page + repliesByParentId.values.flatten()).map { it.memberId }.toSet())         // ③ 작성자 일괄
    .associateBy { it.id }
```

세 줄에 세 번의 쿼리. 그 뒤는 전부 메모리에서 `Map` 을 뒤지는 조립이다.

- **① 커서는 최상위 댓글에만 적용된다.** `parentId is null` 조건이 쿼리에 박혀 있다. 페이지 크기 20 은 "최상위 20개" 이지 "댓글 20개" 가 아니다.
- **② 대댓글은 페이징하지 않는다.** 이번 페이지의 최상위 20개 id 를 모아 `IN` 으로 한 번에 긁고 `groupBy` 한다. 즉 **대댓글이 300개 달린 댓글이 있으면 300개가 다 온다.** 현재 규모에서의 의도적 단순화이고, 문제가 되면 여기가 첫 수술 자리다.
- **③ 작성자도 최상위+대댓글을 합쳐 `toSet()` 한 뒤 한 번에.** 같은 사람이 여러 댓글을 달았어도 조회는 한 번이다.

만약 연관관계를 썼다면(`comment.replies`, `comment.member`), 이 코드는 훨씬 짧아 보이는 대신 20 × (1 + 대댓글 수) 번의 쿼리가 조용히 나갔을 것이다. **길어진 코드가 N+1 을 산 값**이다.

작성자를 못 찾은 경우(탈퇴)의 처리도 여기 있다.

```kotlin
// CommunityService.kt:106-113
fun authorOf(memberId: Long): CommentAuthorResponse =
    authorsById[memberId]?.let { … } ?: WITHDRAWN_AUTHOR
```

`Map` 에 없으면 `WITHDRAWN_AUTHOR`(`memberId = null`, `nickname = "(삭제)"`). §4-3 에서 본 "글은 숨기고 댓글은 익명화" 정책의 구현 지점이다.

### 6-4. 삭제 — 부모를 지우면 자식도 함께

```kotlin
// CommunityService.kt:160-167
@Transactional
fun deleteComment(memberId: Long, commentId: Long) {
    val comment = getMyComment(memberId, commentId)
    comment.delete()
    if (!comment.isReply) {
        commentRepository.softDeleteReplies(comment.id)
    }
}
```

`comment.delete()` 는 변경 감지로 나가는 UPDATE 한 건이고, `softDeleteReplies` 는 벌크 UPDATE 다.

```kotlin
// CommentJpaRepository.kt:34-36
@Modifying
@Query("update Comment c set c.status = com.kbap.common.domain.EntityStatus.DELETED where c.parentId = :parentId")
fun softDeleteReplies(@Param("parentId") parentId: Long)
```

대댓글이 몇 개든 **UPDATE 한 문장**이다. `cascade = REMOVE` 로 자동 전파시켰다면 자식을 전부 로딩한 뒤 한 건씩 지웠을 것이다.

> [!warning] 벌크 UPDATE 는 영속성 컨텍스트를 건너뛴다
> `@Modifying` 쿼리는 DB 에 직접 나가고, 이미 1차 캐시에 올라와 있는 `Comment` 인스턴스는 **옛 상태 그대로 남는다**. 같은 트랜잭션 안에서 그 대댓글을 다시 조회하면 `status = ACTIVE` 인 낡은 객체를 볼 수 있다. 여기서는 삭제 직후 아무것도 조회하지 않아 문제가 없지만, 이 함수 뒤에 코드를 붙일 사람은 알아야 한다. 자세한 원리는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]].

`isReply` 검사 덕에 **대댓글 단독 삭제는 형제를 건드리지 않는다.** 그리고 소프트 삭제라 `@SQLRestriction` 이 이후 모든 조회에서 알아서 걸러준다 — §6-3 의 세 쿼리 어디에도 "삭제 아님" 조건이 없는 이유다.

## 7. 조사: 게스트는 글은 읽는데 왜 댓글은 401 인가

[[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] §4 가 이 이상을 발견해 이 노트로 넘겼다. 사실관계부터 다시 확인하면 —

1. JWT 필터는 URL 패턴 `"/api/community/posts/*"` 에 등록돼 있다(`WebConfig.kt:92`). 서블릿 패턴 `*` 는 하위 경로를 다 잡으므로 `/api/community/posts/42/comments` 도 **필터가 돈다**.
2. 게스트 예외는 정규식 정확 일치다(`WebConfig.kt:72-75`) — `^/api/community/posts$`, `^/api/community/posts/\d+$`, `^/api/reviews$`. `/42/comments` 는 뒤가 남아 **매칭되지 않는다**.
3. 핸들러도 `@AuthMemberId`(필수)를 받는다(`CommunityController.kt:112-114`).

→ 게스트의 댓글 목록 요청은 필터 단계에서 `INVALID_ACCESS_TOKEN` 401 로 끝난다.

**판정: 누락이 아니라 스펙에 명시된 의도다.** 근거 —

| 근거 | 내용 |
|---|---|
| `specs/kb-292-community-comments/spec.md:89` (FR-010) | "게스트에게는 댓글 내용을 제공하지 않는다 — 목록 조회는 인증 오류로 거부하고, **댓글 개수만** 기존 피드·글 상세 응답으로 노출한다(블러 처리는 FE 책임)" |
| 같은 spec.md:46 (수용 시나리오) | "비회원(게스트)이 댓글 목록 조회를 시도하면 인증 오류로 거부된다" |
| `.../contracts/comments-api.md:5` | "인증: 4개 엔드포인트 전부 **회원 전용** — `@AuthMemberId`. `@AuthMemberIdOrNull` 사용처 없음" |

그리고 앞선 스펙(`kb-291.../spec.md:53`)도 상세를 정의하면서 미리 선을 그어뒀다 — "게스트도 본문·사진·태그·카운트를 모두 볼 수 있다. **댓글 목록 자체는 이번 범위가 아니다.**"

즉 설계 의도는 **"보이되 못 읽는다"** 다. 글과 댓글 수까지는 보여줘서 활기를 전달하고, 대화 내용은 로그인 유도의 미끼로 쓴다. 피드의 `COMMUNITY-005` 게이트와 같은 계열의 장치이고, 다만 **구현 수단이 다르다** — 피드는 서비스 로직이 게이트를 판정하고(전용 에러 코드), 댓글은 필터가 그냥 401 을 던진다.

> [!note] 그래서 남는 옥에 티 하나
> 게이트의 **에러 코드가 다르다.** 피드 2페이지는 `COMMUNITY-005`("로그인이 필요합니다")를 주는데, 댓글 목록은 `AUTH-003` 계열의 `INVALID_ACCESS_TOKEN` 을 준다. FE 입장에선 같은 "로그인하면 볼 수 있어요" 상황인데 분기 코드가 다르다. 스펙은 이걸 "기존 인증 오류" 로 의도했으므로 버그는 아니다 — 다만 `COMMUNITY-005` 를 만든 이유(`kb-291.../research.md:25`: "FE 가 이 코드로 로그인 게이트 UI 를 분기한다")를 생각하면 일관되지 않은 지점이다.

`getCommentPage` 의 `memberId` 파라미터가 서비스로 **전달되지 않는다**는 점도 짚어둘 만하다(`CommunityController.kt:113-119` → `communityService.getCommentPage(postId, cursor)`). 값을 쓰려고 받는 게 아니라 **`@AuthMemberId` 리졸버를 통과시키는 것 자체가 목적**이다. 인증을 "필요한 파라미터를 선언함으로써" 요구하는 방식이라, 파라미터를 지우면 조용히 인증이 사라진다. [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] §4 가 경고한 "URL 패턴 목록과 애너테이션을 손으로 맞춰야 한다" 의 또 다른 얼굴이다.

## 8. 요청/응답 실물

봉투는 전부 `BaseResponse<T>` — `{success, payload, message, code}`(`api/core/BaseResponse.kt`). 모든 요청에 `X-API-Version` 헤더가 필요하다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]).

### 글 작성

```http
X-API-Version: 1.0
Content-Type: application/json
```

```json
            "editedAt": "2026-08-27T11:05:00.000"
          }
        ]
      }
    ],
    "hasNext": false,
    "nextCursor": null
  }
}
```

### 답글 작성

```http
POST /api/community/posts/42/comments
{ "content": "저도 먹어봤는데 최고예요 @먹보", "parentCommentId": 87003 }
```

`87003` 은 대댓글인데, 응답의 `parentCommentId` 는 **최상위 댓글 id 로 정규화되어** 돌아온다(§6-2).

```json
{
  "success": true,
  "payload": {
    "commentId": 87004,
    "postId": 42,
    "parentCommentId": 87001,
    "content": "저도 먹어봤는데 최고예요 @먹보",
    "createdAt": "2026-08-27T11:07:00.000",
    "editedAt": null
  }
}
```

`@멘션` 은 **구조화 저장이 없다** — 본문 텍스트의 일부일 뿐이고 하이라이트는 FE 책임이다(`CommentCreateRequest.kt:8`).

## 12. 용어집

- **자기 참조(self-reference)**: 한 테이블의 컬럼이 같은 테이블의 행을 가리키는 것. 여기선 `community_comment.parent_id → community_comment.id`.
- **정규화(이 노트에서)**: DB 정규형이 아니라, 저장 전에 값을 **한 가지 표준 형태로 고쳐서** 저장하는 것. 여기선 "부모 id 는 항상 최상위 댓글 id" 로 맞추는 것.
- **게이트(gate)**: 기능을 막는 게 아니라 **더 보려면 조건을 채우라고 유도하는** 경계. `COMMUNITY-005` 가 그 신호다.
- **조립 지점(assembly point)**: 여러 소스에서 모은 데이터를 응답 모양으로 합치는 단일 함수. 나중에 필터를 끼울 자리를 한 곳으로 모아두는 설계.

## 13. 체크리스트

- [ ] 글 작성이 통과하는 검증 세 겹(이미지 소유 / 음식 태그 / 엔티티 불변식)을 순서대로 말할 수 있다
- [ ] `updatedAt` 이 있는데 `editedAt` 을 따로 둔 이유를 설명할 수 있다
- [ ] 최신순 커서와 등록순 커서의 부등호가 왜 반대인지 안다
- [ ] `resolveTopLevelParentId` 의 `parent.parentId ?: parent.id` 한 줄이 어떻게 깊이를 2단으로 고정하는지 설명할 수 있다
- [ ] 댓글 목록 조립이 왜 쿼리 3번으로 끝나는지, 연관관계를 썼다면 몇 번이 됐을지 말할 수 있다
- [ ] 커뮤니티에서 `viewerMemberId` 가 하는 일이 **게스트 판정뿐**이고 차단 필터는 리뷰에만 있다는 걸 안다
- [ ] "게스트는 글은 읽고 댓글은 401" 이 의도라는 근거를 스펙에서 짚을 수 있다
- [ ] 벌크 `@Modifying` UPDATE 가 영속성 컨텍스트를 건너뛴다는 게 왜 위험한지 안다
