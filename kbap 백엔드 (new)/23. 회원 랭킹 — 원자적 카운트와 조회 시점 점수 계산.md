# 23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산

> 작성: 2026-08-27 · 맥락: [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] 에서 리뷰 한 건이 저장될 때 **랭킹 원장에 행이 하나 남고 회원의 카운트가 오르는 것**까지 봤다. 그 카운트가 어떻게 점수가 되는지는 그 노트가 넘긴 자리다. 그런데 이 노트의 진짜 주제는 랭킹이 아니다 — **여러 요청이 같은 행을 동시에 건드릴 때 어떻게 안 깨지나** 다. FE 에서는 거의 만날 일이 없고, 서버에서는 매일 만나는 종류의 문제다.
> 목표: `count = count + 1` 을 **애플리케이션이 아니라 DB 에게 시키는 이유**를 lost update 로 설명할 수 있게 되고, 락 세 가지의 대가를 비교해 kbap 의 선택을 변호할 수 있게 되고, **원자성만으로는 못 막는 것**(같은 사건의 두 번 반영)을 unique 제약이 어떻게 막는지 말할 수 있게 되기.

---

## 0. 한 줄 요약

랭킹은 **저장하지 않는다.** `member` 행에는 원시 카운트 3개(`scan_count`·`review_count`·`unique_reviewed_food_count`)만 있고, 점수·등급·다음 등급은 **조회할 때마다 값 객체가 계산**한다. 그 카운트를 올릴 때는 엔티티를 읽어서 `+1` 하지 않고 **JPQL `UPDATE … SET c = c + 1` 한 방**을 DB 에 던진다 — 두 요청이 동시에 와도 하나가 사라지지 않게. 그리고 원자성만으로는 **같은 리뷰가 두 번 반영되는 것**을 못 막으므로, `member_ranking_event` 원장에 `uq(review_id, event)` unique 제약을 걸어 DB 가 멱등을 보장한다.

## 1. 개념표 — 이 노트에서 새로 나오는 말

| 말 | 뜻 | FE 에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| **lost update (갱신 유실)** | 두 작업이 같은 값을 각자 읽어 각자 고쳐 쓰면, 나중 쓰기가 앞 쓰기를 덮어써 **한 번의 변경이 사라지는** 현상 | `setCount(count + 1)` 을 두 곳에서 같은 렌더의 `count` 로 호출 → 2 늘 줄 알았는데 1 만 는다. React 가 `setCount(c => c + 1)` 함수형 업데이트를 권하는 이유가 정확히 이거다 |
| **원자적 UPDATE** | `SET c = c + 1` 처럼 **읽기와 쓰기를 DB 가 한 덩어리로** 처리하는 갱신문. 애플리케이션은 현재 값을 알 필요도 없다 | 함수형 업데이트의 서버판. "지금 값이 뭐든 1 더해" 라고 시키는 것 |
| **비관적 락 (pessimistic)** | "충돌이 날 것이다" 라고 보고 **읽는 순간 행을 잠가** 남이 못 건드리게 하는 방식 (`SELECT … FOR UPDATE`) | 편집 중인 문서에 다른 사람이 못 들어오게 아예 문을 잠그는 것 |
| **낙관적 락 (optimistic, `@Version`)** | "충돌은 드물 것이다" 라고 보고 잠그지 않되, **버전 숫자가 어긋나면 나중 것을 거절**하는 방식 | Git 이 push 를 거절하며 "먼저 pull 하라"고 하는 것. 자세히는 [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] §낙관적 락 |
| **멱등 (idempotent)** | 같은 요청을 두 번 처리해도 결과가 한 번과 같은 성질 | 같은 키로 `setQueryData` 를 두 번 = 한 번과 같은 상태 |
| **원장 (ledger)** | 잔액만 두지 않고 **거래 내역 행을 따로 남기는** 설계. 취소는 지우기가 아니라 반대 부호의 새 행 | Redux 의 액션 로그. 현재 state 만 보는 게 아니라 무엇이 언제 일어났는지 남긴다 |
| **값 객체 (value object)** | 식별자(id) 없이 **값만으로 정의되는** 객체. 같은 값이면 같은 것으로 취급하고, DB 행과 1:1 대응하지 않는다 | `{ score, tier }` 같은 순수 계산 결과 객체. `useMemo` 로 파생해 만드는 것과 비슷하다 |

## 2. 이 API 가 하는 일 — 사용자 관점 한 줄

사용자가 프로필 탭에서 **"나는 지금 explorer 3레벨, 128점, regular 까지 52점 남았다"** 를 보고, 그 카드를 누르면 **점수를 어디서 벌었는지 세 줄(리뷰·다양성·스캔)** 을 본다.

읽는 API 는 두 개다.

| 경로 | 무엇을 주나 |
|---|---|
| `GET /api/members/me/profile` | 프로필 정보 + **랭킹 요약**(등급·레벨·점수·다음 등급·남은 점수). 내역은 없다 |
| `GET /api/members/me/ranking` | 랭킹 요약 + **`breakdown`** (리뷰·다양성·스캔 각각의 개수와 점수) |

둘의 랭킹 값은 항상 같아야 한다. 같은 이유는 소박하다 — **둘 다 같은 값 객체 하나를 쓴다**(§5).

## 3. lost update — FE 에는 왜 이 문제가 없고 서버에는 있나

랭킹 카운트를 올리는 가장 자연스러운 코드는 이렇게 생겼다. **이건 kbap 코드가 아니라 반례다.**

```kotlin
@Transactional
fun increaseScanCount(memberId: Long) {
    val member = memberRepository.findById(memberId).orElseThrow()
    member.scanCount = member.scanCount + 1
}
```

[[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 에서 본 변경 감지 덕에 `save()` 조차 필요 없다. 한 명이 쓸 때는 완벽하게 동작한다.

문제는 **두 요청이 동시에 들어올 때**다. 서버는 요청마다 스레드를 하나씩 꺼내 쓰므로, 같은 회원의 스캔 두 건이 진짜로 동시에 돈다([[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]]).

```
scan_count = 5 인 상태

스레드 A                        스레드 B
─────────                       ─────────
SELECT → 5 를 읽음
                                SELECT → 5 를 읽음
5 + 1 = 6 계산
                                5 + 1 = 6 계산
UPDATE SET scan_count = 6
                                UPDATE SET scan_count = 6
                                            ↑ A 의 증가가 사라졌다

결과: 스캔은 2번 했는데 scan_count = 6
```

두 트랜잭션 모두 성공했고, 예외도 로그도 없다. **틀린 값이 조용히 남는다.** 이게 lost update 다.

> [!note] FE 개발자가 이걸 잘 안 만나는 이유
> React 앱에는 **사용자가 한 명**이고 **자바스크립트는 싱글 스레드**다. `count` 를 읽고 고치는 사이에 다른 코드가 끼어들 수가 없다. 그래도 React 가 `setCount(c => c + 1)` 을 권하는 이유는 다른 데 있다 — 이벤트 핸들러 안의 `count` 가 **렌더 시점의 낡은 스냅샷**이라서다. 원인은 다르지만 **처방은 정확히 같다: 현재 값을 읽어서 계산하지 말고, "1 더해라"라는 명령 자체를 넘겨라.**
>
> 서버에서 이 문제가 심각해지는 건 세 가지가 겹쳐서다. ①스레드가 200개다 ②그 사이에 네트워크·DB 지연이 끼어 창문이 밀리초가 아니라 수십 밀리초다 ③틀려도 아무도 예외를 안 던진다.

## 4. 해법 셋 — kbap 은 왜 원자적 UPDATE 를 골랐나

| 해법 | 어떻게 | 대가 | kbap |
|---|---|---|---|
| **① DB 원자적 UPDATE** | `UPDATE member SET scan_count = scan_count + 1 WHERE id = ?` — 읽기 없이 명령만 보낸다. DB 가 행 락을 UPDATE 실행 순간에만 잡고 즉시 놓는다 | **바뀐 후의 값을 모른다**(반환값은 "몇 행이 바뀌었나"뿐). 엔티티를 안 거치니 **영속성 컨텍스트와 어긋난다**(§6) | ✅ **채택** |
| **② 비관적 락** | `SELECT … FOR UPDATE` 로 읽는 순간 행을 잠그고, 트랜잭션이 끝날 때까지 남을 세워둔다 | 트랜잭션 **전체 길이** 동안 행이 잠긴다. 대기 줄이 생기고 커넥션이 묶이며, 여러 행을 다른 순서로 잠그면 **데드락** | ❌ 레포 전체에 `@Lock`·`PESSIMISTIC` 0건 |
| **③ 낙관적 락 (`@Version`)** | 행마다 버전 숫자를 두고, flush 때 버전이 어긋나면 예외로 거절 | **충돌 시 요청이 실패한다.** 재시도 로직을 부르는 쪽이 짜야 한다 | 🔸 `Food`·`Review` **두 엔티티에만**. `Member` 에는 없다 |

**①을 고른 이유는 이 갱신의 모양에 있다.**

- 갱신이 **`+1` 하나뿐**이다. "읽어서 판단하고 고친다"가 아니라 "무조건 1 더한다"이므로, 현재 값을 알 필요가 자체가 없다. ②·③은 **현재 값을 봐야 할 때** 필요한 도구다.
- **충돌해도 둘 다 성공해야 맞다.** 두 스캔은 실제로 둘 다 일어났으니 답은 `+2` 다. ③은 이런 자리에서 한쪽을 실패시켜 버리는데, 그건 틀린 처방이다. ③이 옳은 자리는 *"내가 본 값을 기준으로 고쳤는데 그새 값이 바뀌었다면 내 판단이 무효"* 인 경우다 — 그래서 `Food`(배치가 이미지·설명을 채우는 동안 회수 잡이 같은 행을 건드림)에는 `@Version` 이 붙어 있다.
- **가장 짧게 잠근다.** ①의 락은 UPDATE 문 실행 순간뿐이고, ②는 트랜잭션이 커밋될 때까지다. 리뷰 작성 트랜잭션은 이미지 검증·리뷰 저장·원장 저장을 다 하므로 결코 짧지 않다.

> [!tip] 판단 규칙 하나로 줄이면
> **"현재 값을 안 봐도 되는 갱신이면 ①."** 값을 보고 판단해야 하면 ③(충돌이 드물 때)이나 ②(잦고 대기가 나은 때)로 간다. `+1`·`-1`·`= true` 처럼 절대적인 갱신이 ①의 영역이다.

서비스 본체는 이게 전부다.

```kotlin
@Transactional(readOnly = true)
fun getRanking(memberId: Long): MemberRankingResult =
    MemberRankingResult.from(getMember(memberId).ranking)
```
`api/member/MemberService.kt:57-59`

- `getMember` 는 **`MemberStatus.ACTIVE` 인 회원만** 찾고, 없으면 `MEMBER_NOT_FOUND`(:130-132). 탈퇴 회원은 유효한 토큰이 있어도 랭킹이 안 나온다.
- `readOnly = true` 는 [[6. 설정과 프로필, 트랜잭션 경계]] 의 규약. 읽기 전용 트랜잭션은 flush 를 건너뛰어 변경 감지 비용이 없다.
- 계산은 **서비스에 한 줄도 없다.** `member.ranking` 이 이미 다 계산된 값 객체를 준다.

### 계산은 값 객체 안에서 끝난다

```kotlin
class Ranking private constructor(
    val scanCount: Int, val reviewCount: Int, val uniqueReviewedFoodCount: Int,
) {
    val reviewPoints: Int = reviewCount * REVIEW_POINTS
    val diversityPoints: Int = uniqueReviewedFoodCount * DIVERSITY_POINTS
    val scanPoints: Int = scanCount * SCAN_POINTS
    val score: Int = reviewPoints + diversityPoints + scanPoints
    val tier: RankingTier = RankingTier.of(score)
    val nextTier: RankingTier? = tier.next
    val pointsToNext: Int? = nextTier?.let { it.minScore - score }
```
`common/domain/member/model/Ranking.kt:3-18`

- 전부 `val` 프로퍼티 초기화다 — 객체가 만들어지는 순간 7개 값이 확정되고, 그 뒤로는 변하지 않는다.
- `private constructor` + `companion object { fun of(...) }` — 생성 통로를 하나로 막고, 거기서 **음수 카운트를 거절**한다(:28-30). 도메인 불변식을 값 객체가 스스로 지킨다.
- **`@Entity` 가 아니다.** 테이블도 id 도 없다. `Member` 엔티티가 게터에서 만들어 내는 순수 계산 결과다 → [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]]

가중치는 `Ranking.kt:21-23` 에 상수로 박혀 있다: **리뷰 10점 · 다양성 5점 · 스캔 2점.**

```kotlin
enum class RankingTier(val level: Int, val minScore: Int) {
    NEWCOMER(1, 0), TASTER(2, 30), EXPLORER(3, 80), REGULAR(4, 180),
    GOURMET(5, 350), KFOOD_MASTER(6, 600), KOREAN_AT_HEART(7, 1000);

    val key: String = name.lowercase()
    val next: RankingTier? get() = entries.getOrNull(ordinal + 1)

    companion object {
        fun of(score: Int): RankingTier = entries.last { score >= it.minScore }
    }
}
```
`common/domain/member/model/RankingTier.kt:3-20`

- `of` 는 **조건을 만족하는 마지막 항목**을 고른다. enum 선언 순서가 곧 점수 오름차순이므로, 구간 테이블도 이분 탐색도 필요 없다. 대신 **선언 순서를 뒤섞으면 조용히 망가진다.**
- `key = name.lowercase()` — API 는 `"explorer"` 를 준다. 한국어·영어 등급 이름은 **서버가 만들지 않는다.** 번역은 FE 책임이라는 계약이다(spec FR-004).
- 최고 등급이면 `next` 가 null → `pointsToNext` 도 null. FE 는 이 두 개가 null 이면 진행바를 그리지 않는다.

## 6. 쓰기 경로 — 카운트가 오르는 다섯 개의 문

점수에 기여하는 카운트는 **3개**이고, 그걸 건드리는 메서드는 **5개**다. 전부 `MemberService` 에 있고, 전부 리포지토리의 JPQL UPDATE 한 방으로 끝난다.

| 메서드 (`MemberService.kt`) | 리포지토리 (`MemberJpaRepository.kt`) | 부르는 곳 |
|---|---|---|
| `increaseScanCount` :89-94 | `increaseScanCount` :22-31 | `api/scan/ScanFacade.kt:32`(v1), `:49`(v2) |
| `increaseReviewCount` :96-101 | `increaseReviewCount` :33-42 | `api/review/ReviewService.kt:62` |
| `decreaseReviewCount` :103-108 | `decreaseReviewCount` :44-54 | `api/review/ReviewService.kt:119` |
| `increaseUniqueReviewedFoodCount` :110-115 | :56-65 | `api/review/ReviewService.kt:80` |
| `decreaseUniqueReviewedFoodCount` :117-122 | :67-77 | `api/review/ReviewService.kt:122` |

> [!important] 점수 기여 요소 — 옛 노트의 "스캔만 기여" 는 이제 거짓이다
> 2026-07 시점 노트와 KB-123 스펙은 *"리뷰 도메인이 없어 reviews·diversity 는 항상 0"* 이라고 적었다. **지금은 셋 다 살아 있다** — `ReviewService.createReview`(:62, :80)·`deleteReview`(:119, :122)가 네 메서드를 전부 호출한다. 리뷰가 랭킹에 실제로 반영된다. 적재 흐름은 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] 이 정본이다.

### 다섯 개가 전부 같은 모양이다

```kotlin
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query(
    """
    update Member m
    set m.scanCount = m.scanCount + 1
    where m.id = :memberId
      and m.memberStatus = com.kbap.common.domain.member.model.MemberStatus.ACTIVE
    """,
)
fun increaseScanCount(@Param("memberId") memberId: Long): Int
```
`common/domain/member/MemberJpaRepository.kt:22-31`

한 줄씩 풀면:

- **`update Member m`** — 테이블이 아니라 **엔티티 이름**이다. JPQL 이므로 Hibernate 가 `member` 테이블로 번역한다.
- **`set m.scanCount = m.scanCount + 1`** — §3 의 반례와 결정적으로 다른 지점. 애플리케이션이 현재 값을 읽지 않는다. DB 가 읽기와 쓰기를 한 문장 안에서 한다.
- **`and m.memberStatus = … ACTIVE`** — 탈퇴·정지 회원은 갱신되지 않는다. WHERE 조건이 곧 인가 검사다.
- **`@Modifying`** — Spring Data 에 "이건 SELECT 가 아니라 갱신문" 이라고 알린다. 없으면 실행조차 안 된다.
- **반환 `Int`** — **바뀐 행 수**다. 새 카운트 값이 아니다. 이게 ①의 대가다(§4).

`decrease` 두 개에는 조건이 한 줄 더 붙는다.

```
where m.id = :memberId
  and m.reviewCount > 0
  and m.memberStatus = … ACTIVE
```
`MemberJpaRepository.kt:48-51`

**하한 가드를 애플리케이션이 아니라 WHERE 절로 걸었다.** `if (member.reviewCount > 0)` 로 짰다면 그 확인과 감소 사이에 다시 틈이 생겼을 것이다(check-then-act — [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] §6 이 같은 함정을 Redis 쪽에서 다룬다). 조건을 UPDATE 안에 넣으면 확인과 감소가 같은 원자 연산 안에 들어간다. 카운트가 0이면 **0행이 갱신되고 값은 그대로**다.

### 0행이면 예외 — 그런데 에러 코드가 하나뿐이다

```kotlin
@Transactional
fun increaseScanCount(memberId: Long) {
    if (memberRepository.increaseScanCount(memberId) == 0) {
        throw BusinessException(ErrorCode.MEMBER_NOT_FOUND)
    }
}
```
`api/member/MemberService.kt:89-94`

반환값이 새 카운트가 아니라 행 수라는 사실이 여기서 쓸모를 얻는다 — **0이면 WHERE 를 만족한 행이 없었다**는 뜻이니, 회원이 없거나 탈퇴했거나(증가) 카운트가 이미 0이었다(감소).

> [!warning] `decrease` 의 `MEMBER_NOT_FOUND` 는 이름이 사실과 다르다
> `decreaseReviewCount` 가 0을 반환하는 경우는 **두 가지**다 — ①회원이 없다 ②회원은 멀쩡한데 `reviewCount` 가 이미 0이다. 둘 다 `MEMBER_NOT_FOUND` 로 나간다. 테스트가 이 동작을 의도로 못박아 두긴 했다(`MemberServiceReviewCountTest.kt:80-91`, *"하한 가드로 MEMBER_NOT_FOUND 를 던지고 0 이 유지된다"*). 이 경로는 현재 사용자에게 직접 노출되지 않고 리뷰 삭제 트랜잭션 안에서만 도므로 영향이 작지만, 로그에서 원인을 가려낼 수는 없다.

### `clearAutomatically` · `flushAutomatically` 는 왜 필요한가

원자적 UPDATE 는 **영속성 컨텍스트를 우회한다.** DB 행은 바뀌었는데 1차 캐시에 들고 있는 `Member` 객체는 옛 카운트를 그대로 기억한다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]). 두 옵션이 그 어긋남을 앞뒤로 메운다.

| 옵션 | 언제 | 무엇을 |
|---|---|---|
| `flushAutomatically = true` | UPDATE **전** | 컨텍스트에 쌓인 변경을 먼저 DB 에 밀어넣는다. 안 하면 UPDATE 뒤에 늦게 flush 되며 방금 갱신한 컬럼을 옛 값으로 덮을 수 있다 |
| `clearAutomatically = true` | UPDATE **후** | 컨텍스트를 비운다. 이후 같은 트랜잭션에서 회원을 다시 읽으면 **DB 에서 새로** 읽어 새 카운트를 본다 |

순서가 flush → UPDATE → clear 이므로 **미저장 변경이 유실되지 않는다.** 이 짝이 없으면 원자적 UPDATE 는 lost update 를 막는 대신 **다른 종류의 어긋남**을 만들어 낸다.

> [!note] 이 옵션이 실제로 일을 하는 자리
> **`flushAutomatically`**: 리뷰 삭제는 `review.delete()` 로 소프트 삭제를 표시한 **직후** `decreaseReviewCount` 를 부른다(`api/review/ReviewService.kt:117-119`). 그 표시는 아직 DB 에 안 갔다 — flush 가 UPDATE 전에 밀어넣어 준다.
>
> **`clearAutomatically` 의 청구서**: `createReview` 는 회원을 `:61` 에서 한 번 읽고, 카운트 UPDATE 두 개를 지난 뒤 `authorOf` 에서 또 읽는다(`:83` → `:283`). 원래대로면 두 번째는 1차 캐시가 공짜로 답할 자리인데, **UPDATE 가 캐시를 비워버려 DB 를 다시 친다.** 원자적 UPDATE 의 대가는 "새 값을 모른다"만이 아니라 **같은 트랜잭션의 캐시가 날아간다**는 것이기도 하다.
>
> 자세한 순서는 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]].

## 7. 20번과의 대비 — 같은 문제, 다른 해법

[[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] 도 결국 "동시에 오는 요청이 카운트를 망치는 것"을 막는 노트다. 그런데 도구가 다르다. **문제의 모양이 달라서** 도구가 다르다.

| | 20번 — Redis Lua 예약 | 23번 — DB 원자적 UPDATE |
|---|---|---|
| 막는 것 | **한도 초과**(3회 무료를 4번 쓰기) + 중복 요청 | **갱신 유실**(2번 했는데 1만 오름) |
| 질문의 모양 | "지금 몇 개 있나 **보고**, 여유 있으면 넣는다" — check-then-act | "무조건 1 더한다" — 현재 값이 필요 없다 |
| 원자성 제공자 | Redis 가 Lua 스크립트를 **단일 스레드로 통째 실행** | DB 가 UPDATE 문 하나를 **행 락 안에서 실행** |
| 되돌리기 | 있다 — 실패하면 `release` 로 슬롯 반납 | 없다 — 반대 부호 UPDATE 를 따로 부른다(`decrease*`) |
| 남는 흔적 | TTL 이 지나면 사라짐 (일시 예약) | 영구 (확정된 카운트) |
| 실패했을 때 | 슬롯이 묶였다가 TTL 로 풀림 | 0행 갱신 → 예외 |
| 왜 이걸 골랐나 | 값을 **보고 판단**해야 하므로 읽기·쓰기를 한 덩어리로 묶을 도구가 필요 | 값을 볼 필요가 없으므로 **DB 의 기본 원자성**으로 충분 |

**같은 요청 하나가 두 장치를 순서대로 통과한다.** v2 스캔은 ①Redis 예약(한도 확인, 일시적) → ②비전 LLM 호출 → ③`increaseScanCount`(확정, 영구) 순이다(`api/scan/ScanFacade.kt:36-56`). Redis 는 *"이 회원이 지금 한 칸 쓰는 중"* 을, DB 는 *"이 회원이 총 몇 번 썼는가"* 를 기록한다. 20번 노트가 왜 예약을 `scan_count` 로 선점하지 않았는지를 정리해 뒀다 — **처리 중인 값이 랭킹 데이터를 순간 오염**시키기 때문이다. 이 노트의 카운트가 랭킹 점수의 원료라는 사실이 그 결정의 근거였다.

> [!tip] 고르는 기준 한 줄
> **현재 값을 봐야 하면 그 읽기·쓰기를 감쌀 도구(Lua·락)가 필요하고, 안 봐도 되면 DB 원자 UPDATE 로 끝난다.**

## 8. 원자성만으로는 못 막는 것 — 원장과 unique 제약

여기가 이 노트의 두 번째 반전이다.

**`SET c = c + 1` 이 완벽히 원자적이어도, 그 문장이 두 번 실행되면 카운트는 여전히 틀린다.** 원자성은 "동시에 실행돼도 둘 다 반영된다"를 보장할 뿐, "이 사건이 두 번 반영되면 안 된다"에 대해서는 아무 말도 하지 않는다. 오히려 정직하게 두 번 다 반영해 준다.

같은 리뷰가 두 번 반영되는 경로는 현실적이다 — 앱이 응답을 못 받고 재시도했다, 삭제 요청이 중복으로 들어왔다, 배치가 같은 구간을 다시 돌았다.

**§6 의 `> 0` 가드는 이걸 못 막는다.** 그 가드가 하는 일은 카운트를 **음수로 떨어뜨리지 않는 것**뿐이다. 리뷰 5개를 쓴 회원의 삭제가 두 번 반영되면 카운트는 3이 되고, 3은 음수가 아니므로 가드가 통과시킨다. **틀렸지만 그럴듯한 값**이라 아무도 눈치채지 못한다. 가드는 값의 범위를 지키고, 멱등 장치는 값의 **정확성**을 지킨다 — 다른 일이다.

kbap 은 이걸 **잔액이 아니라 원장으로** 푼다. `member` 의 카운트 컬럼이 잔액이라면, `member_ranking_event` 테이블은 거래 내역이다 — 리뷰 한 건이 랭킹에 준 영향을 행으로 남기고, 취소는 반대 부호의 새 행으로 적는다. 그 테이블에 이 제약이 걸려 있다.

```sql
UNIQUE KEY `uq_member_ranking_event` (`review_id`, `event`),
```
`api/src/main/resources/db/migration/V2026.07.30.13.58.27__member_ranking_event_table.sql:15`

**원장에 무엇이 어떻게 적히는지**(델타 값, 언제 어떤 조건으로 행이 만들어지는지)는 [[22. 리뷰 작성 흐름 — 쓰기 경로와 랭킹 원장]] §6 이 정본이다. 여기서는 **왜 그게 필요한가**만 본다.

**unique 제약이 멱등 장치인 이유**: `(review_id, event)` 조합은 테이블 전체에 최대 한 행이다. 같은 리뷰의 `REVIEW_CREATED` 를 두 번 넣으려 하면 **두 번째 INSERT 가 DB 에서 거절**되고, 그 INSERT 가 든 트랜잭션이 통째로 롤백되면서 **같은 트랜잭션의 카운트 UPDATE 도 함께 되돌아간다.** 중복 반영을 애플리케이션이 아니라 DB 가 막는다.

> [!important] 왜 애플리케이션 코드로 막지 않나
> `if (이미 반영됐나) return` 은 §3 과 똑같은 함정이다 — 확인과 삽입 사이에 다른 요청이 끼어들면 둘 다 통과한다. **DB 제약은 이 틈이 없다.** 확인과 삽입이 한 연산이기 때문이다. 애플리케이션 쪽 확인(`existsByReviewIdAndEvent`)은 여전히 있지만, 그건 **좋은 에러 메시지를 주기 위한 것**이지 안전장치가 아니다. 안전장치는 제약이다.
>
> 같은 패턴을 이미 봤다: 소셜 가입의 unique 인덱스 + `DataIntegrityViolationException` 폴백(`MemberService.kt:77-87`, [[16. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]])과 주문의 `imagePath` unique 충돌 처리다. **"경합은 DB 제약으로 막고, 코드는 그 예외를 받아 처리한다"** 가 이 레포의 반복되는 관용구다.

두 가지만 짚고 넘어간다.

- **`event` 를 unique 키에 포함한 이유**: 같은 리뷰가 `CREATED` 1행 + `DELETED` 1행을 가질 수 있어야 한다. `review_id` 만으로 걸면 **삭제를 아예 기록할 수 없다.** 막고 싶은 건 "같은 리뷰의 재등장"이 아니라 "**같은 사건**의 재등장"이다.
- `MemberRankingEventJpaRepository` 는 메서드가 **하나뿐**이다 — `existsByReviewIdAndEvent`(`common/domain/member/MemberRankingEventJpaRepository.kt:8`). **원장을 읽어서 점수를 계산하는 코드는 레포에 없다.** 원장은 쓰기만 하고, 점수는 잔액에서 나온다.

> [!note] 원장이 있는데 왜 점수는 잔액에서 뽑나
> 원장을 합산하면(`SUM(review_count_delta)`) 카운트 컬럼 없이도 점수를 낼 수 있고 정합성은 더 강하다. kbap 은 그렇게 하지 않는다 — 원장은 **감사·복구·중복 차단**용이고, 조회는 잔액 컬럼 한 번 읽기다. 회원 한 명의 이벤트가 수천 행으로 늘어도 조회 비용이 그대로이기 때문이다. 대가는 **잔액과 원장이 어긋날 수 있다**는 것이고, 그 대비책이 "둘을 같은 트랜잭션에 묶는다"이다(§10).

## 9. 조회 시점 계산 vs 미리 저장 — 실측과 대가

**실측: `member` 테이블에 `score` 도 `tier` 도 없다.** 마이그레이션 49개를 통틀어 두 컬럼명은 한 번도 나오지 않는다. 있는 건 원시 카운트 3개뿐이다(`V2026.07.16.21.38.41__init_schema.sql:47-49`). 점수와 등급은 매 조회마다 `Ranking` 값 객체가 만들어 낸다.

| | 조회 시점 계산 (kbap) | 미리 저장 (score 컬럼) |
|---|---|---|
| 정합성 | **항상 맞다.** 카운트가 오른 다음 순간의 조회는 반드시 새 점수 | 카운트 갱신과 score 갱신이 어긋날 수 있다 |
| 가중치 변경 | 상수 한 줄 고치고 배포 → **전 회원 즉시 반영** | 전 회원 재계산 배치가 필요 |
| 본인 조회 비용 | 행 하나 읽고 곱셈 세 번 — 사실상 0 | 같음 |
| **정렬·상위 N** | **비싸다.** `ORDER BY (r*10 + u*5 + s*2) DESC` 는 계산식이라 **인덱스를 못 탄다** → 전체 스캔 | 싸다. `score` 에 인덱스 걸고 `ORDER BY score DESC LIMIT 100` |

**kbap 은 랭킹 목록(리더보드) API 가 없다.** `MemberController` 에 상위 N 을 뽑는 매핑이 없고, `MemberJpaRepository` 에 정렬 조회 메서드가 없고, 레포 전체에 `leaderboard` 문자열이 0건이다. 랭킹은 **본인 것만 본다** — spec FR-009 가 *"인증된 회원 본인의 값만 제공한다. 타인의 랭킹은 조회할 수 없다"* 로 못박아 뒀다.

**그래서 조회 시점 계산이 공짜다.** 위 표에서 유일하게 비싼 칸이 리더보드인데, 그 기능이 없기 때문이다. 요구사항이 "본인 것만"인 한 이 선택은 순수한 이득이다.

> [!warning] 리더보드가 생기면 이 설계가 흔들린다
> 상위 100명을 뽑아야 하는 순간 세 갈래가 생긴다 — ①정렬용 `score` 컬럼을 **추가**하고 5개 UPDATE 에 `score = score + N` 을 얹는다(계산이 두 곳으로 갈라지는 대가) ②배치로 주기적으로 스냅샷을 만든다(실시간성 포기) ③Redis Sorted Set 으로 옮긴다. **지금 구조에 그대로 `ORDER BY` 를 붙이는 선택지는 없다** — 회원 수만큼 전체 스캔이 돈다.
>
> ①이 가장 유력한 이유는 §6 의 UPDATE 다섯 개가 이미 **모든 카운트 변경이 반드시 지나는 좁은 문**이기 때문이다. 20번 노트가 짚은 `scan_unlocked` 도 정확히 그 성질을 이용해 기존 UPDATE 에 얹혔다(`MemberJpaRepository.kt:37`).

## 10. 경계를 넘는 지점

| 경계 | 어디서 | 왜 넘나 |
|---|---|---|
| `:api` → `:common` | `MemberService` → `MemberJpaRepository`·`Member`·`Ranking` | 도메인 모델과 리포지토리는 `:common`, 유스케이스 조립과 응답 DTO 는 `:api`. 배치 앱도 같은 엔티티를 쓴다 → [[11. 모듈러 모놀리스와 DDD — 3모듈과 도메인 패키지]] |
| 도메인 ↔ 응답 | `Ranking` → `MemberRankingResult` → `MemberRankingResponse` | `Ranking` 은 평평한 7개 값, 응답은 `breakdown` 으로 묶인 모양. **API 계약을 도메인 모양에 종속시키지 않으려는 한 겹** → [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] |
| 컨텍스트 간 | `review` → `member` | `ReviewService` 가 `MemberService` 를 **주입받아 직접 호출**한다. 이벤트나 큐가 아니라 같은 프로세스·같은 트랜잭션의 메서드 호출이다 |
| 외부 시스템 | **없다** | 이 흐름에 `common.port.*` 가 하나도 안 걸린다. DB 만 만진다. 그래서 흐름이 짧다 |

**트랜잭션 경계**가 이 노트에서 가장 중요한 경계다.

| 경로 | 트랜잭션 | 안에 뭐가 들어가나 |
|---|---|---|
| 랭킹 조회 | `MemberService.getRanking` `@Transactional(readOnly = true)` | SELECT 한 방 |
| 리뷰 작성 | `ReviewService.createReview` `@Transactional` | 자격 검증 · 리뷰 저장 · **카운트 UPDATE 2개** · **원장 INSERT** |
| 스캔 확정 | **없다** — `ScanFacade` 에 `@Transactional` 이 없다 | `increaseScanCount` **자기 트랜잭션 하나**뿐 |

- **리뷰 쪽은 한 트랜잭션이다.** `increaseReviewCount` 의 `@Transactional` 은 기본 전파(`REQUIRED`)라 **바깥 트랜잭션에 합류**한다. 그래서 원장 INSERT 가 unique 제약에 걸려 실패하면 **카운트 UPDATE 도 같이 롤백**된다. §8 의 멱등 보장이 성립하는 근거가 바로 이 합류다.
- **스캔 쪽은 일부러 트랜잭션이 없다.** `ScanFacade` 는 수 초 걸리는 LLM 호출을 하므로, 트랜잭션으로 감싸면 DB 커넥션을 그동안 붙잡는다(20번 노트 §트랜잭션). `increaseScanCount` 만 자기 트랜잭션으로 짧게 돈다.
- **`@Transactional` 은 프록시로 동작하므로 같은 클래스 안 호출에는 안 붙는다.** `MemberService` 안에는 그 함정의 실물이 있다(`completeOnboarding` → `getMember`) — [[15. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]] 가 정본이다. 랭킹 경로는 컨트롤러가 `getRanking` 을 **밖에서** 부르므로 정상적으로 프록시를 탄다.

## 16. 용어집

- **lost update (갱신 유실)**: 두 트랜잭션이 같은 값을 각자 읽어 각자 고쳐 쓸 때, 나중 쓰기가 앞 쓰기를 덮어써 변경 하나가 사라지는 현상. 예외가 안 나므로 조용히 틀린다.
- **원자적 UPDATE**: `SET c = c + 1` 처럼 읽기와 계산과 쓰기를 DB 가 한 문장으로 처리하는 갱신. 애플리케이션이 현재 값을 알 필요가 없다.
- **비관적 락**: 읽는 순간 행을 잠가 남의 접근을 막는 방식. 트랜잭션 끝까지 잠기고 데드락 위험이 있다.
- **낙관적 락(`@Version`)**: 행마다 버전 숫자를 두고 동시 수정이 겹치면 나중 것을 flush 때 거절하는 방식. kbap 은 `Food`·`Review` 두 엔티티에만 쓴다.
- **check-then-act**: "확인하고 → 실행한다" 사이의 틈에 다른 요청이 끼어들어 확인 결과가 낡아버리는 버그 유형.
- **멱등(idempotent)**: 같은 요청을 두 번 처리해도 결과가 한 번과 같은 성질.
- **원장(ledger)**: 잔액뿐 아니라 거래 내역 행을 남기는 설계. 취소는 삭제가 아니라 반대 부호의 새 행.
- **값 객체(value object)**: 식별자 없이 값만으로 정의되는 객체. DB 행과 대응하지 않고, `Ranking` 처럼 계산 결과를 담는다.
- **`@Modifying`**: Spring Data JPA 에서 이 쿼리가 SELECT 가 아니라 갱신문임을 알리는 애너테이션.
- **JPQL**: 테이블·컬럼이 아니라 **엔티티·필드 이름**으로 쓰는 쿼리 언어. Hibernate 가 SQL 로 번역한다.

> [!note] 2026-08-27 역링크 — 같은 "두 번 해도 한 번" 을 **다른 수단**으로 푼 실물
> 이 노트의 `uq_member_ranking_event` 는 **DB unique 제약**으로 같은 리뷰 이벤트가 두 번 점수를 더하는 걸 막는다. 같은 문제를 제약 없이 푸는 쪽이 있다 → [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §8. 콘텐츠 적재 API 는 `UPDATE ... WHERE outbox_status IN ('PENDING','SENT')` 의 **갱신 행 수**로 판정한다 — 1이면 이번 호출이 닫은 것, 0이면 이미 `COMPLETE` 이므로 `409 FOOD-004`.
> **왜 갈리나**: 랭킹은 "이 이벤트가 이미 반영됐나" 를 물을 대상이 행의 **존재** 여부라 unique 가 맞고, 아웃박스는 물을 대상이 행의 **상태** 라 `WHERE` 조건이 맞다. 원리는 하나 — 두 번째 시도가 조용히 아무 일도 안 하거나 명확히 거절되게 만든다.
> 이 노트 §4 의 "원자 UPDATE 한 문장 = 읽고-판단하고-쓰기의 틈 제거" 도 아웃박스 상태 전이에서 그대로 반복된다. 특히 `CASE WHEN ... THEN 'SENT' ELSE outbox_status END` 는 **전이가 앞으로만 가게** 만드는 장치다 — 늦게 도착한 발행 응답이 이미 `COMPLETE` 인 행을 `SENT` 로 되돌리지 못한다.
> **409 를 실패로 읽으면 안 된다**는 계약도 짚어둘 만하다. "이미 처리됐다" 는 정상 종료 신호이므로 호출자는 재시도·DLQ 대상에서 제외한다.
