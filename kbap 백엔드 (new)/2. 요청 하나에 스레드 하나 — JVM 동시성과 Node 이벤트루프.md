# 2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프

> 작성: 2026-08-27 · 맥락: 앞 노트에서 "서버는 켜두고 요청을 기다리는 프로그램"까지 왔다. 그런데 **요청이 동시에 100개 오면 그 하나의 프로세스가 어떻게 100개를 처리하나?** 여기서 JS와 JVM의 답이 완전히 갈린다.
> 목표: 읽고 나면 (1) kbap 서버가 요청 하나마다 스레드를 하나씩 쓴다는 걸 설명할 수 있고, (2) 그래서 서비스 코드에서 DB·LLM을 **그냥 기다려도 되는** 이유를 알고, (3) 대신 새로 생기는 문제(여러 스레드가 같은 데이터를 건드림)가 뭔지 말할 수 있다.
> 기준: kbap-server 실측 2026-08-27 · Spring Boot 4.1.0 / Kotlin 2.3.21 / Java 21 (`gradle/libs.versions.toml:2-4`)

---

## 0. 한 줄 요약

**JS는 스레드 하나가 이벤트루프를 돌며 전부 처리하고, JVM 서버는 요청 하나마다 스레드를 하나씩 꺼내 준다.** 그래서 JS에서는 재앙인 "그냥 기다리기(블로킹)"가 JVM에서는 정상 코드이고, 대신 JS엔 거의 없던 **"두 스레드가 같은 데이터를 동시에 건드린다"** 는 문제가 새로 생긴다.

## 1. 핵심 개념

| 용어 | 정체 | FE에서 가장 가까운 것 (완전 동치 아님) |
|---|---|---|
| **프로세스** | 실행 중인 프로그램 하나. 자기 메모리를 가진다 | 실행 중인 Node 앱 하나 |
| **스레드(thread)** | 프로세스 **안에서** 코드를 한 줄씩 실행하는 실행 흐름. 같은 프로세스의 메모리를 **공유**한다 | JS에는 사실상 하나뿐 — 그래서 평소 의식할 일이 없다 |
| **블로킹(blocking)** | 응답이 올 때까지 그 스레드가 **멈춰서 기다리는 것** | `await` 처럼 보이지만 다르다 — JS의 `await`는 스레드를 놔주고, 여기선 스레드를 붙잡고 잔다 |
| **스레드풀(thread pool)** | 스레드를 미리 만들어 두고 빌려주는 창고. 일이 끝나면 반납한다 | 커넥션 풀과 같은 발상 — 매번 새로 만들지 않고 돌려 쓴다 |
| **이벤트루프** | 큐에서 콜백을 하나씩 꺼내 실행하는 단일 스레드 루프 | Node·브라우저가 돌리는 그것 |
| **워커 스레드(톰캣)** | 톰캣이 요청 하나를 맡기려고 풀에서 꺼내는 스레드 | — |
| **경쟁 상태(race condition)** | 두 스레드가 같은 데이터를 같은 시각에 읽고 써서 결과가 순서에 따라 달라지는 것 | JS에서 거의 못 겪는 종류의 버그 |
| **스레드 안전(thread-safe)** | 여러 스레드가 동시에 써도 결과가 망가지지 않는 성질 | — |

## 2. 원리 — 요청 하나에 스레드 하나

kbap의 api 앱은 `spring-boot-starter-web` 을 쓴다(`api/build.gradle.kts:24`). 이 스타터가 딸려 오는 게 **내장 톰캣(Tomcat)** 이고, 톰캣의 동작 모델은 이렇다.

1. 톰캣이 8080 포트에서 커넥션을 받는다.
2. HTTP 요청이 하나 들어오면 **워커 스레드풀에서 스레드를 하나 꺼내** 그 요청을 통째로 맡긴다.
3. 그 스레드가 필터 → 컨트롤러 → 서비스 → 리포지토리 → DB → 응답 직렬화까지 **처음부터 끝까지 혼자** 실행한다.
4. 응답을 다 보내면 스레드를 풀에 **반납**한다. 다음 요청이 그걸 다시 쓴다.

즉 **동시에 처리 중인 요청 수 = 지금 일하고 있는 워커 스레드 수**다. 요청이 200개 동시에 오면 스레드 200개가 각자 자기 요청을 붙잡고 동시에 돈다.

### 그래서 "그냥 기다려도" 된다

FE에서 `await fetch(...)` 없이 응답을 동기로 기다리면 앱이 얼어붙는다. 이벤트루프가 하나뿐이라, 그 하나를 붙잡으면 **다른 모든 요청·타이머·렌더가 전부 멈추기** 때문이다.

JVM 서버는 다르다. 내 스레드가 DB 응답을 기다리며 자고 있어도, **다른 199개 스레드는 자기 요청을 멀쩡히 처리한다.** 멈추는 건 "서버"가 아니라 "이 요청 하나"다. 그래서 백엔드 코드가 이렇게 생겼다.

```kotlin
val extracted = try {
    visionExtractor.extract(imagePath, ocrItems)
} catch (e: MenuBoardVisionUnavailableException) {
```
`api/src/main/kotlin/com/kbap/api/scan/ScanService.kt:40-42`

- `visionExtractor.extract(...)` 는 **OpenAI 비전 모델을 HTTP로 호출하는 코드**다. 수 초가 걸린다.
- `await` 도 `.then()` 도 콜백도 없다. 그냥 함수를 부르고 **결과를 변수에 받는다.**
- 이 줄에서 요청 스레드는 수 초간 **멈춰서 잔다.** 그리고 그건 여기서 정상이다 — 다른 요청들은 다른 스레드에서 계속 처리된다.
- 이 코드가 FE였다면 앱 전체가 수 초간 프리즈했을 것이다. (이 스캔 흐름 전체는 [[19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]])

> [!tip] 세계관 전환 한 줄
> **JS: 동시성을 "기다리지 않기"로 얻는다. JVM: 동시성을 "기다리는 놈을 여러 명 두기"로 얻는다.**

## 3. 비유 — 카페 바리스타 200명

**Node 카페**에는 바리스타가 **한 명**이다. 대신 이 사람은 절대 서서 기다리지 않는다. 에스프레소 머신을 켜 놓고 바로 다음 손님 주문을 받고, 우유를 스팀에 올려놓고 또 다음 손님을 받는다. "삐" 소리가 나면 그때 가서 마무리한다. 손님이 100명이어도 혼자 다 돌린다 — **기다리는 시간을 절대 낭비하지 않기 때문에** 가능하다.

이 카페의 재앙은 딱 하나다. 어떤 손님이 "핸드드립 15분짜리, 제가 지켜볼게요" 라고 하면, **그 15분 동안 카페 전체가 멈춘다.** 주문도 못 받고 다른 커피도 못 나간다. 이게 JS의 블로킹이다.

**JVM 카페**에는 바리스타가 **200명**이다. 손님 한 명당 바리스타 한 명이 붙어서 주문부터 서빙까지 끝까지 전담한다. 이 바리스타는 에스프레소가 내려오는 30초 동안 **그냥 서서 본다.** 낭비 같지만 상관없다 — 옆에 199명이 각자 자기 손님을 보고 있으니까. 여기선 "15분짜리 핸드드립"도 문제가 아니다. 바리스타 한 명이 15분 묶일 뿐이다.

대신 이 카페엔 Node 카페에 없던 두 문제가 생긴다.

- **손님 201명이 오면** 201번째 손님은 문 앞에서 기다려야 한다. 바리스타가 다 찼기 때문이다. (→ 스레드 고갈)
- **바리스타 두 명이 동시에 마지막 남은 우유팩에 손을 뻗으면** 사고가 난다. 둘 다 "우유 있네" 하고 확인한 뒤 각자 따르려 하면, 한 명은 빈 팩을 든다. (→ 경쟁 상태)

> [!warning] 비유의 경계
> - **바리스타 200명 ≠ CPU 코어 200개다.** 실제 CPU 코어는 보통 2~8개고, OS가 스레드들을 잘게 쪼개 번갈아 실행한다(컨텍스트 스위칭). 200명이 *진짜로* 동시에 손을 움직이는 게 아니라, **200명이 각자 자기 손님을 맡고 있고 대부분은 뭔가를 기다리는 중**이다. 그래서 200이라는 숫자가 코어 수보다 훨씬 커도 말이 된다 — 웹 요청 시간의 대부분은 계산이 아니라 **DB·외부 API를 기다리는 시간**이기 때문이다.
> - **바리스타는 공짜가 아니다.** 스레드 하나마다 스택 메모리(보통 512KB~1MB)가 붙고, 스위칭 비용도 든다. "그럼 5000명 두지"가 안 되는 이유다.
> - **"손님 한 명당 바리스타 한 명"은 요청 스레드에만 해당한다.** 뒤에서 도는 배치·`@Async` 작업은 손님 없이 일하는 별도 인력이다(§8).

## 4. 스레드풀 vs 이벤트루프 — 비교표

| | **Node 이벤트루프** | **JVM 스레드풀 (kbap)** |
|---|---|---|
| 동시 요청 처리 방식 | 스레드 1개가 콜백 큐를 돌며 번갈아 처리 | 요청마다 풀에서 스레드 1개를 배정 |
| I/O 기다리는 동안 | 스레드를 **놔주고** 다른 일을 함 | 그 스레드가 **붙잡은 채 잠듦** |
| 블로킹 코드의 의미 | **재앙** — 서버 전체가 멈춤 | **정상** — 그 요청 하나만 느려짐 |
| 코드 모양 | `async`/`await`, 콜백, Promise 체인 | 그냥 순차 코드. 위에서 아래로 |
| 동시성의 한계 | **CPU 바운드 작업**에 취약 (무거운 계산 하나가 전체를 멈춤) | **스레드 수**가 상한 (다 차면 대기열) |
| 에러 추적 | 스택 트레이스가 async 경계에서 끊김 | 요청 하나가 스레드 하나 = **스택 트레이스가 통째로 남음** |
| 공유 데이터 문제 | 거의 없음 (한 번에 한 콜백만 실행) | **있음** — 이게 이 노트 후반부의 주제 |
| 요청별 컨텍스트 | AsyncLocalStorage 등으로 따로 심어야 함 | `ThreadLocal` 로 스레드에 자연히 붙음 (§7) |

**어느 쪽이 낫냐**는 질문은 잘못됐다. 둘은 같은 문제(동시 요청)를 다른 자원으로 푼다. 이벤트루프는 **메모리**를 아끼고, 스레드풀은 **개발자의 머리**를 아낀다 — 순차 코드가 그냥 읽히고 스택 트레이스가 온전히 남는 건 생각보다 큰 값이다.

## 5. 실측 — kbap 톰캣은 스레드를 몇 개 쓰나

여기서 백엔드 레포를 읽는 중요한 기술 하나를 배운다: **설정 파일에 없는 것도 정보다.**

api 앱의 `application.yml` 에서 `server:` 블록은 이게 전부다.

```yaml
server:
  forward-headers-strategy: framework
```
`api/src/main/resources/application.yml:7-11` (주석 3줄 생략)

`server.tomcat.threads.max` 도, `min-spare` 도, `max-connections` 도 **한 줄도 없다.** 프로필별 파일(`application-local/dev/staging/prod.yml`)에도 없다 — 레포 전체에서 `threads` 문자열이 **0건**이다.

**설정이 없다 = 스프링 부트 기본값을 그대로 쓴다.** 그래서 기본값이 뭔지 알아야 한다. Spring Boot 4.1.0 소스의 `TomcatServerProperties` 가 정본이다.

| 프로퍼티 | 기본값 | 뜻 |
|---|---|---|
| `server.tomcat.threads.max` | **200** | 워커 스레드 최대 개수 = **동시에 처리 가능한 요청 수** |
| `server.tomcat.threads.min-spare` | **10** | 놀고 있어도 유지하는 최소 스레드 수 |
| `server.tomcat.threads.max-queue-capacity` | `2147483647` | 스레드가 다 찼을 때 쌓아둘 작업 큐 크기 (사실상 무제한) |
| `server.tomcat.max-connections` | **8192** | 동시에 **열어둘 수 있는** 커넥션 수 |
| `server.tomcat.accept-count` | **100** | 커넥션마저 다 찼을 때 OS 대기열에 쌓아둘 수 |

출처: Spring Boot `v4.1.0` 태그 소스 `module/spring-boot-tomcat/src/main/java/org/springframework/boot/tomcat/autoconfigure/TomcatServerProperties.java` — `Threads.max = 200`, `Threads.minSpare = 10`, `maxConnections = 8192`, `acceptCount = 100`.

**읽는 법**: 커넥션 8192개를 *열어둘 수는* 있지만 **동시에 일이 진행되는 건 200개**다. 나머지는 큐에서 기다린다. 그래서 "동시 접속자 8192명"이 아니라 **"동시 처리 200건"** 이 kbap api 인스턴스 하나의 실질 상한이다.

> [!tip] 이 습관을 들여라
> 백엔드 설정 파일에서 어떤 항목을 못 찾았을 때, "이 앱은 그 기능을 안 쓴다"가 아니라 **"기본값을 쓴다"** 를 먼저 의심해라. 스프링 부트는 안 적으면 방대한 기본값이 자동으로 적용되는 프레임워크다. 기본값의 정본은 블로그가 아니라 **해당 버전의 `*Properties` 클래스**다. ([[6. 설정과 프로필, 트랜잭션 경계]])

## 5-1. 그래서 이 200 은 누가 정하나 — 세 가지 질문

노트를 여기까지 읽으면 자연히 드는 질문 셋이다. (2026-09-02 문답에서 정리)

### ① 200 은 CPU 사양을 보고 자동으로 정해지나 — **아니다**

`TomcatServerProperties` 에 **숫자가 그냥 박혀 있다.** 코어 수를 세서 계산하지 않는다. 정하는 순서는:

| 우선순위 | 누가 | 무엇을 |
|---|---|---|
| 1 | **개발자** | `application.yml` 에 `server.tomcat.threads.max: 500` 이라고 쓰면 그 값 |
| 2 | **Spring Boot** | 안 쓰면 **200** (기본값) |

kbap 은 안 썼으니 200 이다.

> §3 의 *"바리스타 200명 ≠ CPU 코어 200개"* 는 **정반대 취지**다 — "코어가 4개인데 왜 스레드는 200개나 되나?"에 답한 것이지, 코어가 200을 정한다는 뜻이 아니다.

### ② 그럼 서버 사양이 다르면 100개·5000개로 달라지나 — **톰캣 풀은 안 달라진다**

같은 jar 를 노트북에서 돌리든 64코어 서버에서 돌리든 **200 으로 똑같다.** 바꾸려면 설정을 바꿔야 한다.

**단, CPU 수를 보고 자동으로 정해지는 다른 풀들은 있다** — 그래서 "JVM 은 코어 수를 안 본다"고 외우면 틀린다:

| 무엇 | 어떻게 |
|---|---|
| **GC 스레드 수** | 코어 수 기반 자동 |
| **`ForkJoinPool.commonPool()`** (병렬 스트림 `.parallel()`) | 대략 `코어 수 − 1` |
| 일부 라이브러리(Netty 등) | `코어 수 × 2` 같은 공식 |
| **톰캣 요청 스레드풀** | ❌ **코어와 무관 — 고정 200** |

전자들은 `Runtime.getRuntime().availableProcessors()` 를 본다. **Java 10+ 는 컨테이너를 인식**하므로 도커에서 `--cpus=2` 로 제한하면 호스트가 64코어여도 2 로 보인다.

### ③ 스레드 배정은 OS 가 하나 JVM 이 하나 — **세 층이 나눠 맡는다**

```
① 몇 개 만들지 정한다      →  애플리케이션 (톰캣/스프링 설정)   ← "200" 이라는 숫자
② 스레드를 실제로 만든다    →  JVM 이 OS 에 요청 → OS 가 커널 스레드 생성
③ 언제 어느 코어에서 돌린다 →  OS 스케줄러
```

- **①은 JVM 도 OS 도 아니다** — 순전히 프레임워크 설정이다.
- **②에서 JVM 은 중개자**다. 자바의 `Thread`(플랫폼 스레드)는 **OS 커널 스레드와 1:1** 로 묶인다. JVM 이 스레드를 흉내내는 게 아니라 **진짜 OS 스레드를 받아온다.**
- **③은 순전히 OS 몫**이다. 200개 중 무엇을 지금 CPU 에 올릴지 JVM 은 관여하지 않는다.

> **가상 스레드는 이 그림이 달라진다**(§6) — 그건 **JVM 이 직접 스케줄링**한다(M:N). OS 는 밑에 깔린 캐리어 스레드 몇 개만 본다. kbap 은 안 켰으니 지금은 위 3층 그대로다.

## 5-2. 그럼 5,000,000 으로 설정하면? — **막는 장치가 없다**

### 검증은 없다

`threads.max` 는 그냥 `int` 다. **상한 검증이 없어서** 5,000,000 을 써도 스프링 부트도 톰캣도 아무 말 안 한다.

### 그런데 실행하자마자 죽지도 않는다 — **미리 안 만들기 때문**

톰캣은 부팅 때 `min-spare`(10)개만 만들고 **요청이 몰릴 때마다 늘린다.** `max` 는 **"여기까지 늘려도 된다"는 천장**이지 "이만큼 만들어라"가 아니다.

```
부팅 직후        →  스레드 10개.  앱 멀쩡히 뜬다 ✅
동시 요청 50개   →  50개로 증가
동시 요청 3000개 →  3000개로 증가... 여기서부터 무너진다
```

**트래픽이 안 오면 아무 일도 안 일어난다.** 설정 파일만 봐서는 폭탄인지 모른다 — 배포는 성공한 것처럼 보이고 **트래픽이 몰리는 새벽에 터진다.**

### 무너지는 순서 — 두 단계

**① 먼저 느려진다 (이쪽이 더 무섭다)**
스레드 하나당 **스택 메모리 1MB 남짓**을 잡는다(힙이 아니라 **네이티브 메모리**). 3,000개면 그것만 3GB 다. 게다가 코어가 4개인데 스레드가 3,000개면 OS 가 쉴 새 없이 갈아 끼운다(**컨텍스트 스위칭**). 교체 비용이 실제 일보다 커지는 지점부터 — **응답은 다 느린데 CPU 는 100%이고 서버는 살아 있다.** 원인도 안 보이는 최악의 상태다.

**② 그다음 스레드 생성이 거부된다**

```
java.lang.OutOfMemoryError: unable to create native thread
```

**이름은 OOM 이지만 힙 부족이 아니다.** OS 가 "더는 못 만들어준다"고 거절한 것이다. 거절하는 주체:

| 한계 | 무엇 |
|---|---|
| `ulimit -u` | 프로세스당 스레드 수 제한 (보통 수천~수만) |
| cgroup `pids.max` | **컨테이너**의 프로세스/스레드 상한 |
| 네이티브 메모리 | 스택 잡을 공간 없음 |

> [!warning] 진짜 보호장치는 프레임워크가 아니라 OS 다
> 스프링·톰캣은 안 막는다. **커널이 거절한다.** 그래서 같은 설정이라도 `ulimit`·컨테이너 `pids.max` 에 따라 **터지는 지점이 서버마다 다르다.**
> 그리고 **JVM 은 그 거절을 예외로 바꿔 던진다** — 프로세스가 즉사하는 게 아니라 해당 요청만 실패하고 앱은 반쯤 살아서 비틀거린다.
>
> **우연한 방파제가 하나 있다**: `max-connections`(8192)·`accept-count`(100) 때문에 **동시에 받아주는 커넥션 자체에 상한**이 있어, 실제로는 5,000,000 근처에 가기 전에 커넥션 단계에서 먼저 막힌다. 의도한 보호는 아니다.

> [!tip] 여기서 가져갈 것
> **설정값에 상한 검증이 없다는 건 "안전하다"가 아니라 "네가 책임진다"는 뜻이다.** 그리고 이런 값은 **부팅 시점에 안 터지므로** 코드 리뷰·배포 검증을 그냥 통과한다. 스레드풀·커넥션풀·타임아웃처럼 **"평소엔 안 보이고 부하에서만 드러나는 설정"** 은 값을 바꿀 때 근거를 남겨야 한다.

## 6. 가상 스레드 — 쓸 수 있는데 안 켰다

Java 21에는 **가상 스레드(virtual thread)** 가 정식으로 들어왔다. 아주 거칠게 말하면 *"OS 스레드에 1:1로 묶이지 않는 아주 가벼운 스레드"* 라, 수만 개를 만들어도 감당이 된다. 블로킹 코드를 그대로 두면서 이벤트루프급 동시성을 노리는 접근이다.

kbap은 **Java 21을 쓴다**(`gradle/libs.versions.toml:2`). 그러니 켤 수는 있다. 그런데 **안 켰다.**

- 레포 전체에서 `spring.threads.virtual` 설정 **0건**, `virtual` 문자열 **0건**(실측 2026-08-27).
- Spring Boot에서 가상 스레드는 **명시적 opt-in** 이다. `Threading.VIRTUAL` 은 `spring.threads.virtual.enabled` 프로퍼티가 `true` 이고 **동시에** Java 21 이상일 때만 활성이라고 정의돼 있다. 프로퍼티의 기본값은 **`false`**.
- 즉 kbap api는 지금 **플랫폼 스레드 200개짜리 고전 톰캣 풀**로 돈다.

곁다리로, `TomcatServerProperties` 의 `threads.max` javadoc에는 이런 문장이 붙어 있다 — *"Doesn't have an effect if virtual threads are enabled."* 가상 스레드를 켜면 톰캣은 풀 대신 요청마다 가상 스레드를 새로 만들어서, **200이라는 숫자 자체가 무의미해진다**는 뜻이다.

> [!note] 노트로서의 정직함
> "왜 안 켰나"는 레포 어디에도 근거가 적혀 있지 않다. ADR에도 스펙에도 없다. 여기서 말할 수 있는 건 **"Java 21이라 쓸 수는 있는데 켜지 않았고, 그래서 지금은 스레드 200개가 상한이다"** 까지다. 그 이상은 추측이다.

## 7. 대가 — 여러 스레드가 같은 것을 건드린다

> [!tip] 📖 여기서 막히면 순서를 바꿔도 된다
> 이 절부터는 **스프링의 "빈"** 개념이 깔린다. 그런데 빈의 정본은 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다|4번 노트]]라 **아직 안 나왔다**(커리큘럼 순서상 이 노트가 먼저다).
> 아래 7-1 의 🧩 상자로 최소한은 채워 두었지만, **읽다 막히면 4번 → 3번을 먼저 보고 여기로 돌아오는 게 빠르다.** §7~§9 는 §1~§6 과 독립적이라 건너뛰어도 앞부분 이해에는 지장이 없다.

이벤트루프를 버리고 얻은 편의(순차 코드·블로킹 허용)에는 값이 붙는다. **스레드 200개가 같은 프로세스 메모리를 공유한다**는 사실이다.

### 7-1. 빈은 싱글턴이다 — 그래서 상태를 갖지 마라

> [!info] 🧩 먼저 — "빈"과 "싱글턴"만 30초에 (아직 4번 노트를 안 읽었다면)
> 이 절만 읽는 데 필요한 최소한이다. 자세한 건 [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다|4번 노트]]가 정본이다.
>
> **빈(Bean) = 스프링이 대신 만들어서 들고 있는 객체.**
> 보통 코드라면 우리가 `val service = MemberService(repo)` 라고 **직접 만든다**. 스프링에서는 안 그런다 — `@Service` 같은 표시만 붙여 두면 **앱이 켜질 때 스프링이 알아서 만들어 창고에 넣어 둔다.** 그 창고 속 객체 하나하나를 **빈**이라고 부른다.
>
> **싱글턴 = 그 객체를 앱 전체에서 딱 하나만 만든다.**
> 요청이 100개 들어와도 `MemberService` 를 100개 만들지 않는다. **하나를 만들어 두고 전부가 그걸 나눠 쓴다.** (왜? 매 요청마다 객체를 새로 만들면 낭비고, 어차피 이 객체들은 "기억할 게 없는 기능 덩어리"라 하나면 충분하다.)
>
> **JS 로 치면** — 모듈 최상단에 `export const service = createService()` 라고 한 번 만들어 두고 여기저기서 `import` 해 쓰는 것과 같다. 그 파일을 몇 번 import 하든 객체는 하나뿐이다.
>
> ⚠️ **이 절의 핵심은 여기서 나온다**: 객체가 **하나뿐인데** 스레드는 **200개**다.

스프링은 `@Service` 가 붙은 클래스의 객체를 **앱이 뜰 때 딱 하나만 만들어 두고 전부가 그 하나를 나눠 쓴다**(= 위의 **싱글턴 스코프**). 즉 `MemberService` 객체는 앱 전체에 **딱 하나** 있다.

이제 이 노트의 사실을 얹으면 결론이 나온다. **스레드 200개가 그 하나의 객체를 동시에 호출한다.**

```kotlin
@Service
class MemberService(
    private val memberRepository: MemberJpaRepository,
    @Value("\${kbap.storage.public-base-url:}") private val imagePublicBaseUrl: String,
) {
```
`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:17-21`

- 필드가 **`val` 두 개뿐**이다. 생성 후 바뀌지 않는다.
- `memberRepository` 도 싱글턴이지만 자기 상태가 없고, `imagePublicBaseUrl` 은 부팅 시 한 번 읽은 문자열이다.
- 이런 객체를 **무상태(stateless)** 라고 한다. 필드가 안 변하니 스레드 몇 개가 동시에 들어와도 서로 간섭할 게 없다.
- 요청마다 다른 값(회원 ID, 요청 본문)은 전부 **메서드 파라미터와 지역 변수**로만 다닌다. 지역 변수는 **스레드마다 자기 스택에 따로** 있어서 공유되지 않는다.

만약 여기에 `private var lastMemberId: Long? = null` 같은 필드를 하나라도 두면, 스레드 A가 쓴 값을 스레드 B가 읽는 버그가 생긴다. 재현이 거의 안 되고, 부하가 걸릴 때만 터지고, 로컬에선 절대 안 나타나는 종류다.

> **규칙**: 스프링 빈에는 `var` 필드를 두지 않는다. 요청별 데이터는 파라미터로 넘긴다.

### 7-2. lost update — 카운트를 두 스레드가 동시에 올릴 때

같은 회원이 스캔 두 건을 거의 동시에 보내면, 스레드 두 개가 같은 회원 행의 `scanCount` 를 동시에 올린다. 코드로 이렇게 짜면 틀린다.

```kotlin
// 예시 (kbap 코드 아님) — 이렇게 하면 안 된다
val member = repository.findById(memberId)
member.scanCount = member.scanCount + 1
repository.save(member)
```

둘 다 `scanCount = 5` 를 읽고, 둘 다 6을 쓴다. 두 번 올렸는데 결과는 6이다. 하나가 사라졌다 — 이걸 **lost update** 라고 한다. (바리스타 둘이 마지막 우유팩을 동시에 본 그 장면이다.)

kbap의 답은 **읽지 않고 DB에게 직접 더하라고 시키는 것**이다.

```kotlin
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query(
    """
    update Member m
    set m.scanCount = m.scanCount + 1
    where m.id = :memberId
      and m.memberStatus = ...ACTIVE
    """,
)
fun increaseScanCount(@Param("memberId") memberId: Long): Int
```
`common/src/main/kotlin/com/kbap/common/domain/member/MemberJpaRepository.kt:22-31`

- 값을 앱으로 읽어오지 않는다. `scanCount = scanCount + 1` 이라는 **한 문장을 DB에 보낸다.**
- DB는 이 UPDATE 한 건을 **원자적으로**(쪼개지지 않게) 처리한다. 두 스레드가 동시에 보내도 결과는 정확히 +2다.
- 반환값 `Int` 는 실제로 갱신된 행 수다. `0` 이면 그 회원이 없거나 ACTIVE가 아니라는 뜻이라, 호출부가 그걸로 예외를 던진다(`MemberService.kt:89-94`).

**정본은 [[23. 회원 랭킹 — 원자적 카운트와 조회 시점 점수 계산]]** 이다. 이 노트에서 배운 문제가 거기서 실제로 터지고, 그 노트가 해법을 끝까지 다룬다.

### 7-3. check-then-act — 확인하고 행동하는 사이의 틈

더 고약한 패턴이 있다. **"확인한 뒤 행동한다"** 사이에 다른 스레드가 끼어드는 것이다.

> 무료 스캔 한도가 3회다. → 스레드 A: "지금 2회 썼네, 괜찮다" → 스레드 B: "지금 2회 썼네, 괜찮다" → 둘 다 실행 → **4회 사용됨.**

확인(check)과 행동(act)이 **따로 떨어져 있으면** 그 틈으로 다른 스레드가 들어온다. 7-2의 카운트 증가는 DB UPDATE 한 방으로 합쳐서 해결했지만, 이건 "확인"과 "실행"이 물리적으로 떨어져 있어(그 사이에 몇 초짜리 LLM 호출이 있다) 그 수법이 안 통한다.

kbap은 이걸 **Redis에 슬롯을 선점(예약)하는 방식**으로 푼다. 확인과 점유를 Redis 쪽에서 **한 번에 쪼개지지 않게** 처리하고, 실패하면 예약을 해제한다.

**정본은 [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]]** 다. 무료 한도·중복 요청 막기가 전부 이 문제의 실물이다. Redis 자체의 쓰임새는 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식]]에서 다룬다.

> [!info] 이 셋의 공통 구조
> **싱글턴 빈의 `var` 필드**, **lost update**, **check-then-act** — 셋 다 "여러 스레드가 같은 것을 본다"의 변주다. FE에서 이런 버그를 거의 안 겪은 건 실력이 아니라 **이벤트루프가 한 번에 한 콜백만 실행해서** 구조적으로 막혀 있었기 때문이다. 백엔드에선 그 보호막이 없다.

## 8. 스레드마다 자기 것 — 트랜잭션과 영속성 컨텍스트

공유가 문제라면, 반대로 **공유하지 않게 만드는** 장치도 있다. JVM에는 `ThreadLocal` 이라는 게 있다 — **스레드마다 서로 다른 값을 담는 저장소**다. 같은 코드가 같은 변수를 읽어도 스레드 A와 B가 다른 값을 본다.

스프링은 이걸 요청 처리의 뼈대로 쓴다.

- **트랜잭션**: `@Transactional` 메서드에 들어가면 스프링이 DB 커넥션 하나를 잡아 **현재 스레드에 묶어둔다.** 그래서 그 아래 어떤 코드를 부르든 "지금 이 스레드의 트랜잭션"을 알아서 찾아 쓴다. 파라미터로 커넥션을 들고 다니지 않는 이유다. → [[6. 설정과 프로필, 트랜잭션 경계]]
- **영속성 컨텍스트(EntityManager)**: 마찬가지로 **요청 스레드에 하나씩** 붙는다. 그래서 "같은 엔티티를 두 번 조회하면 같은 객체가 온다"는 보장이 **내 요청 안에서만** 성립한다. 옆 스레드의 영속성 컨텍스트는 완전히 별개다. → [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]
- **로그의 요청 ID**: `application.yml:1-5` 의 `logging.pattern.correlation` 이 `%X{requestId}` 를 찍는다. 이 MDC라는 것도 `ThreadLocal` 이다 — 그래서 요청 200개의 로그가 뒤섞여도 각 줄에 **자기 요청의 ID**가 정확히 붙는다. → [[17. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]]

> **한 문장**: 트랜잭션도, 영속성 컨텍스트도, 요청 ID도 **"요청 하나 = 스레드 하나"라는 전제 위에 세워진 장치**다. 이 노트가 그 전제를 다뤘기 때문에 6·8·17번이 성립한다.
>
> 뒤집으면 이런 경고도 나온다 — **요청 스레드에서 다른 스레드로 일을 넘기면 이 셋이 전부 따라가지 않는다.** 트랜잭션도, 영속성 컨텍스트도, 요청 ID도 새 스레드에는 없다.

## 9. 요청 스레드가 아닌 곳에서 도는 코드

kbap에는 "손님 없이 일하는" 코드도 있다. 이 노트에선 **그런 게 있다**는 것만 짚는다.

**(1) `@Async` — 같은 앱, 다른 스레드**

```kotlin
@Async
@EventListener
fun handle(event: LlmCallCostIncurred) {
```
`api/src/main/kotlin/com/kbap/api/metering/LlmCallCostEventListener.kt:15-17` (`@EnableAsync` 는 `api/src/main/kotlin/com/kbap/api/core/config/BackgroundConfig.kt:13`)

- LLM 호출 비용 기록은 응답을 늦출 이유가 없다. `@Async` 가 붙으면 이 메서드는 **요청 스레드가 아니라 별도 실행기 스레드**에서 돈다.
- 요청 스레드는 이벤트만 던지고 곧장 응답을 반환한다.
- **§8의 경고가 여기서 실물이 된다** — 이 메서드에는 요청의 트랜잭션도, 영속성 컨텍스트도, 요청 ID도 따라오지 않는다. 그래서 이 코드는 안에서 예외를 직접 잡아 로그만 남긴다(호출부에 전파할 곳이 없다).
- 자세히는 → [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]]

**(2) 스케줄러 — 시간이 부르는 코드**

`BackgroundConfig.kt:14` 의 `@EnableScheduling` 이 켜져 있다. cron 시각이 되면 요청 없이 스레드가 깨어나 실행된다. 운영 인스턴스가 2대면 **둘 다 동시에 깨는** 문제가 생기는데, 이건 ShedLock으로 1대만 고르게 막아뒀다(`BackgroundConfig.kt:15`, `@EnableSchedulerLock`). → [[21. 이미지 업로드 흐름 — presigned URL과 업로드 완료 확정]]

**(3) 배치 앱 — 아예 다른 프로세스**

kbap의 두 번째 실행 파일인 batch 앱은 톰캣 워커 스레드와 무관한 세계다. Spring Batch가 자기 스레드로 잡을 돌린다(`batch/src/main/kotlin/com/kbap/batch/config/BatchJdbcJobRepositoryConfig.kt:29`). → [[26. 배치 앱의 골격 — Spring Batch 잡·트리거·스케줄]]

## 11. 치트시트

```
요청 1개 = 워커 스레드 1개 = 스택 1개 = 트랜잭션 1개 = 영속성 컨텍스트 1개
```

| 물음 | kbap의 답 (실측 2026-08-27) |
|---|---|
| 웹 서버는? | 내장 톰캣 (`spring-boot-starter-web`, `api/build.gradle.kts:24`) |
| 동시 처리 가능한 요청 수는? | **200** (`server.tomcat.threads.max` 기본값 — 설정 없음) |
| 최소 유지 스레드는? | **10** (`min-spare` 기본값) |
| 동시에 열어둘 커넥션은? | **8192** (`max-connections` 기본값) |
| 가상 스레드는? | **안 씀.** `spring.threads.virtual` 설정 0건 = 기본 `false` |
| 서비스에서 DB·LLM을 기다려도 되나? | **된다.** 그 요청 스레드만 잔다 |
| 빈에 `var` 필드를 둬도 되나? | **안 된다.** 싱글턴 + 스레드 200개 |
| 카운트를 안전하게 올리려면? | 읽지 말고 **DB에 `set x = x + 1` UPDATE** |
| 요청 스레드를 벗어나는 코드는? | `@Async` · `@Scheduled` · batch 앱 |

**한 줄 규칙 세 개**
1. 빈은 무상태로. 요청별 값은 파라미터로.
2. 읽고-고치고-쓰기 대신 **DB에 한 문장으로** 시켜라.
3. 스레드를 넘기면 트랜잭션·영속성 컨텍스트·요청 ID는 **안 따라간다.**

## 12. 용어집

- **스레드(thread)**: 프로세스 안에서 코드를 실행하는 흐름. 같은 프로세스의 힙 메모리를 공유하고, 스택은 각자 갖는다.
- **워커 스레드**: 톰캣이 요청 하나를 처리하려고 풀에서 꺼내 쓰는 스레드.
- **스레드풀**: 스레드를 미리 만들어 두고 빌려주고 반납받는 창고. 생성 비용을 아낀다.
- **블로킹**: 결과를 기다리며 그 스레드를 멈춰 세우는 것.
- **스레드 고갈(thread starvation)**: 풀의 스레드가 전부 묶여 새 요청이 대기하는 상태.
- **컨텍스트 스위칭**: OS가 CPU를 스레드 A에서 B로 옮기는 것. 공짜가 아니다.
- **경쟁 상태(race condition)**: 두 스레드의 실행 순서에 따라 결과가 달라지는 상황.
- **lost update**: 두 갱신 중 하나가 덮여 사라지는 경쟁 상태.
- **check-then-act**: 확인과 행동 사이에 다른 스레드가 끼어들 수 있는 패턴.
- **원자적(atomic)**: 중간에 끼어들 수 없는, 쪼개지지 않는 단위로 실행되는 것.
- **무상태(stateless)**: 호출 사이에 남는 가변 상태가 없는 것. 스레드 안전의 가장 쉬운 길.
- **`ThreadLocal`**: 스레드마다 별도의 값을 담는 저장소. 트랜잭션·영속성 컨텍스트·MDC의 바탕.
- **MDC (Mapped Diagnostic Context)**: 로그에 요청별 꼬리표를 붙이는 `ThreadLocal` 저장소.
- **가상 스레드(virtual thread)**: Java 21의 경량 스레드. OS 스레드에 1:1로 묶이지 않는다. kbap은 안 씀.
- **플랫폼 스레드**: OS 스레드에 1:1로 대응하는 전통적 스레드. kbap이 쓰는 것.

- [ ] 200 이라는 숫자를 **누가** 정하는지 안다(CPU 아님 — 프레임워크 기본값, §5-1)
- [ ] 코어 수를 보는 풀과 안 보는 풀을 구분할 수 있다(GC·commonPool vs 톰캣, §5-1)
- [ ] 스레드 개수 결정 / 생성 / 스케줄링을 **애플리케이션·JVM·OS** 로 나눠 설명할 수 있다(§5-1)
- [ ] `threads.max` 를 터무니없이 크게 잡으면 **언제** 무너지는지 안다(부팅 아님 — 부하 시, §5-2)
1. [ ] 왜 `ScanService.kt:41` 이 `await` 없이 LLM을 호출해도 되는지 설명할 수 있다.
2. [ ] kbap api 인스턴스 하나가 동시에 처리할 수 있는 요청 수와 **그 숫자가 어디서 나왔는지**(설정이 아니라 기본값) 말할 수 있다.
3. [ ] `application.yml` 에 어떤 항목이 없을 때 무엇을 확인해야 하는지 안다.
4. [ ] "kbap은 가상 스레드를 쓰나?"에 근거를 대고 답할 수 있다.
5. [ ] 스프링 빈에 `var` 필드를 두면 안 되는 이유를 **싱글턴 + 요청당 스레드**로 이어서 설명할 수 있다.
6. [ ] lost update가 뭔지, `MemberJpaRepository.increaseScanCount` 가 그걸 어떻게 피하는지 말할 수 있다.
7. [ ] check-then-act가 뭔지, kbap 어디에서 그 문제가 실제로 터지는지 안다.
8. [ ] `@Async` 메서드에 요청의 트랜잭션·영속성 컨텍스트·요청 ID가 따라가지 않는 이유를 안다.
