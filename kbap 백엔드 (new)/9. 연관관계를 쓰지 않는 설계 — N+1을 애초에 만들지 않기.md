# 9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기

> 작성: 2026-08-26 · 맥락: JPA 를 다루는 거의 모든 글의 절반은 "연관관계(`@OneToMany`·`@ManyToOne`)를 어떻게 매핑하고, 거기서 터지는 N+1 을 어떻게 고치나"에 쓰여 있다. 그런데 kbap-server 를 아무리 뒤져도 그 애너테이션이 **하나도 없다**. 남의 글을 읽고 온 뒤 이 레포를 열면 "내가 뭘 못 찾는 건가?" 싶어진다 — 못 찾는 게 아니라 **없는 게 맞다**.
> 목표: N+1 이 무엇이고 왜 무서운지 설명할 수 있게 되고, kbap 이 그 문제를 **고치는 대신 만들지 않기로** 한 선택과 **그 대가**를 둘 다 말할 수 있게 되기.

---

## 0. 한 줄 요약

**N+1** 은 "목록 1번 조회 + 각 항목마다 1번씩 추가 조회 = 총 1+N 번 쿼리"가 나가는 성능 사고다. 대부분의 프로젝트는 이걸 **연관관계를 쓰다가 만들고, `join fetch` 로 고친다**. kbap 은 **엔티티끼리 연관을 아예 매핑하지 않고 `Long` id 컬럼만 두는 쪽**을 택했다 — 그래서 N+1 이 자동으로 생길 통로 자체가 없고, 대신 **필요한 조회를 사람이 손으로 적어야** 한다.

---

## 1. 먼저 N+1 — 연관관계를 쓰는 세계에서

이 절은 **kbap 이 아닌 다른 프로젝트 이야기**다. kbap 의 선택이 왜 선택인지 알려면, 선택하지 않은 쪽을 먼저 봐야 한다.

### 1-1. 연관관계란 게 뭔데

JPA 에서는 테이블끼리의 관계를 **객체 필드로** 표현할 수 있다. 예시(kbap 코드 아님):

```kotlin
@Entity
class Order(
    @OneToMany(mappedBy = "order")
    var items: List<OrderItem> = emptyList(),
)
```

이렇게 해두면 `order.items` 라고 **점을 찍는 것만으로** 다른 테이블의 행들이 딸려 온다. DB 의 외래키를 객체 그래프로 바꿔 주는 게 ORM 의 가장 화려한 마술이고, 실제로 코드가 아주 짧아진다.

문제는 **그 점을 찍는 순간 SQL 이 나간다**는 것이다. 그리고 그 사실이 코드에 안 적혀 있다.

### 1-2. 장바구니 비유

마트에 장을 보러 갔다고 하자.

- **좋은 방식**: 살 것 목록을 미리 다 적어 가서 **한 번에** 카트에 담아 나온다. 왕복 1회.
- **N+1 방식**: 일단 "오늘 살 품목 목록"만 받아 온다(1회). 그리고 **품목 하나를 확인할 때마다 집에 갔다가 다시 마트로 온다**. 품목이 20개면 왕복 21회.

사 오는 물건은 똑같다. 다른 건 **왕복 횟수**뿐이다. 그리고 DB 조회에서 진짜 비싼 건 데이터의 양이 아니라 **왕복(round trip) 횟수**다. 쿼리 한 번이 1ms 걸린다면 21번은 21ms — 별거 아닌 것 같지만, 이건 목록이 20개일 때 얘기다.

> [!warning] 비유의 경계
> 마트 비유에서 "집에 갔다 오는 시간"은 사람이 체감할 만큼 길다. 실제 DB 왕복은 훨씬 짧다(같은 네트워크 안이면 1ms 미만인 경우도 많다). N+1 이 무서운 진짜 이유는 **한 번이 느려서가 아니라 N 이 사용자 수·페이지 크기에 비례해 곱해지기 때문**이다. 목록 20개짜리 화면을 100명이 동시에 열면 왕복은 2,100번이 된다. 그리고 DB 커넥션은 풀에서 빌려 쓰는 유한 자원이라([[6. 설정과 프로필, 트랜잭션 경계]]), 왕복이 길어지면 **커넥션을 붙잡고 있는 시간**도 같이 길어져서 다른 요청까지 밀린다.

### 1-3. FE 에서 이미 겪어 본 그것 — 워터폴

사실 이 패턴은 FE 에서 이름만 다르게 이미 만나 봤다.

```tsx
// 예시 — 안티패턴
function FoodList() {
  const { data: foods } = useQuery(['foods'], fetchFoods);   // 요청 1번
  return foods.map(f => <FoodCard key={f.id} id={f.id} />);
}

function FoodCard({ id }) {
  const { data } = useQuery(['food', id], () => fetchFood(id)); // 카드마다 1번씩
  ...
}
```

목록을 그리고 나서 **카드가 각자 자기 데이터를 부르는** 구조. 네트워크 탭에 요청이 21개 찍힌다. 이걸 고치는 방법도 FE 에서 이미 안다 — **목록 API 가 필요한 걸 다 채워서 한 번에 주게 만든다.**

| | FE 워터폴 | 백엔드 N+1 |
|---|---|---|
| 1 | 목록 API 호출 | 목록 SELECT |
| N | 카드마다 상세 API 호출 | 행마다 연관 SELECT |
| 유발 지점 | 자식 컴포넌트의 `useQuery`/`useEffect` | 엔티티의 연관 필드에 **점 찍기** |
| 눈에 보이나 | **보인다** — 네트워크 탭에 21줄 | **안 보인다** — 코드엔 점 하나뿐 |

**마지막 줄이 핵심이다.** FE 워터폴은 최소한 `fetch` 를 부르는 코드가 눈에 있다. 백엔드 N+1 은 `order.items` 라는 점 하나가 SQL 20번을 부르므로, **SQL 로그를 켜기 전까지는 코드를 아무리 읽어도 안 보인다.** N+1 이 리뷰에서 잘 안 걸리고 운영에 가서야 터지는 이유가 이것이다.

> [!warning] 비유의 경계
> FE 워터폴은 요청이 **순차로 이어질 때**(앞 응답이 있어야 다음 요청 가능) 특히 아프고, 병렬로 쏠 수 있으면 어느 정도 완화된다. 백엔드 N+1 은 **한 스레드 안에서 순차로** 나가므로 병렬화로 완화되지 않는다. 반대로 백엔드는 DB 가 같은 프로세스 옆에 있어서 왕복 하나의 비용은 훨씬 싸다. 구조는 같고, 아픈 지점이 다르다.

### 1-4. 보통은 이렇게 고친다

연관관계를 쓰는 프로젝트에서 N+1 의 표준 처방은 세 가지다.

| 처방 | 하는 일 | 부작용 |
|---|---|---|
| `join fetch` (fetch join) | 목록 쿼리에 조인을 붙여 **한 방에** 다 가져온다 | **페이징과 충돌한다**(4절에서 설명) |
| `@BatchSize` / batch fetch | N 번을 `where id in (…)` 로 **묶어서** 몇 번으로 줄인다 | 여전히 자동이라 예측이 어렵다 |
| Entity Graph | 이번 조회에서 어디까지 같이 가져올지 **호출부에서** 지정 | 조회마다 지정해야 함 |

그리고 세 처방 모두 **"연관관계가 이미 있다"를 전제로 한다.** kbap 은 그 전제를 지웠다.

## 2. kbap 의 선택 — 연관을 아예 매핑하지 않는다

### 2-1. 실코드: 스캔 기록은 회원도 음식도 모른다

`ScanHistory` 는 "어느 회원이 어느 음식을 스캔했다"는 기록이다. 교과서대로면 `@ManyToOne` 이 두 개 붙을 자리다. 실제 코드는 이렇다.

```kotlin
@Entity
@Table(
    name = "scan_history",
    indexes = [Index(name = "idx_scan_history_recent", columnList = "member_id, created_at")],
)
class ScanHistory(
    @Column(name = "member_id", nullable = false)
    var memberId: Long = 0,

    @Column(name = "price")
    var price: Int? = null,

    @Column(name = "food_id")
    var foodId: Long? = null,
) : BaseEntity()
```
— `common/src/main/kotlin/com/kbap/common/domain/scan/model/ScanHistory.kt:9-23`

- `memberId: Long` — `Member` 객체가 아니라 **숫자 하나**다. `scanHistory.member.nickname` 같은 건 애초에 컴파일이 안 된다.
- `foodId: Long?` — 마찬가지. 음식 정보가 필요하면 **그 id 로 다시 조회해야** 한다.
- `@Column(name = "…")` — 테이블에는 `member_id`·`food_id` 컬럼이 그대로 있다. **DB 스키마는 평범하다.** 달라진 건 "그 컬럼을 객체 참조로 볼 것인가, 숫자로 볼 것인가" 하나뿐이다.
- `indexes = [...]` — 연관이 없으니 조회는 항상 "이 컬럼 값으로 찾기"가 된다. 그래서 인덱스가 더 중요해진다.

이 레포의 모든 엔티티가 이 모양이다.

### 2-2. 규율이 아니라 **테스트로 강제**된다

"연관관계 쓰지 맙시다"가 구두 약속이면 반년 뒤 누군가 하나 붙인다. kbap 은 이걸 **빌드에서 깨지는 테스트**로 박아 뒀다.

```kotlin
    given("JPA 연관관계 금지") {
        `when`("엔티티 필드의 연관 애너테이션을 검사하면") {
            then("@OneToMany·@ManyToOne·@OneToOne·@ManyToMany 를 쓰지 않는다 — 참조는 id 값 컬럼") {
                noFields().that().areDeclaredInClassesThat().resideInAPackage("com.kbap..")
                    .should().beAnnotatedWith("jakarta.persistence.OneToMany")
                    .orShould().beAnnotatedWith("jakarta.persistence.ManyToOne")
                    .orShould().beAnnotatedWith("jakarta.persistence.OneToOne")
                    .orShould().beAnnotatedWith("jakarta.persistence.ManyToMany")
                    .allowEmptyShould(true)
                    .check(imported)
            }
        }
    }
```
— `api/src/test/kotlin/com/kbap/api/architecture/ModuleBoundaryTest.kt:155-166`

- `noFields()` — "이런 필드는 **하나도 없어야 한다**"는 규칙. ArchUnit 이라는 라이브러리가 컴파일된 클래스를 읽어 검사한다.
- `resideInAPackage("com.kbap..")` — `com.kbap` 아래 **전부**. 예외 패키지가 없다.
- `.should().beAnnotatedWith(...)` 4줄 — 금지 대상 애너테이션 네 개를 나열했다. `noFields ... should` 조합이므로 "붙어 있으면 실패"로 읽는다.
- `allowEmptyShould(true)` — 검사 대상이 0건이어도 통과 처리. 지금 상태(연관 0개)에서 규칙이 스스로 깨지지 않게 하는 장치다.

즉 **누가 `@ManyToOne` 을 하나라도 추가하면 CI 가 빨개진다.** 코드 리뷰어의 기억력이 아니라 테스트가 경계를 지킨다.

> ArchUnit 이라는 도구 자체와 이 레포가 강제하는 **다른 규칙들**(모듈 의존 방향, `@Entity` 위치, 커널의 Spring 비의존 등)은 뒤의 13번 노트 「경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들」에서 따로 다룬다. 여기서는 이 규칙 하나만 본다.

### 2-3. 문서보다 코드를 믿어라

레포의 `CLAUDE.md:117` 에는 아직 "읽기 전용 연관은 허용(현재 유일: `Food`→성분 `@OneToMany(EAGER)`)"이라고 적혀 있다. **2026-08-26 기준 실측으로는 거짓이다** — 그 연관은 코드에 없고, 위 ArchUnit 규칙이 예외 없이 전면 금지한다. 레포 문서가 코드보다 낡은 자리 중 하나이니, 충돌하면 코드를 믿는다.

## 3. 그럼 관계는 어떻게 표현하나 — 실제로 쓰는 세 가지

연관 매핑을 지운다고 관계가 사라지는 건 아니다. 표현 수단이 바뀔 뿐이다. kbap 에는 세 가지가 있다.

### 3-1. id 로 참조하고, 필요하면 **묶어서** 다시 조회한다

가장 흔한 형태. "N 번 조회"를 "1번의 `IN` 조회"로 바꾸는 것을 사람이 직접 쓴다.

```kotlin
    private fun loadInGivenOrder(ids: List<Long>): List<Food> {
        if (ids.isEmpty()) return emptyList()
        val foodsById = foodRepository.findByIdIn(ids).associateBy { it.id }
        return ids.mapNotNull { foodsById[it] }
    }
```
— `api/src/main/kotlin/com/kbap/api/food/FoodService.kt:71-75`

- `findByIdIn(ids)` — id 목록 하나로 **SELECT 한 번**. `where id in (1, 2, 3, …)` 이 나간다. N+1 의 N 을 1로 접는 자리다.
- `associateBy { it.id }` — 결과를 `Map<Long, Food>` 로 만든다. FE 로 치면 배열을 id 키 객체로 정규화하는 것과 같다.
- `ids.mapNotNull { foodsById[it] }` — **원래 id 순서대로** 다시 줄 세운다. `IN` 조회는 순서를 보장하지 않으므로 이 한 줄이 없으면 정렬이 무너진다.
- `if (ids.isEmpty()) return emptyList()` — 빈 리스트로 `IN ()` 을 만들지 않기 위한 가드. 손으로 쓰는 코드라 이런 가드도 손으로 붙는다.

이 함수는 **연관관계가 해 주던 일을 사람이 쓴 것**이다. 짧지만 공짜는 아니라는 점이 중요하다.

같은 패턴이 상세 조회에도 나온다.

```kotlin
        val allIngredients = food.ingredientsByProbability()
        val codes = allIngredients.map { IngredientCode.valueOf(it.code) }.toSet()
        val catalog = (if (codes.isEmpty()) emptyList() else ingredientRepository.findByCodeIn(codes)).associateBy { it.code }
```
— `api/src/main/kotlin/com/kbap/api/food/FoodService.kt:85-87`

- 음식이 가진 성분 코드를 **먼저 다 모아서**(`toSet()`) 중복을 없애고,
- `findByCodeIn(codes)` **한 번**으로 성분 설명 카탈로그를 통째로 가져온다.
- 연관관계였다면 성분마다 `ingredient.name` 을 찍는 순간 SELECT 가 하나씩 나갔을 자리다.

### 3-2. 값 객체는 **JSON 컬럼**에 그대로 넣는다

"음식의 성분 목록"처럼 **그 부모 없이는 의미가 없고 따로 조회할 일도 없는 것**은 아예 별도 테이블로 쪼개지 않았다.

```kotlin
    @JdbcTypeCode(SqlTypes.JSON)
    @Column(name = "ingredients")
    var ingredients: List<FoodIngredient>? = emptyList(),
```
— `common/src/main/kotlin/com/kbap/common/domain/food/model/Food.kt:56-58`

```kotlin
data class FoodIngredient(
    // 생성자 인자 이름을 애너테이션으로 고정한다 — 파라미터 이름 정보 없이 역직렬화하는 매퍼(웹 요청 바인딩)가 있다.
    @JsonProperty("code") val code: String,
    @JsonProperty("inclusion_percent") val inclusionPercent: Int,
)
```
— `common/src/main/kotlin/com/kbap/common/domain/food/model/FoodIngredient.kt:6-10` (주석은 레포 원문)

- `@JdbcTypeCode(SqlTypes.JSON)` — 이 필드를 DB 의 JSON 컬럼에 통째로 직렬화해 넣으라는 지시. Hibernate 기능이다.
- `FoodIngredient` 는 `@Entity` 가 아니다. 식별자(id)도 없고 테이블도 없는 **값 객체(value object)** 다.
- 결과적으로 `food` 한 행을 읽으면 성분도 **같이 딸려 온다** — 추가 쿼리 0번. `@OneToMany` 로 만들었으면 여기가 N+1 1순위 후보였다.

**교환 조건**은 분명하다. JSON 안의 값으로는 인덱스를 태우거나 조인하기가 어렵다. 그래서 "성분 코드로 음식 검색" 같은 건 이 컬럼으로 못 하고, 별도 설계(벡터 검색 등)로 간다. **자주 조회 조건이 되는 것은 컬럼으로, 부모와 함께 읽고 함께 쓰는 것은 JSON 으로** — 이 판단이 설계의 핵심이다.

### 3-3. **SQL 조인은 쓴다** — 엔티티 연관과 조인은 다른 것

여기가 이 노트에서 가장 헷갈리기 쉬운 지점이다.

> [!important] 엔티티 매핑상의 연관 ≠ SQL 조인
> 금지된 것은 **엔티티 클래스에 연관 필드를 두는 것**이다. **쿼리에서 테이블을 조인하는 것은 금지되지 않았고, 실제로 쓴다.**

```kotlin
    @Query(
        nativeQuery = true,
        value = """
        select sh.food_id from scan_history sh
        join food f on f.id = sh.food_id
        where sh.member_id = :memberId
          and sh.status = 'ACTIVE'
          and f.status = 'ACTIVE'
          and f.content_status = 'READY'
        group by sh.food_id
        order by max(sh.created_at) desc
        limit :limit
        """,
    )
    fun findRecentReadyFoodIds(@Param("memberId") memberId: Long, @Param("limit") limit: Int): List<Long>
```
— `common/src/main/kotlin/com/kbap/common/domain/scan/ScanHistoryJpaRepository.kt:22-36`

- `nativeQuery = true` — JPQL 이 아니라 **DB 에 그대로 보내는 SQL** 이다. 엔티티 매핑을 안 거치므로 연관 유무와 무관하다.
- `join food f on f.id = sh.food_id` — **조인 조건을 사람이 명시**했다. 연관관계였다면 이 `on` 절을 JPA 가 매핑에서 유추했을 것이다.
- `select sh.food_id` — 엔티티가 아니라 **id 목록만** 뽑는다. 그래서 반환 타입이 `List<Long>` 이다.
- 조인의 역할이 "데이터를 붙여 오기"가 아니라 **"거르기"**(비활성·미완성 음식 제외)라는 점을 보라. 붙여 오는 일은 3-1 의 `findByIdIn` 이 맡는다.

JPQL 쪽에서도 조인 없는 집계·투영은 그대로 쓴다.

```kotlin
        select new com.kbap.common.domain.food.dto.FoodStatusCount(f.contentStatus, count(f))
```
— `common/src/main/kotlin/com/kbap/common/domain/food/FoodJpaRepository.kt:19`

- `select new …` — 엔티티가 아니라 **DTO 를 직접 만들어** 반환하는 JPQL 문법(생성자 표현식). 통계·카운트처럼 엔티티가 필요 없는 조회에 쓴다.
- 엔티티를 안 만들면 영속성 컨텍스트에 올라가지도 않는다([[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]).

**정리하면**: kbap 이 버린 건 "객체 그래프 탐색"이지 "관계형 DB 의 조인"이 아니다. 조인이 필요하면 **쿼리에 직접 쓴다.**

## 4. 2단계 키셋 페이징 — 페이징과 조인의 고전적 충돌

음식 목록을 커서로 넘기는 조회는 **일부러 두 번 나눠 돈다.** 왜 그러는지가 이 노트의 실전 하이라이트다.

### 4-1. 실코드

**1단계 — id 만 커서로 페이징한다.**

```kotlin
    @Query(
        """
        select f.id from Food f
        where (:cursor is null or f.id < :cursor)
          and f.contentStatus = 'READY'
        order by f.id desc
        """,
    )
    fun findFoodPageIds(@Param("cursor") cursor: Long?, pageable: Pageable): List<Long>

    fun findByIdIn(ids: List<Long>): List<Food>
```
— `common/src/main/kotlin/com/kbap/common/domain/food/FoodJpaRepository.kt:107-117`

- `select f.id` — **엔티티가 아니라 id 만** 뽑는다. 가벼운 쿼리다.
- `:cursor is null or f.id < :cursor` — 첫 페이지면 조건 없음, 다음 페이지면 "직전 페이지 마지막 id 보다 작은 것". 이게 **키셋(커서) 페이징**이다.
- `order by f.id desc` + `pageable` — 정렬 + `limit`. `OFFSET` 을 쓰지 않으므로 뒤 페이지로 갈수록 느려지지 않는다.
- `findByIdIn` — 이름만으로 쿼리가 만들어지는 Spring Data 파생 쿼리. 2단계에서 쓴다.

**2단계 — 그 id 로 본체를 한 번에 가져온다.**

```kotlin
    @Transactional(readOnly = true)
    internal fun getFoods(cursor: Long?, size: Int): List<Food> =
        loadDescending(foodRepository.findFoodPageIds(cursor, PageRequest.of(0, size)))
```
— `api/src/main/kotlin/com/kbap/api/food/FoodService.kt:46-48`

```kotlin
    private fun loadDescending(ids: List<Long>): List<Food> {
        if (ids.isEmpty()) return emptyList()
        return foodRepository.findByIdIn(ids).sortedByDescending { it.id }
    }
```
— `api/src/main/kotlin/com/kbap/api/food/FoodService.kt:207-210`

- 총 **쿼리 2번**. 목록 크기가 20이든 100이든 2번이다. 이게 "예측 가능한 쿼리 수"의 실물이다.
- `sortedByDescending { it.id }` — 3-1 에서와 같은 이유. `IN` 조회 결과 순서는 보장되지 않는다.

### 4-2. 왜 굳이 두 번 나누나

한 번에 하면 안 되는 이유가 있다. **페이징(`limit`)과 조인은 같이 쓰면 사고가 난다.**

목록 20개를 가져오는데 각 음식에 성분이 5개씩 딸려 있다고 하자. 조인하면 결과 행이 **20 × 5 = 100줄**이 된다. 여기에 `limit 20` 을 걸면 DB 는 **행 20줄**을 자르지 — **음식 20개**를 잘라 주지 않는다. 결과적으로 음식 4개만 돌아온다.

이 때문에 JPA 에서 `join fetch` + 페이징을 같이 쓰면 Hibernate 는 **전체를 메모리로 읽어 와서 애플리케이션에서 자르는** 동작으로 넘어간다(예전 버전은 `HHH000104` 경고를 남겼다). 데이터가 커지면 그대로 메모리 사고다.

**2단계로 나누면 이 충돌이 사라진다.**

| 단계 | 조인 | 페이징 | 결과 |
|---|---|---|---|
| 1단계 (id 페이징) | 없음(또는 거르기용만) | **여기서 한다** | 행 = 음식 1:1 이므로 `limit` 이 정확하다 |
| 2단계 (본체 조회) | — | 안 한다 | 이미 확정된 20개 id 를 `IN` 으로 한 번에 |

kbap 은 연관관계가 없으니 애초에 `join fetch` 를 쓸 일이 없다 — **그래도 2단계 구조를 쓴다.** 1단계 쿼리에서 거르기용 조인·정렬·`LIKE` 검색 같은 무거운 조건을 처리하고, 2단계는 확정된 id 로만 읽기 때문에 **비싼 쿼리가 가벼운 컬럼(id)만 다루게** 되기 때문이다. 실제로 검색·스캔이력 조회도 전부 이 모양이다(`FoodService.kt:51-68`).

> [!warning] 기존 노트에 있던 옛 서술 — 2026-08-26 수리 완료
> [[페이징 — Offset vs No-Offset(Keyset·Cursor)]] 노트에는 "kbap 실코드에선 커서로 ID만 페이징 → 그 ID로 **join fetch** 2단계로 결합(`FoodRepositoryAdapter.findFoodPage`)"이라고 적혀 있었다. 2026-08-26 실측으로 **근거가 둘 다 없어서** 이 절의 내용으로 교체했다(그쪽 노트 하단에 수정 기록이 있다).
> - `join fetch` 는 레포 전체에 **0건**이다.
> - `FoodRepositoryAdapter` 라는 클래스는 **존재하지 않는다**(모듈·계층 개편으로 사라졌다).
> - 실제 코드는 `FoodJpaRepository.findFoodPageIds`(JPQL, id 만 선택) + `findByIdIn`, 조합은 `FoodService.loadDescending`.
> 2단계로 나눈다는 **구조 자체는 그때도 맞았다.** 틀렸던 건 "2단계째가 fetch join 이다"와 클래스 이름 둘뿐이다.

## 5. 트레이드오프 — 얻은 것과 잃은 것

연관관계를 버리는 건 공짜가 아니다. 한쪽만 보면 안 된다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| **쿼리 수** | 코드에 적힌 조회 호출 = 나가는 쿼리. **세어 볼 수 있다** | 자동으로 붙여 주는 편의가 없다 |
| **성능 사고** | N+1 이 **생길 통로가 없다** | 대신 `IN` 조회를 빠뜨려 **직접 루프 안에서 조회**하면 똑같이 N+1 이 난다(6절) |
| **예외** | 지연 로딩 실패(`LazyInitializationException`) 계열이 **원천 소멸** | — |
| **경계** | 도메인 컨텍스트끼리 객체로 얽히지 않아 **모듈 분리가 쉽다** | 컨텍스트를 넘나드는 조회를 서비스가 조립해야 한다 |
| **코드량** | 조회 의도가 **명시적**이라 읽기 쉽다 | **조합 코드를 사람이 손으로 쓴다** — `associateBy`·재정렬·빈 리스트 가드가 곳곳에 반복된다 |
| **무결성** | — | **DB 외래키 제약에 기대지 않는다.** 존재하지 않는 `foodId` 를 넣는 걸 코드 규율로 막아야 한다 |
| **탐색** | — | `food.reviews.first().member.nickname` 같은 **객체 그래프 탐색이 불가능**하다 |

**정직하게 말하면**: 이 선택은 "더 좋은 방법"이 아니라 **"자동화의 편의를 포기하고 예측 가능성을 산 것"** 이다. 팀이 작고 트래픽 패턴이 분명하며 성능 사고를 미리 막고 싶을 때 유리하고, 도메인 모델이 복잡하게 얽힌 화면을 빨리 만들어야 할 때는 불리하다.

> **FE 입장에서의 의미**: 앱은 홈 화면 한 번 부르면 필요한 게 다 붙어서 온다. 그 "한 번"은 서버가 알아서 마술을 부린 결과가 아니라, **서비스 코드가 조회 서너 개를 손으로 조립해 만든 것**이다. 새 필드를 응답에 하나 추가해 달라는 요청이 "그냥 필드 하나"가 아닌 이유이기도 하다 — 조회를 하나 더 붙이고 조합 코드를 고쳐야 할 수 있다.

## 6. 주의점 — 연관이 없어도 N+1 은 만들 수 있다

가장 중요한 함정이다. **연관관계를 지운 건 "자동으로 생기는" N+1 을 막은 것이지, N+1 자체를 불가능하게 만든 게 아니다.**

```kotlin
// 예시 — 이 레포에서 하면 안 되는 것
val foods = foodIds.map { foodRepository.findById(it).get() }   // N번 쿼리
```

`map` 안에서 리포지토리를 부르면 정확히 같은 사고가 난다. 다른 점은 **이번엔 코드에 다 보인다**는 것뿐이다.

| 체크 | 왜 |
|---|---|
| **루프 안에서 리포지토리를 부르는가** | 그게 N+1 이다. 밖으로 빼서 `…In(ids)` 한 번으로 |
| `…In(ids)` 앞에 **빈 리스트 가드**가 있는가 | 빈 `IN` 은 DB 에 따라 문법 오류거나 전체 조회가 된다 |
| `IN` 조회 결과를 **다시 정렬**했는가 | `IN` 은 순서를 보장하지 않는다. 커서 페이징에서 정렬이 무너지면 페이지가 어긋난다 |
| `ids` 가 **커질 수 있는가** | `IN` 목록이 수천 개가 되면 그것대로 느려진다. 페이지 크기로 상한이 잡혀 있는지 확인 |
| 새 엔티티에 `@ManyToOne` 을 붙이고 싶어졌는가 | ArchUnit 이 막는다. 필요하면 규칙을 바꾸는 논의부터 — 몰래 우회하지 않는다 |

## 7. 치트시트

```
[N+1 이란]
  목록 1번 + 항목마다 1번 = 1+N 번 쿼리
  FE 워터폴과 같은 구조인데, 코드에 안 보인다는 게 차이

[kbap 의 선택]
  엔티티 연관 애너테이션 0개 (ArchUnit 이 강제)
  엔티티끼리는 Long id 컬럼으로만 참조
  join fetch 0건

[관계를 표현하는 3가지]
  1. id 참조 + findByIdIn / findByCodeIn 으로 묶어 조회
  2. 부모와 한 몸인 값 객체는 JSON 컬럼 (Food.ingredients)
  3. 거르기·집계가 필요하면 쿼리에 직접 join (native / JPQL)
     ※ 엔티티 매핑상의 연관 ≠ SQL 조인. 후자는 쓴다

[목록 조회 표준 모양 — 2단계]
  1단계: select f.id … where id < :cursor order by id desc limit N   ← 페이징은 여기서
  2단계: findByIdIn(ids) → associateBy → 원래 순서로 재정렬          ← 본체는 여기서
  총 쿼리 2번, 목록 크기와 무관

[손으로 쓰는 조합 코드의 3종 세트]
  if (ids.isEmpty()) return emptyList()
  .associateBy { it.id }
  ids.mapNotNull { map[it] }   또는  .sortedByDescending { it.id }
```

## 8. 용어집

- **연관관계(association)**: 엔티티 클래스가 다른 엔티티를 **필드로** 들고 있는 것. `@OneToMany`·`@ManyToOne`·`@OneToOne`·`@ManyToMany`. kbap 은 전부 금지.
- **N+1 문제**: 목록 조회 1번 뒤에 항목 수만큼 추가 조회가 나가는 성능 문제.
- **fetch join (`join fetch`)**: 조회 시점에 연관 엔티티까지 한 번에 가져오는 JPQL 문법. N+1 의 표준 처방이지만 페이징과 충돌한다. **kbap 에는 0건.**
- **지연 로딩(lazy loading)**: 연관 필드를 실제로 쓸 때 그제야 조회하는 방식. 연관이 없으므로 이 레포에는 해당 개념 자체가 없다.
- **키셋 페이징(keyset / cursor paging)**: `OFFSET` 대신 "직전 마지막 값보다 작은/큰 것"으로 다음 페이지를 잡는 방식. 자세히는 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]].
- **투영(projection)**: 엔티티 전체가 아니라 필요한 컬럼·DTO 만 뽑는 조회. JPQL 의 `select new …` 나 `select f.id`.
- **값 객체(value object)**: 식별자 없이 값 자체로 의미가 결정되는 객체. `FoodIngredient` 처럼 테이블 없이 JSON 컬럼에 들어가기도 한다.
- **네이티브 쿼리(native query)**: JPQL 이 아니라 DB SQL 을 그대로 보내는 조회. `@Query(nativeQuery = true)`.
- **ArchUnit**: 컴파일된 클래스를 읽어 "이런 구조는 금지"를 테스트로 검사하는 라이브러리. 자세히는 뒤의 13번 노트.

## 9. 다음에 빠른 재현 체크리스트

1. **"이 엔티티는 저 엔티티랑 어떻게 이어지지?"** → 연관 필드를 찾지 말고 **`…Id: Long` 필드**를 찾는다. 그게 외래키다.
2. **"이 목록 조회는 쿼리 몇 번 나가지?"** → 서비스 메서드에서 **리포지토리 호출 줄만 세면 된다.** 숨은 쿼리가 없다는 게 이 설계의 값어치다.
3. **목록을 새로 만들 때** → `…PageIds`(id + 커서 + limit) → `findByIdIn` → 재정렬. 기존 `FoodService.getFoods` 를 그대로 베낀다.
4. **여러 항목의 부가 정보가 필요할 때** → 루프를 돌기 전에 **id·code 를 다 모아서** `…In(…)` 한 번 → `associateBy` 로 맵 → 루프에서 맵만 조회.
5. **조인이 꼭 필요할 때** → 엔티티에 연관을 붙이는 게 아니라 **리포지토리에 쿼리를 쓴다**(JPQL 또는 `nativeQuery = true`). 반환은 보통 **id 목록이나 DTO**.
6. **리뷰에서 볼 것** → `for`/`map` 블록 안에 리포지토리 호출이 있으면 잡는다.

이 설계가 실제 화면 하나를 어떻게 만드는지는 뒤의 5단계 흐름 노트들에서 계속 나온다 — 특히 [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지]] §8 에 주문 항목의 음식 썸네일을 연관 없이 배치로 붙이는 실전 사례가 있다(주문 → 항목 → 음식 3단을 쿼리 3번으로 접는다). 자기 참조 트리를 같은 방식으로 조립하는 실전은 [[25. 커뮤니티 흐름 — 포스팅·댓글·커서 페이징]] §6-3.
