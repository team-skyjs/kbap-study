# 8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델

> 작성: 2026-08-26 · 맥락: [[6. 설정과 프로필, 트랜잭션 경계]] 에서 "`save()` 를 안 부르는데 DB 가 바뀐다"를 보고 넘어갔다. 그걸 가능하게 하는 장치가 **영속성 컨텍스트**다. kbap 의 `common/domain/**` 아래 클래스를 열면 이 장치를 전제로 쓰인 코드밖에 없어서, 이걸 모르면 도메인 코드가 통째로 안 읽힌다.
> 목표: **"객체를 고치면 DB 가 따라 바뀐다"** 가 마법이 아니라 **언제·어떤 순서로 일어나는 일**인지 말할 수 있게 되기. 그리고 kbap 의 엔티티 클래스 하나를 열었을 때 애너테이션이 각각 뭘 하는지 읽어낼 수 있게 되기.

---

## 0. 한 줄 요약

**영속성 컨텍스트**는 트랜잭션이 열려 있는 동안 스프링/JPA 가 들고 있는 **작업대**다. 여기 올라온 엔티티 객체는 **"DB 의 그 행 자체"** 로 취급되어, 필드를 바꾸면 나중에 UPDATE 문이 자동으로 나간다. 그리고 kbap 에서 **그 엔티티 클래스가 곧 도메인 모델**이다 — 별도의 도메인 객체도, `toDomain()` 같은 변환도 없다.

---

## 1. 시작하기 전에 — FE 에는 없는 감각 하나

FE 에서 서버 데이터를 고치는 코드는 **항상 이렇게 생겼다.**

```ts
// 예시 (FE)
const profile = await fetchProfile(memberId);
profile.nickname = "새닉네임";
await patchProfile(memberId, { nickname: "새닉네임" }); // ← 이 줄이 없으면 아무 일도 안 일어난다
```

`profile` 은 서버에서 받아 온 **복사본**이다. 이 객체를 아무리 고쳐도 서버는 모른다. **"내가 고쳤다"를 따로 알려 주는 줄(`patchProfile`)이 반드시 있어야 한다.** 이게 FE 개발자의 기본 감각이다.

백엔드에서 JPA 를 쓰면 **이 감각이 뒤집힌다.** 트랜잭션 안에서 읽어 온 엔티티 객체는 복사본이 아니라 **DB 행의 대리인**이다. 필드를 바꾸는 것 자체가 곧 "DB 를 고치겠다"는 선언이고, 알려 주는 줄은 없다.

```kotlin
// 예시 (kbap 스타일 — 이게 전부다)
val member = memberRepository.findById(memberId).orElseThrow()
member.nickname = "새닉네임"
// save() 없음. 트랜잭션이 끝날 때 UPDATE 가 나간다.
```

이 노트는 사실상 **"왜 두 번째 코드가 동작하는가"** 한 문장을 풀어 쓴 것이다.

## 2. 영속성 컨텍스트 — 트랜잭션 동안 열리는 작업대

### 2-1. 핵심 개념

**영속성 컨텍스트(persistence context)** 는 "지금 이 트랜잭션에서 다루는 엔티티들을 모아 둔 메모리 공간"이다. 하이버네이트 공식 문서는 이걸 **"현재 트랜잭션에서 읽어 온 데이터의 캐시"** 라고 설명하고, 그 안에서 **엔티티 식별자 하나당 객체 하나** 라는 대응이 보장된다고 못 박는다.

여기에 올라온 엔티티는 **네 가지 상태** 중 하나다.

| 상태 | 한국어 | 뜻 | 어떻게 이 상태가 되나 |
|---|---|---|---|
| transient | 비영속 | 그냥 `new` 로 만든 객체. JPA 가 모른다 | `Food("김치찌개")` |
| **persistent (managed)** | **영속 / 관리 중** | **작업대 위에 있음. 변경이 추적된다** | 리포지토리로 조회했거나 `save()` 로 저장한 직후 |
| detached | 준영속 | 작업대에서 내려옴. 고쳐도 DB 에 안 간다 | 트랜잭션이 끝난 뒤의 그 객체 |
| removed | 삭제 예정 | 지울 것으로 표시됨 | `delete()` (단, kbap 은 소프트 삭제라 이 상태를 거의 안 쓴다 — 5-4 절) |

**이 노트에서 중요한 건 딱 하나다: `managed` 상태의 객체를 고치면 DB 가 따라 바뀐다.** 나머지 세 상태는 "그게 아닐 때"를 구분하기 위해 존재한다.

작업대가 **열리고 닫히는 시점**은 [[6. 설정과 프로필, 트랜잭션 경계]] 에서 본 트랜잭션 경계와 사실상 같다.

```
@Transactional 메서드 진입  →  작업대 펼침
  조회 → 엔티티가 작업대에 올라옴 (managed)
  필드 변경 → 아직 DB 엔 아무것도 안 감
메서드 정상 종료          →  flush(모아 둔 변경을 SQL 로) → commit → 작업대 접음
```

### 2-2. 비유 — React Query 캐시

FE 에서 가장 가까운 물건은 **React Query 의 캐시**다.

| | React Query 캐시 | 영속성 컨텍스트 |
|---|---|---|
| 하는 일 | 같은 키로 두 번 조회하면 서버에 안 가고 캐시가 답한다 | 같은 id 로 두 번 조회하면 DB 에 안 가고 작업대가 답한다 |
| 식별 방법 | `queryKey`(`['member', 3]`) | **엔티티 타입 + id**(`Member`, `3`) |
| 같은 것을 두 번 꺼내면 | 같은 데이터 | **같은 객체** — `===` 가 참이다 |

같은 트랜잭션 안에서 `getMember(3)` 을 두 번 부르면 **SELECT 는 한 번만 나가고, 두 번 다 완전히 같은 객체가 돌아온다.** 그래서 한 곳에서 필드를 바꾸면 다른 곳에서도 바뀐 값이 보인다.

> [!warning] 비유의 경계 — 여기서부터 완전히 다르다
> **① 수명이 다르다.** React Query 캐시는 **화면을 넘나들며 몇 분씩 산다**(`staleTime`·`gcTime`). 영속성 컨텍스트는 **트랜잭션 하나가 열려 있는 동안만** 산다 — 보통 서비스 메서드 하나, 밀리초 단위다. 요청이 끝나면 통째로 버려진다. **요청 사이에 공유되는 게 아니다.**
> **② 변경 추적이 있다.** React Query 캐시는 **읽기 전용 사본 보관소**다. 캐시 안의 객체를 직접 고쳐 봐야 서버로 아무것도 안 간다(그래서 `useMutation` 이 따로 있다). 영속성 컨텍스트는 **읽기 캐시 + 변경 추적기**다 — 이게 3절 전체의 주제이고, 두 물건의 결정적 차이다.
> **③ 무효화 개념이 다르다.** React Query 는 `invalidateQueries` 로 "다시 받아 와"를 지시한다. 영속성 컨텍스트에서 대응하는 건 `clear()`/`refresh` 인데, 애초에 트랜잭션마다 새로 만들어지므로 **직접 무효화할 일이 거의 없다.** 예외가 벌크 UPDATE 다(4-3 절).
> **④ 여러 서버 사이에서 공유되지 않는다.** kbap 은 여러 인스턴스로 뜰 수 있고, 각 인스턴스의 각 요청이 **자기만의 작업대**를 쓴다. "캐시" 라는 단어에 끌려 "서버 전체가 공유하는 캐시" 로 오해하면 안 된다. 그런 캐시는 [[6. 설정과 프로필, 트랜잭션 경계]] 밖의 얘기이고, kbap 에서 Redis 가 하는 일도 캐시가 아니다(29번 노트 예정).

## 3. 변경 감지 — `save()` 가 없는 이유

### 3-1. 실코드 — 저장하는 줄이 없는 저장 로직

```kotlin
    fun completeOnboarding(
        nickname: String,
        avoidanceSubstanceCodes: List<String>,
        dietCategories: List<String> = emptyList(),
        spicinessPreference: String,
        countryCode: String,
        profileImageUrl: String,
    ) {
        if (onboardingCompleted) {
            throw BusinessException(ErrorCode.ONBOARDING_ALREADY_COMPLETED)
        }
        updateProfile(…)
        onboardingCompleted = true
    }
```
— `common/src/main/kotlin/com/kbap/common/domain/member/model/Member.kt:129-150`

- 이 메서드는 **`Member` 엔티티 클래스 안에** 있다. 리포지토리도, `EntityManager` 도, `save()` 도 나오지 않는다.
- 하는 일은 `if` 로 한 번 막고, 자기 필드 몇 개를 바꾸고, `onboardingCompleted = true` 를 대입하는 것뿐이다. **평범한 Kotlin 객체 조작**처럼 생겼고, 실제로도 그렇다.
- 이걸 부르는 쪽(`api/src/main/kotlin/com/kbap/api/member/MemberService.kt:22-32`)에도 저장 줄이 없다 — `@Transactional` 한 줄과 이 메서드 호출이 전부다. 그 코드는 [[6. 설정과 프로필, 트랜잭션 경계]] 3-3 절에 발췌해 뒀다.

그런데 온보딩은 DB 에 저장된다. **누가 저장했나?**

### 3-2. 메커니즘 — 스냅샷과 대조

**변경 감지(dirty checking)** 라고 부른다. 순서는 이렇다.

1. **로드 시점** — 엔티티가 작업대에 올라올 때, JPA 는 그 객체를 넣어 두는 동시에 **필드 값들을 따로 한 벌 복사해 둔다**(스냅샷).
2. **작업 중** — 코드가 `onboardingCompleted = true` 를 해도 아무 일도 안 일어난다. 그냥 메모리 위 객체가 바뀔 뿐이다.
3. **flush 시점** — 작업대 위 모든 엔티티에 대해 **지금 값 ↔ 스냅샷을 비교**한다. 다른 필드가 있으면 그 엔티티에 대한 UPDATE 문을 만든다.
4. **commit** — 트랜잭션이 확정된다.

하이버네이트 공식 문서의 표현대로, **관리 중인 엔티티의 변경은 `save`/`update` 호출 없이 자동으로 감지되어 flush 때 DB 로 나간다.**

> [!tip] 그래서 `save()` 를 부르면?
> **아무 효과가 없다.** 이미 작업대 위에 있는 엔티티를 `save()` 해도 변경 감지가 어차피 잡아냈을 UPDATE 가 나갈 뿐이다. kbap 이 `CLAUDE.md:121` 에서 *"상태 변경은 관리 엔티티 dirty checking(불필요한 `save()` 호출 금지)"* 라고 못 박은 이유다. **`save()` 를 부르는 쪽이 규약 위반**이고, 리뷰에서 지적당한다.
> `save()` 가 진짜로 필요한 곳은 **새로 만든 객체를 처음 작업대에 올릴 때**뿐이다(`OrderService.kt:50` 의 `saveAndFlush`, `OrderService.kt:55` 의 `saveAll`).

### 3-3. 소프트 삭제도 그냥 필드 변경이다

```kotlin
    fun withdraw() {
        providerUid = deletedProviderUid(id)
        delete()
    }
```
— `common/src/main/kotlin/com/kbap/common/domain/member/model/Member.kt:152-155`

- `delete()` 는 `BaseEntity` 가 준 메서드인데, **행을 지우는 게 아니라 `status` 필드를 `DELETED` 로 바꾼다**(5-4 절). 즉 여기서 일어나는 건 필드 대입 두 번뿐이다.
- `providerUid` 를 "삭제된 값"으로 바꾸는 건 같은 소셜 계정으로 **재가입할 수 있게** 하려는 것이다 — `provider + provider_uid` 에 unique 제약이 걸려 있어서(`Member.kt:20`), 탈퇴한 행이 그 값을 계속 붙들고 있으면 재가입이 막힌다.
- 삭제조차 UPDATE 라서, **변경 감지 하나로 전부 처리된다.** JPA 의 `removed` 상태를 쓰는 곳이 kbap 엔 사실상 없다.

## 4. flush ≠ commit

FE 감각으로 가장 헷갈리는 지점이다. 둘 다 "반영" 처럼 들리는데 **전혀 다른 층위**의 일이다.

| | flush | commit |
|---|---|---|
| 뜻 | 작업대의 변경분을 **SQL 문으로 만들어 DB 로 보낸다** | 트랜잭션을 **확정**한다 |
| 이후 롤백 가능? | **가능** — 아직 트랜잭션 안이다 | 불가능 — 끝났다 |
| 다른 트랜잭션에서 보이나? | **안 보인다** | 보인다 |
| 몇 번 일어나나 | 트랜잭션 하나에서 **여러 번** 가능 | **딱 한 번** |
| 누가 부르나 | 대부분 JPA 가 알아서 | 트랜잭션 매니저 (`@Transactional` 종료 시) |

> [!important] 한 줄로
> **flush = "DB 야, 이거 실행해 봐"** / **commit = "방금 것들 전부 확정"**
> flush 만 하고 예외가 터지면 **전부 없던 일이 된다.** SQL 이 이미 나갔더라도 그렇다.

기본 동작(`FlushMode.AUTO`)에서 JPA 는 **커밋 직전**과 **쿼리 실행 직전**에 알아서 flush 한다. 쿼리 직전에 하는 이유는 명확하다 — 방금 바꾼 값이 반영 안 된 채로 SELECT 하면 결과가 어긋나기 때문이다.

### 4-1. 실코드 — 일부러 먼저 flush 하는 자리

```kotlin
    private fun saveOrder(memberId: Long, request: OrderCreateRequest, roadAddress: String?): Long {
        val order = try {
            orderRepository.saveAndFlush(request.toOrder(memberId, roadAddress))
        } catch (e: DataIntegrityViolationException) {
            if (isImagePathConflict(e)) throw BusinessException(ErrorCode.ORDER_ALREADY_PLACED)
            throw e
        }
        orderItemRepository.saveAll(request.items.map { it.toItem(order.id) })
        return order.id
    }
```
— `api/src/main/kotlin/com/kbap/api/order/OrderService.kt:48-57`

- `saveAndFlush` 는 `save` + **"지금 당장 flush 해"** 다. 왜 굳이?
- `order` 테이블의 `image_path` 에는 unique 제약이 걸려 있다. 그냥 `save` 만 하면 INSERT 는 **트랜잭션이 끝날 때** 나가고, 그때 터지는 제약 위반 예외는 **이 `try` 블록 밖**에서 발생한다 — 잡을 수가 없다.
- `saveAndFlush` 로 INSERT 를 **지금 여기서** 실행시키면, 제약 위반이 `DataIntegrityViolationException` 으로 **이 `catch` 에 잡힌다.** 그래야 "이미 주문한 사진입니다"(`ORDER_ALREADY_PLACED`) 라는 우리 에러 코드로 바꿔 줄 수 있다.
- **이게 flush 와 commit 이 다르다는 걸 실무에서 써먹는 전형적인 방법이다.** "DB 에 물어보되 아직 확정하지는 않는다" 가 가능하기 때문에 성립한다. 예외를 잡아 다른 예외로 바꿔 던져도 트랜잭션은 여전히 롤백된다.

### 4-2. 실코드 — 작업대를 우회하는 벌크 UPDATE

```kotlin
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query(
        """
        update Member m
        set m.scanCount = m.scanCount + 1
        where m.id = :memberId
          and m.memberStatus = com.kbap.common.domain.member.model.MemberStatus.ACTIVE
        """,
    )
    fun increaseScanCount(@Param("memberId") memberId: Long): Int
```
— `common/src/main/kotlin/com/kbap/common/domain/member/MemberJpaRepository.kt:22-31`

이건 변경 감지를 **안 쓰는** 코드다. 엔티티를 읽지도 않고 UPDATE 문을 DB 로 바로 던진다. 그리고 그 대가로 두 개의 옵션이 필요해진다.

- **`flushAutomatically = true`** — 이 UPDATE 를 던지기 **전에** 작업대에 쌓인 변경분을 먼저 밀어낸다. 안 그러면 아직 반영 안 된 변경 위에 이 UPDATE 가 실행돼 순서가 뒤엉킨다.
- **`clearAutomatically = true`** — 이 UPDATE 를 던진 **후에** 작업대를 비운다. **UPDATE 가 작업대를 거치지 않고 DB 만 바꿨으므로, 작업대 위의 `Member` 객체는 옛 `scanCount` 를 들고 있는 낡은 값이 됐기 때문이다.** 비우지 않으면 같은 트랜잭션에서 그 회원을 다시 읽었을 때 **증가 전 값**을 받는다.

> [!warning] 이 두 옵션이 영속성 컨텍스트를 이해했는지 판별하는 시험지다
> "캐시가 있다" 는 걸 모르면 `clearAutomatically` 가 왜 필요한지 절대 설명할 수 없다. 반대로 **작업대라는 그림이 있으면 두 옵션이 각각 "들어가기 전 정리"·"나온 뒤 청소" 라는 게 바로 보인다.**
> 왜 굳이 변경 감지를 버리고 벌크 UPDATE 를 쓰는지(동시에 여러 요청이 카운트를 올릴 때의 정합성)는 랭킹 흐름 노트(23번, 미작성)의 주제다.

## 5. 엔티티 매핑 — 클래스 하나가 테이블 하나

여기서부터는 "객체 ↔ 행" 을 **어떻게 이어 붙였다고 선언하는가** 다. 전부 애너테이션이다.

### 5-1. 테이블과 컬럼

```kotlin
@Entity
@Table(
    name = "food",
    uniqueConstraints = [UniqueConstraint(name = "uq_food_korean_name", columnNames = ["korean_name"])],
)
class Food(
    @Column(name = "korean_name", nullable = false, length = 255)
    var koreanName: String = "",
```
— `common/src/main/kotlin/com/kbap/common/domain/food/model/Food.kt:16-23`

- **`@Entity`** — "이 클래스는 테이블 한 행에 대응한다". 이게 붙어야 JPA 가 관리 대상으로 본다.
- **`@Table(name = "food")`** — 어느 테이블인지. 안 쓰면 클래스 이름이 그대로 테이블 이름이 되는데, kbap 은 **항상 명시**한다.
- **`@Column(name = "korean_name", …)`** — 어느 컬럼인지. Kotlin 은 카멜케이스(`koreanName`), MySQL 은 스네이크케이스(`korean_name`) 라 이 매핑이 필요하다.
- `length = 255` 는 **MySQL 기준으로 고정**한다는 규약이다(`CLAUDE.md:119`). H2 같은 다른 DB 호환은 고려하지 않는다 — 테스트도 MySQL Testcontainers 로 돌리기 때문이다.
- **주의**: 여기 적힌 `nullable`·`length`·`uniqueConstraints` 가 실제로 테이블을 만들지는 **않는다.** 스키마를 만드는 건 Flyway 마이그레이션이고, 이 애너테이션은 **"내가 아는 스키마는 이렇다"는 선언**일 뿐이다. 둘이 어긋나면 부팅이 실패한다(5-5 절).

JSON 컬럼도 있다.

```kotlin
    @JdbcTypeCode(SqlTypes.JSON)
    @Column(name = "name_translations", nullable = false)
    var nameTranslations: Map<String, String> = emptyMap(),
```
— `common/src/main/kotlin/com/kbap/common/domain/food/model/Food.kt:40-42`

- `Map`·`List` 같은 컬렉션을 **MySQL 의 JSON 컬럼 한 칸에 통째로 넣는다**. `Food.ingredients`(`Food.kt:56-58`)도 같은 방식이다.
- 즉 별도 테이블을 만들지 않고 한 행 안에서 끝낸다. **"왜 성분을 별도 테이블로 빼고 연관관계로 잇지 않는가"** 는 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 의 주제다.

### 5-2. `@Id` — 행을 가리키는 이름표

```kotlin
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    open val id: Long = 0
```
— `common/src/main/kotlin/com/kbap/common/domain/BaseEntity.kt:18-20`

- **`@Id`** — 이 필드가 기본키. 2절에서 말한 "작업대는 id 하나당 객체 하나" 의 그 id 다.
- **`@GeneratedValue(IDENTITY)`** — 값을 **DB 가 만든다**(MySQL AUTO_INCREMENT). 그래서 저장 전에는 `0` 이고, INSERT 가 실제로 실행된 뒤에야 진짜 값이 들어온다.
- 이게 4-1 절 `saveAndFlush` 의 **두 번째 이유**이기도 하다. `orderItemRepository.saveAll(… it.toItem(order.id))` 이 `order.id` 를 필요로 하는데, flush 를 안 하면 그 시점에 id 가 아직 `0` 이다.

### 5-3. `BaseEntity` — 22개 엔티티가 공유하는 네 필드

kbap 의 모든 엔티티는 `BaseEntity` 를 상속한다(레포 실측 기준 `@Entity` 클래스 22개).

```kotlin
@MappedSuperclass
@SQLRestriction("status = 'ACTIVE'")
abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    open val id: Long = 0

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, columnDefinition = "ENUM('ACTIVE','DELETED')")
    private var status: EntityStatus = EntityStatus.ACTIVE

    @CreationTimestamp
    open val createdAt: LocalDateTime = LocalDateTime.MIN

    @UpdateTimestamp
    open val updatedAt: LocalDateTime = LocalDateTime.MIN
```
— `common/src/main/kotlin/com/kbap/common/domain/BaseEntity.kt:15-30`

- **`@MappedSuperclass`** — "이 클래스 자체는 테이블이 아니지만, **상속받는 클래스에 이 필드들을 얹어라**". `base_entity` 테이블은 없고, `food`·`member` 테이블 각각에 `id`·`status`·`created_at`·`updated_at` 컬럼이 생긴다.
- **`@CreationTimestamp` / `@UpdateTimestamp`** — 하이버네이트가 INSERT 시점·UPDATE 시점에 **알아서 채운다.** 그래서 서비스 코드에 `createdAt = LocalDateTime.now()` 같은 줄이 없다.
- 규약: **개별 엔티티는 자기 id 나 생성/수정 시각을 따로 두지 않는다**(`CLAUDE.md:118`). 새 엔티티를 만들 때 이 네 개를 다시 쓰면 리뷰에서 지적당한다.
- 도메인 고유의 상태는 **컬럼명을 분리**한다 — `Member` 의 활성/정지 상태는 `status` 가 아니라 `member_status`(`Member.kt:58`)다. `status` 는 소프트 삭제 전용으로 예약돼 있다.

> [!warning] `status` 가 두 종류처럼 보이는 순간 — 헷갈리면 여기로 돌아올 것
> | | 무엇 | 값 | 누가 바꾸나 |
> |---|---|---|---|
> | **`status`** (`BaseEntity`) | **소프트 삭제 플래그** — "이 행이 살아 있나" | `ACTIVE` / `DELETED` | `delete()` / `active()` |
> | **`contentStatus`** (`Food`) | **콘텐츠 생명주기** — "설명·이미지가 어디까지 준비됐나" | `READY` · `PENDING_REVIEW` · `PENDING_IMAGE` … | 검수·수집 흐름 |
> | **`memberStatus`** (`Member`) | **회원 상태** — "활동 중인가 탈퇴했나" | `ACTIVE` / `WITHDRAWN` … | 탈퇴·복구 흐름 |
>
> **셋은 서로 독립된 축**이다. 이름이 비슷해 섞이기 쉬운데, `@SQLRestriction` 이 거르는 건 **첫 번째 하나뿐**이다.
> 예: 음식을 삭제했다 복원하면 `status` 는 `DELETED`→`ACTIVE` 로 돌아오지만 **`contentStatus` 는 삭제 전 값 그대로 보존**된다.

### 5-4. 소프트 삭제 — 지우지 않고 감춘다

`BaseEntity` 맨 위의 이 한 줄이 kbap 전체의 삭제 정책이다.

```kotlin
@SQLRestriction("status = 'ACTIVE'")
```
— `common/src/main/kotlin/com/kbap/common/domain/BaseEntity.kt:16`

- **하이버네이트가 이 엔티티를 조회하는 모든 SQL 에 `and status = 'ACTIVE'` 를 자동으로 붙인다.** `@MappedSuperclass` 에 붙어 있으니 22개 엔티티 전부에 적용된다.
- 그래서 **리포지토리 쿼리에 status 조건을 직접 쓰지 않는다.** 쓰면 중복이다.
- 삭제는 행 제거가 아니라 `BaseEntity.delete()` → `status = DELETED` 다(3-3 절). 데이터는 남아 있고, 조회에서만 사라진다.

| | 하드 삭제 (`DELETE FROM …`) | kbap 의 소프트 삭제 |
|---|---|---|
| 행 | 사라진다 | 남는다 |
| 복구 | 불가 | `active()` 한 줄 |
| 참조하던 다른 행 | 외래키가 깨지거나 연쇄 삭제 | **그대로 유효** |
| 실수로 지웠을 때 | 백업 복원 | 되돌리면 끝 |
| 대가 | — | 테이블이 계속 커지고, **status 조건을 빠뜨리면 유령 데이터가 보인다** |

마지막 대가를 `@SQLRestriction` 이 구조적으로 막아 준다 — 사람이 매번 조건을 쓰는 게 아니라 프레임워크가 붙이기 때문이다.

> [!note] 그래서 외래키에 `ON DELETE` 정책이 없다
> 행이 실제로 지워지지 않으니 연쇄 삭제를 정의할 이유가 없다(`CLAUDE.md:117`). 이 구조가 크로스 도메인 참조 방식에도 영향을 주는데, 그 얘기는 [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 소관이다.

### 5-5. 스키마의 주인은 엔티티가 아니다

```yaml
  jpa:
    database-platform: org.hibernate.dialect.MySQLDialect
    hibernate:
      ddl-auto: validate
```
— `api/src/main/resources/application-local.yml:10-13` (`application-prod.yml:13-16`·테스트용 `api/src/test/resources/application.yml:7-9` 도 같다)

- **`ddl-auto: validate`** — 부팅할 때 **엔티티와 실제 테이블이 맞는지 검사만 하고, 절대 스키마를 건드리지 않는다.**
- JPA 에는 엔티티를 보고 테이블을 자동 생성하는 옵션(`create`·`update`)도 있지만 kbap 은 **쓰지 않는다.** 스키마의 주인은 Flyway 마이그레이션이고, 엔티티는 그걸 따라가는 쪽이다.
- 실전에서 이게 어떻게 나타나냐면 — **엔티티에 필드 하나를 추가하면 부팅이 실패한다.** 그 컬럼이 테이블에 없기 때문이다. 마이그레이션 SQL 을 먼저 쓰고 엔티티를 고치는 순서가 된다. 자세한 건 [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]].
- 로컬·운영·**테스트까지 셋 다 `validate`** 인 게 핵심이다. 테스트도 운영과 똑같은 마이그레이션으로 스키마를 만들기 때문에, "테스트는 통과했는데 배포하니 컬럼이 없다" 가 구조적으로 안 생긴다.

## 6. 엔티티가 곧 도메인 모델 — 변환 계층을 없앤 결정

여기가 이 노트에서 **역사가 있는 부분**이고, 옛 노트(2026-07 판)와 **정반대가 된 부분**이다.

### 6-1. 원래는 이렇지 않았다

kbap 은 원래 클린 아키텍처식으로 **도메인 모델과 JPA 엔티티를 분리**했다. 회원 하나를 다루는 데 필요한 조각이 다섯 개였다(ADR-0012 `docs/adr/0012-dissolve-persistence-module-and-ports.md`).

```
Member          ← 도메인 모델 (ORM 애너테이션 없음, 순수 Kotlin)
MemberRepository ← port 인터페이스
MemberJpaEntity  ← JPA 엔티티 (@Entity)  + toDomain() / from() 변환
MemberJpaRepository ← Spring Data 리포지토리
MemberRepositoryAdapter ← port 구현
```

이 구조의 논리는 깔끔하다. **"도메인은 JPA 를 몰라야 한다"** — 그래야 나중에 ORM 을 갈아 끼울 수 있고, 도메인 규칙이 영속 기술에 오염되지 않는다.

### 6-2. 지금은 이렇다

```
Member            ← @Entity 이면서 동시에 도메인 모델. 도메인 메서드가 여기 붙어 있다
MemberJpaRepository ← Spring Data 리포지토리 (public)
MemberService     ← 도메인 서비스 (com.kbap.api.member 소속)
```

**변환 코드가 아예 없다.** 레포 전체에서 엔티티↔도메인 모델 변환 함수는 **0개**다.

> [!note] 실측 — `toDomain()` 이 딱 하나 남아 있긴 하다
> `api/src/main/kotlin/com/kbap/api/review/ReviewCreateRequest.kt:116` 의 `fun toDomain(): ReviewPlace?`. 이건 **요청 DTO → 값 객체** 변환이라 성격이 다르다 — 밖에서 들어온 JSON 을 우리 타입으로 바꾸는 경계 작업이고, 6-1 절이 말한 "도메인 모델 ↔ 엔티티" 변환이 아니다. 이름이 같아서 헷갈리기 쉬우니 구분해 둔다.

### 6-3. 왜 뒤집었나

ADR-0012 와 ADR-0014(`docs/adr/0014-relax-persistence-encapsulation.md`)가 두 단계에 걸쳐 이 구조를 걷어냈다. 근거는 감상이 아니라 **비용 정산**이다.

| 분리 구조가 사 준 것 | 실제로 일어난 일 |
|---|---|
| "영속 기술을 갈아 끼울 수 있다" | **갈아 끼우는 일이 일어나지 않았다.** ADR-0012 의 표현으로는 *"현실적으로 일어나지 않는 교체에 대한 보험 해지"* |
| "도메인이 ORM 에 오염되지 않는다" | 경계를 지키는 건 어차피 리뷰와 ArchUnit 이었지, 클래스 분리가 아니었다 |
| "페이크 리포지토리로 단위 테스트" | 통합 테스트(MySQL Testcontainers)가 같은 시나리오를 커버했다 |

반대편 비용은 **매일** 냈다 — 기능 하나 추가할 때마다 다섯 조각을 만들고, 필드 하나 추가할 때마다 **도메인 모델·엔티티·변환 코드 세 군데를 같이 고쳐야** 했다. FE 로 치면 "API 응답 타입 · 화면 상태 타입 · 그 사이 매퍼" 를 모든 필드마다 손으로 유지하는 것과 같다.

ADR-0014 는 여기서 한 단계 더 갔다. 엔티티·리포지토리를 `internal` 로 감춰 뒀더니, **위임만 하는 창구 서비스**(`FoodContentBatchService` 등)가 계속 늘어났다 — 도메인 로직이 하나도 없는데 조각 수만 늘리는 클래스다. 그래서 `internal` 을 걷어내고 **리포지토리를 public** 으로 열었다.

### 6-4. 그래서 감수한 것

공짜는 아니다. **정직하게 세 가지를 내줬다.**

1. **엔티티가 ORM 에 묶인다.** `Member` 는 이제 `jakarta.persistence` 없이는 컴파일도 안 된다. 도메인 규칙을 담은 클래스가 영속 기술에 의존한다 — ADR-0012 가 *"순수 도메인 모듈 포기"* 라고 명시한 그 대가다.
2. **도메인 서비스를 우회할 수 있게 됐다.** 리포지토리가 public 이라, 아무 곳에서나 엔티티를 꺼내 비즈니스 로직을 거기 써 버릴 수 있다. 컴파일러가 막아 주던 걸 **이제 리뷰가 막는다**(ADR-0014 Consequences). 규약은 여전히 *"도메인 로직(검증·상태 전이·정책)은 도메인 서비스가 소유"* 다.
3. **도메인 규칙 테스트가 무거워졌다.** 페이크 리포지토리로 빠르게 돌리던 단위 테스트가 DB 를 띄우는 통합 테스트로 옮겨져 느려졌다.

> [!important] 판단의 성격
> 이건 "클린 아키텍처가 틀렸다" 가 아니라 **"이 팀·이 제품 규모에서는 값이 비용보다 작았다"** 는 계산이다. 팀이 커지고 도메인이 복잡해지면 결론이 달라질 수 있고, ADR 이 그때를 위해 남아 있는 것이다. 조각 수를 줄이는 결정과 경계를 지키는 결정은 **원래 서로 당긴다.**

### 6-5. 그래도 남아 있는 분리 — 값 객체

전부 합쳐진 건 아니다. **값 객체는 여전히 ORM 을 모른다.**

```kotlin
    val ranking: Ranking
        get() = Ranking.of(
            scanCount = scanCount,
            reviewCount = reviewCount,
            uniqueReviewedFoodCount = uniqueReviewedFoodCount,
        )
```
— `common/src/main/kotlin/com/kbap/common/domain/member/model/Member.kt:90-95`

- `Member` 는 DB 에 **카운트 세 개만** 저장한다. 점수·티어 같은 계산 결과는 컬럼이 아니다.
- `ranking` 은 필드가 아니라 **계산 프로퍼티**(`get()`)다. 부를 때마다 `Ranking` 객체를 새로 만든다.
- `Ranking`(`common/src/main/kotlin/com/kbap/common/domain/member/model/Ranking.kt`)에는 JPA 애너테이션이 하나도 없다. 순수 계산 로직만 있다.
- **이 경계는 ArchUnit 이 강제한다** — *"도메인 모델은 ORM-free 다 — 도메인 안에서 `jakarta.persistence` 는 엔티티·리포지토리·도메인 서비스만 만진다"*(`api/src/test/kotlin/com/kbap/api/architecture/ModuleBoundaryTest.kt:89`). 값 객체·정책 클래스가 JPA 를 건드리면 **테스트가 깨진다.**

> [!note] 예외 하나 — `@Embeddable`
> 값 객체 중에도 **저장돼야 하는 것**은 있다. `ReviewPlace`(`common/src/main/kotlin/com/kbap/common/domain/review/model/ReviewPlace.kt`)가 그런 경우로, `@Embeddable` 이 붙어 `Review` 엔티티 안에 `@Embedded var place: ReviewPlace?`(`Review.kt:39-40`)로 들어간다. 별도 테이블이 아니라 **`review` 테이블의 컬럼 몇 개로 펼쳐진다.** 위 ArchUnit 규칙이 `@Embeddable` 을 예외 목록에 넣어 둔 이유다(`ModuleBoundaryTest.kt:93`). 레포 전체에서 `@Embeddable` 은 이 하나뿐이다.

정리하면 **"엔티티가 도메인 모델" 이라는 말은 "도메인 코드 전부가 JPA 에 묶였다" 는 뜻이 아니다.** 저장되는 상태를 든 클래스만 엔티티이고, 그 상태로부터 계산되는 것들은 여전히 ORM 과 무관하다. ArchUnit 규칙 전반은 13번 노트(경계를 지키는 테스트, 미작성)가 다룬다.

## 7. Kotlin + JPA 의 함정

JPA 는 **Java 로 설계된 규격**이라 Kotlin 의 기본값과 정면으로 충돌한다. 이 충돌을 컴파일러 플러그인 하나로 덮고 있다는 걸 알아 둬야 한다.

### 7-1. 충돌 지점 두 개

| JPA 가 요구하는 것 | Java 기본 | **Kotlin 기본** |
|---|---|---|
| 인자 없는 생성자 | 없으면 직접 써야 하지만 흔한 관행 | **필드가 있으면 자동 생성 안 됨** |
| 상속·프록시 가능한 클래스 | 클래스는 기본 상속 가능 | **모든 클래스가 `final`** |

- JPA 는 DB 에서 읽은 행으로 객체를 만들 때 **리플렉션으로 빈 객체를 먼저 만들고 필드를 채운다.** (**리플렉션** = 실행 중에 클래스 구조를 들여다보고 객체를 만들거나 필드를 건드리는 JVM 기능. JS 의 `Object.keys`/`obj[key]` 로 남의 객체를 훑는 것과 비슷하되, 생성자·private 필드까지 닿는다.) 그래서 **인자 없는 생성자**가 반드시 필요하다. 그런데 `class Food(var koreanName: String, …)` 에는 그런 생성자가 없다.
- 하이버네이트는 여러 기능에서 엔티티를 상속한 **프록시 클래스**를 런타임에 만든다. Kotlin 클래스는 기본이 `final` 이라 상속이 안 된다.

### 7-2. kbap 이 이걸 어떻게 덮는가 — 실측

```kotlin
plugins {
    id("kbap.kotlin-common")
    id("org.jetbrains.kotlin.plugin.spring")
    id("org.jetbrains.kotlin.plugin.jpa")
    id("io.spring.dependency-management")
    `java-test-fixtures`
}

allOpen {
    annotation("jakarta.persistence.Entity")
    annotation("jakarta.persistence.MappedSuperclass")
    annotation("jakarta.persistence.Embeddable")
}
```
— `buildSrc/src/main/kotlin/kbap.common-conventions.gradle.kts:4-16`

- **`org.jetbrains.kotlin.plugin.jpa`**(= `kotlin-jpa`) — 코틀린 공식 문서에 따르면 이 플러그인은 **no-arg 플러그인의 JPA 전용 래퍼**이고, **`@Entity`·`@Embeddable`·`@MappedSuperclass` 가 붙은 클래스에 인자 없는 생성자를 자동으로 만들어 준다.** 이 생성자는 **코드에서 직접 부를 수 없고 리플렉션으로만 호출된다** — 그래서 우리 코드에는 안 보이는데 하이버네이트는 쓸 수 있다.
- **`allOpen { … }`** — 그 세 애너테이션이 붙은 클래스의 `final` 을 떼어 낸다. 이건 명시적으로 적어 준 것이다. `kotlin-spring` 플러그인이 `@Service`·`@Configuration` 등에 같은 일을 해 주지만, **JPA 애너테이션은 커버하지 않기 때문**이다.
- 이 컨벤션 플러그인을 적용하는 모듈이 `:common`(엔티티가 사는 곳)이다 — `common/build.gradle.kts:2`.
- `BaseEntity` 의 `open val id`(`BaseEntity.kt:20`)처럼 **손으로 `open` 을 붙인 자리**도 있다. `allOpen` 은 클래스를 열어 주지만, 프로퍼티까지 열려면 별도 표시가 필요한 경우가 있어서다.

### 7-3. 그래서 엔티티는 `data class` 로 쓰지 않는다

kbap 의 22개 엔티티는 **전부 그냥 `class`** 다. Kotlin 개발자의 본능(`data class` 로 만들기)을 여기서만 눌러야 한다.

| `data class` 가 자동으로 주는 것 | 엔티티에서 왜 문제인가 |
|---|---|
| `equals`/`hashCode` — **모든 프로퍼티 기준** | 엔티티의 동일성 기준은 **id 하나**여야 한다. 필드 하나만 바뀌어도 "다른 객체" 가 되면, 컬렉션에 넣어 둔 엔티티를 잃어버린다 |
| `copy()` | 복사본이 원본과 **같은 id** 를 갖는다. 작업대 위 객체와 헷갈리기 딱 좋다 |
| `toString()` — 전 프로퍼티 출력 | 로그에 개인정보가 통째로 찍힌다 |
| `componentN()`(구조 분해) | 엔티티에 쓸 일이 없다 |

kbap 에서 `data class` 는 **값 객체**(`FoodIngredient`·`JwtTokenProperties` 등)와 **DTO** 에 쓴다. 그쪽은 "필드가 같으면 같은 것" 이 맞는 의미라서 `data class` 가 정확히 맞는 도구다. **엔티티는 "id 가 같으면 같은 것"** 이라 반대다.

### 7-4. 전 필드에 기본값이 있는 이유

```kotlin
class Food(
    @Column(name = "korean_name", nullable = false, length = 255)
    var koreanName: String = "",
    …
```

`= ""`, `= 0`, `= emptyMap()` 처럼 **모든 생성자 파라미터에 기본값**이 붙어 있는 게 눈에 띈다. 이건 취향이 아니다 — `CLAUDE.md:118` 이 *"전 필드 기본값이 있으면 no-arg 자동 생성"* 이라고 적어 둔 조건을 맞추는 것이다. 기본값이 없는 파라미터가 하나라도 있으면 no-arg 생성자 생성이 성립하지 않는다.

부작용도 있다. **"필수값인데 빈 문자열로 만들어지는 객체"가 문법상 가능해진다.** 그래서 kbap 은 검증을 **팩토리 메서드**에 몰아넣는다 — `Food.failed(...)`(`Food.kt:175-192`)가 `require` 로 이름 길이와 공백을 막는 식이다.

## 8. 주의점 / 트러블슈팅

- **"분명히 필드를 바꿨는데 DB 가 안 바뀐다"** → 트랜잭션이 없었을 가능성이 가장 크다. 변경 감지는 **작업대가 펼쳐져 있을 때만** 동작한다. 특히 **같은 클래스 안에서 메서드를 부르면 `@Transactional` 이 안 먹는다**(self-invocation) — [[6. 설정과 프로필, 트랜잭션 경계]] 4절에 자세히 나온다. 증상이 예외가 아니라 **조용한 무반응**이라 찾기 어렵다.
- **"트랜잭션 밖에서 엔티티를 고쳤다"** → 컨트롤러나 응답 조립 단계에서 엔티티 필드를 바꿔도 아무 일이 안 일어난다. 그 객체는 이미 **준영속(detached)** 이다. 참고로 `spring.jpa.open-in-view` 는 **레포 어디에도 설정돼 있지 않아** 스프링 기본값(켜짐)을 쓴다. 이 설정이 존재하는 원래 이유(뷰 렌더링 중 지연 로딩)는 연관관계를 안 쓰는 이 레포에 해당이 없어서, 이걸로 데일 일은 사실상 없다. **다만 "조회 성능 함정이 없다"는 뜻은 아니다 — 자동으로 생기는 함정이 없을 뿐, 루프 안에서 리포지토리를 부르면 손으로 똑같이 만들 수 있다**([[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]] 6절).
- **"벌크 UPDATE 후 값이 옛날 것"** → 4-2 절. `@Modifying` 에 `clearAutomatically = true` 가 빠졌는지 본다.
- **"부팅이 안 되고 `Schema-validation` 에러가 난다"** → 5-5 절. 엔티티에 컬럼을 추가했는데 마이그레이션을 안 썼거나, 길이·타입이 어긋난 것이다. 에러 메시지에 어느 컬럼인지 나온다.
- **`@Version` 이 붙은 엔티티** → `Food`(`Food.kt:73-75`)와 `Review`(`Review.kt:42-44`) 두 개에만 낙관적 락 필드가 있다. 같은 행을 동시에 두 트랜잭션이 고치면 **나중 것이 flush 때 예외로 거절된다.** 22개 중 둘뿐이니, 이 두 엔티티를 수정하는 코드를 쓸 때만 기억하면 된다.
- **엔티티는 트랜잭션 밖으로 던지지 않는 게 낫다** → kbap 서비스가 `MyProfileResult` 같은 결과 타입을 만들어 반환하는 이유 중 하나다([[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]).

## 9. 치트시트

```kotlin
// ── 엔티티 골격 ─────────────────────────────────
@Entity
@Table(name = "food")                 // 테이블명 항상 명시
class Food(                            // data class ✗ — 그냥 class
    @Column(name = "korean_name", nullable = false, length = 255)
    var koreanName: String = "",       // 전 필드 기본값 (no-arg 생성 조건)
) : BaseEntity() {                     // id·status·createdAt·updatedAt 상속

    fun approve(): Boolean { … }       // 도메인 메서드를 엔티티에 둔다
}

// ── 매핑 애너테이션 ─────────────────────────────
@Entity                 // 이 클래스 = 테이블 한 행
@Table(name = "…")      // 어느 테이블
@Column(name = "…", nullable = …, length = …)   // 어느 컬럼 (MySQL 기준)
@Id + @GeneratedValue(IDENTITY)                  // 기본키, 값은 DB 가
@Enumerated(EnumType.STRING)                     // enum 을 이름 문자열로
@JdbcTypeCode(SqlTypes.JSON)                     // Map/List → JSON 컬럼
@Embeddable / @Embedded                          // 값 객체를 같은 테이블 컬럼들로 펼침
@MappedSuperclass                                // 테이블 아님, 필드만 물려줌
@SQLRestriction("status = 'ACTIVE'")             // 모든 조회에 조건 자동 부착
@CreationTimestamp / @UpdateTimestamp            // 시각 자동 기입
@Version                                         // 낙관적 락 (kbap 은 Food·Review 둘뿐)
```

```kotlin
// ── 상태 변경 ───────────────────────────────────
@Transactional
fun 무언가하기(id: Long) {
    val e = repository.findById(id).orElseThrow()
    e.도메인메서드()          // ← 필드만 바꾼다
}                            // ← 여기서 flush + commit. save() 없음.

// 새 객체만 save 가 필요하다
repository.save(새객체)
repository.saveAndFlush(새객체)   // id 가 지금 당장 필요하거나
                                  // 제약 위반을 지금 잡아야 할 때
```

```
flush  = 작업대의 변경을 SQL 로 DB 에 보냄. 아직 롤백 가능, 남에겐 안 보임
commit = 트랜잭션 확정. 되돌릴 수 없음
자동 flush 시점: 커밋 직전 · 쿼리 실행 직전 (FlushMode.AUTO)
```

## 10. 용어집

- **리플렉션(reflection)**: 실행 중에 클래스의 구조(생성자·필드·메서드)를 조회하고 호출하는 JVM 기능. JPA·스프링이 내 코드를 몰라도 객체를 만들고 값을 채울 수 있는 이유.
- **영속성 컨텍스트(persistence context)**: 트랜잭션 동안 엔티티를 모아 두는 메모리 공간. 1차 캐시 + 변경 추적기. 실체는 `EntityManager` 가 들고 있다.
- **1차 캐시**: 같은 트랜잭션에서 같은 id 를 다시 조회하면 DB 에 안 가고 작업대의 객체를 그대로 주는 것.
- **엔티티(entity)**: `@Entity` 가 붙어 테이블 한 행에 대응하는 클래스. kbap 에서는 **동시에 도메인 모델**이다.
- **영속 상태(managed)**: 엔티티가 작업대 위에 있어 변경이 추적되는 상태. **준영속(detached)** 은 내려온 상태로, 고쳐도 DB 에 안 간다.
- **변경 감지(dirty checking)**: 로드 시점 스냅샷과 flush 시점 값을 비교해 UPDATE 를 자동 생성하는 것. `save()` 를 부를 필요를 없앤다.
- **flush**: 작업대에 쌓인 변경분을 SQL 로 만들어 DB 로 보내는 것. **커밋이 아니다.**
- **`@MappedSuperclass`**: 자기는 테이블이 아니면서 상속받는 엔티티에 필드를 물려주는 클래스. kbap 의 `BaseEntity`.
- **소프트 삭제**: 행을 지우지 않고 `status = DELETED` 로 바꿔 조회에서만 감추는 것.
- **`ddl-auto: validate`**: 엔티티와 실제 테이블이 맞는지 부팅 때 검사만 하는 설정. 스키마를 만들지 않는다.
- **`kotlin-jpa`(no-arg) 플러그인**: `@Entity` 등이 붙은 Kotlin 클래스에 리플렉션 전용 인자 없는 생성자를 컴파일 시점에 넣어 주는 컴파일러 플러그인.
- **allOpen**: 지정한 애너테이션이 붙은 Kotlin 클래스의 `final` 을 떼어 상속 가능하게 만드는 컴파일러 플러그인.
- **낙관적 락(`@Version`)**: 행마다 버전 숫자를 두고, 동시 수정이 겹치면 나중 것을 flush 때 거절하는 방식.

## 11. 다음에 빠른 재현 체크리스트

새 엔티티를 하나 만든다면:

1. `common/src/main/kotlin/com/kbap/common/domain/<도메인>/model/` 에 만든다 (ArchUnit 이 위치를 강제한다).
2. `data class` 가 아니라 **`class`**, `BaseEntity()` 를 상속.
3. `@Entity` + `@Table(name = "…")`. **id·createdAt·updatedAt·status 는 쓰지 않는다** — 이미 물려받았다.
4. 모든 생성자 파라미터에 **기본값**을 준다.
5. `@Column(name = "스네이크케이스", nullable = …, length = …)` — MySQL 기준.
6. 도메인 규칙(검증·상태 전이)은 **엔티티 메서드**로 넣는다. 값 계산은 값 객체로 빼고, 그 값 객체엔 JPA 애너테이션을 넣지 않는다.
7. **Flyway 마이그레이션을 먼저 쓴다.** 안 그러면 `ddl-auto: validate` 에서 부팅이 실패한다 → [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]].
8. 서비스에서 상태를 바꿀 때 **`save()` 를 쓰지 않는다.** `@Transactional` + 엔티티 메서드 호출로 끝낸다.

> [!note] 2026-08-27 역링크 — 변경 감지가 **`save()` 없이** 일하는 실물, 그리고 그 반대편
> 이 노트가 설명한 더티 체킹이 배치 코드에서 그대로 보인다 → [[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기]] §6-4. 벡터 잡의 Writer 는 `findById(...).orElse(null)?.complete()` 가 전부다 — `save()` 호출이 없는데 UPDATE 가 나간다. 영속 상태 엔티티의 필드를 바꿨기 때문이다.
> 같은 레포에서 **정반대 선택**도 볼 수 있다 → [[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §6. 아웃박스 상태 전이 4종은 변경 감지가 아니라 **네이티브 UPDATE 한 문장**으로 짠다(`CASE WHEN outbox_status = 'PENDING' THEN 'SENT' ELSE outbox_status END`). 이유는 동시성이다 — "읽어서 → 판단해서 → 쓰기" 는 그 사이에 남이 끼어들 수 있고, 조건 판단을 `WHERE`·`CASE` 로 DB 에 넘기면 그 틈이 없어진다.
> **갈라 쓰는 기준**: 내가 방금 읽은 그 상태를 나만 바꾼다고 믿을 수 있으면 변경 감지, 아니면 한 문장 UPDATE. 또 하나 — `BaseEntity` 의 소프트 삭제 `status` 와 도메인 상태 `outbox_status` 가 **다른 컬럼**으로 나란히 있는 실물도 여기 있다([[27. 아웃박스와 SQS — 다른 시스템에 일을 넘기는 법]] §4).
