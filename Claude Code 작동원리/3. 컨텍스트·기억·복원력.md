# 3. 컨텍스트·기억·복원력 (s08~11)

> 맥락: 에이전트가 **오래, 안정적으로** 일하게 하는 "생존 장치" 4종.
> 목표: LLM은 기억이 없고 컨텍스트 창이 유한하다는 한계를 어떻게 극복하는지 이해.

---

## 0. 한 줄 요약
**넘치는 대화를 압축하고(s08) → 잃으면 안 될 지식을 파일로 저장하고(s09) → 지시문을 상황에 맞게 조립하고(s10) → 에러가 나도 크래시 대신 복구한다(s11).**
한 줄 흐름: **오래 살아남기 → 잊지 않기 → 유연하게 설정하기 → 넘어져도 일어나기.**

`★ 왜 이 4개가 한 묶음인가 ─────────────────`
LLM은 기억이 없고 모든 정보가 "컨텍스트 창"이라는 한정 공간에만 존재한다.
컨텍스트가 꽉 차면 압축(s08) → 압축하면 세부가 사라지니 파일 기억(s09) →
기억·도구 다 생겼는데 지시문은 하드코딩이니 조립(s10) → 다 갖췄는데 에러에 죽으니 복구(s11).
`──────────────────────────────────────`

---

## 1. s08 — 컨텍스트 압축

대화가 길어지면 읽은 파일·명령 결과가 messages에 쌓임. 컨텍스트 창은 유한 → 꽉 차면 API가 `prompt_too_long`으로 거부. 매 호출 전 공간 비우기. **철학: 싼 것 먼저, 비싼 것 나중(cheap first, expensive last)** — 돈 안 드는 방법부터, 안 되면 마지막에 LLM 요약.

4단계 파이프라인 (앞 3개는 API 호출 0회):
```python
messages[:] = tool_result_budget(messages)   # L3: 큰 결과(>200KB) 먼저 디스크로, 미리보기만
messages[:] = snip_compact(messages)         # L1: 50개 넘으면 중간 잘라내기
messages[:] = micro_compact(messages)        # L2: 오래된 결과를 한 줄 플레이스홀더로
if estimate_size(messages) > CONTEXT_LIMIT:
    messages[:] = compact_history(messages)  # L4: LLM에게 전체 요약 (API 1회)
```

> [!warning] 순서가 생명
> **L3(디스크 저장) → L1 → L2 순서를 바꾸면 안 됨.** L2가 큰 결과를 한 줄로 덮기 전에 L3가 원본을 디스크에 저장해둬야 하니까. L4 요약은 **비가역 손실**(원본은 `.transcripts/`에 있지만 활성 컨텍스트엔 요약만).

> 비유: 책상이 서류로 가득 참 → ①두꺼운 건 캐비닛에 넣고 색인표(L3) ②오래된 뭉치 치우고(L1) ③남은 옛것 포스트잇 요약(L2) ④그래도 넘치면 비서에게 "요약해줘"(L4).

## 2. s09 — 메모리 (기억)

s08 압축은 손실이 있어 "탭 쓰세요"가 "코드 스타일 선호 있음"으로 뭉개짐. 게다가 새 세션 열면 요약도 사라짐. 그래서 **압축에 참여 안 하고 세션을 넘어 살아남는** 파일 저장 계층.

- **저장**: `.memory/`에 각 기억을 `.md`로 (YAML헤더 name/description/type). 4종류: `user`(넌 누구)·`feedback`(어떻게 일할지)·`project`(무슨 일)·`reference`(어디서 찾나)
- **색인**: `MEMORY.md`가 한 줄 링크 인덱스 → 시스템 프롬프트에 항상 주입
- **로딩**: 매 턴 LLM에게 "관련 기억 번호 골라줘"(최대 5개) → 해당 파일만 주입
- **정리(consolidate)**: 파일 10개 넘으면 병합·모순제거. CC에선 이걸 **"Dream"** 이라 부름

```python
if response.stop_reason != "tool_use":       # 턴 끝날 때
    extract_memories(pre_compress)           # 압축 전 스냅샷에서 추출(세부 살아있음)
    consolidate_memories()
    return
```

> 비유: 회사 인수인계 노트. 대화(단기기억)는 퇴근하면 지워지지만 중요한 건("이 고객 탭 선호") 공용 노트에. 다음날 목차(MEMORY.md) 보고 오늘 일 관련 페이지만 펼침.

> [!note] 핵심 함정
> 추출은 **압축 전(`pre_compress`) 스냅샷**에서 해야 함. 압축본에서 뽑으면 이미 세부가 날아간 상태. 관련성 판단이 벡터유사도가 아니라 LLM 판단이라 비용↑ → 5개 제한.

## 3. s10 — 시스템 프롬프트 조립

s01~09까지 시스템 프롬프트는 하드코딩 한 줄. 기능 늘수록 계속 덧붙이고, 프로젝트 바꾸면 다시 쓰고, 필요없는 지시도 매번 토큰 낭비. → **주제별 조각으로 나눠 런타임에 현재 상태에 맞게 조립.**

```python
memories = context.get("memories", "")
if memories:                                 # 키워드 추측이 아니라 "실제 파일 존재"로 결정
    sections.append(f"Relevant memories:\n{memories}")
```

캐시 키에 `hash()` 대신 `json.dumps`를 쓰는 이유가 코드에 명시:
```python
key = json.dumps(context, sort_keys=True, ensure_ascii=False, default=str)
if key == _last_context_key and _last_prompt:  # context 안 바뀌면 재조립 안 함
    return _last_prompt
```
- 파이썬 `hash()`는 프로세스마다 값이 랜덤 + 중첩 dict에 `unhashable` 에러 → 캐시 키로 부적합.

> 비유: 레고 설명서. 매번 새로 쓰는 대신 "정체성 블록·도구 블록·기억 블록"을 준비해두고 지금 필요한 것만 끼움. 상황 그대로면 지난 조립품 재사용(캐시).

> [!note] 헷갈리지 말 것
> 이 캐시는 **프로세스 내 문자열 재조립만** 절약. CC의 진짜 **API 프롬프트 캐시**(정적/동적 경계 분리)와는 다름. 섹션 로딩은 키워드 추측이 아니라 **실제 상태**(파일 존재 등)로 결정 — 이게 핵심 원칙.

## 4. s11 — 에러 복구

프로덕션에서 API 에러는 정상. `529 overloaded` 한 번에 크래시하면 안 됨. 에러를 **종류별로 분류해 각기 다른 복구 경로**로, 복구 후 `continue`로 재시도.

3가지 경로:
1. **출력 잘림(`max_tokens`)**: max_tokens 8K→64K로 **같은 요청 재시도**(1회), 그래도면 "이어서 써"(최대 3회)
2. **컨텍스트 초과(`prompt_too_long`)**: reactive_compact 후 재시도(1회)
3. **일시 실패(429/529)**: 지수 백오프+지터(최대 10회), 529 연속 3회면 폴백 모델 전환

```python
base = min(BASE_DELAY_MS * (2 ** attempt), 32000) / 1000   # 지수 백오프
jitter = random.uniform(0, base * 0.25)                     # 지터: 동시 재시도 충돌 방지
return base + jitter
```

```python
if response.stop_reason == "max_tokens":
    if not state.has_escalated:
        max_tokens = ESCALATED_MAX_TOKENS   # 8K -> 64K
        state.has_escalated = True
        continue                            # 메시지 그대로, 같은 요청 재시도(오염 방지)
```

> 비유: 운전 중 대응. 말이 끊기면(힘 부족) 기어 올려 다시 말하고, 짐 많으면(컨텍스트) 짐 줄이고, 길 막히면(429/529) 조금 더 기다렸다 재출발, 계속 막히면 다른 길(폴백 모델).

> [!warning] 무한루프 방지
> 각 복구는 시도 횟수 제한: escalation 1회, continuation 3회, reactive compact 1회, 재시도 10회. **지터 없으면** 여러 클라이언트가 동시 재시도해 서버를 다시 덮침("thundering herd").

## 5. 용어집
- **컨텍스트 창**: LLM이 한 번에 볼 수 있는 텍스트 최대 크기. 넘으면 거부.
- **reactive compact**: 예방 압축이 실패해 API 에러 후 실행하는 응급 압축.
- **frontmatter**: `.md` 맨 위 `---` YAML 메타데이터.
- **on-demand loading**: 관련된 것만 골라 주입하는 방식(기억·스킬 공통).
- **Dream (consolidation)**: 쌓인 기억을 주기적으로 병합·정리.
- **deterministic serialization**: 같은 입력→같은 문자열(`json.dumps(sort_keys=True)`), 캐시 키로 안전.
- **지수 백오프 / 지터**: 재시도 간격 2배씩 늘리기 / 대기에 더하는 무작위값(충돌 방지).
- **폴백 모델**: 주 모델 과부하 시 쓰는 예비 모델(Opus→Sonnet).
