# 5. 여러 에이전트의 협업 (s15~18)

> 맥락: 에이전트 한 명으로 부족할 때, 여럿이 팀으로 일하는 법.
> 목표: **협업 → 규칙 → 자율 → 격리** 로 점점 손이 덜 가는 팀으로 진화하는 과정 이해.

---

## 0. 한 줄 요약
**파일 기반 우편함으로 소통하는 팀(s15) → 안전한 약속(프로토콜, s16) → 스스로 일감 찾기(s17) → 각자 격리된 폴더에서 충돌 없이(s18).**
흐름: **협업(s15) → 규칙(s16) → 자율(s17) → 격리(s18).**

`★ s06 서브에이전트 vs s15 팀원 ─────────────`
[[2. 행동을 다듬는 장치 — 훅·투두·서브에이전트·스킬|s06 서브에이전트]] = 한 번 쓰고 버리는 일회용 알바(요약만 반환).
s15 팀원(teammate) = 여러 턴 살아있으며 서로 대화하는 동료(MessageBus로 통신).
`──────────────────────────────────────`

## 1. s15 — 에이전트 팀 (협업)

혼자선 백엔드 전체 리팩터링 같은 큰 일을 못 함(컨텍스트 창 한정). 여러 에이전트가 **팀**을 이룸. 리더가 `spawn_teammate`로 팀원(alice, bob)을 각각 백그라운드 스레드로 띄움. 소통은 **MessageBus**(파일 우편함).

```python
def read_inbox(self, agent):
    inbox = MAILBOX_DIR / f"{agent}.jsonl"
    msgs = [json.loads(line) for line in inbox.read_text().splitlines()]
    inbox.unlink()                            # 소비: 읽고 삭제
    return msgs
threading.Thread(target=run, daemon=True).start()   # 각자 독립 스레드로 병렬
```
- 우편함은 그냥 `.jsonl` 파일. 보낼 땐 append, 읽을 땐 읽고 삭제. 리더는 루프마다 자기 우편함 확인 → 온 메시지를 **대화 기록에 주입**(그래야 LLM이 반응).

> 비유: 회사에서 팀원마다 **개인 사서함**. 쪽지 넣으면 상대가 꺼내 읽고 버림. 리더는 자기 사서함을 주기적으로 확인.

> [!note] 경쟁 상태
> "읽고 삭제"는 두 스레드가 동시에 읽으면 메시지가 사라지는 **race** 위험. 교육용이라 괜찮지만 실제 CC는 `proper-lockfile`로 잠금.

## 2. s16 — 팀 프로토콜 (규칙)

s15 소통은 느슨(그냥 텍스트). 근데 "종료"나 "계획 승인"은 **정식 약속(프로토콜)** 필요. 예: 리더가 alice 스레드를 그냥 죽이면 파일이 반쯤 쓰이다 망가짐. → "리더 요청 → alice 마무리·확인 → 종료" 악수(handshake).

핵심 = `request_id`가 요청과 응답을 잇는 **연결 열쇠**:
```python
def match_response(response_type, request_id, approve):
    state = pending_requests.get(request_id)
    if state.type == "shutdown" and response_type != "shutdown_response":
        return                                # 타입 불일치 → 무시
    if state.status != "pending":
        return                                # 이미 처리됨 → 중복 무시
    state.status = "approved" if approve else "rejected"   # pending→approved 한 방향
```
- `request_id`로 찾을 뿐 아니라 **타입까지 검증**(shutdown 응답이 plan 승인을 실수로 통과 못 하게).

> 비유: 택배 송장번호. 보낼 때 번호(`request_id`) 붙이고, 받는 쪽이 그 번호로 "받았다" 확인. 번호가 있어야 어느 요청 응답인지 안 헷갈림.

> [!note] 교육용은 흐름만
> 계획 미승인이어도 팀원 bash/write를 **실제로 막진 않음**(execution gating 없음). 실제 CC는 승인 전 위험 작업을 가로챔. (이 게이팅은 [[6. 확장과 종합 — MCP·플러그인·전체 그림|s20]]에서 실제로 등장.)

## 3. s17 — 자율 에이전트 (자율)

s16까진 리더가 "너는 이거" 일일이 배정(작업 10개면 10번 배정, 확장 안 됨). → 팀원이 **스스로 게시판 보고 임자 없는 일감을 집게(auto-claim).** 리더는 작업만 만들면 됨.

생애주기가 3단계(WORK→IDLE→SHUTDOWN):
```python
def scan_unclaimed_tasks():
    for f in sorted(TASKS_DIR.glob("task_*.json")):
        task = json.loads(f.read_text())
        if (task.get("status")=="pending"
                and not task.get("owner")     # 임자 없음
                and can_start(task["id"])):    # 의존성 완료됨
            unclaimed.append(task)
```
- **IDLE**: 5초마다 폴링 — ①우편함 우선(shutdown 오면 즉시 응답·종료) ②없으면 게시판 스캔해 claim → WORK. **SHUTDOWN**: 60초간 새 일 없으면 요약 보내고 종료.

> 비유: 카페 주방 주문 게시판. 매니저 지시 없이도 요리사가 한가하면 아직 아무도 안 집은 주문표를 스스로 떼어감.

> [!warning] 정체성 재주입
> autoCompact로 메시지가 요약되면 팀원이 자기가 누군지 잊을 수 있어, `len(messages) <= 3`이면 `<identity>`를 다시 삽입. 파일락 없어 동시 claim race는 여전(실제 CC는 `proper-lockfile`로 원자적 claim).

## 4. s18 — 워크트리 격리 (격리)

s17까지 alice·bob이 **같은 폴더**에서 일함 → 둘 다 `config.py` 고치면 서로 덮어씀. **git worktree** = 한 저장소에서 독립 작업폴더+브랜치를 여러 개. alice는 `.worktrees/auth-refactor/`, bob은 `.worktrees/ui-login/` → 충돌 없음. s15~17이 "누가/어떻게 소통"이면 s18은 "어디서 일하나".

```python
def _run_claim_task(task_id):
    result = claim_task(task_id, owner=name)
    if "Claimed" in result:
        task = load_task(task_id)
        if task.worktree:
            wt_ctx["path"] = str(WORKTREES_DIR / task.worktree)   # cwd 전환
    return result
def _run_bash(command):
    return run_bash(command, cwd=wt_ctx["path"])                  # 그 폴더에서 실행
VALID_WT_NAME = re.compile(r'^[A-Za-z0-9._-]{1,64}$')            # ../ 경로탈출 거부
```

> 비유: 공유 사무실에서 팀원마다 **개인 작업실** 배정. 같은 회사(저장소)지만 각자 방(worktree)에서 서류 고치니 서로 책상 안 어지럽힘. 끝나면 방 남겨 검토(keep) 또는 정리(remove).

> [!note] 안전장치
> `remove_worktree`는 **커밋 안 된 변경 있으면 기본 거부**(`discard_changes=true`로 강제). 바인딩은 상태를 안 바꿈(작업은 pending 유지 → 리더가 미리 만들고 팀원이 나중에 claim). 정리해도 작업 자동완료 안 됨(`complete_task` 명시 호출 필요).

## 5. 용어집
- **MessageBus**: 파일 기반 메시지 전달. 에이전트마다 `.jsonl` 우편함.
- **Teammate(팀원)**: 여러 턴 살아있으며 비동기 소통하는 에이전트(일회용 서브에이전트와 대비).
- **inbox injection**: 받은 메시지를 대화 기록에 넣어 LLM이 보게 하기.
- **ProtocolState / request_id**: 요청 상태 기록 / 요청↔응답을 잇는 연결 열쇠.
- **handshake(악수)**: 요청→확인→실행 양방향 합의.
- **auto-claim**: 리더 지시 없이 팀원이 스스로 작업 집기.
- **can_start**: blockedBy 의존성이 다 완료됐는지 확인.
- **git worktree**: 한 저장소에서 여러 독립 작업폴더(각자 브랜치).
- **event log**: worktree 생성/삭제 이력을 남겨 감사 가능하게(`events.jsonl`).

## 6. 한 줄 복습
> 팀(우편함)→프로토콜(request_id 악수)→자율(auto-claim)→격리(worktree). 점점 손이 덜 가는 팀.


> [!note] 2026-08-26 갱신 — 인용하던 kbap 에이전트 팀은 해체됐다
> 이 노트는 kbap-server 를 "`test-writer` → `implementer` → (`code-reviewer` ∥ `database-expert`) 팀"의 실사례로 인용했었다. 그 **구현 팀은 2026-08-14 해체**됐다(레포 `CLAUDE.md` 첫 절). 사유는 두 가지 — **"구현 단계가 느려지고"**, **"과한 코드가 나오는 문제"**. 앞은 위 1절이 말한 협업의 대가 그대로다(팀원은 부모 맥락을 물려받지 못해 이미 읽은 파일을 다시 읽는다). 뒤는 분업 자체가 만든 부작용이다 — `implementer` 는 **자기가 쓰지 않은 테스트**를 받으므로 최소 구현의 '최소'를 판단할 근거가 없고, 방어 코드와 확장 지점을 얹는다. TDD 의 Green 이 요구하는 최소 판단을 분업이 막은 셈이다.
> 지금은 **구현은 단일 세션이 직접**, 리뷰만 `kbap-code-review`·`kbap-db-review` 스킬로 **명시 호출**한다. 팀으로 남길 값어치가 있던 역할은 (a) 서로의 맥락을 크게 필요로 하지 않고 (b) 사람이 원할 때만 불러도 되는 역할이었고, 리뷰가 정확히 그렇다. 다에이전트를 걷어내고 단일 세션으로 회귀한 사례로 읽어라 — **팀을 짜기 전에 물을 질문은 "나눌 수 있나"가 아니라 "나눠서 뭘 버나"다.**
