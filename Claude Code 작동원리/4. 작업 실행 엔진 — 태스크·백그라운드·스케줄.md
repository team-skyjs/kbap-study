# 4. 작업 실행 엔진 — 태스크·백그라운드·스케줄 (s12~14)

> 맥락: 에이전트의 "작업 관리 3종 세트". 무엇을·어떻게(비동기)·언제(자동).
> 목표: 수동적이던 에이전트가 점점 자율적으로 일을 관리하게 되는 흐름 이해.

**큰 목표를 의존성 있는 작은 태스크로 쪼개 파일로 저장하고(s12) → 느린 작업은 백그라운드로 돌리며(s13) → 정해진 시각에 스스로 일을 만들어내게(s14) 한다.**
흐름: **s12(순서) → s13(비동기 실행) → s14(시간 자동화).**

## 1. s12 — 태스크 시스템 (순서)

큰 프로젝트("DB설정→API작성→테스트")를 순서 없이 시작하면 낭패(기초공사 없이 지붕부터). 각 할 일을 **JSON 파일 하나**로 저장하고 **의존성**을 붙임. s05 TodoWrite(세션 메모리 체크리스트)와 달리 **디스크 저장** → 세션 꺼져도 살아남음.

핵심: `blockedBy`로 "이 태스크는 저게 끝나야 시작 가능"을 표현. `claim_task`의 관문이 `can_start`:
```python
def can_start(task_id):
    task = load_task(task_id)
    for dep_id in task.blockedBy:            # 선행 태스크 하나씩 확인
        if not _task_path(dep_id).exists(): return False   # 의존 파일 없으면 막힘
        if load_task(dep_id).status != "completed": return False  # 안 끝났으면 시작불가
    return True
```

> 비유: 요리 레시피 순서 카드. "양파 볶기" 카드엔 "먼저 양파 썰기 완료" 조건이 붙어, 썰기 전엔 볶기 카드를 못 집음. 카드는 냉장고에 붙여둬(디스크) 내일도 어디까지 했는지 앎.

> [!note] 교육용 단순화
> **순환 의존성(A→B, B→A) 검사 없음** → 둘 다 영원히 시작 못 함. `in_progress→pending` 복구 경로 없음(실제 CC는 작업자 죽으면 owner 지우고 재개방).

## 2. s13 — 백그라운드 태스크 (비동기)

세탁기 돌려놓고 딴 일 하듯, 오래 걸리는 명령(`npm install`)은 별도 스레드에 던지고 에이전트는 계속 딴 일. LLM은 토큰당 과금이라 10분 멍때리기 = 순수 낭비.

```python
def worker():
    result = execute_tool(block)
    with background_lock:                     # 락으로 보호
        background_tasks[bg_id]["status"] = "completed"
        background_results[bg_id] = result
thread = threading.Thread(target=worker, daemon=True)  # 데몬 스레드
thread.start()
return bg_id                                  # 결과 아닌 추적용 ID를 즉시 반환
```
완료되면 매 턴 `collect_background_results`가 모아서 `<task_notification>` XML로 대화에 주입.

> 비유: 식당 진동벨. 주문(느린 명령) 넣으면 벨(bg_id) 받고 자리로 돌아가 딴 일. 완성되면 벨이 울림(notification 주입).

> [!warning] tool_result 규칙
> 알림은 원래 `tool_use_id`를 **재사용 안 함**. Messages API 규칙상 하나의 tool_use엔 정확히 하나의 tool_result만. 원래 호출엔 자리표시자로 답했고, 완료는 별도 `<task_notification>` 이벤트로 주입. (어기면 API 에러)
> 실제 CC의 "백그라운드"는 진짜 스레드가 아님 — Node.js는 단일 스레드라 "await 안 한다"는 뜻. 교육용만 실제 `threading.Thread`.

## 3. s14 — 크론 스케줄러 (시간 자동화)

알람시계처럼, "매일 9시 테스트", "5분마다 CI 확인"을 사람이 매번 안 시켜도 시간 맞춰 스스로 일을 생성.

**4층 모델**: ①스케줄러(생산자, 1초마다 시각 확인해 큐에 넣음) → ②큐(완충지대) → ③큐 프로세서(배달부, 에이전트 한가하면 턴 실행) → ④소비자(agent_loop, `[Scheduled]` 주입)

```python
if cron_matches(job.cron, now):
    if _last_fired.get(job.id) != minute_marker:   # 같은 분 중복 발화 방지
        cron_queue.append(job)
        _last_fired[job.id] = minute_marker
    if not job.recurring:                           # 일회성은 발화 후 제거
        scheduled_jobs.pop(job.id, None)
```
- `minute_marker`="2026-07-02 09:00" 형태. 1초마다 검사해 같은 분에 60번 매칭되지만 마커 비교로 **분당 딱 1회**만 큐에 넣음.

> 비유: 호텔 모닝콜. 프런트(스케줄러)가 시계 보며 "703호 7시 콜" 요청서를 대기함(큐)에 넣으면, 교환원(프로세서)이 회선 비면 전화. 장부에 적어두면(durable) 교대해도 이어받음.

> [!warning] "durable"의 진짜 의미
> durable 잡이라도 스케줄러는 에이전트 프로세스 안에서만 돔 → **앱 끄면 스케줄러도 멈춤.** "durable"=재시작 후 정의가 살아남아 다시 로드된다는 뜻이지 "앱 꺼져도 실행"이 아님. 후자는 시스템 crontab/systemd timer 필요.
> **크론 요일+날짜는 AND가 아니라 OR** — `0 9 1 * 1`="매월1일 OR 매주월요일 9시".

## 4. 용어집
- **blockedBy**: 이 태스크 전에 끝나야 할 선행 태스크 ID 목록.
- **DAG**: 화살표가 한 방향, 원 안 그리는 의존 구조. 태스크 순서의 이상형.
- **claim(클레임)**: "내가 맡겠다" 선언해 owner 지정 + 진행중 전환.
- **데몬 스레드**: 메인 끝나면 같이 종료되는 뒤에서 도는 스레드.
- **Lock(락)**: 여러 스레드가 같은 데이터 동시에 건드려 꼬이는 걸 막는 잠금.
- **휴리스틱**: 정답 대신 경험칙으로 빠르게 추측("install" 있으면 느린 작업).
- **크론 표현식**: `분 시 일 월 요일` 5칸. `*/5 * * * *`="5분마다".
- **큐**: 생산/소비 속도를 분리하는 대기열.
- **durable(영속)**: 잡 정의를 파일 저장해 재시작 후 복원.
