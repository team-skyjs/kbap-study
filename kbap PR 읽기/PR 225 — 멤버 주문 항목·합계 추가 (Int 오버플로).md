# PR 225 — 멤버 주문 항목·합계 추가 (Int 오버플로)

> 작성: 2026-09-03 · 맥락: **직접 앱을 써보다 발견한 구멍**. 어드민 멤버 상세의 주문 탭이 메뉴판 사진과 주소만 보여줘서 **"뭘 주문했는지"가 안 보였다.**

## 0. 한 줄 요약

**주문 응답에 "무엇을 몇 개 얼마에" 를 추가했다.** 도메인(`OrderItem`)과 배치 조회가 **이미 있어서** 순수 재사용이었는데, 리뷰에서 **합계가 `Int` 라 오버플로**하는 게 잡혀 어드민 쪽만 `Long` 으로 고쳤다.

---

## 1. 왜 나왔나 — dogfooding

PR 본문에 출처가 적혀 있다: *"예진 dogfooding: 주문 탭에 음식 목록 부재"*. **직접 써보다 발견한 것**이다.

> 이 시리즈에서 [[PR 214 — 벡터 아웃박스 목록 검색 q 추가|214]](운영 QA 로 검색 추가)에 이어 **두 번째 "사용이 만든 PR"** 이다. 기획서에서 나온 게 아니라 **화면을 열어보니 허전해서** 나왔다.

**조사해보니 데이터는 이미 다 있었다** — `OrderItem` 도메인에 `foodId`·`menuName`·`quantity`·`price` 가 있고 배치 조회 메서드도 있었다. **화면에 안 내려주고 있었을 뿐**이다. 그래서 도메인도 마이그레이션도 안 건드렸다.

---

## 2. 무엇이 추가됐나

`GET /api/admin/members/{id}/orders` 의 각 주문에 세 필드가 붙었다:

```jsonc
{
  "items": [                                    // ← 신설
    { "foodId": 7, "menuName": "김치찌개", "quantity": 2, "price": 9000 },
    { "foodId": 12, "menuName": "계란말이", "quantity": 1, "price": null }
  ],
  "totalQuantity": 3,                           // ← 신설
  "totalPrice": 18000                           // ← 신설
}
```

- **`menuName` 은 주문 시점 스냅샷**이다 — 음식이 개명되거나 삭제돼도 **그때 주문한 이름 그대로** 보인다. [[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|219]] 의 아웃박스 `displayName` 과 **같은 설계**(스냅샷 vs 조인)이고, [[PR 218 — 표시 이름 편집·어드민 반려 유형·삭제 시 이름 반납|218]] 의 개명이 이걸 안 건드리는 이유이기도 하다.
- **`foodId` 는 음식 상세로 가는 링크용**이다.
- **`price` 가 널일 수 있다** — 메뉴판에서 가격을 못 읽은 경우. 합계는 **널을 0 으로** 친다(도메인 규칙이고 Swagger 에 명시).

**N+1 은 없다** — 주문 목록을 먼저 뽑고 그 id 들로 `findByOrderIdInOrderByIdAsc` 한 번. [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기|9번 노트]]의 그 손동작이고, [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지|앱 쪽 OrderService]]가 이미 쓰던 패턴을 그대로 가져왔다.

## 3. 핵심 — `Int` 오버플로

### 무엇이 문제였나

초판은 도메인 헬퍼를 그대로 썼다:

```kotlin
// common/domain/order/model/OrderItem.kt:35
fun totalPriceOf(items: List<OrderItem>): Int = items.sumOf { (it.price ?: 0) * it.quantity }
//                                       ↑ Int
```

**`Int` 는 약 ±21억(2,147,483,647)까지**다. 그런데 `price * quantity` 를 **`Int` 끼리 곱하면 결과도 `Int`** 라, 넘치면 **에러가 아니라 조용히 음수로 돌아버린다.**

테스트가 그 시나리오를 못 박았다:

```kotlin
OrderItem.place(order.id, food.id, "금박한우", quantity = 2_000, price = 2_000_000)
// 2,000 × 2,000,000 = 40억  →  Int 범위(21억) 초과 💥
```

> [!warning] 자바·코틀린 정수 오버플로는 **조용하다**
> 파이썬은 정수가 무한히 커지고, JS 는 `number` 가 실수라 2⁵³까지 안전하다. **JVM 은 다르다** — `Int` 가 넘치면 **예외도 경고도 없이 값이 한 바퀴 돌아 음수가 된다.**
> ```
> 2_147_483_647 + 1  ==  -2_147_483_648
> ```
> 그래서 **합계·누적·곱셈은 `Long` 으로 올려 두는 게 기본기**다. → [[3. JVM 위의 Kotlin — 컴파일·널 안전·Gradle 3모듈]]

### 어떻게 고쳤나 — 어드민 DTO 에서만 `Long`

```kotlin
// 어드민 응답 DTO
val totalPrice: Long,
…
totalPrice = orderItems.sumOf { (it.price ?: 0).toLong() * it.quantity }
//                                            ↑ 곱하기 전에 Long 으로 올린다
```

**`.toLong()` 을 곱셈 *앞*에 붙인 게 핵심**이다. `(a * b).toLong()` 이면 이미 `Int` 로 넘친 뒤에 변환하는 거라 **아무 소용이 없다.**

```kotlin
(2_000 * 2_000_000).toLong()   // ❌ Int 로 곱해서 넘친 뒤 변환 → 틀린 값
(2_000).toLong() * 2_000_000   // ✅ Long 으로 곱함 → 4_000_000_000
```

### 왜 도메인 헬퍼(`totalPriceOf: Int`)는 그대로 뒀나

**앱 경로가 그걸 공유하기 때문**이다(`api/order/OrderService.kt:89`).

| | 쓰는 곳 | 고치면? |
|---|---|---|
| `OrderItem.totalPriceOf(): Int` | **앱**(사용자 주문 조회) | 반환 타입을 바꾸면 **앱 응답 DTO 까지 연쇄**로 바뀐다 — 출시된 앱의 계약 |
| 어드민 DTO 의 `sumOf { … }` | **어드민만** | 새 표면이라 **자유롭게 `Long`** |

> [!tip] 여기가 판단의 갈림길이었다
> "도메인 헬퍼가 `Int` 라 위험하니 거기부터 고치자" 가 자연스러워 보이지만, **그건 출시된 앱의 계약을 건드리는 일**이다. 반면 **어드민은 아직 우리만 쓰는 새 표면**이라 비용이 0 이다.
> 그래서 **위험이 실제로 드러나는 곳(합계를 크게 낼 수 있는 어드민)부터 막고, 공유 헬퍼는 남겼다.** 앱 쪽도 언젠가 오버플로가 가능하지만 — 개인 주문 하나가 21억을 넘기는 일은 현실적으로 없다.
> **"완벽한 수정"이 아니라 "위험이 있는 곳부터"** 를 고른 것이고, 그 근거(앱 경로 공유)가 분명하다.

## 4. 값 범위를 넓히는 건 왜 하위호환인가 — JSON 숫자의 성질

`totalPrice` 의 타입이 `Int` → `Long` 으로 바뀌었는데 **FE 는 아무것도 안 고쳐도 된다.** 왜?

**JSON 에는 정수/실수 구분이 없다.** 스펙상 숫자는 그냥 `number` 하나다.

```jsonc
{ "totalPrice": 18000 }        // 전
{ "totalPrice": 4000000000 }   // 후 — JSON 문법상 완전히 같은 종류의 값
```

- **서버**: 코틀린이 `Int` 든 `Long` 이든 직렬화되면 **똑같이 숫자 리터럴**이다. 필드명도 그대로다.
- **FE(TypeScript)**: `number` 는 배정도 실수라 **2⁵³(약 9,007조)까지 정확**하다. 40억은 여유롭다.

> [!note] 단, 무한정 안전하진 않다
> `Long` 의 최댓값(약 9.2×10¹⁸)은 **JS `number` 의 안전 범위(2⁵³ ≈ 9×10¹⁵)를 넘는다.** id 같은 값에 `Long` 최댓값 근처를 쓰면 **JS 에서 정밀도가 깨진다**(그래서 큰 id 를 문자열로 내리는 API 들이 있다).
> 여기선 금액이라 그 근처에 갈 일이 없어 안전하다. **"Long 이면 항상 안전"이 아니라 "이 값의 현실적 범위가 2⁵³ 아래라 안전"** 이다.

**정리하면 하위호환인 이유는 셋이다**: ①필드명 그대로 ②JSON 타입 그대로(number) ③실제 값이 클라이언트 안전 범위 안. 셋 중 하나라도 깨지면 하위호환이 아니다.

## 5. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 4건을 물었고 판정이 났다(2026-09-03). **채택 1 · 근거 확인 1 · 불필요 1 · 관찰 1.**

### ⬜ 1. `totalQuantity` 는 여전히 `Int` — 왜 한쪽만 올렸나

**→ 유지가 맞다. 다만 근거는 남길 값이 있다.**

| | 상한이 있나 |
|---|---|
| **수량**(`totalQuantity`) | **있다** — 한 사람이 주문할 수 있는 개수에는 물리적 한계가 있다 |
| **금액**(`totalPrice`) | **없다** — 단가 × 수량이라 곱셈으로 커진다 |

**곱셈이 들어가는 쪽만 위험하다**는 게 비대칭의 이유다. 다만 그 판단이 코드에 안 보이므로 **주석 한 줄** 정도(별도 작업은 아님).

### ✅ 2. 도메인 헬퍼와 어드민 계산이 갈라졌다

`OrderItem.totalPriceOf()`(Int)와 어드민의 `sumOf { … }`(Long)가 **"널은 0" 규칙을 두 번 구현**한다.

**→ 채택.** 진짜 중복이 맞다 — **규칙이 바뀌면**(예: "널은 집계에서 제외") **한 곳만 고쳐서 두 화면이 어긋난다.** `totalPriceLongOf()` 를 **도메인에 두고 어드민이 호출**하는 방향으로 정리한다(소정리 묶음).

> §3 에서 "도메인 헬퍼를 안 고친 게 맞다"고 했는데 **그건 반환 타입을 바꾸지 말라는 뜻**이었다. **새 헬퍼를 하나 더 두는 것**은 앱 계약을 안 건드리면서 규칙을 한 곳에 모은다 — **더 나은 답**이다.

### ⬜ 3. `price` 널의 뜻이 응답에서 안 읽힌다

**→ 불필요.** 어드민 화면에 **이미 "가격 미인식" 칩과 "합계에 0 집계" 병기**가 있다(P-A23). 응답에 뜻을 더 실을 이유가 없다.

> 이 시리즈에서 반복된 판단이다 — **판단 재료가 이미 있으면 FE 가 푼다**([[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|209]]·[[PR 214 — 벡터 아웃박스 목록 검색 q 추가|214]]). 다만 여기선 **이미 풀려 있었다.**

### 👍 4. `sum`·`total` 이 붙는 새 필드는 타입부터 본다

**→ 관찰 채택.** 기능 자체는 "이미 있는 데이터를 내려주기"라 단순했는데, **합계라는 단어가 붙는 순간 타입 문제가 생겼다.**

## 6. 다음에 이 PR 을 다시 볼 때

1. **JVM 정수 오버플로는 조용하다** — 예외 없이 음수로 돈다. `sum`·`total` 은 `Long` 이 기본.
2. **`.toLong()` 은 곱셈 *앞*에** — 뒤에 붙이면 이미 넘친 값을 변환할 뿐이다.
3. **고칠 곳을 고를 때 "공유되는가"를 본다** — 도메인 헬퍼는 앱과 공유라 남기고, 새 표면인 어드민만 고쳤다.
4. **Int→Long 확장이 하위호환인 건** ①필드명 ②JSON number ③값이 2⁵³ 아래 — 셋이 다 맞을 때다.
5. **리뷰 결과**(§5): **채택 1**(도메인에 `totalPriceLongOf()` 신설 — "널은 0" 규칙을 한 곳으로) · 근거 확인 1 · 불필요 1 · 관찰 1.
