## 0. 한 줄 요약

**세 가지를 한 번에 고쳤다** — ①표시 이름을 매치키와 **분리해서 편집**할 수 있게 하고, ②어드민 반려에 **전용 실패 유형**(`ADMIN_REJECTED`)을 주고, ③소프트삭제가 **유니크 이름을 계속 붙들고 있어 같은 이름 재등록이 500 으로 터지던 버그**를 고쳤다.

## 1. 먼저 알아야 할 것 — 음식 이름이 두 개다

이 PR 은 이걸 모르면 한 줄도 안 읽힌다.

| 컬럼 | 정체 | 유니크? | 값 예시 |
|---|---|---|---|
| **`korean_name`** | **매치키** — 스캔한 메뉴명을 음식에 붙일 때 대조하는 키 | **✅ `uq_food_korean_name`** | `김치찌개` |
| **`display_name`** | **표시 이름** — 화면에 보여줄 문자열 | ❌ | `김치찌개 (2인분)` |

**매치키는 정규화된 값**이다 — [[19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지|19번 노트]]에서 본 `KoreanMenuNameNormalizer.matchKey` 가 **NFC 정규화 후 `가`~`힣` 만 남긴다.** 공백·괄호·숫자·영문이 전부 떨어져 나간다.

```kotlin
matchKey("김치찌개 (2인분)")  →  "김치찌개"
```

> [!tip] 왜 굳이 둘로 나눴나
> 스캔 매칭은 **글자가 정확히 같아야** 하고(정규화된 키), 화면 표시는 **사람이 읽기 좋아야** 한다(원문 그대로). 한 컬럼이 둘을 겸하면 **"(2인분)"을 붙이는 순간 스캔 매칭이 깨진다.** 그래서 **키는 좁게 정규화하고, 표시는 자유롭게** 둔 것이다.

**이 PR 전에는 표시 이름을 따로 못 정했다** — 수정 API 가 `koreanName` 입력값을 표시 이름에도 그대로 넣었다.

```kotlin
- food.displayName = command.koreanName
+ food.displayName = command.displayName?.trim()?.takeIf { it.isNotEmpty() } ?: command.koreanName
```

생략하면 종전대로 동작하므로 **하위호환**이다.

## 2. 세 변경 각각

### 2-1. 표시 이름 편집 (`displayName` 추가)

```kotlin
@field:Size(max = 255, message = "displayName 은 255자 이하여야 합니다")
val displayName: String? = null,

@AssertTrue(message = "displayName 은 공백일 수 없습니다")
fun isDisplayNamePresentable(): Boolean = displayName == null || displayName.isNotBlank()
```

- **`null` 은 허용, 공백은 금지** — `null` 은 "안 보냈다"(→ `koreanName` 사용)이고 `"  "` 는 "빈 이름으로 하겠다"라 **의도가 다르다.** `@AssertTrue` 로 그 둘을 가른다. → [[PR 201 — 어드민 음식 상세·수정·재수집·삭제 REST|PR 201]] 의 `@AssertTrue` 와 같은 도구.
- **중복 검사는 매치키(FOOD-005)만 한다** — `display_name` 은 유니크가 아니다. PR 본문이 *"스키마 실물 대조: `uq_food_korean_name` 뿐"* 이라고 **확인 근거를 남긴** 게 좋다.
- **상세 응답에 `displayName` 원값이 신설**됐고, 기존 `koreanName` 응답 필드는 **표시명 resolve 값 그대로** 둬서 하위호환을 지켰다(FE 가 안 깨진다).
- **`matchKey` 필드도 신설**(리뷰 반영) — 진짜 매치키를 따로 내려준다. **활성이면 `koreanName`, 삭제됐으면 `deletedOriginalKoreanName` 로 폴백**한다:

```kotlin
matchKey = food.deletedOriginalKoreanName ?: food.koreanName
```

  **묘비 문자열(`김치찌개_deleted_42`)이 FE 로 새지 않게** 하는 장치다. 폴백을 `from()` **한 곳에만** 두고 노출 표면 6곳을 전수 점검해 **누출 0** 을 확인했다 — 이런 건 한 곳에 모아야 빠뜨리지 않는다.

### 2-2. 어드민 반려 유형 `ADMIN_REJECTED`

```kotlin
// Food.reject()
fun reject(reason: String?) {
    requireReviewable()
    contentStatus = FoodContentStatus.FAILED
+   contentFailureKind = FoodContentFailureKind.ADMIN_REJECTED   // ← 이 한 줄
    contentReviewAttempts++
    contentReviewRejectionReason = truncateReason(reason)
}
```

**문제**: 기존엔 어드민이 반려해도 `contentStatus = FAILED` + 사유 텍스트뿐이라, **파이프라인이 실패한 것과 사람이 반려한 것이 화면에서 구분되지 않았다.**

**해법**: 실패 유형 enum 에 값 하나를 더한다.

| 값 | 누가 만드나 |
|---|---|
| `NOT_FOOD` · `JUDGE_REJECTED` · `INGREDIENT_GUARD` | **파이프라인**(LLM·가드) |
| **`ADMIN_REJECTED`** ⭐ | **사람**(어드민 반려) |

**그리고 오용을 막는다** — 랭체인 콜백이 `ADMIN_REJECTED` 를 보내지 못하게 검증을 건다:

```kotlin
@AssertTrue(message = "failureKind 는 파이프라인 실패 유형이어야 합니다")
fun isFailureKindFromPipeline(): Boolean = failureKind != FoodContentFailureKind.ADMIN_REJECTED
```

> [!tip] 이 가드가 이 PR 에서 가장 사려 깊은 부분이다
> 한 enum 에 **출처가 다른 값들**을 섞으면, "누가 이 값을 쓸 수 있나"가 흐려진다. 콜백이 `ADMIN_REJECTED` 를 보낼 수 있으면 **외부 시스템이 사람의 판단을 대신 기록**하게 되고, 나중에 "이 반려는 누가 한 거지?"에 답할 수 없다.
> **값을 추가하면서 그 값의 쓰기 권한도 같이 좁힌 것** — 데이터 무결성을 타입이 아니라 **검증으로** 지킨 사례다.

**DB enum 도 함께 넓혔다** — MySQL `ENUM` 은 스키마에 값 목록이 박혀 있어서 마이그레이션이 필요하다:

```sql
ALTER TABLE food
    MODIFY COLUMN content_failure_kind ENUM ('NOT_FOOD','JUDGE_REJECTED','INGREDIENT_GUARD','ADMIN_REJECTED') NULL;
```

코틀린 enum 과 DB enum **양쪽을 같이** 고쳐야 한다는 게 `@Enumerated(EnumType.STRING)` + `columnDefinition` 조합의 대가다. → [[10. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]

### 2-3. 삭제 시 이름 반납 — **실제 500 버그 수정**

이게 이 PR 의 알맹이다.

**무엇이 터졌나:**

```
"김치찌개" 삭제 → status = DELETED (행은 남고, korean_name = "김치찌개" 그대로)
"김치찌개" 재등록 시도
  → 중복 검사: findByKoreanNameIn 은 @SQLRestriction 때문에 ACTIVE 만 본다 → "없네, 통과" ✅
  → INSERT → uq_food_korean_name 위반 → 💥 500
```

**검사는 통과했는데 제약이 막는다.** 애플리케이션이 보는 세계(ACTIVE 만)와 DB 제약이 보는 세계(전부)가 **다르기 때문**이다.

> [!warning] 소프트삭제 + 유니크 제약의 고전적 함정
> 소프트삭제는 행을 남긴다. 유니크 인덱스는 **살았든 죽었든 모든 행**을 본다. 그래서 **"지웠는데 이름을 계속 붙들고 있는"** 상태가 된다.
> [[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|PR 209]] 리뷰에서 *"MySQL 은 부분 유니크 인덱스(`WHERE status <> 'DELETED'`)를 지원하지 않는다"* 는 판정이 있었는데, **그 제약이 바로 여기서 비용을 청구한 것**이다. PostgreSQL 이면 부분 인덱스로 끝났을 문제다.

**해법 — 삭제할 때 매치키를 "묘비(tombstone)"로 바꿔 키를 놓아준다:**

```kotlin
// 삭제
food.deletedOriginalKoreanName = food.koreanName                    // ① 원명은 별도 컬럼에 보존
food.koreanName = deletedKoreanNameOf(food.koreanName, food.id)     // ② 매치키만 묘비로

// 접미 충돌 불가: 음식 id 는 유니크·불변이라 tombstone 키가 겹칠 수 없고(255자 절단 무관),
// 정규화(순수 한글)로 원명에 구분자가 못 들어간다. 원명은 별도 컬럼이 보존한다.
private fun deletedKoreanNameOf(name: String, foodId: Long): String {
    val suffix = "$DELETED_NAME_SEPARATOR$foodId"                   // "_deleted_42"
    return name.take(KoreanMenuNameNormalizer.MAX_MENU_NAME_LENGTH - suffix.length) + suffix
}
private const val DELETED_NAME_SEPARATOR = "_deleted_"
```

- **왜 매치키만 바꾸나** — 유니크 제약이 걸린 건 `korean_name` **하나뿐**이다. `display_name` 은 유니크가 아니므로 건드릴 이유가 없고, **건드리면 오히려 손해**다: 삭제 목록·상세에서 운영자가 원래 이름을 알아볼 수 없게 된다. **문제가 있는 컬럼만 최소로 손댄 것.**
- **구분자 `_deleted_` 가 안전한 이유** — 매치키는 정규화로 **순수 한글(`가`~`힣`)만** 남는다. 밑줄·영문·숫자가 **원래 들어갈 수 없으므로** 구분자와 절대 충돌하지 않는다. **정규화가 강했던 게 여기서 배당금을 준다.**
- **접미사가 `foodId` 인 이유** — 음식 id 는 **유니크하고 불변**이다. 그래서 묘비 키끼리 **절대** 겹치지 않는다. 코드 주석의 *"(255자 절단 무관)"* 이 그 뜻이다.

> [!note] 원래 요청은 **타임스탬프**였다 — 왜 id 로 바뀌었나
> 초판은 요청대로 `_deleted_<epochMillis>` 였다. 그런데 **255자 절단과 만나면 구멍이 생긴다**:
> - **타임스탬프**: 이름이 긴 서로 다른 두 음식이 **잘린 뒤 앞부분이 같아지고**, 하필 **같은 밀리초에** 삭제되면 묘비 키가 충돌한다. 확률은 낮지만 **0 이 아니다.**
> - **음식 id**: 접미사 자체가 **음식마다 유일**하므로, 이름이 아무리 잘려도 **묘비 키가 겹칠 수 없다.**
>
> 덤으로 **id 는 불변**이라 같은 음식을 지웠다 복원했다 반복해도 묘비 키가 늘 같다(타임스탬프는 매번 달라진다).
> **"언제 지웠나"는 `updated_at` 이 이미 갖고 있다** — 접미사는 시각을 기록하는 자리가 아니라 **유일성만 만들면 되는** 자리였다.

> [!warning] 여기가 리뷰로 두 번 바뀐 자리다 — 배울 게 그 과정에 있다
> **초판**은 접미사가 `System.currentTimeMillis()` 였고 **원명 보존 컬럼이 없었다.**
>
> | | 초판 | 최종 |
> |---|---|---|
> | 접미사 | `_deleted_<epochMillis>` (최초 요청안) | **`_deleted_<foodId>`** |
> | 원명 | **묘비 문자열에서 `substringBefore` 로 복구** | **`deleted_original_korean_name` 컬럼에 보존** |
> | 255자 초과 시 | **원명 앞이 잘려 복구 불가** 💥 | 잘려도 **원명은 컬럼에 온전** |
>
> **초판의 결함**: 이름이 길면 접미사 자리를 만들려고 앞을 잘라내는데, 그러면 복원할 때 `substringBefore` 로 되돌려도 **잘린 이름이 나온다.** 조용히 데이터가 손상되는 종류다.
> **교훈**: **문자열에 정보를 인코딩해 두고 나중에 파싱해 되찾는 방식은 길이 제한 앞에서 깨진다.** 되찾아야 할 값이면 **따로 저장**하는 게 맞다. (id 접미사는 그래도 남았는데, 그건 되찾을 정보가 아니라 **유일성만 만들면 되는** 값이라서다.)

**복원은 접미사를 벗긴다 — 단, 그 사이 누가 그 이름을 차지했을 수 있다:**

```kotlin
val originalName = food.deletedOriginalKoreanName ?: originalKoreanNameOf(food.koreanName)  // ← 컬럼 우선, 없으면 파싱(레거시)
if (foodRepository.findByKoreanNameIn(setOf(originalName)).any { it.id != food.id }) {
    throw BusinessException(ErrorCode.FOOD_RESTORE_NAME_CONFLICT)   // 409 FOOD-009
}
food.koreanName = originalName
food.deletedOriginalKoreanName = null                                // ← 묘비 흔적 제거
```

- **409 FOOD-009 를 새로 판 이유** — "복원 실패"라고만 하면 FE 가 뭘 안내할지 모른다. **"이름 충돌"**이라고 알려줘야 *"새로 만든 음식의 이름을 바꾼 뒤 다시 시도하세요"* 를 띄울 수 있다. → [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]]
- **`?:` 폴백이 레거시를 받는다** — 컬럼 도입 **전에** 삭제된 행은 `deletedOriginalKoreanName` 이 널이라 **문자열 파싱으로 떨어진다.** 접미사도 없으면 `substringBefore` 가 원본을 그대로 돌려주니 결과적으로 no-op.
- **그리고 backfill 마이그레이션이 그 레거시를 정리한다** — 옛 DELETED 행에도 묘비 규칙을 소급 적용한다(**멱등**이라 여러 번 돌아도 안전).
- **복원 레이스도 막는다** — 검사와 저장 사이에 남이 그 이름을 차지하면 **flush 시점 유니크 위반**이 나는데, 그것도 **409 FOOD-009 로 매핑**한다. 즉 **검사(친절한 안내용)와 제약(진짜 보증)의 두 겹** — [[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지|24번 노트]]의 중복 주문 방어와 같은 구조다.

## 3. 세 변경이 사실 한 뿌리다

따로 보면 잡동사니 같지만, **전부 "이름과 상태를 어떻게 표기하느냐"** 다.

```
매치키 ≠ 표시명 을 분리        →  2-1  화면 이름을 자유롭게
그 분리 덕에 삭제 개명이 안전  →  2-3  매치키만 바꾸면 표시는 그대로
상태 표기의 해상도를 올림      →  2-2  "실패"를 파이프라인/사람으로 가름
```

**2-1 과 2-3 은 서로를 가능하게 한다** — 이름이 하나였다면 삭제 시 개명이 곧 **화면에 `김치찌개_deleted_1756…` 이 뜨는 것**을 뜻했을 테고, 그러면 이 해법을 쓸 수 없었다.

## 4. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 6건을 물었고 **전부 판정이 닫혔다**(2026-09-02, 커맨드 센터 경유). **반영 1 · 반려 4 · 칭찬 1.**
> **5번은 내가 걱정한 시나리오가 애초에 불가능**했다 — 그런데 그걸 막는 게 [[PR 215 — 검수 비대상 거절에 전용 코드 FOOD-008 채번|PR 215]] 에서 추출한 바로 그 가드다.

### ✅ 1. `System.currentTimeMillis()` 충돌 가능성

같은 음식을 같은 밀리초에 두 번 삭제할 수 없고, 다른 두 음식이 같은 매치키를 가질 수도 없으니 실제 충돌은 없어 보인다. 다만 **근거가 코드에 안 적혀 있다.**

**→ 반영 완료**(커밋 `6af1c914`). 실충돌은 **세 겹으로 불가능**하다 — ①같은 음식 같은 ms 이중 삭제 불가 ②매치키 유니크 ③정규화로 구분자 충돌 0. 다만 **그 세 겹이 코드 어디에도 안 적혀 있어서**, 다음 사람이 "타임스탬프로 유일성을 보장한다고?" 하고 불안해할 자리다. 주석 발주.

### ⬜ 2. 매치키 문자열을 참조하는 곳이 또 있나 — 조사 결과 없음

`ScanHistory` 는 `foodId` 로 참조하니 안전한데, **매치키 문자열로 조인하는 경로**가 있으면 개명이 그걸 깬다.

**→ 조사 완료. 깨지는 경로 0건 — 수정 불요.** 매치키 문자열을 **조인 키로 붙들고 있는 곳이 없다**는 게 4갈래로 확인됐다:

| 경로 | 왜 안 깨지나 |
|---|---|
| **스캔 매칭** (`findByKoreanNameIn`) | `@SQLRestriction` 으로 **ACTIVE 만** 본다 — 삭제된 행은 개명 전에도 이미 매칭 대상이 아니었다 |
| **존재 검사**(중복 등록) | 개명 덕에 **오히려 재등록 500 이 사라졌다**(§2-3 이 고친 그 버그) |
| **임베딩·벡터** | **로드 시점의 실체**를 기준으로 만든다 — 저장된 이름 문자열로 조인하지 않는다 |
| **영속 스냅샷**(스캔 이력 등) | **표시용**으로 남긴 값이지 **조인 키가 아니다** |

> [!tip] 왜 이 질문을 했어야 했나 — 답이 "괜찮다"여도
> **개명은 "아무도 그 문자열을 조인 키로 붙들고 있지 않을 때만" 안전하다.** id 참조는 개명에 무관하지만 **문자열 참조는 조용히 깨진다** — 에러도 안 나고 그냥 안 맞는다.
> 여기선 마침 **모든 경로가 id 를 쓰거나 ACTIVE 만 보고 있어서** 안전했는데, 그건 **운이 아니라 앞선 설계의 결과**다: 연관관계를 id 로만 두는 규약(→ [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]])과 소프트삭제 자동 필터(→ [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]])가 **개명이라는 나중 결정을 미리 받쳐 준** 셈이다.

### ⬜ 3. 복원 충돌을 운영자가 두 단계로 풀어야 한다

복원 API 가 `newKoreanName` 을 옵션으로 받아 한 번에 끝낼 수 없나?

**→ 반려(v1).** **복원의 의미론은 "원래대로"** 이고 **이름 변경은 수정(PUT)의 몫**이다. 한 API 에 두 의미를 얹지 않는 게 레포 관례다. 충돌 자체가 드물어 2단계를 감수한다.

> [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭|PR 216]] 에서 *"복원이 `contentStatus` 를 안 바꾼다"* 를 물었을 때와 **완전히 같은 답**이 돌아왔다 — **복원은 되돌리는 것이지 바꾸는 게 아니다.** 두 번 같은 답을 들었으니 이건 이 레포의 확립된 원칙으로 봐야 한다.

### ⬜ 4. `contentFailureKind` 의 의미가 넓어졌다 — 출처 필드를 분리해야 하나

**→ 반려(YAGNI).** 값이 **4개인 지금은 무리가 없다.** 사람 쪽 사유가 **실제로 늘어날 때** 리팩터한다.

> 내 지적은 "언젠가 늘어나면"이라는 **가정 위의 비용**을 말한 것이고, 판정은 **그 가정이 실현되면 그때 치른다**는 쪽이다. 지금 필드를 나누면 4개짜리 enum 을 두 필드로 쪼개 놓고 쓰는 셈이라 오히려 복잡하다.

### ⬜ 5. `reject()` 가 기존 `contentFailureKind` 를 덮어쓴다 — 사유가 사라지지 않나

**→ 반려(안전 확인됨). 그리고 내가 괄호로 단 추측이 정답이었다.**

실코드 확인 결과 **그 시나리오는 애초에 불가능**하다:

```kotlin
fun recordContentFailure(kind, reason) {   // 파이프라인 실패 (NOT_FOOD 등)
    contentFailureKind = kind
    …
    contentStatus = FoodContentStatus.FAILED       // ← PENDING_REVIEW 가 아니다
}

fun reject(reason: String?) {
    requireReviewable()                            // ← PENDING_REVIEW 만 통과
    contentFailureKind = FoodContentFailureKind.ADMIN_REJECTED
    …
}
```

파이프라인이 실패시킨 음식은 **`FAILED`** 상태라 **검수 큐에 올라오지 않고**, `requireReviewable()` 이 반려 자체를 막는다. **덮어쓸 사유가 존재할 수 없다.**

> [!tip] 가드 하나가 두 번 일한다
> `requireReviewable()` 은 [[PR 215 — 검수 비대상 거절에 전용 코드 FOOD-008 채번|PR 215]] 에서 **"복붙 정리 + 로그 추가"** 목적으로 추출된 함수다. 그런데 그게 여기서 **데이터 무결성 가드**로도 일하고 있다 — 사유 소실을 구조적으로 막는다.
> **좋은 가드는 만들 때 의도하지 않은 것까지 막아준다.** 그리고 이런 건 **함수로 뽑혀 있을 때** 눈에 띈다 — `if` 두 개로 복붙돼 있었다면 "두 곳 다 그런가?"를 따로 확인해야 했다.

### 👍 6. 테스트가 "동명 재등록 성공"까지 검증한다

**→ 칭찬 수용.** 증상(500)이 아니라 **원래 하려던 일(재등록)이 되는지**를 확인한다. 500 만 안 나면 통과하는 테스트였다면, 개명은 됐는데 재등록이 다른 이유로 막히는 경우를 놓쳤을 것이다.
