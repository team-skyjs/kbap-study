## 0. 한 줄 요약

**테이블 하나(`food_image`)를 만들고 기존 데이터를 옮겨 담았는데, 밖에서 보면 아무것도 안 바뀐다.** 앱도 공개 API 도 **전부 예전 필드(`food.image_ref`)를 그대로 읽는다.** 그 "안 바뀜"을 만드는 장치가 이 PR 의 전부다.

## 1. 무엇을 하려는 기획인가

지금은 **음식 하나에 이미지 한 장**이다(`food.image_ref`). 이걸 **여러 장 쌓아 두고 어드민이 대표를 고르는** 구조로 바꾸려 한다.

| 단계 | 무엇 | 이 PR |
|---|---|---|
| **P1** | `food_image` 테이블 · 백필 · 수집 연결 | ⬅️ **여기** |
| P2 | 재생성·선택 배치·대표 교체 **API** | 다음 |
| P3 | 어드민 **화면**(갤러리 뷰·대표 선택 버튼) | 그다음 |

**앱은 이번 웨이브에서 아예 안 바뀐다**(스펙 결정 D2). 갤러리는 **어드민만** 본다.

> 기획 출발점도 dogfooding 이다 — *"잘못/부적절하게 생성된 음식 이미지를 다시 만들 수 있게"*. [[PR 225 — 멤버 주문 항목·합계 추가 (Int 오버플로)|225]]와 같은 계열이다.

## 2. 핵심 설계 ① — 왜 `food.image_ref` 를 안 지우나

새 테이블을 만들었으면 옛 컬럼은 지우는 게 정석처럼 보인다. **안 지웠다.** 그게 이 PR 의 첫 번째 결정이다.

### 이유: 그 필드를 **모든 공개 API 가 읽고 있다**

`food.image_ref` 는 목록·상세·검색·주문·스캔·리뷰 응답에 전부 실린다. 그리고 **이미 출시된 앱**이 그걸 읽는다. 지우면:

```
food.image_ref 삭제 → 모든 응답 조립 코드 수정 → 앱 계약 변경 → 앱 재배포 → 구버전 앱 깨짐
```

**남겨두면 그 전부가 일어나지 않는다.**

### 그래서 `image_ref` 의 정체가 바뀌었다 — **비정규화 캐시**

```
food_image 테이블          ← 진실(원본). 음식당 여러 행, 그중 하나가 is_primary
food.image_ref            ← 그 primary 행의 image_key 를 복사해 둔 것 (캐시)
```

**같은 값이 두 군데 있다.** 정규화 원칙으로는 나쁜 짓인데, 일부러 그렇게 했다:

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 비정규화 캐시 유지 | **읽는 쪽 전부 무변경**(조인도 불필요) | **두 값이 어긋날 수 있다**(정합성 부담) |

> [!tip] "비정규화"는 게으름이 아니라 거래다
> 데이터를 한 곳에만 두는 게 원칙이지만, **읽는 쪽이 아주 많고 그 전부를 고칠 수 없을 때** 사본을 남긴다. 대가는 **"두 값을 어떻게 맞춰 두느냐"** 라는 새 숙제이고, 이 PR 의 §3 이 그 숙제다.
> 이미 본 사례가 있다 — [[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|219]]의 아웃박스 `displayName` 스냅샷. **거긴 낡아도 되는 사본**(그때의 사실)이었고, **여긴 절대 낡으면 안 되는 사본**이다. 같은 "사본"이라도 요구가 다르다.

## 3. 핵심 설계 ② — 불변식을 누가 지키나

**불변식(invariant)** = 언제 봐도 반드시 참이어야 하는 규칙. 여기선 두 개다.

```
① food.image_ref == (그 음식의 is_primary 행의 image_key)
② 음식 하나에 is_primary 행은 정확히 1개
```

### ② 는 **DB 가 지킨다** — 생성 컬럼 + 유니크

MySQL 에는 **부분 유니크 인덱스**(`UNIQUE ... WHERE is_primary = 1`)가 없다. [[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|209]] 리뷰와 [[PR 218 — 표시 이름 편집·어드민 반려 유형·삭제 시 이름 반납|218]]에서 이미 비용을 치른 그 제약이다. 이번엔 **다른 우회로**를 쓴다:

```sql
`primary_food_id` bigint AS (IF(`is_primary` = 1, `food_id`, NULL)) STORED,
UNIQUE KEY `uq_food_image_primary` (`primary_food_id`),
```

**생성 컬럼(generated column)** — 다른 컬럼에서 **자동으로 계산되는** 컬럼이다. 여기선:

| `is_primary` | `primary_food_id` 값 | 유니크 검사 |
|---|---|---|
| `1`(대표) | `food_id` 그대로 | **같은 음식에 둘이면 위반** ✅ |
| `0`(대표 아님) | **`NULL`** | **NULL 은 유니크 검사에서 제외** — 몇 개든 허용 |

**핵심은 "SQL 의 유니크 제약이 NULL 을 무시한다"** 는 성질이다. 대표가 아닌 행은 전부 NULL 로 만들어 **검사 밖으로 빼내고**, 대표만 실제 값을 갖게 해서 **음식당 하나**를 강제한다.

> 이 기법은 이 레포에 **선례가 있다** — `image_batch_item.pending_food_id`. 새로 발명한 게 아니라 **있는 패턴을 재사용**했다. [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭|216]]의 native 우회가 217 로 번진 것과 같은 흐름이다.

### ① 은 **코드가 지킨다** — 그리고 여기가 제일 재밌다

이미지가 새로 생기면(`attachImage`) 갤러리와 `image_ref` 를 **동시에** 옮겨야 한다.

```kotlin
fun promoteAsPrimary(foodId: Long, imageKey: String) {
    demotePrimaryByFoodId(foodId)                       // ① 기존 대표를 먼저 끌어내린다
    val existing = findByFoodIdAndImageKey(foodId, imageKey)
    if (existing != null) { existing.isPrimary = true; save(existing) }
    else { save(FoodImage.primary(foodId, imageKey)) }  // ② 그다음 새 대표를 세운다
}

@Modifying(flushAutomatically = true)
@Query("update FoodImage fi set fi.isPrimary = false where fi.foodId = :foodId and fi.isPrimary = true")
fun demotePrimaryByFoodId(foodId: Long): Int
```

**왜 "강등 먼저"인가** — 순서를 바꾸면 터진다.

```
[새 대표 먼저 저장 → 기존 대표 강등]  ❌
  INSERT (is_primary=1)  →  이 순간 같은 food_id 에 대표가 둘
                         →  uq_food_image_primary 위반 💥

[기존 대표 강등 → 새 대표 저장]  ✅
  UPDATE (is_primary=0)  →  대표 0개
  INSERT (is_primary=1)  →  대표 1개. 위반 없음
```

> [!warning] 그런데 "순서대로 썼다"가 곧 "순서대로 실행된다"가 아니다
> JPA 는 우리가 `save()` 를 부른 순서대로 SQL 을 보내지 않는다. **영속성 컨텍스트에 모아 뒀다가 트랜잭션이 끝날 때 한꺼번에 내보내는데(flush), 그때 하이버네이트는 자기 순서를 쓴다 — INSERT 를 UPDATE 보다 먼저** 내보내는 경향이 있다. → [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]
>
> 그래서 코드에서 강등을 먼저 써도, **그냥 두면 INSERT 가 앞질러 나가** 유니크 제약에 걸릴 수 있다. `@Modifying(flushAutomatically = true)` 가 그걸 막는다 — **이 UPDATE 를 실행하기 전에 밀린 것들을 먼저 내보내라**는 지시이자, 이 UPDATE 자체가 **즉시 DB 로 나가게** 만든다.
>
> **배울 점**: DB 제약(유니크)과 ORM 의 지연 쓰기(flush)가 만나면 **"코드 순서 ≠ SQL 순서"** 라는 함정이 생긴다. 제약을 촘촘히 걸수록 이 문제를 자주 만난다.

## 4. 핵심 설계 ③ — 벡터 문서에서 `imageRef` 를 걷어냈다

[[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기|벡터 저장소]]에 넣는 문서에 `imageRef` 메타데이터가 들어 있었다. **전부 제거**했다.

### 왜 지웠나 — 읽는 코드가 **0** 이었다

조사해보니:
- **검색은 MySQL 이 한다** — 벡터 저장소는 **id 와 점수만** 돌려주고, 화면에 뿌릴 내용은 **그 id 로 MySQL 을 다시 읽어** 만든다.
- 그래서 벡터에 복사해 둔 `imageRef` 를 **읽는 프로덕션 코드가 하나도 없었다.**

**즉 낡을 수만 있고 쓰이지는 않는 사본**이었다. 갤러리가 들어오면 이미지가 바뀔 일이 많아지니 **더 잘 낡는다.** 그래서 지웠다.

> [!tip] 이 결정이 규칙을 하나 굳혔다
> **"벡터 = id, MySQL = 내용."** 벡터 저장소는 **누가 비슷한지만** 답하고, 무엇을 보여줄지는 항상 원본에서 읽는다.
> PR 이 이 규칙을 레포 `CLAUDE.md` 에 넣자고 **제안**했다(직접 수정은 안 하고 문구만 올렸다):
> > 벡터 스토어 = id만 반환, 표시 내용은 항상 MySQL 재조회. 벡터 메타데이터에 표시용 필드를 넣지 말 것(넣으려면 변경감지 해시에 포함해 stale 방지).

- **"반쪽 삭제 금지"** — 상수·필드·저장 코드·대입 코드를 **전부** 지웠다. 하나라도 남기면 다음 사람이 그걸 보고 다시 채운다. 전부 지우면 **컴파일러가 재발을 막아준다.**
- **기존 벡터에 남은 값은 그대로 둔다** — 재업서트될 때만 사라지고 대부분 **영구 잔존**한다. **읽는 코드가 0 이라 무해**하므로 전량 재인덱싱은 안 한다. [[28. 임베딩과 벡터 검색 — 뜻으로 음식 찾기|28번 노트]]의 "재색인은 비싸다"와 같은 판단.

## 5. 마이그레이션이 2개인 이유

```
V…18.12.29__create_food_image_table.sql     ← 테이블 생성
V…18.12.30__backfill_food_image_primary.sql ← 기존 image_ref 를 primary 행으로 복사
```

**왜 한 파일에 안 넣었나** — **백필 SQL 을 테스트가 리소스로 읽어 다시 실행**하기 때문이다. `CREATE TABLE` 과 섞여 있으면 **두 번째 실행에서 "이미 존재함" 으로 터진다.**

백필은 **멱등**하게 짰다:

```sql
INSERT INTO food_image (…)
SELECT f.id, f.image_ref, 1, 'GENERATED', 0, 'ACTIVE', NOW(6), NOW(6)
…
WHERE f.image_ref IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM food_image fi WHERE fi.food_id = f.id);   -- ← 이미 있으면 건너뜀
```

> [[PR 218 — 표시 이름 편집·어드민 반려 유형·삭제 시 이름 반납|218]]의 tombstone 백필과 **같은 선례**를 따랐다 — 멱등 + 별도 파일. **한 번 만든 패턴이 다음 작업의 기본형이 되는** 모습이 이 시리즈에서 계속 보인다.

## 6. 리뷰가 잡은 것 — 테스트 DB 정리 경로

Codex 리뷰의 P1 지적이 실용적이다:

> **새 자식 테이블을 통합테스트 DB 정리 경로에 안 넣으면**, FK 때문에 잔여물이 남아 다른 테스트를 오염시킨다.

`food_image` 는 `food` 를 **FK 로 참조**한다. 테스트가 끝나고 `food` 를 지우려 하면 **자식이 남아 있어 삭제가 막히고**, 남은 행이 다음 테스트에 섞여 든다.

> [!tip] 테이블을 새로 만들 때 딸려오는 숙제
> 스키마에 테이블을 추가하는 일은 `CREATE TABLE` 로 끝나지 않는다 — **테스트 정리 경로**, **삭제 순서**(자식 먼저), **소프트삭제 정책**까지 딸려온다. 이 PR 은 그중 정리 경로를 리뷰에서 놓쳤다가 잡혔다.

**소프트삭제 정책도 정해뒀다**(스펙 D3) — `FoodImage` 도 `BaseEntity` 라, 음식을 삭제해도 **갤러리 행은 남고 복원 시 함께 부활**한다. → [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭]]

## 7. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 6건을 물었고 판정이 났다(2026-09-03). **반려 3 · 유지 확인 2 · 칭찬 1 · 유효 1.**
> **4번의 답이 이 노트에서 가장 중요한 구분**을 만들어냈다 — 아래에서 가장 길게 다룬다.

### ⬜ 1. 불변식 ①의 구멍 — 어드민 PUT 의 `imageRef` 직접 편집

**→ 가드 불필요. 근거가 있다.**
- **어드민 UI 에 이미지 편집 입력 자체가 없다.**
- `imageRef` 는 PUT 왕복에서 **기존 값이 그대로 재전송**된다 → **변화 0**.
- 즉 실제로 어긋나게 만들려면 **손으로 API 를 직접 호출**해야 한다.

**임시 가드를 넣으면 P2 에서 바로 걷어내야 하는 또 다른 임시 구조**가 된다([[PR 224 — LLM 비용 레포트 컨트롤러 합류 (임시 분리 청산)|224]]의 교훈을 반대 방향으로 적용한 셈). **P2(KB-414) DoD 에 이미 포함**돼 있으니 그대로 간다.

### ⬜ 2. `source` enum 에 값이 하나뿐

**→ 유지. [[PR 217 — 멤버 목록·상세·활동 3종과 대시보드 메트릭 REST|217]] 의 `sanctions` 와는 성격이 다르다.**

| | 217 `sanctions: []` | 230 `source: GENERATED` |
|---|---|---|
| 무엇인가 | **미래를 위한 자리표시** | **현재 사실의 기록** — 지금 모든 이미지는 생성물이다 |
| 없으면 | 나중에 필드를 추가하면 됨(하위호환) | 업로드 이미지가 섞였을 때 **구분 불가** |

그리고 값 추가는 `ALTER … MODIFY` 라 **저렴하다.** — 내 지적("enum 은 마이그레이션이 필요해 성격이 다르다")은 맞았지만, **결론이 반대**였다: 마이그레이션 비용보다 **출처를 구분 못 하게 되는 비용**이 크다.

### ⬜ 3. `sort_order` 도 이번엔 미사용

**→ 유지.** P3 갤러리 UI 가 **곧 순서를 다루고**, 컬럼 추가는 마이그레이션 비용이 없어 부담이 작다. **P3 까지 안 쓰이면 그때 재검토.**

### ⭐⬜ 4. `food.image_ref` 를 언제까지 캐시로 남기나 — **회수 대상이 아니다**

**→ 아주 중요한 구분이 나왔다.**

> ### 임시 스캐폴딩 vs 의도된 중복
>
> | | **임시 스캐폴딩** | **의도된 중복(비정규화 캐시)** |
> |---|---|---|
> | 예 | [[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|219]] 의 분리된 컨트롤러 · [[PR 223 — 음식 목록 3필터·LIKE 이스케이프·READY 직행 가드|223]] 의 `/deleted` 중복 경로 | **`food.image_ref`** |
> | 왜 생겼나 | **당장의 제약**(파일 충돌·기존 계약) 회피 | **읽기 경로에서 조인을 없애려는 영구 설계** |
> | 언제 없애나 | **조건이 충족되면 회수**(224 가 그 예) | **없애지 않는다** |
> | 정합성 | — | **불변식으로 보장**(§3) |
>
> **앱이 `images[]` 를 읽게 되는 다음 웨이브 이후에도 `image_ref` 는 남는다** — 갤러리가 생겨도 **썸네일 1장은 여전히 필요**하기 때문이다.

> [!warning] 다음 사람이 오해하기 쉬운 자리라 명시한다
> 이 시리즈가 계속 **"임시 구조에는 회수 조건을 붙여라"**([[PR 224 — LLM 비용 레포트 컨트롤러 합류 (임시 분리 청산)|224]])를 강조했기 때문에, **중복이 보이면 반사적으로 "회수 대상"으로 읽기 쉽다.**
> **`image_ref` 는 아니다.** 이건 **영구 유지 + 불변식으로 정합 보장**이 정답이다. **중복이라고 다 빚이 아니다** — 갚을 빚과 **의도한 투자**를 구분해야 한다.

### ✅ 5. 벡터 잔존 수용은 "지금 기준" 무해

**→ 정확한 지적, 그대로 유효.** 규칙이 `CLAUDE.md` 에 반영되기 전까지는 **구두 약속**이 맞다. **승인 대기 중**이며, 반영되면 이 노트에도 표시한다.

> 이게 왜 중요하냐면 — **"읽는 코드가 0 이라 무해하다"는 지금의 사실**이다. 나중에 누가 벡터 메타데이터를 읽는 코드를 짜면 **낡은 값을 진짜로 읽게** 된다. 규칙이 문서에 박혀야 **그 코드를 안 짜게** 된다.

### 👍 6. P1 이 "겉보기 변화 0"인 게 미덕

**→ 칭찬 접수.** **"데이터 → API → 화면 3단 분리"** 라는 표현이 이 전환의 구조를 잘 담는다.

## 9. 다음에 이 PR 을 다시 볼 때

1. **`image_ref` 는 이제 비정규화 캐시**다 — 진실은 `food_image` 의 primary 행. 남겨둔 덕에 **앱·공개 API 가 무변경**이다.
2. **"음식당 대표 1개"는 DB 가 지킨다** — 생성 컬럼 `IF(is_primary, food_id, NULL)` + 유니크. **NULL 은 유니크 검사에서 빠진다**는 성질을 이용한 것.
3. **강등이 먼저인 이유** — 새 대표를 먼저 넣으면 순간적으로 대표가 둘이 되어 제약 위반. 그리고 **`flushAutomatically` 가 없으면 코드 순서대로 SQL 이 안 나간다.**
4. **벡터에는 표시용 데이터를 넣지 않는다** — 낡을 수만 있고 읽히지는 않는다.
5. **큰 전환은 "겉보기 변화 0"인 토대부터** — 데이터 → API → 화면 순서로 쪼개면 각 단계가 안전하다.
