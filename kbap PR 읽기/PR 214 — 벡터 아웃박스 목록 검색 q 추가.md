## 0. 한 줄 요약

**아웃박스 목록에 `q` 파라미터 하나를 붙였다.** 그런데 아웃박스 테이블에는 음식 이름이 없어서(연관관계도 없다), **JPQL `exists` 서브쿼리로 `food` 테이블을 뒤져 매칭**해야 했다. 응답은 그대로라 **하위호환**이다.

## 1. 왜 검색이 필요했나

[[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|PR 209]] 가 만든 화면은 **id 내림차순 50건씩**이 전부였다. 운영자가 "아까 재시도 누른 그 건"을 다시 보려면 페이지를 넘겨가며 눈으로 찾아야 한다. **QA 에서 나온 실제 불편**을 고치는 PR이다.

## 3. 핵심 — 조인 없이 다른 테이블로 검색하기

### 문제

찾고 싶은 건 **아웃박스 행**인데, 검색어는 **음식 이름**이다. 그런데:

- `food_vector_outbox` 테이블에는 `food_id`만 있고 **이름이 없다**.
- 이 레포는 **JPA 연관관계를 안 쓴다** — `@ManyToOne Food food` 같은 필드가 없으니 `join o.food f` 도 못 쓴다. → [[9. 연관관계를 쓰지 않는 설계 — N+1을 애초에 만들지 않기]]

### 해법 — `exists` 서브쿼리

```sql
select o from FoodVectorOutbox o
where (:foodId is not null and o.foodId = :foodId)
   or exists (
       select 1 from Food f
       where f.id = o.foodId and f.displayName like concat('%', :keyword, '%')
   )
```
— `searchByFoodKeyword` (`FoodVectorOutboxJpaRepository`). 상태 필터가 붙는 `searchByFoodKeywordAndStatus` 는 이 조건을 `o.outboxStatus = :outboxStatus and (…)` 로 감싼 것뿐이다.

- **연관관계 매핑이 없어도 JPQL 안에서는 다른 엔티티를 직접 참조할 수 있다.** `exists` 서브쿼리가 `o.foodId` 를 바깥에서 끌어와 `Food` 를 뒤진다(상관 서브쿼리). **엔티티 매핑상의 연관 ≠ 쿼리 조인**이라는 구분이 여기서 실물로 나온다.
- `select 1` — 값이 필요한 게 아니라 **있느냐만** 보므로 아무거나 고른다. SQL 의 관용구.
- **소프트삭제된 음식은 이름으로 안 잡힌다** — `Food` 에 `@SQLRestriction("status = 'ACTIVE'")` 가 걸려 있어 서브쿼리에도 자동으로 붙기 때문. PR 은 이걸 버그로 두지 않고 **Swagger 에 명시**했다("숫자(foodId)로만 찾힌다"). → [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]

### 숫자면 foodId 로도 찾는다 — 널이면 그 조건이 통째로 꺼진다

```kotlin
val foodId = keyword.toLongOrNull()          // 숫자가 아니면 null
```

검색어가 `"123"` 이면 **이름 부분 일치 + foodId=123** 을 둘 다 본다. 숫자가 아니면 `null` 이 들어가고, 쿼리의 `(:foodId is not null and o.foodId = :foodId)` 가 **통째로 거짓**이 되어 **이름 조건만 남는다.**

> [!note] 처음엔 센티널 `-1` 이었다
> 초기 구현은 `keyword.toLongOrNull() ?: NO_FOOD_ID`(`= -1L`) 로, **"절대 어떤 행과도 안 맞는 id"** 를 넣어 조건을 무력화했다. id 가 `AUTO_INCREMENT` PK 라 동작은 안전했지만, **`-1` 의 뜻이 쿼리에 안 드러난다**는 리뷰 지적으로 널 방식으로 바뀌었다(§6-3). **동작은 같고 의도만 드러나게 된 리팩터링**이다.

> [!note] 왜 이렇게까지 하나
> 운영자는 화면에서 **`foodId` 를 눈으로 보고 있다**(§3 의 목록 항목에 `foodId` 가 있다). 그 숫자를 그대로 검색창에 붙여넣는 게 가장 자연스러운 동작이라, 이름 검색과 **한 칸에서** 처리한다. 음식 목록 `q` 도 같은 관례라 일관된다.

## 4. 작은 기능이 4갈래로 불어난다

```kotlin
val result = when {
    keyword == null && status == null -> findAll(pageable)                          // ①
    keyword == null                   -> findByOutboxStatus(status!!, pageable)     // ②
    else -> when (status) {
        null -> searchByFoodKeyword(keyword, foodId, pageable)                      // ③
        else -> searchByFoodKeywordAndStatus(keyword, foodId, status, pageable)     // ④
    }
}
```

**선택 파라미터 2개(`q`·`status`) = 조합 4가지**, 각각 다른 리포지토리 메서드다. 하나 더 늘면 8가지가 된다.

- **왜 이렇게 짰나** — Spring Data JPA 는 **조건을 동적으로 조립하는 기능이 기본 제공되지 않는다.** 파라미터가 널일 때 `WHERE` 절을 빼려면 별도 도구(Querydsl·Criteria API·`@Query` 안의 `:param is null or …` 트릭)가 필요하다. 이 레포는 도구를 안 들이고 **분기로 푼다**.
- **대안 하나** — `where (:keyword is null or exists(...)) and (:status is null or o.outboxStatus = :status)` 처럼 한 쿼리로 합칠 수 있다. 다만 **널 검사가 인덱스 사용을 방해**할 수 있고 쿼리가 읽기 어려워진다. 지금처럼 조합이 4개면 분기가 오히려 명확하다 — **6~8개가 되면 그때 도구를 고민할 자리**다.

## 5. 하위호환으로 만든 방법

```kotlin
fun getVectorOutboxPage(page: Int, status: …?, query: String? = null)   // ← 기본값
```

- **기본값이 있는 새 파라미터**라 기존 호출부(Thymeleaf 경로)는 **한 줄도 안 고쳐도 컴파일된다.**
- **응답 DTO 무변경** — FE 는 `q` 를 안 보내면 예전과 똑같이 동작한다.
- 이게 [[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|PR 209]] 의 `enqueueReadyFoodsForVectorSync(): Unit → Int` 와 같은 요령이다 — **넓히기만 하고 좁히지 않으면 깨지지 않는다.**

## 6. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 아래 4개를 물었고 **실제 리뷰로 올라가 판정이 났다**(2026-09-01, 커맨드 센터 세션 경유 전달).
> **수용 1 · 수정 발주 2 · 의도 확정 1.**

### ⬜ 1. `like concat('%', :keyword, '%')` 는 인덱스를 못 탄다

앞에 와일드카드가 붙으면 B-트리 인덱스를 못 쓰고 전체 스캔이 된다. **음식 테이블이 커지면 이 검색이 느려지는 첫 자리**다.

**→ 수용(수정 안 함).** 어드민 2인이 가끔 여는 저빈도 화면이고, **음식 목록 `q` 도 이미 같은 방식**이라 여기만 바꿀 이유가 없다. 다만 **"테이블이 커지면 최적화 1순위"** 라는 인식은 유지한다 — 전환 후보는 **FULLTEXT 인덱스** 또는 **prefix 검색**(`'kw%'`, 앞 와일드카드 제거).

### ✅ 2. 규약형 메서드 이름 + `@Query` 혼용

`findByFoodDisplayNameContainingOrFoodIdAndOutboxStatus` — `@Query` 를 직접 쓰는데도 Spring Data 자동 생성 규약처럼 이름을 지었다.

**→ 유효, 반영 완료**(커밋 `381f991a`). `@Query` 가 붙으면 **스프링이 이름을 파싱하지 않는다.** 즉 이름의 `Containing`·`And` 는 **아무 효력이 없는 장식**이고, 읽는 사람은 "이름이 곧 쿼리"라고 오해한다. → **`searchByFoodKeyword` · `searchByFoodKeywordAndStatus`** 로 리네임됐다.

### ✅ 3. 센티널 `-1`

도메인에 없는 값을 "절대 안 맞는 id" 로 쓴다.

**→ 유효, 반영 완료**(커밋 `381f991a`). id 는 `AUTO_INCREMENT` PK 라 **항상 1 이상**이므로 동작 자체는 안전했다. 다만 그건 **가정에 기댄 안전**이고 쿼리를 읽는 사람에게 `-1` 의 뜻이 안 보인다. → **`(:foodId is not null and o.foodId = :foodId)`** 로 교체됐다. 파라미터 타입도 `Long` → `Long?` 이 됐다.

### ✅ 4. `exists` 안의 소프트삭제 필터 — 의도인가?

**→ 의도 확정 + 이미 해소.** 서버 계약(Swagger)에 명시돼 있고, 지적한 **화면 안내도 반영됐다** — FE 가 검색창에 **"삭제된 음식은 foodId 로만 검색됩니다"** 힌트를 넣었다(P-A13). **서버 변경 없이 FE 에서 푼 케이스**다 — [[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|PR 209]] 의 "삭제된 음식 행 retry 비활성"과 같은 해법이다(판단 재료가 이미 응답에 있으면 FE 가 푼다).

## 7. 다음에 이 PR 을 다시 볼 때

3. 하위호환 요령: **기본값 있는 파라미터 추가 + 응답 무변**.
4. **리뷰 결과**(§6): 4건 중 **수용 1 · 수정 반영 2 · 의도 확정 1**. 반영 2건(메서드 리네임·센티널→널)은 **동작 무변 리팩터링**이라 §3 의 원리 설명은 그대로다.
