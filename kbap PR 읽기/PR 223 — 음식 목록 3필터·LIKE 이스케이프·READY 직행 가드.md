## 2. ① 필터 3개 — 조합 폭발을 어떻게 피했나

### 문제: 선택 파라미터가 늘면 분기가 두 배씩 는다

[[PR 214 — 벡터 아웃박스 목록 검색 q 추가|214번 노트]] §4 에서 본 그 문제다. 선택 파라미터 2개면 조합 4가지, **3개면 8가지, 4개면 16가지**다. 그때는 파라미터가 2개라 `when` 분기 4갈래로 풀었는데, **여기선 4개**(`q`·`status`·`failureKind`·`deleted`)라 그 방식이 무너진다.

### 해법: 조건을 쿼리 안에서 끄고 켠다

```sql
SELECT * FROM food
WHERE status = :entityStatus
  AND (:contentStatus IS NULL OR content_status = :contentStatus)
  AND (:failureKind   IS NULL OR content_failure_kind = :failureKind)
  AND (:keyword       IS NULL OR display_name LIKE CONCAT('%', :keyword, '%') ESCAPE '\\')
ORDER BY id DESC
```

**`(:param IS NULL OR 조건)`** 이 관용구다. 파라미터가 널이면 **그 줄이 항상 참이 되어 조건이 없는 셈**이 되고, 값이 있으면 조건으로 동작한다. **메서드 하나로 8가지 조합을 다 받는다.**

> [!note] 214 에서 배운 게 여기서 다시 쓰였다
> 214 리뷰에서 센티널 `-1` 을 **`(:foodId is not null and o.foodId = :foodId)`** 로 바꿨다. **같은 관용구의 반대 방향**이다:
> - `AND (:p IS NULL OR 조건)` — 널이면 **조건을 끈다**(다른 조건과 `AND` 로 묶일 때)
> - `(:p IS NOT NULL AND 조건)` — 널이면 **거짓**(다른 조건과 `OR` 로 묶일 때)
>
> **`AND` 문맥에서 끄려면 참이 되어야 하고, `OR` 문맥에서 끄려면 거짓이 되어야 한다.** 이걸 뒤집어 쓰면 조용히 전체가 매칭되는 버그가 된다.

- **`deleted` 는 널 조건이 아니라 값 매핑**이다 — `status = :entityStatus` 에 `"DELETED"` 또는 `"ACTIVE"` 를 넣는다. 기본값은 `false`(활성만).
- **native 쿼리인 이유**는 [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭|216번]]과 같다 — `@SQLRestriction` 이 자동으로 `ACTIVE` 를 붙여버려서, **삭제된 것을 보려면 우회**해야 한다.

### `/deleted` 엔드포인트는 남겼다

216 이 만든 `GET /api/admin/foods/deleted` 는 이제 `?deleted=true` 와 **같은 결과**다. 그런데 지웠다가는 **이미 발주된 FE 계약이 깨지므로** 남겼고, PR 본문에 *"신규 화면은 단일 목록 권장"* 이라고 방향만 적었다.

> **중복 경로가 생겼다** — 이건 비용이다. 언젠가 하나로 모아야 하고, [[PR 224 — LLM 비용 레포트 컨트롤러 합류 (임시 분리 청산)|224]] 처럼 **회수 조건을 적어 두지 않으면 영구가 된다.**

## 3. ② LIKE 이스케이프 — 이 PR 에서 가장 배울 게 많은 부분

### 무엇이 문제였나

검색어를 그대로 `LIKE '%키워드%'` 에 넣으면, **키워드 안의 `%` 와 `_` 가 특수문자로 해석된다.**

| SQL LIKE 의 특수문자 | 뜻 |
|---|---|
| `%` | **아무 글자 몇 개든** (0개 포함) |
| `_` | **아무 글자 정확히 한 개** |

그래서 운영자가 검색창에 `%` 하나만 쳐 넣으면:

```sql
LIKE '%%%'      -- 사실상 "아무거나" → 전체 매칭
```

**필터를 걸었는데 전부 다 나온다.** `_` 도 마찬가지로 "아무 한 글자"라 의도치 않게 많이 걸린다.

### 고친 방법

```kotlin
private fun escapeLikeWildcards(keyword: String): String =
    keyword
        .replace("\\", "\\\\")   // ① 역슬래시를 먼저!
        .replace("%", "\\%")
        .replace("_", "\\_")
```

그리고 쿼리에 **이스케이프 문자를 선언**한다:

```sql
LIKE CONCAT('%', :keyword, '%') ESCAPE '\\'
```

- **`ESCAPE '\'` 를 안 쓰면 `\%` 가 그냥 두 글자**로 취급된다. "무엇을 탈출 문자로 쓸지"를 SQL 에 알려줘야 한다.
- **역슬래시를 가장 먼저 바꾸는 게 핵심**이다. 순서를 바꿔서 `%` 를 먼저 `\%` 로 만들면, 그다음 역슬래시 치환이 그 `\` 까지 `\\` 로 바꿔 **`\\%` 가 되어 이스케이프가 풀린다.** 문자열 치환에서 **탈출 문자 자신을 먼저 처리**하는 건 고전 규칙이다.

### 진짜 배울 점 — 같은 레포 안의 비대칭

> [!warning] 파생 쿼리는 자동으로 막아주는데, native 쿼리만 구멍이었다
> - **Spring Data 파생 쿼리**(`findByDisplayNameContaining` 같은 메서드 이름 규약)는 **스프링이 값을 이스케이프해서** 넣어준다. 그래서 지금까지 이 문제가 안 보였다.
> - **native 쿼리**(`@Query(nativeQuery = true)`)는 **내가 쓴 SQL 이 그대로** 나간다. 스프링이 손대지 않으니 **이스케이프도 내 몫**이다.
>
> 즉 **"이 레포는 원래 안전했는데, native 로 내려가는 순간 그 안전망이 사라졌다."** [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭|216]]에서 `@SQLRestriction` 우회를 위해 native 를 도입했고, 그 대가가 여기서 청구된 셈이다.
>
> **프레임워크가 대신 해주던 일**은 **그 프레임워크 밖으로 나가는 순간 내가 해야 한다.** 그런데 대신 해주던 일은 **원래 안 보이니까** 빠뜨리기 쉽다.

> [!note] SQL 인젝션과는 다른 문제다
> 헷갈리기 쉬운데 **이건 인젝션이 아니다.** `:keyword` 는 **바인딩 파라미터**라 값이 SQL 문법으로 해석되지 않는다 — `'; DROP TABLE food; --` 를 넣어도 그냥 문자열로 검색될 뿐이다.
> 여기서 새는 건 **LIKE 패턴 문법**이다. 값은 안전하게 들어가지만, 그 값 **안의 `%`** 를 LIKE 가 와일드카드로 읽는다. **"인젝션은 막혔는데 패턴은 안 막혔다"** 가 정확한 표현이다.

**테스트가 Red→Green 으로 잡혔다** — `q=%` 하나로 전체가 매칭되는 시나리오를 먼저 실패시키고 고쳤다. → [[14. SDD와 TDD — 스펙과 테스트로 개발하기]]

## 4. ③ READY 직행 가드 — 서버에서 막는다

### 무엇이 문제였나

수정 API 는 `contentStatus` 를 **자유롭게** 받았다. 그래서 검수를 안 거친 음식도 **PUT 한 번으로 READY** 로 만들 수 있었다. READY 는 **앱에 노출되는 상태**라, 검수 절차 전체를 우회하는 길이 열려 있었던 셈이다.

### 고친 방법

```kotlin
if (command.contentStatus == FoodContentStatus.READY && !food.isReady()) {
    return AdminFoodUpdateResult.READY_NOT_ALLOWED   // → 400 FOOD-010
}
```

**전이 규칙을 표로 보면:**

| 지금 상태 | → READY 로 바꾸려 하면 | 왜 |
|---|---|---|
| **비 READY**(PENDING_REVIEW 등) | ❌ **400 FOOD-010** | 검수 승인 API 로만 가능 |
| **이미 READY** | ✅ 허용(멱등) | 상태가 안 바뀌니 우회가 아니다 |
| READY → **FAILED 등으로 내리기** | ✅ 허용 | **잘못된 콘텐츠를 급히 회수**하는 길은 열어둔다 |

> [!tip] "올리는 건 막고 내리는 건 연다"
> 보안·품질 게이트의 전형적인 모양이다. **위험한 방향(노출로 올리기)** 만 막고 **안전한 방향(노출에서 내리기)** 은 열어 둔다. 사고가 났을 때 급히 내릴 수단까지 막으면 **가드가 오히려 사고를 키운다.**

- **에러 코드 `FOOD-010` 을 새로 팠다** — "요청이 잘못됨"(COMMON-002)이 아니라 **"이 길로는 못 간다, 검수 승인 API 를 써라"** 를 알려주기 위해서다. [[PR 215 — 검수 비대상 거절에 전용 코드 FOOD-008 채번|215번]]의 그 원칙("전용 코드로 FE 가 분기할 수 있게")이 또 나온다.
- **`contentFailureKind` 는 여전히 수정 불가**다 — 검수 반려와 파이프라인만 쓴다. [[PR 218 — 표시 이름 편집·어드민 반려 유형·삭제 시 이름 반납|218]]에서 *"값을 추가할 때 쓰기 권한도 같이 정한다"* 고 했던 그 원칙이 유지된 것.

### 서버에서 막는 것과 화면에서 막는 것

Thymeleaf 수정 폼도 **같은 서비스를 공유**하므로 자동으로 같은 정책이 적용된다(페이지 컨트롤러에 분기 한 줄 추가).

> [!warning] 화면에서만 막으면 막은 게 아니다
> 드롭다운에서 READY 를 빼는 것으로도 "실수로 누르는 것"은 막힌다. 하지만 **API 는 화면을 거치지 않고도 부를 수 있다.** 서버에서 막아야 **진짜 막힌 것**이고, 화면 조치는 **안내**다.
> 이 PR 은 둘 다 했다 — **서버 가드(진짜 방어) + 폼 안내(친절)**. [[PR 209 — 어드민 벡터 아웃박스 조회·enqueue·재시도 REST|209]]·[[24. 주문 흐름 — 스캔 결과가 주문 이력이 되기까지|24번]]에서 본 **"검사는 안내용, 제약이 보증"** 과 같은 층 구조다.

## 5. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 5건을 물었고 판정이 났다(2026-09-03). **채택 3 · 보류 1 · 반려 1.**
> **1번이 이 시리즈에서 처음으로 "노트 리뷰가 실제 버그를 잡은" 사례**가 됐다 — 별도 티켓(KB-416)으로 발주됐다.

### ⭐✅ 1. `escapeLikeWildcards` 가 이 서비스에만 있다 — **같은 구멍이 두 곳 더 있었다**

[[PR 214 — 벡터 아웃박스 목록 검색 q 추가|214]]의 아웃박스 검색과 [[PR 217 — 멤버 목록·상세·활동 3종과 대시보드 메트릭 REST|217]]의 멤버 검색도 **같은 `LIKE '%…%'` native 쿼리**인데 이스케이프가 없다.

**→ 채택. 별도 티켓 `KB-416` 발주.** 조치 범위:
1. `escapeLikeWildcards` 를 **`common` 유틸로 승격**
2. **아웃박스·멤버 검색에 적용**
3. **네이티브 LIKE 전수 확인**을 DoD 에 포함

> [!tip] 왜 "한 곳 더 고치기"가 아니라 "공통화"가 근본 수정인가
> 원인이 **파생 쿼리 ↔ native 쿼리의 비대칭**(§3)이라, **native 를 새로 쓸 때마다 같은 실수가 재발**한다. 세 곳을 각각 고치면 **네 번째가 또 생긴다.**
> 유틸 하나로 모으면 ①이미 있는 곳은 그걸 부르면 되고 ②없는 곳을 **찾는 기준**이 생긴다("`LIKE` 를 native 로 쓰는데 이 유틸을 안 부르는 곳").
>
> **무증상 오작동끼리 묶인다** — 이 지적(`q=%` 로 전체 매칭)과 §2 의 관용구 뒤집기(`AND`/`OR` 문맥 혼동)는 **둘 다 에러 없이 조용히 틀린 결과**를 낸다. 그래서 **테스트로만 잡힌다.**

### ✅ 2. `/deleted` 엔드포인트 중복

`?deleted=true` 와 같은 결과인데 둘 다 산다.

**→ 채택([[PR 224 — LLM 비용 레포트 컨트롤러 합류 (임시 분리 청산)|224]] 교훈 적용).** **회수 조건을 명시**한다 — *"어드민이 `?deleted=true` 로 완전 이전한 뒤 제거"*. **에픽 종결 체크리스트**에 넣는다.

> 224 에서 배운 그대로다: **조건 없는 임시는 영구가 된다.** 이번엔 지적 즉시 조건이 붙었다.

### ⬜ 3. 정렬 옵션이 없다

**→ 지금은 안 만드는 게 맞다(YAGNI).** 요구가 오면 그때. **다만 그때의 설계 제약을 미리 적어둔다:**

> [!warning] 동적 정렬을 native 쿼리로 만들 때
> 정렬 컬럼을 **문자열로 조립**하면 **SQL 인젝션**이 된다 — 바인딩 파라미터는 **값**만 막아주지 `ORDER BY` 뒤의 **컬럼 이름**은 못 막는다.
> ```kotlin
> "ORDER BY $sortColumn DESC"   // ❌ sortColumn 이 사용자 입력이면 인젝션
> ```
> **정석은 허용 컬럼 화이트리스트** — 받은 값을 미리 정한 목록(`id`·`updated_at` …)과 대조해 **일치하는 것만** 쓴다. 목록에 없으면 기본값으로.
> §3 의 LIKE 문제가 "값은 안전한데 패턴이 샌 것"이었다면, 이건 **값이 아니라 SQL 구조 자체가 새는** 진짜 인젝션이다.

### ✅ 4. `deleted=true` + `status=READY` 조합의 의미

**→ 의미 있다.** 어드민이 **3필터를 나란히 노출**하도록 바꿨고, **"삭제됐지만 READY 였던 것"** 은 **복원 후보를 찾는 실제 질의**다. → [[PR 216 — 삭제 음식 조회·복원 REST와 벡터 큐 대칭]]

## 7. 다음에 이 PR 을 다시 볼 때

1. **선택 필터가 3개 이상이면 `(:p IS NULL OR 조건)`** — 분기 대신 쿼리 안에서 끄고 켠다. 단 `AND` 문맥이면 널일 때 **참**, `OR` 문맥이면 **거짓**이어야 한다.
2. **native 쿼리를 쓰면 이스케이프가 내 몫이 된다** — 파생 쿼리는 스프링이 해주던 일이다. **프레임워크 밖으로 나가면 그 안전망도 없어진다.**
3. **LIKE 와일드카드 문제는 SQL 인젝션이 아니다** — 값은 안전하게 들어가고, 그 안의 `%` 를 LIKE 가 패턴으로 읽는 것이다.
4. **가드는 위험한 방향만 막는다** — READY 로 올리기는 막고, READY 에서 내리기는 연다.
5. **리뷰 결과**(§5): **채택 3 · 보류 1 · 반려 1.** 1번이 **KB-416** 으로 발주됐다 — 같은 이스케이프 구멍이 아웃박스·멤버 검색에 **두 곳 더** 있었다.
6. 2026-09-03 기준 **OPEN** — 이후 변경은 [PR 223](https://github.com/team-skyjs/kbap-server/pull/223) 에서 확인.
