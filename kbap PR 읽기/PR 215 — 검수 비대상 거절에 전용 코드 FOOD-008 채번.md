## 0. 한 줄 요약

**`require(...)` 를 `throw BusinessException(FOOD-008)` 로 바꿨다.** 실질 코드 변경은 두 곳 네 줄인데, 그 결과 **FE 가 "이미 처리된 항목"을 다른 검증 실패와 구분**할 수 있게 된다.

## 1. 무엇이 문제였나

검수 큐 화면에서 관리자 A·B 가 같은 음식을 보고 있다. A 가 먼저 승인하면 그 음식은 `PENDING_REVIEW` 를 벗어난다.

> 여기 나오는 `contentStatus`(`PENDING_REVIEW`·`READY` …)는 **콘텐츠 생명주기**이고, 소프트 삭제 플래그인 `status`(`ACTIVE`/`DELETED`)와는 **다른 축**이다. 이름이 비슷해 섞이기 쉽다 → [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]] 이제 B 가 승인을 누르면:

```
이전: 400 COMMON-002 "요청이 올바르지 않습니다"
```

FE 입장에선 이 코드가 **`passed` 필드를 빼먹었을 때와 똑같다.** 그래서 "입력을 고치세요"라고 안내해야 할지 "이미 처리됐으니 목록을 새로고침하세요"라고 해야 할지 알 수 없다.

```
이후: 400 FOOD-008 "검수 대상(PENDING_REVIEW)이 아닙니다"
```

> [!note] 두 리뷰어가 독립적으로 같은 걸 지적했다
> PR 본문에 *"FE 세션·Codex 독립 지적 2회"* 라고 적혀 있다. **다른 관점에서 같은 결론이 나오면 그건 대개 진짜 문제**다. 한 명이 말하면 취향일 수 있지만 둘이 따로 말하면 설계 결함에 가깝다.

## 2. 실질 변경은 네 줄

```kotlin
// common/domain/food/model/Food.kt — 최종 형태 (커밋 ce7121da)
// 재승인(READY)은 이미 원하는 결과라 멱등 성공, 그 외 비대상은 운영자 실수 신호라 예외 — 의도된 비대칭.
fun approve(): Boolean {
    …
    requireReviewable()          // ← approve()·reject() 가 같은 가드를 공유
    …
}

private fun requireReviewable() {
    if (contentStatus != FoodContentStatus.PENDING_REVIEW) {
        log.warn("검수 대상 아님: foodId={}, contentStatus={}", id, contentStatus)   // ← 진단은 로그로
        throw BusinessException(ErrorCode.FOOD_NOT_REVIEWABLE)                       // ← 계약은 고정 메시지
    }
}

companion object { private val log = LoggerFactory.getLogger(Food::class.java) }
```

> **처음엔 이랬다** — `require(contentStatus == PENDING_REVIEW) { "…아닙니다: $contentStatus" }`. `require` 를 `throw BusinessException` 으로 바꾼 게 이 PR 의 출발이고, **가드 추출·WARN 로그·비대칭 주석은 리뷰를 거쳐 붙었다**(§6-1·6-2·6-3).

```kotlin
// common/core/error/ErrorCode.kt
+    FOOD_NOT_REVIEWABLE("FOOD-008", 400, "검수 대상(PENDING_REVIEW)이 아닙니다"),
```

### `require` 와 `throw BusinessException` 의 차이

| | `require(조건) { 메시지 }` | `throw BusinessException(코드)` |
|---|---|---|
| 던지는 것 | `IllegalArgumentException` (코틀린 표준) | 우리가 만든 예외 |
| 전역 핸들러가 매기는 코드 | **범용 `COMMON-002`** | **그 코드 그대로** |
| 뜻 | "프로그래머가 잘못 불렀다" | "**업무 규칙상 안 되는 상황이다**" |

- `require` 는 원래 **계약 위반(내부 버그)** 을 알리는 장치다. 그런데 여기 상황은 버그가 아니라 **정상적으로 일어날 수 있는 업무 상태**(남이 먼저 처리함)라 성격이 안 맞았다.
- 즉 이 PR 은 코드를 고쳤다기보다 **"이건 버그가 아니라 업무 규칙"이라고 분류를 바로잡은 것**이다.

## 3. 도메인 엔티티가 에러 코드를 알아도 되나?

`Food` 는 **도메인 모델**인데(→ [[8. 영속성 컨텍스트와 엔티티 매핑 — 엔티티가 곧 도메인 모델]]) 이제 `ErrorCode.FOOD_NOT_REVIEWABLE` 이라는 **API 계약의 어휘**를 참조한다. 교과서적 클린 아키텍처라면 "도메인이 바깥을 알면 안 된다"고 할 자리다.

**이 레포에선 괜찮다. 이유 셋:**

1. **선례가 있다** — `MemberProfile` 이 이미 같은 방식이다(`INVALID_NICKNAME`·`INVALID_COUNTRY_CODE` 등 4곳). 새 관행이 아니라 기존 관행을 따른 것.
2. **`ErrorCode` 는 커널에 있다** — `common.core.error` 는 도메인보다 **더 안쪽**인 공용 커널이고 **Spring·JPA 를 모른다**. 도메인이 커널을 참조하는 건 안→밖이 아니라 **안→더 안**이라 방향이 맞다. → [[13. 경계를 지키는 테스트 — ArchUnit이 강제하는 규칙들]]
3. **이 레포는 이미 순수성을 포기했다** — ADR-0014 로 **JPA 엔티티가 곧 도메인 모델**이 됐다. 하이버네이트 애너테이션을 달고 있는 클래스에 "프레임워크를 몰라야 한다"를 요구하는 건 앞뒤가 안 맞는다. → [[12. 포트와 어댑터 — 외부 시스템을 갈아끼우는 자리]]

> [!tip] 트레이드오프는 남는다
> 대가는 **도메인 로직을 다른 맥락(배치·다른 앱)에서 재사용할 때 HTTP 어휘가 따라온다**는 것이다. 지금은 호출처가 검수 서비스 하나뿐이라 비용이 0에 가깝다. **"지금 값이 싸니까 한다"는 판단**이지 "원래 맞다"가 아니다.

## 4. 눈여겨볼 것 — 문서가 코드에서 자동으로 나온다

이 PR 이 건드린 파일 중 **`OpenApiSnapshotTest.kt`** 가 있다.

```kotlin
then("에러 코드 표에 검수 대상 아님(FOOD-008)이 실린다") {
    val reviewDesc = docOf("/v3/api-docs/1.0")
        .path("paths").path("/api/admin/foods/content-reviews/{foodId}").path("post")
        .path("description").asText()
    reviewDesc.contains("FOOD-008").shouldBeTrue()
}
```

그리고 API 인터페이스에는 이런 애너테이션이 붙는다:

```kotlin
-    @ApiErrors(ErrorCode.FOOD_NOT_FOUND)
+    @ApiErrors(ErrorCode.FOOD_NOT_FOUND, ErrorCode.FOOD_NOT_REVIEWABLE)
```

- **`@ApiErrors` 는 이 레포가 직접 만든 애너테이션**이다(`api/core/config/ApiErrors.kt`, 16곳 사용). 여기 적은 `ErrorCode` 들이 **Swagger 설명의 "발생 가능한 에러 코드" 표로 자동 생성**된다.
- **`OpenApiSnapshotTest` 는 그 생성 결과를 검사한다** — 즉 **"문서에 이 코드가 실려 있는가"를 테스트가 강제**한다.
- 이게 왜 좋은가: 앞서 [[PR 201 — 어드민 음식 상세·수정·재수집·삭제 REST|PR 201]] 에서 **PR 본문이 코드보다 낡았던 사고**가 있었다. 사람이 쓰는 문서는 낡지만, **코드에서 생성되고 테스트가 지키는 문서는 낡을 수 없다.** 이 레포가 그 방향으로 가고 있다는 신호다.

## 5. 계약 변경이라 FE 에 알려야 한다

PR 본문에 **"계약 변경 (FE 전달)"** 절이 따로 있다:

> 검수 결과 적용의 "승인 대상 아님"이 **400 COMMON-002 → 400 FOOD-008** 로 변경(HTTP 상태 유지). COMMON-002 는 이제 요청 자체 검증 실패(passed 누락 등)만 의미.

- **HTTP 상태(400)는 그대로**라 `status` 로만 분기하던 FE 는 안 깨진다.
- 하지만 **`code` 로 분기하던 FE 는 영향**을 받는다 — [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 의 "클라이언트는 message 가 아니라 code 로 분기한다" 규약 때문에, **code 를 바꾸는 건 계약 변경**이다.
- 그래서 PR 이 **FE 가 할 일까지 지정**했다: *"FE 는 FOOD-008 을 '이미 처리된 stale 항목 — 큐에서 제거·새로고침' 분기로 사용."*

> 서버만 고치고 끝나는 변경이 아니라는 걸 PR 이 스스로 표시한 것 — 작은 PR 이지만 **협업 관점에선 모범**이다.

## 6. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 4개를 물었고 판정이 났다(2026-09-01, 커맨드 센터 경유). **반영 2 · 반려 2.**
> 반려 2건이 특히 읽을 만하다 — **"안 고치는 게 맞는 이유"** 가 둘 다 명확하다.

### ✅ 1. `require` 의 상태값이 응답에서 사라졌다

옛 코드는 `"…아닙니다: $contentStatus"` 로 **실제 상태값**을 담았는데, `ErrorCode` 메시지는 고정 문구라 **어떤 상태였는지가 사라진다.**

**→ 반영 완료**(`ce7121da`). 다만 **응답 메시지는 고정 그대로 둔다** — 전역 예외 핸들러가 `ErrorCode` 의 메시지를 그대로 내보내는 설계라, 상태값을 넣으려면 예외에 동적 메시지를 싣는 구조 변경이 필요하다. 대신 **`throw` 직전에 WARN 로그로 `foodId`·`contentStatus` 를 남긴다.**

> **응답과 로그의 역할을 가른 것**이 핵심이다. 응답은 **FE 가 분기할 안정적 계약**이라 고정이 낫고(→ [[7. API 계약의 모양 — 공통 봉투·에러 코드·헤더 버저닝]] 의 "message 가 아니라 code 로 분기"), 진단 정보는 **운영자가 보는 로그**로 간다. 둘을 한 곳에 욱여넣지 않는다.

### ✅ 2. `approve()` 와 `reject()` 의 가드 복붙

**→ 반영 완료**(`ce7121da`). `private fun requireReviewable()` 로 추출됐다. 1번의 WARN 로그도 이 함수 안에 들어가므로 **두 지적이 한 수정으로 묶인다** — 로그를 두 곳에 복붙하지 않아도 된다.

### ⬜ 3. READY 재승인은 멱등, 비대상은 예외 — 비대칭이 의도인가?

이미 승인된 것을 또 승인하면 `false` 반환(조용히 통과), 검수 대상이 **아예 아니면** 예외. 같은 "아무것도 안 함"인데 표현이 다르다.

**→ 반려. 의도 확정.** 둘은 **다른 상황**이다:

| | READY 재승인 | 비대상(예: PENDING_IMAGE) 승인 |
|---|---|---|
| 무슨 일인가 | **원하는 결과가 이미 달성됨** | **운영자가 잘못된 대상을 눌렀다** |
| 그래서 | 무해 — 조용히 `false` (멱등) | **실수 신호** — 알려줘야 한다 (예외) |

멱등은 "같은 요청을 반복해도 안전하다"는 뜻이지 **"모든 실패를 삼킨다"는 뜻이 아니다.** 재승인은 전자, 비대상은 후자라 갈리는 게 맞다. → 다만 **코드만 봐선 이 구분이 안 보이므로 주석으로 명시**했다(`ce7121da`): *"재승인(READY)은 이미 원하는 결과라 멱등 성공, 그 외 비대상은 운영자 실수 신호라 예외 — 의도된 비대칭."*

### ⬜ 4. FOOD- 코드가 계속 쌓인다 — 별도 코드표가 필요하지 않나?

이 시리즈에서만 005·006·007·008 넷이 늘었다.

**→ 반려. 현행 유지.** **Swagger 의 에러 표가 이미 정본**이고, 이 PR 이 추가한 `OpenApiSnapshotTest` 가 그 표를 **테스트로 검증**한다(§4). 손으로 관리하는 별도 표를 만들면 **그게 드리프트의 원천**이 된다 — 코드는 바뀌는데 표만 안 바뀌는 상황.

> [[PR 201 — 어드민 음식 상세·수정·재수집·삭제 REST|PR 201]] 에서 **PR 본문이 코드보다 낡았던 사고**가 정확히 그 사례다. **문서를 늘리지 않고 생성·검증되게 만드는 쪽**이 이 레포의 방향이다.
