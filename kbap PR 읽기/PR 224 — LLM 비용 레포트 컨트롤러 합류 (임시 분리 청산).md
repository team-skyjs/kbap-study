## 1. 왜 갈라져 있었나 — 되짚기

[[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|PR 219]] 를 만들 때 [[PR 217 — 멤버 목록·상세·활동 3종과 대시보드 메트릭 REST|PR 217]] 이 **아직 머지 전**이었다. 둘 다 대시보드를 건드리는데 같은 파일을 고치면 **머지 충돌**이 난다.

그래서 219 는 **의도적으로 다른 클래스를 팠다**:

```kotlin
// TODO: #217 머지 후 AdminDashboardController(/api/admin/dashboard)로 합류
//       — 충돌 회피용 임시 분리, 후속 이슈로 추적.
@RestController
@RequestMapping(ApiPaths.ADMIN + "/dashboard/llm-costs", version = "1.0+")
class AdminLlmReportController(…)
```

**URL 은 처음부터 `/dashboard/llm-costs` 로 맞춰 뒀다** — 즉 **밖에서 보이는 계약은 최종형이고, 안쪽 클래스만 임시**였다. 그래서 나중에 합쳐도 FE 는 아무것도 모른다.

> [!tip] 이게 임시 조치의 모범이다
> 219 리뷰([[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|§5-4]])에서 **"임시 분리에 만료일을 붙여라"** 는 지적이 나왔고, 그 답이 ①**TODO 주석에 조건 명시**("#217 머지 후") ②**PR 본문에 계획 기재** ③**후속 이슈 등록**이었다. 그리고 이 PR 이 그 셋을 실제로 회수한다.
>
> **임시 조치가 영구가 되는 건 "임시"라고 적지 않아서**가 아니라 **회수 조건과 담당을 안 정해서**다. 여기선 조건(217 머지)이 명확했고, 그게 충족되자 실행됐다.

## 3. 메커니즘 — URL 은 같은데 조립이 다르다

이 PR 에서 유일하게 "코드를 읽는" 재미가 있는 부분이다.

```kotlin
// 전 — 클래스가 전체 경로를 갖고, 메서드는 비어 있다
@RequestMapping(ApiPaths.ADMIN + "/dashboard/llm-costs")
class AdminLlmReportController {
    @GetMapping                                     // ← 경로 없음
    override fun getLlmCostReport(…)
}

// 후 — 클래스는 공통 접두사만, 메서드가 나머지를 갖는다
@RequestMapping(ApiPaths.ADMIN + "/dashboard")      // ← AdminDashboardController
class AdminDashboardController {
    @GetMapping("/llm-costs")                       // ← 여기로 옮겨왔다
    override fun getLlmCostReport(…)
}
```

**최종 URL 은 `/api/admin/dashboard/llm-costs` 로 완전히 동일하다.** 스프링은 **클래스 레벨 경로 + 메서드 레벨 경로**를 이어 붙일 뿐이라, **어디서 끊어 적든 결과가 같다.**

- **왜 이제 메서드 쪽으로 옮겼나** — 합류한 클래스에는 이미 `/metrics` 가 있다. 클래스가 `/dashboard` 라는 **공통 접두사**를 갖고 각 메서드가 자기 뒷부분을 갖는 게 **자연스러운 모양**이다.

```
AdminDashboardController  @RequestMapping("/api/admin/dashboard")
 ├─ @GetMapping("/metrics")     → /api/admin/dashboard/metrics
 └─ @GetMapping("/llm-costs")   → /api/admin/dashboard/llm-costs   ← 합류
```

**의존성도 한 줄 늘었을 뿐이다:**

```kotlin
class AdminDashboardController(
    private val adminDashboardMetricsService: …,
    private val adminLlmReportService: AdminLlmReportService,   // ← 추가
)
```

생성자 주입이라 **스프링이 알아서 두 서비스를 꽂는다.** 컨트롤러가 서비스를 **직접 만들지 않기 때문에** 이런 이사가 싸다. → [[4. IoC 컨테이너와 의존성 주입 — 부품을 직접 만들지 않는다]]

### `@Min`/`@Max` 가 인터페이스에 그대로 따라왔다

```kotlin
// AdminDashboardApi.kt 로 이동한 부분
@Min(1, message = "days 는 1 이상이어야 합니다")
@Max(30, message = "days 는 30 이하여야 합니다")
days: Int,
```

이건 [[PR 219 — 콘텐츠 아웃박스·이미지 배치·LLM 비용 레포트 REST|219]] 리뷰 1번(*"`require` 대신 검증 계층으로"*)의 반영분이다. **이사하면서 잃어버리지 않고 같이 옮겼다** — 리팩터링에서 흔히 새는 게 이런 애너테이션인데 지켜졌다.

## 4. 테스트를 안 고쳤다는 게 증거다

PR 본문의 한 줄이 이 PR 의 핵심 검증이다:

> 기존 `AdminLlmReportControllerTest`(4)·`AdminDashboardControllerTest`(2) **무수정 그린** = 계약 무변 검증

- 테스트가 **HTTP 요청/응답 수준**에서 쓰여 있으니(MockMvc), **어느 클래스가 처리하든 상관없다.** 클래스 이름을 알고 있었다면 이사할 때마다 테스트도 고쳐야 했을 것이다.
- **테스트 파일 이름은 여전히 `AdminLlmReportControllerTest`** 인데 그 컨트롤러는 이제 없다 — 이름만 남았다(§5-2).

> [!tip] 좋은 테스트는 "무엇을 하는가"를 검증하고 "어떻게 짜였는가"는 모른다
> 이 PR 이 **테스트 수정 0** 으로 끝난 건 우연이 아니라 **테스트가 계약(URL·응답)에 붙어 있고 구현(클래스 구조)에는 안 붙어 있어서**다. 만약 테스트가 컨트롤러 클래스를 직접 인스턴스화했다면 이 리팩터는 테스트까지 고쳐야 했고, 그러면 **"계약이 안 바뀌었다"를 증명할 수단이 사라진다.** → [[14. SDD와 TDD — 스펙과 테스트로 개발하기]]

## 5. 읽으며 눈에 띈 것 — 그리고 리뷰 결과

> 5건을 물었고 판정이 났다(2026-09-03, 커맨드 센터 경유). **반려 1 · 후속 정리 2 · 채택 1 · 칭찬 1.**
> **1번의 답이 이 PR 전체를 한 줄로 설명한다** — 그래서 아래에서 가장 길게 다룬다.

### ⬜ 1. `AdminLlmReportService` 는 왜 안 합쳤나 — **안 합친 게 설계 정답이다**

컨트롤러는 합쳤는데 서비스는 `AdminDashboardMetricsService`·`AdminLlmReportService` 둘로 남는다. 일관성이 없어 보였다.

**→ 반려. 일관성이 없는 게 아니라 축이 두 개다.**

> ### 컨트롤러는 **URL 축**, 서비스는 **도메인 축**

- **컨트롤러를 합친 근거는 "HTTP 표면의 공통 접두사"**(`/dashboard`)다 — 도메인이 같아서가 아니다.
- **서비스는 관심사가 다르다** — 대시보드 **메트릭 집계** vs LLM **비용 리포트**. 접두사가 같다는 이유로 합치면 **무관한 로직이 한 클래스에 모이는 god service** 가 된다.

| | 무엇을 기준으로 묶나 | 이 PR 에서 |
|---|---|---|
| **컨트롤러** | **URL** — 같은 접두사를 쓰면 한 클래스 | ✅ 합친다 |
| **서비스** | **도메인** — 관심사가 같아야 한 클래스 | ❌ 안 합친다 |

**컨트롤러 하나가 서비스 둘을 주입받는 모양은 정상**이다. 오히려 그게 [[5. kbap의 계층 — 컨트롤러에서 리포지토리까지|계층 노트]]가 말한 **"컨트롤러는 번역기"** 의 자연스러운 귀결이다 — 번역기는 여러 출처의 결과를 HTTP 로 옮기는 자리이지, 로직을 소유하는 자리가 아니다.

> **다음 사람의 의문은 컨트롤러 KDoc 한 줄이면 해소된다** — 별도 작업으로 잡을 것 없이, 그 파일을 다음에 만질 때 동승시키기로 했다.

### ✅ 2. 테스트 파일 이름이 낡았다 → **후속 정리**

`AdminLlmReportControllerTest` 인데 그 컨트롤러는 삭제됐다.

**→ 지적 유효. 단 이번 PR 에서 안 고친 판단도 옳다** — **무수정 그린이 계약 무변의 증거**였으므로(§4), 이번에 건드리면 그 증거가 사라진다. **후속 정리 대상**으로 확정하되 **단독 PR 은 과하니 다음 어드민 서버 PR 에 동승**한다.

### ✅ 3. DTO 가 서비스 파일에 얹혀 있다 → **후속 정리 (2번과 묶음)**

레포 관례는 `*Response.kt` 분리인데(`AdminContentOutboxResponse.kt` 등) 여기만 다르다.

**→ 컨벤션 이탈 맞다.** 컨트롤러가 이사한 지금은 **더 어색해졌다.** 2번과 **한 커밋으로 묶어** 정리한다(둘 다 순수 이름·배치 정리).

> [!note] 📌 후속 정리 항목 (2·3번 — 다음 어드민 PR 에 동승)
> - `AdminLlmReportControllerTest` → 이름 정리(`AdminDashboardControllerTest` 합류 또는 `AdminDashboardLlmCostTest`)
> - `AdminLlmCostReportResponse` 등 DTO → `AdminLlmReportResponse.kt` 로 분리(레포 관례 복귀)
> - `AdminDashboardController` 에 **"컨트롤러=URL 축, 서비스=도메인 축"** KDoc 한 줄(§5-1)

### ✅ 4. 남은 청산 대상 TODO 를 목록화하자 — **가장 값진 지적으로 채택**

219 처럼 충돌 회피용 임시 구조를 만든 자리가 더 있다면 같은 방식으로 회수 대상이다.

**→ 채택. BE 세션에 읽기 전용 TODO 스윕을 발주**했다(충돌 회피·임시 분리 흔적 전수). 결과는 **에픽을 닫을 때 체크리스트**로 쓰고, **회수 조건이 이미 충족된 게 있으면 즉시 정리 발주**한다.

> [!tip] 왜 이게 가장 값진 지적이었나
> 224 는 **"기억하고 있던 하나"** 를 갚은 것이다. 그런데 **기억하지 못한 것들**은 그대로 남는다. 임시 조치는 **만든 사람만 알고 있을 때 영구가 된다** — 목록으로 만드는 순간 **팀의 것**이 되고, 에픽 종료 조건에 들어간다.
> 이 시리즈가 계속 확인한 원칙과 같다: **판단은 코드에 안 남으니 어딘가에 적어야 한다.**

## 7. 다음에 이 PR 을 다시 볼 때

1. **기능 변화 0, 클래스만 이동.** URL·응답·서비스·DTO 전부 그대로다.
2. **URL 은 클래스 경로 + 메서드 경로의 합**이라, 어디서 끊어 적든 결과가 같다. 합류하면서 **끊는 지점만 옮겼다.**
3. **테스트 무수정 그린이 곧 증명**이다 — 테스트가 구현이 아니라 계약에 붙어 있어서 가능했다.
4. **임시 조치가 영구가 되는 건 "임시"라고 안 적어서가 아니라 회수 조건을 안 정해서다.** 219 는 조건(217 머지)·기록(TODO·PR 본문·이슈)을 남겼고, 224 가 그걸 회수했다.
