# OCR 메뉴 스캔 — 박스 그룹핑 (방사형 최근접)

> 맥락: kbap-fe `src/lib/scan/segmentMenu.ts`. OCR이 준 라인별 박스를, 요리명마다 가장 가까운 가격·영문 라인을 붙이는 방식.
> 목표: **지금 쓰는 알고리즘의 원리 + 왜 되는지 + 한계 + 더 나은 알고리즘**을 코드 수준까지 이해.
> (시드 노트를 리서치로 검증·확장한 완성본.)

---

## 0. 한 줄 요약
OCR이 뱉은 **라인별 박스**를, **각 요리명 박스에서 가장 가까운 가격/영문 박스**를 중심거리(유클리드)로 붙여 하나의 메뉴 항목으로 묶는다. **이게 "association(연관) 문제"** 이고, 지금 구현은 그중 제일 단순한 **"독립 최근접(nearest-neighbor)"**. 레이아웃(그리드/리스트) 방향과 무관하게 대체로 맞지만, **전역 최적이 아니라** 밀집·개수불일치에서 오배치가 난다 → 업그레이드는 **헝가리안(전역 최적 매칭)** 또는 **열 클러스터링 후 매칭**.

---

## 1. 문제 정의 — 이건 "OCR 후처리 · 연관(association)" 문제다

OCR은 글자를 읽어줄 뿐, **"이 가격이 이 요리 것"** 이라는 관계는 안 준다. 그 관계를 좌표(박스 위치)로 복원하는 게 이 단계.

- **입력**: OCR 라인들. 각 라인 = `{ text, box }`, box = 정규화 `{x, y, width, height}` (0~1).
- **분류**(`classifyLine.ts`): 각 라인을 `dishName / price / origin / latin(영문) …` 로 태깅.
- **출력**: 요리마다 `{ itemId, rawMenuName, box, price, latin }`. `price`/`latin`은 "가장 가까운" 라인.

> [!note] 문서 레이아웃 분석(DLA)의 한 조각
> 이 작업은 학술적으로 **Document Layout Analysis**의 후반부 — "요소를 논리적 그룹으로 묶기"에 해당. 전통 기법엔 projection profile, XY-cut, Voronoi, 거리기반 그룹핑 등이 있고, 지금 코드는 그중 **거리기반 그룹핑**의 최소 버전이다.

---

## 2. 지금 알고리즘 — 독립 최근접 (Nearest-Neighbor)

### 2-1. 절차
1. 라인을 타입별로 나눔: 요리명 풀 / 가격 풀 / 영문 풀.
2. **각 요리명 박스마다**, 가격 풀·영문 풀에서 **중심 간 유클리드 거리 최소**인 라인을 하나씩 붙임.
3. 요리명은 `itemId`(0..n)를 받아 BE 매칭 키로 씀.

```ts
center(b) = (b.x + b.width/2, b.y + b.height/2)
dist(a, b) = Math.hypot(Δcx, Δcy)              // √(Δcx² + Δcy²)
nearest(dish, pool) = argmin_{line ∈ pool} dist(dish.box, line.box)
```

### 2-2. 복잡도
요리 D개 · 가격 P개면 **O(D·P)** (각 요리가 모든 가격을 훑음). 메뉴판 규모(수십 라인)에선 무시할 수준.

### 2-3. ⚠️ 중요한 성격 — "1:1 매칭"이 아니라 "복원(replacement) 허용"
각 요리가 **독립적으로** 최근접을 고르므로:
- **같은 가격이 여러 요리에 중복** 배정될 수 있다 (배타성 없음).
- **어떤 가격은 아무에게도** 안 붙을 수 있다.
→ 시드가 "여러 요리가 한 가격에 몰린다"고 한 게 이 성질. 엄밀히는 **매칭(matching)이 아니라 독립 argmin**이다. 이 구분이 뒤(한계·대안)의 핵심.

---

## 3. 왜 이 단순한 게 두 레이아웃 다 되나 (원리)

`★ 기하 직관 ─────────────────────────────`
유클리드 거리는 **등방성(isotropic)** — 방향을 안 가린다.
- **그리드형**(가격이 이름 *아래*): 자기 가격이 세로로 제일 가까움.
- **리스트형**(가격이 이름 *오른쪽*): 자기 가격이 가로로 제일 가까움.
둘 다 "이름 중심에 최단 거리인 가격 = 자기 가격"이 성립 → **방향 분기 없이** 하나로 커버.
`──────────────────────────────────────`

이게 규칙 기반(if 그리드 then 아래, if 리스트 then 오른쪽)보다 **견고한** 이유: 레이아웃을 먼저 판별할 필요가 없다. "가까운 게 내 것"이라는 물리적 사실만 쓴다.

---

## 4. 한계 — 왜 전역 최적이 아닌가 (탐욕의 함정)

독립 최근접은 **각자 국소 최적**만 본다. 전체를 같이 보면 더 나은 배치가 있는데 놓친다.

### 4-1. 개수 불일치 · OCR 누락
요리의 **자기 가격이 OCR에서 빠지면**, 그 요리는 **옆 요리의 가격**을 최근접으로 잡아 오배치. (독립 argmin이라 "내 것이 없다"를 모름.)

### 4-2. 밀집 메뉴판 · 세로 정렬 가정 붕괴
줄 간격이 좁으면 중심거리가 애매해져, 아래/위 줄 가격이 뒤바뀜.

### 4-3. 전역 최적을 놓치는 구체 예 (탐욕 vs 최적)
요리 D1·D2, 가격 P1·P2. 거리표:

| | P1 | P2 |
|---|---|---|
| **D1** | 1.0 | 2.0 |
| **D2** | 1.1 | 3.0 |

- 만약 **배타적 탐욕**(먼저 온 요리가 가격 선점): D1→P1(1.0), 그럼 D2는 P2(3.0)만 남음 → 합 **4.0**.
- **전역 최적**: D1→P2(2.0) + D2→P1(1.1) → 합 **3.1**. ✅ 더 좋음.
- 현재 코드(복원 허용): D1→P1(1.0), D2→P1(1.1) → **둘 다 P1** (P2 미사용). 개수 안 맞으면 이렇게 뭉친다.

→ **각자 최선 ≠ 전체 최선.** 이게 "전역 최적이 아니다"의 정확한 의미.

---

## 5. 더 나은 알고리즘 (업그레이드 경로)

### 5-1. 헝가리안 알고리즘 (전역 최적 1:1 매칭) — 정공법
"요리↔가격을 **하나씩 짝지어 총 거리 합 최소**"는 고전적인 **할당 문제(Assignment Problem)**. **헝가리안(=Kuhn–Munkres) 알고리즘**이 **전역 최적**을 **O(n³)** 에 보장.

- **원리**: 요리(행)·가격(열)의 거리 행렬을 만들고, 행/열에서 최소값을 빼(reduce) 0을 만든 뒤, 0들만으로 완전매칭을 찾는 선형계획의 조합적 해법.
- **탐욕과 차이**: 탐욕은 "지금 제일 가까운 것"을 확정해 되돌리지 않음 → 국소최적. 헝가리안은 **전체 합**을 최소화해 4-3 같은 함정을 피함.
- **비용**: 메뉴 수십 개면 n³도 순식간. FE에서 충분히 돌릴 만함.

> [!tip] 배타성이 필요할 때만
> 헝가리안은 **1:1 배타**를 강제한다(한 가격 → 한 요리). 메뉴판은 보통 요리 1 : 가격 1이라 잘 맞음. 단 **개수가 다르면**(가격 누락/중복) 정사각이 아니라 **직사각 할당** 또는 **더미(dummy) 노드 + 게이팅 임계거리**로 "짝 없음"을 허용해야 함.

### 5-2. 불균형/누락 대응 — 게이팅 + 더미
- **거리 임계값(gating)**: 최근접이라도 거리가 임계 초과면 **안 붙임**(=가격 없음). OCR 누락 오배치를 막는 실전 필수 장치.
- **더미 열/행**: 할당 행렬에 "미할당" 가상 노드를 넣어 남는 요리를 흡수.

### 5-3. 열(column) 클러스터링 후 매칭 — 구조를 먼저 복원
밀집·다단(multi-column) 메뉴에서 강함.
1. 모든 박스의 **x-중심으로 1D 클러스터링**(간격 기반 / k-means / DBSCAN) → "열" 복원.
2. **같은 열 안에서만** 세로 근접으로 가격을 붙임 → 옆 열 침범 원천 차단.
- DBSCAN은 열 개수를 미리 안 정해도 되고 이상치(outlier)를 자연히 배제 → 메뉴판처럼 열 수가 가변일 때 적합.

### 5-4. 비등방(anisotropic) 거리 — 거리 함수 자체를 튜닝
메뉴는 열 구조라 **가로 이탈에 더 큰 벌점**을 주면 옆 열 오염이 준다:
```
dist²= (wx·Δcx)² + (wy·Δcy)²,   보통 wx > wy (가로로 멀어지면 크게 페널티)
```
- 리스트형(가격이 오른쪽)이면 반대로 튜닝. 즉 **레이아웃 사전지식을 거리에 주입**.
- 유클리드(등방) → 이 가중 버전으로 바꾸는 것만으로 큰 개선이 나기도.

### 5-5. 안정 매칭(Gale–Shapley)은 왜 안 쓰나
"서로의 선호 순위가 안정적"을 보장하지만, 우리가 원하는 건 **총 거리 합 최소(=최적)** 라 목적함수가 다름. 여기선 헝가리안이 맞다. (참고용 구분.)

## 6. 그래서 이 코드엔 뭘? (실용 판단)

> [!important] 안전과 기하가 분리돼 있다는 게 핵심
> 위험도(안전 판정)는 **요리 이름 자체**에 바인딩됨. 가격/영문이 잘못 붙어도 **안전 판정엔 무해** — 오버레이 표시 편의일 뿐. 원산지(origin)는 요리에 안 붙이고 표시용으로만 모음(BE 전송 X).

→ 결론: **지금은 독립 최근접으로 충분**할 가능성이 큼(오배치의 피해가 "표시가 살짝 어긋남" 수준). 다만 사용자 신뢰(잘못된 가격 노출)가 중요해지면 **순서대로** 올리면 된다:
1. **거리 게이팅**(5-2) — 제일 싸고 효과 큼(엉뚱한 가격 안 붙임).
2. **비등방 거리**(5-4) — 코드 몇 줄, 옆 열 오염 감소.
3. **헝가리안**(5-1) — 개수 맞을 때 전역 최적.
4. **열 클러스터링**(5-3) — 다단·밀집까지 견고.

> **별개 이슈 → 노트로 확장됨 (2026-07-09)**: "요리인지 아닌지" 판별(`classifyLine`)이 실기기에서 실제로 무너졌다(요리 전멸 미검출 + 탭 텍스트 SAFE 오탐, KB-72). 원인·원리·해법(BE 카탈로그 퍼지 매칭 확정 방향)은 [[OCR 라인 분류 — 휴리스틱의 한계와 대안]] 참고. 그룹핑(이 노트)과는 **별개 단계**지만 파이프라인상 바로 앞 공정이다: 분류 → 그룹핑.

## 7. 용어집
- **연관/association 문제**: 검출된 요소들 사이의 "누가 누구 것"을 좌표로 복원하는 문제.
- **최근접(Nearest-Neighbor)**: 각 대상에서 가장 가까운 후보를 고르는 것. 여기선 배타성 없는 독립 argmin.
- **탐욕(greedy)**: 매 순간 국소 최적을 확정하고 안 되돌림 → 전역 최적 보장 안 됨.
- **할당 문제(Assignment Problem)**: 1:1로 짝지어 총비용 최소화하는 고전 최적화.
- **헝가리안 / Kuhn–Munkres**: 할당 문제를 O(n³)에 **전역 최적**으로 푸는 알고리즘.
- **게이팅(gating)**: 임계 거리 초과면 매칭 안 함(짝 없음 허용).
- **비등방(anisotropic) 거리**: 축마다 가중치가 다른 거리. 열 구조 반영에 씀.
- **DBSCAN**: 밀도 기반 클러스터링. 군집 수 미지정 + 이상치 배제.
- **등방성(isotropic)**: 방향을 안 가리는 성질(유클리드 거리).
- **projection profile / XY-cut**: 문서 레이아웃 분석의 고전적 분할 기법.

## 8. 다음에 빠른 재현 체크리스트
1. 이건 **OCR 후처리 연관 문제** — "가까운 게 내 것" 최근접으로 요리에 가격/영문을 붙임.
2. 지금 구현 = **독립 최근접(복원 허용)**. 방향 무관해서 그리드·리스트 다 됨.
3. 함정: **각자 최적 ≠ 전체 최적**. 개수 불일치·OCR 누락·밀집에서 오배치.
4. 안전은 **요리 이름**에 바인딩 → 가격 오배치는 표시 문제일 뿐(피해 작음).
5. 업그레이드 순서: **게이팅 → 비등방 거리 → 헝가리안 → 열 클러스터링**.

> ③ **가장 큰 변화 — 서버가 사진을 다시 읽는다.** 이 노트는 "FE 가 묶은 후보를 BE 가 검증한다"는 그림이었지만, 지금 서버는 같은 사진을 **비전 LLM 에 다시 던져** 메뉴명·가격을 스스로 뽑는다. FE 가 보낸 `items` 는 **힌트**로만 쓰이고(`specs/kb-320-scan-vision-ocr-ignore/`), **응답의 기준은 비전이 추출한 메뉴**다. 그래서 요청 17개에 응답 12개가 정상이고, **배열 순서가 아니라 `idx` 로 짝을 맞춰야 한다.** 서버는 비전이 돌려준 `matchedIdx` 를 ⓐ요청에 실제로 있던 값인가 ⓑ아직 안 쓴 값인가로 두 번 걸러, 걸리면 `idx = null` 로 내려보낸다 — **그릴 박스가 없는 항목**이니 오버레이가 아니라 리스트로만 표시하면 된다.
> → 그래서 §4 가 지적한 오배치(개수 불일치·밀집)의 **안전 영향은 더 작아졌다.** 위험도는 애초에 요리 이름에 바인딩돼 있었는데(§6), 이제 그 이름조차 FE 그룹핑이 아니라 서버 비전이 만든다. 가격 오배치는 여전히 "표시가 어긋남" 수준이다.
> **v2 에서는 이 노트의 공정 전체가 서버로 넘어간다** — 앱이 `items` 를 아예 보내지 않고 사진만 올린다 → [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]]. 즉 이 노트는 **v1 경로의 기록**이 되어 가는 중이다.
