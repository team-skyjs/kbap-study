# OCR 라인 분류 — 휴리스틱의 한계와 대안

> 맥락: K-Bap 실기기 테스트에서 김치찌개·된장찌개가 **전부 미검출**되고, 브라우저 탭 텍스트("1스프린트")가 요리로 오탐돼 **SAFE 판정**까지 받은 실사고(KB-72). `classifyLine.ts`의 정규식 분류기가 무너진 이유와 해법.
> 목표: "규칙 기반 분류기는 왜, 언제 무너지는가"를 원리로 이해하고, 매칭 기반 대안과 방어 장치까지.

---

## 0. 한 줄 요약
정규식 분류기는 **작성 당시 샘플의 암묵적 가정(분포)** 위에 서 있다 — ML Kit이 "한글 요리명+로마자"를 한 줄로 병합하자(분포 변화) 길이 규칙이 실제 요리를 전부 버렸다. 임시 패치는 **판정 대상을 한글부로 축소**(적용 완료), 근본 해결은 **"카탈로그 매칭 = 최고의 분류기"** — 표면 특징(길이·구분자) 대신 의미 특징(사전에 있는가)으로 옮기는 것.

---

## 1. 사고 재구성 (실기기 OCR 라인 → 판정)

문제 당시의 rule 5 (설명문 판정):
```ts
// 길이 ≥12자 또는 구분자(공백·쉼표··) ≥3개 → description으로 버림
if (hasHangul && (t.length >= 12 || breaks >= 3)) return 'description';
```

| OCR 라인 | 판정 | 결과 |
|---|---|---|
| `"된장찌개 Doeniang fioe"` | 20자 ≥12 → description | ❌ 요리인데 버려짐 |
| `"· 김치찌가개 d"` | 구분자 3 ≥3 → description | ❌ (OCR 오타 "찌**가**개"까지) |
| `"· 닭볶음탕 Dak Bokkeumtang 2인 이상"` | ≥12자 → description | ❌ |
| `"· 순두부찌개"` | 8자·구분자 2 → dishName | ✅ 유일한 생존자 |
| `"1스프린트"` (브라우저 탭!) | 짧은 한글 → dishName | ❌ 오탐 → mock BE **SAFE 판정** |

> [!warning] 마지막 줄이 진짜 사고다
> 알레르기 안전 앱에서 "요리가 아닌 것에 SAFE"는 **false-safe** — 미탐(요리 놓침)보다 훨씬 비싼 실패. §3에서 이 비대칭을 다룬다.

## 2. 왜 무너졌나 — 두 가지 원리

### 2-1. 규칙은 "작성된 샘플의 분포"에 과적합돼 있다
규칙 기반 분류기도 학습을 한다 — 단지 **사람 머릿속에서**. "설명문은 길다(≥12자)"는 규칙은 *한글만 있는 메뉴판* 샘플에서 관찰된 사실이다. 그런데 [ML Kit의 Line은 "같은 축 위 연속된 단어들"](https://developers.google.com/ml-kit/vision/text-recognition/v2) — 같은 줄의 한글 요리명과 로마자 병기를 **하나의 라인으로 병합**한다. 로마자 병기 메뉴판이 들어오는 순간 "요리명 라인"의 길이 분포가 통째로 이동했고, 규칙은 그대로인데 세상이 바뀌었다. ML 용어로 **distribution shift** — 규칙 기반이라고 면제되지 않는다.

### 2-2. 표면 특징 vs 의미 특징
- **표면 특징(surface feature)**: 길이, 구분자 수, 위치, 문자 종류 — "어떻게 생겼나". 싸지만 **의미와의 상관이 깨지기 쉽다** (위 사례가 증명).
- **의미 특징(semantic feature)**: "이 문자열이 **요리 카탈로그에 있는가**" — "무엇인가" 그 자체.

`★ 핵심 통찰 ─────────────────────────────`
"김치찌개인가?"를 판별하는 최고의 방법은 김치찌개처럼 *생겼는지* 재는 게 아니라
**김치찌개 목록에 있는지 찾아보는 것**이다. 사전(gazetteer) 대조는 분류가 아니라 확인이라
분포가 어떻게 변해도 흔들리지 않는다. — "카탈로그 매칭 = 최고의 분류기"
`──────────────────────────────────────`

## 3. 비용 비대칭 — 미탐과 오탐은 같은 죄가 아니다

| | 미탐 (요리를 버림) | 오탐 (탭 제목을 요리로) |
|---|---|---|
| 사용자가 보는 것 | 오버레이 없음 → "인식 안 됐네" (**실패가 보임**) | 비-요리에 SAFE 배지 (**실패가 안 보임**) |
| 안전 영향 | 정보 부재 — 사용자가 경계 유지 | **false-safe — 위험을 안전이라 단언** |
| 허용치 | 아쉽지만 견딜 만 | **0이어야 함** (안전앱 원칙) |

그래서 임계값을 "한쪽으로 틀기"보다 **판단을 2단으로 쪼개는 게** 답이다 — 실제 K-Bap 코드 헤더가 이 설계를 명시한다:
```ts
// SAFETY: filtering downstream uses ONLY the structural type — never the BE match
// result. A plausible short Korean line is a `dishName` (matchable, always shown);
```
- **1단(후보 선정, FE)**: recall 우선 — 그럴듯한 짧은 한글은 일단 dishName으로 살려서 보냄 (요리를 버리는 게 더 아까움)
- **2단(안전 단언, BE)**: precision 우선 — **카탈로그 매칭에 성공한 것만** 안전 정보를 표시 (매칭 실패 = 오버레이 숨김)
→ "1스프린트"는 1단을 통과해도 2단(카탈로그에 없음)에서 떨어진다. **SAFE는 매칭이 증명한 것에만.**

## 4. 임시 패치 해부 (적용 완료) + 유니코드 함정

현재 코드의 rule 5는 원문이 아니라 **한글부만 추출해** 판정한다:
```ts
// classifyLine.ts (KB-72 패치 적용본)
const hangulPart = t
  .replace(/\d+\s*인(분)?(\s*이상)?/g, ' ')  // 수량 태그: "2인 이상" 제거
  .replace(/[^가-힣\s]/g, ' ')               // 한글만 남김
  .replace(/\s+/g, ' ').trim();
const judged = hangulLen >= 2 ? hangulPart : t;  // 한글 2자 이상일 때만
```
→ `"된장찌개 Doeniang fioe"`의 판정 대상이 `"된장찌개"`(4자)가 되어 통과. 진짜 설명문은 한글부도 길어서 여전히 걸러짐. 추가로 rule 4b: 한글+로마자 혼합 라인이 **화면 가장자리**(y<0.17 / y>0.81)에 있으면 junk — 브라우저 탭 제목("메뉴판 - Google x") 대응.

> [!note] `[가-힣]` vs `\p{Script=Hangul}` — 함정은 "같다고 믿는 것"
> - `[가-힣]` = **완성형 음절만** (U+AC00–D7A3). "김치찌개" ✅, 낱자 "ㄱ", "ㅏ" ❌
> - `\p{Script=Hangul}` = 음절 + **자모**(U+1100–) + **호환 자모**(U+3130–, "ㄱㄴㄷ") + 옛한글까지 전부
> OCR 노이즈엔 낱자 파편("ㅇ", "ㄱ")이 흔한데, `\p{Script=Hangul}`을 쓰면 이런 파편도 "한글 있음"으로 세어 오탐이 는다. **이 용도엔 좁은 `[가-힣]`이 오히려 정답** — 넓은 게 항상 좋은 게 아니라, 뭘 세고 싶은지가 기준.

## 5. 근본 해결 — 카탈로그 퍼지 매칭 (2026-07 예고안 — 실제 구현은 다르게 풀렸다, ↓ 하단 note)

구조: FE는 후보를 전부 전송 → **BE가 카탈로그(음식 100선)에 정규화+퍼지 매칭** → 성공=`foodId` 반환(요리), 실패=요리 아님(숨김).

### 단계적 매칭 전략 — 단계마다 오탐 위험이 다르다
| 단계 | 방법 | 잡는 것 | 오탐 위험 |
|---|---|---|---|
| 1 | **정확 일치** | "김치찌개" | 사실상 0 |
| 2 | **정규화 후 일치** (공백·불릿·수량태그 제거, NFC 정규화) | "· 김치찌개 " | 매우 낮음 — 정규화 규칙이 과하면 다른 항목이 충돌할 수 있음 |
| 3 | **편집거리 허용** (Levenshtein ≤ k) | "김치찌**가**개"(OCR 오타) | **여기가 위험 지대** — 한식명은 짧아서 거리 1~2로도 다른 요리가 됨 ("김치찜"↔"김치찌개") |

> 3단계 안전장치: 임계값을 **길이 비례**로 (4자 이하엔 거리 1도 신중), 후보가 2개 이상 비슷하면 **매칭 포기**(모호하면 안전 쪽 = 숨김), 자모 분해 비교(김치찌개→ㄱㅣㅁㅊㅣ…)로 한글 특화 거리 계산도 고려.

### OCR 오류 유형별 대응
| 오류 유형 | 예 | 대응 |
|---|---|---|
| 글자 치환/삽입 | 김치찌**가**개 | 3단계 편집거리 |
| 라인 병합 (한글+로마자) | 된장찌개 Doeniang | 스크립트 분리(한글부 추출) — §4 패치 |
| 라인 분리 (한 요리명이 두 줄) | "묵은지\n김치찜" | 분류가 아니라 **그룹핑 단계** 소관 → [[OCR 메뉴 스캔 — 박스 그룹핑]] |

## 6. 분류를 어디에 두나 — 클라이언트 vs 서버

| | FE(온디바이스) 분류 | BE(서버) 매칭 |
|---|---|---|
| 튜닝 배포 | **앱 배포 주기에 갇힘** (심사+사용자 업데이트, 며칠~몇 주) | 즉시 (서버 배포) |
| 카탈로그 접근 | 번들에 복사해야 (동기화 문제) | 원본이 거기 있음 |
| 오프라인/속도 | 됨/빠름 | 네트워크 필요 |
| 적합한 역할 | **1단: 싸고 보수적인 후보 거르기** | **2단: 의미 판정 (매칭)** |

→ K-Bap의 결론(그리고 일반 원칙): **표면 특징 필터는 FE에, 의미 판정은 BE에.** 사고 당일 임계값을 고치고 싶어도 앱 배포를 기다려야 했다는 것 자체가 FE 분류의 비용 증명.

## 7. 골든 픽스처 — 실패를 자산으로

§1의 표 5줄이 바로 **골든 픽스처의 씨앗**이다:
1. 실기기 OCR 덤프(라인 텍스트+박스)를 **JSON으로 저장** → 테스트 자산화
2. `classifyLine` 회귀 테스트: 픽스처 전 라인의 기대 판정을 스냅샷으로 고정
3. 규칙/임계값을 바꿀 때마다 전체 픽스처 재실행 — "이번 수정이 지난 사고를 되살리지 않는가"
4. 새 실패가 나올 때마다 픽스처에 **추가** (지우지 않음) → 분류기의 시험 문제가 복리로 쌓임

> 휴리스틱 분류기는 명세가 없고 사례가 명세다 — 그래서 사례 보존(픽스처)이 곧 문서화이자 안전망.

## 8. 용어집
- **휴리스틱/규칙 기반 분류기**: 사람이 쓴 규칙(정규식·임계값)으로 판정. 빠르지만 분포 변화에 취약.
- **distribution shift(분포 변화)**: 규칙/모델이 가정한 입력 분포와 실제 입력이 달라지는 것.
- **표면/의미 특징**: 생김새(길이·문자종류) / 정체("사전에 있는가").
- **gazetteer(사전) 매칭**: 알려진 엔티티 목록과 대조해 판별. "카탈로그 매칭"의 학술 이름.
- **미탐(FN)/오탐(FP)**: 진짜를 놓침 / 가짜를 잡음. precision↔recall 트레이드오프의 양끝.
- **false-safe**: 위험한 것을 안전하다고 판정 — 안전 시스템 최악의 실패 모드.
- **Levenshtein 편집거리**: 삽입·삭제·치환 몇 번으로 같아지는가. / **Jaro-Winkler**: 접두 일치에 가중치를 주는 유사도.
- **NFC 정규화**: 유니코드 조합 문자를 표준 형태로 통일 (자모 조합 ↔ 완성형).
- **골든 픽스처**: 실제 입력 덤프를 고정 테스트 자산으로 삼는 회귀 테스트 기법.

---

## 9. 다음에 빠른 재현 체크리스트
1. 규칙 분류기가 갑자기 무너지면 **입력 분포가 바뀌었는지**부터 (새 레이아웃? OCR 병합 방식?).
2. 표면 특징으로 의미를 판정하고 있진 않은가 — 사전이 있다면 **매칭이 최고의 분류기**.
3. 실패 비용이 비대칭이면 임계값 조정이 아니라 **판단 2단 분리** (후보=recall, 단언=precision).
4. 한글 정규식: 음절만 원하면 `[가-힣]`, `\p{Script=Hangul}`은 자모·낱자까지 포함 — 용도로 선택.
5. 짧은 이름에 편집거리 매칭 쓸 땐 **길이 비례 임계 + 모호하면 포기**.
6. 사고 라인은 버리지 말고 **골든 픽스처로 승격** — 실패가 시험 문제가 된다.
7. 튜닝이 잦을 로직은 FE(배포 주기)보다 BE(즉시 배포)에.

> **②그런데 §5 의 3단계 전략은 채택되지 않았다.** 서버의 정규화는 **세 줄짜리**다 — NFC 정규화 후 **한글 음절(`가`~`힣`)만 남긴다**(`KoreanMenuNameNormalizer.matchKey`). 편집거리(Levenshtein)도, 자모 분해도, 형태소 분석도 **없다.** §5 가 "여기가 위험 지대"라고 경고한 3단계를 **아예 안 밟았다.**
> **③안 밟아도 되게 만든 방법이 이 노트의 진짜 후속이다.** 서버는 FE OCR 문자열을 대조 대상으로 쓰지 않는다 — 같은 사진을 **비전 LLM 에 다시 던져** 표준 한국어명을 받아낸다(`specs/kb-320-scan-vision-ocr-ignore/`). 입력이 이미 깨끗하니 뒤 단계에 퍼지 매칭이 필요 없다. **정제를 앞으로 옮겨 뒤를 단순하게 만든 것** — §5 가 "매칭을 똑똑하게"로 풀려던 문제를 "입력을 깨끗하게"로 푼 셈이다. 그래서 `"김치찌**가**개"` 같은 OCR 오타도 FE 가 보내든 말든 결과에 영향이 없다.
> **④단순한 만큼 남은 구멍도 실측대로다.** 한글만 남기므로 `"김치찌개 (2인분)"` → `"김치찌개인분"` 이 되어 **수량 태그의 한글 조각은 그대로 남는다**(§4 의 FE 패치가 지운 그 `2인 이상` 문제가 서버 쪽엔 없다). 반대로 `"Kimchi Stew"` 처럼 한글이 0자면 매칭 키가 빈 문자열이라 그대로 탈락한다.
> **⑤§3 의 false-safe 방어 — 절반만 지켜진다.** 매칭 실패는 `matched: false` + `riskLevel: UNKNOWN` 으로 내려오니 "1스프린트"에 SAFE 가 붙는 일은 없다(그것도 카탈로그 이전, 비전 추출 단계에서 이미 떨어진다). **다만 서버는 겹치는 기피 성분이 0개면 `SAFE` 를 준다** — 기피 성분을 아예 등록하지 않은 회원에게는 **모든 음식이 `SAFE`** 다. "안전이 확인됨"과 "확인할 게 없었음"이 같은 값으로 내려온다는 뜻이라, 이 노트가 정의한 false-safe 의 변종이 서버 쪽에 남아 있다(→ [[19. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]] §5-4).
> **⑥§6 의 "FE 1단 / BE 2단" 은 한 발 더 갔다.** v2 에서는 표면 특징 필터조차 서버로 넘어갔다 — 앱은 글자를 읽지 않고 사진만 올린다. §6 의 결론("튜닝이 잦을 로직은 배포 주기가 없는 BE 로")을 끝까지 밀면 나오는 자리다 → [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]]
