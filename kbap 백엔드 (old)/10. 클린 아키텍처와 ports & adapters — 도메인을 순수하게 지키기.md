# 10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기

> **한 줄 요약**: 2단계에서 본 "인터페이스에 의존한다"와 3단계에서 본 "도메인은 JPA를 모른다"는 사실 **같은 원리 하나의 두 조각**이었다 — 핵심 규칙(도메인)을 Spring·DB 같은 바깥 기술로부터 격리하고, 바깥이 도메인이 정한 **인터페이스(port)** 를 **구현(adapter)** 한다. 이 노트는 그 역전을 큰 그림으로 묶는다.

이번 단계는 **새 개념을 늘어놓는 자리가 아니다.** 1~3단계에서 스치듯 만난 규칙들 — 도메인 모듈이 왜 Spring-free인지, `toDomain()/from()`이 왜 엔티티 안에 있는지, 유스케이스가 왜 구현이 아니라 인터페이스를 주입받는지 — 이 전부가 **하나의 설계 원리**에서 나온 것임을 보이는 게 목표다.

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| port | 도메인이 "나는 이런 게 필요하다"고 선언한 **인터페이스**. 도메인 쪽에 산다 | 커스텀 훅이 기대하는 `props`/콜백 타입 시그니처 — "이런 함수를 넘겨줘"라는 계약 |
| adapter | 그 port를 실제 기술(JPA·HTTP·LLM)로 **구현한 클래스**. 바깥(infra)에 산다 | 그 콜백을 실제 `fetch`로 채워 넣은 구현 |
| 의존성 역전 (DIP) | 화살표를 뒤집어 **바깥이 안쪽(도메인)에 의존**하게 만드는 것 | 유틸 함수가 특정 API 클라이언트를 import하지 않고, 호출부가 클라이언트를 주입해 주는 것 |
| 도메인 순수성 | 도메인 코드에 프레임워크·DB·외부 SDK import가 **하나도 없는** 상태 | 비즈니스 로직 훅에 `axios`·`react-navigation` import가 전혀 없는 상태 |

> 이 네 개는 서로 다른 개념이 아니라 **한 그림의 부품**이다: 도메인이 port를 선언(→ 순수성 유지)하고, 바깥이 adapter로 구현(→ 역전)한다.

## 문제 — 도메인 규칙이 Spring·JPA에 묶이면?

회원 등급 계산, 메뉴 판정 같은 **핵심 비즈니스 규칙**이 곧 이 서비스의 가치다. 그런데 이 규칙 코드가 `@Entity`, `JpaRepository`, `@Autowired` 같은 프레임워크 타입을 직접 들고 있으면 무슨 일이 생기나:

- **테스트가 지옥이 된다.** 등급 공식 하나 검증하려고 DB를 띄우고 Spring 컨텍스트를 로드해야 한다. 순수 계산인데 인프라가 딸려 온다.
- **기술 교체가 도메인을 흔든다.** MySQL → 다른 저장소, JPA → 다른 ORM으로 바꾸면 비즈니스 규칙 코드까지 줄줄이 고쳐야 한다.
- **규칙이 프레임워크에 오염된다.** "회원"이라는 개념을 읽으려는데 JPA 애너테이션·영속 관심사가 뒤섞여 진짜 규칙이 안 보인다.

**FE로 옮기면**: 할인 계산·유효성 검증 같은 순수 로직을 특정 UI 라이브러리 컴포넌트 안에 박아 넣은 상황과 같다. 그 로직만 따로 테스트하거나 다른 화면에서 재사용하려는데 컴포넌트·네비게이션이 통째로 딸려 온다.
→ *다른 점*: FE의 UI 결합은 대개 "불편"에 그치지만, 백엔드에서 도메인이 영속 기술에 묶이면 **팀 규모·수명이 긴 코드베이스**라 교체·테스트 비용이 복리로 커진다. 그래서 아예 컴파일 단계에서 격리를 강제한다(경계 강제 = [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]).

## 해법 — 의존성 역전(화살표 뒤집기)

순진하게 짜면 의존 방향은 이렇다:

```
도메인 규칙  ──의존──▶  JPA/Spring (기술)
```

규칙이 기술을 안다. 그래서 기술이 흔들리면 규칙이 흔들린다.

**의존성 역전**은 이 화살표를 뒤집는다. 도메인은 자기가 필요로 하는 걸 **인터페이스(port)로 선언만** 하고, 그 인터페이스를 **바깥(infra)이 구현(adapter)** 한다:

```
도메인 규칙 + port(인터페이스)   ◀──구현── JPA adapter (기술)
        ▲                                    │
        └────────── 컴파일 의존은 안쪽으로만 ──┘
```

도메인은 이제 아무것도 import하지 않는다. adapter가 도메인의 port를 import해 구현한다. **화살표가 전부 안쪽(도메인)을 향한다.** 이것이 클린 아키텍처의 "의존성 규칙"이고, 같은 구조를 포트/어댑터 방식으로 부른 게 **ports & adapters(헥사고날)** 다.

**2단계에서 본 그것이 이거였다**: [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]에서 "구현이 아니라 인터페이스에 의존하고, 런타임에 구현을 주입받는다"고 배웠다. 그 **인터페이스가 port**, 그 **주입되는 구현이 adapter**다. DI는 이 역전을 실제로 배선하는 수단이었다.

## kbap에서 — core는 순수, infra가 구현

kbap의 모듈 구조가 이 원리를 **Gradle 의존 방향으로 그대로 새겨** 두었다.

- **도메인 모듈 `core:*` 는 완전 Spring-free·ORM-free** 다. model + port 인터페이스 + 도메인 정책만 있고, JPA·Spring 의존을 빌드에서 아예 끌어오지 않는다.
- **JPA 전부**(엔티티·리포지토리·adapter)는 `infra:persistence` 한 곳에 모여 있다.
- 부트앱(`app:api`)이 이 둘을 **`runtimeOnly`로** 결합한다 — 컴파일 시점엔 서로 모르고, 실행 시점에만 스프링이 adapter 빈을 port 자리에 꽂는다.

> CLAUDE.md 모듈 구조 설명(`CLAUDE.md:34`):
> "도메인은 ORM-free·**완전 Spring-free** 로 model+port+도메인서비스/정책을 갖고 (…) infra(외부)·persistence(JPA)가 각각 port 를 구현한다. port 구현체는 부트앱(`app:api`·`app:batch`)이 `runtimeOnly`로 런타임 주입한다."

이 `runtimeOnly` 한 단어가 중요하다. 만약 `app:api`가 persistence를 `implementation`(컴파일 의존)으로 물면 도메인 JPA 타입이 컨트롤러 클래스패스로 전이돼 실수로 import할 수 있다. `runtimeOnly`라 **컴파일 클래스패스엔 안 보이고 실행 때만 전이**된다 — 격리가 빌드 도구 레벨에서 강제된다.

### 회원(member) 컨텍스트로 따라가 보기

같은 개념(`MemberRepository`)이 **세 모듈에 걸쳐** 어떻게 나뉘는지가 핵심이다.

**① port — 도메인 쪽 (`core:member`, Spring-free)**

`core/member/src/main/kotlin/com/meogo/core/member/MemberRepository.kt:1-15`
```kotlin
package com.meogo.core.member

interface MemberRepository {
    fun findById(id: Long): Member?
    fun findByIdentity(provider: SocialProvider, providerUserId: String): Member?
    fun saveNew(member: Member): Member
    fun update(member: Member): Member
    fun increaseScanCount(memberId: Long)
    fun withdraw(id: Long)
}
```
- import가 **하나도 없다.** Spring도 JPA도 모른다 — 순수 Kotlin 인터페이스다. 이게 도메인 순수성의 증거다.
- 반환·인자 타입이 전부 도메인 타입(`Member`)이다. "DB row"가 아니라 "회원"이라는 도메인 언어로 계약을 적었다.
- 도메인이 "나는 회원을 id로 찾고, 저장하고, 스캔 횟수를 올릴 수단이 필요하다"고 **선언만** 한다. 어떻게 하는지는 모른다.

**② port에 의존하는 유스케이스 (`application:client`)**

`application/client/src/main/kotlin/com/meogo/application/client/member/MemberProfileUseCase.kt:19-22`
```kotlin
@Service
class MemberProfileUseCase(
    private val memberRepository: MemberRepository,
) {
```
- 생성자가 받는 건 **port 타입** `MemberRepository`다. 구현 클래스 이름은 어디에도 없다.
- `@Service`라 스프링 빈이지만, 어떤 구현이 꽂힐지는 이 파일이 정하지 않는다(런타임 DI가 정함). 유스케이스는 "저장소가 있다"는 것만 알면 된다.
- 그래서 이 유스케이스를 테스트할 땐 진짜 DB 대신 **가짜 `MemberRepository`(in-memory)** 를 넣으면 된다 — 3단계에서 예고된 "port에 페이크 주입"이 여기서 실현된다.

**③ adapter — 바깥 쪽 구현 (`infra:persistence`)**

`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/member/MemberRepositoryAdapter.kt:1-16`
```kotlin
package com.meogo.infra.persistence.member

import com.meogo.core.member.Member
import com.meogo.core.member.MemberRepository
...
import org.springframework.stereotype.Repository

@Repository
class MemberRepositoryAdapter(
    private val memberJpaRepository: MemberJpaRepository,
) : MemberRepository {
    override fun findById(id: Long): Member? = findActive(id)?.toDomain()
    ...
}
```
- `: MemberRepository` — 도메인의 port를 **구현**한다. adapter가 도메인을 import하지, 그 반대가 아니다(화살표가 안쪽으로).
- 진짜 기술(`MemberJpaRepository`, `@Repository`, JPA)은 **여기에만** 있다. 도메인은 이 파일의 존재조차 모른다.
- `findActive(id)?.toDomain()` — DB에서 꺼낸 **JPA 엔티티를 도메인 객체로 되돌린다.** 이 `toDomain()`이 바로 3단계에서 본 그 변환이다.

정리하면, **하나의 `MemberRepository`가 "선언(core)–사용(application)–구현(infra)" 세 조각으로 쪼개져** 있고, 컴파일 의존은 전부 안쪽(core)을 향한다. 2단계의 "인터페이스에 의존", 3단계의 "도메인은 JPA를 모른다"가 이 한 그림 안에서 만난다.

## 왜 이득인가 — `toDomain()/from()`이 "경계 지킴이"였던 이유

역전이 주는 실제 값어치는 두 가지다.

1. **도메인 단위 테스트에 DB가 필요 없다.** 유스케이스·도메인 규칙은 port 타입만 알므로, 테스트에서 가짜 구현을 주입하면 스프링·MySQL 없이 순수하게 돈다. (등급 공식 검증이 대표 예 — `MemberRankingTest`는 저장소 없이 공식만 본다.)
2. **영속 기술을 갈아끼워도 도메인은 무변경.** 저장 방식이 바뀌면 `infra:persistence`의 adapter만 다시 쓴다. port 계약이 그대로면 도메인·유스케이스는 한 줄도 안 바뀐다.

이 격리를 실제로 지키는 문지기가 3단계에서 본 **`toDomain()` / `from()`** 이다.

> 컨벤션 문서 "도메인 객체 불변성 & 영속 변환"(`docs/architecture/meogo-conventions.md:83`):
> "도메인 ↔ JPA 변환은 JPA 엔티티 안에 둔다. (…) `RepositoryAdapter`는 `Entity.from(domain)`·`entity.toDomain()`만 호출한다. **(도메인 클래스는 JPA를 모른다 — 의존 방향 유지.)**"

즉 `toDomain()/from()`은 단순 매핑 유틸이 아니라 **port 경계를 물리적으로 지키는 번역기**였다. DB row(JPA 엔티티)와 도메인 객체를 오갈 때 이 번역을 강제해, 도메인이 절대 JPA 타입을 손에 쥐지 않게 한다. [[7. 영속성 컨텍스트와 엔티티 매핑]]에서 "도메인은 JPA를 모른다"고 배운 그 규칙이, 알고 보니 ports & adapters 경계를 지키기 위한 장치였던 것이다.

## LLM도 같은 패턴 — 단, 판단을 곁들여

외부 LLM 호출도 도메인 바깥이다. kbap은 이것도 어댑터 모듈 `infra:llm`으로 분리했다(ADR-0010). 벤더 SDK(Spring AI) 타입이 어댑터 밖으로 새지 않고 공개 API는 벤더 중립(`LlmFanoutClient`)으로 둔다 — **"외부 기술은 도메인 밖 어댑터에 가둔다"는 원리는 persistence와 동일**하다.

단, 흥미로운 차이가 있다. persistence는 `core`에 port를 두고 부트앱이 `runtimeOnly`로 조립하는 **정석 배선**을 쓰는데, LLM은 **소비자가 배치 잡 하나뿐**이라 `core:kernel` port·`runtimeOnly` 조립을 **일부러 생략**하고 `app:batch`가 `infra:llm`을 직접 의존한다.

> ADR-0010 Decision:
> "`:core:kernel` port·`runtimeOnly` 조립은 생략한다 — 단일 소비자(배치)라 간접층의 비용만 크고 이득이 없다(속도 우선)."

이게 시사하는 바: **ports & adapters는 교리가 아니라 도구다.** 여러 소비자가 도메인/유스케이스 계층에서 재사용해 경계가 실제로 필요할 때 port의 값어치가 나온다. 소비자가 하나뿐이면 port 인터페이스는 순수 오버헤드(YAGNI)라, 재사용 시점이 오면 그때 kernel port로 **승격**하기로 하고 지금은 직접 의존한다. persistence가 정석을 쓰는 이유(여러 유스케이스가 공유)와 대조하면 "언제 역전이 값을 하는가"가 선명해진다.

## 주의점 / 자주 헷갈리는 것

- **port는 도메인 쪽, adapter는 바깥 쪽.** 인터페이스를 어디에 두느냐가 방향을 결정한다. port를 infra에 두면 역전이 아니라 그냥 인터페이스 하나 만든 것뿐이다. kbap에서 `MemberRepository`가 `core:member`에 있는 게 핵심.
- **"인터페이스가 있다 = 클린 아키텍처"가 아니다.** 화살표가 안쪽을 향해야 한다. 도메인이 infra 인터페이스를 import하면 역전이 무너진다.
- **`runtimeOnly` vs `implementation`.** 부트앱이 persistence를 `implementation`으로 물면 JPA 타입이 상위 컴파일 클래스패스로 전이돼 격리가 샌다. kbap이 굳이 `runtimeOnly`를 쓰는 이유.
- **이 경계는 "지키자 다짐"이 아니라 테스트로 강제된다.** 도메인이 spring/jpa에 의존하면 빌드가 깨진다 — 그 장치(ArchUnit)의 상세는 [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]에서 다룬다. 여기선 "port/adapter가 뭔지"까지가 범위.
- **낡은 ADR 주의.** `ADR-0006`은 이 영속 어댑터 결정을 처음 적은 문서지만 **옛 패키지 이름**(`com.meogo.api.persistence`, batch 완전 디커플)을 쓴다. 현재 구조는 **ADR-0008(모듈러 모놀리스)** 기준(`com.meogo.infra.persistence`, batch가 도메인 직접 의존)이다. ports & adapters 원리 자체는 두 ADR에서 동일하나, 모듈 이름·batch 결합은 0008을 따른다.

## 치트시트

| 질문 | kbap에서의 답 |
|---|---|
| port는 어디 사나? | 도메인 모듈 `core:<도메인>` (예: `core/member/MemberRepository.kt`) |
| adapter는 어디 사나? | `infra:persistence/<도메인>` (예: `MemberRepositoryAdapter.kt`) |
| 유스케이스가 의존하는 건? | port 인터페이스 (구현 클래스명 안 씀) |
| 구현은 언제 꽂히나? | 런타임 — 부트앱이 `runtimeOnly`로 조립, 스프링 DI가 배선 |
| 도메인이 JPA를 안 만지는 걸 뭐가 지키나? | 엔티티 안의 `toDomain()/from()` 번역 + 컴파일 경계(+ ArchUnit) |
| 화살표 방향은? | 항상 안쪽(도메인)으로. 바깥이 안쪽을 import |
| LLM은 왜 port 생략? | 소비자가 배치 하나뿐 → YAGNI. 재사용 시 kernel port로 승격 |

## 용어집

- **port(포트)**: 도메인이 필요로 하는 능력을 선언한 인터페이스. 도메인 모듈에 위치. 예: `MemberRepository`.
- **adapter(어댑터)**: port를 특정 기술로 구현한 클래스. 바깥 모듈(infra)에 위치. 예: `MemberRepositoryAdapter`.
- **의존성 역전 원칙(DIP)**: 상위(도메인)가 하위(기술)에 의존하지 않고, 둘 다 추상(port)에 의존하게 만들어 화살표를 뒤집는 것.
- **ports & adapters (헥사고날 아키텍처)**: 도메인을 중심에 두고 모든 외부 연동(DB·web·LLM)을 port/adapter로 격리하는 구조. 클린 아키텍처의 "의존성 규칙"을 포트 관점으로 표현한 것.
- **도메인 순수성**: 도메인 코드에 프레임워크·인프라 import가 전혀 없는 상태. kbap에선 `core:*`가 Spring-free·ORM-free인 것으로 실현.
- **`runtimeOnly`**: Gradle 의존 스코프. 컴파일 클래스패스엔 안 보이고 실행 시점에만 전이 — 부트앱이 adapter를 조립하되 상위가 JPA를 컴파일 의존하지 않게 한다.

## 체크리스트 (이 노트를 이해했다면)

- [ ] port와 adapter가 각각 어느 모듈에 사는지, 왜 그래야 하는지 말할 수 있다.
- [ ] "2단계의 인터페이스 의존"과 "3단계의 도메인은 JPA를 모른다"가 같은 원리의 두 조각임을 설명할 수 있다.
- [ ] `toDomain()/from()`이 왜 단순 매퍼가 아니라 "경계 지킴이"인지 안다.
- [ ] `runtimeOnly` 조립이 왜 `implementation`보다 격리에 유리한지 안다.
- [ ] LLM이 port를 생략한 이유(YAGNI·단일 소비자)로 "역전은 언제 값을 하는가"를 설명할 수 있다.
