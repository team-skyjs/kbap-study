# 8. LAZY 로딩과 N+1 문제

> 작성: 2026-07-14 · 맥락: 엔티티가 다른 엔티티(음식 → 기피 성분들)를 참조할 때, 그걸 **언제** DB에서 가져올지가 성능을 가른다.
> 목표: kbap이 **모든 연관을 LAZY로 고정**하고 필요할 때만 **fetch join**으로 명시 로딩하는 이유 — 백엔드 성능 버그 1위 N+1을 막는 규약 — 을 30분 뒤의 나도 재현.

---

## 0. 한 줄 요약

**연관 데이터는 기본 "안 가져오고 미뤄둔다(LAZY)". 진짜 필요할 때 쿼리 하나로 같이 끌어온다(`join fetch`).** 이 둘을 안 지키면 목록 N건에 쿼리가 1+N번 나가는 **N+1 문제**가 터진다. kbap은 전 연관을 `FetchType.LAZY`로 고정하고, 목록 조회는 `left join fetch`로 명시한다.

> [!note] 먼저 알아야 할 것
> 이 노트는 [[7. 영속성 컨텍스트와 엔티티 매핑]]에서 정의한 **엔티티**, **영속성 컨텍스트(세션)** 개념을 그대로 쓴다. "엔티티 = DB 테이블 한 행에 대응하는 Kotlin 객체", "영속성 컨텍스트 = 트랜잭션 한 개 동안 살아있는 1차 캐시"라는 것만 기억하면 된다.

## 1. 핵심 개념

| 구분 | 정체 | FE에서 가장 가까운 것 (비유, 완전 동치 아님) |
|---|---|---|
| 연관관계 | 엔티티가 다른 엔티티를 필드로 참조 (`@OneToMany` 등) | 객체 안에 다른 객체 배열을 물고 있는 것 (`food.substances: []`) |
| LAZY | 참조를 **실제로 건드릴 때** DB에서 가져옴 | React Query의 `enabled: false` — 필요해질 때 fetch |
| EAGER | 부모를 조회하는 **즉시** 연관까지 다 가져옴 | 컴포넌트 mount하자마자 관련 데이터 전부 prefetch |
| N+1 | 목록 N건을 돌며 연관을 하나씩 따로 조회 → 쿼리 1+N번 | 리스트 렌더 중 각 항목이 `useEffect`로 개별 fetch 하는 워터폴 |
| fetch join | 부모 + 연관을 **JPQL**(테이블 대신 엔티티를 기준으로 쓰는 JPA의 쿼리 언어) **한 방**에 조인해서 같이 로딩 | 서버가 이미 조인해서 내려준 완성형 응답 하나 |

## 2. 연관관계 — 엔티티가 엔티티를 가리킨다

[[7. 영속성 컨텍스트와 엔티티 매핑]]에서 엔티티 하나가 테이블 한 개에 대응한다고 봤다. 실제 데이터는 서로 얽혀 있다. kbap의 음식(`food`)은 여러 개의 **기피 성분**(`food_avoidance_substance`, 알레르기·비선호 성분 등)을 가진다. 이 "1:다" 관계를 엔티티에서는 컬렉션 필드로 표현한다.

```kotlin
@OneToMany(cascade = [CascadeType.ALL], fetch = FetchType.LAZY, orphanRemoval = true)
@JoinColumn(name = "food_id", nullable = false)
var foodAvoidanceSubstances: MutableSet<FoodAvoidanceSubstanceJpaEntity> = mutableSetOf(),
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodJpaEntity.kt:58`

- `@OneToMany`: 음식 1건이 기피 성분 N건을 가진다는 1:다 선언.
- `fetch = FetchType.LAZY`: **핵심 규약.** 이 컬렉션은 `foodAvoidanceSubstances`를 실제로 읽는 순간까지 DB에서 안 가져온다.
- `@JoinColumn(name = "food_id")`: 자식 테이블의 `food_id` 컬럼으로 부모를 가리키는 외래키 매핑.
- `MutableSet<...>`: 자식 엔티티 타입은 `FoodAvoidanceSubstanceJpaEntity`(별도 `@Entity`, 테이블 `food_avoidance_substance`).
- `cascade = [CascadeType.ALL]` · `orphanRemoval = true`: 부모(음식)를 저장·삭제하면 자식(성분)도 따라가고, 컬렉션에서 빠진 자식은 DB에서도 지워지는 **생명주기 옵션** — 로딩(이 노트 주제)과는 별개 축이라 여기선 이 한 줄까지만.

> FE 비유로 보면 `food` 객체 안에 `substances: FoodAvoidanceSubstance[]`가 들어있는 모양이다. **다른 점**: FE 객체 배열은 이미 메모리에 다 있지만, LAZY 컬렉션은 "아직 안 채워진 빈 자리(프록시)"이고 건드리는 순간 쿼리가 나간다.

## 3. LAZY vs EAGER — 언제 가져오나

같은 연관이라도 **가져오는 시점**을 두 가지로 정할 수 있다.

- **EAGER(즉시)**: 부모(`Food`)를 조회하면 Hibernate가 곧바로 기피 성분까지 추가 쿼리로 다 끌어온다. 안 쓸 데이터도 무조건 딸려와서 낭비가 생긴다.
- **LAZY(지연)**: 부모만 먼저 가져오고, `food.foodAvoidanceSubstances`를 코드에서 실제로 읽는 순간 그때 성분 쿼리가 나간다.

kbap은 [레포 규약상] **모든 연관을 LAZY로 고정**한다(`FetchType.LAZY`를 빠짐없이 명시). 왜냐하면 EAGER는 "이 화면에선 성분이 필요 없는데도 항상 가져오는" 통제 불능 로딩을 만들기 때문이다. 필요 여부는 화면(유스케이스)마다 다르니, 기본은 안 가져오고 필요한 곳에서만 명시적으로 가져오게 뒤집는 것이다.

> [!warning] LAZY의 대가 — LazyInitializationException
> LAZY 컬렉션은 **영속성 컨텍스트(세션)가 살아있는 동안**에만 지연 로딩이 가능하다. 트랜잭션이 끝나 세션이 닫힌 뒤에 `food.foodAvoidanceSubstances`를 건드리면 `LazyInitializationException`("could not initialize proxy - no Session")이 터진다. kbap이 컨트롤러가 아니라 **도메인 객체로 변환(`toDomain()`)해서 반환**하는 것도 이 함정과 무관하지 않다 — 트랜잭션 안에서 필요한 걸 다 로딩해 순수 Kotlin 객체로 꺼내두면, 밖에서는 프록시를 건드릴 일이 없다.

## 4. N+1 문제 — LAZY만으론 안 되는 이유 (핵심)

LAZY로 미뤘다고 문제가 사라지는 게 아니다. **목록**을 다룰 때 오히려 함정이 된다.

음식 20건을 조회한 뒤, 각 음식의 기피 성분을 화면에 보여준다고 하자.

1. 음식 목록 조회 → 쿼리 **1번** (`select ... from food ... limit 20`)
2. 반복문에서 `food.foodAvoidanceSubstances`를 읽음 → 음식마다 성분 조회 쿼리 **1번씩 × 20** (LAZY라 그때그때 나감)

합계 **1 + 20 = 21번**. 목록이 100건이면 101번. 이게 **N+1 문제**다. 쿼리 개수가 데이터 건수에 비례해 폭증한다. 각 쿼리는 빠를지 몰라도, 네트워크 왕복 수백 번이 쌓여 응답이 급격히 느려진다.

`★ 핵심 통찰 ─────────────────────────────`
N+1은 "LAZY라서" 생기는 게 아니라 **"목록을 돌며 각 항목의 LAZY 연관을 하나씩 깨워서"** 생긴다.
- EAGER로 바꾸면? 여전히 부모 목록당 자식 쿼리가 따로 나가 N+1이 그대로거나 더 나빠진다 (게다가 안 쓸 때도 낭비).
- 해법은 로딩 시점(LAZY↔EAGER)을 바꾸는 게 아니라, **한 번에 조인해서 가져오는 것** → `join fetch`.
`──────────────────────────────────────`

> 비유: 장바구니 20개를 확인하는데, 목록은 한 번에 받았지만 각 바구니 속 내용물은 **바구니마다 창고에 다시 뛰어가서** 확인하는 꼴. `join fetch`는 처음부터 "내용물까지 다 채운 바구니 20개"를 한 번에 받아오는 것. **다른 점**: FE의 워터폴(각 항목이 `useEffect`로 개별 fetch)과 증상은 같지만, N+1은 DB↔앱 사이에서 조용히 일어나 화면 코드만 봐선 안 보인다.

## 5. fetch join — 한 방에 필요한 연관까지

`join fetch`(JPQL)는 부모와 연관을 **SQL 조인 하나**로 함께 조회한다. kbap은 음식을 ID로 로딩할 때 성분까지 붙여 가져온다.

```kotlin
@Query(
    """
    select distinct f from FoodJpaEntity f
    left join fetch f.foodAvoidanceSubstances
    where f.id in :ids
    order by f.id desc
    """,
)
fun findByIdInWithAvoidanceSubstancesDesc(@Param("ids") ids: List<Long>): List<FoodJpaEntity>
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodJpaRepository.kt:41`

- `left join fetch f.foodAvoidanceSubstances`: 음식과 그 성분을 **한 쿼리로** 조인해 로딩. 이 결과의 음식들은 성분이 이미 채워져 있어 나중에 건드려도 추가 쿼리가 안 나간다 → N+1 소멸.
- `left`: 성분이 하나도 없는 음식도 결과에서 빠지지 않게 함(내부 조인이면 성분 없는 음식이 사라짐).
- `select distinct f`: 1:다 조인은 성분 개수만큼 **부모 행이 중복**된다(음식 A에 성분 3개면 A가 3줄). `distinct`로 부모 기준 중복을 없앤다.
- `:ids`: 왜 ID 목록으로 조회하는지는 다음 절에서.

> [!tip] 왜 EAGER로 안 풀고 fetch join으로 푸나
> EAGER는 "항상·자동" 로딩이라 안 쓰는 화면에서도 성분을 끌어오고, N+1도 못 막는다. fetch join은 "이 조회에서만·명시적으로" 함께 로딩한다. 즉 **기본은 LAZY로 잠가두고(안 가져옴), 필요한 조회마다 join fetch로 열어주는** 게 kbap 규약이다. 로딩을 코드로 통제할 수 있게 된다.

## 6. fetch join과 페이징의 충돌 — kbap의 2단계 해법

여기가 이 노트에서 제일 미묘한 지점이다. **컬렉션을 `join fetch`하면서 동시에 페이징(`LIMIT`)을 걸 수 없다.**

이유: 1:다 조인 결과는 부모 행이 자식 수만큼 불어나 있다. 이 상태에서 SQL로 `LIMIT 20`을 자르면 **어떤 음식의 성분이 중간에 잘려** 성분 일부만 달린 음식이 나올 수 있다. Hibernate는 정합성을 위해 이 경우 `LIMIT`을 DB에 넘기지 않고 **전체를 다 읽어와 메모리에서 잘라낸다**(경고 `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!`). 수백만 행이면 메모리로 다 퍼올리는 재앙이다.

kbap의 해법: **① ID만 커서 페이징으로 자르고 → ② 그 ID들로 join fetch 재조회**하는 2단계.

```kotlin
@Query(
    """
    select f.id from FoodJpaEntity f
    where (:cursor is null or f.id < :cursor)
      and f.contentStatus = 'READY'
    order by f.id desc
    """,
)
fun findFoodPageIds(@Param("cursor") cursor: Long?, pageable: Pageable): List<Long>
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodJpaRepository.kt:31`

- 컬렉션 조인 없이 **`f.id`만** 뽑는다. 조인이 없으니 부모 행이 안 불어나고, `LIMIT`을 안전하게 DB에서 걸 수 있다(`pageable`이 `LIMIT` 담당).
- `where (:cursor is null or f.id < :cursor)`: **커서 방식** 페이징. 직전 페이지 마지막 id보다 작은 것부터 이어 읽는다(`order by f.id desc`). 첫 페이지는 `cursor = null`.

```kotlin
override fun findFoodPage(cursor: Long?, size: Int): List<Food> {
    val ids = foodJpaRepository.findFoodPageIds(cursor, PageRequest.of(0, size))
    return loadDescending(ids)
}

private fun loadDescending(ids: List<Long>): List<Food> {
    if (ids.isEmpty()) return emptyList()
    return foodJpaRepository.findByIdInWithAvoidanceSubstancesDesc(ids).map { it.toDomain() }
}
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodRepositoryAdapter.kt:38`

- 1단계: `findFoodPageIds`로 이번 페이지에 해당하는 **음식 id 20개만** 페이징해서 얻는다 (조인 없음 → `LIMIT` 안전).
- 2단계: `loadDescending`이 그 20개 id로 `findByIdInWithAvoidanceSubstancesDesc`(5절의 join fetch 쿼리)를 호출 → 성분까지 채운 음식 20건을 **쿼리 2번**으로 완성. (`in :ids`엔 `LIMIT`이 없으니 join fetch가 자유롭게 동작)
- 결과: 페이징 + 연관 로딩을 **N+1 없이, 메모리 폭발 없이** 둘 다 만족. 총 쿼리 = 딱 2번.

> [!note] 페이징 이론과의 연결
> 1단계가 쓰는 `where f.id < :cursor` + `order by f.id desc`가 바로 **keyset/커서 페이지네이션**이다. offset 페이징이 왜 깊은 페이지에서 느려지고, keyset이 왜 인덱스 seek로 일정하게 빠른지는 [[페이징 — Offset vs No-Offset(Keyset·Cursor)]]에 정리돼 있다. kbap은 그 keyset 커서를 **fetch join과 2단계로 결합**해, "빠른 페이징"과 "N+1 없는 연관 로딩"을 동시에 얻는다. 근거 기능은 무한 스크롤 메뉴 목록(kb-63).

## 7. 트러블슈팅 (실제로 막히는 것)

- **증상**: 목록 API가 데이터 늘수록 급격히 느려짐, 로그에 같은 모양 쿼리가 수십 번.
  → 원인: N+1 (목록 돌며 LAZY 연관을 개별 로딩).
  → 해결: 해당 조회에 `left join fetch`로 연관을 함께 로딩.

- **증상**: 컨트롤러/직렬화 단계에서 `LazyInitializationException: could not initialize proxy - no Session`.
  → 원인: 트랜잭션(세션)이 닫힌 뒤 LAZY 연관을 건드림.
  → 해결: 트랜잭션 안에서 필요한 연관을 fetch join으로 미리 로딩(kbap은 `toDomain()`으로 순수 객체 변환까지 트랜잭션 안에서 끝냄).

- **증상**: 로그에 `HHH000104 ... applying in memory!` 경고, 페이징이 느리고 메모리 튐.
  → 원인: 컬렉션 `join fetch`에 `LIMIT`(페이징)을 같이 걸어 Hibernate가 전량 로딩 후 메모리에서 자름.
  → 해결: **ID 페이징 → ID로 join fetch** 2단계 분리 (6절 kbap 방식).

- **증상**: 1:다 join fetch 결과에서 부모가 중복(음식 A가 여러 줄).
  → 원인: 조인으로 부모 행이 자식 수만큼 늘어남.
  → 해결: JPQL에 `select distinct` (kbap의 fetch join 쿼리들이 전부 사용).

## 8. 치트시트

```kotlin
// 1) 연관은 전부 LAZY로 잠근다 (kbap 규약)
@OneToMany(fetch = FetchType.LAZY, ...) var children: MutableSet<Child> = mutableSetOf()

// 2) 필요한 조회에서만 join fetch로 연다 (+ distinct로 부모 중복 제거)
@Query("select distinct p from Parent p left join fetch p.children where p.id in :ids")
fun findWithChildren(ids: List<Long>): List<Parent>

// 3) 컬렉션 fetch join + 페이징은 금지 → 2단계로
//    ① 조인 없이 ID만 페이징 (LIMIT 안전)
@Query("select p.id from Parent p where (:cursor is null or p.id < :cursor) order by p.id desc")
fun findPageIds(cursor: Long?, pageable: Pageable): List<Long>
//    ② 그 ID들로 join fetch 재조회 (LIMIT 없음)
```

- N+1 판정: "목록 조회 후 반복문에서 연관 접근" → 쿼리 1+N이면 N+1.
- 방어 순서: **기본 LAZY → 조회별 join fetch → 페이징 겹치면 ID 2단계.**

---

## 9. 용어집

- **연관관계(association)**: 엔티티가 다른 엔티티를 참조하는 관계. `@OneToMany`(1:다), `@ManyToOne`(다:1) 등.
- **LAZY(지연 로딩)**: 연관을 실제 접근하는 순간 DB에서 가져오는 전략. kbap 전 연관의 기본값.
- **EAGER(즉시 로딩)**: 부모 조회 즉시 연관까지 가져오는 전략. kbap은 안 씀.
- **N+1 문제**: 목록 N건의 연관을 각각 따로 조회해 쿼리가 1+N번 나가는 성능 문제.
- **fetch join**: JPQL `join fetch`로 부모와 연관을 한 쿼리에 함께 로딩. N+1 해소 수단.
- **LazyInitializationException**: 세션(영속성 컨텍스트) 종료 후 LAZY 연관을 건드릴 때 나는 예외.
- **HHH000104**: 컬렉션 fetch join에 페이징을 걸 때 Hibernate가 메모리에서 자른다는 경고.
- **커서 페이지네이션**: `where id < :cursor`로 "마지막 본 값 다음부터" 읽는 페이징. → [[페이징 — Offset vs No-Offset(Keyset·Cursor)]]

## 10. 다음에 빠른 재현 체크리스트

1. 새 연관 매핑? → `fetch = FetchType.LAZY` 명시 (kbap은 전부 LAZY).
2. 목록에서 그 연관을 쓸 거면? → 조회 쿼리에 `left join fetch` + `select distinct`.
3. 그 목록에 페이징도 필요하면? → 컬렉션 join fetch + LIMIT 금지 → **① ID만 페이징 → ② ID로 join fetch** 2단계.
4. `LazyInitializationException` 나면 → 트랜잭션 안에서 필요한 연관을 미리 fetch(또는 도메인 변환).
5. 실물 참고: `FoodJpaEntity.kt:58`(LAZY), `FoodJpaRepository.kt:31,41`(ID 페이징·fetch join), `FoodRepositoryAdapter.kt:38`(2단계 조립).
