# 3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점

## 한 줄 요약

JS는 브라우저/Node 엔진에서 소스 그대로 돌았지만, kbap의 Kotlin은 **JVM용 바이트코드로 먼저 컴파일된 뒤** JVM 위에서 돈다. 이 "컴파일 단계"가 실행 전에 타입·널 오류를 잡아주고, kbap은 컴파일러 플래그(`-Xjsr305=strict`)로 그 안전망을 Java 라이브러리 경계까지 넓혀 놨다.

---

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| JVM (Java Virtual Machine) | 바이트코드를 받아 실제 CPU에서 실행해 주는 런타임 엔진 | 브라우저의 JS 엔진(V8)·Node 런타임 |
| 바이트코드 | 사람이 쓴 소스를 JVM이 읽을 수 있게 변환한 중간 형식(`.class`) | `tsc`가 뽑아낸 결과물 — 단, 그건 여전히 JS 소스다(차이는 아래) |
| 컴파일 | 실행 전에 소스 전체를 기계가 읽을 형식으로 번역하며 오류를 검사하는 단계 | `tsc`로 `.ts` → `.js` 변환 |
| Kotlin ↔ Java | Kotlin은 Java와 같은 바이트코드로 컴파일돼, Java 라이브러리(Spring 등)를 그대로 가져다 쓴다 | TS가 JS 라이브러리(npm 패키지)를 그대로 쓰는 관계 |
| Gradle 멀티모듈 | 한 저장소를 여러 모듈로 쪼개고 의존 방향을 정해 빌드하는 구조 | pnpm workspace 같은 모노레포 패키지 분리 |
| 버전 카탈로그 | 모든 라이브러리 버전을 한 파일에 모아 단일 출처로 관리 | 모노레포 루트의 의존성 버전 고정(`pnpm` catalog / 루트 `package.json`) |

## 원리 — JVM이란 무엇인가

FE에서 코드가 도는 그림은 이랬다. 브라우저나 Node에는 **JS 엔진(V8)** 이 들어 있고, 이 엔진이 JS 소스를 읽어 그 자리에서 실행한다. TS를 쓰더라도 결국 `tsc`가 `.ts`를 `.js`로 바꾼 뒤, **엔진이 실행하는 건 JS 소스**다. 타입은 이 변환 과정에서 전부 지워진다.

JVM 위의 Kotlin은 한 겹이 더 있다.

1. **컴파일**: `kotlinc`(Gradle이 대신 호출)가 `.kt` 소스를 **바이트코드**(`.class`)로 번역한다. 이때 타입·널 오류를 잡는다.
2. **실행**: JVM이 그 바이트코드를 받아 실제 CPU에서 돌린다.

여기서 JVM의 핵심 성질이 "한 번 컴파일하면 어디서든 돈다(Write Once, Run Anywhere)"이다. 바이트코드는 특정 OS·CPU에 묶이지 않은 중간 형식이라, JVM만 깔려 있으면 macOS든 리눅스 서버든 같은 `.jar`가 그대로 돈다.

> [!note] 어디까지 같고 어디서 다른가
> **같은 점**: JS 엔진(V8)도 JVM도 "내 코드를 실제로 실행해 주는 런타임 엔진"이라는 점은 같다. 둘 다 실무에선 번역 단계(`tsc` ↔ `kotlinc`)를 거친다.
> **다른 점**: `tsc`의 결과물은 **여전히 JS 소스**이고 엔진이 그 소스를 읽는다. `kotlinc`의 결과물은 **바이트코드라는 바이너리**이고 JVM은 소스가 아니라 그 바이너리를 실행한다. 그래서 TS의 타입은 실행 시점에 흔적도 없지만(아래 "안전망" 참고), JVM에서는 타입이 실행 중에도 살아 있다.

---

## Kotlin과 Java 생태계 — TS와 JS의 관계를 닮았다

FE에서 TS로 개발해도 실제로 쓰는 라이브러리(React, axios…)는 전부 JS 생태계의 npm 패키지다. TS는 그 위에 타입이라는 층을 얹었을 뿐이다.

Kotlin과 Java도 똑같다. kbap이 쓰는 Spring, JPA(Hibernate), Jackson은 전부 **Java로 만들어진 라이브러리**다. Kotlin은 이들을 그대로 가져다 쓴다 — 같은 바이트코드로 컴파일되기 때문이다.

kbap의 버전 카탈로그를 보면 Kotlin과 Java 라이브러리가 한 표에 섞여 있다.

```toml
[versions]
java = "21"
kotlin = "2.3.21"
spring-boot = "4.1.0"
```
`gradle/libs.versions.toml:2`

- `java = "21"` — 이 프로젝트가 목표로 하는 JVM 버전(자세히는 아래 툴체인).
- `kotlin = "2.3.21"` — 소스를 바이트코드로 번역하는 Kotlin 컴파일러 버전.
- `spring-boot = "4.1.0"` — Java로 만들어진 Spring Boot 프레임워크. Kotlin 코드가 이 Java 라이브러리를 그대로 의존한다.

> [!note] 어디까지 같고 어디서 다른가
> **같은 점**: TS가 JS 생태계를, Kotlin이 Java 생태계를 "내 언어 문법으로 그대로 소비한다"는 점은 같다.
> **다른 점**: TS는 컴파일하면 **사실상 JS 그 자체**가 된다(같은 언어 계열). Kotlin은 Java와 **문법이 전혀 다른 별개 언어**인데, 공통 바이트코드/JVM을 공유해서 상호 운용된다. 다리가 "소스 호환"(TS)이냐 "바이트코드 호환"(Kotlin)이냐가 다르다.

---

## 컴파일 언어의 안전망 — 실행 전에 잡는다, 그리고 실행 중에도

TS의 `strictNullChecks`나 타입 검사도 "실행 전에 오류를 잡는다"는 점에선 컴파일 언어의 안전망과 같다. `tsc`가 에러를 뱉으면 빌드가 실패한다.

차이는 **실행 시점**에 있다. TS의 타입은 컴파일 후 지워진다(type erasure). 그래서 `as any` 캐스팅이나 `JSON.parse` 결과처럼 타입 검사를 우회한 값이 들어오면, 실행 중에 엉뚱한 타입이 흘러 다니다가 `undefined is not a function` 같은 런타임 에러가 난다. 즉 TS의 타입 보장은 **컴파일 시점까지만** 유효하다.

JVM은 타입을 **실행 중에도 강제**한다. 잘못된 타입으로 캐스팅하면 JVM이 실행 도중 `ClassCastException`을 던진다. 타입이 컴파일 후에도 살아서 감시한다.

> [!note] 어디까지 같고 어디서 다른가
> 한 줄 차이: **TS 타입은 컴파일 때만 검사하고 실행 시점엔 사라진다. JVM 타입은 실행 중에도 VM이 직접 강제한다.**

## 널 안전 — Kotlin `String?` vs `String`

Kotlin은 타입 자체에 "널이 될 수 있는가"를 새겨 넣는다. 이건 TS의 `string | null`과 아주 비슷하다.

- `String` — 절대 `null`이 아니다. `null`을 넣으면 **컴파일 에러**.
- `String?` — `null`일 수 있다. 값을 쓰기 전에 널 처리를 강제한다.

공식 문서(kotlinlang.org)의 표현 그대로: *"non-null 변수를 선언하면, 컴파일러가 그 변수는 `null`을 담을 수 없도록 강제해 NPE를 예방한다."* (NPE = `NullPointerException` — 널인 값에 접근해서 프로그램이 실행 중에 터지는 오류. JS의 `Cannot read properties of null`과 같은 사고다.) 널일 수 있는 값에 바로 접근하면(`b.length`) 컴파일이 막히고, 안전 호출 `?.`(널이면 `null` 반환)이나 명시적 검사를 써야 한다. `!!`는 "널 아님을 내가 보증한다"는 강제 단언이라, 실제로 널이면 그 자리에서 NPE가 난다.

여기까지는 TS의 `strictNullChecks`와 거의 같은 그림이다. **kbap이 한 발 더 나간 지점**은 Java 라이브러리 경계다.

```kotlin
configure<KotlinJvmProjectExtension> {
    compilerOptions {
        freeCompilerArgs.addAll(
            "-Xjsr305=strict",
            "-Xannotation-default-target=param-property",
            "-Xemit-jvm-type-annotations",
        )
    }
}
```
`buildSrc/src/main/kotlin/meogo.kotlin-common.gradle.kts:34`

- `configure<KotlinJvmProjectExtension>` — 모든 모듈에 공통 적용되는 Kotlin 컴파일 설정 블록.
- `-Xjsr305=strict` — 핵심 줄. Java API가 붙여 둔 널 관련 애너테이션(`@Nonnull`/`@Nullable` 계열, Spring도 이걸 붙인다)을 **진짜 Kotlin 타입 제약으로 취급**한다.

이게 왜 특별한가. Kotlin이 Java 코드를 부를 때, 기본적으로 Java의 값은 널일지 아닐지 알 수 없는 **플랫폼 타입(`T!`)** 이 된다 — 컴파일러가 널 검사를 못 하고 봐준다는 뜻이다. `-Xjsr305=strict`를 켜면, 애너테이션이 붙은 Java 선언은 플랫폼 타입이 아니라 Kotlin의 nullable/non-null 타입으로 해석돼 **Spring 같은 Java 라이브러리를 호출하는 지점까지 널 검사가 강제**된다.

> [!note] 어디까지 같고 어디서 다른가
> **같은 점**: 타입 레벨에서 널 가능성을 컴파일 때 구분하는 발상은 TS `strictNullChecks`와 같다.
> **다른 점**: TS에서 타입 없는 JS 라이브러리를 부르면 결과가 `any`가 돼 널이 그냥 새어 들어온다. kbap은 `-Xjsr305=strict`로 **Java 라이브러리 경계의 널까지** 검사망 안으로 끌어온다. 게다가 널 위반은 실행 시점에도 JVM이 NPE로 막는다(컴파일 때만이 아니다).

## Gradle 멀티모듈 — 모노레포와 같은 발상

kbap은 한 저장소를 여러 모듈로 쪼갠다. `core/`(도메인)·`infra/`(DB·외부연동)·`app/`(실행 앱) 식이다. 이건 pnpm workspace로 한 레포를 여러 패키지로 나누는 모노레포와 같은 발상이다.

어떤 모듈들이 한 빌드에 속하는지는 `settings.gradle.kts`가 목차처럼 등록한다.

```kotlin
rootProject.name = "meogo-server"

include(
    ":core:kernel",       // 도메인 공유 커널
    ":core:food",
    // …
    ":application:client", // 사용자 API 유스케이스
    ":infra:persistence", // 영속 adapter (JPA)
    ":infra:llm",         // LLM 외부 연동 어댑터
    ":app:api",           // web bootJar (조립)
    ":app:batch",         // batch bootJar
    ":common",
)
```
`settings.gradle.kts:19` (일부 생략)

- `include(...)` — 이 빌드에 속하는 모듈 목록. 콜론(`:`)은 폴더 계층을 뜻한다(`:core:food` = `core/food`).
- `pnpm-workspace.yaml`의 `packages:` 목록과 정확히 같은 역할이다.

버전 관리도 모노레포와 닮았다. 앞에서 본 `gradle/libs.versions.toml`이 **모든 라이브러리 버전의 단일 출처**다. 모듈마다 버전을 따로 적지 않으니, pnpm 루트에서 의존성 버전을 한곳에 고정하는 것과 같다.

Java 버전(툴체인)도 이 공통 설정에서 한 번에 정해진다.

```kotlin
configure<JavaPluginExtension> {
    toolchain {
        languageVersion = JavaLanguageVersion.of(javaVersion)
    }
}
```
`buildSrc/src/main/kotlin/meogo.kotlin-common.gradle.kts:28`

- `toolchain { languageVersion = ... }` — 로컬 PC에 어떤 JDK가 깔려 있든, Gradle이 Java 21을 직접 확보해 그걸로 빌드한다(값 `javaVersion`은 카탈로그의 `java = "21"`에서 읽는다).
- FE로 치면 `.nvmrc`로 Node 버전을 고정해 팀원 모두 같은 런타임으로 빌드하는 것과 같은 목적이다.

> [!note] 어디까지 같고 어디서 다른가
> **같은 점**: 레포를 패키지/모듈로 쪼개고, 버전을 루트 한곳에 모으고, 의존 그래프를 그리는 큰 그림은 모노레포와 같다.
> **다른 점**: Gradle은 모듈 의존을 `implementation`(내부용, 바깥에 안 보임) vs `api`(바깥에 공개)로 구분해 **컴파일 클래스패스 수준에서 경계를 강제**한다. 예컨대 JPA 타입을 특정 모듈 안에 `implementation`으로 숨기면 다른 계층은 아예 import조차 못 한다. pnpm workspace는 이 정도의 컴파일-레벨 경계 강제를 기본 제공하지 않는다.

## 주의점 / 트러블슈팅

- **`.kt` 파일에 주석이 없다.** kbap은 Kotlin 소스 주석을 전면 금지하는 레포다(이름과 구조로 의도를 드러내는 self-documenting 규약). 위 발췌 중 `.gradle.kts`·`.toml` 파일에 달린 주석은 예외로, 비-Kotlin 파일이라 허용된 것이다.
- **플랫폼 타입은 조용히 NPE를 낼 수 있다.** `-Xjsr305=strict`가 있어도, 애너테이션이 없는 Java API는 여전히 플랫폼 타입(`T!`)으로 넘어온다. 이런 값은 컴파일러가 봐주므로, 널이 들어오면 실행 중에 NPE가 난다. Java 라이브러리 경계의 값은 습관적으로 nullable(`?`)로 받아 두는 게 안전하다.
- **버전을 모듈에 직접 박지 말 것.** 새 라이브러리는 `libs.versions.toml`에 추가하고 `libs.*`로 참조한다. 모듈 `build.gradle.kts`에 버전 문자열을 하드코딩하면 단일 출처 원칙이 깨진다.
- **`buildSrc`를 고치면 전체 빌드 캐시가 무효화**돼 빌드가 느려질 수 있다(공통 설정을 한곳에 모은 대가). 컨벤션 플러그인은 자주 건드리지 않는다.

## 치트시트

```kotlin
// 널 안전 (예시)
val a: String  = "abc"   // 절대 null 아님 — null 대입은 컴파일 에러
val b: String? = null    // null 가능 — 접근 전 널 처리 강제

b.length      // 컴파일 에러 (널 처리 안 함)
b?.length     // 안전 호출: b가 null이면 결과도 null
b!!.length    // 강제 단언: b가 null이면 그 자리에서 NPE
b?.length ?: 0 // 엘비스: null이면 0
```

| 하고 싶은 것 | Gradle 명령 |
|---|---|
| 전체 컴파일 + 테스트 + 패키징 | `./gradlew build` |
| 특정 모듈만 테스트 | `./gradlew :app:api:test` |
| 모듈 목록 보기 | `./gradlew projects` |
| 산출물 정리 | `./gradlew clean` |

> 서버·배치 앱 실행(`bootRun`)과 진입점은 [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]]에서 다룬다.

## 용어집

- **바이트코드**: 소스를 JVM이 읽을 수 있게 번역한 중간 바이너리(`.class`). 특정 OS·CPU에 묶이지 않는다.
- **툴체인(toolchain)**: Gradle이 빌드에 쓸 JDK 버전을 로컬 환경과 무관하게 직접 확보하는 장치.
- **플랫폼 타입(`T!`)**: 널 여부가 불분명한, Java에서 넘어온 타입. 컴파일러가 널 검사를 봐주므로 실행 중 NPE 위험이 있다.
- **JSR-305**: Java의 널 관련 애너테이션 표준(`@Nonnull`/`@Nullable` 등). `-Xjsr305=strict`는 이걸 Kotlin 타입 제약으로 격상한다.
- **버전 카탈로그**: `gradle/libs.versions.toml`. 모든 라이브러리/플러그인 버전의 단일 출처.
- **BOM(Bill of Materials)**: 서로 호환되는 라이브러리 버전 묶음표. Spring Boot BOM이 스타터 버전을 자동 정렬해 주므로 카탈로그에 버전을 안 적는 항목이 많다.

---

## 체크리스트

- [ ] JVM은 바이트코드를 실행하는 런타임 엔진이고, Kotlin은 실행 전에 바이트코드로 컴파일된다는 것을 설명할 수 있다.
- [ ] TS 타입은 실행 시점에 지워지지만 JVM 타입은 실행 중에도 강제된다는 차이를 말할 수 있다.
- [ ] `String`과 `String?`의 차이, `?.`·`!!`·`?:`의 동작을 안다.
- [ ] `-Xjsr305=strict`가 Java 라이브러리 경계의 널까지 검사에 포함시킨다는 것을 안다.
- [ ] `settings.gradle.kts`(모듈 목차)와 `libs.versions.toml`(버전 단일 출처)의 역할을 구분한다.
