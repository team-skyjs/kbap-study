# 영속성 컨텍스트와 엔티티 매핑 — 객체와 DB 행을 잇는 중개자

> 작성: 2026-07-14 · 맥락: 3단계 JPA·영속성. 2단계에서 "UseCase 메서드가 트랜잭션 경계"라는 것까지 봤다. 이제 그 경계 **안에서** JPA가 Kotlin 객체를 DB 행으로, DB 행을 객체로 바꾸고(매핑), 그 사이를 **영속성 컨텍스트**가 중개하는 원리를 잡는다.
> 목표: "왜 코드에 `save()`가 안 보이는데 값이 저장되나", "왜 엔티티마다 id를 안 쓰나", "도메인 객체랑 엔티티는 왜 따로 있나"를 30분 뒤의 나도 바로 설명.

---

## 0. 한 줄 요약

**JPA는 `@Entity` 클래스 하나를 테이블 하나에, 프로퍼티를 컬럼에 매핑한다(엔티티 매핑). 트랜잭션이 열리면 그 안에서 조회한 엔티티는 `영속성 컨텍스트`라는 1차 캐시에 담기고, 필드를 바꾸기만 하면 트랜잭션이 끝날 때 JPA가 변경을 감지해 UPDATE를 자동으로 내보낸다(변경 감지 → flush). kbap은 여기에 더해 순수 도메인 객체와 JPA 엔티티를 분리하고, 둘 사이 변환을 엔티티 안 `toDomain()`/`from()`에 둔다.**

---

## 1. 핵심 개념

| 구분 | 엔티티(Entity) | 영속성 컨텍스트(Persistence Context) | 엔티티 매핑(Mapping) | 도메인↔엔티티 변환 |
|---|---|---|---|---|
| 정체 | DB 테이블 한 개와 짝지어진 클래스 | 트랜잭션 안에서 조회한 엔티티를 담아두는 1차 캐시 | 클래스↔테이블, 프로퍼티↔컬럼을 잇는 규칙 | 순수 도메인 객체와 JPA 엔티티를 서로 바꾸기 |
| 언제 | DB에 저장/조회할 데이터를 다룰 때 | `@Transactional` 메서드가 실행되는 동안 | `@Entity`/`@Column` 등 애너테이션으로 선언 | 저장(`from`)·조회 결과 반환(`toDomain`) 시점 |
| kbap에서 | `infra/persistence`의 `*JpaEntity` | 트랜잭션(=UseCase 메서드) 1개 수명 | `@Column(length=N)` 등 MySQL 기준 고정 | 엔티티 안 `toDomain()` / `companion object.from()` |
| FE 대응 | (직접 대응물 약함 — DB 스키마와 1:1) | React Query 캐시 (1번 비유 참고) | API 응답 타입 vs DB 스키마의 차이 | API 응답 타입 → 화면 상태 타입 매핑 |

## 2. 엔티티 매핑 — Kotlin 클래스 한 개가 테이블 한 개

**엔티티(entity)** 는 DB 테이블 하나와 짝지어진 클래스다. JPA(Java Persistence API, 객체를 관계형 DB에 저장하는 자바 표준 규격. kbap은 그 구현체인 **Hibernate**를 쓴다)는 `@Entity`가 붙은 클래스를 보고 "이 클래스는 이 테이블", "이 프로퍼티는 이 컬럼"이라는 지도를 만든다. 그래서 개발자가 SQL을 손으로 쓰지 않아도 객체를 저장하면 INSERT, 조회하면 SELECT가 나간다.

kbap의 `FoodJpaEntity`가 전형이다:

```kotlin
@Entity
@Table(
    name = "food",
    uniqueConstraints = [UniqueConstraint(name = "uq_food_korean_name", columnNames = ["korean_name"])],
)
class FoodJpaEntity(
    @Column(name = "korean_name", nullable = false, length = 255)
    var koreanName: String = "",

    @Column(name = "image_ref", length = 500)
    var imageRef: String? = null,
    …
) : BaseEntity() {
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodJpaEntity.kt:21-39`

- `@Entity` + `@Table(name = "food")` — 이 클래스는 `food` 테이블과 짝. 클래스 = 테이블.
- `@Column(name = "korean_name", nullable = false, length = 255)` — `koreanName` 프로퍼티는 `korean_name` 컬럼. `NOT NULL`, `VARCHAR(255)`. **컬럼 길이·null 여부를 MySQL 기준으로 여기서 못박는다** — 이게 kbap의 고정 규약이다(이 길이는 뒤에 Flyway 마이그레이션 SQL의 컬럼 정의와도 정확히 일치해야 한다 → [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]).
- `imageRef: String?` — Kotlin의 nullable 타입(`?`)이 그대로 `nullable` 컬럼이 된다. Kotlin의 널 안전이 DB 스키마까지 이어지는 셈([[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]]).
- `@UniqueConstraint(...)` — `korean_name`에 유니크 제약. 같은 한식 이름이 두 번 안 들어가게 DB가 막는다.

> [!note] FE의 "응답 타입"과는 다르다
> FE에서도 `type Food = { koreanName: string; imageRef: string | null }` 같은 타입을 쓴다. 비슷해 보이지만 **결정적 차이**가 있다: FE 타입은 "서버가 준 JSON의 모양"을 적은 것이고, 엔티티는 "DB 테이블의 실제 스키마"와 1:1이다. 그래서 엔티티에는 길이(`length=255`)·유니크·null 같은 **DB 제약**이 붙는다 — 화면이 아니라 저장소가 진짜 주인이다.

참고로 kbap은 컬렉션 값(다국어 번역 맵 등)을 `@JdbcTypeCode(SqlTypes.JSON)`으로 **JSON 컬럼 한 칸**에 통째로 넣기도 한다(`FoodJpaEntity.kt:47-53`). "한 프로퍼티 = 한 컬럼"이 기본이되, 이렇게 예외도 있다는 정도만 알아두면 된다.

## 3. 영속성 컨텍스트 — 트랜잭션 안의 1차 캐시

여기가 2단계에서 예고한 "`@Transactional`이 켜지면 안에서 무슨 일이 일어나나"의 답이다.

**영속성 컨텍스트(persistence context)** 는 트랜잭션이 열려 있는 동안 JPA가 관리하는 **엔티티 보관소(1차 캐시)** 다. 트랜잭션 안에서 엔티티를 조회하면 JPA는 그 엔티티를 이 보관소에 넣어두고("이건 내가 관리 중인 놈"), 같은 트랜잭션 안에서 같은 엔티티를 또 조회하면 **DB에 다시 안 가고 보관소에서 꺼내 준다**.

> 비유: **React Query 캐시**. 같은 쿼리 키를 두 번 조회하면 네트워크를 다시 안 타고 캐시가 답하는 것과 같은 발상이다. 변경도 곧장 반영하지 않고 모아뒀다 내보낸다는 점도 닮았다.
> **어디까지 같고 어디서 다른가**: React Query 캐시는 **컴포넌트 트리 전역**에서 살아 있고 **쿼리 키**로 접근한다. 영속성 컨텍스트는 **트랜잭션 하나의 수명**만큼만 살고(=UseCase 메서드가 끝나면 통째로 사라진다), 키가 아니라 **엔티티의 식별자(id)** 로 같은 것인지 판단하며, 변경을 자동 감지해 **flush(SQL 실행)** 로 내보낸다. RQ는 네가 `invalidate`/`setQueryData`로 손대야 하지만, 영속성 컨텍스트는 **필드를 바꾸기만 하면 알아서** 나간다(다음 절).

핵심은 **수명이 트랜잭션 1개**라는 점이다. `@Transactional` 메서드가 시작될 때 영속성 컨텍스트가 열리고, 그 메서드가 끝날 때(commit) 닫힌다. 그래서 이 보관소에서 조회한 엔티티는 트랜잭션 밖으로 나가면 "관리 대상"이 아니게 된다(이 사실이 로딩 전략과 만나 문제가 되는 지점은 [[8. LAZY 로딩과 N+1 문제]]에서 다룬다).

## 4. 변경 감지와 flush — 왜 `save()`가 안 보이나

2단계 노트를 보다가 이런 의문이 들었을 수 있다: `MemberProfileUseCase.completeOnboarding`에서 회원 프로필을 바꾸는데, DB에 UPDATE를 날리는 코드가 왜 안 보이지?

답이 **변경 감지(dirty checking)** 다. 영속성 컨텍스트는 엔티티를 조회할 때 그 **최초 상태를 몰래 스냅샷으로 떠둔다**. 그리고 트랜잭션이 끝날 무렵, 관리 중인 엔티티들의 현재 상태를 스냅샷과 비교해서 **바뀐 필드가 있으면 그에 맞는 UPDATE SQL을 자동으로 만들어 내보낸다**. 이 "쌓아둔 변경을 실제 SQL로 DB에 밀어내는 동작"을 **flush**라고 한다.

즉 흐름은 이렇다:

1. `@Transactional` 메서드 시작 → 영속성 컨텍스트 열림.
2. 엔티티 조회 → 보관소에 담기고 최초 상태 스냅샷.
3. 엔티티의 **필드 값만 바꿈**(예: `member.status = ...`). 이 순간엔 아직 SQL이 안 나간다.
4. 메서드 정상 종료 → commit 직전에 **flush**: 스냅샷과 비교해 바뀐 것만 UPDATE. → commit.

그래서 "값을 바꾸면 저장된다"는 감각이 성립한다. 명시적 `UPDATE`도, 대부분의 경우 명시적 `save()`도 필요 없다 — 트랜잭션이 경계이자 flush의 트리거이기 때문이다. (반대로 트랜잭션 중간에 예외가 나면 flush 자체가 일어나지 않거나 롤백되어 아무 흔적도 안 남는다 — 2단계 "전부 아니면 전무"의 실제 메커니즘이 이것이다.)

> [!tip] flush ≠ commit
> 헷갈리기 쉬운 둘: **flush**는 "쌓인 변경을 SQL로 DB에 내보냄"이고, **commit**은 "그 트랜잭션을 확정함"이다. 보통 commit 직전에 flush가 자동으로 일어나므로 한 몸처럼 보이지만, flush가 나갔어도 commit 전이면 아직 되돌릴 수 있다.

> [!note] 새로 만든 엔티티는 `save`/`persist`가 필요
> 변경 감지는 **이미 영속성 컨텍스트가 관리 중인**(=조회해 온) 엔티티에만 적용된다. `from(...)`으로 **새로 만든** 엔티티는 아직 보관소에 없으니, 리포지토리로 한 번 저장(`persist`/`save`)해 넣어야 관리가 시작된다. "조회해서 고치면 save 불필요, 새로 만들면 save 필요"로 기억하면 된다.

## 5. BaseEntity 규약 — id·시각·소프트삭제를 한곳에

kbap의 모든 엔티티는 `BaseEntity`를 상속한다. 그래서 `FoodJpaEntity`에는 `id` 선언이 안 보인다 — 공통 뼈대를 부모가 다 갖고 있기 때문이다.

```kotlin
@MappedSuperclass
@SQLRestriction("status = 'ACTIVE'")
abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long = 0

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, columnDefinition = "ENUM('ACTIVE','DELETED')")
    private var status: EntityStatus = EntityStatus.ACTIVE

    @CreationTimestamp
    val createdAt: LocalDateTime = LocalDateTime.MIN

    @UpdateTimestamp
    val updatedAt: LocalDateTime = LocalDateTime.MIN
    …
    fun delete() { status = EntityStatus.DELETED }
}
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/BaseEntity.kt:15-42`

- `@MappedSuperclass` — 이 클래스 자체는 테이블이 아니고, **상속한 자식 엔티티들이 이 필드들을 자기 테이블 컬럼으로 물려받는다**. "공통 컬럼 묶음"이라 보면 된다. 그래서 `FoodJpaEntity`가 `id`를 직접 안 써도 `food` 테이블엔 `id` 컬럼이 생긴다.
- `@Id @GeneratedValue(strategy = IDENTITY)` — 기본키. `IDENTITY`는 값 생성을 **DB의 AUTO_INCREMENT에 맡긴다**(MySQL이 새 행마다 1씩 증가시켜 부여).
- `@CreationTimestamp` / `@UpdateTimestamp` — 생성·수정 시각을 Hibernate가 자동으로 채운다. 모든 테이블이 "언제 만들어지고 언제 바뀌었나"를 공짜로 갖는다.
- `status` + `@SQLRestriction("status = 'ACTIVE'")` — **소프트 삭제(soft delete)** 의 핵심. 행을 진짜 DELETE 하지 않고 `status`를 `DELETED`로만 바꾼다(`delete()`). 그리고 `@SQLRestriction`이 이 엔티티를 조회하는 **모든 SELECT에 `WHERE status = 'ACTIVE'`를 자동으로 덧붙인다** — 그래서 평소 조회에는 삭제된 행이 애초에 안 딸려 온다. 데이터를 실제로 지우지 않으니 감사·복구가 가능하다.

정리하면 "왜 엔티티마다 id를 안 쓰나?" → id·시각·삭제상태라는 **모든 테이블의 공통 뼈대를 `BaseEntity` 한곳에 모아** 상속으로 재사용하기 때문이다. FE로 치면 여러 컴포넌트가 공유하는 베이스 props 타입을 `extends`로 물려받는 것과 비슷하다.

## 6. 도메인 ↔ 엔티티 변환 — 도메인은 JPA를 모른다

`FoodJpaEntity` 이름에 붙은 `Jpa`가 힌트다. kbap에는 **같은 "음식"을 표현하는 두 종류의 클래스**가 있다:

- `com.meogo.core.food.Food` — **순수 도메인 객체**. ORM·Spring을 전혀 모르는 순수 Kotlin. 비즈니스 규칙이 사는 곳.
- `com.meogo.infra.persistence.food.FoodJpaEntity` — **JPA 엔티티**. `@Entity`가 붙고 DB 저장이 목적.

이 둘을 잇는 변환을 **엔티티 클래스 안**에 둔다:

```kotlin
fun toDomain(): Food =
    Food.reconstitute(
        id = id,
        content = FoodContent(
            name = LocalizedText(korean = koreanName, translations = resolve(nameTranslations)),
            …
        ),
        …
    )

companion object {
    fun from(food: Food): FoodJpaEntity =
        FoodJpaEntity(
            koreanName = food.koreanName(),
            imageRef = food.imageRef,
            …
        )
}
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/food/FoodJpaEntity.kt:62-88` (본문 일부 생략)

- `toDomain()` — 엔티티(DB에서 읽어온 것)를 순수 도메인 객체 `Food`로 바꾼다. DB→도메인 방향.
- `companion object`의 `from(food)` — 반대로 도메인 객체를 저장용 엔티티로 바꾼다. 도메인→DB 방향. (`companion object`는 Kotlin에서 인스턴스 없이 부르는 정적 팩토리 자리 — `FoodJpaEntity.from(food)`처럼 쓴다.)
- **방향이 한쪽으로만 흐른다**: 변환 코드가 `infra`(엔티티) 쪽에 있으니 `infra`는 `core.food.Food`를 import 하지만, **`core`(도메인)는 `infra`나 JPA를 절대 import 하지 않는다**. 그래서 `Food`는 `@Entity` 없이 순수하게 남는다.

왜 이 고생을 하나? 도메인을 JPA에서 떼어놓기 위해서다. DB 저장 방식(JPA/Hibernate)이 바뀌어도 비즈니스 규칙(`core`)은 그대로고, 도메인 테스트에 DB가 필요 없다. 이게 2단계에서 본 **계층 분리**([[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]])의 영속 계층 버전이다. 도메인이 정의한 저장 인터페이스(port)를 `infra`의 어댑터가 구현하고, 그 경계에서 이 변환이 일어난다 — "도메인이 JPA를 모르게 두는" 이 구조를 4단계(아키텍처, ports & adapters)에서 본격적으로 다룬다.

> [!note] 연관관계도 매핑된다 (로딩은 다음 노트)
> `FoodJpaEntity`에는 다른 엔티티를 참조하는 `@OneToMany` 연관관계(`foodAvoidanceSubstances`)도 매핑돼 있다(`FoodJpaEntity.kt:58`). "엔티티가 다른 엔티티를 필드로 갖는" 이 관계를 **언제 실제로 DB에서 가져올지**(LAZY 로딩)와 그로 인한 성능 문제(N+1)는 → [[8. LAZY 로딩과 N+1 문제]]에서 이어진다. 이 노트는 "관계도 매핑 대상"이라는 사실까지만.

## 7. 트러블슈팅 / 주의점

- **트랜잭션 밖에서 엔티티를 쓰면 위험.** 영속성 컨텍스트는 트랜잭션과 함께 죽는다. 그래서 kbap은 트랜잭션 밖(컨트롤러 응답 등)으로는 엔티티가 아니라 **도메인 객체/DTO를 내보낸다**(`toDomain()`). 엔티티를 그대로 밖으로 흘리면, 트랜잭션이 닫힌 뒤 아직 안 불러온 연관을 건드리다 터진다 — 상세는 [[8. LAZY 로딩과 N+1 문제]].
- **소프트 삭제된 행은 "안 보일 뿐" 남아 있다.** `@SQLRestriction` 덕에 평소 조회엔 안 나오지만 테이블엔 그대로다. "지웠는데 유니크 제약에 걸린다" 같은 상황이 나올 수 있다(예: `korean_name`이 유니크인데 DELETED 행이 그 이름을 점유). 소프트 삭제 규약을 잊으면 헷갈리는 지점.
- **`var` vs `val`.** 엔티티 필드가 `var`인 건 변경 감지(dirty checking)로 값을 바꿔 저장하기 위해서다. 반면 도메인 `Food`는 불변(값을 바꾸면 새 객체) 지향 — 두 세계의 설계 철학이 다르다.
- **id 기본값 `0`.** `BaseEntity`의 `id: Long = 0`은 "아직 저장 안 된(=DB가 번호를 안 준) 새 엔티티"를 뜻한다. 저장되면 DB가 실제 id를 채운다. id가 0인지로 신규/기존을 판단하는 코드가 있을 수 있다.

## 8. 치트시트

```
# 매핑 (infra/persistence 의 *JpaEntity)
@Entity @Table(name="food")        # 클래스 = 테이블
@Column(name=.., length=255, nullable=false)  # 프로퍼티 = 컬럼 (MySQL 기준 길이/null 고정)
@JdbcTypeCode(SqlTypes.JSON)        # 컬렉션을 JSON 컬럼 한 칸에

# BaseEntity (모든 엔티티가 상속)
@MappedSuperclass                  # 이 클래스는 테이블 아님, 자식이 컬럼 물려받음
@Id @GeneratedValue(IDENTITY)      # PK = MySQL AUTO_INCREMENT
@CreationTimestamp / @UpdateTimestamp  # 생성/수정 시각 자동
@SQLRestriction("status='ACTIVE'") # 소프트삭제: 조회에 자동 WHERE, delete()는 status만 변경

# 영속성 컨텍스트 (트랜잭션 1개 수명)
조회 → 1차 캐시에 담김(+최초 스냅샷)
필드만 변경 → (아직 SQL 안 나감)
메서드 종료 → flush(변경 감지→UPDATE) → commit
# 조회해서 고치면 save 불필요 / 새로 from()한 건 save 필요

# 도메인↔엔티티 변환 (방향: infra→core 만)
entity.toDomain()                  # DB→도메인 (읽기)
FoodJpaEntity.from(domain)         # 도메인→DB (저장)   ← core는 JPA를 모른다
```

## 9. 용어집

- **엔티티(Entity)**: `@Entity`가 붙어 DB 테이블 하나와 매핑되는 클래스. kbap에선 `*JpaEntity`.
- **JPA / Hibernate**: JPA는 객체를 관계형 DB에 저장하는 자바 표준 규격, Hibernate는 kbap이 쓰는 그 구현체.
- **엔티티 매핑**: 클래스↔테이블, 프로퍼티↔컬럼을 애너테이션으로 잇는 것.
- **영속성 컨텍스트(Persistence Context)**: 트랜잭션 동안 엔티티를 담아두는 1차 캐시. 트랜잭션 1개 수명.
- **변경 감지(Dirty Checking)**: 조회 시 뜬 스냅샷과 현재 상태를 비교해 바뀐 필드의 UPDATE를 자동 생성하는 것.
- **flush**: 쌓아둔 변경을 실제 SQL로 DB에 내보내는 동작. commit 직전 자동 실행.
- **`@MappedSuperclass`**: 그 자체는 테이블이 아니고, 상속한 엔티티에 공통 컬럼을 물려주는 부모 클래스.
- **소프트 삭제(Soft Delete)**: 행을 실제로 지우지 않고 `status=DELETED`로만 표시. `@SQLRestriction`이 조회에서 자동 제외.
- **`@SQLRestriction`**: 해당 엔티티 조회 SQL에 항상 `WHERE` 조건을 덧붙이는 Hibernate 애너테이션. kbap은 `status='ACTIVE'`.
- **`toDomain()` / `from()`**: 엔티티↔도메인 객체 변환. 엔티티 쪽에 두어 도메인이 JPA를 모르게 유지.

## 10. 다음에 빠른 재현 체크리스트

1. "이 클래스는 어느 테이블?" → `@Entity @Table(name=..)`. 프로퍼티는 `@Column`. 길이·null은 MySQL 기준으로 여기서 고정.
2. "id·생성시각·삭제상태는 어디?" → 안 쓴다. `BaseEntity` 상속으로 공통 제공.
3. "삭제하면 행이 사라지나?" → 아니다. `status=DELETED`(소프트 삭제) + `@SQLRestriction`으로 조회에서 자동 제외.
4. "왜 `save()`가 안 보이는데 저장되나?" → 트랜잭션 안에서 조회한 엔티티는 필드만 바꾸면 flush 때 변경 감지로 UPDATE 자동. (새로 만든 건 save 필요.)
5. "flush와 commit 차이?" → flush = 변경을 SQL로 내보냄, commit = 트랜잭션 확정. commit 직전 flush 자동.
6. "도메인이랑 엔티티는 왜 둘?" → 도메인(core)을 JPA에서 떼어놓기 위해. 변환은 엔티티 안 `toDomain()`/`from()`, 방향은 infra→core 한쪽만.
7. (다음 노트 예고) 엔티티가 참조하는 다른 엔티티(`@OneToMany`)는 언제 가져오고, 그게 왜 성능 문제가 되나? → [[8. LAZY 로딩과 N+1 문제]].
