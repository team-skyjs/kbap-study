# 17. 홈 화면 조회 흐름 — 세 섹션을 한 응답으로 모으기

## 한 줄 요약

홈에 진입하면 **한 번의 요청**(`GET /api/v1/home`)으로 세 섹션 — 내 기피 성분, 인기 음식 5개, 내 최근 스캔 10개 — 을 프로필 언어로 함께 받는다. 로그인 안 했으면 인기 음식만(영어), 개인화 섹션은 **빈 배열**로 내려온다.

이 노트는 앞의 세 흐름과 성격이 다르다. 5a(온보딩·스캔)·5b(로그인)는 **쓰기**였지만 홈은 **읽기 하나**다. 그리고 여러 화면을 각각 부르는 대신 서버가 네 도메인의 데이터를 한 메서드 안에서 모아 내려준다(fan-in). FE로 치면 홈 화면이 `useAvoidances()` `usePopularFoods()` `useRecentScans()` 세 훅을 각각 부르는 대신, 서버가 그 세 쿼리를 하나의 응답으로 합쳐주는 셈이다.

## 계층 경계마다 — 여기서 모듈이 바뀌는 이유

### Controller → UseCase: 웹은 UseCase를 만들지 않고 주입받는다

```kotlin
class HomeController(
    private val homeQueryUseCase: HomeQueryUseCase,
) : HomeApi {
    override fun home(
        @AuthMemberIdOrNull memberId: Long?,
    ): ResponseEntity<BaseResponse<HomeResponse>> {
        val result = homeQueryUseCase.getHome(memberId)
        return ResponseEntity.ok(BaseResponse.ok(HomeResponse.from(result, authenticated = memberId != null)))
    }
}
```

- `HomeController.kt:13-14` — 컨트롤러는 `HomeQueryUseCase`를 **생성자로 받는다**. 직접 `new` 하지 않는다. 이 조립을 대신 해주는 게 IoC 컨테이너다. → [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]], [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]
- `HomeController.kt:18` — 반환 타입이 `ResponseEntity<BaseResponse<HomeResponse>>`. `BaseResponse`는 이 레포의 모든 응답을 감싸는 공통 봉투(성공 여부·payload). FE 응답 인터셉터에서 `res.data.payload`만 꺼내 쓰는 것과 같은 규약.
- `HomeController.kt:20` — 컨트롤러가 하는 유일한 판단은 `authenticated = memberId != null` 한 줄. "누구냐"는 리졸버가 정하고, "무엇을 조회하냐"는 UseCase가 하고, 컨트롤러는 그 둘을 이어 붙여 web 형태로 포장만 한다.

### 선택 인증 리졸버 — note 16 `@AuthMemberId`의 형제

note 16의 `@AuthMemberId`는 **필수**였다(헤더 없으면 401). 홈의 `@AuthMemberIdOrNull`은 그 **선택 버전**이다.

```kotlin
override fun resolveArgument(...): Long? {
    val request = webRequest.getNativeRequest(HttpServletRequest::class.java) ?: return null
    val header = request.getHeader(AUTHORIZATION_HEADER) ?: return null
    if (!header.startsWith(BEARER_PREFIX)) return null
    return tokenParser.parseAccessToken(header.removePrefix(BEARER_PREFIX)).memberId
}
```

- `AuthMemberIdOrNullArgumentResolver.kt:23-25` — 헤더가 없거나 `Bearer ` 접두가 아니면 조용히 `null`을 반환한다. 이 `null`이 곧 "비회원"이다.
- `AuthMemberIdOrNullArgumentResolver.kt:26` — 그러나 `Bearer ` 접두가 붙어 있으면 `parseAccessToken`을 그대로 통과시킨다. 여기서 토큰이 위조·만료면 **예외가 던져져 401**이 된다. 즉 "헤더 없음 = 비회원"과 "가짜 토큰 = 거절"은 다르게 처리된다. (아규먼트 리졸버가 무엇인지, 토큰 파싱이 왜 여기서 일어나는지는 → [[16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]])

> [!tip] FE 관점 — 왜 위조 토큰을 비회원으로 폴백하지 않나
> 클라이언트가 만료된 토큰을 계속 들고 홈만 조용히 보는 상황을 막기 위해서다. "토큰을 보냈다"는 건 로그인 상태라는 신호이므로, 그 신호가 깨졌으면 401로 재로그인을 유도한다. 반대로 아예 헤더가 없으면 애초에 비회원 화면을 기대하는 것이라 그대로 비회원으로 응답한다.

### UseCase → 도메인 port들: fan-in read

```kotlin
@Transactional(readOnly = true)
fun getHome(memberId: Long?): HomeResult {
    val member = memberId?.let { memberRepository.findById(it) }
    val lang = member?.profile?.appLanguage ?: LanguageCode.EN
    val avoidedCodes = avoidedSubstanceProvider.avoidedCodes(member?.id)
    val avoidedRefs = avoidedCodes.map { AvoidanceSubstanceCodeRef(it.name) }.toSet()

    return HomeResult(
        avoidedSubstances = avoidanceSubstanceRepository.findByCodes(avoidedCodes)
            .map { AvoidedSubstanceView(code = it.code.name, name = it.displayName(lang)) },
        popularFoods = foodRepository.findRandomReady(POPULAR_SIZE)
            .map { FoodSummaryView.from(it, lang, avoidedRefs) },
        recentScans = member?.id?.let { id ->
            val recentIds = scanHistoryRepository.findRecentReadyFoodIds(id, RECENT_SCAN_SIZE)
            val foodsById = foodRepository.findAllReadyByIds(recentIds).associateBy { it.id }
            recentIds.mapNotNull { foodsById[it] }.map { FoodSummaryView.from(it, lang, avoidedRefs) }
        }.orEmpty(),
    )
}
```

- `HomeQueryUseCase.kt:17-23` — 이 UseCase는 생성자에서 **5개 port에만** 의존한다(member·food·scan·avoidance repository + avoidedSubstanceProvider). 전부 인터페이스이고, 실제 DB 구현(adapter)은 `infra/persistence`에 있다. 도메인은 "무엇을 조회할지"만 알고 "어떻게 조회할지(JPA)"는 모른다. → [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]
- `HomeQueryUseCase.kt:26-27` — 언어 결정: 회원 프로필의 `appLanguage`, 없으면(비회원·온보딩 미완료) `EN`. 요청 파라미터로 언어를 받지 않는다 — 프로필이 단일 출처.
- `HomeQueryUseCase.kt:24` — `@Transactional(readOnly=true)`. 쓰기가 하나도 없는데 왜 트랜잭션을 여나? 여러 port 조회를 **한 스냅샷·한 커넥션** 안에서 일관되게 읽고, readOnly 힌트로 JPA가 변경 감지(dirty checking, [[7. 영속성 컨텍스트와 엔티티 매핑]] 참고)를 끄게 하기 위해서다(불필요한 flush 비용 제거). → [[6. 설정과 프로필, 트랜잭션 첫걸음]]

> [!info] member·food·scan·avoidance 네 컨텍스트를 어디서 엮나
> 이 네 도메인은 서로를 직접 참조하지 않는다(경계 격리). 이들을 조합하는 유일한 곳이 **application 계층인 이 UseCase**다. 도메인끼리 엮이지 않게 하고 조합은 위층에서만 하는 게 모듈러 모놀리스 규칙이다. → [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]

## 최근 스캔 — N+1을 피하는 조회 패턴

`recentScans` 블록(`HomeQueryUseCase.kt:36-40`)이 이 노트에서 가장 눈여겨볼 부분이다.

1. `findRecentReadyFoodIds(id, 10)` — 스캔 이력에서 **foodId 목록만** 최신순으로 뽑는다(음식 본문은 아직 안 가져옴).
2. `findAllReadyByIds(recentIds)` — 그 id들을 **한 번의 쿼리로 batch 조회**하고 `associateBy { it.id }`로 `Map<id, Food>`을 만든다.
3. `recentIds.mapNotNull { foodsById[it] }` — 원래의 최신순 id 순서를 기준으로 Map에서 꺼내 **순서를 복원**한다.

핵심은 2번이다. id마다 `findById`를 10번 부르면 쿼리가 10번 나간다(N+1). 대신 한 번에 묶어 가져오고 메모리에서 매칭한다. → [[8. LAZY 로딩과 N+1 문제]]

3번이 필요한 이유: batch 조회(`findAllReadyByIds`)는 결과 순서를 보장하지 않는다(테스트가 이를 `.shuffled()`로 일부러 뒤섞어 검증한다, `HomeQueryUseCaseTest.kt:50`). 그래서 "최신순"이라는 의미 있는 순서는 스캔 이력이 준 `recentIds` 순서로 다시 세운다.

도메인 `Food`를 web `FoodSummaryResponse`로, 성분 코드를 언어별 이름으로 바꾸는 변환(`displayName(lang)`)은 → [[7. 영속성 컨텍스트와 엔티티 매핑]]

## 요청 / 응답 JSON

**요청** (회원)

```
GET /api/v1/home
Authorization: Bearer eyJhbGciOi...   # 선택. 없으면 비회원
```

**응답 200 — 회원**

```json
{
  "success": true,
  "payload": {
    "authenticated": true,
    "avoidedSubstances": [
      { "code": "EGG", "name": "달걀" }
    ],
    "popularFoods": [
      { "foodId": 12, "name": "김치찌개", "koreanName": "김치찌개",
        "imageRef": "foods/12.jpg", "spiciness": 2, "overallRiskStatus": "SAFE" }
    ],
    "recentScans": [
      { "foodId": 7, "name": "계란말이", "koreanName": "계란말이",
        "imageRef": null, "spiciness": 0, "overallRiskStatus": "DANGER" }
    ]
  }
}
```

**응답 200 — 비회원** (`Authorization` 헤더 없음)

```json
{
  "success": true,
  "payload": {
    "authenticated": false,
    "avoidedSubstances": [],
    "popularFoods": [ /* 영어 이름, 최대 5개 */ ],
    "recentScans": []
  }
}
```

**응답 401** — 헤더는 있는데 토큰이 위조·만료: `{ "success": false, ... }`

> [!warning] 스펙과 다름 — 비회원 개인화 섹션은 `null`이 아니라 **빈 배열**
> spec의 US2 AS1은 "기피 성분과 최근 스캔은 **null**로", `HomeResponse.kt:11-12`의 `@Schema` 설명도 "false면 개인화 섹션이 **null**"이라 써 있다. 하지만 **실제 코드는 빈 배열을 내려준다**:
> - `HomeResponse.kt:17,21` — `avoidedSubstances`·`recentScans`가 non-nullable `List<...>`(널 불가 타입).
> - `HomeQueryUseCase.kt:40` — `recentScans`를 `.orEmpty()`로 항상 리스트로 채운다(비회원은 빈 리스트).
> - 같은 레포의 `HomeApi.kt:26` Swagger 설명은 오히려 코드와 일치한다: "모든 배열 필드는 **null을 내려주지 않는다** — 값이 없으면 빈 배열".
>
> 즉 문서 두 곳(spec·`@Schema`)이 서로 모순이고, 코드는 **빈 배열** 편이다. `HomeGuestTest.kt:47-50`이 이를 못박는다(`isNull shouldBe false`, `isEmpty shouldBe true`).
> **→ 클라이언트는 `avoidedSubstances == null` 같은 null 분기를 하면 안 된다.** 대신 `authenticated` 플래그로 개인화 영역 표시 여부(가입 유도 블러 등)를 판단한다.

## forward / 보류

- **인기 음식은 현재 무작위**다(`findRandomReady`). 인기도 지표가 쌓이기 전 임시 구현으로, 응답 형태(`FoodSummaryResponse`)가 메뉴 목록·검색과 동일해서 나중에 정렬만 실제 인기도로 바뀌어도 클라이언트는 수정할 필요가 없다(`HomeApi.kt:34-35` 문서 근거).
- 홈은 5개·10개 **고정 크기** fan-in이라 커서 페이징이 없다. 메뉴 목록의 커서 페이징(kb-63)과는 접점이 없어 여기서 링크하지 않는다.

## 치트시트

- 진입점: `GET /api/v1/home`, `@AuthMemberIdOrNull`(선택 인증) → 없으면 비회원, 가짜 토큰이면 401.

- 최근 스캔: id만 조회 → batch 음식 조회 → id 순서 복원(N+1 회피).
