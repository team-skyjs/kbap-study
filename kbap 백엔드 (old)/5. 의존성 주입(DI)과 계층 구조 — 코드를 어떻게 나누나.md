# 5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나

> [!summary] 한 줄 요약
> [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다|컨테이너가 만들어 둔 Bean]]들을 **서로의 생성자에 꽂아 넣는 것**이 DI(의존성 주입)다. 그리고 kbap는 코드를 Controller → UseCase → 도메인 → 영속의 **계층**으로 나눠, 각 층이 아래 층을 **인터페이스(port)로만** 알게 한다. 그래서 구현을 갈아끼워도 위 층은 안 바뀐다.

앞 노트에서 "컨테이너가 객체(Bean)를 만들어 보관한다"까지 봤다. 이 노트는 그다음 질문 두 개를 잡는다. **(1)** 만들어 둔 Bean들을 어떻게 서로 연결하나(= DI). **(2)** 애초에 코드를 왜 여러 덩어리로 쪼개 두나(= 계층 구조). 둘은 한 몸이다 — 계층으로 쪼개 놨으니 DI로 다시 이어야 한다.

---

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 (비유, 완전 동치 아님) |
|---|---|---|
| DI (의존성 주입) | 필요한 부품을 **내가 만들지 않고 밖에서 받는 것** | `props`/`useContext`로 의존을 내려받기 |
| 생성자 주입 | 그 "받기"를 **클래스 생성자 파라미터**로 하는 방식 | 컴포넌트가 필요한 값을 전부 props로 요구하는 것 |
| 의존성(dependency) | A가 일하려면 B가 있어야 할 때, B가 A의 의존성 | 훅이 쓰는 다른 훅/서비스 |
| 인터페이스 (port) | "무엇을 할 수 있는가"만 적은 계약. 구현은 없음 | TypeScript `interface` / 함수 타입 시그니처 |
| 구현체 (adapter) | 그 계약을 실제로 채운 클래스 | 그 인터페이스를 만족하는 실제 함수 |
| 계층(layer) | 역할이 다른 코드를 위아래로 나눈 층 | 화면 컴포넌트 / 커스텀 훅 / 순수 유틸의 분리 |

## 원리 1 — DI란: 내가 안 만들고 받는다

FE에서 어떤 훅이 API 클라이언트를 쓴다고 하자. 보통 두 가지로 구했다.

```tsx
// 예시 (실코드 아님)
function useProfile() {
  const api = new ApiClient();        // (A) 내가 직접 만든다
  // 또는
  const api = useContext(ApiContext); // (B) 위에서 내려준 걸 받는다
}
```

(A)는 `useProfile`이 `ApiClient`를 **직접 만든다** — 그래서 `ApiClient` 만드는 법이 바뀌면 `useProfile`도 바뀌고, 테스트할 때 가짜 클라이언트로 못 바꾼다. (B)는 **받아 쓴다** — 만드는 책임이 밖으로 나갔다. 이 (B)가 바로 DI의 감각이다.

스프링은 이 "받기"를 **생성자 파라미터**로 한다. 클래스가 필요한 것들을 생성자에 나열해 두면, 컨테이너가 서버 뜰 때 그 자리에 맞는 Bean을 찾아 넣어 준다. 코드는 `new`를 한 번도 쓰지 않는다.

```kotlin
@Service
class MemberProfileUseCase(
    private val memberRepository: MemberRepository,
)
```
`application/client/src/main/kotlin/com/meogo/application/client/member/MemberProfileUseCase.kt:19-22`

- `@Service`: "이 클래스를 Bean으로 등록하라"는 표시(이 표시의 의미와 종류는 [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]에서 정의).
- `(private val memberRepository: MemberRepository)`: **생성자**다. "나는 `MemberRepository` 하나가 있어야 일할 수 있다"고 선언만 했다.
- 이 클래스는 `MemberRepository`를 **어디서도 `new` 하지 않는다.** 서버가 뜰 때 컨테이너가 알맞은 구현 Bean을 이 자리에 꽂아 준다.

> [!tip] 코틀린 문법 하나
> 코틀린은 생성자 파라미터에 `val`을 붙이면 그게 곧 클래스의 프로퍼티가 된다. 그래서 위 4줄이 "필드 선언 + 생성자 + 대입"을 한꺼번에 한다. 타입 얘기는 [[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]] 참고.

### 비유: props와 어디까지 같고 어디서 다른가

생성자 주입은 **"이 컴포넌트는 이 props들이 반드시 있어야 렌더된다"** 와 거의 같다. 부품 목록을 스스로 만들지 않고 바깥에 요구한다는 점에서 동일하다.

**다른 점 두 가지.** ① props는 부모 컴포넌트가 매 렌더마다 직접 넘긴다. 생성자 주입은 **넘기는 주체가 사람이 아니라 컨테이너**이고, **서버 부팅 때 딱 한 번** 꽂고 끝이다(매 요청마다 다시 안 꽂는다). ② props는 "무슨 값을 넘길지" 부모가 안다. DI는 **타입만 보고 컨테이너가 알아서** 맞는 Bean을 찾아 넣는다 — 누가 넣어 주는지 코드에 안 나온다.

> [!info] `@Autowired`가 왜 안 보이나
> 스프링 예제에는 `@Autowired`가 붙곤 하지만 kbap 코드엔 없다. **생성자가 하나뿐이면 스프링이 그 생성자를 자동으로 주입에 쓴다** — Spring 4.3부터 `@Autowired`를 생략해도 된다([공식 문서](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)). 코틀린 클래스는 주 생성자 하나가 기본이라 자연히 생략된다.

## 원리 2 — 왜 구체 클래스가 아니라 인터페이스에 의존하나

위 코드에서 `MemberProfileUseCase`가 받는 `MemberRepository`는 **인터페이스**다 — DB를 실제로 어떻게 만지는지는 한 줄도 없고, "무엇을 할 수 있는지"만 적혀 있다.

```kotlin
interface MemberRepository {
    fun findById(id: Long): Member?
    fun update(member: Member): Member
    fun increaseScanCount(memberId: Long)
    // …
}
```
`core/member/src/main/kotlin/com/meogo/core/member/MemberRepository.kt:3-15`

- 몸통(`{ }` 안 구현)이 없다. `findById`를 "할 수 있다"는 **계약**만 있다.
- 실제로 DB를 만지는 코드는 **다른 모듈**의 구현체에 있다.

```kotlin
@Repository
class MemberRepositoryAdapter(
    private val memberJpaRepository: MemberJpaRepository,
) : MemberRepository {
    override fun findById(id: Long): Member? = findActive(id)?.toDomain()
    // …
}
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/member/MemberRepositoryAdapter.kt:12-16`

- `: MemberRepository` — 이 클래스가 위 인터페이스 계약을 **실제로 채운다**.
- `@Repository`도 Bean 표시의 한 종류다. 그래서 이 구현체도 컨테이너가 만들어 관리한다.

**연결이 일어나는 순간:** 컨테이너는 `MemberProfileUseCase`를 만들 때 "`MemberRepository` 타입이 필요하네" 하고, 그 타입을 만족하는 Bean(`MemberRepositoryAdapter`)을 찾아 꽂는다. `MemberProfileUseCase`는 자기에게 꽂힌 게 어떤 구현인지 **모른다.** 계약(`findById`, `update`…)만 믿고 부른다.

### 그래서 뭐가 좋은가

- **구현을 갈아끼워도 위 층은 무변경.** DB를 JPA에서 다른 걸로 바꾸고 싶으면 `MemberRepository`를 구현한 새 클래스를 만들어 Bean으로 등록만 하면 된다. `MemberProfileUseCase` 코드는 한 글자도 안 바뀐다.
- **테스트할 때 가짜를 꽂을 수 있다.** 진짜 DB 없이, `findById`가 정해진 `Member`를 돌려주는 가짜 `MemberRepository`를 만들어 생성자에 넣으면 UseCase 로직만 따로 검증된다. (A처럼 안에서 `new` 했으면 이게 불가능하다.)

> [!note] 여기선 "인터페이스에 의존하고 구현은 갈아끼운다"까지만
> 도메인(`core`)이 인터페이스를 **소유**하고 영속(`infra`)이 그걸 **구현**하는 이 방향 뒤집기(port/adapter, "왜 화살표가 이렇게 향하나")는 **4단계**에서 다룬다. 지금은 "위 층은 인터페이스만 알고, 실제 구현은 런타임에 컨테이너가 꽂는다"는 사실만 챙기면 된다.

## 원리 3 — 계층 구조: 코드를 왜 층으로 나누나

kbap는 요청을 처리하는 코드를 역할별로 네 층에 나눈다.

| 층 | 하는 일 | 하면 안 되는 일 | FE 대응 (비유) |
|---|---|---|---|
| **Controller** | HTTP 요청/응답을 받고 돌려줌. URL·상태코드·JSON 담당 | 비즈니스 규칙 판단 | 화면 컴포넌트 (이벤트 받고 화면 그림) |
| **UseCase** | 한 작업을 **조율**. 여러 단계를 순서대로 부르고 [[6. 설정과 프로필, 트랜잭션 첫걸음|트랜잭션 경계]]를 그음 | HTTP도 DB SQL도 직접 안 만짐 | 커스텀 훅 (컴포넌트와 데이터 사이 조율) |
| **도메인(core)** | 순수한 규칙·계산. "닉네임은 공백이면 안 된다" 같은 판단 | 스프링·DB를 아예 모름(Spring-free) | 순수 유틸 함수 (입력→출력, 부수효과 없음) |
| **영속(infra)** | 실제로 DB를 읽고 씀 | 규칙 판단 | fetch/스토리지 접근 코드 |

**비유가 어디까지 같고 어디서 다른가:** FE에서도 "화면 컴포넌트 / 커스텀 훅 / 순수 유틸"로 관심사를 나누는 감각과 같다. 다른 점은 **강제력**이다. FE에선 훅이 실수로 `fetch`를 직접 불러도 그냥 돌아간다. kbap는 이 경계를 **모듈로 물리적으로 갈라 놓고**(도메인 모듈엔 스프링·JPA 라이브러리 자체가 없음) 어기면 **빌드가 깨지는 테스트**(ArchUnit — "어느 패키지가 어느 패키지를 import하면 안 된다" 같은 아키텍처 규칙을 검사하는 테스트 라이브러리)로 막는다. 규칙이 아니라 벽이다.

핵심은 **의존 방향이 한쪽으로만 흐른다**는 것이다. 위 층이 아래 층을 부르지, 아래가 위를 부르지 않는다. 그리고 UseCase→영속은 **직접**이 아니라 **인터페이스(port)를 사이에 두고** 이어진다(원리 2). 그래서 제일 중요한 도메인 규칙이 DB나 웹 프레임워크에 묶이지 않는다.

## 한 요청이 계층을 타는 그림

`PATCH /api/v1/members/me` (프로필 수정) 요청 하나가 어떻게 아래로 흐르는지 보자. **각 층이 다음 층을 생성자 주입으로 받아** 이어져 있다.

```
요청 ─▶ MemberController ─▶ MemberProfileUseCase ─▶ MemberRepository(인터페이스)
         (HTTP 받기)          (작업 조율)             └─ 런타임엔 MemberRepositoryAdapter ─▶ DB
```

**Controller가 UseCase를 주입받는다:**

```kotlin
@RestController
@RequestMapping(ApiPaths.V1 + "/members")
class MemberController(
    private val memberProfileUseCase: MemberProfileUseCase,
    private val memberRankingUseCase: MemberRankingUseCase,
) : MemberApi {
```
`app/api/src/main/kotlin/com/meogo/app/api/member/MemberController.kt:13-18`

- `@RestController`도 Bean 표시의 한 종류(HTTP를 받는 Bean).
- 생성자로 UseCase **두 개**를 받는다 — 원리 1과 똑같은 생성자 주입. Controller는 UseCase를 `new` 하지 않는다.

**Controller는 받은 걸 UseCase에 넘기고 결과를 포장만 한다:**

```kotlin
    override fun updateProfile(
        @AuthMemberId memberId: Long,
        @RequestBody request: ProfileUpdateRequest,
    ): ResponseEntity<BaseResponse<Unit>> {
        memberProfileUseCase.update(request.toInput(memberId))
        return ResponseEntity.ok(BaseResponse.ok(Unit))
    }
```
`app/api/src/main/kotlin/com/meogo/app/api/member/MemberController.kt:41-47`

- Controller는 **규칙 판단을 안 한다.** 요청을 UseCase 입력으로 바꿔(`toInput`) 넘기고, 돌아온 걸 HTTP 응답으로 포장(`ResponseEntity.ok`)할 뿐이다.
- 실제 일(회원 찾고, 닉네임 검증하고, 저장)은 `memberProfileUseCase.update(...)` 안에서 벌어진다 — 그게 UseCase 층의 책임이다(`MemberProfileUseCase.kt:38-53`).

여기까지가 "층이 나뉘어 있고, 생성자 주입으로 이어진다"는 그림이다. **각 단계 안에서 실제로 무슨 일이 벌어지는지**(도메인이 어떻게 검증하고 영속이 어떻게 저장하는지)를 코드로 끝까지 따라가는 건 **5단계 실코드 흐름 노트**에서 한다.

## 주의점 / 트러블슈팅

- **순환 의존을 만들지 마라.** A가 B를 생성자 주입받고 B가 다시 A를 주입받으면, 컨테이너가 "누구부터 만들지" 못 정해 부팅이 실패한다(`BeanCurrentlyInCreationException` 류). 계층 방향(위→아래 한 방향)을 지키면 자연히 안 생긴다.
- **필요한 Bean이 없으면 부팅 때 터진다, 요청 때가 아니라.** `MemberRepository`를 구현한 Bean이 하나도 없으면 서버가 아예 안 뜬다. FE의 "이 훅 부를 때 터지는" 런타임 에러와 달리 **부팅 시점에** 조립이 검증된다 — 뜨기만 하면 배선은 맞다는 뜻이라 오히려 안심.
- **후보 Bean이 둘 이상이면 애매해서 터진다.** 한 인터페이스를 구현한 Bean이 둘이면 컨테이너가 어느 걸 꽂을지 못 정한다(`NoUniqueBeanDefinitionException`). 지금 kbap는 port마다 구현이 하나라 문제없지만, 개념으로 알아 둘 것.
- **생성자 주입을 기본으로 써라.** 스프링엔 필드 주입(`@Autowired` 필드) 같은 다른 방식도 있지만, 생성자 주입은 "필요한 의존이 생성자에 다 드러나고", "한 번 꽂히면 못 바뀌고(`val`)", "테스트에서 가짜 넣기 쉽다"는 이점이 있다. kbap는 전부 생성자 주입이다.

## 치트시트

```kotlin
// Bean 선언 + 생성자 주입 = 한 덩어리
@Service                                   // "나를 Bean으로 등록"
class SomethingUseCase(
    private val repo: SomethingRepository, // "일하려면 이게 필요" → 컨테이너가 꽂음
) {
    fun doIt() = repo.findById(1L)         // new 없이 그냥 씀
}
```

| 상황 | 이렇게 |
|---|---|
| Bean에 다른 Bean이 필요하다 | 생성자 파라미터로 선언. `@Autowired` 안 붙여도 됨(생성자 1개면 자동) |
| 구현을 나중에 바꾸고 싶다 | 위 층은 **인터페이스**를 주입받게 하고, 구현체를 Bean으로 등록 |
| 테스트에서 진짜 DB 없이 UseCase만 보고 싶다 | 인터페이스의 가짜 구현을 만들어 생성자에 직접 넣기 |
| "이 요청 어느 층에?" | HTTP=Controller · 조율=UseCase · 규칙=도메인 · DB=영속 |
| 부팅 때 `NoSuchBeanDefinition` | 그 타입을 구현한 Bean이 없음 → 구현체에 Bean 표시 붙었는지 확인 |

---

## 용어집

- **DI (Dependency Injection, 의존성 주입)**: 객체가 필요로 하는 다른 객체를, 그 객체가 직접 만들지 않고 밖에서 넣어 주는 것.
- **생성자 주입**: DI를 클래스 생성자 파라미터로 하는 방식. kbap의 기본.
- **의존성(dependency)**: A가 동작하려면 B가 있어야 할 때의 B.
- **인터페이스(port)**: 구현 없이 "무엇을 할 수 있는가"만 정의한 계약.
- **구현체(adapter)**: 인터페이스 계약을 실제로 채운 클래스.
- **계층(layer)**: 역할별로 나눈 코드 층(Controller/UseCase/도메인/영속).
- **UseCase**: 한 작업을 조율하는 계층. 여러 단계를 부르고 트랜잭션 경계를 긋는다.
