# 9. Flyway 마이그레이션 — 스키마를 코드로 관리하기

> 테이블을 DB 콘솔에서 손으로 만들지 않는다. **버전을 매긴 SQL 파일**을 레포에 쌓아 두면, 어느 환경이든(내 로컬·CI·운영) 그 파일들을 순서대로 돌려 **똑같은 스키마를 재현**한다. 스키마도 코드처럼 버전 관리하는 것 — 그게 Flyway다.

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 |
|---|---|---|
| 마이그레이션(migration) | 스키마 변경 한 덩어리를 담은 SQL 파일 하나 | 되돌릴 수 없는 "한 커밋" — 순서대로 쌓이는 변경 이력 |
| Flyway | 마이그레이션 파일을 순서대로 적용하고 "무엇을 이미 적용했는지" 기록/관리하는 도구 | `package-lock.json`을 관리하는 패키지 매니저에 가까움(적용 이력을 잠가둠) |
| 버전(version) | 파일명 앞부분 `V...` — 적용 순서를 정하는 키 | 마이그레이션의 정렬 키(kbap은 timestamp) |
| 스키마 owner | 스키마를 만들/바꿀 **권한을 가진 단 하나의 실행 파일** | 여러 앱이 한 DB를 봐도 마이그레이션은 한 곳만 |
| out-of-order | 늦게 머지된 과거 버전도 뒤늦게 적용을 허용하는 옵션 | 브랜치 머지 순서와 버전 순서가 어긋나도 부팅 거부 안 함 |
| checksum | 적용된 파일 내용의 지문 — 나중에 바뀌면 Flyway가 감지 | 이미 적용한 파일은 "동결"됐다는 걸 강제하는 안전장치 |

## 왜 필요한가 — FE엔 없던 문제

프론트에서 상태는 앱을 껐다 켜면 사라진다. 백엔드의 DB는 **끄지 않고 계속 쌓이는 것**이라, 테이블 구조(스키마)를 바꾸는 일이 곧 "이미 사람들의 데이터가 들어있는 창고의 선반 배치를 바꾸는 일"이 된다. 손으로 `ALTER TABLE`을 치면:

- 내 로컬 DB엔 적용됐는데 동료 DB엔 안 됨 → "내 컴퓨터에선 되는데요"의 DB 버전.
- 운영 배포 때 무슨 SQL을 어떤 순서로 돌렸는지 아무도 기록을 안 함.

마이그레이션은 이 변경들을 **레포 안 SQL 파일**로 만들어 코드와 함께 커밋한다. 앱을 새 DB에 올리면 Flyway가 `db/migration/` 폴더의 파일을 **버전 순서대로** 전부 돌려 스키마를 처음부터 재구성한다. 한 번 적용한 파일은 이력 테이블(`flyway_schema_history`)에 기록해 두고 **두 번 돌리지 않는다** — 그래서 파일은 "추가만 하고 고치지 않는" 로그처럼 쌓인다.

> [!tip] 비유 — Git 커밋 로그
> 마이그레이션 파일 하나 = 되돌릴 수 없는 커밋 하나. 새 변경은 **새 파일(=새 커밋)** 로 앞에 쌓지, 옛날 파일을 고쳐 쓰지 않는다.
> **어디까지 같고 어디서 다른가**: Git은 커밋을 rebase/amend로 고쳐 쓸 수 있지만, 이미 적용된 마이그레이션은 checksum으로 동결돼 **수정 자체가 금지**된다(고치면 부팅이 거부됨). 되돌리기(rollback)도 Git처럼 공짜가 아니라 "되돌리는 새 마이그레이션"을 또 써야 한다.

kbap의 실제 `db/migration/` 폴더는 이렇게 파일이 시간순으로 쌓여 있다(발췌):

```
V2026.06.29.20.35.02__create_scan_tables.sql
V2026.06.29.20.35.03__create_food_tables.sql
V2026.07.08.16.49.46__create_member_tables.sql
V2026.07.09.21.45.01__drop_menu_scan_tables.sql
V2026.07.13.00.19.27__add_member_ranking_counts.sql
```
`app/api/src/main/resources/db/migration/`

- 파일명은 `V{버전}__{설명}.sql` 형식. `V`와 설명 사이는 **언더스코어 두 개**(`__`).
- `create_...`로 테이블을 만들고, 나중에 `drop_...`·`add_...`로 바꾼다 — **앞 파일을 고치는 게 아니라 뒤에 새 파일을 붙인다**.

## kbap의 버전 규칙 — 정수 대신 timestamp

Flyway의 흔한 예시는 `V1__`, `V2__`, `V3__`처럼 정수를 쓴다. 문제는 팀이 브랜치를 나눠 일할 때다: A 브랜치와 B 브랜치가 각자 "다음은 `V11`"이라고 잡으면, 둘 다 머지될 때 `V11`이 두 개가 되어 **버전 번호 머지 충돌**이 난다.

kbap은 이걸 없애려고 **파일 생성 시각을 버전으로** 쓴다(고정 규약, KB-44):

```
V2026.07.13.00.19.27__add_member_ranking_counts.sql
  └── 2026-07-13 00:19:27 에 만든 파일이라는 뜻 (각 파트 두 자리 zero-pad)
```

시각은 사람마다 다르니 두 브랜치가 같은 버전을 잡을 일이 거의 없다. 대신 **머지 순서와 버전 순서가 어긋날 수** 있다 — 먼저 만든(=버전이 과거인) 파일이 나중에 머지되면, 이미 더 최신 버전이 적용된 DB에 "과거 버전"이 뒤늦게 들어온다. 정석 Flyway는 이걸 "순서 위반"으로 보고 부팅을 거부하는데, kbap은 이를 정상으로 허용한다:

```yaml
spring:
  flyway:
    out-of-order: true
```
`app/api/src/main/resources/application.yml:15-20`

- `out-of-order: true` — 늦게 머지된 과거 버전도 거부하지 않고 그냥 적용한다.
- 이게 성립하는 **전제**: 각 마이그레이션은 다른 미적용 마이그레이션의 실행 순서에 기대지 않게 **독립적으로** 써야 한다. (예: "앞 파일이 만든 컬럼이 반드시 먼저 있어야 하는" 식으로 짜면 out-of-order에서 깨진다.)

## 스키마 owner — 한 DB, 마이그레이션은 한 곳만

1단계에서 kbap의 **실행 파일이 두 개**(`app:api` 웹 서버, `app:batch` 배치)라고 봤다 → [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]]. 두 앱은 **같은 DB**를 공유한다. 그러면 스키마를 누가 만드나? 둘 다 만들면 같은 마이그레이션을 두 번 돌리려다 충돌한다.

그래서 규약은 **`app:api`만 스키마 owner**다. 마이그레이션 폴더도 `app:api` 안에만 있고(`app/api/src/main/resources/db/migration/`), 배치는 **Flyway를 끈다**(`flyway off`). 배치는 이미 만들어진 테이블을 읽고 쓸 뿐, 스키마를 건드리지 않는다. "스키마 변경의 단일 소스"를 한 곳으로 못박는 것.

## 엔티티와 스키마는 반드시 일치해야 한다

JPA 엔티티(Kotlin 클래스)는 자바 객체 쪽에서 본 테이블 모습이고, 마이그레이션 SQL은 실제 DB 쪽에서 본 테이블 모습이다. **이 둘이 어긋나면 런타임에 터진다** — 엔티티는 `VARCHAR(20)`이라 믿는데 실제 컬럼이 `VARCHAR(10)`이면 저장하다 잘리거나 에러가 난다. (엔티티에서 컬럼을 어떻게 정의하는지 — `@Column(length = N)`, `BaseEntity` 공통 컬럼 — 는 [[7. 영속성 컨텍스트와 엔티티 매핑]]에서 다룬다. 여기선 SQL 쪽만 본다.)

kbap의 SQL은 **MySQL 기준으로 고정**돼 있고, 엔티티의 컬럼 길이·타입과 한 짝을 이룬다. 실제 파일을 보자:

```sql
CREATE TABLE menu_scan (
    id           BIGINT      NOT NULL AUTO_INCREMENT,
    scan_status  VARCHAR(20) NOT NULL,
    status       VARCHAR(20) NOT NULL,
    created_at   DATETIME(6) NOT NULL,
    updated_at   DATETIME(6) NOT NULL,
    PRIMARY KEY (id)
);
```
`app/api/src/main/resources/db/migration/V2026.06.29.20.35.02__create_scan_tables.sql:3-10`

- `id`·`status`·`created_at`·`updated_at`은 모든 테이블에 공통으로 있다 — 엔티티 쪽 `BaseEntity`(`@MappedSuperclass`)가 내려주는 공통 컬럼과 짝이다([[7. 영속성 컨텍스트와 엔티티 매핑]]).
- `scan_status`는 도메인 고유 상태라 공통 `status`와 컬럼명이 겹치지 않게 따로 뒀다.
- SQL 파일 안의 `--` 주석은 허용된다 — kbap은 Kotlin에만 주석을 금지하고, SQL·YAML 같은 비-Kotlin 파일은 예외다.

이 정합(엔티티 ↔ 스키마)을 사람 눈이 아니라 **테스트가 자동으로** 검증한다. 다음 절이 그 얘기다.

## 테스트도 같은 마이그레이션을 돌린다 — 진짜 MySQL로

kbap 테스트는 인메모리 가짜 DB를 쓰지 않는다. 테스트를 돌리면 **진짜 MySQL을 Docker 컨테이너로 띄워서**(Testcontainers, KB-46) 거기에 **운영과 똑같은 마이그레이션**을 적용한다:

```yaml
spring:
  flyway:
    enabled: true
  jpa:
    hibernate:
      ddl-auto: validate
```
`app/api/src/test/resources/application.yml:5-9`

- `flyway.enabled: true` — 테스트에서도 `db/migration/`의 SQL을 그대로 돌린다. 즉 **마이그레이션 SQL 자체가 실제 MySQL에서 도는지**를 테스트가 검증한다(문법 오류·MySQL 전용 구문 실수를 CI에서 잡음).
- `ddl-auto: validate` — Hibernate가 엔티티를 보고 테이블을 **만들지 않고**(create 아님), 마이그레이션이 만든 스키마와 엔티티 매핑이 **일치하는지 검사만** 한다. 어긋나면 부팅 실패 → 엔티티와 SQL이 틀어진 순간 테스트가 빨개진다.

컨테이너는 이렇게 붙는다:

```kotlin
@TestConfiguration(proxyBeanMethods = false)
class MySqlContainerConfig {

    @Bean
    @ServiceConnection
    fun mySqlContainer(): MySQLContainer =
        MySQLContainer(DockerImageName.parse(MYSQL_IMAGE))
            .withDatabaseName(DATABASE_NAME)
            ...

    companion object {
        const val MYSQL_IMAGE: String = "mysql:8.4"
```
`infra/persistence/src/testFixtures/kotlin/com/meogo/infra/persistence/testsupport/MySqlContainerConfig.kt:9-27`

- `@ServiceConnection` — Spring Boot이 이 컨테이너의 접속 정보(URL·계정)를 **자동으로** 테스트 데이터소스에 꽂아준다. 손으로 JDBC URL을 적을 필요가 없다.
- `mysql:8.4` — 운영과 같은 MySQL 8.4 이미지를 띄운다. "테스트에서만 통과하고 운영에서 깨지는" 방언 차이를 없앤다.

정리하면 kbap의 안전망은 세 겹이다: **① 마이그레이션 SQL이 진짜 MySQL에서 돈다 → ② 그 위에서 엔티티 매핑을 `validate`로 대조 → ③ 어긋나면 테스트 실패.** 스키마와 코드가 갈라지는 걸 배포 전에 막는다.

## 주의점 / 트러블슈팅

- **이미 적용된 마이그레이션 파일은 수정·리네임 금지.** Flyway는 적용 시점의 파일 내용을 checksum으로 기록해 둔다. 나중에 그 파일을 한 글자라도 고치면 checksum이 안 맞아 **부팅이 거부**된다. 바꾸고 싶으면 옛 파일은 그대로 두고 **새 마이그레이션 파일**을 뒤에 붙인다.
- **신규 마이그레이션에 정수 버전(`V11`) 쓰지 말 것.** 반드시 timestamp 포맷(`V2026.07.14.09.30.00__...`). 정수는 브랜치 충돌의 원인이라 규약으로 금지.
- **순서 의존 마이그레이션 금지.** out-of-order 전제라, "직전 파일이 만든 것"에 기대는 SQL을 쓰면 머지 순서가 바뀔 때 깨진다. 각 파일이 독립적으로 성립하게.
- **시드 SQL 파일명을 함부로 바꾸지 말 것.** 일부 테스트는 시드가 담긴 마이그레이션을 **리소스 경로로 하드코딩**해 읽는다(예: `AvoidanceCatalogSeedSyncTest`). 그 파일명을 바꾸면 파일을 못 찾아 내용이 빈 문자열로 읽히고, "파일 없음"이 아니라 **데이터 불일치 실패**로 조용히 깨진다(오진 주의). 옮기면 테스트의 참조도 함께 갱신한다.
- **테스트가 갑자기 다 깨졌다 → Docker 확인.** Testcontainers는 로컬 Docker 데몬이 떠 있어야 MySQL 컨테이너를 띄운다. Docker가 꺼져 있으면 테스트가 컨테이너 시작 단계에서 실패한다.

## 치트시트

| 하고 싶은 것 | 방법 |
|---|---|
| 스키마 바꾸기 | `db/migration/`에 **새** `V{timestamp}__desc.sql` 파일 추가 |
| 파일명 만들기 | `V2026.07.14.09.30.00__add_review_table.sql` (`V`+점구분 시각+`__`+설명) |
| 이미 적용된 파일 고치기 | ❌ 금지 — 되돌리는/바꾸는 **새 파일**을 추가 |
| 컬럼 길이 정하기 | MySQL 기준. 엔티티 [[7. 영속성 컨텍스트와 엔티티 매핑\|`@Column(length=N)`]]과 일치시킬 것 |
| 배치에서 스키마 만들기 | ❌ — 스키마 owner는 `app:api`뿐(배치 flyway off) |
| 엔티티↔스키마 정합 확인 | 테스트 실행 → `ddl-auto: validate`가 자동 대조 |
| SQL 문법이 MySQL에서 도는지 확인 | 테스트 실행 → Testcontainers 실 MySQL에 `flyway.enabled: true`로 적용 |

## 용어집

- **마이그레이션**: 스키마 변경 한 덩어리를 담은 순서 있는 SQL 파일.
- **Flyway**: 마이그레이션을 버전 순서로 적용하고 적용 이력(`flyway_schema_history`)을 관리하는 도구.
- **timestamp 버전**: 정수 대신 파일 생성 시각을 버전으로 쓰는 규칙 — 브랜치 버전 충돌 방지(KB-44).
- **out-of-order**: 늦게 머지된 과거 버전 마이그레이션도 뒤늦게 적용 허용하는 옵션.
- **스키마 owner**: 스키마를 만들/바꿀 유일한 실행 파일. kbap은 `app:api`.
- **checksum**: 적용된 마이그레이션 파일 내용의 지문. 파일이 바뀌면 감지해 부팅 거부.
- **Testcontainers**: 테스트 중 진짜 DB(여기선 MySQL 8.4)를 Docker 컨테이너로 띄우는 라이브러리(KB-46).
- **`@ServiceConnection`**: 그 컨테이너의 접속 정보를 Spring Boot 테스트 데이터소스에 자동 연결하는 애너테이션.
- **`ddl-auto: validate`**: Hibernate가 테이블을 만들지 않고 엔티티↔스키마 일치만 검사하는 모드.

## 체크리스트

- [ ] 스키마를 바꿀 때 옛 파일을 고치지 않고 **새 timestamp 파일**을 추가했다.
- [ ] 파일명이 `V{점구분 시각}__{설명}.sql` 형식이고 정수 버전이 아니다.
- [ ] 새 마이그레이션이 다른 미적용 파일의 순서에 기대지 않는다(독립적).
- [ ] SQL 컬럼 길이·타입을 MySQL 기준으로 잡고 엔티티 `@Column`과 맞췄다.
- [ ] 배치가 아니라 `app:api`에만 마이그레이션을 넣었다.
- [ ] 테스트를 돌려 `validate`(엔티티 정합)와 실 MySQL 적용(SQL 문법)을 통과했다.
