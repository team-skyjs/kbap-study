# 13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지

## ① 이 API가 하는 일 (한 줄)

온보딩 화면에서 **닉네임·기피 성분·국가·앱 언어**를 제출하면, 서버가 각 값을 검증하고 → 도메인 프로필로 조립해 → 회원 행을 갱신하고 → 온보딩을 "완료"로 표시한다. `POST /api/v1/members/me/onboarding`.

이 노트는 그 요청 한 번이 **어느 파일들을 순서대로 지나 DB 한 행에 닿는지**를 실코드로 따라간다. 각 계층이 무엇이고 왜 나뉘는지의 개념 설명은 앞선 개념 노트로 링크한다 — 여기서는 "이 요청에서 그 개념이 실제로 어떻게 나타나는가"만 본다.

## ③ 계층 경계마다 — "여기서 모듈이 바뀌는 이유"

각 화살표는 Gradle 모듈 경계다. 왜 그 지점에서 파일이 다른 모듈로 넘어가는지가 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]·[[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]에서 배운 규칙의 실물이다.

### 경계 1 — Controller → UseCase (`app:api` → `application:client`)

Controller는 HTTP·JSON·JWT 같은 **웹의 사정만** 안다. 그걸 다 벗겨 `MemberProfileInput`(순수 데이터)로 바꿔 UseCase에 넘긴다.

```kotlin
override fun completeOnboarding(
    @AuthMemberId memberId: Long,
    @RequestBody request: OnboardingRequest,
): ResponseEntity<BaseResponse<Unit>> {
    memberProfileUseCase.completeOnboarding(request.toInput(memberId))
    return ResponseEntity.ok(BaseResponse.ok(Unit))
}
```
`MemberController.kt:19-25`. `request.toInput(memberId)`가 web DTO → 경계 DTO 변환이다(`OnboardingRequest.kt:11-18`). `memberProfileUseCase`는 **생성자 주입**으로 받은 부품이라 컨트롤러가 직접 `new` 하지 않는다 → [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]], [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]. `BaseResponse`로 모든 응답을 감싸는 규약도 여기서 적용된다(FE의 공통 API 응답 래퍼와 같은 역할).

`app:api`는 `application:client`에 의존하지만 그 반대는 없다 — 의존은 **한 방향**. UseCase는 자기가 HTTP로 불렸는지 배치로 불렸는지 모른다.

> [!note] `@AuthMemberId`의 memberId는 어디서 오나 (5b에서 확인)
> 이 파라미터에 회원 PK가 채워지는 정체 — 매 요청 JWT 필터가 `Authorization: Bearer` 토큰을 검증해 넣어둔 request attribute를 인증 리졸버가 꺼내 주입하는 **2단 릴레이** — 는 [[16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]]에서 확인한다.

### 경계 2 — UseCase → 도메인 + port (`application:client` → `core:member`)

UseCase는 **조율자**다. 검증하고, 도메인 객체를 조립하고, 저장을 지시한다. 규칙 자체(불변, 이미 온보딩했으면 거절)는 도메인에 있다.

```kotlin
@Transactional
fun completeOnboarding(input: MemberProfileInput) {
    val member = findMember(input.memberId)

    val profile = MemberProfile.of(
        nickname = validatedNickname(input.nickname),
        avoidanceSubstanceCodes = validatedCodes(input.avoidanceSubstanceCodes),
        spicinessPreference = member.profile.spicinessPreference,
        countryCode = validatedCountry(input.countryCode),
        appLanguage = validatedLanguage(input.appLanguage),
    )

    memberRepository.update(member.updateProfile(profile).completeOnboarding())
}
```
`MemberProfileUseCase.kt:23-36`.
- `findMember`는 없으면 `MEMBER_NOT_FOUND` 예외(`:61-63`).
- `validated*` 넷은 검증 + 변환을 겸한다(`:65-83`): 닉네임 `trim` 후 공백이면 거절, 성분 코드는 카탈로그(`AvoidanceSubstanceCode.entries`)에 없으면 거절, 국가·언어는 열거형으로 파싱 실패 시 거절. 하나라도 걸리면 예외가 나 **아무것도 저장되지 않는다**(부분 저장 없음).
- `spicinessPreference`는 온보딩 입력에 없다 → 기존 회원 값을 그대로 넘겨 보존한다.
- `member.updateProfile(profile).completeOnboarding()` — 도메인 메서드를 **체이닝**해 새 회원 상태를 만든 뒤 그 결과를 `memberRepository.update`에 넘긴다.

여기서 `@Transactional`이 이 메서드 전체를 한 트랜잭션으로 묶는다 → [[6. 설정과 프로필, 트랜잭션 첫걸음]]. 조회·검증·저장이 하나의 원자 단위라, 저장 도중 실패하면 앞의 변경도 롤백된다.

`memberRepository`의 타입은 `core:member`의 **인터페이스**(port)이지 JPA 구현이 아니다. UseCase는 infra 모듈을 import조차 하지 않는다 — 이게 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]의 의존성 역전이다.

### 경계 3 — 도메인의 불변성 (`core:member` 안)

```kotlin
fun updateProfile(profile: MemberProfile): Member = copy(profile = profile)

fun completeOnboarding(): Member {
    if (onboardingCompleted) {
        throw MemberException(MemberErrorCode.ONBOARDING_ALREADY_COMPLETED)
    }
    return copy(onboardingCompleted = true)
}
```
`Member.kt:13-20`. 두 메서드 다 **자기를 바꾸지 않고 새 `Member`를 반환**한다. `copy`는 `private`(`:22-32`)이라 외부에서 임의 복제할 수 없고, 통제된 상태 전이만 허용된다. `MemberProfile`도 같은 규약의 불변 데이터 클래스다(`private constructor` + `of`/`empty` 팩토리, `MemberProfile.kt:6-46`). 이 불변 규약의 근거는 `docs/architecture/meogo-conventions.md`의 "도메인 객체 불변성 & 영속 변환" 절.

`completeOnboarding()`이 "이미 완료면 거절"이라는 **업무 규칙**을 도메인 안에 둔 게 핵심이다. UseCase가 아니라 도메인이 자기 불변식을 지킨다 → member 바운디드 컨텍스트의 자기 완결성([[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]).

### 경계 4 — port → Adapter → 엔티티 → DB (`core` → `infra:persistence`)

port의 `update`를 실제로 구현하는 곳:

```kotlin
override fun update(member: Member): Member {
    val id = member.id ?: throw MemberException(MemberErrorCode.MEMBER_NOT_FOUND)
    val entity = findActive(id) ?: throw MemberException(MemberErrorCode.MEMBER_NOT_FOUND)
    entity.applyDomain(member)
    return memberJpaRepository.save(entity).toDomain()
}
```
`MemberRepositoryAdapter.kt:30-35`. 새 엔티티를 만들어 덮어쓰는 게 아니라, **활성 행을 먼저 로드**(`findActive`)해 `applyDomain`으로 필드만 갱신한다. 로드된 엔티티는 이미 영속성 컨텍스트가 추적 중이라, 값을 바꾸면 트랜잭션 커밋 시점에 자동으로 UPDATE가 나간다(더티 체킹) → [[7. 영속성 컨텍스트와 엔티티 매핑]]. `findActive`는 소프트 삭제되지 않은(`MemberStatus.ACTIVE`) 행만 본다(`:51-52`).

엔티티 쪽 변환:

```kotlin
fun applyDomain(domain: Member) {
    nickname = domain.profile.nickname
    profile = MemberProfileJson.from(domain.profile)
    onboardingCompleted = domain.onboardingCompleted
}
```
`MemberJpaEntity.kt:69-73`. 도메인 → 영속 변환을 **엔티티 클래스 안에** 둔다(컨벤션). 주목할 점: **닉네임은 자기 컬럼**(`nickname`), 나머지 프로필(기피 성분·맵기·국가·언어)은 `MemberProfileJson`으로 묶여 **`profile` JSON 컬럼 하나**에 통째로 들어간다. `@JdbcTypeCode(SqlTypes.JSON)`(`:36-38`)가 그 매핑이다. 기피 성분 목록이 별도 테이블·행이 아니라 JSON 배열이라는 뜻 — 회원 취향은 항상 회원과 함께 조회되므로 정규화 대신 JSON으로 묶었다.

`MemberProfileJson.from`/`toDomain`(`MemberProfileJson.kt:14-31`)이 도메인 값 ↔ JSON 표현을 오간다(예: `CountryCode` → `"KR"` 문자열).

### 경계 5 — 스키마 (Flyway)

`member` 테이블은 한 번에 태어나지 않았다. `create_member_tables.sql`이 프로필을 4개 컬럼으로 만든 뒤, `consolidate_member_schema.sql`(KB-117)이 그 4컬럼을 **단일 `profile` JSON 컬럼으로 합쳤다**(위 엔티티 매핑과 짝). 이후 `rename_onboarding_status_to_onboarding_completed`, `add_member_ranking_counts`로 진화했다. 스키마 변경이 코드(마이그레이션 파일)로 남아 순서대로 재생되는 원리는 [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]. 이 요청이 최종적으로 UPDATE 하는 컬럼은 `nickname`·`profile`(JSON)·`onboarding_completed` 셋이다.

## ④ 요청 / 응답 JSON

**요청** `POST /api/v1/members/me/onboarding` (헤더 `Authorization: Bearer {accessToken}`, 예시는 `MemberApi.kt:47-54`)

```json
{
  "nickname": "길동이",
  "avoidanceSubstanceCodes": ["EGG", "MILK", "PEANUT"],
  "countryCode": "KR",
  "appLanguage": "ko"
}
```

**성공 응답** 200 — `BaseResponse.ok(Unit)` (`BaseResponse.kt:9`). 온보딩 완료는 돌려줄 데이터가 없어 payload가 `Unit`(빈 값)이다. 요지는 `success: true`:

```json
{
  "success": true,
  "payload": {},
  "message": null
}
```

**실패 응답** 400 — 예: 카탈로그에 없는 기피 성분 코드. `BaseResponse.fail(message)` 형태이고 메시지는 `OnboardingErrorCode`(`OnboardingErrorCode.kt:9-12`)에서 온다:

```json
{
  "success": false,
  "payload": null,
  "message": "지원하지 않는 기피 성분 코드입니다"
}
```
(같은 400 계열: 닉네임 공백 `INVALID_NICKNAME`, 국가 `INVALID_COUNTRY_CODE`, 언어 `UNSUPPORTED_APP_LANGUAGE`, 이미 완료 `ONBOARDING_ALREADY_COMPLETED`, 회원 없음 `MEMBER_NOT_FOUND`. 미인증은 401.)

## ⑤ 관련 테스트가 보장하는 것

`application/client/.../member/MemberProfileUseCaseTest.kt` (Kotest `BehaviorSpec`, given/when/then 한국어). 이 테스트는 **DB 없이** `FakeMemberRepository`(port의 인메모리 가짜 구현)만 끼워 UseCase를 검증한다 — port 덕분에 도메인 로직을 인프라와 분리해 테스트할 수 있다는 게 클린 아키텍처의 실익이다([[12. SDD와 TDD — 스펙과 테스트로 개발하기]]).

- **정상 저장 + 상태 전이**: 유효 입력이면 프로필이 저장되고 `onboardingCompleted`가 true로 바뀐다 (`:67-81`).
- **맵기 보존**: 온보딩 입력에 없는 `spicinessPreference`는 기존 값이 유지된다 (`:84-100`).
- **이미 완료면 거절 + 불변**: 재제출은 `ONBOARDING_ALREADY_COMPLETED`, 프로필은 그대로 (`:116-137`).
- **검증 실패 시 저장 없음**: 카탈로그 밖 코드/소문자 코드/잘못된 국가/정확히 일치하지 않는 언어(`fr`·`EN`·`ko-KR`)/공백 닉네임 → 각 에러코드로 거절되고 `onboardingCompleted`·`nickname` 미변경 (`:152-222`).
- **정규화**: 닉네임 앞뒤 공백 제거, 중복 성분 코드 제거 (`:224-246`).
- **거절 후 재시도**: 무효 입력으로 실패한 뒤 유효 입력으로 정상 완료 (`:248-260`).

> [!note] 대비 — PATCH 프로필 부분 수정(kb-124)
> 프로필 재설정 `PATCH /api/v1/members/me/profile`은 **같은 파일의 바로 옆 메서드** `MemberProfileUseCase.update()`(`:38-53`)가 처리한다. 계층 경유는 온보딩과 완전히 동일하고, 차이는 두 가지뿐: (1) 미전송(null) 필드는 기존 값 유지, 빈 배열 `[]`은 "전부 해제"로 다르게 동작해 현재 값과 **병합**한다. (2) `completeOnboarding()`을 호출하지 않아 온보딩 상태를 전이시키지 않는다(`updateProfile`만). 그래서 별도 흐름 노트로 두지 않는다.

> [!tip] forward 예고
> `MemberRepository`에는 `increaseScanCount`도 있는데(스캔 1회당 원자적 증가), 이건 **회원 랭킹 흐름**(kb-123)에서 다룬다. 온보딩 흐름은 이 메서드를 지나지 않는다.
