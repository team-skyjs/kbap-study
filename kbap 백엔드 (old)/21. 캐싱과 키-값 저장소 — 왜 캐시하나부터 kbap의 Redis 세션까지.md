# 21. 캐싱과 키-값 저장소 — 왜 캐시하나부터 kbap의 Redis 세션까지

> **한 줄 요약**: 캐싱은 "느리거나 비싼 걸 두 번 안 하려고 결과를 가까이·임시로 둔다"는 것 하나다. 너는 FE에서 React Query 캐시로 이미 쓰고 있었다. Redis는 그 "가까이·임시" 저장을 프로세스 밖 별도 서버로 옮긴 인메모리 키-값 저장소인데, kbap은 이걸 **캐시가 아니라 refresh 세션 저장소**로 쓴다 — 같은 도구를 다른 목적에 쓴 사촌이다.

---

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 (비유, 완전 동치 아님) |
|---|---|---|
| 캐시(cache) | 원본을 다시 구하는 비용을 아끼려고 결과를 **가까이·임시로** 복사해 둔 것 | React Query가 같은 쿼리 키를 캐시에서 답하는 것 |
| 무효화(invalidation) | 캐시에 든 값이 낡았을 때 버리거나 갱신하는 일 | `queryClient.invalidateQueries(...)` |
| TTL (Time To Live) | 키에 붙인 수명. 시간이 지나면 값이 **자동 소멸** | React Query `staleTime`/`gcTime`과 결이 같음 |
| 키-값 저장소 | `Map`처럼 key→value 하나로만 저장·조회. 값의 구조·의미는 앱이 정함 | JS `Map`, `AsyncStorage` |
| 인메모리(in-memory) | 디스크가 아니라 **RAM**에 둠 → 빠르지만 기본적으로 휘발 | JS 변수에 담아둔 상태(새로고침하면 사라짐) |
| Redis | 프로세스 밖 별도 서버로 도는 **인메모리 키-값 저장소**(TTL 내장) | 여러 앱이 공유하는 서버 쪽 `Map` |
| 분산 캐시/저장소 | 앱 인스턴스 밖에 있어 **여러 인스턴스가 함께 보는** 저장소 | (FE엔 직접 대응 없음 — 서버가 여러 대인 세계의 개념) |

## 1. FE에서 이미 캐시를 쓰고 있었다

캐시는 백엔드의 낯선 개념이 아니다. 너는 이미 매일 썼다.

- **React Query 캐시** — `useQuery(['menu', id])`를 두 번 호출해도, 두 번째는 서버에 안 가고 캐시가 답한다. "같은 걸 또 요청하지 말자"가 캐시의 전부다.
- **브라우저 HTTP 캐시** — 이미지·JS 번들을 `Cache-Control` 헤더가 허락하는 동안 다시 내려받지 않는다.

**왜 캐시하나?** 어떤 일이 **느리거나(네트워크 왕복·무거운 계산) 비싼(LLM 호출·DB 조회)** 때, 그 결과를 반복해서 다시 구하지 않으려고. 한 번 구한 답을 가까운 곳에 잠깐 복사해두고 다음엔 그걸 준다.

> **캐시의 한 줄 정의**: 원본을 다시 구하는 비용을 아끼려고, 결과를 **가까이(빠른 곳)·임시로** 복사해 둔 것.

"임시"가 핵심이다. 캐시는 원본이 아니다. 원본이 바뀌면 캐시는 **낡는다**. 그래서 다음 절이 진짜 어려운 부분이다.

---

## 2. 캐싱의 세 질문

캐시를 넣을 때 늘 던지는 질문 셋:

1. **왜 캐시하나** — 비용 회피(느림·비쌈). 안 느리고 안 비싸면 캐시는 그냥 복잡도만 늘린다. `ponytail`식으로 말하면, 캐시는 "측정해서 느릴 때만" 넣는 것.
2. **어디에 두나** — ① 프로세스 메모리(그 서버 안 변수), ② 로컬 디스크, ③ **별도 분산 서버**(Redis 같은). 가까울수록 빠르지만 공유가 안 되고, 멀수록 여러 서버가 함께 볼 수 있다.
3. **언제 버리나(무효화·TTL)** — 이게 진짜 난제다. *"캐시 무효화와 이름 짓기는 컴퓨터 과학의 두 어려운 문제"*라는 오래된 농담이 있을 정도. 낡은 값을 붙들고 있으면 사용자에게 틀린 데이터를 준다.

React Query가 세 번째를 어떻게 다루는지가 좋은 다리다:
- `staleTime` — "이 시간 동안은 캐시를 신선하다고 믿어라"(TTL과 같은 발상).
- `invalidateQueries` — "이 키는 이제 낡았으니 다음 조회 때 다시 가져와라"(명시적 무효화).

Redis의 TTL은 여기서 `staleTime`의 서버판이라고 보면 된다 — 다만 Redis는 시간이 지나면 값을 **표시만 하는 게 아니라 실제로 지운다**(다음 절).

---

## 3. 키-값 저장소란

대부분의 백엔드 저장소는 RDB(관계형 DB)다 — 테이블·컬럼·스키마·조인이 있다(너는 [[7. 영속성 컨텍스트와 엔티티 매핑]], [[8. LAZY 로딩과 N+1 문제]]에서 이 세계를 봤다). 키-값 저장소는 결이 완전히 다르다.

- 저장 단위가 **key → value 하나뿐**이다. `Map`과 똑같다. `set("auth:refresh:abc", "42")` / `get("auth:refresh:abc")`.
- 값의 **구조·의미는 저장소가 모른다**. 앱이 정한다 — 문자열이든 JSON 덩어리든 저장소 입장에선 그냥 값이다.
- 그래서 **조인도 스키마도 쿼리 언어도 없다**. 대신 key 하나로 꺼내는 조회가 극단적으로 빠르고 단순하다.

FE 비유로는 `AsyncStorage`가 가장 가깝다 — `getItem(key)`/`setItem(key, value)`뿐이고, value 안이 뭔지는 네가 `JSON.parse`로 해석한다. 저장소는 관여하지 않는다.

> 비유의 경계: `AsyncStorage`는 **한 기기 안** 로컬이고, Redis는 **서버 밖 별도 프로세스**라 여러 서버 인스턴스가 공유한다. "key-value API"라는 모양만 같고 위치·공유 범위가 다르다.

---

## 4. Redis의 성질

Redis는 "**인메모리 키-값 저장소**"다. 공식 정의를 뜯어보면 왜 캐시·세션에 쓰이는지가 보인다.

- **인메모리(RAM)** → MySQL은 디스크를 읽지만 Redis는 메모리에서 답한다. 그래서 빠르다. 대신 **기본적으로 휘발**이다(재시작하면 날아갈 수 있다 — 이게 오히려 캐시·세션엔 맞는 성질).
- **TTL 내장** → 키에 수명을 붙일 수 있다(`EXPIRE`/`SET ... ttl`). 시간이 지나면 Redis가 **키를 스스로 지운다**. 앱이 "만료된 거 청소하는 코드"를 짤 필요가 없다.
- **단일 스레드 원자 연산** → 명령을 하나씩 처리해서, `getAndDelete`처럼 "읽으면서 동시에 지우기"가 중간에 끼어들 틈 없이 원자적으로 끝난다. (동시성은 [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]] 참고 — Redis는 명령 처리를 아예 한 줄로 세워서 경쟁을 없앤다.)
- **프로세스 밖 별도 서버** → 앱 인스턴스가 여러 대여도([[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]]에서 본 그 "켜둔 프로그램"들) 모두 **한 Redis를 함께** 본다. A 서버가 저장한 세션을 B 서버가 읽는다. 이게 "분산"의 의미다.

**왜 이걸 세션/캐시에 쓰고 MySQL을 안 쓰나?** 세션·캐시는 (1) 잠깐 살고(TTL) (2) 매우 자주 빠르게 읽고 (3) 잃어도 재로그인·재조회로 복구되는 데이터다. RAM·자동 만료·빠른 key 조회가 정확히 이 요구에 맞는다. 반대로 주문·회원처럼 절대 잃으면 안 되는 원본 데이터는 디스크에 안전하게 두는 MySQL이 맞다.

## 5. kbap 실사용 — 정직하게: 여기서 Redis는 캐시가 아니다

레포를 전수 확인한 결과다(`grep redis`, `@Cacheable`, `@EnableCaching`, `Caffeine`, `cache`). **kbap에는 캐시 추상화가 전혀 없다** — `@Cacheable`도 `@EnableCaching`도 없고, Redis 사용처는 딱 하나: **refresh 토큰 세션 저장소**.

즉 이 노트 제목은 "캐싱"인데 kbap의 실제 Redis 예시는 캐시가 **아니다**. 이건 약점이 아니라 이 노트의 핵심 교보재다(6절에서 왜인지 매듭짓는다). 먼저 실코드를 보자.

### 어댑터 — TTL·getAndDelete·delete

```kotlin
@Repository
class RefreshTokenRedisAdapter(
    private val redisTemplate: StringRedisTemplate,
) : RefreshTokenStore {
    override fun save(jti: String, memberId: Long, ttl: Duration) {
        redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
    }

    override fun consume(jti: String): Long? =
        redisTemplate.opsForValue().getAndDelete(key(jti))?.toLongOrNull()

    override fun delete(jti: String) {
        redisTemplate.delete(key(jti))
    }

    private fun key(jti: String): String = "$KEY_PREFIX$jti"
```
`infra/persistence/src/main/kotlin/com/meogo/infra/persistence/auth/RefreshTokenRedisAdapter.kt:8-23`

한 줄씩(주석 금지 레포라 코드에는 설명이 없다):
- `set(key, value, ttl)` — key `auth:refresh:<jti>`에 memberId를 저장하되 **TTL을 함께** 건다. refresh 토큰 수명(14일)과 저장 수명을 하나로 맞춘 것 — 토큰이 만료될 때 Redis가 알아서 그 key를 지운다. **앱이 만료 청소 코드를 안 짜도 된다**(4절의 TTL 내장).
- `consume(jti)` — `getAndDelete`: **읽으면서 동시에 삭제**한다. 4절의 "단일 스레드 원자 연산"이 여기서 값을 한다 — refresh 토큰 회전(한 번 쓴 토큰은 즉시 폐기)을 경쟁 없이 원자적으로 처리한다. 같은 토큰으로 두 번 갱신 시도하면 두 번째는 `null`을 받는다.
- `delete(jti)` — 로그아웃 시 세션을 명시적으로 폐기. access 토큰은 stateless라 만료 전 무효화가 불가능하지만, refresh는 Redis에서 지우면 그 순간 죽는다.
- `KEY_PREFIX = "auth:refresh:"` — key에 접두를 붙여 네임스페이스를 나눈다(키-값엔 폴더가 없으니 접두로 구분).

> 이 흐름의 전체 맥락(로그인→발급→회전→로그아웃)은 [[15. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]], [[16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]]에 있다. 이 노트는 그 노트들이 "Redis"라고만 부르고 지나간 부분이 **뭔지·왜 이걸 쓰는지**를 채운다.

### port는 core에, adapter는 infra에

주목할 점: 위 클래스가 구현하는 `RefreshTokenStore`는 **core(도메인)에 있는 인터페이스**(port)이고, "Redis로 구현한다"는 사실은 `infra/persistence`의 이 어댑터에만 있다. 도메인은 "refresh 세션을 어딘가 저장한다"만 알고 "그게 Redis다"는 모른다 — [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]], [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]에서 본 그 경계 규칙이 여기서도 지켜진다. 나중에 Redis를 다른 저장소로 바꿔도 도메인은 안 바뀐다.

### 설정 — 연결·의존성·컨테이너

```yaml
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
```
`app/api/src/main/resources/application-local.yml:14-17`

`spring.data.redis.host/port` — 스프링이 이 설정으로 Redis에 붙는다(환경변수 없으면 `localhost:6379`). 프로필별 설정 얼개는 [[6. 설정과 프로필, 트랜잭션 첫걸음]] 참고.

```kotlin

    "implementation"(libs.spring.boot.starter.data.redis)
```
`infra/persistence/build.gradle.kts:21-22`

`spring-boot-starter-data-redis` 의존성을 `infra/persistence`가 가진다(도메인이 아니라 어댑터 모듈이). 주석이 "TTL로 토큰 수명=저장 수명"이라고 설계 의도를 못박아 뒀다.

```yaml
  redis:
    image: redis:8
    container_name: meogo-redis
    ports:
      - "6379:6379"
    # refresh token 저장소(KB-118). TTL 로 만료가 자동 처리되므로 영속 볼륨을 두지 않는다 —
    # 재시작 시 세션이 날아가면 사용자는 재로그인하면 된다(복구 가능한 데이터).
```
`docker-compose.yml:69-77` (프로덕션은 `docker-compose.prod.yml:53-58` — 호스트 포트도 안 열고 앱 컨테이너 내부 통신 전용)

로컬·운영 모두 Redis를 `redis:8` 컨테이너로 띄운다. 주석이 4절의 "인메모리=휘발"을 **의도적으로 받아들인** 근거다: **영속 볼륨을 안 둔다**. 세션이 날아가도 재로그인으로 복구되니까. 원본 데이터라면 절대 이렇게 안 한다.

```kotlin

    @ServiceConnection(name = "redis")
    fun redisContainer(): GenericContainer<*> =
        GenericContainer(DockerImageName.parse(REDIS_IMAGE))
            .withExposedPorts(REDIS_PORT)
    // ...
        const val REDIS_IMAGE: String = "redis:8"
```
`infra/persistence/src/testFixtures/kotlin/com/meogo/infra/persistence/testsupport/RedisContainerConfig.kt:11-19`

테스트도 진짜 `redis:8`을 Testcontainers로 띄운다(가짜 Redis가 아니라 실물). `@ServiceConnection`이 스프링에 "이 컨테이너를 Redis 연결로 쓰라"고 자동 연결해준다.

## 6. 그럼 왜 "캐싱" 노트에 Redis 세션이 들어와 있나

앞 절이 보여준 게 이 노트의 진짜 통찰이다: **캐시와 세션 저장은 같은 도구를 다른 목적에 쓴 사촌**이다.

둘 다 요구하는 성질이 똑같다:

| 요구 | 캐시 | refresh 세션(kbap) |
|---|---|---|
| 임시(수명 있음) | TTL로 낡으면 버림 | TTL 14일, 만료 자동 삭제 |
| 빠른 조회 | 매 요청마다 읽음 | 매 갱신마다 읽음 |
| 프로세스 밖 공유 | 여러 서버가 같은 캐시 | 여러 서버가 같은 세션 |
| 잃어도 복구됨 | 원본 다시 구하면 됨 | 재로그인하면 됨 |

그래서 **같은 Redis(인메모리·TTL·키-값)가 양쪽 다에 맞는다**. kbap이 지금 쓰는 건 후자(세션)일 뿐, 도구의 성질은 캐시와 한 몸이다. "캐시 노트인데 예시가 캐시가 아님"이 아니라, "캐시를 이해하면 세션 저장이 왜 같은 도구인지가 보인다"가 이 노트의 결론이다.

FE 쪽에서 이 refresh 세션의 반대편도 이미 다뤘다: 토큰을 **클라이언트가 어디에 보관하나**는 [[클라이언트 저장소 — AsyncStorage·SecureStore·메모리 (K-Bap 실전)]]에 있다. FE는 access/refresh 토큰을 SecureStore(기기 안전 저장소)에 두고, BE는 그 refresh의 **세션 유효성**을 Redis에 둔다 — 같은 토큰의 양쪽 끝을 각자의 키-값 저장소가 나눠 관리하는 셈이다.

### 게다가 — 캐시는 이미 지나온 개념이다

Redis가 처음 만난 캐시도 아니다. [[7. 영속성 컨텍스트와 엔티티 매핑]]에서 본 **영속성 컨텍스트가 곧 1차 캐시(first-level cache)**다:
- 한 트랜잭션 안에서 같은 엔티티를 두 번 조회하면, 두 번째는 DB에 안 가고 영속성 컨텍스트가 답한다 — 이게 캐시다.
- 범위가 트랜잭션 하나(짧고 좁음)라는 점만 Redis(프로세스 밖·공유·오래 삶)와 다르다.

즉 "캐시"라는 단어는 낯선 신개념이 아니라, 스코프만 다른 **여러 층**으로 이미 네 코드 안에 있었다:

```
영속성 컨텍스트(1차 캐시)  → 트랜잭션 하나 안,  JPA가 자동
React Query 캐시           → 브라우저 하나 안,  FE에서 이미 씀
Redis                      → 서버 전체가 공유,  kbap은 세션에 사용
```

같은 발상("두 번 안 하려고 가까이 둔다")을 범위만 넓히거나 좁힌 것들이다.

## 7. kbap이 언제 진짜 캐시로 확장할까 (forward, 지금 필요 아님)

지금 kbap은 홈·카탈로그 같은 읽기도 **매번 DB**를 친다([[17. 홈 화면 조회 흐름 — 세 섹션을 한 응답으로 모으기]]). 캐시가 자연스러울 후보:
- **자주 읽고 잘 안 변하는** read — 홈 인기 음식, 회피 재료 카탈로그 같은 것.
- 이런 걸 Redis에 잠깐 캐시하면 DB 부하가 준다.

하지만 넣는 순간 **2절의 세 번째 질문(무효화)**이 숙제가 된다: 인기 음식이 바뀌면 캐시를 언제 버릴 것인가. `@Cacheable`+`@EnableCaching`(스프링 캐시 추상화)을 쓰면 코드는 간단해지지만, TTL을 며칠로 잡을지·변경 시 어떻게 무효화할지는 여전히 설계 결정이다. `ponytail`식 결론: **측정해서 느릴 때 넣는다. 지금은 YAGNI.** 이 노트는 그때가 오면 "Redis가 뭔지"는 이미 안다는 준비물이다.

---

## 주의점 / 트러블슈팅

- **캐시는 낡는다** — 캐시를 넣으면 "왜 데이터가 안 바뀌지?" 버그의 절반은 무효화 문제다. 값을 캐시했으면 원본이 바뀔 때 버릴 경로를 반드시 같이 설계한다.
- **인메모리 = 재시작하면 날아감** — Redis에 둔 게 세션·캐시라 kbap은 영속 볼륨을 안 둔다(의도적). 만약 "절대 잃으면 안 되는" 걸 Redis에만 두면 사고다 — 그건 MySQL로.
- **`getAndDelete`의 원자성에 기대라** — refresh 회전에서 "읽고 나서 지우기"를 두 명령으로 나누면 그 사이 경쟁이 생긴다. Redis의 단일 명령 원자성이 이걸 막아준다. 직접 read→delete로 풀지 말 것.
- **캐시로 안 쓴다고 얕보지 말기** — kbap엔 `@Cacheable`이 없다. "우리 Redis는 세션 전용"이 현재 사실이다. 코드에서 캐시 추상화를 찾으려다 없어서 헤매지 말 것 — 실측이다.
- **key 네임스페이스** — 키-값엔 폴더가 없어 접두(`auth:refresh:`)로 구분한다. 새 용도로 Redis를 쓴다면 접두를 겹치지 않게 정한다.

## 치트시트

```
캐시 한 줄       : 비싼/느린 결과를 가까이·임시로 복사해 둔 것
세 질문          : 왜(비용) / 어디(메모리·디스크·별도서버) / 언제 버리나(TTL·무효화)
키-값 저장소     : Map처럼 key→value 하나. 스키마·조인 없음. 값 의미는 앱이 정함
Redis 4성질      : 인메모리(빠름·휘발) · TTL내장(자동삭제) · 단일스레드원자 · 프로세스밖공유
Redis vs MySQL   : Redis=잠깐·빠름·잃어도복구 / MySQL=원본·안전·디스크
kbap 실측        : Redis = refresh 세션 저장소(캐시 아님). @Cacheable/@EnableCaching 없음
  save(jti,id,ttl)      → set + TTL(토큰수명=저장수명)
  consume(jti)          → getAndDelete(회전, 원자적 1회성)
  delete(jti)           → 로그아웃 폐기
캐시는 이미 지나옴 : 영속성 컨텍스트=1차 캐시(트랜잭션 범위) · React Query 캐시(브라우저 범위)
사촌론           : 캐시 ≈ 세션저장 = 같은 도구(인메모리·TTL·키값) 다른 목적
```

---

## 용어집

- **캐시(cache)**: 원본을 다시 구하는 비용을 아끼려 결과를 가까이·임시로 복사해 둔 것.
- **무효화(invalidation)**: 캐시의 낡은 값을 버리거나 갱신하는 일. 캐싱의 가장 어려운 부분.
- **TTL (Time To Live)**: 키에 붙인 수명. 지나면 저장소가 값을 자동 삭제. Redis는 표시가 아니라 실제 삭제.
- **키-값 저장소(key-value store)**: key 하나로 value를 넣고 꺼내는 저장소. 스키마·조인·쿼리 언어 없음.
- **인메모리(in-memory)**: 디스크가 아닌 RAM에 저장. 빠르지만 기본 휘발.
- **Redis**: 프로세스 밖 별도 서버로 도는 인메모리 키-값 저장소. TTL·원자 연산 내장.
- **분산(distributed)**: 앱 인스턴스 밖에 있어 여러 인스턴스가 함께 보는 상태.
- **1차 캐시(first-level cache)**: JPA 영속성 컨텍스트. 트랜잭션 범위 안의 엔티티 캐시.
- **refresh 세션 저장소**: refresh 토큰의 유효/폐기를 서버가 관리하는 저장소. kbap에선 Redis.

## 체크리스트 (이 노트를 덮었다면)

- [ ] "왜 캐시하나"를 한 문장으로 답할 수 있다(느림·비쌈 회피).
- [ ] 캐싱의 세 질문 중 **가장 어려운 게 무효화**인 이유를 말할 수 있다.
- [ ] 키-값 저장소가 RDB와 어떻게 다른지(스키마·조인 없음) 설명할 수 있다.
- [ ] Redis의 네 성질(인메모리·TTL·원자·프로세스밖공유)과 각각이 왜 세션/캐시에 맞는지 안다.
- [ ] kbap이 Redis를 **캐시가 아니라 refresh 세션 저장소**로 쓴다는 실측을 안다.
- [ ] `getAndDelete`가 왜 refresh 회전에 원자적으로 맞는지 설명할 수 있다.
- [ ] 캐시와 세션 저장이 "같은 도구 다른 목적"인 이유를 말할 수 있다.
- [ ] 영속성 컨텍스트가 1차 캐시라는 것과 Redis의 스코프 차이를 안다.
