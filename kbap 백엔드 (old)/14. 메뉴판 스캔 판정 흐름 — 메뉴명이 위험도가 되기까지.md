# 14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지

> [!summary] 이 API가 하는 일 (사용자 관점 한 줄)
> 메뉴판 사진에서 뽑은 메뉴명 목록을 보내면, 서버가 각 메뉴를 한국 음식으로 매칭하고 회원의 기피 성분에 비춰 위험도(SAFE/CAUTION/DANGER/UNKNOWN)를 항목별로 돌려준다.

`POST /api/v1/scans` — 로그인 필수. 이 노트는 컨트롤러 진입부터 DB 저장까지 **실제 코드가 지나는 경로**를 한 단계씩 따라간다. FE 개발자가 "스캔 버튼을 누르면 백엔드에서 무슨 일이 일어나나"를 코드로 읽을 수 있게.

---

## ① 입력이 어디서 오나 — FE recall → BE precision 2단 판단

이 API의 입력 `items[].rawMenuName`은 FE가 OCR로 메뉴판 사진에서 뽑아낸 **후보 문자열**이다. 판단은 두 단계로 나뉜다:

- **FE = recall**(빠짐없이 후보를 긁어모으기): 사진 → 텍스트 박스 그룹핑 → 라인을 메뉴명 후보로 분류. FE 쪽 사정과 한계는 [[OCR 메뉴 스캔 — 박스 그룹핑]], [[OCR 라인 분류 — 휴리스틱의 한계와 대안]]에 정리돼 있다.
- **BE = precision**(후보를 정밀 확정): 이 API가 그 후보 목록을 받아 정규화 → 정제(표준 한국어명/음식아님) → 카탈로그 매칭으로 좁힌다.

즉 FE가 "된장찌개 8,000원 kimchi jjigae" 같은 지저분한 줄까지 통째로 넘기면, BE가 "된장찌개"로 깎아내 저장된 음식과 맞춘다. **FE는 놓치지 않는 게 목표, BE는 틀리지 않는 게 목표**다.

## ③ UseCase 안에서 실제로 벌어지는 일 (한 트랜잭션)

`ScanUseCase.assessMenuBoard` 는 아래 순서로 흐른다. 발췌는 주석 금지 레포라 원문 그대로이고, 풀이는 발췌 아래에 둔다.

```kotlin
val matchKeys = input.items.map { KoreanMenuNameNormalizer.matchKey(it.rawMenuName) }
val refinement = refineMenuNames(input, matchKeys)
val resolvedItems = resolveFoods(input, matchKeys, refinement.byItemIndex)

val lang = LanguageCode.KO
val avoidedCodes = avoidedSubstanceProvider.avoidedCodes(input.memberId)
    .map { AvoidanceSubstanceCodeRef(it.name) }.toSet()

val items = input.items.mapIndexedNotNull { index, item ->
    val resolved = resolvedItems[index] ?: return@mapIndexedNotNull null
    ScanResult.ItemRiskResult(
        idx = item.idx,
        riskLevel = (resolved.food?.overallRisk(avoidedCodes) ?: RiskLevel.UNKNOWN).name,
        matched = resolved.food?.isReady() == true,
        foodId = resolved.food?.id,
        name = resolved.food?.displayName(lang),
        koreanName = resolved.food?.koreanName(),
    )
}
recordHistory(input.memberId, items)
recordScanCount(input.memberId)
```
(`ScanUseCase.kt:33-56`)

- **1줄 정규화**: 항목마다 한글만 남긴 `matchKey` 를 만든다. `"김치찌개 kimchi jjigae"` → `"김치찌개"`.
- **2줄 정제(`refineMenuNames`, :127-142)**: 한글이 있는 항목만 모아 `interpreter.interpret(texts)` 를 **스캔당 딱 한 번** 호출한다(LLM 비용 절약). 성공하면 항목별 `StandardName`/`NotFood`. **예외를 던지거나 개수가 안 맞으면** `degraded=true` 로 표시하고 `byItemIndex=null` 폴백(정제 없이 정규화 exact 매치만).
- **3줄 매칭(`resolveFoods`, :71-93)**: 표준명의 matchKey 로 `findByKoreanMatchKeys` 조회 → 있으면 그 음식. 없고 정제가 확정한 이름이면 `createIncomplete` 로 조사대기 등록 후 그 음식. 폴백 중(정제 실패)이면 아는 음식만 매칭하고 나머지는 미해결(음식 생성 안 함).
- **`lang = LanguageCode.KO`**: 응답 표시명 언어를 **한국어로 고정**(아래 실측 경고 참고).
- **위험도**: `food.overallRisk(avoidedCodes)` — 도메인이 판정. 음식이 없으면 `UNKNOWN`.
- **`matched`**: `food.isReady()` — 조사대기(INCOMPLETE) 음식은 `false`, 완성(READY)이라야 `true`.
- **결과에서 제외**: `NotFood` 판정·한글 0글자 항목은 `resolvedItems[index]` 가 null → `mapIndexedNotNull` 로 응답에서 빠진다. **그래서 results 개수가 요청 items 보다 적을 수 있다.**
- **이력·카운트**: 뒤 §⑤에서.

### 위험도는 어떻게 계산되나 (도메인 안)

```kotlin
fun overallRisk(avoidedCodes: Set<AvoidanceSubstanceCodeRef>): RiskLevel {
    if (!isReady()) return RiskLevel.UNKNOWN
    val targeted = avoidanceSubstances.filter { it.substanceCode in avoidedCodes }
    return RiskLevel.aggregate(targeted.map { it.riskLevel() })
}
```
(`Food.kt:36-40`)

- 완성되지 않은 음식은 곧장 `UNKNOWN`.
- 음식이 가진 기피 성분 중 **이 회원이 피하는 것만** 골라낸다. 회원이 콩(SOY)을 피하는데 음식에 콩이 없으면 그 음식은 이 회원에겐 안전.
- 각 성분의 위험도는 포함 확률(`inclusionProbability`)로 정해진다: `<10%` → SAFE, `<60%` → CAUTION, `그 이상` → DANGER (`RiskLevel.kt:16-25`).
- `RiskLevel.aggregate` (`:27-32`): 대상 성분이 없으면 SAFE, 하나라도 UNKNOWN 이면 UNKNOWN, 아니면 **가장 위험한 값**을 택한다. → 같은 음식이라도 **회원마다 위험도가 다르게 나온다**.

## ④ 계층 경계마다 — 여기서 모듈이 바뀌는 이유

이 흐름은 모듈을 4번 갈아탄다. 각 경계는 4단계에서 배운 클린아키텍처 규칙이 코드로 강제되는 지점이다.

- **Controller(app:api) → UseCase(application:client)**: 컨트롤러는 `ScanUseCase` 를 생성자 주입으로만 받고 직접 `new` 하지 않는다 → [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]. 부품 조립은 컨테이너가 → [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]. 컨트롤러는 web(DTO·검증·HTTP)만, 판정 순서는 UseCase가 갖는다.
- **UseCase → 도메인/port(core:\*)**: UseCase는 구현체를 모른다. `FoodRepository`·`ScannedNameInterpreter`·`ScanHistoryRepository`·`MemberRepository`·`AvoidedSubstanceProvider` **인터페이스(port)에만** 의존한다. "LLM이 무엇인지", "DB가 무엇인지"는 core 바깥의 어댑터가 안다 → [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]].
- **위험도 판정은 왜 UseCase가 아니라 `Food` 안에 있나**: 판정 규칙(포함 확률 → 위험도, 집계)은 음식 도메인의 불변 규칙이라 `core/food` 에 산다. UseCase는 food·scan·member **세 바운디드 컨텍스트를 조합**하는 조율자일 뿐, 어느 한 도메인의 규칙을 품지 않는다. 세 컨텍스트를 한 트랜잭션으로 엮는 건 application 계층에서만 허용된다 → [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]].
- **port → Adapter/엔티티(infra:persistence)**: 카탈로그 조회는 `Food` 도메인과 `FoodJpaEntity` 를 오가며 변환한다. 성분을 함께 읽어야 위험도를 매길 수 있어 `left join fetch f.foodAvoidanceSubstances` 로 한 번에 당겨온다(항목마다 성분을 다시 조회하는 N+1 회피) → [[8. LAZY 로딩과 N+1 문제]], [[7. 영속성 컨텍스트와 엔티티 매핑]].

## ⑤ 이력 저장 vs 스캔 카운트 — 왜 쓰기 경로가 둘인가

```kotlin
private fun recordHistory(memberId: Long, items: List<ScanResult.ItemRiskResult>) {
    val readyFoodIds = items.filter { it.matched }.mapNotNull { it.foodId }.distinct()
    if (readyFoodIds.isEmpty()) return
    scanHistoryRepository.saveAll(readyFoodIds.map { ScanHistory.record(memberId, it) })
}
private fun recordScanCount(memberId: Long) {
    memberRepository.increaseScanCount(memberId)
}
```
(`ScanUseCase.kt:61-69`)

- **`scan_history`** 는 **매칭된 READY 음식마다 1행**(같은 음식이 여러 idx로 나와도 `distinct` 로 음식당 1건). 홈화면 "최근 스캔" 용이고 `(member_id, created_at)` 인덱스로 최신순 조회한다.
- **`member.scan_count`** 는 랭킹용 카운터라 **메뉴판 한 장 = 1회**. 매칭이 0건이어도 1 오른다.
- 두 값을 하나로 못 쓰는 이유: `scan_history` 는 음식마다 행이 생겨 "스캔 횟수"를 셀 수 없다(스키마 주석에 명시). 그래서 카운트는 `member` 행의 별도 컬럼.
- 카운트업은 **원자적 UPDATE**다. 어댑터가 도메인을 읽어 +1 해서 저장하는 게 아니라 DB에서 직접 증가시킨다:

```kotlin
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update MemberJpaEntity m set m.scanCount = m.scanCount + 1 where m.id = :memberId and ...ACTIVE")
fun increaseScanCount(@Param("memberId") memberId: Long): Int
```
(`MemberJpaRepository.kt:18-28`, 어댑터 `MemberRepositoryAdapter.kt:37-43` — 반환값 0이면 `MEMBER_NOT_FOUND`) — 동시에 여러 스캔이 들어와도 read-modify-write 경합 없이 정확히 누적된다. `@Modifying`의 두 옵션은 이 직접 UPDATE와 [[7. 영속성 컨텍스트와 엔티티 매핑|영속성 컨텍스트]] 캐시의 불일치를 막는 장치다 — `flushAutomatically`(쿼리 실행 전에 쌓인 변경을 먼저 DB로 밀어냄)·`clearAutomatically`(실행 후 캐시를 비워, 캐시에 남은 옛 scanCount를 다시 읽는 사고 방지). `MemberRepository` port와 member 도메인 자체의 설명은 [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]에 있다 — 여기선 스캔이 그 port의 `increaseScanCount` 만 쓴다.

> `increaseScanCount` 랭킹 집계와 `ScannedNameInterpreter` 의 LLM 구현은 이 노트의 범위 밖이다 — 각각 **회원 랭킹 흐름(kb-123)**, **5b 배치 LLM 파이프라인**에서 다룬다.

## ⑥ 요청 / 응답 JSON 예시

요청 (`ScanApi.kt:69-78` 의 실제 Swagger 예시):
```json
{
  "items": [
    {"idx": 0, "rawMenuName": "된장찌개"},
    {"idx": 1, "rawMenuName": "김치찌개 kimchi jjigae"},
    {"idx": 2, "rawMenuName": "공기밥"},
    {"idx": 3, "rawMenuName": "원산지 중국"}
  ]
}
```

응답 (`BaseResponse` 로 감싼 형태, 필드는 `ScanResponse.kt` 기준):
```json
{
  "success": true,
  "payload": {
    "degraded": false,
    "results": [
      {"idx": 0, "matched": true,  "foodId": 12, "riskLevel": "CAUTION", "name": "된장찌개", "koreanName": "된장찌개"},
      {"idx": 1, "matched": true,  "foodId": 7,  "riskLevel": "DANGER",  "name": "김치찌개", "koreanName": "김치찌개"},
      {"idx": 2, "matched": false, "foodId": 55, "riskLevel": "UNKNOWN", "name": "공기밥",  "koreanName": "공기밥"}
    ]
  }
}
```
- `idx 3`("원산지 중국")은 `NotFood` 판정이라 **results 에서 빠졌다** — 응답 개수 < 요청 개수.
- `idx 2` 는 처음 보는 음식이라 조사대기 등록됨: `foodId` 는 있지만 `matched=false`, `riskLevel=UNKNOWN`. **`foodId` 유무가 아니라 `matched` 로 판단**해야 한다.

> [!warning] 실측 — 응답 언어는 한국어 하드코딩(미구현)
> `ScanUseCase.kt:37-38` 에 `// TODO: 회원 설정값(MemberProfile.appLanguage)에서 언어를 가져와…` 주석과 함께 `val lang = LanguageCode.KO` 가 **박혀 있다**(이 레포는 Kotlin 주석 금지인데 미구현 표시로 예외 존재). 그래서 `name` 은 en 번역이 있어도 지금은 **항상 한국어**이고 `koreanName` 과 같다. 회원 언어 반영은 아직 붙지 않았다.
>
> [!warning]- 스펙과 다름 (펼쳐보기)
> spec(`specs/001-menu-scan-mock/spec.md` FR-010a, `specs/kb-99-always-korean-menu-name/`)은 "9개국어 + 회원 `MemberProfile` 언어 권위 출처"를 그린다. 다만 그 spec 자신이 스캔 API에 대해 "회원 기반 언어 해석은 **후속**"이라 명시하고, `ScanApi.kt:39-41` OpenAPI 문서도 "현재는 항상 한국어 / 언어를 요청 파라미터로 받지 않는다(LLM 비용 경로라 호출자가 언어를 지정하지 못하게)"라고 적어 둔다. 즉 다국어는 음식 상세·목록 조회(`lang` 파라미터 있음)에서 이미 동작하고, **스캔 API만 의도적으로 한국어 고정**이다. 코드가 곧 현재 계약이다.

## ⑦ 관련 테스트가 보장하는 것

전부 Kotest `BehaviorSpec`(한국어 given/when/then). 스캔 흐름의 핵심 규칙이 여기 못 박혀 있다 → [[12. SDD와 TDD — 스펙과 테스트로 개발하기]].

- **판정·매칭** (`application/client/.../scan/usecase/ScanUseCaseTest.kt`): 표준명이 READY 음식과 일치하면 `matched=true`+산출 위험도(콩 100% → DANGER), 저장에 없으면 미완성 등록 후 `UNKNOWN`, `NotFood`·한글없음은 결과 제외. **정제 실패 시 폴백**(아는 메뉴만 매칭, 나머지 `degraded=true`)과 **정제 결과 개수 불일치 시 폴백**도 검증.
- **LLM 호출 최소화**: 여러 항목·중복 표준명이어도 `interpreter` 는 **스캔당 1회**, `createIncomplete` 도 이름을 모아 **1회**만 부른다(항목마다 반복 저장 안 함).
- **응답 언어**(같은 파일 "현재는 한국어 고정" given): en 번역이 있어도 `name`=한국어=`koreanName` — §⑥ 경고를 테스트가 고정.
- **이력·랭킹** (`ScanUseCaseHistoryTest.kt`): READY만 이력 저장, 같은 음식 여러 항목이어도 **음식당 1건**, INCOMPLETE는 이력 제외. 스캔 카운트는 **메뉴판당 1회**(매칭 0건이어도 1, 회원별로 격리).
- **웹 검증** (`app/api/.../scan/ScanValidationTest.kt`): items 빈 배열·101개·idx 중복·idx 누락·rawMenuName blank → 모두 400.
- **컨트롤러 통합** (`ScanControllerTest.kt`): 실제 MySQL 컨테이너로 토큰 인증 + `scan_history` 적재 카운트까지 확인.
