# 4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다

## 한 줄 요약

FE에선 필요한 객체를 그때그때 `new` 하거나 훅으로 만들어 썼다. 스프링은 반대다 — **컨테이너가 서버 뜰 때 객체(Bean)들을 미리 만들어 보관·조립**해두고, 내 코드는 **만들지 않고 받아 쓴다**. "부품을 누가 만드는가"의 주도권이 나에서 프레임워크로 넘어간 것, 이게 제어의 역전(IoC)이다.

---

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 (비유이며 완전 동치 아님) |
|---|---|---|
| IoC (제어의 역전) | 객체를 **만들고 연결하는 일**을 내 코드가 아니라 프레임워크가 하게 뒤집는 것 | 라우터가 화면 컴포넌트를 언제 만들지 정해주는 것 — 내가 직접 마운트 안 함 |
| 컨테이너 (ApplicationContext) | 그 Bean들을 만들어 담아두고 필요할 때 꺼내주는 **객체 창고 겸 조립 공장** | React 루트가 Provider들을 세워두고 트리에 값을 흘려보내는 그 조립 지점 |
| Bean | 컨테이너가 관리하는 객체 **한 개**. 내가 `new` 안 하고 컨테이너가 만든 인스턴스 | Context Provider가 들고 있는 값 객체 하나 (단, Bean은 앱 전체 1개·싱글턴) |
| 컴포넌트 스캔 | 서버 부팅 때 지정한 패키지를 훑어 **표식 붙은 클래스를 Bean으로 자동 등록**하는 과정 | 파일 기반 라우팅이 폴더를 훑어 라우트를 자동 등록하는 것과 발상이 같음 |

---

## 원리 — "내가 만든다"(FE) vs "받아 쓴다"(스프링)

FE에서 어떤 기능에 필요한 객체가 있으면 **내가 직접 만들었다**. API 클라이언트가 필요하면 `new ApiClient()`, 상태가 필요하면 `useState`, 공유가 필요하면 Context Provider를 내 손으로 세웠다. 만드는 시점·순서·수명이 전부 내 코드의 책임이었다.

스프링은 이 책임을 뒤집는다. **객체를 만들고 서로 연결하는 일을 컨테이너가 대신** 한다. 나는 "이 클래스는 컨테이너가 관리해라"라고 표식만 붙이고, 정작 그 객체가 **언제 만들어지는지, 어떻게 다른 객체와 연결되는지는 신경 쓰지 않는다.** 필요하면 컨테이너가 알아서 가져다 꽂아 준다. 이 방향 전환이 **제어의 역전(Inversion of Control, IoC)** 이다 — "제어(객체 생성·연결의 주도권)"가 "역전(내 코드 → 프레임워크)"됐다는 뜻.

> [!tip] 왜 뒤집는 게 이득인가
> 1. **교체가 쉽다** — 내 코드가 구현체를 직접 `new` 하지 않으니, 컨테이너가 꽂아줄 부품을 바꾸면 내 코드는 그대로다. (실제 구현을 갈아끼우는 이야기는 → [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]])
> 2. **테스트가 쉽다** — 진짜 대신 가짜(mock)를 꽂아 넣기만 하면 된다. `new`가 코드에 박혀 있으면 이게 안 된다.
> 3. **수명을 프레임워크가 관리** — 언제 만들고 언제 재사용할지(대개 앱당 1개, 싱글턴)를 컨테이너가 책임진다. 내가 인스턴스를 들고 다니며 관리할 필요가 없다.

이 대비는 비유이며 완전 동치는 아니다. FE에도 "내가 안 만드는" 객체는 있다 — 라우터가 만들어 주는 화면 컴포넌트, 프레임워크가 관리하는 훅 상태가 그렇다. 다만 스프링은 **거의 모든 앱 구성요소**(요청 처리기·서비스·DB 접근 객체)를 이 방식으로 통째로 관리한다는 게 규모의 차이다.

## Bean이란 — 컨테이너가 관리하는 객체 한 개

**Bean = 컨테이너가 만들어 관리하는 객체 하나.** 내가 `new`로 만든 평범한 객체는 Bean이 아니고, 컨테이너 창고 안에 등록된 것만 Bean이다. 그럼 어떤 클래스가 Bean이 되나 — **표식(스테레오타입 애너테이션)이 붙은 클래스**다.

| 애너테이션 | 붙이는 대상 | 의미 |
|---|---|---|
| `@Component` | 일반 부품 | "이건 컨테이너가 관리하는 부품이다"의 가장 기본 표식 |
| `@Service` | 유스케이스·비즈니스 로직 | `@Component`의 특수판 — "서비스 계층 부품"이라고 의도를 드러냄 |
| `@RestController` | HTTP 요청을 받는 진입 클래스 | `@Controller`(역시 `@Component` 계열) + JSON 응답 표식이 합쳐진 것 |
| `@Configuration` | 설정용 클래스 | 이 클래스 자체도 Bean이고, 안에서 `@Bean` 메서드로 **다른 Bean을 손수 등록**할 수 있다 |

핵심: `@Service`·`@Repository`·`@Controller`·`@RestController`는 전부 속을 까보면 **`@Component`를 메타 애너테이션으로 얹은 특수판**이다(Spring 공식 문서). 그래서 스캔은 `@Component` 하나만 알아도 이들을 전부 잡아낸다 — 이름만 다르지 "나는 Bean이다"라는 신호는 같다.

Bean을 만드는 방법은 두 갈래다:
- **자동(스테레오타입 + 스캔)** — 클래스에 `@Service` 등을 붙이면 컴포넌트 스캔이 찾아 자동 등록. kbap의 대부분이 이 방식.
- **수동(`@Bean` 메서드)** — 내 코드가 아닌 **남의 라이브러리 클래스**처럼 애너테이션을 못 붙이는 객체는, `@Configuration` 클래스 안에서 `@Bean` 붙인 메서드가 직접 만들어 등록한다.

## 컨테이너가 언제 Bean을 만드나 — 부팅 때 딱 한 번

FE 컴포넌트는 **렌더될 때마다** 함수가 다시 돈다. Bean은 정반대다 — **서버가 뜰 때 컴포넌트 스캔이 한 번 돌면서 Bean들을 만들고**, 그 뒤로는 만들어 둔 인스턴스를 **재사용**한다(기본 스코프가 싱글턴, 즉 앱 전체에 인스턴스 1개). 요청이 만 번 와도 `MemberProfileUseCase`는 부팅 때 만든 그 한 개를 계속 쓴다.

그럼 컨테이너는 어느 클래스를 스캔할지 어떻게 아나 — **진입점 클래스가 있는 패키지와 그 하위 패키지**를 훑는다. kbap 웹 앱의 진입점은 패키지 루트인 `com.meogo`에 있다:

```kotlin
@SpringBootApplication
class MeogoApiApplication

fun main(args: Array<String>) {
	runApplication<MeogoApiApplication>(*args)
}
```
`app/api/src/main/kotlin/com/meogo/MeogoApiApplication.kt:6` (1단계에서 이미 본 진입점 → [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]])

풀이(레포는 주석 금지 규약이라 코드만으로 낯설 수 있어 한 줄씩 붙인다):
- `@SpringBootApplication` — 이 안에 **컴포넌트 스캔이 포함**돼 있다. 스캔 기준점은 이 클래스가 놓인 패키지, 즉 `com.meogo`.
- 진입점을 일부러 최상위 `com.meogo`에 둔 이유가 여기 있다 — 스캔이 `com.meogo.app.api`·`com.meogo.application`·`com.meogo.infra` 등 **전 계층을 한 번에 커버**한다. (CLAUDE.md: "진입점 `MeogoApiApplication`은 `com.meogo` 루트 — 스캔이 전 계층 커버".)
- `runApplication<...>` — 이 호출 안에서 스캔 → Bean 생성 → 조립이 부팅 절차로 일어난다. 이 줄이 끝나기 전에 컨테이너가 채워진다.

> [!note] FE의 "매 렌더" vs 서버의 "부팅 1회"
> 같은 점: 둘 다 "프레임워크가 필요한 걸 알아서 만들어 준다."
> 다른 점: FE 훅/컴포넌트는 **렌더마다** 다시 평가되고 인스턴스가 새로 생길 수 있지만, Bean은 **부팅 때 한 번** 만들어 앱이 죽을 때까지 **같은 인스턴스를 공유**한다. 그래서 Bean에 요청별로 바뀌는 상태를 담아두면 안 된다(모든 요청이 같은 객체를 보므로).

## FE 비유 — React 루트의 Provider 조립과 대비

가장 가까운 FE 그림은 **앱 루트에서 Context Provider들을 한 번 세워두는 코드**다.

```tsx
// 예시 (FE, 개념 대비용)
<QueryClientProvider client={queryClient}>
  <AuthProvider>
    <App />
  </AuthProvider>
</QueryClientProvider>
```

여기서 `queryClient`·`AuthProvider`는 "앱 시작할 때 한 번 세워두고, 트리 아래에서 꺼내 쓰는 공용 부품"이다. 컨테이너가 Bean을 세워두고 필요한 곳에 꽂아주는 것과 발상이 같다.

**어디까지 같고 어디서부터 다른가:**
- 같음 — "부품을 미리 만들어 두고, 쓰는 쪽은 만들지 않고 받아 쓴다"는 구조.
- 다름 ① **스코프**: Provider는 **트리 위치에 매인다**(감싼 하위에서만 유효, 다른 Provider로 덮어쓸 수 있음). Bean은 **앱 전체에 1개**(싱글턴)라 위치 개념이 없다.
- 다름 ② **조립 시점·주체**: Provider 배치는 **내가 JSX로 직접** 짠다. Bean 조립은 **컨테이너가 스캔 결과로 자동** 한다 — 나는 어떤 Bean이 어떤 Bean을 필요로 하는지 선언만 하고 연결 코드를 쓰지 않는다.
- 다름 ③ **리렌더**: Provider 값이 바뀌면 구독하는 컴포넌트가 리렌더된다. Bean엔 그런 반응성이 없다 — 그냥 같은 객체를 계속 참조한다.

## 실코드 — kbap의 Bean 두 종류

### 1) 스테레오타입으로 자동 등록되는 Bean (`@Service`)

kbap의 유스케이스는 `@Service`가 붙어 컴포넌트 스캔에 자동으로 잡힌다:

```kotlin
@Service
class MemberProfileUseCase(
    private val memberRepository: MemberRepository,
) {
    @Transactional
    fun completeOnboarding(input: MemberProfileInput) {
        ...
    }
}
```
`application/client/src/main/kotlin/com/meogo/application/client/member/MemberProfileUseCase.kt:19`

풀이:
- `@Service` — 이 표식 하나로 이 클래스는 **Bean이 된다**. 부팅 때 컨테이너가 이걸 발견해 인스턴스 1개를 만들어 창고에 넣는다. 내 코드 어디에도 `MemberProfileUseCase()`를 `new` 하는 곳이 없다 — 그런데도 컨트롤러는 이걸 받아 쓴다.
- 생성자 괄호 안의 `private val memberRepository: MemberRepository` — 이건 이 Bean이 **동작하려면 필요한 다른 부품**이다. 컨테이너가 이 Bean을 만들 때 창고에서 `MemberRepository` Bean을 찾아 **여기에 꽂아 준다**. 즉 이 괄호는 "내가 만들 부품 목록"이 아니라 "컨테이너야, 이것들 좀 채워줘"라는 요청이다. (부품을 꽂아주는 이 방식 = 의존성 주입. 왜 인터페이스로 받는지·계층이 어떻게 나뉘는지는 → [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]에서 다룬다.)

### 2) `@Configuration`에서 손수 등록하는 Bean (`@Bean`)

애너테이션을 못 붙이는 라이브러리 객체는 `@Configuration` 안에서 직접 만들어 등록한다. kbap의 Swagger(OpenAPI) 설정이 그 예다:

```kotlin
@Configuration
class OpenApiConfig {

    @Bean
    fun openApi(): OpenAPI =
        OpenAPI().components(
            Components().addSecuritySchemes(
                BEARER_AUTH,
                SecurityScheme()
                    .type(SecurityScheme.Type.HTTP)
                    .scheme("bearer")
                    .bearerFormat("JWT"),
            ),
        )
    ...
}
```
`app/api/src/main/kotlin/com/meogo/app/api/config/OpenApiConfig.kt:12`

풀이:
- `@Configuration class OpenApiConfig` — 이 클래스 **자체도 Bean**이다. 다만 역할이 "설정을 담고, 그 안에서 다른 Bean을 등록하는 곳".
- `@Bean fun openApi(): OpenAPI` — `OpenAPI`는 스프링독(라이브러리)의 타입이라 `@Component`를 붙일 수 없다. 그래서 **메서드가 그 객체를 직접 만들어 `return` 하고, 반환값이 컨테이너에 Bean으로 등록**된다. 메서드 이름(`openApi`)이 Bean 이름이 된다.
- 요점: 자동 스캔(방법 1)과 수동 `@Bean`(방법 2)은 **등록 경로만 다를 뿐**, 일단 등록되면 똑같이 컨테이너가 관리하는 Bean이다.

> [!note] 참고 — `@Configuration`이지만 `@Bean` 메서드가 없는 경우도 있다
> 같은 `config` 폴더의 `CorsConfig`는 `@Configuration`만 붙고 `@Bean` 메서드 없이 `WebMvcConfigurer`(스프링이 "웹 동작을 조정하고 싶으면 이 인터페이스를 구현해라"라고 제공하는 확장 지점)를 구현해 CORS 설정을 얹는다(`app/api/.../config/CorsConfig.kt`). "`@Configuration` = 설정 담당 Bean"이고, 그 안에서 `@Bean`으로 새 객체를 등록할 수도, 인터페이스 구현으로 프레임워크 동작을 조정할 수도 있다는 뜻.

## 치트시트

- **IoC** = 객체를 만들고 연결하는 주도권이 내 코드 → 프레임워크로 넘어간 것. FE의 "내가 `new`/훅으로 만든다"의 반대.
- **컨테이너(ApplicationContext)** = Bean을 만들어 담아두고 꽂아주는 창고 겸 조립 공장.
- **Bean** = 컨테이너가 관리하는 객체 1개. 내가 `new` 한 건 Bean 아님.
- Bean 되는 법: **표식 붙이고 스캔에 잡히기**(`@Service`/`@RestController`/`@Component`/`@Configuration`) **또는** `@Configuration` 안 **`@Bean` 메서드로 손수 등록**.
- `@Service`·`@RestController` 등은 전부 **`@Component`의 특수판**. 스캔은 `@Component` 계열을 다 잡는다.
- **언제 만드나**: 서버 **부팅 때 컴포넌트 스캔 1회**. 기본 스코프 **싱글턴**(앱당 1개, 재사용). FE의 "매 렌더"와 반대.
- **어디를 스캔하나**: 진입점 클래스가 놓인 패키지 + 하위. kbap은 `com.meogo` 루트에 두어 전 계층 커버.
- Bean에 **요청별로 바뀌는 상태 담지 말 것** — 모든 요청이 같은 인스턴스를 공유하니까.

## 용어집

- **IoC(제어의 역전, Inversion of Control)**: 객체 생성·연결의 제어권을 애플리케이션 코드에서 프레임워크로 넘기는 설계 원칙.
- **컨테이너 / ApplicationContext**: 스프링의 IoC 컨테이너. Bean을 생성·보관·조립·제공한다.
- **Bean**: 스프링 컨테이너가 인스턴스화하고 관리하는 객체.
- **스테레오타입 애너테이션**: `@Component`와 그 특수판(`@Service`/`@Repository`/`@Controller`/`@RestController`). 붙으면 스캔 대상 Bean이 된다.
- **컴포넌트 스캔(component scan)**: 지정 패키지를 훑어 스테레오타입 붙은 클래스를 Bean 정의로 자동 등록하는 과정.
- **`@Configuration` / `@Bean`**: 설정 클래스와, 그 안에서 반환 객체를 Bean으로 손수 등록하는 메서드.
- **싱글턴 스코프(singleton scope)**: 컨테이너당 인스턴스를 1개만 만들어 공유하는 기본 Bean 스코프.

## 체크리스트 (이해했는지 스스로 점검)

- [ ] "제어의 역전"에서 무엇의 제어가, 누구에서 누구로 넘어가는지 한 문장으로 말할 수 있다.
- [ ] Bean과 "내가 `new` 한 그냥 객체"의 차이를 설명할 수 있다.
- [ ] 클래스가 Bean이 되는 두 경로(스캔 / `@Bean`)를 구분한다.
- [ ] `@Service`·`@RestController`가 `@Component`와 어떤 관계인지 안다.
- [ ] Bean이 **언제**(부팅 1회) 만들어지고 **몇 개**(싱글턴)인지, FE 렌더와 어떻게 다른지 안다.
- [ ] kbap이 진입점을 `com.meogo` 루트에 둔 이유를 스캔 관점에서 설명할 수 있다.
- [ ] `MemberProfileUseCase`의 생성자 괄호가 "내가 만들 것"이 아니라 "컨테이너가 채워줄 것"임을 안다.
