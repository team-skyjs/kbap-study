# 설정과 프로필, 트랜잭션 첫걸음 — 코드 바깥의 값과 "전부 아니면 전무"

> 작성: 2026-07-14 · 맥락: 2단계 Spring 핵심. IoC/DI로 "누가 객체를 만들고 꽂는가"를 봤으니, 이제 그 객체들이 쓸 **값(DB 주소·키)을 코드 밖에서 주입**하는 법과, UseCase에 붙는 `@Transactional`이 대체 뭘 묶는지를 잡는다.
> 목표: `.yml`이 왜 4개나 있는지, `@Transactional` 한 줄이 뭘 보장하는지 30분 뒤의 나도 바로 설명.

---

## 0. 한 줄 요약

**DB 주소·API 키 같은 "코드 바깥 값"은 `application.yml`에 두고 환경별로 `application-{프로필}.yml`이 덮어쓴다(FE의 `.env`와 같은 발상). 그리고 UseCase 메서드에 붙는 `@Transactional`은 "이 메서드 안의 DB 변경을 전부 성공 아니면 전부 취소로 묶는다"는 경계 선언이다.**

---

## 1. 핵심 개념

| 구분 | 외부 설정(Externalized Config) | 프로필(Profile) | 트랜잭션(Transaction) |
|---|---|---|---|
| 정체 | 코드에 안 박고 파일/환경변수로 주입하는 값 | 환경(local/dev/staging/prod)별 설정 묶음 | "작업 하나"를 전부 성공 or 전부 취소로 묶는 경계 |
| 왜 | 값이 바뀔 때마다 재컴파일하지 않으려고 | 같은 코드를 환경마다 다른 값으로 띄우려고 | 중간에 깨지면 반쯤 저장된 쓰레기 데이터를 막으려고 |
| kbap에서 | `app/api/.../resources/application.yml` | `application-local.yml` 등 4종 + `SPRING_PROFILES_ACTIVE` | UseCase 메서드에 붙는 `@Transactional` |
| FE 대응 | `.env` / `app.config.ts` | `.env.development` vs `.env.production` | (직접 대응물 거의 없음 — 4번 비유 참고) |

> 비유: 외부 설정 = FE의 `.env`. 프로필 = `.env.development`·`.env.production`을 빌드/실행 시 골라 쓰는 것. 여기까지는 거의 같다. **다른 점**: FE `.env`는 빌드 타임에 번들로 구워지지만, Spring 프로필은 **실행 시점(런타임)에** `SPRING_PROFILES_ACTIVE` 환경변수로 고르므로 **같은 jar 하나를 어느 환경에도 그대로 배포**하고 환경변수만 바꿔 띄운다.

## 2. 외부 설정 — 코드에 값을 박지 않는다

DB 주소를 `val url = "jdbc:mysql://prod-db:3306/meogo"` 처럼 코드에 적으면, 주소가 바뀔 때마다 코드를 고치고 다시 빌드해야 한다. 그래서 이런 "환경마다 다른 값"은 코드 밖 `application.yml`에 두고, 앱이 뜰 때 읽어 들인다. FE에서 API 베이스 URL을 `.env`에 두고 `process.env.EXPO_PUBLIC_API_URL`로 읽던 것과 같은 이유다.

kbap의 베이스 설정 `application.yml`은 **모든 프로필이 공유하는 바닥값**이다. 눈여겨볼 두 줄:

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
  application:
    name: meogo-api
```
`app/api/src/main/resources/application.yml:11-14`

- `config.import: optional:file:.env[...]` — 프로젝트 루트의 `.env` 파일을 읽어 `${...}` 자리에 채운다. `optional:`이라 `.env`가 **없으면 조용히 건너뛰고** OS 환경변수를 쓴다(배포 서버엔 `.env` 파일 없이 환경변수만 있으므로).
- `application.name` — 이 앱의 이름. 로그·모니터링에서 앱을 식별하는 라벨.

값을 꽂는 문법은 `${환경변수:기본값}`이다. `local` 프로필을 보면:

```yaml
spring:
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/meogo}
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:root}
```
`app/api/src/main/resources/application-local.yml:2-6`

- `${DB_URL:jdbc:...localhost...}` — `DB_URL` 환경변수가 있으면 그 값, **없으면 콜론 뒤 기본값**(로컬 MySQL)으로 뜬다. 그래서 로컬은 아무것도 설정 안 해도 바로 실행된다.
- FE의 `process.env.X ?? '기본값'`과 같은 널 병합이라고 보면 된다.

---

## 3. 프로필 4종 — 같은 코드, 다른 값

kbap은 실행 프로필이 **`local` / `dev` / `staging` / `prod` 4종**이고, 뜰 때 `SPRING_PROFILES_ACTIVE`로 하나를 고른다(`CLAUDE.md` 실행 규약). 베이스 `application.yml`이 깔린 뒤, 고른 프로필의 `application-{프로필}.yml`이 **겹치는 값만 덮어쓴다**(override).

같은 `datasource` 블록이 프로필마다 어떻게 다른지 비교하면 프로필의 존재 이유가 한눈에 보인다:

| | `local` | `dev` / `prod` |
|---|---|---|
| DB URL | `${DB_URL:jdbc:...localhost...}` (기본값 있음) | `${DB_URL}` (기본값 없음 — 환경변수 필수) |
| `show-sql` | `true` (쿼리 로그 봄) | `prod`는 `false` (로그 소음·성능) |

로컬은 "기본값으로 바로 뜨게", 운영은 "환경변수를 안 주면 아예 안 뜨게"(실수로 로컬 DB를 붙는 사고 방지) — 같은 코드에 값만 갈아끼우는 게 프로필이다.

> [!note] 프로필을 안 주면?
> 베이스 `application.yml`은 **datasource나 기본 프로필을 강제하지 않는다**(파일 주석에 명시). 그래서 프로필 없이 뜨는 테스트(`@SpringBootTest`)는 DB 설정이 없어 **임베디드 H2**로 동작한다(`CLAUDE.md` 실행 규약). "프로필 = 어떤 DB·값으로 이 서버 프로세스를 띄우는가"의 스위치인 셈 — 서버가 뜨는 과정 자체는 [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]] 참고.

참고로 `application.yml`엔 `meogo.auth.jwt.secret`, `meogo.llm.upstage.api-key` 같은 **인증 키·LLM 키**도 `${...}`로 주입된다. 이 값들이 실제 요청 처리에서 어떻게 쓰이는지는 5단계 실코드 흐름(JWT 인증·스캔 API)에서 다룬다 — 여기선 "키도 코드 밖 설정으로 주입된다"까지만.

## 4. 트랜잭션 첫걸음 — 전부 아니면 전무

트랜잭션(transaction)은 **여러 DB 작업을 "하나의 덩어리"로 묶어, 전부 성공하면 확정(commit)하고 중간에 하나라도 실패하면 전부 없던 일로 되돌리는(rollback) 경계**다. 은행 이체가 고전 예시다: "A 계좌에서 1만 원 빼기"와 "B 계좌에 1만 원 넣기"는 **둘 다 되거나 둘 다 안 돼야** 한다. 빼기만 되고 넣기에서 서버가 죽으면 1만 원이 증발한다.

Spring에서는 메서드에 `@Transactional` 한 줄을 붙이면, **그 메서드가 시작될 때 트랜잭션이 열리고, 정상 종료하면 commit, 예외가 터지면 rollback** 된다. kbap의 실물:

```kotlin
@Service
class MemberProfileUseCase(
    private val memberRepository: MemberRepository,
) {
    @Transactional
    fun completeOnboarding(input: MemberProfileInput) {
        val member = findMember(input.memberId)
        val profile = MemberProfile.of(...)
        memberRepository.update(member.updateProfile(profile).completeOnboarding())
    }
```
`application/client/src/main/kotlin/com/meogo/application/client/member/MemberProfileUseCase.kt:19-36` (본문 일부 생략)

- `@Transactional`이 `completeOnboarding` **메서드**에 붙어 있다 → 이 메서드 안에서 일어나는 DB 변경이 하나의 트랜잭션이다.
- 메서드가 예외 없이 끝나면 `memberRepository.update(...)`의 변경이 확정된다. 중간에 검증 실패로 예외가 나면(`findMember`가 회원을 못 찾아 `throw`) DB엔 아무 흔적도 안 남는다.
- `MemberProfile.of(...)`처럼 값 만들고 검증하는 부분은 DB를 안 건드리는 순수 로직 — 트랜잭션은 결국 `memberRepository`가 DB에 쓰는 순간을 감싼다.

같은 파일엔 **읽기 전용** 변형도 있다:

```kotlin
    @Transactional(readOnly = true)
    fun getMyProfile(memberId: Long): MyProfileResult {
```
`application/client/src/main/kotlin/com/meogo/application/client/member/MemberProfileUseCase.kt:55-56`

- 조회만 하는 메서드엔 `readOnly = true`를 준다. "이 트랜잭션은 데이터를 안 바꾼다"는 선언이라, DB/JPA가 그에 맞게 최적화한다. 지금은 "쓰기엔 그냥 `@Transactional`, 읽기 전용엔 `readOnly = true`" 정도로만 알아두면 된다.

> [!warning] 여기까지가 이번 범위
> 트랜잭션은 **개념(경계)과 붙는 위치**까지가 2단계 몫이다. `@Transactional`이 붙으면 안에서 **영속성 컨텍스트**가 뭘 하는지, 변경이 언제 실제 SQL로 나가는지(**flush**), 어떤 예외에서 롤백되는지, 트랜잭션 안에서 다른 트랜잭션 메서드를 부르면 어떻게 되는지(**전파, propagation**)는 전부 **3단계(JPA·영속성)** 에서 다룬다. 지금은 "메서드 하나 = 전부 아니면 전무" 감만 잡으면 충분하다.

## 5. 왜 하필 UseCase에 붙나

`@Transactional`이 Controller도 도메인도 아닌 **UseCase 메서드**에 붙은 게 핵심이다. 이유는 계층의 역할 분담에 있다([[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]] 참고):

- **Controller**는 HTTP 요청을 받아 넘기는 얇은 입구다 — "한 작업"이 아니라 "한 요청"만 안다.
- **도메인(core)** 은 순수 규칙(Spring-free)이라 트랜잭션 같은 인프라 개념을 몰라야 한다.
- **UseCase(application)** 는 여러 도메인·리포지토리 호출을 **조율**해 "온보딩 완료" 같은 하나의 업무 단위를 만든다. 그래서 "여기부터 여기까지가 한 작업"이라는 트랜잭션 경계가 딱 여기 붙는다.

`CLAUDE.md` 모듈 규약도 UseCase 계층(`:application:*`)을 명시적으로 **"transaction boundary"** 라고 부른다. 즉 트랜잭션 경계는 우연이 아니라 계층 설계상 정해진 자리다.

## 6. 트러블슈팅 / 주의점

- **트랜잭션 안에서 외부 호출(LLM·네트워크) 하지 말기 (감만).** `@Transactional` 메서드는 그동안 DB 커넥션을 붙잡고 있다. 그 안에서 응답이 느린 외부 API(예: LLM)를 부르면 커넥션을 오래 점유해 커넥션 풀이 마른다. kbap이 LLM 정제(Upstage) 호출을 사용자 요청 경로에서 타임아웃·폴백으로 관리하는 것도 같은 맥락 — 상세 이유·패턴은 뒤 단계에서.
- **프로필 오타 = 조용한 사고.** `SPRING_PROFILES_ACTIVE=prd`(오타)처럼 존재하지 않는 프로필을 주면, 해당 `application-prd.yml`이 없어 베이스만 적용된다. `dev`/`prod`는 DB URL 기본값이 없어 대개 부팅이 실패하니 그나마 티가 나지만, 값 오버라이드가 안 먹는 미묘한 사고의 원인이 될 수 있다.
- **`.yml` vs `.yaml`.** kbap은 확장자를 `.yml`로 통일한다(`CLAUDE.md` 규약). `.yaml`로 만들면 규약에서 벗어난다.

## 7. 치트시트

```
# 프로필 지정해서 실행 (환경변수로 런타임 선택)
SPRING_PROFILES_ACTIVE=local ./gradlew :app:api:bootRun

# 설정 파일 위치: app/api/src/main/resources/
application.yml            # 모든 프로필 공유 바닥값 (프로필/DB 강제 안 함)
application-local.yml      # 로컬: 기본값 있어 바로 뜸, show-sql=true
application-dev.yml        # 개발: 환경변수 필수
application-staging.yml    # 스테이징
application-prod.yml       # 운영: 환경변수 필수, show-sql=false

# 값 주입 문법
${DB_URL}                  # 환경변수 필수 (없으면 실패)
${DB_URL:기본값}           # 없으면 기본값 (FE의 ?? 와 유사)

# 트랜잭션
@Transactional             # 쓰기: 메서드 = 전부 성공 or 전부 취소
@Transactional(readOnly = true)   # 읽기 전용 (조회만)
# → 붙는 위치: UseCase(application) 메서드
```

## 8. 용어집

- **외부 설정(Externalized Configuration)**: 코드에 값을 박지 않고 `application.yml`·환경변수 등 코드 밖에서 주입하는 것. 값이 바뀌어도 재컴파일 불필요.
- **프로필(Profile)**: 환경별 설정 묶음. `application-{프로필}.yml`로 두고 `SPRING_PROFILES_ACTIVE`로 런타임에 하나 선택. kbap은 `local`/`dev`/`staging`/`prod` 4종.
- **트랜잭션(Transaction)**: 여러 DB 작업을 하나로 묶어 전부 성공(commit) 아니면 전부 취소(rollback)하는 경계.
- **`@Transactional`**: 그 경계를 메서드 단위로 선언하는 애너테이션. kbap은 UseCase 메서드에 붙인다.
- **commit / rollback**: 트랜잭션 변경을 확정 / 되돌림.
- **H2**: 파일 없이 메모리에서 도는 임베디드 DB. 프로필 없이 뜨는 테스트가 쓴다.

## 9. 다음에 빠른 재현 체크리스트

1. DB 주소·키 같은 "환경마다 다른 값"은? → 코드가 아니라 `application.yml` + `${환경변수:기본값}`.
2. 환경 바꿔 띄우려면? → 코드 그대로, `SPRING_PROFILES_ACTIVE`만 바꿈. 프로필 4종.
3. 프로필 안 주면? → 베이스만 적용, DB 설정 없어 테스트는 H2.
4. "이 작업은 전부 아니면 전무"를 어디에 선언? → UseCase 메서드에 `@Transactional`.
5. 조회만 하는 메서드는? → `@Transactional(readOnly = true)`.
6. (3단계 예고) `@Transactional`이 켜지면 안에서 **영속성 컨텍스트**가 실제로 뭘 하고, 변경은 언제 SQL로 나가나(flush)? → JPA·영속성 노트에서.
