# 12. SDD와 TDD — 스펙과 테스트로 개발하기

> 작성: 2026-07-14 · 맥락: 3단계에서 "Kotest 통합 테스트", "테스트 DB"가 스치듯 나왔다. 이게 이 레포에서 우연이 아니라 **강제된 개발 방식**이라는 걸 큰 그림으로 묶는다.
> 목표: kbap 코드가 "어떤 순서로" 만들어지는지 — 스펙 먼저(SDD), 테스트 먼저(TDD) — 를 30분 뒤의 나도 재현.

---

## 0. 한 줄 요약

kbap은 기능마다 **코드보다 스펙을 먼저** 쓰고(SDD: spec→plan→tasks), **구현보다 실패하는 테스트를 먼저** 쓴다(TDD: Red→Green→Refactor). 이 두 규율은 취향이 아니라 레포의 **헌법이 강제**하며, 실제로는 **에이전트 팀**이 이 사이클을 돌려 코드를 만든다.

---

## 1. 핵심 개념

| 구분 | SDD (명세 주도 개발) | TDD (테스트 주도 개발) |
|---|---|---|
| 정체 | 코드 전에 "무엇을·왜·어떻게"를 문서로 고정하는 방식 | 구현 전에 "이 코드가 통과해야 할 조건"을 테스트로 먼저 고정하는 방식 |
| 산출물 | `specs/<기능>/`의 `spec.md`·`plan.md`·`tasks.md` … | 실패하는 테스트 → 통과하는 구현 → 정리된 코드 |
| 언제 | 기능을 시작할 때 (설계 단계) | task 하나하나를 구현할 때 |
| kbap에서 | SpecKit 워크플로가 담당 | 헌법 원칙 I이 강제(NON-NEGOTIABLE) |

> **SpecKit**: SDD를 슬래시 명령(`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`)으로 굴리는 도구. `specs/` 폴더에 문서를 쌓는 골격을 제공한다.
> **헌법(constitution)**: `.specify/memory/constitution.md`. 이 레포의 모든 관행에 우선하는 최상위 규칙 문서. 원칙 I~V를 담고, 위반은 "정당화하거나 설계를 수정"해야 한다.

## 2. 원리

### 2-1. SDD — 코드 전에 문서를 쌓는다

FE에서 익숙한 흐름은 보통 "티켓 하나 잡고 → 바로 컴포넌트 짜기 → 되는지 보기"다. kbap은 그 앞에 **문서 단계**를 강제로 끼운다. 기능 하나(`kb-104` 온보딩)를 예로 들면, 코드가 한 줄도 없을 때 이미 이런 폴더가 만들어져 있다:

```
specs/kb-104-onboarding-profile/
├── spec.md          무엇을·왜 (유저 스토리·요구사항 FR-001~011·성공 기준)
├── plan.md          어떻게 (기술 선택·설계 방향)
├── tasks.md         할 일 (T001~T019, 순서·의존·병렬 가능 표시)
├── data-model.md    데이터 모델
├── research.md      사전 조사(대안 검토 R1~R8)
├── contracts/       API 계약 (onboarding-api.md)
└── checklists/      요구사항 체크리스트
```
`경로: specs/kb-104-onboarding-profile/`

- `spec.md`는 **"무엇을/왜"만** 담는다 — 기술 얘기 없이 "온보딩 미완료 회원이 유효한 정보를 제출하면 프로필이 저장되고 완료로 전이된다"(Acceptance Scenario) 같은 **행동 계약**을 쓴다.
- `plan.md`는 그걸 **"어떻게"** 로 옮긴다(어느 모듈·어떤 패턴).
- `tasks.md`는 실행 단위로 쪼갠다 — 각 항목이 체크박스 하나(`T001`~`T019`).

핵심은 **순서**다. `plan`을 통과("Constitution Check 게이트")해야 `tasks`로 넘어가고, 문서가 서면 그때 코드를 짠다. "일단 만들고 스펙은 나중에"가 구조적으로 막혀 있다.

> [!quote] 헌법이 이 순서를 못박는다
> ```
> 기능 작업은 Spec Kit 흐름을 따른다: /speckit-specify → /speckit-plan → /speckit-tasks → /speckit-implement …
> /speckit-plan의 Constitution Check 게이트를 통과해야 다음 단계로 진행한다.
> ```
> `.specify/memory/constitution.md:131` (Development Workflow)
> — 게이트를 통과해야 다음 단계로 간다는 것: 스펙·계획이 헌법과 어긋나면 코드로 진입조차 못 한다는 뜻.

### 2-2. TDD — 구현 전에 실패하는 테스트를 쓴다

TDD는 세 박자를 반복한다:

1. **Red** — 아직 없는 기능의 테스트를 먼저 쓴다. 당연히 **실패한다(빨강)**. 실패를 눈으로 확인하는 게 규칙이다("테스트가 진짜로 무언가를 검증하는가"를 보증).
2. **Green** — 그 테스트를 통과시키는 **최소한의 구현**만 한다(초록).
3. **Refactor** — 초록을 유지한 채 코드를 정리한다.

kbap에서 이건 권장이 아니라 **1순위 헌법 조항**이다:

> [!quote] 원칙 I — 타협 불가
> ```
> ### I. Test-First Development (NON-NEGOTIABLE)
> TDD로 진행한다. 요구사항을 토대로 실패하는 테스트를 우선 작성하고, 이를 통과시키는
> 방향으로 구현하며 코드를 완성해 나간다. Red → Green → Refactor 사이클을 엄격히 따른다.
> …
> 테스트 없는 구현은 머지 대상이 아니다. 테스트는 선택이 아니라 필수다.
> ```
> `.specify/memory/constitution.md:32`
> — `NON-NEGOTIABLE`(협상 불가)·"머지 대상이 아니다": 테스트 없는 PR은 아예 병합하지 않는다는 강제 규칙.

`tasks.md`를 보면 이 박자가 task 이름에 그대로 박혀 있다 — 한 기능이 `Red → Green → Refactor` 쌍으로 쪼개져 있다:

```
T005 [US1] Red:  CompleteOnboardingUseCase 단위 테스트 작성 … 실패(Red) 확인.
T006 [US1] Green: 제출 유스케이스 구현 … T005 통과 확인.
T007 [US1] Red:  제출 엔드포인트 MockMvc 통합 테스트 작성 … 실패(Red) 확인.
T008 [US1] Green: 제출 API 구현 … T007 통과 확인.
T009 [US1] Refactor + 전체 검증 … ArchUnit ModuleBoundaryTest 통과 확인.
```
`경로: specs/kb-104-onboarding-profile/tasks.md:34`

- 테스트(T005)가 **구현(T006)보다 앞 번호**다 — 우연이 아니라 규율이다.
- Green 태스크마다 "TNNN 통과 확인"이 붙는다 — 앞서 쓴 빨강 테스트를 초록으로 바꾸는 게 목표임을 명시.

## 3. 비유 — FE에서 가장 가까운 것

| kbap 방법론 | FE에서 가까운 것 | 어디까지 같고, 어디서 다른가 |
|---|---|---|
| SDD (spec→plan→tasks) | 기능 전에 PRD·디자인 시안·Jira 티켓을 확정하고 시작 | **같은 점**: 코드 전에 "무엇을"을 문서로 고정. **다른 점**: FE는 대개 관습(안 지켜도 됨)이지만, kbap은 게이트로 **강제**되고 문서가 레포 안(`specs/`)에 코드와 함께 산다. |
| TDD Red→Green→Refactor | Jest/Vitest로 `test()` 먼저 쓰고 구현하는 것 | **같은 점**: 테스트가 먼저. **다른 점**: FE에선 "테스트는 나중에/선택"이 흔하지만, 여긴 테스트 없는 코드는 머지 불가. |
| Kotest `BehaviorSpec` | Jest의 `describe / it / expect` | **같은 점**: 중첩으로 "상황별 기대"를 서술. **다른 점**: `describe`가 아니라 `given/when/then` 3단이고 설명을 **한국어**로 쓴다. |
| MySQL Testcontainers | 통합 테스트에서 MSW로 API를 목킹 | **거의 반대**: MSW는 진짜를 **가짜로** 대체하지만, Testcontainers는 테스트마다 **진짜 DB(MySQL)** 를 컨테이너로 띄운다. "목킹을 줄이고 운영과 똑같이 검증"이 목표. |

## 4. Kotest BehaviorSpec — 테스트가 읽히는 방식

이 레포의 **모든 테스트는 Kotest `BehaviorSpec` 한 가지 스타일로 고정**돼 있다(다른 스타일·JUnit `@Test` 금지). 구조는 `given(대상/전제) > \`when\`(상황) > then(기대 결과)`이고, 세 설명 모두 **한국어**로 쓴다.

> **Kotest**: Kotlin용 테스트 프레임워크(FE의 Jest·Vitest 위치). `BehaviorSpec`은 그 중 given/when/then 문체를 쓰는 스펙 스타일.

실제 도메인 테스트 발췌(온보딩 완료 전이 규칙):

```kotlin
given("Member.completeOnboarding — 온보딩 전이") {
    `when`("미완료 회원이 완료 처리하면") {
        then("완료 상태로 전이한 새 인스턴스를 반환한다") {
            val member = Member.signUp(googleIdentity())

            val completed = member.completeOnboarding()

            completed.onboardingCompleted shouldBe true
            member.onboardingCompleted shouldBe false
        }
    }
    `when`("이미 완료된 회원이 재완료하면") {
        then("ONBOARDING_ALREADY_COMPLETED 예외를 던진다") { … }
    }
}
```
`core/member/src/test/kotlin/com/meogo/core/member/MemberTest.kt:97`

- `given`은 검사 대상, `` `when` ``은 상황, `then`은 기대 결과. 위에서 아래로 **한국어 문장으로 읽힌다** — "완료 처리하면 / 완료 상태로 전이한 새 인스턴스를 반환한다".
- `` `when` `` 이 백틱으로 감싸진 이유: `when`은 Kotlin **예약어**라 함수 이름으로 쓰려면 백틱 이스케이프가 필요하다.
- `shouldBe`는 Kotest의 단언(assertion). Jest의 `expect(...).toBe(...)`에 해당.
- `member.onboardingCompleted shouldBe false` — 원본 `member`는 안 바뀌고 `completed`만 true. 3단계에서 본 **도메인 객체 불변**(상태 변경은 새 인스턴스 반환)을 테스트가 그대로 검증한다.
- 코드에 주석이 없는 이유: 이 레포는 [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나|Kotlin 주석 금지 규약]]이라, 의도를 given/when/then 문장과 이름으로 드러낸다.

## 5. 테스트가 "진짜 DB"를 쓴다

FE에서 통합 테스트를 짤 땐 보통 네트워크·DB를 가짜로 막는다(MSW 등). kbap의 **통합 테스트는 반대로 간다** — 테스트를 돌릴 때마다 **운영과 똑같은 MySQL을 컨테이너로 띄워서**(Testcontainers) 검증한다.

> **Testcontainers**: 테스트 실행 시 Docker로 실제 미들웨어(여기선 MySQL 8.4)를 잠깐 띄웠다 내리는 라이브러리. "테스트에서만 쓰는 가짜 DB(H2)" 대신 "운영과 동일한 진짜 DB"로 검증.

```yaml
spring:
  # 테스트 컨텍스트: … DB 는 MySQL Testcontainers(@ServiceConnection)로 붙는다(KB-46).
  # 운영과 동일한 Flyway 마이그레이션으로 스키마를 만들고(ddl-auto=validate 로 엔티티↔스키마 정합만 검증) …
  flyway:
    enabled: true
  jpa:
    hibernate:
      ddl-auto: validate
```
`app/api/src/test/resources/application.yml:1`

- `flyway.enabled: true` — 테스트도 [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기|운영과 똑같은 Flyway 마이그레이션]]으로 스키마를 만든다. 즉 마이그레이션 SQL 자체가 매 테스트에서 검증된다.
- `ddl-auto: validate` — Hibernate가 스키마를 만들지 않고, **엔티티와 실제 스키마가 일치하는지만 확인**한다. 어긋나면 부팅 실패 → 드리프트를 배포 전에 잡는다.
- 효과: "테스트는 통과했는데 운영에서 깨지는" 간극을 줄인다. TDD의 초록이 진짜 초록이 되도록 받쳐주는 장치.

> [!note] 문서 간 사소한 불일치
> `CLAUDE.md`의 기술 스택 줄엔 아직 `H2(test)`가 남아 있지만, 이는 KB-46에서 **MySQL Testcontainers로 이미 전환**됐다(헌법 v2.3.1 Sync Report·위 테스트 `application.yml`가 실체). 노트는 실측(Testcontainers)을 따른다.

## 6. 이 레포는 "에이전트 팀"이 이 사이클을 돌린다

여기서 한 겹이 더 있다. kbap의 TDD 사이클은 사람이 손으로만 도는 게 아니라, **Claude Code 에이전트 팀(하네스)** 이 자동으로 돌리도록 구성돼 있다.

> [!quote] CLAUDE.md — SpecKit·TDD 개발 팀
> ```
> 목표: 헌법 원칙 I(Test-First)을 강제하며 test-writer→implementer→(code-reviewer∥database-expert)
>       에이전트 팀으로 task 를 Red→Green→Refactor→리뷰까지 구동한다.
> ```
> `CLAUDE.md:7`

- **test-writer**: 실패하는 테스트를 쓴다(Red 담당).
- **implementer**: 그 테스트를 통과시킨다(Green 담당).
- **code-reviewer ∥ database-expert**: 병렬로 리뷰(∥ = 동시 실행).
- 오케스트레이터 스킬(`tdd-harness-orchestrator`)이 이 순서를 조율한다.

즉 "테스트 먼저"라는 **규율을 역할 분담으로 물리화**한 것이다 — 테스트 쓰는 에이전트와 구현하는 에이전트를 아예 분리하면, 구현자가 테스트를 대충 맞추는 일이 구조적으로 줄어든다.

이건 내가 이 노트들을 만드는 **공부 하네스와 같은 발상의 다른 적용**이다. 하나의 큰 작업을 역할별 서브에이전트로 쪼개 돌리는 아이디어 →
- [[2. 행동을 다듬는 장치 — 훅·투두·서브에이전트·스킬]] — 서브에이전트·스킬로 역할을 나누는 장치.
- [[5. 여러 에이전트의 협업]] — 여러 에이전트가 한 목표로 협업하는 방식. kbap의 test-writer→implementer→reviewer 팀이 바로 그 실제 백엔드 사례.

> [!tip] 두 노트와의 접점
> 그동안 배운 "Claude Code가 서브에이전트를 어떻게 굴리나"는 추상 지식이었는데, kbap의 개발 하네스가 **그 개념이 실제 프로덕션 백엔드에서 쓰이는 실물**이다. 개념(Claude Code 작동원리) ↔ 적용(kbap 개발 하네스)이 여기서 만난다.

## 7. 세 조각이 하나로 — 테스트가 "설계 지킴이"

3~4단계에서 본 규율들이 사실 다 "테스트로 강제된다"는 한 점으로 모인다:

- 아키텍처 경계(도메인이 Spring/JPA에 의존 금지) → **ArchUnit 테스트**가 강제 → [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]
- 스키마가 엔티티와 일치 → 통합 테스트의 `ddl-auto=validate`가 강제 → [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기]]
- 기능 요구사항(FR) → BehaviorSpec 단위·통합 테스트가 강제

문서로 "이렇게 하자"고 적는 대신, **테스트를 벽으로 세워 어기면 빌드가 깨지게** 만든 것 — 이게 kbap이 규칙을 유지하는 방식이다.

---

## 8. 트러블슈팅 / 주의점

- **Red를 건너뛰면 안 된다.** 테스트를 실패시켜 본 적 없이 통과부터 보면, 그 테스트가 애초에 아무것도 검증 안 하는 껍데기일 수 있다. tasks가 "실패(Red) 확인"을 매번 요구하는 이유.
- **spec → plan → tasks 순서를 건너뛰지 않는다.** Constitution Check 게이트를 통과 못 하면 구현 단계로 못 넘어간다.
- **테스트 스타일은 하나로 고정.** 새 테스트도 반드시 `BehaviorSpec` + given/when/then 한국어. JUnit `@Test`나 다른 Kotest 스타일을 섞으면 규약 위반.
- **회귀(regression) 가드.** 새 기능이 기존 기능을 깨지 않는지 전체 테스트를 다시 돌려 확인한다(`./gradlew build`). "회귀"=예전엔 되던 게 변경 때문에 다시 깨지는 것.
- **통합 테스트엔 Docker가 필요하다.** Testcontainers가 MySQL 컨테이너를 띄우므로, 로컬에 Docker가 안 떠 있으면 통합 테스트가 실패한다(단위 테스트는 무관).

## 9. 치트시트

```
# SDD 흐름 (SpecKit 슬래시 명령)
/speckit-specify   # spec.md  — 무엇을/왜 (유저 스토리·FR·성공 기준)
/speckit-plan      # plan.md  — 어떻게 (+ Constitution Check 게이트)
/speckit-tasks     # tasks.md — 할 일 (Red/Green/Refactor 쌍)
/speckit-implement # 구현
# (필요 시) /speckit-clarify · /speckit-analyze · /speckit-checklist

# TDD 한 사이클
Red      → 실패하는 테스트 먼저, 실패를 눈으로 확인
Green    → 통과시키는 최소 구현
Refactor → 초록 유지하며 정리

# 테스트 실행
./gradlew test                 # 전체 모듈 테스트
./gradlew :app:api:test        # 특정 모듈
./gradlew build                # 전체 컴파일 + 테스트 + ArchUnit 경계 (회귀 가드)

# 테스트 스타일 (고정)
given("대상/전제") { `when`("상황") { then("기대 결과") { … shouldBe … } } }   # 한국어
```

핵심 파일:
- `.specify/memory/constitution.md` — 헌법(원칙 I = Test-First NON-NEGOTIABLE)
- `specs/<기능>/` — 기능별 spec·plan·tasks (SDD 산출물)
- `CLAUDE.md` "하네스: SpecKit·TDD 개발 팀" — 에이전트 역할 분담
- `app/api/src/test/resources/application.yml` — Testcontainers·validate 테스트 설정

## 10. 용어집

- **SDD (Spec-Driven Development)**: 코드 전에 스펙·계획·태스크 문서를 먼저 쌓는 개발 방식.
- **SpecKit**: SDD를 슬래시 명령으로 굴리는 도구. `specs/` 폴더에 문서 골격 생성.
- **TDD (Test-Driven Development)**: 구현 전에 실패하는 테스트를 먼저 쓰는 개발 방식.
- **Red → Green → Refactor**: TDD 한 사이클. 실패 테스트 → 최소 구현 → 정리.
- **헌법(constitution)**: `.specify/memory/constitution.md`. 레포 최상위 규칙 문서(원칙 I~V).
- **NON-NEGOTIABLE**: "협상 불가" — 어떤 이유로도 예외 없이 지켜야 하는 조항.
- **Kotest**: Kotlin 테스트 프레임워크(FE의 Jest 위치).
- **BehaviorSpec**: Kotest의 given/when/then 스타일 스펙. kbap의 고정 테스트 문체.
- **Testcontainers**: 테스트 시 Docker로 진짜 미들웨어(MySQL)를 잠깐 띄우는 라이브러리.
- **회귀(regression)**: 변경 때문에 예전엔 되던 기능이 다시 깨지는 것.
- **하네스(harness)**: 여러 에이전트·스킬을 조립해 한 작업을 자동으로 돌리는 구성.

## 11. 다음에 빠른 재현 체크리스트

1. 새 기능? → 코드부터 짜지 말고 `specs/<기능>/`에 spec → plan → tasks 순서로 문서부터.
2. plan 통과(Constitution Check) 확인 후 tasks로.
3. task 구현은 반드시 **테스트 먼저(Red)** → 실패 확인 → 최소 구현(Green) → 정리(Refactor).
4. 테스트는 `BehaviorSpec` given/when/then 한국어로만.
5. 통합 테스트 전 Docker 실행 확인(Testcontainers).
6. 머지 전 `./gradlew build`로 전체 테스트 + ArchUnit 경계 회귀 확인.
