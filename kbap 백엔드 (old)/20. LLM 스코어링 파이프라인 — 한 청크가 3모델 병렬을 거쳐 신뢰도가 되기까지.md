# 20. LLM 스코어링 파이프라인 — 한 청크가 3모델 병렬을 거쳐 신뢰도가 되기까지

## 한 줄 요약

음식 10개 청크와 기피성분 81종 후보를 **하나의 프롬프트**로 묶어 **3개 LLM 모델(OpenAI·Upstage·Gemini)에 동시 호출**하고, 세 응답을 성분별 **하나의 포함 신뢰도(`inclusionConfidence`, 정수 1~100)** 로 **Consensus Ensemble** 집계한다. **셋 다 성공해야** 확정하고, 하나라도 빠지면 청크 전체를 재조사로 남긴다.

> [!info] 이 노트가 다루는 범위
> [[19. 배치 실행 골격 — 두 번째 실행 파일과 조사 대기열 순회]]가 "배치가 어떻게 돌고 무엇을 10개씩 순회하나"(`run()`)를 다뤘다. 이 노트는 그 순회가 **청크 하나를 꺼낸 다음**(`scoreChunk()`)을 다룬다. 프롬프트 조립 → 병렬 호출 → 파싱 → 집계까지의 파이프라인이 주제다.

### ① 청크를 프롬프트로 — `scoreChunk()` 도입부

`app/batch/.../scoring/AvoidanceScoringJob.kt:59-65`

```kotlin
private fun scoreChunk(
    fresh: List<Food>,
    candidates: List<CandidateSubstance>,

    val scoringFoods = fresh.map { ScoringFood(foodId = it.id!!, koreanName = it.displayName(LanguageCode.KO)) }
```

### ③ 3모델 병렬 호출 — `LlmFanoutClient.generate()`

`infra/llm/.../client/LlmFanoutClient.kt:20-27`

```kotlin
fun generate(requestFor: (LlmModelId) -> LlmChatRequest): LlmFanoutResult {
    val outcomes = callers
        .map { caller -> outcomeFuture(caller, requestFor(caller.modelId)) }
        .map { it.join() }

    val successes = outcomes.filterIsInstance<CallOutcome.Success>().map { it.result }
    val failures = outcomes.filterIsInstance<CallOutcome.Failure>().map { it.failure }
    return LlmFanoutResult(successes, failures)
}
```

- **병렬의 핵심은 `.map`이 두 번 나뉜 것**이다(`:22-24`). 첫 `.map`이 3개 caller 각각에 대해 `CompletableFuture`를 만들어 **executor에 전부 제출**하고(즉시 시작), 그다음 `.map { it.join() }`이 결과를 기다린다. 첫 caller가 끝날 때까지 둘째를 시작하지 않는 순차 실행이 아니다 — 셋을 먼저 다 쏘고 나서 걷어온다.
- `:25-26` — 결과를 성공(`LlmChatResult`)과 실패(`LlmModelFailure`)로 가른다. 한 모델이 던진 예외가 다른 두 모델을 죽이지 않는다(격리).

`infra/llm/.../client/LlmFanoutClient.kt:34-43`

```kotlin
CompletableFuture
    .supplyAsync({ caller.call(request) }, executor)
    .orTimeout(callTimeout.toMillis(), TimeUnit.MILLISECONDS)
    .handle { content, throwable ->
        if (throwable == null) {
            CallOutcome.Success(LlmChatResult(caller.modelId, content))
        } else {
            CallOutcome.Failure(LlmModelFailure(caller.modelId, reasonOf(throwable)))
        }
    }
```

- `:35` — `caller.call(request)`(⑤, 네트워크로 LLM 호출)를 `executor` 위에서 비동기로 돌린다.
- `:36` — 타임아웃을 건다. 기본 30초(`:16`)이지만 실제로는 설정값 `properties.callTimeout`이 주입된다(`config/LlmConfiguration.kt:79`). 늦으면 그 모델만 실패로 떨어진다.
- `:37-43` — 성공이든 예외든 `handle`이 받아 `CallOutcome`으로 감싼다. 그래서 예외가 밖으로 새지 않고 실패 목록에 담긴다.

> [!tip] 가상 스레드 — [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]]의 세 번째 모델
> [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]]에서 본 두 모델은 (a) Node의 싱글 스레드 이벤트루프, (b) JVM의 요청당 OS 스레드(스레드풀)였다. 여기 executor는 **세 번째 — 가상 스레드**다: `Executors.newVirtualThreadPerTaskExecutor()`(`config/LlmConfiguration.kt:72`). LLM 호출은 대부분 네트워크 응답을 **기다리는(blocking)** 시간이다. OS 스레드는 그 대기 동안 통째로 놀지만, 가상 스레드는 JVM이 대기 중인 것을 값싸게 치워두고 다른 일에 스레드를 내준다. 그래서 3개를 동시에 띄워도 무겁지 않다. (더 깊은 설명은 개념 노트가 아직 없다 — 지금은 "blocking 대기가 값싼 경량 스레드"로만.)

### ④ 응답 파싱 — `ScoringResponseParser.parse()`

`core/research/.../parse/ScoringResponseParser.kt:29-44`

```kotlin
for (itemNode in judgementsNode) {
    val values = readIntArray(itemNode, JUDGEMENT_ARITY) ?: continue
    val (foodIndex, substanceIndex, score, probability) = values
    val food = foods.getOrNull(foodIndex) ?: continue
    val candidate = candidates.getOrNull(substanceIndex) ?: continue
    if (score !in 0..2 || probability !in 1..100) {
        continue
    }
    val pairKey = foodIndex.toLong() * candidates.size + substanceIndex
    if (!acceptedPairs.add(pairKey)) {
        continue
    }
    coveredFoodIds.add(food.foodId)
    included.getOrPut(food.foodId) { mutableListOf() }
        .add(SubstanceJudgement(code = candidate.code, score = score, probability = probability))
}
```

- 압축 응답의 `r` 배열을 한 줄씩 읽어 **(음식→성분→{score,probability})** 구조로 되돌린다.
- 방어가 촘촘하다: 4-원소 정수 배열이 아니면(`:30`), 인덱스가 청크 밖이면(`:32-33`), score/probability가 범위를 벗어나면(`:34-36`), 같은 (음식,성분) 쌍이 중복이면(`:37-40`) 그 항목만 **건너뛴다**(`continue`). LLM 출력은 못 믿으니 항목 단위로 걸러낸다.
- `:46`(발췌 밖) — `c` 배열로 "판단은 마쳤으나 포함 성분이 없는" 음식도 covered에 넣는다. **포함 0건도 정상 응답**이다(빈 음식 ≠ 실패).

### ⑥ 집계 — `ConsensusEnsembleAggregator.score()`

`core/research/.../ensemble/ConsensusEnsembleAggregator.kt:39-52`

```kotlin
val judgements = perModel.map { model ->
    model.included[foodId]?.firstOrNull { it.code == candidate.code }
}
val scoreValues = judgements.map { it?.score ?: MISSING_SCORE }
val probabilityValues = judgements.map { it?.probability ?: MISSING_PROBABILITY }

val avgScore = scoreValues.average()
val avgProbability = probabilityValues.average()
val base = policy.scoreWeight * (avgScore / MAX_SCORE) +
    (1.0 - policy.scoreWeight) * (avgProbability / MAX_PROBABILITY)
val agreementFactor = agreementFactor(scoreValues.distinct().size)
val inclusionConfidence = (base * agreementFactor * MAX_PROBABILITY)
    .roundToInt()
    .coerceIn(policy.floor, MAX_PROBABILITY)
```

성분 하나에 대해 세 모델의 판단을 하나의 숫자로 합치는 공식이다.

- `:39-41` — 세 모델 각각에서 이 (음식,성분)의 판단을 찾는다. **한 모델이 이 성분을 응답에 안 담았으면**(미포함으로 본 것) `null` → 다음 줄에서 `score 0`, `probability 1`로 취급된다(`MISSING_SCORE=0`, `MISSING_PROBABILITY=1`, `:73-74`). 즉 미판단은 "빠짐"이 아니라 "약한 반대표"로 평균에 섞인다.
- `:47-48` — `base = scoreWeight·(avgScore/2) + (1-scoreWeight)·(avgProb/100)`. 가중치 `scoreWeight`의 기본값은 **0.6**이다(`EnsemblePolicy.kt:4`, `DEFAULT`). score는 0~2라 2로, probability는 1~100이라 100으로 나눠 각각 0~1로 정규화한 뒤 6:4로 섞는다.
- `:49` — `agreementFactor`는 **score 값의 서로 다른 개수**로 정해진다(`:64-69`): 3개 동일 → 1.0, 2종 → 0.9, 3종 상이 → 0.75. 모델들이 엇갈릴수록 신뢰도를 깎는다.
- `:50-52` — `base·factor·100`을 반올림하고 **1~100으로 clamp**한다(`floor=1`, `EnsemblePolicy.kt:5`). 공식상 0이 나와도 하한 1을 보장한다 — [[14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]]의 위험도 정책(KB-9)이 1~100 입력을 기대하기 때문(`spec.md:107`, FR-006).

**골든 케이스 검산** (비빔밥 EGG, 3모델 score `[2,1,2]`·prob `[90,70,80]`, `spec.md:63`):
avgScore = 5/3 ≈ 1.667, avgProb = 80 →
base = 0.6·(1.667/2) + 0.4·(80/100) = 0.5 + 0.32 = **0.82** →
score 2종({2,1}) → factor **0.9** → round(0.82·0.9·100) = round(73.8) = **74**. spec 예시와 일치.

```
Output raw JSON only in this exact schema — no code fences, no explanation:
{"c":[food indices you judged],"r":[[food index, substance index, score, probability], ...]}
...
[Candidate avoidance substances - index:CODE]
0:EGG
1:MILK
2:PEANUT
...

user:
[Foods to judge - index:name]
0:비빔밥
1:김밥
```

**모델 응답(파서가 받는 것, 압축 JSON)**

```json
{"c":[0,1],"r":[[0,0,2,90],[0,1,1,40]]}
```

`c`는 "0·1번 음식 판단 완료", `r`은 "0번 음식에 0번 성분(EGG) score 2·prob 90, 1번 성분(MILK) score 1·prob 40 포함". 1번 음식(김밥)은 `c`에만 있고 `r`엔 없으니 포함 성분 0건(정상).

**산출 DTO(`FoodScoringResult`, SCORED 예)**

```
FoodScoringResult(
  foodId = 100,           // 비빔밥
  status = SCORED,
  scores = [ FoodInclusionScore(substanceCode="EGG", inclusionConfidence=74, ...), ... ],  // 81종
  nameTranslations = { EN: "Bibimbap", JA: "ビビンバ", ... },
  description = ...
)
```

## 경계마다 "여기서 모듈이 바뀌는 이유"

- **배치 → 도메인(프롬프트·파싱·집계)**: 프롬프트 문자열 조립도, 앙상블 공식도, JSON 파싱도 전부 `core/research`에 있다. **Spring도 네트워크도 없는 순수 Kotlin**이다. 그래서 LLM 없이 값만 넣어 단위 테스트로 공식을 검증할 수 있다 — [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]].
- **도메인 → infra(fan-out·caller)**: 실제 네트워크 호출·가상 스레드·Spring AI는 `infra/llm`에 격리된다. 도메인은 `LlmModelCaller.call(request): String` 포트 뒤의 "문자열 하나 넣으면 문자열 하나 나온다"만 안다 — 어느 벤더인지 모른다. [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]의 조립(`config/LlmConfiguration.kt`)이 caller 3개를 리스트로 주입한다([[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]).
- **`core/research`는 이 기능이 도입한 새 도메인 모듈**이다. 앙상블·파싱·프롬프트라는 "LLM 결과를 신뢰도로 만드는 계산"이 자기 경계를 갖는다 — [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]].

## 이 신뢰도는 어디로 가나 (먼 원천, 아직 연결 안 됨)

이 잡이 만드는 `inclusionConfidence`(1~100)는 **먼 미래에** [[14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]]의 위험도(SAFE/CAUTION/DANGER)로 이어질 값이다. 다만 지금은 **직접 연결이 없다**: 이 잡은 신뢰도를 저장하지 않고(KB-54 미구현), 위험도 변환도 KB-9의 별개 정책이다. "이 배치가 스캔 위험도의 먼 원천"이라는 정도로만 이해하면 된다.

## 치트시트

- 진입: `AvoidanceScoringJob.scoreChunk()` (순회 `run()`은 → [[19. 배치 실행 골격 — 두 번째 실행 파일과 조사 대기열 순회]]).
- 병렬: caller 3개를 `supplyAsync`로 **먼저 다 발사** → `join`. 가상 스레드 executor. 예외·타임아웃은 그 모델만 실패.
- 확정: `실패 0 && 파싱 3 && 전원 커버` → 아니면 청크 전체 FAILED.
- 공식: `base = 0.6·(avgScore/2) + 0.4·(avgProb/100)`, `factor = {1.0, 0.9, 0.75}[score 종수]`, `round(base·factor·100).coerceIn(1,100)`.
- 미판단 성분 = score 0·prob 1로 평균에 섞임(빠짐 아님).
- 끝: `FoodScoringResult` 반환. **저장·위험도는 범위 밖(KB-54/KB-9)**.

## 용어집

- **fan-out**: 하나의 요청을 여러 수신자(여기선 3모델)에게 동시에 뿌리고 응답을 모으는 패턴.
- **가상 스레드(virtual thread)**: JVM이 관리하는 경량 스레드. blocking 대기가 값싸 다수를 동시에 띄워도 부담이 적다. → [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]].
- **Consensus Ensemble**: 여러 모델 판단을 평균 + 일치도 보정으로 하나의 값으로 종합하는 집계 방식.
- **`inclusionConfidence`**: (음식,성분) 조합의 포함 신뢰도(정수 1~100). 통계적 확률이 아니라 LLM 추정 종합값.
- **agreement_factor**: 3모델 score 일치 정도로 신뢰도를 깎는 계수(1.0/0.9/0.75).
