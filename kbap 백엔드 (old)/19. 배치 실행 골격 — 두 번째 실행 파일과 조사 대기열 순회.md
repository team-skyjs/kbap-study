# 19. 배치 실행 골격 — 두 번째 실행 파일과 조사 대기열 순회

## 이 잡이 하는 일 (한 줄)

web 서버(계속 떠서 요청을 기다림)와 달리, 배치는 **한 번 돌고 끝나는 두 번째 실행 파일(bootJar)**이다. 켜지면 조사 대기열의 음식을 10개씩 청크로 끝까지 순회하며 스코어링 잡을 돌리고, 결과 개수만 로깅한 뒤 프로세스가 종료된다.

[[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]]에서 "두 번째 bootJar는 배치에서 다룬다"고 예고했던 그 실행 파일이 바로 이것이다.

> [!tip] FE 비유
> web은 `expo start`처럼 켜두면 계속 사는 dev 서버, 배치는 `node scripts/migrate.js`처럼 **한 번 실행하고 끝나는 스크립트**에 가깝다. 다만 그 스크립트가 Spring 컨텍스트를 통째로 조립해서 뜬다는 점이 다르다 — 부팅하면서 필요한 Bean을 다 만든 뒤에야 잡이 돈다.

## 경계마다 "여기서 왜 이렇게 갈리나"

### 왜 두 번째 실행 파일인가 — web과 batch의 수명 차이

web(api)과 batch는 **서로 다른 bootJar**다. 진입점이 각각 하나씩 있다.

```kotlin
@SpringBootApplication(scanBasePackages = ["com.meogo"])
@AutoConfigurationPackage(basePackages = ["com.meogo"])
class MeogoBatchApplication

fun main(args: Array<String>) {
    runApplication<MeogoBatchApplication>(*args)
}
```
`MeogoBatchApplication.kt:7-13`
- `@SpringBootApplication` — 이 클래스가 하나의 독립 실행 애플리케이션의 시작점이다. api에도 이런 클래스가 따로 있고, 이건 **두 번째** 것이다.
- `scanBasePackages = ["com.meogo"]` — 부팅 시 `com.meogo.*` 아래를 훑어 필요한 Bean을 조립한다. 배치가 의존하는 모듈(`build.gradle.kts`가 정한 범위)만 클래스패스에 있으므로, 실제로 조립되는 건 그 부분집합이다.
- `main` — web은 이 자리에서 톰캣을 띄우고 무한정 요청을 기다리지만, 배치는 부팅 → `ApplicationRunner` 실행 → 할 일이 끝나면 컨텍스트가 닫히고 **프로세스가 종료**된다.

수명이 왜 이렇게 다른지(상주 서버 vs 1회 실행)는 [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]]에서 다뤘다. 배치가 골라 조립하는 Gradle 멀티모듈 구조는 [[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]] 참고.

### 부팅과 실행의 분리 — ApplicationRunner와 게이팅

부팅되었다고 잡이 바로 도는 게 아니다. 실행은 두 개의 스위치를 통과해야 한다.

```kotlin
override fun run(args: ApplicationArguments) {
    val results = job.run()
    val scored = results.count { it.status == FoodScoringStatus.SCORED }
    val failed = results.count { it.status == FoodScoringStatus.FAILED }
    logger.info("기피성분 스코어링 잡 완료 total={} scored={} failed={}", results.size, scored, failed)
}
```
`ScoringJobRunner.kt:13-18`
- `ApplicationRunner` — Spring이 부팅을 마친 직후 `run(args)`를 자동으로 한 번 불러주는 약속된 인터페이스다. "부팅 끝나면 이거 실행해줘"를 등록하는 훅.
- `job.run()` — 실제 순회 로직(아래)을 1회 돌리고 결과 리스트를 받는다.
- `logger.info(... total/scored/failed ...)` — **이 러너가 하는 유일한 마무리는 개수 집계 로깅**이다. score를 DB에 쓰지 않는다.

이 러너 Bean 자체가 게이팅으로 막혀 있다.

```kotlin
@Bean
@ConditionalOnProperty(prefix = "meogo.scoring.runner", name = ["enabled"], havingValue = "true")
fun scoringJobRunner(job: AvoidanceScoringJob): ScoringJobRunner = ScoringJobRunner(job)
```
`ScoringJobConfig.kt:46-48`
- `@ConditionalOnProperty(... havingValue="true")` — `meogo.scoring.runner.enabled=true`일 때만 이 Bean을 만든다. 기본값은 off(`application.yml:37`)이므로, 그냥 실행하면 **부팅만 되고 잡은 안 돈다**. 실 실행 시에만 명령행 인자로 켠다.
- `@Bean` / 생성자로 `job`을 받는 것 — 부품을 직접 `new` 하지 않고 컨테이너가 주입한다. IoC/DI 개념은 [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]], [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]].
- 나머지 협력자(프롬프트 팩토리·파서·집계기·잡)도 같은 파일 `:17-44`에서 `@Bean`으로 조립되고, `chunk-size`는 `@Value("\${meogo.scoring.chunk-size:10}")`로 주입된다. 설정/프로필/`@Value` 주입은 [[6. 설정과 프로필, 트랜잭션 첫걸음]].

> [!note] 실측 — 이 잡은 결과를 DB에 저장하지 않는다
> `ScoringJobRunner`는 결과 **개수만 로깅**하고 끝난다(`ScoringJobRunner.kt:13-18`). 산출물(`FoodScoringResult`)을 어디에도 쓰지 않는다. kb-53은 "저장 직전 산출물"까지만 책임지고, 저장·위험도 반영은 후속(kb-54/kb-9) 몫이다. **다른 흐름(온보딩·랭킹 등)이 persistence 쓰기로 끝나는 것과 달리**, 이 배치는 쓰기로 끝나지 않는다. 배치가 `infra:persistence`를 조립하는 건 아래에서 보듯 음식 대기열을 **읽기** 위해서지 score를 저장하기 위해서가 아니다.

### 순회 골격 — run()이 대기열을 어떻게 도는가

```kotlin
fun run(): List<FoodScoringResult> {
    val candidates = loadCandidates()
    check(candidates.isNotEmpty()) { "scoring.candidates 는 비어있을 수 없습니다 …" }
    val results = mutableListOf<FoodScoringResult>()
    val seen = mutableSetOf<Long>()
    var page = 0
    while (true) {
        val chunk = foodScoringSource.nextChunk(page, chunkSize)
        if (chunk.isEmpty()) break
        val fresh = chunk.filter { it.id != null && seen.add(it.id!!) }
        if (fresh.isEmpty()) break
        results += scoreChunk(fresh, candidates)
        page++
    }
    return results
}
```
`AvoidanceScoringJob.kt:33-52`
- `loadCandidates()` + `check(... isNotEmpty())` — 먼저 기피성분 후보 카탈로그를 로드하고, 비어 있으면 즉시 예외로 중단(fail-fast). 순회를 시작하기 전에 입력을 검증한다.
- `seen = mutableSetOf<Long>()` — 이미 처리한 음식 id를 기록하는 집합. 페이지네이션 도중 같은 음식이 다시 나오면 중복 처리하지 않으려는 방어.
- `while (true) { nextChunk(page, chunkSize) ... page++ }` — 대기열을 `chunkSize`(기본 10)개씩 페이지로 끝까지 순회한다. FE의 무한 스크롤 페이지네이션과 같은 구조: 다음 페이지를 계속 당겨오다가 빈 페이지가 오면 멈춘다.
- `if (chunk.isEmpty()) break` — 대기열이 소진되면 종료.
- `fresh = chunk.filter { seen.add(it.id!!) }` — 이번 청크에서 아직 안 본 음식만 추린다. `seen.add`는 새로 넣었을 때만 `true`라 중복 필터로 쓴다. `if (fresh.isEmpty()) break` — 전부 이미 본 것뿐이면(대기열이 제자리를 맴돌면) 무한 루프를 막으려 종료.
- `results += scoreChunk(fresh, candidates)` — **여기서부터 청크 1개의 처리(3모델 fan-out·파싱·집계)는 [[20. LLM 스코어링 파이프라인 — 한 청크가 3모델 병렬을 거쳐 신뢰도가 되기까지]]가 주인이다.** 이 노트는 `scoreChunk` 안으로 들어가지 않는다.

대기열이 무엇이고 어떻게 채워지는지는 port로 추상화돼 있다.

```kotlin
interface FoodScoringSource {
    fun nextChunk(page: Int, size: Int): List<Food>
}
```
`FoodScoringSource.kt:3-5`
- `core/food`에 있는 **순수 인터페이스**(port). 잡은 "다음 청크를 달라"고만 요청하지, 그게 DB에서 어떤 쿼리로 오는지는 모른다.
- 실제 구현은 `infra/persistence/.../food/FoodScoringSourceAdapter.kt`이고, 배치는 이 구현을 `runtimeOnly`로만 조립한다(컴파일 타임엔 port만 안다). 도메인을 순수하게 지키는 ports & adapters 규칙은 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]], 모듈 경계는 [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]].

### 왜 batch는 flyway를 의존하지 않는가 — 스키마 소유는 web 한 곳

배치는 api와 **같은 DB**를 쓰지만, 스키마 마이그레이션(flyway)은 의존하지 않는다.

```kotlin
"implementation"(project(":core:research"))
"implementation"(project(":core:food"))
"implementation"(project(":core:avoidance"))
"runtimeOnly"(project(":infra:persistence"))
```
`build.gradle.kts:14-17` (주석: "research 도메인 로직 + food/avoidance 입력 수집 + persistence 어댑터 런타임 조립")
- `:core:research/food/avoidance`를 `implementation`으로 직접 의존 — 잡이 이 도메인 코드를 컴파일 타임에 부른다.
- `:infra:persistence`는 `runtimeOnly` — 대기열 어댑터 같은 구현체를 **실행 시점에만** 필요로 한다. 그래서 도메인 port에만 의존하고 구현은 런타임에 끼운다.
- **이 build 파일에 flyway가 없다**(`grep flyway` → 없음). 반면 `app/api/build.gradle.kts:22-25`는 `spring-boot-flyway`·`flyway-core`·`flyway-mysql`을 의존한다.

즉 **DB 스키마의 소유권은 web(api) 한 곳**에 있다. web이 마이그레이션으로 테이블을 만들고 바꾸며, 배치는 이미 존재하는 그 DB를 **읽기만** 한다(대기열 조회). 배치가 스키마를 건드리지 않으니 두 앱이 같은 테이블을 서로 마이그레이션하겠다고 충돌할 일이 없다. Flyway가 무엇인지·왜 한 곳이 소유해야 하는지는 [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기]].

DB 연결 자체는 이 파일이 아니라 런타임 프로필이 공급한다 — `application.yml:78-80`이 "배치는 persistence를 조립해 부팅 시 JPA/데이터소스가 필요하므로 런타임에 프로필(`SPRING_PROFILES_ACTIVE=local` 등)을 지정한다"고 명시한다.

## 입출력 — 어떻게 실행하고 무엇이 나오나

이 노트가 다루는 "실행 골격"의 입출력은 **실행 명령**과 **집계 로그 한 줄**이다. 청크가 만드는 산출 DTO(`FoodScoringResult`)의 형태는 [[20. LLM 스코어링 파이프라인 — 한 청크가 3모델 병렬을 거쳐 신뢰도가 되기까지]]가 다룬다.

**실행 (기본 off이므로 인자로 켬)** — `application.yml:27-29` 주석:
```
java -jar batch.jar --meogo.scoring.runner.enabled=true --meogo.scoring.chunk-size=20
MEOGO_SCORING_RUNNER_ENABLED=true MEOGO_SCORING_CHUNK_SIZE=20 java -jar batch.jar
./gradlew :app:batch:bootRun --args='--meogo.scoring.runner.enabled=true'
```
- 프로퍼티 우선순위는 커맨드라인 인자 > 환경변수 > yml 기본값(`application.yml:26`). 재배포 없이 실행 시점에 청크 크기나 on/off를 조정한다.
- LLM을 실제로 켜려면 `meogo.llm.<openai|upstage|gemini>.enabled=true`와 api-key(.env 주입)도 함께 필요하다(`application.yml:38-40`). 기본 off + 키 미설정이면 caller 빈이 비어 부팅은 안전.

**출력 (프로세스가 남기는 것)** — 콘솔 로그 한 줄:
```
기피성분 스코어링 잡 완료 total=37 scored=30 failed=7
```
- `total` = 순회한 음식 수, `scored`/`failed`는 각 음식의 최종 상태 개수. 그 뒤 컨텍스트가 닫히고 프로세스가 끝난다. DB에 새로 써진 것은 없다(위 실측 참고).

> [!note] 실측 — 부분 실패는 청크 전체를 FAILED로 남긴다
> 한 청크의 `scoreChunk`는 3모델이 모두 성공·파싱·커버돼야 확정한다(`AvoidanceScoringJob.kt:88-90`). 하나라도 실패/파싱불가/커버리지 미달이면 그 청크의 음식 전부를 `FAILED`로 되돌린다(`:91-101`) — 재조사로 남기려는 정책이다. 그래서 위 로그의 `failed`는 "일부 모델만 실패한 청크"까지 포함한다. 이 판정 로직 자체는 노트 20의 몫이고, 여기선 로그 집계에 그대로 반영된다는 점만 짚는다. (spec은 이 "3개 모두 취합돼야 확정" 정책으로 이미 개정됨 — 낡은 것은 Jira DoD 문구뿐, 코드가 개정 스펙과 일치.)
