# 18. 회원 랭킹 흐름 — 원자적 카운트 증가와 조회 시점 점수 계산

프로필/랭킹 화면에서 내 **등급·점수·다음 등급까지 남은 점수·점수 내역**(리뷰·다양성·스캔)을 한 번에 받는다. 핵심은 두 가지다. ① 점수는 어딘가 저장해 둔 게 아니라 **조회할 때마다** 누적 카운트로 다시 계산된다. ② 그 카운트는 스캔할 때마다 DB가 **원자적으로 +1** 한다 — 엔티티를 로드해 고치는 방식이 아니다.

그래서 랭킹은 두 얼굴을 가진다. **증가(write)** 는 스캔 흐름([[14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]])에 얹힌 단일 호출이고, **조회(read)** 는 값 객체 하나 + 읽기 전용 유스케이스 하나다. 이 노트는 둘을 맞물려 본다.

---

## 이 노트의 척추 — 원자적 UPDATE vs 변경 감지

먼저 결론부터. 랭킹 카운트를 올리는 코드는 [[7. 영속성 컨텍스트와 엔티티 매핑]]에서 배운 **변경 감지(dirty checking)** 를 쓰지 **않는다**.

- **변경 감지 방식**(온보딩 프로필 수정 등, [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]): 엔티티를 SELECT로 로드 → 필드를 바꿈 → 트랜잭션이 끝날 때 영속성 컨텍스트가 "바뀐 걸 알아채고" UPDATE를 flush. **read → modify → write** 세 박자.
- **원자적 벌크 UPDATE 방식**(랭킹 증가): 로드 없이 `update member set scan_count = scan_count + 1 where id=…` 한 방을 DB에 직접 쏜다. **한 박자.**

왜 굳이 다르게? **동시성 때문이다.** 이건 아래 [[#흐름 A — 증가(write)]]에서 자세히 본다. 조회 쪽은 정반대로, 값을 읽어 계산만 하고 아무것도 쓰지 않는다(`@Transactional(readOnly = true)`). 한 노트에서 이 write ↔ read 대비를 같이 보는 이유다.

## 흐름 A — 증가(write)

랭킹 증가에는 **엔드포인트가 없다.** 사용자가 "점수 올려줘"를 호출하는 게 아니라, 메뉴판을 스캔하면 스캔 유스케이스가 판정을 끝낸 뒤 곁다리로 카운트를 올린다.

| 계층 | 파일 | 하는 일 |
|---|---|---|
| 호출 지점 | `application/client/.../scan/usecase/ScanUseCase.kt:55-63` | 스캔 판정·이력 저장 끝에 `recordScanCount(memberId)` → `memberRepository.increaseScanCount(memberId)` (메뉴판 1장 = 1회) |
| port | `core/member/.../MemberRepository.kt:12` | `fun increaseScanCount(memberId: Long)` — 도메인이 아는 건 이 **인터페이스**뿐 |
| adapter | `infra/persistence/.../member/MemberRepositoryAdapter.kt:37-43` | JPA 벌크 UPDATE를 호출하고, 영향받은 행이 `0`이면 `MEMBER_NOT_FOUND` 예외 |
| 벌크 UPDATE | `infra/persistence/.../member/MemberJpaRepository.kt:18-28` | `@Modifying @Query` — DB에 UPDATE 한 방. **원자적·변경 감지 우회** |
| 스키마 | `infra/persistence/.../member/MemberJpaEntity.kt:47-54` | `scan_count`·`review_count`·`unique_reviewed_food_count` 컬럼(전부 not-null, 기본값 0) |

### 벌크 UPDATE 실코드

```kotlin
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query(
    """
    update MemberJpaEntity m
    set m.scanCount = m.scanCount + 1
    where m.id = :memberId
      and m.memberStatus = com.meogo.infra.persistence.member.MemberStatus.ACTIVE
      and m.status = com.meogo.infra.persistence.EntityStatus.ACTIVE
    """,
)
fun increaseScanCount(@Param("memberId") memberId: Long): Int
```
`MemberJpaRepository.kt:18-28`

줄 단위 풀이(주석 금지 레포라 발췌 아래에 푼다):
- `set m.scanCount = m.scanCount + 1` — 현재 값을 앱으로 읽어오지 않는다. "지금 DB에 있는 값에 1 더해라"를 **DB가** 실행한다. 이게 원자성의 핵심.
- `@Modifying` — 이 `@Query`가 SELECT가 아니라 UPDATE/DELETE임을 Spring Data JPA에 알린다. 없으면 실행되지 않는다.
- `flushAutomatically = true` — UPDATE를 보내기 **전에** 영속성 컨텍스트에 쌓인 다른 변경을 먼저 flush(순서 꼬임 방지).
- `clearAutomatically = true` — UPDATE **후에** 영속성 컨텍스트를 비운다. 벌크 UPDATE는 DB만 바꾸고 메모리에 캐시된 엔티티는 낡은 채 남기 때문에, 비워서 낡은 엔티티 재사용을 막는다. ([[7. 영속성 컨텍스트와 엔티티 매핑]]의 캐시 개념과 이어짐)
- 반환값 `Int` — 실제로 바뀐 행 수. `where`의 상태 조건(탈퇴/정지 회원 제외)까지 안 맞으면 `0`.
- `memberStatus = ACTIVE and status = ACTIVE` — 정지 회원과 소프트 삭제된 행을 JPQL 안에서 직접 걸러낸다. 평소 조회처럼 `BaseEntity`의 `@SQLRestriction`(소프트 삭제 자동 필터 — [[7. 영속성 컨텍스트와 엔티티 매핑]] §BaseEntity 참고)이 자동으로 붙지 않으므로(벌크 UPDATE 경로) 조건을 명시한다.

### 왜 이게 lost update를 막나 (동시성)

[[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]]에서 본 것처럼 JVM 서버는 요청마다 스레드를 하나씩 꺼내 **동시에** 돌린다. 같은 회원이 메뉴판 두 장을 거의 동시에 스캔하면 스레드 두 개가 함께 이 코드에 닿는다.

변경 감지 방식이었다면 이렇게 깨진다(이게 **lost update**):

```
스레드1: scan_count 읽음 → 5
스레드2: scan_count 읽음 → 5   (아직 1이 저장 안 됨)
스레드1: 6으로 UPDATE
스레드2: 6으로 UPDATE          ← 5+1+1=7이어야 하는데 6. 한 번 증가가 증발
```

`set scan_count = scan_count + 1`은 읽기·더하기·쓰기를 **DB 한 문장 안에서** 처리해 이 경합이 원천적으로 없다. 두 문장이 순서대로 실행돼 5→6→7이 된다. FE로 치면, 여러 탭이 동시에 `count+1` 하는 상황을 클라이언트 상태에서 계산하지 않고 서버의 원자적 증가에 맡기는 것과 같다(비유이며, DB 락 수준까지 완전 동치는 아님).

adapter 쪽 처리:

```kotlin
@Transactional
override fun increaseScanCount(memberId: Long) {
    val updated = memberJpaRepository.increaseScanCount(memberId)
    if (updated == 0) {
        throw MemberException(MemberErrorCode.MEMBER_NOT_FOUND)
    }
}
```
`MemberRepositoryAdapter.kt:37-43` — 반환된 행 수가 0이면(=조건에 맞는 회원이 없으면) 회원 없음 예외로 바꾼다.

### 점수는 저장이 아니라 "조회 시점 계산"

DB에 저장되는 건 **카운트 3개뿐**이다(`scan_count`·`review_count`·`unique_reviewed_food_count`). 점수·등급 같은 파생값은 컬럼이 없다. 엔티티를 도메인으로 되살릴 때(`toDomain`) 그 카운트로 `Ranking`을 만들고, `Ranking`이 내부에서 계산한다.

```kotlin
class Ranking private constructor(
    val scanCount: Int,
    val reviewCount: Int,
    val uniqueReviewedFoodCount: Int,
) {
    val reviewPoints: Int = reviewCount * REVIEW_POINTS        // ×10
    val diversityPoints: Int = uniqueReviewedFoodCount * DIVERSITY_POINTS  // ×5
    val scanPoints: Int = scanCount * SCAN_POINTS             // ×2

    val score: Int = reviewPoints + diversityPoints + scanPoints
    val tier: RankingTier = RankingTier.of(score)
    val nextTier: RankingTier? = tier.next
    val pointsToNext: Int? = nextTier?.let { it.minScore - score }
    ...
```
`Ranking.kt:3-18`

줄 단위 풀이:
- **`private constructor` + `of`/`initial` 팩토리** — 밖에서 `new` 못 한다. 반드시 `Ranking.of(...)`를 거치고, 거기서 `require(... >= 0)`로 음수 카운트를 막는다(불변식을 생성자 한 곳에 몰아둠).
- **계산 프로퍼티** — `score`·`tier` 등은 필드에 값을 넣어 두는 게 아니라, 객체가 만들어질 때 카운트로부터 즉시 계산돼 확정된다. 저장값이 아니다.
- 한 번 만들어지면 값이 안 바뀌는 **불변 값 객체**다. 점수 올리기는 새 카운트로 새 `Ranking`을 만드는 것이지 기존 것을 수정하는 게 아니다.

이 계산 로직·정책이 `infra`(JPA)나 `app/api`(web)가 아니라 순수 도메인(`core:member`)에 사는 건 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]·[[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]의 규칙이다. 점수식을 바꾸려면 DB나 컨트롤러가 아니라 `Ranking.kt` 한 곳만 고치면 된다.

### 등급 판정

```kotlin
enum class RankingTier(val level: Int, val minScore: Int) {
    NEWCOMER(1, 0), TASTER(2, 30), EXPLORER(3, 80), REGULAR(4, 180),
    GOURMET(5, 350), KFOOD_MASTER(6, 600), KOREAN_AT_HEART(7, 1000),
    ;
    val key: String = name.lowercase()
    val next: RankingTier? get() = entries.getOrNull(ordinal + 1)

    companion object {
        fun of(score: Int): RankingTier = entries.last { score >= it.minScore }
    }
}
```
`RankingTier.kt:3-21`

- `of(score)` — 진입 점수(`minScore`)를 넘긴 등급 중 **마지막 것**을 고른다. 점수 80이면 explorer(80) 진입, 179까지 explorer, 180부터 regular.
- `next` — enum 정의 순서상 바로 다음 등급. 최고등급 `KOREAN_AT_HEART`이면 `getOrNull`이 `null`을 돌려주고, 그래서 `nextTier`·`pointsToNext`가 `null`이 된다("만렙" 표시).
- `key`(소문자 스네이크)와 `level`(숫자)을 응답에 실어 보낸다. **등급명 번역은 클라이언트 몫**이라 서버는 안정 키만 내려준다(`MemberApi.kt:99-103,122-125`).

## 계층 경계에서 모듈이 바뀌는 이유

이 흐름은 4개 Gradle 모듈([[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]]에서 본 멀티모듈)을 가로지른다. 경계마다 이유가 있다:

- **Controller(`app:api`) → UseCase(`application:client`)**: 컨트롤러는 HTTP만 안다(누가 요청했나 = `@AuthMemberId`로 memberId 주입, [[16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]]). "무엇을 할지"는 유스케이스가 안다. 둘 다 생성자 주입으로 조립된다([[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]]·[[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]).
- **UseCase(`application:client`) → 도메인(`core:member`)**: 유스케이스는 트랜잭션 경계를 긋고([[6. 설정과 프로필, 트랜잭션 첫걸음]]), 점수 계산 규칙은 손대지 않는다. 규칙은 `Ranking`이 소유. 그래서 규칙을 바꿔도 유스케이스는 그대로다.
- **도메인 → 영속(`infra:persistence`)**: 도메인은 `MemberRepository` **인터페이스(port)** 만 알고 JPA를 모른다. `increaseScanCount`가 벌크 UPDATE인지 변경 감지인지는 어댑터가 정한다 — 도메인은 "카운트를 1 올려라"만 말한다. 의존이 안쪽(도메인)을 향하는 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]의 핵심.

## 요청/응답 JSON

요청: 바디 없음. `Authorization: Bearer {accessToken}`만 필요(회원 식별은 토큰에서).

```
GET /api/v1/members/me/ranking
Authorization: Bearer eyJhbGciOi...
```

응답(스캔 9회, 리뷰·다양성 0인 회원):

```json
{
  "code": "SUCCESS",
  "data": {
    "tier": "newcomer",
    "level": 1,
    "score": 18,
    "nextTier": "taster",
    "pointsToNext": 12,
    "breakdown": {
      "reviews":   { "count": 0, "points": 0 },
      "diversity": { "count": 0, "points": 0 },
      "scans":     { "count": 9, "points": 18 }
    }
  }
}
```

- 바깥 `code`/`data` 껍데기는 전 API 공통 `BaseResponse`.
- `breakdown`의 3항목은 화면 "점수 내역"에 그대로 대응. `scans.points = 9 × 2 = 18`.
- `score 18`이면 taster 진입선(30)까지 `pointsToNext = 30 - 18 = 12`.
- 응답 DTO를 `MemberRankingResult`(평평)와 `MemberRankingResponse`(`breakdown` 중첩)로 나눈 건 [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]에서 본 계층별 DTO 분리와 같다. 화면 모양(중첩)이 유스케이스 결과 모양(평평)에 새지 않게 web 계층에서만 재조립한다.

> [!warning] 스펙과 다름 — 지금 실제로 오르는 점수는 스캔뿐
> spec의 Acceptance 예시(US1: "리뷰 8개·음식 6종·스캔 9회 → 128점")는 **리뷰 기능이 있는 미래 상태**를 가정한다. 코드 실측으로는 `increaseScanCount`만 존재하고 **`reviewCount`·`uniqueReviewedFoodCount`를 올리는 경로가 없다** — 엔티티 기본값 0에서 안 바뀐다(`MemberJpaEntity.kt:50,53`). 그래서 현재 실제로 오르는 점수는 `scanCount × 2`뿐이다.
> 같은 레포의 **Swagger는 코드와 일치**한다("리뷰 기능 도입 전이라 reviews·diversity 는 현재 항상 0", `MemberApi.kt:125`). 어긋난 건 spec의 AS 예시 하나뿐이다.
> 점수식·등급표 자체는 리뷰·다양성까지 `Ranking.kt`에 **다 구현·테스트돼 있다**(리뷰 도메인이 붙는 날 바로 살아난다). 이 노트의 점수식·등급 설명은 코드 기준이므로 그대로 유효하다.

## 관련 테스트가 보장하는 것

- **`core/member/.../RankingTest.kt`** — 점수 산출과 등급 정책 전부를 도메인 단위로 못박는다: 점수식(리뷰×10+다양성×5+스캔×2 = 128), 항목별 내역 합이 총점과 같음, 등급 경계값(진입 점수와 정확히 같으면 상위, 직전이면 하위), 최고등급이면 `nextTier`/`pointsToNext`가 `null`, 음수 카운트 예외, 안정 키(`kfood_master` 등). **리뷰 입력을 넣은 케이스도 통과**한다 — 위 warning처럼 도메인은 리뷰를 계산할 준비가 돼 있고, 막힌 건 프로덕션의 증가 경로일 뿐임을 이 테스트가 증명한다.
- **`application/client/.../member/MemberRankingUseCaseTest.kt`** — 조회 유스케이스: 스캔만 반영된 랭킹을 돌려줌, 리뷰·다양성은 0, 스캔 이력 없으면 0점 newcomer, 존재하지 않는 회원이면 `MEMBER_NOT_FOUND`. `FakeMemberRepository`로 port를 가짜 구현해 DB 없이 검증(port 분리 덕).
- **원자적 증가의 동시성 보장**은 이 두 테스트가 아니라 **스캔 쪽**이 커버한다([[14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]]). `increaseScanCount`의 벌크 UPDATE·행 수 0 → 예외는 `MemberRepositoryAdapter` 통합 테스트 영역이다.

테스트 스타일(Kotest `BehaviorSpec`, given/when/then 한국어)과 그 배경은 [[12. SDD와 TDD — 스펙과 테스트로 개발하기]] 참고.

## 남은 것 (forward)

- **리뷰 기능이 붙으면** `reviewCount`·`uniqueReviewedFoodCount` 증가 경로가 생겨 점수 3항목이 다 살아난다. 도메인·테스트는 이미 준비돼 있어 증가 경로만 추가하면 된다.
- **홈 화면(note 17)과는 접점이 없다.** 홈은 랭킹을 조회하지 않는다(인기 음식은 랜덤). 랭킹은 프로필/랭킹 화면 전용. (일부러 `[[링크]]`를 걸지 않았다 — 접점이 없어 그래프에 연결을 만들지 않는다.)
