# 🗺️ kbap 백엔드 공부 지도

이 지도는 2026-07 커리큘럼의 기록이다. 재구축은 2026-08-27 완주했다 — 현행 커리큘럼 29노트는 전부 새 지도에 있다. 여기 21노트는 그 시점의 코드를 알고 싶을 때만 본다.

프론트엔드(React Native/Expo)만 해온 내가 **kbap-server**(Kotlin·Spring Boot 백엔드)에 합류하기 위한 커리큘럼이다. 이 노트는 목차이자 진도표 — 각 단계를 끝낼 때마다 체크한다.

> [!info] 읽는 순서의 원칙
> 아래에서 위로 쌓는다. 각 단계는 **바로 앞 단계 지식만 전제**한다. "서버가 뭔지"(1단계)를 알아야 "스프링이 그 서버를 어떻게 조립하는지"(2단계)가 보이고, 조립을 알아야 "데이터를 어떻게 저장하는지"(3단계), 그 위에서 "왜 이런 구조로 나눴는지"(4단계)를 이해한다. 5단계부터는 실제 코드 한 흐름을 세로로 관통하며 앞의 개념들을 한꺼번에 확인한다.

---

## 1단계 · 백엔드 기초 — 서버라는 프로그램
> 왜 먼저: FE는 "화면을 그리는 코드"였다. 백엔드는 "켜두고 요청을 기다리는 프로그램"이다. 이 세계관 전환이 없으면 뒤 단계 전부가 공중에 뜬다.

- [x] [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]] — 서버 프로세스·포트·진입점(main), kbap가 web/batch 두 개로 도는 이유
- [x] [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]] — 스레드풀 vs 이벤트루프, 블로킹 호출이 JVM에선 왜 괜찮은지
- [x] [[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]] — JVM·Kotlin·Gradle 멀티모듈, TS와 대비한 컴파일 언어의 안전망

## 2단계 · Spring 핵심 — 부품을 직접 만들지 않는 프레임워크
> 왜 먼저: 1단계에서 "서버가 뜬다"를 알았다. 그 서버 안에서 객체들을 누가·어떻게 연결하는가가 스프링의 전부다. IoC/DI를 모르면 실코드에서 `@Autowired`·생성자 주입이 마법으로 보인다.

- [x] [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]] — 부품을 직접 `new` 하지 않고 컨테이너가 조립·주입. React 루트가 Provider를 조립하는 것과 대비
- [x] [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]] — 생성자 주입, Controller/UseCase/도메인 계층 분리. FE의 화면/훅/유틸 분리와 대비
- [x] [[6. 설정과 프로필, 트랜잭션 첫걸음]] — `application.yml`·프로필 4종, `@Transactional`이 여는 "작업 경계"의 개념

## 3단계 · JPA·영속성 — 객체를 DB에 저장하기
> 왜 먼저: 2단계에서 계층을 나눴다. 그 맨 아래 계층이 DB와 대화한다. 영속성 컨텍스트·LAZY·N+1은 백엔드 버그의 최대 진원지라 개념을 먼저 잡아야 한다.

- [x] [[7. 영속성 컨텍스트와 엔티티 매핑]] — JPA가 객체↔테이블을 잇는 법. React Query 캐시와 대비한 영속성 컨텍스트
- [x] [[8. LAZY 로딩과 N+1 문제]] — 왜 kbap는 전부 `FetchType.LAZY` + fetch join 규약인지
- [x] [[9. Flyway 마이그레이션 — 스키마를 코드로 관리하기]] — 스키마 버전 관리, timestamp 버전 규칙

## 4단계 · 아키텍처·방법론 — 왜 이렇게 나눴나
> 왜 먼저: 1~3단계로 "부품·조립·저장"을 안다. 이제 kbap가 그것들을 왜 core/infra/app 모듈로 쪼개고 도메인을 Spring-free로 두는지 — 코드를 읽을 때 매번 마주칠 "경계"의 이유를 배운다.

- [x] [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]] — 도메인이 ORM·Spring을 모르게 두는 이유, port/adapter 역전
- [x] [[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]] — 바운디드 컨텍스트, Gradle 멀티모듈 경계(ArchUnit 강제). 모노레포 패키지와 대비
- [x] [[12. SDD와 TDD — 스펙과 테스트로 개발하기]] — spec→plan→tasks 흐름, Kotest BehaviorSpec Red→Green→Refactor

## 5단계 이후 · 실코드 한 흐름 관통하기
> 왜 나중에: 개념(1~4단계)을 손에 쥔 뒤라야, 하나의 요청이 Controller→UseCase→도메인→영속을 지나는 걸 따라가며 "아 이게 그거였구나"가 된다. 아래는 `specs/`를 훑어 **사용자 가치가 크고 계층을 넓게 지나가는** 순서로 고른 후보다. 실제 진행 시 그때 계획서를 새로 뽑는다.

- [x] ① [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]] (`kb-104`, `kb-124`) — 유저 첫 접점. Controller→UseCase→member 도메인→persistence(profile JSON)를 얇게 관통. *가장 쉬운 세로 슬라이스라 첫 실코드로 추천*
- [x] ② [[14. 메뉴판 스캔 판정 흐름 — 메뉴명이 위험도가 되기까지]] (`001-menu-scan-mock`, scan 도메인) — 앱의 핵심 가치. 메뉴명+바운딩박스 수신→위험도 4단계 판정→scan 이력 저장. FE의 [[OCR 메뉴 스캔 — 박스 그룹핑]]가 만든 입력이 여기로 들어온다
- [x] ③ [[17. 홈 화면 조회 흐름 — 세 섹션을 한 응답으로 모으기]] (`kb-111`) — 여러 도메인(기피 성분·인기 음식·최근 스캔)을 한 응답으로 모으는 read 경로. fan-in 조합을 UseCase에서 보는 예
- [x] ④ [[15. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]] · [[16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃]] (`kb-118`) — 로그인. 필터라는 횡단 계층, 응답 본문 Bearer 발급/재발급. 내 기존 [[OAuth 2.0과 OIDC — 소셜 로그인의 원리]]와 이어짐
- [x] ⑤ [[18. 회원 랭킹 흐름 — 원자적 카운트 증가와 조회 시점 점수 계산]] (`kb-123`) — 도메인 값 객체(`Ranking`) 설계, DB 원자적 증가로 동시성 lost update 막기, 조회 시점 계산
- [x] ⑥ [[19. 배치 실행 골격 — 두 번째 실행 파일과 조사 대기열 순회]] · [[20. LLM 스코어링 파이프라인 — 한 청크가 3모델 병렬을 거쳐 신뢰도가 되기까지]] (`kb-53`) — 두 번째 bootJar(batch)+`infra:llm`. 가상스레드 fan-out으로 3모델 병렬→consensus 집계. 가장 넓게 관통하는 고급 흐름이라 마지막
