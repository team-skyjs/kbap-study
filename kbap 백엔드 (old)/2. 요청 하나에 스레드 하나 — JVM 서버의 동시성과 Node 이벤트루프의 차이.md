# 2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이

> [!summary] 한 줄 요약
> Node는 스레드 하나(**이벤트루프**)가 모든 요청을 번갈아 처리했다. JVM 서버(kbap)는 요청이 올 때마다 **스레드풀**에서 스레드를 하나 꺼내 그 요청만 전담시킨다 — 그래서 DB 조회처럼 "기다리는" 코드를 편하게 **블로킹**으로 짜도 서버 전체가 멈추지 않는다.

이전 노트: [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]] 에서 "서버는 포트를 열고 요청을 기다리는 프로세스"라는 걸 잡았다. 이 노트는 그 서버가 **동시에 들어오는 여러 요청을 어떻게 나눠 처리하는가**를 다룬다.

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 |
|---|---|---|
| 스레드(thread) | 한 프로그램(프로세스) 안에서 코드를 실행하는 **일꾼 한 명**. 여러 스레드는 같은 메모리를 공유하며 동시에 돈다. | JS엔 직접 대응물이 거의 없음 — JS는 기본적으로 일꾼이 한 명뿐이었다 |
| 스레드풀(thread pool) | 일꾼(스레드)을 미리 여러 명 만들어 대기시켜 둔 **대기조**. 요청이 오면 한 명 꺼내 쓰고, 끝나면 반납받아 재사용한다. | 커넥션 풀·워커 풀과 같은 "미리 만들어 돌려쓰는 자원 주머니" 발상 |
| 블로킹(blocking) | 어떤 호출이 끝날 때까지 그 스레드가 **멈춰서 기다리는** 것. 기다리는 동안 그 스레드는 다른 일을 못 한다. | `await fetch()` 를 안 쓰고 결과가 나올 때까지 줄을 붙잡는 느낌 |
| 논블로킹(non-blocking) | 기다리지 않고 "끝나면 알려줘" 하고 **바로 다음 일로 넘어가는** 것. | JS의 `Promise`/콜백/`async-await` 그 자체 |
| 이벤트루프(event loop) | 스레드 하나가 "할 일 목록"을 계속 돌면서, 준비된 작업만 골라 조금씩 처리하는 방식. | Node의 실행 모델 — 네가 이미 아는 그것 |

## 원리 — 요청 하나의 여정

kbap 같은 JVM 웹 서버는 내부에 **내장 톰캣(embedded Tomcat)** 이라는 웹 서버 엔진을 품고 있다. 톰캣은 [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일|서버가 열어둔 포트]]로 들어오는 HTTP 요청을 받아 스레드풀로 분배하는 역할을 한다. 요청 하나가 처리되는 흐름은 이렇다.

1. 브라우저/앱이 포트로 요청을 보낸다 (예: `POST /api/v1/scans`).
2. 톰캣이 소켓에서 요청을 받는다.
3. 톰캣이 **스레드풀에서 노는 스레드 한 명을 꺼내** 이 요청에 배정한다.
4. 그 스레드가 컨트롤러 → 유스케이스 → DB 조회까지 **처음부터 끝까지** 실행한다.
5. 응답을 다 만들어 돌려보낸다.
6. 스레드는 **풀로 반납**되어 다음 요청을 기다린다.

핵심은 **"요청 하나 = 스레드 하나"** 라는 점이다. 요청 A를 처리하는 스레드와 요청 B를 처리하는 스레드는 서로 다른 사람이고, 동시에 나란히 돈다.

kbap에서 3번(스레드가 컨트롤러에 도착하는 지점)의 실물은 컨트롤러의 핸들러 메서드다.

```kotlin
@RestController
@RequestMapping(ApiPaths.V1 + "/scans")
class ScanController(
    private val scanUseCase: ScanUseCase,
) : ScanApi {
    override fun scan(
        @AuthMemberId memberId: Long,
        @RequestBody request: ScanRequest,
    ): ResponseEntity<BaseResponse<ScanResponse>> {
        val result = scanUseCase.assessMenuBoard(request.toInput(memberId))
        return ResponseEntity.ok(BaseResponse.ok(ScanResponse.from(result)))
    }
}
```
`app/api/src/main/kotlin/com/meogo/app/api/scan/ScanController.kt:12`

- `scan(...)` 이 요청 하나를 처리하는 함수다. 톰캣이 배정한 스레드가 이 함수 몸통을 위→아래로 쭉 실행한다.
- `scanUseCase.assessMenuBoard(...)` 안에서 DB 조회 등 오래 걸리는 일이 일어나도, 그 스레드는 그 자리에서 **기다린다**(블로킹). 다음 줄 `return` 은 결과가 나온 뒤에야 실행된다.
- 이 함수는 "동시성"을 신경 쓰는 코드가 **한 줄도 없다**. 동시 처리는 톰캣이 스레드를 여러 개 배정해 각각 이 함수를 독립적으로 돌려주는 것으로 해결된다. 그래서 우리는 마치 요청이 나 하나뿐인 것처럼 단순하게 짜면 된다.
- 발췌 곳곳의 `@RestController`·`@AuthMemberId` 같은 `@` 표시(애너테이션)는 스프링이 이 클래스를 조립하고 요청을 연결할 때 읽는 라벨이다 — 의미는 2단계(Spring 핵심)에서 다룬다.

> [!note] kbap의 스레드풀은 어디에 설정돼 있나 (레포 실측)
> kbap의 `app/api/src/main/resources/application.yml` 에는 스레드풀 크기 설정이 **따로 없다** — `server:` 블록엔 프록시 헤더 설정(`forward-headers-strategy`)만 있다(`app/api/src/main/resources/application.yml:1`). 설정을 안 하면 톰캣 **기본값**이 그대로 쓰인다: 최대 스레드 200명, 최소 대기 25명. 즉 kbap은 동시 요청 200개까지는 각각 스레드를 붙여 처리하고, 그 이상은 큐에서 대기시킨다. (숫자를 바꾸려면 `server.tomcat.max-threads` 같은 프로퍼티를 추가하면 되지만, 지금 레포는 손대지 않았다.)

## 스레드풀 vs 이벤트루프 — Node를 알던 눈으로 보기

네가 Node에서 쓰던 모델과 정면으로 대비하면 이렇다.

| | Node (네가 알던 것) | JVM 서버 (kbap) |
|---|---|---|
| 요청을 처리하는 일꾼 | **스레드 1명**(이벤트루프)이 전부 | 요청마다 **스레드 1명씩** 풀에서 배정 |
| 동시성을 얻는 법 | 한 명이 대기 중인 작업들을 **번갈아** 처리 | 여러 명이 **진짜로 나란히** 처리 |
| "기다리는 코드"의 기본형 | 논블로킹(`await`/`Promise`) — 안 그러면 전체가 멈춤 | 블로킹 — 그 스레드만 멈추고 남들은 계속 감 |
| 코드를 짜는 느낌 | 곳곳에 `async`/`await` | 그냥 위에서 아래로 순서대로 (동기처럼) |

**어디까지 같고 어디서부터 다른가:** 둘 다 "요청 하나가 오래 걸려도 다른 요청이 굶지 않게 한다"는 **목표는 같다**. 다른 건 그 목표를 이루는 방법이다. Node는 **일꾼을 안 늘리고**(1명 유지) 그 한 명이 절대 한 곳에서 멈추지 않도록 모든 I/O를 논블로킹으로 만들어 해결한다. JVM 서버는 반대로 **일꾼을 여러 명 두고**(스레드풀) 한 명쯤 멈춰도 괜찮게 만든다. 그래서 Node에선 "블로킹 코드"가 죄악이지만, JVM 서버에선 자연스러운 기본값이다.

> [!tip] FE 비유
> 카페로 치면 — **Node**는 바리스타 한 명이 주문 여러 개를 요령껏 번갈아 만드는 가게다. 이 바리스타가 원두 배송을 기다리며 문 앞에 멍하니 서 있으면(블로킹) 가게 전체가 멈춘다. **JVM 서버**는 바리스타를 200명 고용해 손님 한 명당 한 명을 붙이는 가게다. 한 바리스타가 원두를 기다리며 서 있어도 나머지 199명은 계속 커피를 만든다.
> **경계:** 비유는 "왜 블로킹이 각자 다르게 취급되나"까지만 맞다. 실제로 스레드 200명은 카페 직원과 달리 같은 재료 창고(=메모리)를 **공유**하므로, 두 명이 같은 물건을 동시에 건드리면 문제가 생긴다(아래 [[#주의점 — 여러 스레드가 같은 것을 건드리면?|주의점]] 참고). 카페 직원은 남의 손을 침범하지 않지만 스레드는 침범할 수 있다.

## 블로킹 DB 호출이 JVM에선 왜 문제가 아닌가

FE 하다 백엔드 코드를 처음 보면 가장 이상한 게 이거다: **DB 조회를 `await` 없이 그냥 함수 호출로 쓴다.**

```kotlin
val result = scanUseCase.assessMenuBoard(request.toInput(memberId))
```

이 한 줄 안에서 DB를 다녀오는 데 예를 들어 50ms가 걸린다면, 그 50ms 동안 이 스레드는 **말 그대로 멈춰 서서** DB 응답을 기다린다(블로킹). Node였다면 이건 재앙이다 — 유일한 일꾼(이벤트루프)이 50ms 동안 얼어붙어 그동안 들어온 다른 요청을 하나도 못 받으니까.

그런데 JVM 서버에선 괜찮다. 이 요청을 맡은 스레드는 나 하나가 아니라 풀에 있는 200명 중 한 명이기 때문이다. 이 한 명이 DB 앞에서 멈춰 있는 동안, **다른 스레드들이 다른 요청을 계속 처리한다.** 멈춘 스레드는 그저 자기가 맡은 손님의 커피 재료를 기다릴 뿐, 가게를 막지 않는다.

정리하면:
- **Node**: 일꾼이 1명 → 멈추면 전부 멈춤 → 그래서 "절대 안 멈추는" 논블로킹 코드가 **필수**.
- **JVM**: 일꾼이 여럿 → 한 명 멈춰도 나머지가 감 → 그래서 편하게 읽히는 블로킹 코드를 **기본**으로 쓴다.

이 차이 하나가, 왜 백엔드 코드엔 `async`/`await`가 안 보이고 DB·외부 호출을 그냥 순서대로 부르는지를 설명한다.

## 가상 스레드 살짝 — kbap의 LLM fan-out

> [!warning] 모순 — 이 절이 가르치는 사실은 지금 코드에 **없다** (2026-08-27 확인)
> 아래에서 다루는 `newVirtualThreadPerTaskExecutor()` 기반 LLM fan-out(`LlmConfiguration.kt:71`)은 **레포에서 사라졌다.** 실측: kbap-server 전체에서 `virtual` 문자열 **0건**, `LlmConfiguration.kt` 는 83줄로 줄었고 `@Bean` 셋(비전 추출기·이미지 배치 클라이언트·임베딩 클라이언트)뿐이라 **실행기 빈이 하나도 없다**. 3모델 병렬 스코어링 자체가 `kbap-langchain` 별도 레포로 이관됐다.
> 그래서 **지금 kbap 은 가상 스레드를 아예 쓰지 않는다.** 아래 §"그럼 kbap 웹 요청도 가상 스레드로 도나?" 의 답("웹 요청은 아니고 fan-out 에서만")도 이제 절반이 틀렸다 — 웹 요청도 fan-out 도 아니다. 현행은 [[2. 요청 하나에 스레드 하나 — JVM 동시성과 Node 이벤트루프]] §6 이 정본이다(`spring.threads.virtual` 설정 0건 → 기본 `false`, 플랫폼 스레드 200개짜리 고전 톰캣 풀).
> 이 절은 **"가상 스레드가 무엇인가" 라는 개념 설명으로만** 읽는다. kbap 의 현재 사실로 읽으면 안 된다.

스레드풀 모델에도 한계가 있다. 스레드 한 명은 꽤 무겁다(OS가 관리하는 진짜 스레드라 메모리를 수백 KB씩 먹는다). 그래서 기본 200명 같은 상한이 생긴다. 만약 "동시에 수천 개를 기다려야 하는" 작업이 있으면 스레드가 모자란다.

JDK 21이 도입한 **가상 스레드(virtual thread)** 가 이걸 푼다. 가상 스레드는 JVM이 관리하는 아주 **가벼운 스레드**라, 수천~수만 개를 띄워도 부담이 적다. "기다리는 일이 많은" 작업에 특히 좋다.

kbap은 LLM(대형 언어 모델) 여러 개를 **동시에 호출**하는 곳에서 이걸 쓴다. 여러 모델에 같은 요청을 던지고 응답을 모으는 걸 **fan-out**(부채꼴로 펼쳐 던진다)이라 부른다. 실물은 이렇다.

```kotlin
@Bean
fun llmFanoutExecutor(): Executor = Executors.newVirtualThreadPerTaskExecutor()
```
`infra/llm/src/main/kotlin/com/meogo/infra/llm/config/LlmConfiguration.kt:71`

- `Executor` 는 "작업을 넘기면 알아서 스레드에 실어 돌려주는" 실행기다(스레드풀도 Executor의 한 종류).
- `newVirtualThreadPerTaskExecutor()` 는 넘어온 **작업 하나마다 가상 스레드를 새로 하나** 만들어 돌리는 실행기다. 가상 스레드는 싸서, 미리 풀을 만들어 아껴 쓸 필요 없이 그때그때 새로 뽑는다.
- `@Bean` 이 뭔지(스프링이 이 객체를 만들어 관리하는 것)는 2단계에서 다룬다. 지금은 "이 실행기를 준비해 둔다"로만 보면 된다.

이 실행기를 실제로 쓰는 곳:

```kotlin
private fun outcomeFuture(
    caller: LlmModelCaller,
    request: LlmChatRequest,
): CompletableFuture<CallOutcome> =
    CompletableFuture
        .supplyAsync({ caller.call(request) }, executor)
        .orTimeout(callTimeout.toMillis(), TimeUnit.MILLISECONDS)
        .handle { content, throwable -> ... }
```
`infra/llm/src/main/kotlin/com/meogo/infra/llm/client/LlmFanoutClient.kt:30`

- `CompletableFuture` 는 JVM판 `Promise` 라고 보면 된다 — "나중에 값이 채워질 상자".
- `supplyAsync({ caller.call(request) }, executor)` = "`caller.call(request)`(모델 한 개 호출)를 저 가상 스레드 실행기에 얹어 **비동기로 돌려라**". 모델마다 이걸 하나씩 만드니, 3개 모델이면 가상 스레드 3개가 동시에 각자 모델을 부른다.
- `.orTimeout(...)` 은 "이만큼 안에 안 오면 실패 처리". `.handle { ... }` 은 성공/실패를 정리한다.

**어디까지가 이 노트 범위인가:** 여기선 "kbap은 여러 개를 동시에 기다리는 자리에서 가상 스레드를 쓴다"까지만 안다. 이 fan-out을 **누가**(사용자 요청? 배치?) **왜** 부르는지, 부분 실패를 어떻게 다루는지는 [[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점|다음 노트]] 이후 5단계 배치 흐름에서 코드로 따라간다. (참고로 이 fan-out의 소비자는 웹 앱이 아니라 배치 앱이다 — 사용자 스캔 요청 경로의 LLM 정제는 모델 하나를 동기로 부른다.)

> [!info] 그럼 kbap 웹 요청도 가상 스레드로 도나?
> 아니다. 스프링 부트는 `spring.threads.virtual.enabled=true` 를 켜면 톰캣의 요청 처리까지 가상 스레드로 바꿀 수 있는데, **kbap은 이 옵션을 켜지 않았다**(application.yml에 없음). 그래서 kbap의 일반 API 요청은 앞서 설명한 **평범한 톰캣 스레드풀(요청당 플랫폼 스레드)** 로 처리되고, 가상 스레드는 위 LLM fan-out 같은 곳에서만 **명시적으로** 쓴다. 이 둘을 헷갈리지 말 것.

## 주의점 — 여러 스레드가 같은 것을 건드리면?

스레드가 여럿이라는 건 공짜가 아니다. 스레드들은 **같은 메모리를 공유**하므로, 두 스레드가 같은 객체를 동시에 읽고 쓰면 값이 꼬일 수 있다. 이걸 **공유 상태(shared state)** 문제, 이런 상황에서도 안전한 코드를 **스레드 안전(thread-safe)** 하다고 한다.

Node에선 일꾼이 하나였으니 이 걱정이 거의 없었다 — 한 번에 한 곳만 실행되니까. JVM 서버는 진짜로 동시에 도는 일꾼이 여럿이라 이 문제가 실재한다.

지금 단계에서 감만 잡을 것:
- **매 요청마다 새로 만드는 값**(위 `ScanController` 의 지역 변수 `result`, 요청 객체 등)은 그 스레드만의 것이라 안전하다. 남과 공유하지 않는다.
- 위험한 건 **여러 요청이 공유하는 하나의 객체를 요청 중에 바꾸는** 경우다.
- kbap이 이 위험을 구조적으로 줄이는 장치 하나를 미리 언급하면: 도메인 객체를 **불변(immutable)** 으로 만든다(상태를 바꾸는 대신 새 객체를 반환). 한 번 만든 값이 절대 안 바뀌면 여러 스레드가 동시에 읽어도 꼬일 일이 없다. 이 규약과 이유는 뒤 단계(도메인/JPA)에서 실코드로 본다.

깊은 동기화 기법(락, `synchronized`, 원자적 연산 등)은 지금 범위 밖이다. **"스레드가 여럿이니 공유 상태를 함부로 바꾸면 위험하다"** 는 감각만 챙기면 된다.

## 용어집

- **스레드(thread)**: 프로세스 안에서 코드를 실행하는 일꾼. 여럿이 같은 메모리를 공유하며 동시에 돈다.
- **스레드풀(thread pool)**: 스레드를 미리 여러 개 만들어 두고 요청마다 꺼내 쓰고 반납받는 대기조.
- **톰캣(Tomcat)**: 스프링 부트 웹 앱에 내장돼 포트를 열고 요청을 스레드풀로 분배하는 웹 서버 엔진.
- **블로킹 / 논블로킹**: 호출이 끝날 때까지 스레드가 멈춰 기다림 / 안 기다리고 다음 일로 넘어감.
- **이벤트루프(event loop)**: 스레드 하나가 준비된 작업만 골라 번갈아 처리하는 Node의 실행 모델.
- **가상 스레드(virtual thread)**: JDK 21의 아주 가벼운 스레드. 수천 개를 띄워도 부담이 적어 "기다리는 일이 많은" 작업에 좋다.
- **fan-out**: 하나의 작업을 여러 대상(여기선 여러 LLM)에 동시에 펼쳐 던지고 결과를 모으는 패턴.
- **CompletableFuture**: JVM의 "나중에 채워질 값" 상자. JS의 `Promise` 에 대응.
- **공유 상태 / 스레드 안전**: 여러 스레드가 함께 쓰는 데이터 / 그런 상황에서도 안 꼬이는 코드.

## 체크리스트

- [ ] "요청 1개 = 스레드 1개"라는 그림을 말로 설명할 수 있다.
- [ ] Node(이벤트루프)와 JVM(스레드풀)이 "같은 목표, 다른 방법"인 이유를 안다.
- [ ] 백엔드 코드가 DB를 `await` 없이 부르는 게 왜 괜찮은지 안다.
- [ ] kbap 웹 요청은 톰캣 스레드풀, LLM fan-out만 가상 스레드라는 걸 구분한다.
- [ ] 스레드가 여럿이면 공유 상태가 위험해진다는 감을 잡았다.
