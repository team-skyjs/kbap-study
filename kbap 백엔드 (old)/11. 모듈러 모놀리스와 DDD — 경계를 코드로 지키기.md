# 11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기

> 작성: 2026-07-14 · 맥락: 1단계에서 "kbap은 Gradle 멀티모듈이다"라고 스쳐 봤다. 그 모듈 쪼개기가 사실은 **도메인 경계를 코드로 못 박는 설계**였다는 걸 묶는다.
> 목표: "왜 하나의 앱을 굳이 여러 모듈로 쪼개고, 그 경계가 안 무너지게 뭘로 강제하나?"를 30분 뒤의 나도 재현.

---

## 0. 한 줄 요약

kbap은 **하나로 배포하는(모놀리스) 서버를 도메인별 모듈로 쪼갠 "모듈러 모놀리스"**다. 각 모듈은 DDD의 **바운디드 컨텍스트**(자기 도메인 언어를 소유하는 경계)이고, 모듈 사이 의존은 **한 방향으로만** 흐르도록 고정한다. 그리고 이 경계는 문서로 부탁하는 게 아니라 **ArchUnit 테스트가 CI에서 위반을 빌드 실패로 막는다** — 규칙이 곧 실행되는 코드다.

---

## 1. 핵심 개념

| 구분 | 모듈러 모놀리스 | 바운디드 컨텍스트 | 단방향 의존 | ArchUnit |
|---|---|---|---|---|
| 정체 | 하나의 배포 단위(bootJar) 안을 여러 모듈로 나눈 구조 | 하나의 도메인 언어·모델이 통하는 경계(DDD 전략 설계 단위) | 모듈 A→B 의존은 되지만 B→A는 금지 = 화살표가 순환하지 않음 | 자바/코틀린 아키텍처를 **테스트 코드로 검증**하는 라이브러리 |
| kbap에서 | `com.meogo` 한 서버(실은 부트앱 2개가 같은 모듈 공유) | `core:food` · `core:member` · `core:scan` · `core:avoidance` · `core:research` Gradle 모듈 | `app → application → core:도메인 → core:kernel` | `ModuleBoundaryTest.kt` — 도메인이 Spring/JPA 쓰면 빌드 실패 |
| 왜 쓰나 | MSA의 운영 복잡도 없이 경계의 이점만 | 큰 모델을 작은 모델 여럿으로 쪼개 언어 충돌 방지 | 순환·계층 역전 방지 → 갈아끼우기·테스트가 국소화 | 경계가 "합의"가 아니라 "강제"가 되게 |

> 비유: 바운디드 컨텍스트는 **회사의 부서**다. 개발팀이 말하는 "배포"와 인사팀이 말하는 "배포(이동)"는 같은 단어라도 뜻이 다르다. 부서 경계 안에서만 그 단어가 한 가지 뜻으로 통한다 — 컨텍스트란 "한 단어가 한 뜻으로 통하는 범위"다. **여기까지 같고**, 다른 점: 부서는 조직도상 선일 뿐이지만 kbap의 컨텍스트는 **Gradle 모듈 + 패키지 + 테스트**로 물리적으로 격리돼 있어 넘으면 컴파일/빌드가 깨진다.

---

## 2. 원리

### 2-1. 모놀리스와 마이크로서비스, 그 사이

- **모놀리스**: 코드 전부가 한 덩어리 한 배포. 단순하지만, 내부가 얽혀 "아무 데서나 아무 걸 부르는" 진흙탕(big ball of mud)이 되기 쉽다.
- **마이크로서비스(MSA)**: 도메인마다 별도 서비스로 배포·격리. 경계는 확실하지만 네트워크·배포·트랜잭션·장애전파를 전부 운영해야 한다.
- **모듈러 모놀리스**: 배포는 하나(모놀리스)로 두되, 안은 도메인 모듈로 쪼개 경계를 준다. "쪼개되(모듈) 나누지는 않은(단일 배포)" 선택.

kbap이 MSA가 아닌 이유는 ADR-0001(`docs/adr/0001-multi-app-modular-layout.md`)·ADR-0008(`docs/adr/0008-modular-monolith-shared-domain.md`)에 나온다: MVP 단계라 운영 복잡도를 낮게 유지하고 싶고, 여러 도메인이 같은 MySQL·같은 도메인 모델을 재사용하므로 서비스로 쪼개면 같은 엔티티를 두 번 정의해 **드리프트(안전 직결 데이터의 불일치)** 위험이 생긴다.

> FE 비유: 프론트 모노레포(pnpm workspace)에서 `apps/`는 배포 단위, `packages/`는 공유 모듈로 나눈 것과 골격이 같다. **여기까지 같고**, 다른 점: FE 모노레포의 패키지 경계는 주로 *코드 재사용* 단위지만, kbap의 모듈 경계는 그 위에 **도메인 언어 경계(바운디드 컨텍스트)**라는 의미가 더 얹혀 있다.

### 2-2. 바운디드 컨텍스트 — Gradle 모듈이 곧 도메인 경계

1단계에서 "kbap = Gradle 멀티모듈(모노레포)"이라고만 봤던 것의 정체가 이것이다. `settings.gradle.kts`에 등록된 모듈 하나하나가 **바운디드 컨텍스트**다.

- `food`(음식·재료 카탈로그), `member`(회원·식이 제한), `scan`(메뉴판 스캔 이력), `avoidance`(위험도 판정), `research`(미스 메뉴 LLM 조사·배치 전용) — 이 다섯이 active 컨텍스트. `review`는 아직 기능을 안 만든 placeholder 모듈이다.
- 각 컨텍스트는 **자기 도메인 언어와 모델을 소유**한다. 예: `avoidance`는 위험도(`RiskLevel`: SAFE/CAUTION/DANGER/UNKNOWN)를, `member`는 식이 제한 프로필을 소유한다. 서로의 내부를 직접 알지 않는다.
- 공유가 필요한 최소한의 vocabulary(공통 타입·port 인터페이스·`LanguageCode` 같은 여러 컨텍스트 공용 코드)만 `core:kernel`에 둔다. kernel은 "공유 커널"이다 — 모두가 의존해도 되는 얇은 공통층.

핵심 규칙(레포 `docs/architecture/meogo-conventions.md`의 "도메인 간 의존 규칙"): **도메인끼리는 서로 직접 의존하지 않는다.** 여러 컨텍스트를 조합하는 유스케이스(예: 메뉴판 판정 = scan+food+member+avoidance)는 반드시 `application` 계층에서 조립한다. avoidance가 food 엔티티를 직접 들지 않고, application이 food 데이터를 `avoidance` 전용 입력 VO(Value Object, 값 객체 — id 없이 담긴 값 자체가 정체성인 작은 불변 객체)인 `AvoidanceInput`으로 변환해 넘기는 식이다.

### 2-3. 단방향 의존 — 화살표가 한 방향으로만

모듈 의존은 아래 한 방향으로만 흐른다(화살표 = "…에 의존한다"):

```
common        ← 아무에게도 의존 안 함 (leaf, Spring-free). 두 부트앱이 공유.

core:kernel   ← core:도메인(food/member/scan/avoidance/research/review) ← application:client
   ▲                                                                          ▲
   │  infra:persistence (JPA, 도메인 port 구현)  ── implementation ─┐          │
   │       ▲ runtimeOnly 조립                                       │          │
   └───────┴──────────────── app:api (web bootJar, 조립·Flyway owner)          │
                             app:batch (배치 bootJar) ── core 도메인 직접 의존 ─┘
```

- 안쪽(`core:kernel`, 도메인)은 바깥(application·infra·app)을 **모른다**. 화살표는 항상 바깥→안쪽.
- 왜 한 방향이어야 하나: 순환 의존이 생기면 A를 바꾸면 B가 깨지고 B를 바꾸면 A가 깨지는 진흙탕이 된다. 방향을 고정하면 안쪽(핵심 규칙)은 바깥(프레임워크·DB) 교체와 무관하게 안정적으로 남는다. 이게 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]에서 다루는 **의존성 역전을 모듈 차원에서 실현한 형태**다. (port/adapter의 정의와 역전 원리 자체는 그 노트에 있으니 여기서는 링크만 건다.)

> FE 비유: ESLint `import/no-cycle`이나 `no-restricted-paths`로 "utils가 features를 import하면 에러"를 거는 것과 목적이 같다. **여기까지 같고**, 다른 점: FE에서는 린트 규칙이라 우회(`eslint-disable`)가 쉽지만, kbap은 **Gradle 모듈 의존을 아예 선언하지 않아** 컴파일 클래스패스에서 타입이 안 보인다 + ArchUnit이 이중으로 막는다. 우회하려면 빌드 파일을 고쳐야 하니 훨씬 뻑뻑하다.

### 2-4. 경계를 코드로 강제 — 문서가 아니라 테스트가 벽

여기가 이 노트의 심장이다. 위의 "도메인은 Spring/JPA를 모른다", "도메인끼리 직접 의존 금지", "app:api는 영속/도메인을 직접 import 못 함" 같은 규칙은 **말로만 두면 언젠가 무너진다.** kbap은 이걸 `ModuleBoundaryTest.kt` 하나로 **빌드 시 검증**한다. 규칙을 어긴 import가 하나라도 들어오면 테스트가 빨개지고 빌드가 실패한다.

이 테스트가 3단계까지 봤던 규약들(도메인은 JPA를 모른다 / `@Entity`는 persistence에만 / 계층 역전 금지)이 **왜 실제로 안 무너지는지**의 답이다. 규약이 self-documenting 코드 + 리뷰뿐 아니라 자동 테스트로 받쳐져 있다.

> FE 비유: 타입체크·린트를 CI 필수 통과 조건으로 걸어 "규칙 어기면 머지 불가"로 만드는 것과 같다. **여기까지 같고**, 다른 점: 여기서 검사하는 건 스타일이 아니라 **아키텍처 의존 방향** 그 자체다.

### 2-5. 두 부트앱이 같은 도메인을 공유 (ADR-0008)

1단계 "실행 파일(bootJar)이 2개"([[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]])의 큰 그림이 여기서 완성된다. `app:api`(web)와 `app:batch`(배치)는 **별개 배포지만 같은 `core:도메인`·`infra:persistence`를 직접 재사용**한다(ADR-0008(`docs/adr/0008-modular-monolith-shared-domain.md`)).

- 예전 결정(과거 결정: ADR-0001(`docs/adr/0001-multi-app-modular-layout.md`)·ADR-0006(`docs/adr/0006-central-persistence-adapter-and-decoupled-batch.md`))에서는 batch를 "api 무의존·통합 이벤트로만 소통하는 디커플드 위성 앱"으로 뒀었다.
- 그런데 데이터 계층은 **이미 공유**였다(batch는 같은 MySQL을 쓰되 `flyway off`, 스키마 owner는 api). 디커플은 코드 레벨에만 있었다. 회피 성분 공통 코드·도메인 모델을 batch(LLM 파이프라인)도 써야 하는데, 이벤트로만 소통하면 같은 엔티티를 두 번 정의해야 하고 안전 직결 데이터가 어긋날 위험이 생긴다.
- 그래서 ADR-0008이 **모듈러 모놀리스로 전환**: 공유 계층(core·application·infra)을 최상위로 올리고 두 부트앱이 필요한 모듈을 직접 의존. **도메인·엔티티 중복 0, 단일 소스.**
- 트레이드오프(−): 앱 간 결합이 강해져 독립 배포·장애 격리가 약해진다. 단 DB가 원래 공유였으므로 손실은 제한적이다.

## 3. 실코드 예시

### 3-1. Gradle 모듈 = 바운디드 컨텍스트 (`settings.gradle.kts`)

```kotlin
include(
    ":core:kernel",       // 도메인 공유 커널 (Spring-free) — 공통타입·port·stereotype·공유 코드
    ":core:food",
    ":core:member",
    ":core:avoidance",
    ":core:research",
    ":core:review",
    ":core:scan",         // 스캔 이력 컨텍스트 (KB-111)
    ":application:client", // 사용자 API 유스케이스
    ":infra:persistence", // 영속 adapter — 도메인 port 구현
    ":infra:llm",         // LLM 외부 연동 어댑터 — 배치가 직접 의존
    ":app:api",           // web bootJar (조립)
    ":app:batch",         // batch bootJar — flyway off
    ":common",
)
```
`settings.gradle.kts:21-44`(발췌·모듈 목록만 추림)

- `core:` 아래 6개가 도메인 컨텍스트 모듈이다. Gradle에 이렇게 등록되어야 각 컨텍스트가 컴파일 단위로 격리된다 — 즉 **모듈 목록이 곧 바운디드 컨텍스트 목록**이다.
- (참고: 빌드 파일 `*.gradle.kts`는 Kotlin 소스 주석 금지 규약의 예외라 주석이 붙어 있다. 도메인 `.kt` 발췌에는 주석이 없다.)

### 3-2. 도메인은 kernel *하나*만 의존한다 (`meogo.domain-conventions.gradle.kts`)

```kotlin
plugins {
    id("meogo.kotlin-common")
}

dependencies {
    "api"(project(":core:kernel"))
}
```
`buildSrc/src/main/kotlin/meogo.domain-conventions.gradle.kts`(dependencies 블록)

- food/member/scan/avoidance/research/review 모든 도메인 모듈이 이 한 줄짜리 컨벤션 플러그인을 적용한다(`core/food/build.gradle.kts`는 `id("meogo.domain-conventions")` 한 줄뿐). 그 결과 도메인은 **`core:kernel` 외에는 어떤 것도 의존하지 않는다** — Spring·JPA·다른 도메인·상위 계층 전부 컴파일 클래스패스에 없다. 단방향 의존이 빌드 설정 레벨에서 이미 강제된다.

### 3-3. 경계를 지키는 테스트 (`ModuleBoundaryTest.kt`)

도메인이 Spring/JPA를 못 쓰게:

```kotlin
given("도메인 모듈(core:*) 경계") {
    `when`("도메인이 스프링·JPA 에 의존하는지 검사하면") {
        then("완전 Spring-free·ORM-free 다") {
            noClasses().that().resideInAPackage(anyDomain).and().resideOutsideOfPackage(kernel)
                .should().dependOnClassesThat().resideInAnyPackage(spring, jpa)
                .allowEmptyShould(true)
                .check(imported)
        }
    }
```
`app/api/src/test/kotlin/com/meogo/app/api/architecture/ModuleBoundaryTest.kt:53-60`

- `noClasses().that().resideInAPackage("com.meogo.core..")` = "core 패키지의 어떤 클래스도" / `.should().dependOnClassesThat().resideInAnyPackage(spring, jpa)` = "spring·jpa 패키지에 의존해선 안 된다". 도메인 코드에 `import org.springframework...`나 `import jakarta.persistence...`가 하나라도 섞이면 이 테스트가 실패한다.
- `given/when/then`이 한국어인 건 kbap의 테스트 스타일(Kotest BehaviorSpec) 규약이다 — 이 스타일 자체는 [[12. SDD와 TDD — 스펙과 테스트로 개발하기]]에서 다룬다.

도메인 컨텍스트끼리 격리:

```kotlin
domains.forEach { domain ->
    `when`("$domain 가 다른 도메인 컨텍스트에 의존하는지 검사하면") {
        then("서로 다른 도메인 컨텍스트는 격리된다") {
            val others = domains.filter { it != domain }.toTypedArray()
            noClasses().that().resideInAPackage(domain)
                .should().dependOnClassesThat().resideInAnyPackage(*others)
                .allowEmptyShould(true)
                .check(imported)
        }
    }
}
```
`app/api/.../ModuleBoundaryTest.kt:77-87`

- food/member/scan/avoidance/research/review 각각에 대해 "나 말고 다른 도메인들(`others`)에 의존하면 실패"를 건다. 이것이 §2-2의 "도메인끼리 직접 의존 금지, 조합은 application에서"를 코드로 못 박는 부분이다.

조립 계층도 안쪽 구현을 못 뚫게:

```kotlin
given("부트앱 모듈(app:api) 경계") {
    `when`("app:api 가 영속·도메인 내부에 의존하는지 검사하면") {
        then("persistence·도메인 컨텍스트를 직접 import 하지 않는다") {
            noClasses().that().resideInAPackage("com.meogo.app.api..")
                .should().dependOnClassesThat().resideInAnyPackage(
                    "com.meogo.infra.persistence..",
                    *domains.toTypedArray(),
                )
```
`app/api/.../ModuleBoundaryTest.kt:104-113`(발췌)

- web 계층(`app:api`)이 JPA 엔티티나 도메인 엔티티를 직접 import하는 걸 막는다. 컨트롤러는 `application`이 노출한 경계 타입(Input/Result DTO)만 봐야 한다 — 3단계에서 "도메인/영속 모델을 API로 그대로 노출하지 않는다"고 배운 규약의 강제 장치다.
- 이 테스트가 `app:api`에 있는 이유: `app:api`가 런타임에 전 모듈을 조립(`com.meogo` 전체를 클래스패스에 봄)하므로, 여기서 `importPackages("com.meogo")`로 전 계층을 한 번에 스캔·검증할 수 있다.

### 3-4. 두 부트앱이 같은 도메인 공유 (`app/batch/build.gradle.kts`)

```kotlin
dependencies {
    "implementation"(project(":infra:llm"))
    "implementation"(project(":core:research"))
    "implementation"(project(":core:food"))
    "implementation"(project(":core:avoidance"))
    "runtimeOnly"(project(":infra:persistence"))
    ...
}
```
`app/batch/build.gradle.kts`(dependencies 발췌)

- batch가 `core:research/food/avoidance`(도메인)와 `infra:persistence`(영속)를 **직접** 의존한다. api와 batch가 같은 도메인/엔티티를 재사용하는 ADR-0008 구조의 실물이다. (`infra:persistence`는 `runtimeOnly` — 컴파일엔 안 보이고 런타임에만 조립되므로 batch 코드도 JPA 엔티티를 직접 import할 수 없다.)

## 4. 트러블슈팅 / 주의점

- **낡은 ADR 함정** → ADR-0005·0006은 **옛 패키지 이름**(`com.meogo.api.<모듈>`, `:meogo-api:persistence`) 기준이다. 이후 ADR-0008 + `005-module-restructure`로 대체돼 현재는 `com.meogo.<layer>`, `:infra:persistence`, batch가 도메인 직접 의존이다. 0005·0006은 "이렇게 바뀌어 왔다"는 역사 맥락으로만 인용하고, 현재 구조는 ADR-0008 기준으로 읽는다.
- **"batch가 api에 의존"처럼 보이는 착시** → 옛 구조에선 경로상 `:meogo-batch → :meogo-api:application`이라 그렇게 읽혔다. 현재는 공유 계층이 최상위로 올라가 batch가 `core:*`·`infra:*`를 직접 의존한다. api·batch는 형제 부트앱이지 상하 관계가 아니다.
- **경계 위반이 "조용히" 나는 경우** → ArchUnit 테스트는 빌드 시 잡지만, 개발 중엔 애초에 **Gradle 모듈 의존을 선언하지 않아** 타입이 컴파일 클래스패스에 안 보이는 게 1차 방어선이다. 억지로 의존을 추가하면 그때 ArchUnit이 2차로 막는다. 두 겹이라는 걸 기억.
- **`allowEmptyShould(true)`가 왜 붙나** → 아직 비즈니스 코드가 적어 매칭되는 클래스가 0개일 수 있다. 이 옵션이 없으면 "검사 대상이 없음"만으로 ArchUnit이 실패한다. 스캐폴드 단계용 안전장치.

```
모듈러 모놀리스 = 배포는 하나, 안은 도메인 모듈로 쪼갬 (MSA 아님)
바운디드 컨텍스트 = Gradle 모듈 하나 = 자기 도메인 언어 소유
  active: food · member · scan · avoidance · research   (review = placeholder)
공유 커널 = core:kernel (얇은 공통 vocabulary·port, 모두가 의존 가능)

의존 방향(단방향, 화살표 = 의존):
  app → application → core:도메인 → core:kernel
  app → infra:persistence(runtimeOnly) → core:도메인(implementation)
  common = leaf (아무도 안 바라봄 / 두 앱이 공유)
  도메인끼리 직접 의존 X → 조합은 application 에서만

경계 강제 = ArchUnit ModuleBoundaryTest.kt (위반 = 빌드 실패)
 · 도메인은 spring/jpa 의존 금지
 · 도메인끼리 격리
 · app:api 는 persistence/도메인 직접 import 금지
 · @Entity 는 infra:persistence 에만

두 부트앱 공유 = app:api + app:batch 가 같은 core·infra 재사용 (ADR-0008)
  스키마 owner = app:api (Flyway), batch = flyway off
```

## 6. 용어집

- **모놀리스(monolith)**: 애플리케이션 전체가 하나의 배포 단위인 구조.
- **모듈러 모놀리스(modular monolith)**: 단일 배포를 유지하되 내부를 모듈로 분리해 경계를 준 구조. 마이크로서비스의 운영 복잡도 없이 모듈 경계의 이점을 취한다.
- **바운디드 컨텍스트(bounded context)**: DDD 전략 설계의 핵심 패턴. 하나의 도메인 모델·언어(유비쿼터스 언어)가 일관되게 통하는 경계. 경계 밖에서는 같은 용어라도 다른 뜻일 수 있다.
- **유비쿼터스 언어(ubiquitous language)**: 개발자와 도메인 전문가가 함께 쓰는, 한 컨텍스트 안에서 통일된 용어 체계.
- **공유 커널(shared kernel)**: 여러 컨텍스트가 공유하는 최소 공통 모델·코드. kbap에선 `core:kernel`.
- **단방향 의존(acyclic dependency)**: 모듈 의존 그래프에 순환이 없도록 방향을 고정하는 원칙.
- **ArchUnit**: JVM 아키텍처 규칙(레이어링·의존 방향·패키지 격리 등)을 **단위 테스트로 검증**하는 라이브러리.
- **드리프트(drift)**: 같은 개념을 두 곳에 각자 정의했을 때 시간이 지나며 정의가 어긋나는 현상. kbap이 도메인을 단일 소스로 공유하는 이유.
- **bootJar**: 실행 가능한 Spring Boot 산출물. kbap엔 `app:api`·`app:batch` 두 개 → [[1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일]].

## 7. 다음에 빠른 재현 체크리스트

1. "kbap 모듈 = 바운디드 컨텍스트"를 `settings.gradle.kts`의 `core:*` 목록으로 확인한다.
2. 의존 방향은 `app → application → core:도메인 → core:kernel` 한 방향. 도메인끼리 직접 의존 X, 조합은 `application`.
3. 경계가 왜 안 무너지나? → `ModuleBoundaryTest.kt`가 위반을 빌드 실패로 막기 때문. (문서 아님, 테스트임.)
4. api·batch는 형제 부트앱, 같은 `core·infra`를 공유(ADR-0008). 스키마 owner는 api뿐.
5. 옛 이름(ADR-0005·0006)과 현재(ADR-0008)를 헷갈리지 않는다 — 현재 기준은 항상 ADR-0008.
