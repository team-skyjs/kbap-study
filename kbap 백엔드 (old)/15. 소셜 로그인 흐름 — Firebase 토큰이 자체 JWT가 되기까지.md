# 15. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지

## ① 이 API가 하는 일 (한 줄)

앱이 구글·애플 로그인으로 받은 **Firebase ID 토큰**을 보내면, 서버가 그 토큰의 진위를 검증해 신원(플랫폼·원본 id·이메일)을 꺼내 → 기존 회원이면 로그인, 처음이면 가입시키고 → **우리 서비스 자체** access·refresh JWT를 만들어 응답 본문으로 돌려준다. `POST /api/v1/auth/login`.

이 노트는 그 요청 한 번이 **어느 파일들을 순서대로 지나 두 개의 자체 토큰이 되는지**를 실코드로 따라간다. "왜 자체 JWT를 또 발급하나", "왜 앱은 쿠키를 안 쓰나" 같은 개념은 인증 개념 노트로 링크하고, 여기서는 "그 개념이 이 요청에서 실제로 어떻게 나타나는가"만 본다.

> [!note] 스펙 제목·지도의 "쿠키"는 낡음 — 실제 코드는 응답 **본문** Bearer
> spec 초기 제목("자체 JWT 쿠키 발급")과 공부 지도 ④ 설명("쿠키 발급/재발급")은 초기 결정의 잔재다. spec **본문은 이미 개정**됐고(`research.md` R5 "개정 2026-07-11 쿠키→응답 본문", `spec.md` FR-005), **코드도 본문 방식**이다. 컨트롤러는 토큰을 JSON 본문에 담을 뿐 `Set-Cookie`를 쓰지 않고(`AuthController.kt:23-28`), 이후 매 요청은 `Authorization: Bearer` 헤더로 보낸다(`AuthApi.kt:23-25`). 테스트도 이걸 못 박는다: `result.getHeaders("Set-Cookie").isEmpty() shouldBe true`(`AuthControllerTest.kt:160`). **왜 앱은 쿠키 대신 Bearer인지**는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]]. 코드=개정 스펙 일치이므로 `> [!warning] 스펙과 다름`이 아니라 참고 표기다.

## ③ 계층 경계마다 — "여기서 모듈이 바뀌는 이유"

각 화살표는 Gradle 모듈 경계다. 온보딩 흐름과 같은 규칙([[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]·[[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]])이 여기서도 그대로 작동하되, 로그인은 **바깥 세계(Firebase)를 검증에 끌어들인다**는 점이 새롭다.

### 경계 1 — Controller → UseCase (`app:api` → `application:client`)

Controller는 HTTP·JSON만 안다. 요청 본문에서 `idToken` 문자열 하나만 벗겨 UseCase에 넘기고, 결과를 응답 DTO로 감싼다.

```kotlin
override fun login(
    @RequestBody request: LoginRequest,
): ResponseEntity<BaseResponse<LoginResponse>> {
    val result = loginUseCase.login(request.idToken)
    return ResponseEntity.ok(BaseResponse.ok(LoginResponse.from(result)))
}
```
`AuthController.kt:23-28`. `loginUseCase`는 **생성자 주입**으로 받은 부품이라 컨트롤러가 직접 `new` 하지 않는다(`AuthController.kt:17-22`에서 3개 UseCase를 한꺼번에 주입받는다) → [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나]], [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]. 모든 응답을 `BaseResponse`로 감싸는 규약도 온보딩과 동일(FE의 공통 API 응답 래퍼와 같은 역할).

주목할 점: `LoginResult`에는 `memberId`가 있는데(`LoginUseCase.kt:12-17`), 응답 DTO `LoginResponse`는 그걸 **일부러 복사하지 않는다**(`LoginResponse.kt:11-16`). 회원 식별은 이제부터 access 토큰의 `sub` 클레임이 하므로 응답 본문에 회원 번호를 노출할 이유가 없다. 테스트가 이걸 못 박는다: `payload.has("memberId") shouldBe false`(`AuthControllerTest.kt:159`).

### 경계 2 — UseCase가 조율하는 신원 확립 (`application:client` 안)

UseCase는 로그인이라는 시나리오의 **조율자**다. 검증 → 회원 해결 → 토큰 발급 → 세션 저장을 순서대로 지시한다.

```kotlin
fun login(idToken: String): LoginResult {
    val identity = socialTokenVerifier.verify(idToken)
    val (member, isNewMember) = resolveMember(identity)
    val memberId = member.id ?: throw AuthException(AuthErrorCode.INVALID_SOCIAL_TOKEN)

    val refreshToken = tokenIssuer.issueRefreshToken(memberId)
    refreshTokenStore.save(refreshToken.jti, memberId, properties.refreshTtl)

    return LoginResult(
        memberId = memberId,
        newMember = isNewMember,
        accessToken = tokenIssuer.issueAccessToken(memberId, MemberRole.USER),
        refreshToken = refreshToken.token,
    )
}
```
`LoginUseCase.kt:27-41`.
- `socialTokenVerifier.verify`는 **port 타입**(`SocialTokenVerifier`)이라 UseCase는 Firebase를 모른다(경계 3).
- `resolveMember`가 기존 회원 조회 또는 신규 가입을 판단한다(경계 4).
- refresh를 **먼저** 발급하고 그 `jti`를 세션 저장소에 등록한 뒤(경계 5) access를 발급한다. access는 저장하지 않는다 — stateless이기 때문(왜 그런지는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]]).

> [!note] 이 UseCase에는 `@Transactional`이 없다
> 온보딩·스캔 UseCase는 `@Transactional`이었지만 `LoginUseCase`는 `@Service`만 붙는다(`LoginUseCase.kt:19-20`). member 저장은 1건 단발이고, refresh 저장은 **Redis**(아래 콜아웃) — RDB 트랜잭션 밖이라 DB 트랜잭션 경계로 묶을 게 없다. "모든 UseCase가 `@Transactional`인 건 아니다"의 반례다 → [[6. 설정과 프로필, 트랜잭션 첫걸음]].

### 경계 3 — 검증은 port, Firebase는 adapter (`application:client` 안의 역전)

로그인의 핵심 새 요소. UseCase가 의존하는 건 **인터페이스**다:

```kotlin
interface SocialTokenVerifier {
    fun verify(idToken: String): SocialIdentity
}
```
`SocialTokenVerifier.kt:5-7`. 이게 port다. 실제 Firebase 호출은 이 port의 **구현(adapter)** 에만 있다:

```kotlin
override fun verify(idToken: String): SocialIdentity {
    val decoded = try {
        FirebaseAuth.getInstance(firebaseApp).verifyIdToken(idToken)
    } catch (e: FirebaseAuthException) {
        ...
        throw AuthException(AuthErrorCode.INVALID_SOCIAL_TOKEN)
    } catch (e: IllegalArgumentException) {
        ...
        throw AuthException(AuthErrorCode.INVALID_SOCIAL_TOKEN)
    }
    return FirebaseClaimMapper.toSocialIdentity(decoded.claims)
}
```
`FirebaseTokenVerifier.kt:14-29`. `verifyIdToken`이 토큰의 서명·발급자·수신자·만료를 Firebase 규칙대로 확인한다 — 이 한 줄이 "이 토큰이 진짜 구글/애플이 발급한 것인가"의 전부다. Firebase가 소셜 IdP(구글·애플)의 검증을 대신 떠맡는 층인 배경은 [[OAuth 2.0과 OIDC — 소셜 로그인의 원리]].

검증에 성공한 뒤 claims를 우리 도메인 값으로 옮기는 매퍼:

```kotlin
val provider = PROVIDERS[signInProvider] ?: throw AuthException(AuthErrorCode.UNSUPPORTED_PROVIDER)
...
val providerUserId = (identities[signInProvider] as? List<*>)
    ?.firstOrNull()
    ?.toString()
    ...
return SocialIdentity(provider = provider, providerUserId = providerUserId, email = claims[EMAIL] as? String)
```
`FirebaseClaimMapper.kt:21-34`.
- `PROVIDERS`는 `"google.com" → GOOGLE`, `"apple.com" → APPLE`만 담는다(`:12-15`). 그 외(예: `facebook.com`)는 `UNSUPPORTED_PROVIDER`.
- **원본 uid**는 최상위 `sub`(= Firebase 내부 uid)가 **아니라** `identities[provider]`의 첫 원소, 즉 구글·애플이 발급한 진짜 식별자다. Firebase uid는 저장하지 않는다 — 나중에 회원 탈퇴 시 소셜 계정을 직접 지우려면 IdP 원본 id가 필요하기 때문. provider별 차이(애플의 이메일 가리기 릴레이 주소 시나리오)는 [[Google vs Apple 소셜 로그인 비교]].
- `email`은 nullable(`SocialIdentity.kt:3-6`) — 애플은 이메일을 안 줄 수 있다.

`SocialTokenVerifier`가 port로 앉아 있어서, UseCase는 `application:client`가 Firebase SDK에 의존하는지조차 신경 쓰지 않는다. 이게 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]의 의존성 역전이 인증에 적용된 모습이다.

> [!info] 자격증명 유무로 다른 부품을 조립한다
> 어느 구현이 주입될지는 `AuthConfig`의 `@Bean`이 부팅 시점에 결정한다:
> ```kotlin
> @Bean
> fun socialTokenVerifier(...): SocialTokenVerifier {
>     val app = firebaseAppOrNull(credentialsJson, credentialsPath)
>     if (app == null) {
>         log.warn("Firebase 자격증명 미설정 — 소셜 로그인 비활성(모든 로그인이 401 로 거절된다)")
>         return UnavailableSocialAuth
>     }
>     return FirebaseTokenVerifier(app)
> }
> ```
> `AuthConfig.kt:26-38`. 자격증명이 없으면 `verify`가 항상 `INVALID_SOCIAL_TOKEN`을 던지는 폴백(`UnavailableSocialAuth`, `AuthConfig.kt:68-73`)이 등록된다 — 부팅은 정상이고 로그인만 401이다(`application.yml:42` 주석과 일치). "부품을 자격증명 상태에 따라 다르게 조립"하는 게 [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]]의 실물이다.

### 경계 4 — 회원 조회 또는 가입 (`application:client` → `core:member`)

```kotlin
private fun resolveMember(identity: SocialIdentity): Pair<Member, Boolean> {
    memberRepository.findByIdentity(identity.provider, identity.providerUserId)?.let {
        return it to false
    }
    return try {
        memberRepository.saveNew(Member.signUp(identity)) to true
    } catch (e: MemberException) {
        if (e.errorCode != MemberErrorCode.DUPLICATE_SOCIAL_IDENTITY) throw e
        val existing = memberRepository.findByIdentity(identity.provider, identity.providerUserId)
            ?: throw e
        existing to false
    }
}
```
`LoginUseCase.kt:43-56`.
- 신원으로 회원을 찾으면 로그인(`false` = 신규 아님).
- 없으면 `Member.signUp(identity)`로 **새 회원**을 만들어 저장(`true` = 신규). `signUp`은 순수 도메인 팩토리다:
  ```kotlin
  fun signUp(identity: SocialIdentity): Member =
      Member(id = null, identity = identity, profile = MemberProfile.empty(), onboardingCompleted = false, ranking = Ranking.initial())
  ```
  `Member.kt:34-42`. 프로필이 비어 있고 `onboardingCompleted=false`인 회원이 태어난다 — 이 빈 프로필을 채우는 게 [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]다.
- `catch`는 **동시 첫 로그인 경합**을 흡수한다: 두 요청이 동시에 "회원 없음"을 보고 둘 다 `saveNew`를 시도하면, 유니크 제약에 걸린 쪽이 `DUPLICATE_SOCIAL_IDENTITY`를 받는다. 그때 예외를 터뜨리지 않고 **재조회**해 먼저 이긴 회원을 반환한다(`false`). 두 사용자가 각자 로그인 성공하는 결과를 보장.

`memberRepository`의 타입은 `core:member`의 **인터페이스**(port)다(`MemberRepository.kt:3-15`). UseCase는 JPA도 Redis도 import하지 않는다. `Member`·`SocialIdentity`가 member 바운디드 컨텍스트의 순수 도메인이라는 점([[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]])도 온보딩과 동일.

### 경계 5 — 토큰 발급과 세션 저장 (`application:client` + `core`/`infra`)

두 토큰은 `TokenIssuer`가 jjwt(JVM용 JWT 발급·검증 라이브러리)로 만든다:

```kotlin
fun issueAccessToken(memberId: Long, role: MemberRole): String {
    val now = System.currentTimeMillis()
    return Jwts.builder()
        .subject(memberId.toString())
        .claim(TokenType.CLAIM, TokenType.ACCESS.name)
        .claim(ROLE_CLAIM, role.name)
        .issuedAt(Date(now))
        .expiration(Date(now + properties.accessTtl.toMillis()))
        .signWith(key)
        .compact()
}
```
`TokenIssuer.kt:23-33`. 서명 키는 `SecretKeySpec(properties.secret.toByteArray(), "HmacSHA256")`(`:21`) — HS256 대칭키다. 같은 키로 발급도 검증도 한다(검증은 노트 2). access 클레임은 `sub`(회원 id)·`token_type: ACCESS`·`role`뿐 — **이메일·닉네임 같은 개인정보는 넣지 않는다**(테스트가 `payload shouldNotContain "email"`로 못 박음, `TokenTest.kt:36-43`).

refresh는 `jti`(UUID)를 더 담는다:

```kotlin
fun issueRefreshToken(memberId: Long): IssuedRefreshToken {
    val now = System.currentTimeMillis()
    val jti = UUID.randomUUID().toString()
    val token = Jwts.builder()
        .subject(memberId.toString())
        .claim(TokenType.CLAIM, TokenType.REFRESH.name)
        .id(jti)
        ...
    return IssuedRefreshToken(token = token, jti = jti)
}
```
`TokenIssuer.kt:35-47`. `jti`는 이 refresh를 서버가 식별·폐기할 손잡이다. 그 손잡이를 세션 저장소에 등록한다:

```kotlin
override fun save(jti: String, memberId: Long, ttl: Duration) {
    redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
}
```
`RefreshTokenRedisAdapter.kt:12-14`. `RefreshTokenStore` port(`core:member`)의 구현이고, `jti → memberId`를 **TTL과 함께 Redis**에 넣는다(키는 `auth:refresh:{jti}`, `:23-26`).

> [!note] 세션 저장소는 MySQL이 아니라 Redis (개념 노트 후보)
> 온보딩·스캔이 JPA로 MySQL에 쓴 것과 달리, refresh 세션은 **Redis**에 산다. Redis는 키-값 저장소로, 여기서 쓰는 두 성질이 핵심이다: (1) **TTL 자동 만료** — `set(key, value, ttl)`로 14일 뒤 키가 스스로 사라져 refresh 만료와 세션 만료가 자동으로 맞는다. (2) **`getAndDelete` 원자성** — 재발급 시 "읽으면서 동시에 지우기"로 회전을 안전하게 한다(노트 2에서 사용). `RefreshTokenStore` port는 `core/member`에, Redis 구현만 `infra/persistence/auth`에 있어([[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]) 도메인은 Redis를 모른다. 3~4단계 개념 노트가 Redis를 다루지 않으므로 여기선 이 콜아웃으로만 소개한다. (2026-07-16 추가: Redis가 뭔지·왜 캐시/세션에 쓰는지는 → [[21. 캐싱과 키-값 저장소 — 왜 캐시하나부터 kbap의 Redis 세션까지]].)

### 설정값 — 부팅 시 강제되는 것

토큰 수명·키는 `application.yml`에 있고 `AuthTokenProperties`로 검증한다:

```yaml
meogo:
  auth:
    jwt:
      secret: ${JWT_SECRET:}
      access-ttl: 30m
      refresh-ttl: 14d
```
`application.yml:46-51`. `secret`은 32바이트 이상이어야 하고, 미달이면 부팅이 **실패**한다:

```kotlin
init {
    require(secret.toByteArray().size >= MIN_SECRET_BYTES) {
        "meogo.auth.jwt.secret 는 ${MIN_SECRET_BYTES}바이트 이상이어야 합니다"
    }
}
```
`AuthTokenProperties.kt:10-14`(`MIN_SECRET_BYTES = 32`). 조용한 약한 키를 막는 방어다(HS256 최소 길이). 이 프로퍼티 객체 자체가 `AuthConfig`의 `@Bean`으로 조립된다(`AuthConfig.kt:19-24`) → [[6. 설정과 프로필, 트랜잭션 첫걸음]]. `access-ttl: 30m`(짧게, 만료 전 무효화 불가)·`refresh-ttl: 14d`(길게, Redis 폐기 가능)의 이유는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]].

## ④ 요청 / 응답 JSON

**요청** `POST /api/v1/auth/login` (인증 불필요 — "서비스의 문"이라 아직 토큰이 없다)

```json
{
  "idToken": "eyJhbGciOiJSUzI1NiI..."
}
```
`idToken`은 FE가 Firebase SDK로 소셜 로그인을 마치고 받은 값이다(`LoginRequest.kt:5-8`, `@NotBlank`). 누락·공백이면 400.

**성공 응답** 200 — `BaseResponse.ok(LoginResponse)`. payload에 신규 여부와 두 토큰이 담긴다(`LoginResponse.kt:5-9`):

```json
{
  "success": true,
  "payload": {
    "newMember": true,
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "refreshToken": "eyJhbGciOiJIUzI1NiJ9..."
  },
  "message": null
}
```
- `newMember: true`면 FE는 온보딩 화면으로, `false`면 홈으로 분기한다(`AuthApi.kt:27-28`).
- **memberId는 없다** — 회원 식별은 access 토큰의 `sub`가 한다(`AuthControllerTest.kt:159`).
- `Set-Cookie` 헤더는 없다 — 토큰은 본문으로만 내려온다(`AuthControllerTest.kt:160`).

**실패 응답** 401 — 토큰 검증 실패 또는 미지원 provider. `BaseResponse.fail(message)` 형태이고 메시지는 `AuthErrorCode`에서 온다(`AuthErrorCode.kt`):

```json
{
  "success": false,
  "payload": null,
  "message": "유효하지 않은 소셜 인증 토큰입니다"
}
```
같은 401 계열: 미지원 provider `지원하지 않는 소셜 로그인 제공자입니다`(`UNSUPPORTED_PROVIDER`). idToken 누락은 400. (access/refresh 토큰 계열 에러코드는 발급 이후 이야기라 노트 2에서 다룬다.)

## ⑤ 관련 테스트가 보장하는 것

로그인은 검증 adapter·UseCase·엔드포인트가 각각 다른 테스트로 지켜진다.

- **`FirebaseClaimMapperTest.kt`** (`application/client/.../auth/`): claims → 신원 매핑의 규칙. 구글은 `GOOGLE`+원본 sub 추출(`:22-35`), **Firebase uid는 저장하지 않음**(`:38-49`), 애플 릴레이 이메일 보존·이메일 없어도 매핑(`:53-82`), `facebook.com`은 `UNSUPPORTED_PROVIDER`(`:85-100`), 훼손 claims는 `INVALID_SOCIAL_TOKEN`(`:102-136`).
- **`LoginUseCaseTest.kt`** (`application/client/.../auth/`): `FakeSocialTokenVerifier`·인메모리 store를 끼워 **DB 없이** UseCase 로직만 검증(port 덕분). 신규 가입 시 회원 생성+토큰 2종(`:38-52`), refresh의 jti가 store에 회원과 함께 등록됨(`:54-65`), 기존 회원 재로그인은 `newMember=false`+중복 가입 없음(`:68-87`), 검증 실패 시 회원·세션 미생성(`:89-103`), **동시 경합 재조회 폴백**(`:105-123`), 미지원 provider 전파(`:125-138`).
- **`TokenTest.kt`** (`application/client/.../auth/`): 발급·서명. access는 파싱 시 memberId·role 복원+개인정보 미포함(`:23-45`), refresh는 jti+memberId 복원, 두 번 발급하면 다른 jti(`:75-95`), 32바이트 미만 시크릿은 예외(`:189-201`).
- **`AuthControllerTest.kt`** (`app/api/.../auth/`): 엔드포인트 전 구간(MySQL+Redis Testcontainers, 페이크 verifier 빈). 미가입자 로그인 시 200+`newMember:true`+본문 토큰+**Set-Cookie 없음**+**memberId 없음**(`:147-161`), 회원이 신원과 함께 저장됨(`:164-175`), 재로그인 `newMember:false`(`:178-190`), 검증 실패·미지원 provider 401(`:192-214`), idToken 공백 400(`:216-222`), 발급 access에 개인정보 없음(`:239-249`).
