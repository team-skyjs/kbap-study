# 1. 서버는 켜두는 프로그램 — 서버 프로세스와 두 개의 실행 파일

## 한 줄 요약

FE 코드는 **빌드해서 배포하면 끝**이었지만, 서버는 **프로세스로 계속 떠서 포트를 열고 요청을 기다리는 프로그램**이다. kbap-server는 이 "떠 있는 프로그램"을 두 개(웹 앱 `app:api`, 배치 앱 `app:batch`) 돌린다.

---

## 개념표

| 용어 | 한 줄 정의 | FE에서 가장 가까운 것 |
|---|---|---|
| 프로세스 | OS가 메모리를 떼어주고 실행 중인 프로그램 하나. 켜지면 끌 때까지 살아 있다 | `node server.js`를 터미널에서 띄우고 `Ctrl+C` 전까지 도는 그 상태 |
| 포트 | 한 컴퓨터 안에서 프로그램을 구분하는 번호(예: 8080). 서버는 이 번호로 들어오는 요청을 "듣는다" | Expo dev server의 `:8081`, Vite의 `:5173` 같은 그 번호 |
| 진입점 `main` | 프로그램이 **여기서 시작한다**는 단 하나의 함수 | `index.js` / 앱 엔트리 — 다만 서버는 이게 언어 문법으로 못박혀 있다 |
| bootJar | 서버 코드를 **혼자 실행 가능한 하나의 파일**로 묶은 것. `java -jar`로 그냥 뜬다 | 번들러가 뽑은 단일 산출물에 가깝지만, 런타임(JVM)까지 전제로 깔고 도는 실행 파일 |

---

## 원리 — "배포하고 끝"(FE) vs "띄워두고 대기"(서버)

FE 개발에서 코드의 최종 상태는 **정적 산출물**이었다. `expo export`나 웹 번들을 만들면 그건 CDN이나 스토어에 올라가 앉아 있고, **사용자 기기에서 그때그때 실행**된다. 내 코드가 24시간 어딘가에서 "돌고 있는" 게 아니다.

서버는 반대다. 서버 코드는 **하나의 프로세스로 실행돼 계속 살아 있어야** 한다. 아무도 요청을 안 보내는 새벽 3시에도 프로그램은 메모리에 떠서, 포트를 붙잡고, 다음 요청을 기다린다. 요청이 오면 처리하고 응답한 뒤 **죽지 않고** 다시 대기로 돌아간다.

> [!tip] 핵심 전환
> FE는 "요청이 올 때 실행되는 코드"를, 서버는 "요청을 기다리며 이미 실행 중인 프로그램"을 짠다. 이 프로그램을 어떻게 **시작(main)** 하고, 무엇으로 **듣고(포트)**, 몇 개를 **띄우는지(bootJar)** 가 이 노트의 전부다.

이 대비는 비유이며 완전 동치는 아니다. FE에도 "떠 있는 프로세스"는 있다 — Node로 짠 API 서버나 Expo dev server가 그렇다. 다만 **배포되는 앱 코드(화면)** 는 서버처럼 상주하지 않는다는 게 차이다.

---

## 진입점 `main`과 `@SpringBootApplication`

FE에는 "여기가 프로그램의 시작점"이라는 게 문법으로 강제되지 않았다(엔트리 파일은 번들러 설정일 뿐). JVM 프로그램은 **`main` 함수가 유일한 시작점**이다 — `java`가 이 함수를 호출하며 프로그램이 켜진다.

kbap 웹 앱의 실제 진입점:

```kotlin
@SpringBootApplication
class MeogoApiApplication

fun main(args: Array<String>) {
	runApplication<MeogoApiApplication>(*args)
}
```
`app/api/src/main/kotlin/com/meogo/MeogoApiApplication.kt:6`

풀이(레포는 주석 금지 규약이라 코드만으로 낯설 수 있어 한 줄씩 붙인다):
- `@SpringBootApplication` — "이 클래스를 시작점 삼아 스프링을 부팅하라"는 표식. **여기서 서버가 조립되고 내장 웹 서버가 켜진다**. 무엇을 조립하는지(=스프링)는 2단계에서 다룬다.
- `class MeogoApiApplication` — 표식을 붙일 대상 클래스. 알맹이는 비어 있다(조립은 애너테이션이 대신 한다).
- `fun main(...)` — JVM이 호출하는 유일한 시작 함수. **이 줄이 실행되는 순간 프로그램이 살아난다.**
- `runApplication<MeogoApiApplication>(*args)` — 스프링을 실제로 부팅하는 호출. 이 함수는 부팅 후 **바로 끝나지 않고**, 내장 서버가 요청을 기다리는 동안 프로세스를 살려 둔다. (`*args`는 실행 시 넘긴 커맨드라인 인자를 그대로 전달.)

> [!note] `@SpringBootApplication` = "자동으로 웹 서버가 켜지는" 이유
> 클래스패스에 웹 서버를 띄울 부품(내장 톰캣 등)이 있으면 스프링이 **알아서** 서버를 시작한다. 그래서 이 짧은 코드만으로 포트가 열린다 — 내가 소켓을 열고 리스닝 루프를 도는 코드를 쓰지 않는다.

## 포트와 프로필

### 포트 — 서버가 "듣는" 번호

서버는 포트에서 요청을 듣는다. kbap의 실제 설정 파일에서 `server:` 블록은 이렇다:

```yaml
server:
  forward-headers-strategy: framework
```
`app/api/src/main/resources/application.yml:1`

풀이:
- 여기엔 **포트 번호가 없다.** Spring Boot는 `server.port`가 없으면 **기본 8080**으로 뜬다. 그래서 로컬에서 `./gradlew :app:api:bootRun` 하면 `http://localhost:8080`이 열린다. (바꾸려면 `server.port` 를 이 블록에 추가.)
- `forward-headers-strategy: framework` — nginx 같은 리버스 프록시 뒤에 있을 때, 프록시가 붙여 보내는 원래 요청 정보(`X-Forwarded-*` 헤더)를 신뢰하라는 설정. 지금 단계에선 "실서비스에선 서버 앞에 프록시가 한 겹 더 있다" 정도만 알면 된다.

내장 서버(톰캣)가 이 포트로 들어온 요청을 **실제로 어떻게 처리하는지**(요청마다 스레드를 배정하는 모델)는 다음 노트에서 다룬다 → [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]].

### 프로필 — 환경별 설정 묶음 (맛보기)

같은 서버 코드라도 내 노트북, 개발 서버, 실서비스는 DB 주소·키가 다르다. 스프링은 이걸 **프로필**로 가른다. kbap은 4종이다:

| 프로필 | 언제 |
|---|---|
| `local` | 내 노트북 개발 |
| `dev` | 팀 공용 개발 서버 |
| `staging` | 실서비스 직전 검증 |
| `prod` | 실서비스 |

실행할 때 환경변수로 고른다 — `SPRING_PROFILES_ACTIVE=local`. 실제 `application.yml`에도 이렇게 적혀 있다:

```yaml
# 활성 프로필은 런타임에 지정한다 (예: SPRING_PROFILES_ACTIVE=local|dev|staging|prod).
```
`app/api/src/main/resources/application.yml:21`

FE의 `.env.development` / `.env.production` 갈아끼우기와 발상이 같다. **차이**: FE `.env`는 빌드 시점에 값이 코드로 굳지만, 스프링 프로필은 **뜰 때 골라서 서로 다른 설정 파일 묶음**(`application-local.yml` 등)을 얹는다 — 같은 산출물을 재빌드 없이 환경만 바꿔 띄울 수 있다. 프로필의 구체 동작은 2단계에서 다룬다.

## kbap는 왜 실행 파일이 2개인가 — web과 배치

kbap-server는 코드가 한 레포에 있지만 **띄울 수 있는 프로그램(bootJar)이 두 개**다(CLAUDE.md "개요", [ADR-0001](docs/adr/0001-multi-app-modular-layout.md)):

| 실행 파일 | 하는 일 | FE 비유 |
|---|---|---|
| `app:api` | 사용자 요청을 받는 **웹 서버**. 포트를 열고 HTTP 요청에 응답 | 앱이 때리는 API 서버 |
| `app:batch` | 정해진 작업을 **스스로 도는 배치**. 요청을 기다리는 게 아니라 잡(job)을 실행 | 크론으로 도는 스크립트 / 스케줄 함수 |

같은 도메인·DB 코드를 공유하되, **요청을 받는 앱**과 **정해진 일을 도는 앱**을 나눈 것이다. 배치 앱의 진입점도 별도로 있다:

```kotlin
@SpringBootApplication(scanBasePackages = ["com.meogo"])
@AutoConfigurationPackage(basePackages = ["com.meogo"])
class MeogoBatchApplication

fun main(args: Array<String>) {
    runApplication<MeogoBatchApplication>(*args)
}
```
`app/batch/src/main/kotlin/com/meogo/app/batch/MeogoBatchApplication.kt:7`

풀이:
- 웹 앱과 **똑같은 골격**(`@SpringBootApplication` + `main` + `runApplication`) — 둘 다 독립적으로 뜨는 프로그램이라 각자 자기 `main`을 가진다.
- `scanBasePackages = ["com.meogo"]` — 배치 진입점은 패키지 루트(`com.meogo`)가 아니라 `com.meogo.app.batch`에 있어서, 조립 대상을 `com.meogo` 전체로 **명시적으로 넓혀** 준다. (웹 앱은 진입점이 이미 루트 `com.meogo`에 있어 이 지정이 필요 없다 — 그래서 위 코드엔 없었다.)

> [!warning] 왜 하나로 안 합쳤나
> "요청 받기"와 "배경 작업 돌리기"를 한 프로세스에 섞으면, 무거운 배치가 사용자 요청 응답을 갉아먹는다. 프로세스를 나누면 배치가 터져도 웹은 멀쩡하고, 각자 필요한 만큼만 서버 대수를 늘릴 수 있다. (결정 근거: [ADR-0001](docs/adr/0001-multi-app-modular-layout.md).)

## 실행 명령어

kbap은 모든 작업을 Gradle 래퍼(`./gradlew`)로 실행한다(CLAUDE.md "명령어"):

```bash
./gradlew :app:api:bootRun      # 웹 앱을 띄운다 (포트 8080에서 대기)
./gradlew :app:batch:bootRun    # 배치 앱을 실행한다
```

프로필을 골라 띄우려면 환경변수를 앞에 붙인다:

```bash
SPRING_PROFILES_ACTIVE=local ./gradlew :app:api:bootRun
```

`:app:api`, `:app:batch`는 **모듈 경로**다(콜론 표기). 두 개의 bootJar가 각각 별개 모듈이라는 게 명령어에도 드러난다. 모듈 구조와 Gradle 자체는 → [[3. JVM 위의 Kotlin — 컴파일·타입·널 안전이 TypeScript와 다른 점]]에서 다룬다.

> [!note] 2단계 예고
> 이렇게 **뜬 서버 안에서 객체(Bean)를 조립해 주는 게 스프링**이다. `@SpringBootApplication`이 부팅 때 정확히 무엇을 조립하는지가 2단계의 주제다.

## 치트시트

- 서버 = **끄기 전까지 계속 떠서 포트를 듣는 프로세스**. FE 앱처럼 "요청 시 실행"이 아니라 "이미 실행 중".
- JVM 프로그램의 시작점은 **`main` 함수 하나**. kbap 웹 앱은 `MeogoApiApplication.kt`의 `main` → `runApplication`.
- `@SpringBootApplication`이 붙으면 부팅 시 **내장 웹 서버가 자동으로 켜진다**(소켓 여는 코드 직접 안 씀).
- 포트 미설정 시 **기본 8080**. kbap `application.yml`엔 포트가 없으니 8080.
- 프로필 **4종**: `local` / `dev` / `staging` / `prod`. `SPRING_PROFILES_ACTIVE`로 선택.
- kbap는 bootJar **2개**: `app:api`(웹, 요청 대기) + `app:batch`(배치, 잡 실행). 각자 `main`을 가진다.
- 실행: `./gradlew :app:api:bootRun` / `./gradlew :app:batch:bootRun`.

## 용어집

- **프로세스(process)**: OS가 메모리·실행 흐름을 배정한, 실행 중인 프로그램 하나.
- **포트(port)**: 한 호스트에서 프로그램을 구분하는 번호. 서버는 특정 포트로 들어오는 연결을 듣는다.
- **진입점(entry point) / `main`**: 프로그램 실행이 시작되는 함수. JVM에선 문법적으로 정해져 있다.
- **`@SpringBootApplication`**: 스프링 부팅을 시작시키는 애너테이션. 조립 + (웹이면) 내장 서버 시작을 촉발.
- **내장 서버(embedded server)**: 별도 설치 없이 앱 안에 딸려 오는 웹 서버(kbap은 톰캣). bootJar 하나로 서버까지 함께 뜬다.
- **bootJar**: 앱 + 의존성 + 내장 서버를 묶어 `java -jar`로 바로 실행되는 산출물.
- **프로필(profile)**: 환경별 설정 묶음. 실행 시 활성 프로필을 골라 해당 설정을 얹는다.
- **배치(batch)**: 요청을 받는 게 아니라 정해진 작업(잡)을 실행하는 프로그램.

- [ ] "FE 앱 배포"와 "서버 프로세스 상주"의 차이를 한 문장으로 말할 수 있다.
- [ ] `main` 함수가 왜 서버 코드에서 특별한지 설명할 수 있다.
- [ ] `@SpringBootApplication` 하나로 웹 서버가 켜지는 이유를 안다.
