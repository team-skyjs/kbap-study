# 16. JWT 인증 필터와 세션 생명주기 — 매 요청 검증·재발급·로그아웃

## 이 흐름이 하는 일 (한 줄)

로그인 뒤 모든 보호된 요청은 `Authorization: Bearer {access}` 헤더를 **필터**가 가로채 검증하고, 꺼낸 회원 PK를 컨트롤러 파라미터에 꽂아준다(5a에서 예고만 하고 넘어간 `@AuthMemberId`의 정체가 바로 이것이다). access 토큰이 만료되면 refresh 토큰으로 access·refresh를 **둘 다** 새로 발급하고(rotation), 로그아웃하면 서버에 저장된 refresh 세션을 폐기한다.

> 이 노트는 [[15. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]]의 **뒷이야기**다. 저 노트가 "토큰을 어떻게 만들어 발급하나"(신원 확립)라면, 이 노트는 "발급된 토큰이 그 뒤 매 요청에서 어떻게 쓰이고 세션이 어떻게 끝나나"(세션 유지)를 다룬다. 토큰이 왜 응답 **본문**으로 나가고 매 요청은 왜 `Authorization: Bearer` 헤더인지(쿠키가 아니라)는 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]]에서 다룬다.

이 흐름에는 API 엔드포인트가 아닌 **횡단 계층 하나**(모든 보호 요청에 걸리는 필터)와 엔드포인트 **둘**(`/auth/refresh`, `/auth/logout`)이 섞여 있다. 세 갈래로 나눠 따라간다.

## 흐름 A — 매 요청 인증 (횡단 계층)

FE 비유로 시작하면, React에서 화면 컴포넌트가 렌더되기 **전에** 라우터 가드(`<ProtectedRoute>`)가 먼저 돌아 로그인 여부를 확인하는 것과 같다. 서버의 **필터**는 컨트롤러(=화면 컴포넌트)에 요청이 닿기 전에 먼저 실행되는 가드다. 다만 여기서만 같고, 필터는 서버 쪽 요청 스레드에서 돈다는 점이 다르다(→ [[2. 요청 하나에 스레드 하나 — JVM 서버의 동시성과 Node 이벤트루프의 차이]]).

| 계층 | 파일 | 하는 일 |
|---|---|---|
| 필터 등록 | `app/api/.../common/auth/WebMvcAuthConfig.kt:20-29` | `FilterRegistrationBean`으로 `members/*`·`scans`·`scans/*`·`auth/withdraw` 경로에만 필터를 건다. login·refresh·logout은 **비보호** — 문 앞이라 아직 토큰이 없다 |
| 리졸버 등록 | `app/api/.../common/auth/WebMvcAuthConfig.kt:15-18` | `addArgumentResolvers`로 `AuthMemberIdArgumentResolver`·`AuthMemberIdOrNullArgumentResolver`를 스프링에 등록 |
| 필터 | `app/api/.../common/auth/JwtAuthenticationFilter.kt:19-41` | `OncePerRequestFilter`. `Authorization: Bearer` 추출 → `tokenParser.parseAccessToken` → memberId·role을 **request attribute**에 저장 → 체인 진행. 실패는 필터에서 401 JSON을 직접 write |
| 파서 | `application/client/.../auth/TokenParser.kt:29-37` | 같은 HS256 키로 서명·만료·`token_type` 검증, `sub`→memberId·role 복원. 실패는 `EXPIRED_/INVALID_ACCESS_TOKEN` |
| 리졸버 | `app/api/.../common/auth/AuthMemberIdArgumentResolver.kt:12-24`, `AuthMemberId.kt` | `@AuthMemberId Long` 파라미터에, 필터가 넣어둔 request attribute(memberId)를 주입. **5a 노트가 "5b 예고"로 남긴 바로 그 조각** |

### 필터가 memberId를 넘기는 방법 — request attribute

`JwtAuthenticationFilter.kt:24-32`:

```kotlin
try {
    val token = bearerToken(request)
    val parsed = tokenParser.parseAccessToken(token)
    request.setAttribute(MEMBER_ID_ATTRIBUTE, parsed.memberId)
    request.setAttribute(ROLE_ATTRIBUTE, parsed.roleName)
    filterChain.doFilter(request, response)
} catch (e: AuthException) {
    writeUnauthorized(response, e)
}
```

- `bearerToken(request)`(`:35-41`): `Authorization` 헤더가 없거나 `Bearer `로 시작하지 않으면 즉시 `INVALID_ACCESS_TOKEN` 예외. 있으면 `Bearer ` 접두를 떼고 토큰 문자열만 반환.
- `tokenParser.parseAccessToken(token)`: 서명·만료·토큰 종류를 검증하고 `ParsedAccessToken(memberId, role)`을 돌려준다. 검증에 실패하면 여기서 예외가 튀어 아래 `catch`로 간다.
- `request.setAttribute(...)`: 검증에 성공한 memberId·role을 **이 요청에만 살아있는 임시 보관함**(request attribute)에 넣는다. FE로 치면 이 요청 처리 동안만 유효한 context 값을 세팅하는 것. 컨트롤러는 나중에 이 값을 꺼내 쓴다.
- `filterChain.doFilter(...)`: 다음 단계(다른 필터, 결국 컨트롤러)로 요청을 흘려보낸다. 이 줄을 호출해야 컨트롤러가 실행된다.
- `catch (e: AuthException)`: 검증 실패 시 `doFilter`를 **부르지 않는다** → 컨트롤러는 아예 실행되지 않고, `writeUnauthorized`가 401 JSON을 응답에 직접 쓴다(`:43-48`).

핵심은 필터가 요청을 통과시키거나(성공) 컨트롤러 실행 전에 잘라내거나(실패) 둘 중 하나만 한다는 점이다. 컨트롤러는 "여기까지 왔다 = 이미 인증됨"을 전제로 쓸 수 있다.

### `@AuthMemberId`가 값을 얻는 지점 — ArgumentResolver

5a의 온보딩·스캔 컨트롤러는 `fun something(@AuthMemberId memberId: Long)`처럼 회원 PK를 파라미터로 받기만 했다. 그 값이 **어디서** 오는지가 여기서 닫힌다. `AuthMemberIdArgumentResolver.kt:17-24`:

```kotlin
override fun resolveArgument(
    parameter: MethodParameter,
    mavContainer: ModelAndViewContainer?,
    webRequest: NativeWebRequest,
    binderFactory: WebDataBinderFactory?,
): Long =
    webRequest.getAttribute(JwtAuthenticationFilter.MEMBER_ID_ATTRIBUTE, RequestAttributes.SCOPE_REQUEST) as? Long
        ?: throw AuthException(AuthErrorCode.INVALID_ACCESS_TOKEN)
```

- 스프링은 컨트롤러 메서드를 호출하기 직전, `@AuthMemberId`가 붙은 파라미터를 보고 이 리졸버에게 "이 값 채워줘"라고 위임한다(리졸버 등록은 `WebMvcAuthConfig.kt:15-18`에서 했다).
- `getAttribute(MEMBER_ID_ATTRIBUTE, ...)`: 흐름 A에서 **필터가 넣어둔** request attribute를 그대로 꺼낸다. 필터와 리졸버는 같은 상수 키(`"authMemberId"`)를 공유한다.
- `as? Long ?: throw ...`: 값이 없으면(필터를 안 거친 경로에서 실수로 `@AuthMemberId`를 쓴 경우) 401. 방어 코드다.

즉 **필터가 검증→저장, 리졸버가 꺼내서 주입**의 2단 릴레이다. 컨트롤러 코드에는 토큰이나 헤더가 전혀 등장하지 않는다 — 이 계층이 그 지저분함을 전부 흡수한다.

## 흐름 B — 재발급 (rotation) · `POST /api/v1/auth/refresh`

access 토큰은 만료가 30분(짧다)이다. 만료되면 FE는 refresh 토큰으로 이 엔드포인트를 불러 **두 토큰을 새로** 받아온다.

| 계층 | 파일 | 하는 일 |
|---|---|---|
| Controller | `app/api/.../auth/AuthController.kt:30-35` | `refresh(@RequestBody RefreshRequest)` → `refreshUseCase.refresh(request.refreshToken!!)` → `TokenResponse.from` → `BaseResponse.ok` |
| 요청/응답 DTO | `app/api/.../auth/TokenRequests.kt:6-23` | 입력 `{refreshToken}`(`@NotBlank`) / 출력 `{accessToken, refreshToken}` |
| UseCase | `application/client/.../auth/RefreshUseCase.kt:21-45` | `parseRefreshToken` → `store.consume(jti)`(원자적 소비=구 토큰 즉시 폐기) → 회원 존재 확인 → 새 refresh 발급·save + 새 access. 만료 시(`:22-29`)엔 Redis jti를 지운 뒤 예외 재throw = 강제 로그아웃 |
| 세션 저장 port/adapter | `core/member/.../RefreshTokenStore.kt`(port), `infra/persistence/.../auth/RefreshTokenRedisAdapter.kt:16-21`(Redis 구현) | `consume`=`getAndDelete`(회전 원자성), `save`(새 세션 등록) |

### rotation의 핵심 — 소비하고 새로 낸다

`RefreshUseCase.kt:21-45`:

```kotlin
fun refresh(refreshToken: String): RefreshResult {
    val parsed = try {
        tokenParser.parseRefreshToken(refreshToken)
    } catch (e: AuthException) {
        if (e.errorCode == AuthErrorCode.EXPIRED_REFRESH_TOKEN) {
            tokenParser.refreshTokenJtiOrNull(refreshToken)?.let { refreshTokenStore.delete(it) }
        }
        throw e
    }
    val memberId = refreshTokenStore.consume(parsed.jti)
        ?: throw AuthException(AuthErrorCode.INVALID_REFRESH_TOKEN)
    if (memberRepository.findById(memberId) == null) {
        throw AuthException(AuthErrorCode.INVALID_REFRESH_TOKEN)
    }
    val rotated = tokenIssuer.issueRefreshToken(memberId)
    refreshTokenStore.save(rotated.jti, memberId, properties.refreshTtl)
    return RefreshResult(
        accessToken = tokenIssuer.issueAccessToken(memberId, MemberRole.USER),
        refreshToken = rotated.token,
    )
}
```

- `parseRefreshToken`: 서명·만료·`token_type=REFRESH`를 검증하고 토큰 안의 `jti`(발급 때 심은 고유 ID)와 memberId를 꺼낸다.
- **만료 catch 블록**(`:24-28`): refresh가 만료됐으면 그 토큰의 jti를 최선껏 추출해(`refreshTokenJtiOrNull`) Redis 세션을 지우고 예외를 다시 throw한다. 결과적으로 그 세션은 더 못 쓴다 = **강제 로그아웃**. FE는 401을 받으면 저장한 토큰을 버리고 재로그인해야 한다.
- `store.consume(parsed.jti)`: Redis에서 jti를 **읽으면서 동시에 지운다**(getAndDelete, 한 연산). 저장돼 있지 않으면(=이미 회전됐거나 로그아웃된 토큰) null → `INVALID_REFRESH_TOKEN`. 이 "읽자마자 삭제"가 rotation의 안전장치다.
- `memberRepository.findById(memberId) == null`: 탈퇴한 회원의 잔여 토큰이면 거절. 회원이 없으면 잔여 세션 전부가 무력화된다.
- `issueRefreshToken` + `save`: 새 jti를 가진 refresh를 발급하고 Redis에 다시 등록한다(수명은 refresh-ttl로 재충전). 새 access도 함께 발급.

`consume`이 왜 **읽기+삭제 한 연산**이어야 하는지가 이 흐름의 심장이다. 만약 "읽고 나서 따로 삭제"였다면, 같은 refresh로 두 요청이 동시에 들어왔을 때 둘 다 읽기에 성공해 토큰이 두 벌 발급될 수 있다. `getAndDelete`는 하나만 값을 얻고 나머지는 null을 받아 거절되게 만든다.

> [!info] Redis — 이 흐름에서 새로 등장하는 인프라
> refresh 세션은 3단계에서 배운 MySQL이 아니라 **Redis**에 저장된다(`RefreshTokenRedisAdapter`, `application-*.yml`의 `spring.data.redis`). Redis는 메모리 기반 **키-값 저장소**다 — FE로 치면 `Map<string, value>`에 만료 시간이 붙은 것. 여기서 알아둘 성질 셋: ① 키(`auth:refresh:{jti}`) 하나에 값(memberId) 하나, ② **TTL**(time-to-live)을 주면 그 시간이 지나 자동 삭제되므로 refresh 만료 관리를 저장소가 대신해준다(`save(jti, memberId, ttl)`), ③ `consume`=`getAndDelete`는 **원자적**(읽기와 삭제 사이에 다른 요청이 끼어들 수 없음)이라 rotation 경합을 막는다. Redis 자체는 아직 개념 노트가 없어 여기 콜아웃으로만 소개한다 — 지금은 "TTL 붙는 키-값 저장소, 원자적 소비 가능" 정도만 알면 이 흐름을 읽는 데 충분하다. (2026-07-16 추가: 이제 Redis 개념 노트가 생겼다 — 왜 캐시/세션에 쓰나는 → [[21. 캐싱과 키-값 저장소 — 왜 캐시하나부터 kbap의 Redis 세션까지]].)

`RefreshTokenRedisAdapter.kt:12-21`이 port를 구현한 전부다:

```kotlin
override fun save(jti: String, memberId: Long, ttl: Duration) {
    redisTemplate.opsForValue().set(key(jti), memberId.toString(), ttl)
}
override fun consume(jti: String): Long? =
    redisTemplate.opsForValue().getAndDelete(key(jti))?.toLongOrNull()
override fun delete(jti: String) {
    redisTemplate.delete(key(jti))
}
```

- `save`: `set(키, 값, ttl)` — TTL을 넘기면 Redis가 그 시간 뒤 알아서 지운다. refresh 만료를 서버가 타이머로 관리할 필요가 없다.
- `consume`: `getAndDelete` — 앞서 말한 원자적 읽기+삭제.
- `delete`: 로그아웃·강제 폐기용 단순 삭제.

## 흐름 C — 로그아웃 · `POST /api/v1/auth/logout`

| 계층 | 파일 | 하는 일 |
|---|---|---|
| Controller | `app/api/.../auth/AuthController.kt:37-42` | `logout(@RequestBody(required=false) LogoutRequest?)` → `logoutUseCase.logout(request?.refreshToken)`. 바디가 없어도 200(멱등) |
| UseCase | `application/client/.../auth/LogoutUseCase.kt:11-17` | refresh가 없거나 파싱 불가면 no-op, 있으면 jti 추출해 `store.delete` — 이후 그 refresh로 재발급 불가 |
| 세션 저장 | `infra/persistence/.../auth/RefreshTokenRedisAdapter.kt:19-21` | `delete(key(jti))` — Redis 세션 제거 |

`LogoutUseCase.kt:11-17`:

```kotlin
fun logout(refreshToken: String?) {
    if (refreshToken.isNullOrBlank()) {
        return
    }
    val jti = tokenParser.refreshTokenJtiOrNull(refreshToken) ?: return
    refreshTokenStore.delete(jti)
}
```

- `isNullOrBlank()` → `return`: 토큰이 없으면 아무것도 안 하고 성공. FE가 이미 토큰을 잃어버린 상태에서 로그아웃을 눌러도 에러가 나지 않는다.
- `refreshTokenJtiOrNull(refreshToken) ?: return`: 서명이 깨졌거나 조작된 토큰이면 jti를 못 얻어 그냥 통과. 이미 무효한 세션이니 지울 것도 없다.
- `refreshTokenStore.delete(jti)`: 정상 토큰이면 해당 Redis 세션을 지운다. 지운 뒤엔 그 refresh로 흐름 B(재발급)를 해도 `consume`이 null을 받아 거절된다.

**멱등**(idempotent)이 핵심이다 — 몇 번을 불러도 결과(세션 없음)가 같고 에러가 안 난다. access 토큰은 여기서 건드리지 않는다(stateless라 서버가 무효화할 수단이 없다). 대신 access는 수명이 30분으로 짧아 자연 만료된다. 그래서 로그아웃은 "폐기 가능한 refresh만 즉시 죽이고, access는 만료를 기다린다"는 절충이다. 이 비대칭(access=짧게 stateless, refresh=Redis로 폐기 가능)이 두 토큰을 쓰는 이유이며, 자세한 배경은 [[쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가]]에 있다.

## 계층 경계마다 "여기서 모듈이 바뀌는 이유"

이 흐름은 4단계에서 배운 [[10. 클린 아키텍처와 ports & adapters — 도메인을 순수하게 지키기]]·[[11. 모듈러 모놀리스와 DDD — 경계를 코드로 지키기]]의 규칙을 그대로 밟는다. 경계가 왜 거기 그어졌는지만 짚는다.

- **필터·리졸버는 `app/api` 모듈에만 있다.** `JwtAuthenticationFilter`·`AuthMemberIdArgumentResolver`·`WebMvcAuthConfig`는 전부 `app/api/.../common/auth/`에 산다. 이들은 서블릿(`HttpServletRequest`)·스프링 MVC에 묶인 **웹 계층 관심사**라, 웹을 모르는 하위 모듈(application·core)로 내려보내면 안 된다. FE로 치면 라우터 가드가 도메인 로직 폴더가 아니라 라우팅 폴더에 있어야 하는 것과 같다.
- **토큰 검증 로직(`TokenParser`)은 `application/client`에 있다.** 필터는 "언제 검증할지"(매 요청)를 알고, 파서는 "어떻게 검증할지"(HS256 서명·만료·클레임)를 안다. 웹 계층은 검증 **방법**을 몰라도 되게, `TokenParser`라는 재사용 가능한 부품으로 분리했다. 필터는 이 부품을 [[5. 의존성 주입(DI)과 계층 구조 — 코드를 어떻게 나누나|생성자 주입]]으로 받는다(`WebMvcAuthConfig.kt:12-13` → 필터·리졸버로 전달).
- **`RefreshTokenStore`는 port가 `core/member`, 구현이 `infra/persistence`에 있다.** UseCase(`RefreshUseCase`·`LogoutUseCase`)는 `core/member`의 `RefreshTokenStore` **인터페이스**에만 의존한다(save/consume/delete 세 메서드). "Redis"라는 단어는 UseCase 어디에도 없다. 실제 Redis 코드는 `infra/persistence/.../auth/RefreshTokenRedisAdapter`에 갇혀 있고, 나중에 저장소를 바꿔도 UseCase는 그대로다. 이게 4단계 ports & adapters의 핵심이고, [[13. 온보딩 프로필 저장 흐름 — 요청이 DB에 닿기까지]]에서 본 `MemberRepository`(port)↔JPA(adapter)와 정확히 같은 패턴이다 — 저장 기술만 MySQL/JPA 대신 Redis일 뿐.
- **필터·리졸버·필터등록 조립은 `@Configuration`/`@Bean`이 한다.** `WebMvcAuthConfig`가 `TokenParser`를 주입받아 필터·리졸버를 만들어 스프링에 등록한다. 우리가 `new JwtAuthenticationFilter(...)`를 직접 부르는 곳은 없다 → [[4. IoC 컨테이너와 Bean — 부품을 직접 만들지 않는다]].

> [!note] 세 UseCase에 `@Transactional`이 없다
> 5a 온보딩·스캔 UseCase에는 `@Transactional`이 붙어 있었지만 `RefreshUseCase`·`LogoutUseCase`엔 `@Service`만 있고 트랜잭션 애노테이션이 없다. 세션 저장이 MySQL이 아니라 **Redis**(RDB 트랜잭션 경계 밖)이고, refresh 재발급은 여러 테이블을 한 묶음으로 커밋/롤백할 필요가 없기 때문이다. "모든 UseCase가 `@Transactional`인 것은 아니다" — 트랜잭션은 여러 DB 변경을 원자적으로 묶어야 할 때만 쓴다(→ [[6. 설정과 프로필, 트랜잭션 첫걸음]]).

## 요청/응답 JSON 예시

**재발급 — `POST /api/v1/auth/refresh`**

요청:
```json
{ "refreshToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI1IiwidG9rZW5fdHlwZSI6IlJFRlJFU0giLCJqdGkiOiJ..." }
```
응답 (`BaseResponse`로 감싸, 두 토큰을 **모두** 새로):
```json
{
  "success": true,
  "payload": { "accessToken": "eyJ...새 access...", "refreshToken": "eyJ...새 refresh..." },
  "message": null
}
```
구 refreshToken은 이 시점에 이미 폐기되어 재사용하면 401(`INVALID_REFRESH_TOKEN`)이다.

**로그아웃 — `POST /api/v1/auth/logout`**

요청(바디는 선택 — 없어도 200):
```json
{ "refreshToken": "eyJ...refresh..." }
```
응답:
```json
{ "success": true, "payload": {}, "message": null }
```

**매 요청 인증(흐름 A)** 은 별도 엔드포인트가 아니다. FE는 보호된 API를 부를 때마다 헤더 `Authorization: Bearer {accessToken}`만 실어 보내면 된다. 필터가 통과시키면 정상 응답, 만료면:
```json
{ "success": false, "payload": null, "message": "만료된 인증 토큰입니다" }
```
(HTTP 401. `AuthErrorCode.kt:11-14`의 access/refresh 4종 메시지를 필터·파서·재발급이 공유한다.)

## 관련 테스트가 보장하는 것

- **`app/api/.../common/auth/JwtAuthenticationFilterTest.kt`** — 정상 Bearer 토큰이면 memberId·role이 request attribute로 저장되고 체인이 진행됨(200), 헤더 없음·`Bearer` 아닌 접두·위조 서명·만료·access 자리에 refresh를 낸 경우(`token_type` 불일치)는 전부 401이고 **체인이 진행되지 않음**(`chain.request.shouldBeNull()`). 즉 "인증 실패 시 컨트롤러가 절대 안 돈다"를 못박는다.
- **`application/client/.../auth/RefreshUseCaseTest.kt`** — 정상 rotation(access·refresh 둘 다 새로, 구 jti 폐기·새 jti가 전체 수명으로 저장), 회전된 구 토큰 재사용 거절, 저장소에 없는/조작된 토큰 거절, 탈퇴 회원 토큰 거절, **만료 refresh는 남은 세션까지 폐기하며 강제 로그아웃**을 검증.
- **`application/client/.../auth/LogoutUseCaseTest.kt`** — 정상 세션 폐기, null·조작 토큰은 no-op(`delete` 호출 0회), 이미 로그아웃한 토큰 재로그아웃도 멱등.
- **`infra/persistence/.../auth/RefreshTokenRedisAdapterTest.kt`** — Testcontainers로 진짜 Redis를 띄워 save 후 값 복원·TTL 설정·`consume`의 원자적 읽기+삭제(두 번째 consume은 null)·delete·회원별 다중 기기 세션 공존을 검증. rotation 경합 방어가 실제 Redis에서 성립하는지까지 확인.

모두 Kotest `BehaviorSpec`(given/when/then 한국어)이다 → [[12. SDD와 TDD — 스펙과 테스트로 개발하기]].

| 상황 | 무슨 일이 일어나나 | 근거 |

| access 만료 | 필터가 401(`만료된 인증 토큰`), 컨트롤러 실행 안 됨 | `JwtAuthenticationFilter.kt:30-32`, `TokenParser.kt:60-64` |

| access 만료 후 refresh 제출 | 구 refresh를 `consume`(원자적 폐기) → access·refresh 둘 다 새로 발급 | `RefreshUseCase.kt:31-44` |

| 로그아웃 | refresh jti 추출해 Redis 세션 delete(멱등) | `LogoutUseCase.kt:11-17` |

## 체크리스트

- [ ] 필터는 컨트롤러 **전에** 돌아, 인증 실패면 컨트롤러를 아예 실행시키지 않는다 (`doFilter`를 안 부름)
- [ ] `@AuthMemberId`의 값 = 필터가 저장한 request attribute를 리졸버가 꺼낸 것 (2단 릴레이)
- [ ] login·refresh·logout은 비보호 경로 (문 앞이라 토큰이 아직 없음)
- [ ] rotation = `consume`(원자적 읽기+삭제)로 구 토큰 즉시 폐기 후 새 토큰 발급
- [ ] refresh 세션은 MySQL 아닌 **Redis**에 jti→memberId + TTL로 저장 (port는 `core/member`, 구현만 `infra/persistence`)
- [ ] access는 stateless라 로그아웃해도 즉시 무효화 못 함 → 짧은 수명(30분)으로 자연 만료
