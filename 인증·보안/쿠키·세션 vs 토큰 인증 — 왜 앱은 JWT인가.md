# 쿠키·세션 vs 토큰 인증 — 왜 앱은 JWT인가

> 맥락: K-Bap 저장소 시드의 Q3 — "cookie/session은 왜 네이티브 앱에 없나?"가 출발점.
> 목표: 웹의 세션 인증과 앱의 토큰 인증이 **각자 왜 그 모양인지**를 원리로 이해하기.

---

## 0. 한 줄 요약
**쿠키·세션 인증은 "브라우저라는 인프라"에 기생하는 방식이고, 토큰(JWT) 인증은 그 인프라 없이 클라이언트가 증명을 직접 들고 다니는 방식이다.** 네이티브 앱에는 브라우저 인프라(origin, 쿠키 자동첨부, SOP)가 없으므로 토큰이 표준이 됐다. K-Bap이 JWT로 가는 건 취향이 아니라 **구조적 필연.**

---

## 1. 웹의 방식 — 쿠키 + 서버 세션

동작 원리:
```
① 로그인 성공 → 서버가 세션 저장소에 {sessionId: 유저정보} 기록
② 응답 헤더: Set-Cookie: SESSIONID=abc123 (HttpOnly)
③ 이후 브라우저가 같은 사이트 요청마다 쿠키를 자동으로 실어 보냄
④ 서버는 sessionId로 저장소를 조회해 "누구인지" 복원
```
- **상태는 서버에 있다** (stateful). 클라이언트는 번호표(sessionId)만 듦.
- 핵심 기반: **브라우저가 쿠키를 자동 관리·자동 첨부**한다는 것. 개발자는 아무것도 안 해도 됨.

> 비유: **호텔 클로크룸.** 코트(내 정보)는 호텔(서버)이 보관하고 나는 **번호표(sessionId)** 만 받는다. 번호표 자체엔 아무 정보가 없어서 주워도 코트 주인이 누군지 모른다 — 대신 호텔은 보관대를 계속 운영해야 한다.

## 2. 앱·API의 방식 — 토큰 (JWT)

동작 원리:
```
① 로그인 성공 → 서버가 서명한 JWT 발급 (유저정보가 토큰 안에 들어있음)
② 클라이언트가 토큰을 직접 보관 (메모리/SecureStore)
③ 요청마다 클라이언트가 명시적으로 첨부: Authorization: Bearer <JWT>
④ 서버는 저장소 조회 없이 서명만 검증해 "누구인지" 판단
```
- **상태는 클라이언트에 있다** (서버는 stateless). 서버는 기억하지 않고 검증만 한다.

> 비유: **위조 방지 도장이 찍힌 출입증.** 내 신원이 출입증에 적혀 있고, 경비(서버)는 명부를 뒤지지 않고 도장(서명)만 확인한다. 명부 운영이 필요 없어 어느 문(서버 인스턴스)에서든 통한다 — 대신 **한번 발급한 출입증은 회수하기 어렵다.**

K-Bap의 ③번이 실제 코드로 이미 준비돼 있다:
```ts
// api/client.ts — JWT injection skeleton
let authToken: string | null = null;
export function setAuthToken(token: string | null) { authToken = token; }
// ...
if (authToken) headers.Authorization = `Bearer ${authToken}`;
```
> 브라우저가 쿠키를 자동으로 붙여주던 일을, 앱에서는 **이 두 줄이 수동으로** 한다. 이게 두 방식의 차이 전부를 압축한 코드다.

## 3. 정면 비교

| | **쿠키 + 세션** | **토큰 (JWT)** |
|---|---|---|
| 상태 위치 | 서버 (세션 저장소 필요) | 클라이언트 (서버 무상태) |
| 첨부 방식 | 브라우저가 **자동** | 코드가 **수동** (`Authorization` 헤더) |
| 수평 확장 | 세션 공유 필요 (Redis 등) | 서명 키만 있으면 어느 서버든 검증 |
| **즉시 폐기(로그아웃)** | ✅ 서버에서 세션 삭제하면 끝 | ⚠️ **어려움** — 만료 전까지 유효 (블랙리스트/짧은 만료+리프레시로 보완) |
| 주요 취약점 | **CSRF** (자동 첨부를 악용) | **XSS·탈취** (토큰을 읽히면 끝) |
| 어울리는 곳 | 같은 도메인의 전통 웹 | **모바일 앱, SPA, 서드파티 API, MSA** |

`★ 취약점이 갈리는 이유 ─────────────────────`
쿠키의 약점 CSRF는 "**자동 첨부**" 때문이다 — 악성 사이트가 내 브라우저로 요청을 쏘면 쿠키가 저절로 실린다.
토큰의 약점 탈취는 "**수동 보관**" 때문이다 — 자동 첨부가 없어 CSRF는 원천 차단되지만, 코드가 접근 가능한 곳에
두면 XSS로 읽힌다. **방식의 장점이 곧 그 방식의 공격면이다.** 그래서 저장 위치가 중요해진다
→ [[클라이언트 저장소 — AsyncStorage·SecureStore·메모리 (K-Bap 실전)|저장소 노트]]의 "액세스는 메모리, 리프레시는 SecureStore".
`──────────────────────────────────────`

## 4. 그래서 — cookie/session은 왜 네이티브 앱에 없나 (시드 Q3의 답)

쿠키·세션이 성립하려면 브라우저가 제공하던 4가지가 필요한데, 네이티브 앱엔 다 없다:

1. **쿠키 저장소 + 자동 첨부**: OS HTTP 스택(iOS NSURLSession)에 쿠키 기능이 *있긴* 하지만, RN에서 이를 다룰 표준 API가 없고 플랫폼마다 동작이 달라 **신뢰할 수 없다.** "있는데 못 쓴다"가 정확.
2. **origin 개념**: 쿠키의 격리·전송 규칙(도메인, SameSite)은 전부 origin 기준인데, 앱은 origin이 없다.
3. **SOP(동일 출처 정책)**: 쿠키 보안 모델의 전제. 앱엔 해당 없음.
4. **CSRF 방어 모델**: SameSite·CSRF 토큰 등 쿠키 생태계의 방어 장치도 전부 브라우저 전제.

→ 결국 앱은 "요청에 뭘 실을지"를 **코드가 100% 직접 결정**해야 하고, 그 표준 형태가 `Authorization: Bearer`다. **K-Bap이 JWT로 가는 이유 = 앱이라서.** (웹도 SPA/API 시대가 되며 같은 방향으로 이동했다.)

> [!note] 흑백이 아니다 — 하이브리드 현실
> 요즘 웹은 "JWT를 HttpOnly 쿠키에 담아" 두 방식을 섞기도 한다(토큰의 무상태 + 쿠키의 XSS 방어). 또 토큰 진영도 폐기 문제를 **짧은 액세스 토큰 + 리프레시 토큰 회전**(RFC 9700, [[OAuth 2.0과 OIDC — 소셜 로그인의 원리|OAuth 노트]] §6)으로 보완한다. "세션 vs 토큰"은 종교 전쟁이 아니라 **인프라 전제에 따른 선택.**

---

## 5. K-Bap 설계에 대입 (미래 구조)

```
소셜 로그인 성공 (credentials.ts — 크리덴셜 SecureStore 파킹)
  → BE 교환: POST /auth/{provider} → { jwt }        ← 계약 확정 대기 중인 스텁
  → setAuthToken(jwt)  — 액세스 토큰은 메모리
  → (도입 시) 리프레시 토큰은 SecureStore
  → 이후 모든 요청: Authorization: Bearer 자동 주입 (client.ts)
```
- 로그아웃 = `setAuthToken(null)` + SecureStore 청소 + (서버에 리프레시 폐기 요청).
- JWT 즉시 폐기의 어려움(§3) 때문에 액세스 토큰 만료는 짧게 잡는 게 정석.

---

## 6. 용어집
- **세션(session)**: 서버가 보관하는 로그인 상태. 클라이언트는 sessionId만 듦.
- **Set-Cookie / 자동 첨부**: 서버가 쿠키를 심고, 브라우저가 매 요청 자동으로 실어 보내는 메커니즘.
- **HttpOnly**: JS(`document.cookie`)로 못 읽는 쿠키 속성 — XSS 방어.
- **stateful / stateless**: 서버가 상태를 기억함 / 기억 안 하고 검증만 함.
- **CSRF**: 쿠키 자동 첨부를 악용해 사용자의 의도치 않은 요청을 위조하는 공격.
- **SOP / origin / SameSite**: 브라우저 보안 모델의 3형제. 전부 앱엔 없는 개념.
- **Bearer 토큰**: "소지자(bearer)가 곧 권한자" — 들고 있으면 인정되는 토큰. 그래서 보관이 중요.
- **토큰 폐기(revocation)**: 발급된 토큰을 무효화하는 것. JWT의 구조적 약점.

---

## 7. 다음에 빠른 재현 체크리스트
1. 세션 = 번호표(상태는 서버), 토큰 = 서명된 출입증(상태는 클라이언트).
2. 앱에 쿠키·세션이 없는 이유 = **브라우저 인프라(자동첨부·origin·SOP) 부재.** 앱은 헤더를 수동 주입.
3. 약점 교환: 쿠키=CSRF(자동 첨부 탓) ↔ 토큰=탈취(수동 보관 탓). **장점이 곧 공격면.**
4. JWT는 즉시 폐기가 어렵다 → 짧은 액세스 + 리프레시 회전으로 보완.
5. 토큰 저장: 액세스=메모리, 리프레시=SecureStore ([[클라이언트 저장소 — AsyncStorage·SecureStore·메모리 (K-Bap 실전)|저장소 노트]]).

> [!note] §3 "짧은 액세스 + 리프레시 회전"의 미구현 절반 — 재사용 탐지 (2026-08-27 추가)
> 교과서적 rotation 에는 짝이 하나 더 있다. 회전돼 죽은 옛 refresh 가 **다시 제출되면** 탈취로 보고 그 세션 계보 전체를 폐기하는 **재사용 탐지(reuse detection)** 다. kbap 에는 없다 — `GETDEL` 로 옛 토큰은 죽지만, 재사용 시 계보를 끊지 않고 `AUTH-005` 401 만 준다(`AuthService.kt:56-57`). 결과적으로 탈취를 막지는 못하되 조용히 영구화되지도 않는다(정상 사용자가 다음 갱신에서 튕겨 나가는 게 이상 신호가 된다). 이 선택을 기록한 ADR·스펙 문장은 레포에 없다 → [[17. > [!note] JWT 를 "너 누구냐" 말고 "이거 해도 되냐"에 쓰면 — 스캔 티켓 (2026-08-27 추가)
> 이 노트는 JWT 를 **인증** 수단으로만 다뤘다. kbap 에는 같은 기술을 **자원 사용권**으로 쓰는 두 번째 용례가 있다 — 스캔 티켓(`X-Scan-Ticket`). 서명 알고리즘도 **비밀 키도 access 토큰과 같고**, 다른 건 세 가지다: `token_type: SCAN_TICKET` 클레임(이게 없으면 access 토큰을 티켓 자리에 넣어도 통과한다), 5분 수명, 그리고 **`jti`(토큰 한 장의 고유 번호)** — 이 번호가 그대로 Redis 예약 키가 되어 같은 티켓의 동시 사용을 막는다.
> 실패 응답이 **401 이 아니라 400** 인 것도 §3 의 관점을 한 칸 넓혀준다 — 티켓을 검사하는 시점엔 access 토큰이 이미 통과해서 **누군지는 안다.** 잘못된 건 신원이 아니라 함께 보낸 파라미터다. 앱 대응도 갈린다: 401 은 토큰 갱신, 400 `SCAN-007` 은 **티켓 재발급 후 재시도**. → [[20. 스캔 v2와 사용량 티켓 — 서버 OCR·무료 한도·중복 요청 막기]] §5

> [!note] Redis 쪽에서 본 같은 이야기 — 그리고 그건 캐시가 아니다 (2026-08-27 추가)
> 위 2026-08-26 콜아웃이 "refresh 를 어디에 두나" 를 **포트 계약**(`RefreshTokenStore`) 쪽에서 봤다면, 저장소 쪽에서 본 정본은 [[29. 캐싱과 키-값 저장소 — kbap이 Redis를 쓰는 두 가지 방식]] 이다. 핵심은 **Redis 를 쓴다고 캐시가 아니라는 것** — 캐시의 정의는 "원본이 따로 있는 사본" 인데, 이 refresh 키가 날아가면 다시 채울 원본이 없어 전 사용자가 강제 로그아웃된다. §3 의 "JWT 는 즉시 폐기가 어렵다" 를 푸는 대가가 바로 이것이다: **폐기 능력을 얻으려면 어딘가에 잃으면 안 되는 상태를 둬야 한다.** 위 표(§ 수평 확장 행)의 "세션 공유 필요 (Redis 등)" 를 JWT 가 완전히 없앤 게 아니라, **access 에서만 없애고 refresh 로 옮긴 것**에 가깝다.
