# OAuth 2.0과 OIDC — 소셜 로그인의 원리

> 맥락: "구글로 로그인" 버튼 뒤에서 무슨 일이 일어나는지, 개념부터 보안 메커니즘까지.
> 목표: 등장인물·토큰·흐름을 이해하고, **왜 PKCE/state/nonce 같은 게 덕지덕지 붙었는지**까지 납득하기.

---

## 0. 한 줄 요약
**OAuth 2.0은 "비밀번호를 안 주고 권한만 위임"하는 인가(authorization) 프로토콜이고, OIDC(OpenID Connect)는 그 위에 "너 누구야?"를 얹은 인증(authentication) 층이다.** 우리가 아는 "소셜 로그인"의 정체는 OAuth가 아니라 **OIDC**. 핵심 흐름은 **인가 코드 플로우**(코드 → 토큰 2단계 교환)이고, state·PKCE·nonce는 각각 다른 공격을 막는 자물쇠다.

---

## 1. 왜 태어났나 — 비밀번호 공유 안티패턴

OAuth 이전(2000년대): "Gmail 주소록으로 친구를 찾아드려요! **Gmail 아이디/비번을 입력하세요**" — 실제로 이렇게 했다. 문제:
- 그 서비스가 내 비밀번호로 **뭐든** 할 수 있음 (메일 삭제, 비번 변경…)
- 서비스가 해킹되면 내 구글 계정도 끝
- 권한 회수 = 비밀번호 변경뿐 (다른 서비스 연동도 다 끊김)

> 비유: **호텔 발렛 키.** 주차요원에게 마스터 키(비밀번호)를 주는 게 아니라, **시동·주차만 되는 발렛 키(액세스 토큰)** 를 준다. 트렁크·글로브박스는 안 열리고, 잃어버려도 그 키만 무효화하면 된다.

OAuth 2.0 = 이 "발렛 키 발급 절차"의 표준 (RFC 6749, 2012).

## 2. 등장인물 4명

| 역할 | 정체 | 예시 |
|---|---|---|
| **Resource Owner** | 자원의 주인 = **사용자** | 나 |
| **Client** | 권한을 빌리려는 **내 서비스** | K-Bap 앱/서버 |
| **Authorization Server** | 인증하고 토큰을 **발급**하는 곳 | accounts.google.com, appleid.apple.com |
| **Resource Server** | 실제 자원(API)이 있는 곳 | Google 프로필 API |

> 소셜 로그인에선 Authorization Server와 Resource Server가 둘 다 구글/애플이라 하나처럼 보이지만, 역할은 분리돼 있다.

## 3. OAuth vs OIDC — 인가와 인증은 다르다 (제일 중요한 구분)

`★ 핵심 구분 ─────────────────────────────`
- **인가(authorization)** = "이 앱이 내 주소록을 **읽어도 된다**" — 권한의 문제. OAuth 2.0의 본업.
- **인증(authentication)** = "지금 이 사람이 **누구인가**" — 신원의 문제. OAuth의 본업이 아님!
OAuth의 액세스 토큰은 "권한 증서"지 "신분증"이 아니다. 토큰만 보고 로그인 처리하면
**토큰 바꿔치기 공격**에 뚫린다(다른 앱에서 발급된 토큰을 들고 와도 구분 못 함).
그래서 "OAuth 위에 신분증(ID 토큰)을 표준으로 얹은 것"이 **OIDC**다.
`──────────────────────────────────────`

| | OAuth 2.0 | OIDC (= OAuth 2.0 + 신원층) |
|---|---|---|
| 답하는 질문 | 뭘 해도 되나? | + **누구인가?** |
| 핵심 산출물 | 액세스 토큰 | + **ID 토큰(JWT)** |
| scope | `contacts.read` 등 | + `openid profile email` |
| 소셜 로그인 | (원래 용도 아님) | ✅ **이게 소셜 로그인** |

## 4. 토큰 3형제

| 토큰 | 용도 | 형태 | 수명 |
|---|---|---|---|
| **액세스 토큰** | API 호출용 "발렛 키" | 불투명 문자열 or JWT | 짧게 (분~시간) |
| **리프레시 토큰** | 액세스 토큰 재발급용 | 불투명 문자열 | 길게 (일~월) |
| **ID 토큰** (OIDC) | "이 사람 누구" **신분증** | **항상 JWT** | 짧게 |

### JWT = 서명된 신분증
`header.payload.signature` 세 부분을 base64url로 이어붙인 것:
```
헤더    { "alg": "RS256", "kid": "어떤 키로 서명했나" }
페이로드 { "iss": "https://accounts.google.com",  ← 발급자
          "sub": "10769150350006150715113082367", ← 유저 고유 ID (불변!)
          "aud": "내앱클라이언트ID", "exp": 1736300000,
          "email": "...", "name": "...", "nonce": "..." }
서명    = 발급자의 개인키로 서명 (위조하면 서명이 안 맞음)
```
- **`sub`가 유저의 진짜 기본키.** 이메일은 바뀔 수 있으니 DB엔 `(iss, sub)`로 유저를 식별하는 게 정석.

## 5. 핵심 흐름 — 인가 코드 플로우 (Authorization Code Flow)

"구글로 로그인" 클릭부터 로그인 완료까지:

```
① 내 앱 → 구글 로그인 페이지로 보냄 (브라우저 리다이렉트)
   ?client_id=...&redirect_uri=...&scope=openid email
   &state=랜덤A&nonce=랜덤B&code_challenge=해시C     ← 자물쇠 3개 장착
② 사용자가 구글에서 로그인 + "이 앱에 이메일 제공 동의"
③ 구글 → 내 redirect_uri로 돌려보냄: ?code=인가코드&state=랜덤A
④ 내 서버 → 구글에 뒷채널로 직접 요청:
   code + client_secret(내 앱 증명) + code_verifier(자물쇠C 열쇠)
⑤ 구글 → 토큰 발급: { access_token, id_token, refresh_token }
⑥ 내 서버가 id_token 서명·클레임 검증 → 세션/자체 토큰 발급 → 로그인 완료
```

`★ 왜 "코드"를 거치나 — 앞채널 vs 뒷채널 ─────────`
- **앞채널(front channel)** = 브라우저 리다이렉트 경로. 주소창·히스토리·로그에 노출됨 → **위험 지대.**
- **뒷채널(back channel)** = 내 서버 ↔ 구글 서버 직통 HTTPS → 안전 지대.
토큰을 앞채널로 바로 주면(과거 implicit flow) 훔쳐보기 딱 좋다. 그래서
**앞채널로는 "1회용 교환권(코드)"만** 보내고, **진짜 토큰은 뒷채널에서** 코드+비밀을 내고 받는다.
코드가 유출돼도 client_secret/code_verifier 없이는 못 바꾼다.
`──────────────────────────────────────`

## 6. 보안 메커니즘 — 자물쇠마다 막는 공격이 다르다

| 장치 | 막는 공격 | 원리 |
|---|---|---|
| **state** | CSRF (공격자가 만든 응답을 내 세션에 꽂기) | ①에서 보낸 랜덤값이 ③에 그대로 돌아왔는지 확인. 다르면 내가 시작한 흐름이 아님 |
| **PKCE** | 인가 코드 가로채기 | ①에서 `code_challenge`(해시)를 맡기고, ④에서 원본 `code_verifier`를 제출 — 코드를 훔쳐도 원본 없인 교환 불가 |
| **nonce** | ID 토큰 재사용(리플레이) | ①의 랜덤값이 ID 토큰 안에 박혀 돌아옴. 예전 토큰 재제출 차단 |
| **redirect URI 정확 일치** | 코드를 공격자 주소로 배달 | 사전 등록한 URI와 **글자 단위 일치**만 허용 (와일드카드 금지) |

> [!important] 2025년 이후의 상식 (RFC 9700, Best Current Practice)
> - **Implicit flow(토큰을 앞채널로 직접) · 비밀번호 그랜트(ROPC) → 공식 폐기 권고.**
> - **PKCE는 모바일뿐 아니라 모든 클라이언트에 권장** (OAuth 2.1에선 사실상 의무).
> - 리프레시 토큰은 **사용할 때마다 회전(rotation)** + 재사용 감지 시 일가족 전부 폐기.
> - 왜 PKCE가 특히 모바일에서 필수였나: 앱은 client_secret을 숨길 곳이 없고(디컴파일하면 끝),
>   커스텀 URL 스킴은 악성 앱이 가로챌 수 있어서 → 코드만 훔치면 끝이었기 때문. PKCE가 그 구멍을 막음.

## 7. ID 토큰 검증 — 서버가 하는 5가지 체크

ID 토큰을 "받았다"고 끝이 아니다. **검증해야 신분증이다:**

1. **서명**: 발급자의 공개키(**JWKS** 엔드포인트에서 `kid`로 찾음)로 서명 확인 → 위조 차단
2. **`iss`**: 발급자가 기대한 곳인가 (`https://accounts.google.com` / `https://appleid.apple.com`)
3. **`aud`**: 청중이 **내 client_id**인가 → 남의 앱용 토큰 바꿔치기 차단
4. **`exp`**: 만료 안 지났나
5. **`nonce`**: 내가 ①에서 보낸 값인가 → 리플레이 차단

> JWKS(JSON Web Key Set) = 발급자가 공개키들을 게시하는 URL. 키는 주기적으로 회전되므로 `kid`(키 ID)로 맞는 키를 골라 쓴다. 검증은 직접 구현하지 말고 검증된 라이브러리 사용이 정석.

## 8. 용어집
- **인가(authorization) / 인증(authentication)**: 권한 위임 / 신원 확인. OAuth는 전자, OIDC가 후자를 추가.
- **grant(그랜트)**: 토큰을 얻는 방법의 종류. 표준은 **인가 코드 그랜트**(+PKCE).
- **scope**: 요청하는 권한 범위 (`openid email profile` …). 최소로 요청하는 게 원칙.
- **인가 코드**: 앞채널로 전달되는 1회용 교환권. 수명 초 단위.
- **앞채널/뒷채널**: 브라우저 경유(노출 위험) / 서버 간 직통(안전).
- **PKCE(픽시)**: 코드 가로채기 방지. verifier(원본)–challenge(해시) 쌍.
- **state / nonce**: CSRF 방지 / ID 토큰 리플레이 방지 랜덤값.
- **JWT / JWKS / kid**: 서명된 토큰 형식 / 공개키 게시소 / 키 식별자.
- **`sub`**: 발급자 내 유저 고유 불변 ID. DB 유저 식별은 `(iss, sub)`로.
- **RFC 6749 / RFC 9700**: OAuth 2.0 원본 스펙 / 2025 보안 모범사례(BCP).

---

## 9. 다음에 빠른 재현 체크리스트
1. 소셜 로그인 = OAuth가 아니라 **OIDC** (액세스 토큰은 신분증이 아니다).
2. 흐름은 **인가 코드 플로우**: 앞채널엔 코드만, 토큰은 뒷채널에서.
3. 자물쇠 암기: **state=CSRF, PKCE=코드 가로채기, nonce=리플레이.**
4. ID 토큰은 **5체크**(서명·iss·aud·exp·nonce) 후에만 믿는다.
5. 유저 식별은 이메일이 아니라 **`(iss, sub)`**.
6. implicit flow·비밀번호 그랜트는 죽은 패턴. PKCE는 이제 어디서나.

> 디버깅 프록시(Proxyman)로 앱 트래픽을 MITM하면 `Authorization: Bearer …`와 ID 토큰이 **평문 그대로** 보인다 — 학습·디버깅엔 최고지만, 뒤집으면 **"HTTPS는 신뢰된 CA를 전제로만 안전하다"** 는 뜻이다(사용자가 악성 루트 CA를 신뢰하면 그 순간 끝). Bearer 토큰이 왜 짧은 수명·회전이 필요한지의 실물 근거 → [[프록시와 MITM 디버깅 (Proxyman)]]

> [!note] OIDC 검증을 끝낸 다음이 더 있다 — 왜 자체 토큰으로 갈아타나 (2026-08-27 추가)
> 이 노트는 "ID 토큰을 어떻게 검증하나"까지 다룬다. 그런데 kbap 은 **검증에 성공한 그 토큰을 계속 쓰지 않는다.** 옛 설계(KB-109)가 실제로 매 요청 Firebase ID 토큰을 검증하는 방식이었고 교체됐다. 이유는 세 가지 — ① ID 토큰은 "구글 계정 X 의 소유자"만 증명하지 **우리 회원 #42**를 증명하지 않아 매 요청 uid→memberId 조회가 붙는다, ② 수명을 구글이 정한다(1시간 고정), ③ 특정 사용자를 강제 로그아웃시킬 수단이 없다. 그래서 **OIDC 검증은 로그인 순간 딱 한 번**이고 이후 세션은 자체 access(30분)·refresh(14일)가 진다 → [[16. 소셜 로그인 흐름 — Firebase 토큰이 자체 JWT가 되기까지]] §2
